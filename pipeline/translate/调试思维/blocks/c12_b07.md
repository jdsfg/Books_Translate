#### 应用题

**Q1.** 一个 Python 应用在 macOS 上能工作，在 Linux 上失败，报错：`FileNotFoundError: [Errno 2] No such file or directory: 'data/Config.json'`。文件存在。利用本章知识，识别最可能的原因，并解释如何验证你的假设。

提示

macOS 文件系统 vs. Linux 文件系统——它们处理文件名的方式有什么不同？

**答案：** **最可能的原因：** 文件系统大小写敏感性。在 macOS（不区分大小写）上，`'data/Config.json'` 和 `'data/config.json'` 指向同一个文件。在 Linux（区分大小写）上，它们是不同文件。实际文件可能名为 `config.json`（小写），但代码引用的是 `Config.json`（大写 C）。

**验证：** SSH 到 Linux 机器并运行 `ls -la data/`。检查实际文件名。如果它是 `config.json`，但代码写的是 `Config.json`，那就是原因。

**修复：** 让代码中的大小写匹配实际文件名。到处使用 `config.json`。

**预防：** (1) 使用 linting 规则或 CI 检查来捕捉大小写不匹配。(2) 采用约定：所有文件名都使用小写加连字符（例如 `config.json`、`user-data.csv`）。(3) 考虑在本地测试 Linux（通过 Docker）后再推送。

**Q2.** 一个团队把他们的 Node.js 应用从传统服务器迁移到一个内存限制为 512MB 的 Kubernetes pod。应用在生产环境中间歇性崩溃，但在开发环境中从不崩溃（开发环境有 16GB RAM）。你会如何调试？

**答案：**

**第 1 步：确认这是内存问题。** 检查 pod 重启原因：`kubectl describe pod <name>`——查找 `OOMKilled`（Out Of Memory Killed）。如果存在，说明 pod 超过了 512MB 限制。

**第 2 步：在本地分析内存。** 用 512MB 内存限制在本地运行应用：`node --max-old-space-size=512 server.js`。这会模拟生产约束。尝试复现崩溃。

**第 3 步：理解内存画像。** 使用 `node --inspect` 配合 Chrome DevTools 在负载下获取堆快照。识别：(a) 基线内存使用量（是否已经接近 512MB？）。(b) 内存随时间增长（表明泄漏——回想第 10 章的慢性毒药谜题）。(c) 特定操作下的内存尖峰（大数据处理、文件上传）。

**第 4 步：调查具体原因：**

* **内存中的大型数据集：** 应用是否加载完整数据集？改用流式处理。
* **内存泄漏：** 内存是否无界增长？找到未释放的引用（事件监听器、缓存、闭包）。
* **依赖开销：** 某些库很消耗内存。检查哪些包消耗最多内存。

**第 5 步：合理调整解决方案。** 要么降低内存使用（正确修复），要么提高内存限制（快速权宜之计）。监控内存指标（第 10 章）以防未来意外。
