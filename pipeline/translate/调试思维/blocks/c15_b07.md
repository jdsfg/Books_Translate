#### 应用题

**Q1.** 一个 Web 应用的商品列表页需要 3 秒加载。你怀疑可能是数据库问题，但需要验证。请用性能分析和调试循环设计一次系统性调查。你会先测量什么，会形成哪些假设，又会如何缩小范围？

提示

思考这些层次：数据库查询时间、服务器处理时间、网络传输时间、客户端渲染时间。分别分析每一层。

**答案：**

**观察：** 页面加载需要 3 秒。让我按层拆解它。

**步骤 1：浏览器侧测量。** 打开 DevTools → Network 选项卡。API 请求用了多长时间？假设是 2.5 秒。那么 2.5s 是服务器端 + 网络，0.5s 是客户端渲染。服务器侧占主导。

**步骤 2：服务器侧性能分析。** 给服务器端点添加计时：

* 数据库查询：测量每个查询的时间
* 业务逻辑：测量处理时间
* 响应序列化：测量 JSON.stringify 时间

假设结果是：数据库查询 = 2.2s，业务逻辑 = 0.1s，序列化 = 0.2s。数据库占主导。

**步骤 3：数据库调查。** 正在运行多少次查询？如果是 200 次查询共 2.2s——N+1 问题。如果是 1 次查询耗时 2.2s——慢查询。

**如果是 N+1：** 用 JOIN 或 IN 子句批量查询。**如果是慢查询：** 对查询运行 EXPLAIN ANALYZE。它在使用索引吗？它在扫描整张表吗？它是不是返回了太多数据（在只需要少数字段时使用 SELECT *）？

**步骤 4：验证。** 优化后，再次测量。总页面加载时间是否低于 1 秒？如果没有，新的瓶颈就是下一个最大的组件——可能是大型 JSON 响应的序列化（减少负载大小），或者客户端渲染（虚拟化长列表）。

**Q2.** 你分析一个 Python 函数后发现，80% 的时间花在 `json.loads()` 上，用于解析一个来自外部 API 的 10MB JSON 响应。解析本身是必要的——你需要这些数据。在不改变外部 API 的前提下，可以用哪些策略提升性能？

**答案：**

有几种策略，从最简单到最复杂：

  1. **缓存解析结果。** 如果 API 数据不频繁变化，缓存解析后的 Python 对象。后续调用中，同时跳过 API 请求和解析。根据数据变化频率使用 TTL（time-to-live）。

  2. **使用更快的 JSON 解析器。** Python 内置的 `json` 模块是纯 Python。`orjson` 或 `ujson` 等库基于 C，解析速度快 3-10x。直接替换：`import orjson; data = orjson.loads(response_body)`。

  3. **只解析你需要的部分。** 如果你只使用 JSON 数据的 5%，可以用流式解析器（如 `ijson`）提取特定字段，而不解析完整的 10MB 结构。这会同时减少解析时间和内存使用。

  4. **请求更少数据。** 如果 API 支持过滤（用于特定字段、分页的查询参数），只请求你需要的数据，而不是完整的 10MB 响应。

  5. **异步解析。** 如果解析阻塞了 Web 请求，把它移到后台 worker。立即返回响应给用户，并异步处理数据。

  6. **压缩传输。** 请求 gzip/brotli 压缩（`Accept-Encoding: gzip`）。一个 10MB JSON 可能压缩到 1MB，从而减少网络传输时间。
