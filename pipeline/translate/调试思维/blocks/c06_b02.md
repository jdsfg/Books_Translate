### 6.3 构建 MRE：减法方法

构建 MRE 有两种方法：

**自顶向下（减法）：** 从完整系统开始，一次移除一些东西，直到得到仍然有 bug 的最小版本。

**自底向上（加法）：** 从零开始，一次添加一些东西，直到能够复现 bug。

当 bug 位于现有系统中时，减法方法通常更快：

**Step 1:** 制作项目副本（或一个 branch）。你接下来会做破坏性操作。

**Step 2:** 移除你能想到的、看起来与 bug 无关的最大块。删除整个 module，禁用一个 service，注释掉大块代码。测试——bug 仍然发生吗？

* 如果是：那一块无关。保持移除并继续。
* 如果否：那一块参与其中。把它放回去，并尝试移除其中更小的一部分。

**Step 3:** 重复，直到你无法在不让 bug 消失的情况下移除任何东西。

**Step 4:** 简化剩下的内容。用硬编码值替换复杂数据。用静态响应替换真实 API 调用。如果可能，把嵌套逻辑简化为平铺序列。

让我们走一个例子：

> **Bug:** 一个 API endpoint 在用某些输入调用时返回 500 error。

起点：一个完整的 Web 应用，包含 50 条 routes、一个 database、authentication、logging、caching 和 rate limiting。

  1. 移除除失败 route 之外的所有 routes。bug 仍然存在吗？是 → 49 条 routes 被排除。
  2. 移除 authentication middleware。bug 仍然存在吗？是 → auth 无关。
  3. 移除 logging。bug 仍然存在吗？是 → logging 无关。
  4. 移除 caching。bug 仍然存在吗？否！→ caching 参与其中。
  5. 放回缓存。移除限流。bug 仍然存在吗？是 → 限流无关。
  6. 现在：一条路由 + 缓存。把路由简化到最小——用硬编码数据替换数据库查询。bug 仍然存在吗？是 → 数据库无关。
  7. 简化缓存配置——使用默认值而不是自定义设置。bug 仍然存在吗？否！→ 自定义缓存设置是原因。
  8. MRE：一条路由 + 一个自定义缓存设置。缓存 TTL 被设置为 `0`，这会在缓存失效逻辑中导致 division-by-zero。

七步。从一个 50-route 应用开始；最终得到一个 10-line reproduction。原因在完整系统中不可见，但在 MRE 中显而易见。


### 6.4 构建 MRE：加法方法

当你怀疑某个特定组件但不确定它如何与其他部分交互时，加法方法最有效：

**Step 1:** 创建一个空白项目。真正的空。

**Step 2:** 添加触发 bug 所在区域所需的最少代码。只添加那个 function、那个 API call、那个 component。

**Step 3:** 运行它。bug 出现了吗？

* 如果是：你已经找到了 MRE。bug 在这个孤立组件中。
* 如果否：bug 还需要其他东西。添加下一个最可能的依赖。

**Step 4:** 重复，直到 bug 出现。你最后添加的东西（至少部分）负责。

加法方法对涉及组件间交互的 bug 尤其有用。每次添加都让你可以问：“添加这个会让 bug 出现吗？”
