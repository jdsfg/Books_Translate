#### 概念检查

**Q1.** 什么是 90/10 规则，为什么它意味着你应该先做性能分析再优化？

**答案：** 90/10 规则指出，大约 90% 的执行时间花在大约 10% 的代码上。这意味着绝大多数代码对性能的影响可以忽略不计。如果没有性能分析，你很可能会优化那 90% 已经很快的代码——浪费精力，并在没有改善性能的情况下增加复杂性。性能分析会识别真正关键的 10%，也就是优化真正有意义的地方。一个占总时间 1% 的函数提速 50%，总时间只节省 0.5%。一个占总时间 80% 的函数提速 50%，总时间节省 40%。

**Q2.** 解释 N+1 查询问题，以及为什么它会随着数据规模线性降低性能。

**答案：** N+1 查询问题发生在代码先执行一次查询获取 N 个条目的列表，然后为每个条目再执行 N 次额外查询来获取相关数据——总共 N+1 次查询。无论每次查询返回多少数据，每次查询都有固定开销（网络往返、连接处理、查询解析）。有 100 个条目：101 次查询 × 每次约 5ms = 约 500ms。有 10,000 个条目：10,001 次查询 × 约 5ms = 约 50 秒。性能会随着条目数量线性下降，因为每个条目都会增加一次查询的开销。修复方法：用一次批量查询替代 N 次单独查询，一次性获取所有相关数据。

**Q3.** CPU 受限和 I/O 受限的性能问题有什么区别？为什么这种区别会影响优化策略的选择？

提示

想想程序“慢”的时候正在做什么——CPU 是忙于计算，还是空闲等待？

**答案：** **CPU 受限：** CPU 利用率达到 100%，正在积极计算。程序慢是因为计算需要时间。优化：更好的算法（更低复杂度）、编译型代码、跨多个核心并行。**I/O 受限：** CPU 大多空闲，在等待 I/O 操作（磁盘读取、网络请求、数据库查询）完成。程序慢是因为它把时间花在等待上，而不是计算上。优化：批量处理 I/O 操作、异步/非阻塞 I/O、用缓存消除重复 I/O、连接池。

这种区别很重要，因为解决方案完全不同。增加更多 CPU 核心能帮助 CPU 受限问题，但对 I/O 受限问题没有帮助。添加缓存能帮助 I/O 受限问题，但对 CPU 受限问题没有帮助。使用错误的优化就是浪费精力。

**Q4.** 为什么“过早优化”被认为有害？边写边优化难道不是节省时间吗？

**答案：** 过早优化有害，因为：(1) **你还不知道哪里慢。** 90/10 规则意味着大多数代码不需要优化。优化很少运行的代码是在浪费精力。(2) **优化后的代码通常更难阅读和维护。** 一个优化算法可能是正确的，但很晦涩，使未来调试更困难。(3) **你可能优化错东西。** 没有测量，你依赖直觉，而直觉在性能问题上经常出错。(4) **优化会增加复杂性。** 缓存会带来缓存失效缺陷。并行会带来竞态。每一种优化都是速度和其他品质之间的权衡。

正确做法：先写清晰、正确的代码。在真实条件下测量。只优化测得的瓶颈。验证优化确实有帮助。
