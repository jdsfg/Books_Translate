#### 常见误解

**“我应该在写代码时就顺手优化，确保它足够快。”** 这就是 Donald Knuth 警告过的过早优化陷阱：“过早优化是万恶之源。” 在你知道实际哪里慢之前就优化，会导致代码变复杂，更难阅读，更难调试，而且可能根本不会更快——因为你优化错了东西。

正确做法：

  1. **先写清晰、正确的代码。** 可读性和正确性是优先事项。
  2. **测量。** 在真实条件下对应用做性能分析。
  3. **识别实际瓶颈。** 90/10 规则意味着大部分代码不需要优化。
  4. **只优化瓶颈。** 让热点路径更快，同时让其余部分保持可读。
  5. **验证改进。** 再次做性能分析，确认优化确实有帮助，并且没有引入新的瓶颈。


### 15.5 CPU 受限 vs. I/O 受限 vs. 内存受限

并非所有“慢”都有同一个原因。理解瓶颈是哪一种资源，会改变优化策略：

**CPU 受限**：程序受计算速度限制。CPU 达到 100%，解决方案是更快的计算（更好的算法、编译型代码、并行化）。

**I/O 受限**：程序在等待输入/输出——磁盘读取、网络请求、数据库查询。CPU 在等待时处于空闲。解决方案：批量处理 I/O 操作，使用异步/非阻塞 I/O，添加缓存以避免重复 I/O。

**内存受限**：程序受内存访问模式限制——大型数据结构、缓存未命中、垃圾回收。解决方案：减小数据结构大小，改善内存局部性，降低分配速率。

**诊断**：做性能分析时，检查 CPU 利用率。如果 CPU 是 100%，程序就是 CPU 受限。如果 CPU 很低但程序仍然慢，那就是 I/O 受限或内存受限。内存分析可以区分后两者。


### 15.6 调试谜题：每个月都变慢的报表

**调试谜题：为什么月度报表越来越慢？**

一份月度销售报表在 1 月需要 30 秒生成，在 2 月需要 45 秒，在 3 月需要 60 秒，到 6 月需要 120 秒。代码没有变化。服务器硬件没有变化。

**线索 1：** 报表查询从年初到当前月份的全部销售数据。

**线索 2：** 数据库查询使用 `SELECT * FROM sales WHERE date >= '2024-01-01' AND date <= CURRENT_DATE ORDER BY date`。

**线索 3：** 查询的 EXPLAIN 计划显示顺序表扫描——没有使用索引。

**你的任务：** 报表为什么越来越慢，修复方法是什么？

**答案：** 查询每个月扫描的数据都更多，因为日期范围在增长（1 月：1 个月的数据，6 月：6 个月的数据）。顺序扫描会读取 sales 表中的每一行来寻找匹配日期。随着表在全年不断增长，扫描耗时会线性增加。

**修复：** 在 `date` 列上添加索引：`CREATE INDEX idx_sales_date ON sales(date)`。有了索引，数据库可以直接跳到相关行，而不是扫描整张表。无论表大小如何，查询时间都会变得近乎恒定。

**调试技术：** 这是把版本比较（第 9 章）应用到数据上——代码和环境相同，但数据量变了。对数据库查询做性能分析揭示了瓶颈在查询计划中，而不是在应用代码中。
