#### 数据处理 bug

剥离到：一个 transformation step、一行数据。
    
    
    # MRE: prices are wrong after currency conversion
    price = 19.99
    rate = 1.13
    converted = round(price * rate, 2)
    # Expected: 22.59
    # Actual: 22.59 — wait, this works?
    
    # Try with the ACTUAL problematic value:
    price = 0.1 + 0.2  # 0.30000000000000004
    converted = round(price * rate, 2)
    # Now the floating point error propagates
    

通过剥离到一次计算，MRE 揭示出问题不在 conversion logic，而在 price 是如何在上游计算出来的——floating-point arithmetic 正在产生不精确的值，随后这些值被 conversion 放大。


#### 日常排错

MRE 原则延伸到软件之外，适用于任何复杂性会掩盖问题的领域。如果你的面包总是扁而密实，你在厨房中遇到的是一个可复现性问题——但你仍然可以构建一个 MRE：把包含十二种原料和特殊技巧的复杂食谱先放到一边。烤一个尽可能简单的面包：flour、water、yeast、salt，除此之外什么都不要。如果这个简单面包正确膨胀，你的问题就在额外原料或步骤中的某处。如果这个简单面包也很扁，你就把失败隔离到了基础条件——temperature、yeast freshness 或 flour type。那个朴素面包就是你的 MRE：仍然显示失败的最小设置。

同样的方法适用于调试网络连接、一辆无法启动的汽车，或一个不再产生效果的健身计划。一次剥离一个变量，测试每次移除，并收敛到仍然显示问题的最小配置。


### 6.7 当 MRE 过程本身就是修复

有时，构建 MRE 的行为会在你完成之前解决 bug：

**场景 1：消失的 bug。** 你开始移除组件，当移除 module X 时 bug 消失。你把 module X 放回去，bug 又出现。你已经在完成 MRE 之前找到了元凶。

**场景 2：明显的原因。** 你把代码剥离到 15 行，bug 就在第 8 行——一个简单的 typo、错误的 operator、缺失的 condition。MRE 让它变得可见。

**场景 3：“等等，那不可能对”的时刻。** 在决定要移除什么时，你第一次仔细查看某个组件，并意识到它正在做意料之外的事。“为什么这个 function 在 mutate 它的输入？那不应该发生。”对保留与移除内容的调查迫使你真正阅读代码——在完整系统中，由于代码库令人畏惧，你可能一直在回避这件事。

这就是为什么 MRE 不只是调试技术——它是一个_迫使理解的机制_。不理解每个组件做什么，就无法构建 MRE，而这种理解往往正是找到 bug 所需要的。
