* 可得性启发：“我刚刚部署，所以一定是我的代码改动错了。”但代码在本地可用。问题可能是生产环境数据或配置差异。
* 确认偏差：不要只检查代码改动——也要检查生产环境 API 响应。

**步骤 4 —— 调查：**

  1. 检查 UserList.jsx 第 18 行做了什么——它很可能类似于 `users.map(...)`。`users` 来自哪里？很可能来自 API 调用或 props。
  2. 检查生产环境 API 响应——它是否与代码预期一致？
  3. “本地可用，生产环境崩溃”的常见原因：(a) 本地 mock 数据具有预期形状，但生产数据没有，(b) 生产环境缺少某个环境变量，(c) API endpoint URL 在不同环境之间不同，(d) API version 在生产环境改变了，但本地没有。

**Q3.** 以下错误在一个生产 Node.js 应用中间歇出现——每天数千个请求中大约出现 5 次：
    
    
    Error: ETIMEDOUT
        at TCPConnectWrap.afterConnect [as oncomplete] (net.js:1141:16)
    

这个错误没有指向应用代码的堆栈跟踪——只有 Node.js 内部代码。你会如何调试这个问题？

**答案：** 这是一个具有挑战性的案例，因为堆栈跟踪只显示 Node.js 内部代码，而不是应用代码。方法：

  1. **理解错误：** `ETIMEDOUT` 表示一次 TCP 连接尝试超时——客户端试图连接到服务器，但服务器没有在超时时间内响应。这是一个网络层错误。

  2. **添加上下文：** 由于堆栈跟踪没有显示应用的哪个部分触发了它，要添加插桩。用错误处理包装所有出站连接（数据库查询、对外部服务的 HTTP 请求、缓存连接），记录哪个连接失败。使用类似这样的代码：`try { await fetch(url); } catch(e) { logger.error('Connection failed', { url, error: e.message }); }`。

  3. **寻找模式：** 每天数千次请求中出现 5 次——它们什么时候发生？是集中一起发生（暗示短暂网络抖动），还是分散在一天中？它们是否与高流量（连接池耗尽）或低流量（空闲连接超时）相关？

  4. **形成假设：** (a) 某个下游服务偶尔变慢/无响应。(b) 连接池在流量高峰期间耗尽。(c) DNS 解析间歇失败。(d) 某条网络路径存在丢包。

  5. **应用版本比较（第 9 章）：** 这个错误率最近是否变化？检查它是新问题（某些东西改变了），还是长期存在的问题（网络可靠性）。

  6. **系统化调查：** 一旦插桩揭示哪个连接超时，就把调查范围缩小到那个具体服务/网络路径。检查该服务的健康指标、网络路径延迟和连接池配置。
