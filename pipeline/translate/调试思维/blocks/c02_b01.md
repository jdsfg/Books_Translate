在第 1 章中，我们已经确立：调试是由假设驱动的调查——与科学方法是同一个过程。但仅仅知道调试“像科学”还不够。化学家不会只是含糊地“做科学”——他们会遵循一套具体的实验规程。侦探也不会只是“调查”——他们会遵循处理证据的程序。

你也需要一套程序。当你凌晨 2 点盯着一个坏掉的系统，大脑昏沉，本能地想开始随机改东西时，你需要某种可以遵循的东西。它要足够具体，以至于即使你疲惫、紧张，或者完全迷失时也能发挥作用。

这个程序就是**调试循环**。


### 2.1 五个步骤

调试循环有五个步骤，你会反复执行它们，直到找到根本原因。步骤如下：

**观察 → 假设 → 预测 → 测试 → 缩小范围**

就是这样。五个步骤，反复执行。我们用一个贯穿始终的例子逐一说明。

假设你正在构建一个 Web 应用，有用户报告：“我点击 Submit 按钮时，什么也没有发生。”


#### 步骤 1：观察

在做任何其他事之前，先收集信息。不是猜测——是_观察_。症状究竟是什么？它在什么条件下发生？预期行为和实际行为分别是什么？

对于我们的 Submit 按钮：

* “什么也没有发生”——页面是否保持完全不变？按钮看起来有被点击吗（视觉反馈）？URL 是否变化？浏览器控制台中是否有错误？
* 这发生在所有用户身上，还是只有这个用户？所有浏览器都会这样，还是只有某一个？
* 它每次都会发生，还是间歇发生？
* 它什么时候开始发生？一直都是坏的，还是以前能正常工作？

你的观察质量决定了后续所有工作的质量。含糊的观察会导向含糊的假设，进而导向浪费时间。


#### 定义：调试中的观察

观察是关于系统行为的、具体且可验证的事实。好的观察是精确的（“点击 Submit 会在 Chrome 控制台产生一个 JavaScript 错误：`TypeError: Cannot read property 'submit' of null`”），而不是含糊的（“按钮不能用”）。

用普通话说：观察是你_看到_的东西，而不是你_认为_的东西。“我在控制台看到一个错误”是观察。“表单处理器坏了”是解释。把二者分开。

假设你的观察显示：点击按钮时按钮确实有视觉下压，没有发出网络请求（已在 Network 标签页检查），浏览器控制台显示：`TypeError: Cannot read property 'value' of null at handleSubmit (form.js:42)`。

现在你有东西可以着手分析了。


#### 步骤 2：假设

基于你的观察，形成一个关于问题原因的_具体、可测试_的假设。

错误显示在 `form.js:42` 处 `Cannot read property 'value' of null`。这意味着第 42 行的代码正在尝试对某个 `null` 的东西访问 `.value`。一个合理的假设是：“表单正在按 ID 读取一个 DOM 元素，但该元素不存在——要么 ID 拼错了，要么元素尚未渲染。”

注意这个假设有多具体。不是“表单出了点问题”——那太含糊，无法测试。也不是“JavaScript 坏了”——那不可操作。好的假设是一个关于_什么_坏了以及_为什么_坏了的精确主张。
