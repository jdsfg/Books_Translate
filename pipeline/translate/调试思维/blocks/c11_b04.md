#### 定义：竞态

当程序的行为取决于事件（例如两个线程或两个异步操作）的相对时序，而这些事件又没有保证按特定顺序执行时，就会发生竞态。"race" 发生在这些事件之间——谁先完成，谁就决定行为。

用直白的话说：两件事同时发生，结果取决于哪件事先完成。有时能工作。有时不能。你无法预测是哪一种。
    
    
    // Race condition: two requests update the same account balance
    // Thread 1: read balance ($100), add $50, write balance ($150)
    // Thread 2: read balance ($100), subtract $30, write balance ($70)
    // If both read $100 before either writes:
    // Thread 1 writes $150, Thread 2 overwrites with $70
    // Expected: $120 ($100 + $50 - $30). Actual: $70 or $150.
    

**为什么竞态很难：**

  1. **不可复现** ：它们取决于时序，因此运行同一段代码两次可能产生不同结果。调试工具（print 语句、调试器）会改变时序，可能隐藏缺陷。
  2. **依赖环境** ：竞态可能从不在你快速的开发机器上显现，却在较慢的生产服务器上稳定出现（或反过来）。
  3. **间歇性** ：这个缺陷可能每 1000 次只出现 1 次，让你很难确认修复是否有效。

**竞态的诊断模式：**

* 没有明确原因的**间歇性失败**——同一段代码有时工作，有时失败
* **"It works on my machine"**——不同硬件速度改变时序
* **缺陷在调试时消失**（第 10 章的海森缺陷）——调试器暂停改变了时序
* 缺陷报告中出现 **"sometimes"** 这个词——"It sometimes shows stale data" 或 "It occasionally crashes"

**调查方法：**

  1. **寻找共享可变状态**——任何多个线程/进程/异步操作都可以读写的数据
  2. **寻找缺失的同步**——缺失的锁、缺失的 `await`、缺失的事务边界
  3. **添加压力测试**——运行大量并发操作，以提高竞态显现的概率
  4. **使用线程安全分析工具**——竞态检测器，例如 ThreadSanitizer（C/C++）、`go vet -race`（Go），或 Java 的 `FindBugs`

Therac-25 放射治疗机器（第 14 章）曾因竞态杀死患者。安全关键系统中的竞态可能致命。这就是为什么并发编程需要极端谨慎，也就是为什么 Rust 这类语言从设计上让数据竞态不可能发生。


### 11.7 断言与不变量：尽早捕捉缺陷

**断言**是代码中的一条语句，用来声明在某个特定点上某件事应当始终为真。如果断言失败，程序会立即停止，并准确告诉你哪里出了什么问题。
    
    
    def withdraw(account, amount):
        assert amount > 0, f"Withdrawal amount must be positive, got {amount}"
        assert account.balance >= amount, f"Insufficient funds: {account.balance} < {amount}"
        
        account.balance -= amount
        
        assert account.balance >= 0, f"Balance went negative: {account.balance}"
        return account.balance
    

断言是内置在代码中的调试基础设施。它们像绊线——正常运行时不可见，但一旦有什么违反了你的假设，就会立即提醒你。
