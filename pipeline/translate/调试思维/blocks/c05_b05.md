### 5.7 二分查找何时不起作用

二分查找有局限。要识别这些局限，避免在不适用时浪费时间：

**没有清晰的顺序。** 二分查找需要一个可以拆分的维度。如果 bug 可能在 20 个彼此无关、没有顺序关系的模块中的任意一个里，你就无法 bisect——你需要另一种方法（例如独立测试每个模块）。

**多个相互作用的 bug。** 如果两个 bug 相互作用，bisect 可能会给出误导性结果。Commit A 引入 bug 1（测试失败），commit B 引入 bug 2（测试仍然失败），commit C 意外掩盖了 bug 1（测试通过！），commit D 什么也没做。Bisect 可能会把 commit C 识别为“第一个坏提交”，因为测试行为在那里发生变化，但那实际上是掩盖前一个 bug 的提交。

**非确定性 bug。** 如果 bug 随机出现（第 2 章关于间歇性失败的讨论），你的中点检查可能因为偶然通过或失败，把二分查找引向错误的一半。对于非确定性 bug，你需要在每个中点进行多次测试，以建立统计置信度。

**“diff”太复杂。** Bisect 会告诉你是哪个提交，但如果那个提交是一个庞大的 500 行变更，你仍然需要在其中继续收窄。更小、更聚焦的提交会让 bisect 有用得多。


### 5.8 调试谜题：消失的折扣

**调试谜题：20% 去了哪里？**

一个电商系统会对超过 100 USD 的订单应用 20% 折扣。一位客户的订单总额为 150 USD，但收据没有显示任何折扣——他们被收取了完整的 150 USD。

**线索逐步揭示：**

**线索 1：** 订单处理管道有 6 个步骤：validate → price → tax → discount → format → save。在 discount step 之后添加日志显示折后总额是 120 USD（正确——150 USD 打 20% 折）。

所以折扣确实被正确计算了。bug 在 discount step 之后。

**线索 2：** 在 format step 之后添加日志显示总额是 150 USD（错误——折扣消失了）。

bug 在 format step——它破坏了折扣。

**你的任务：** 在阅读解答之前，提出假设：一个“format”步骤怎么会改变总金额？

**解答：** format step 从原始订单商品重建收据，并通过求和商品价格重新计算总额——没有应用折扣。折扣作为单独字段存储在订单对象上（`order.discount = 30`），但 format function 忽略了它，只是求和 `order.items[].price`。二分查找方法（检查管道中的中点）只用了 2 次检查就找到了确切步骤，而不需要完整审查全部 6 个步骤。
