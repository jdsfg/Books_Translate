#### 应用题

**Q1.** 你负责向一个运行在 50 台服务器上的系统部署关键更新。以 Knight Capital 案例为警示，设计一个能防止部分部署失败的部署流程。包括：部署前检查、部署步骤、部署后验证和回滚流程。

提示

思考：你如何知道所有服务器都已更新？如果有些失败怎么办？你如何验证正在运行的版本？

**答案：**

**部署前：**

  1. 所有 50 台服务器通过健康端点报告当前版本（`GET /health` 返回 `{"version": "2.3.0"}`）
  2. 开始前验证所有服务器都在同一个当前版本
  3. 在 staging 环境中让新版本通过集成测试
  4. 确保 rollback artifacts（上一版本的部署包）可访问

**部署（滚动更新）：**

  1. 分批部署到服务器，每批 5 台（一次 10%）
  2. 每批之后：验证所有已更新服务器报告新版本，并通过健康检查
  3. 监控错误率和延迟。如果它们退化到超过阈值，则暂停部署
  4. 每批之间等待 5 分钟，以检测缓慢显现的问题
  5. 如果任何批次失败：停止部署，不要继续下一批

**部署后验证：**

  1. 查询所有 50 台服务器的健康端点。所有服务器都必须报告新版本。任何不匹配 = 调查
  2. 针对生产环境运行端到端 smoke tests
  3. 比较部署前后的错误率（版本比较——第 9 章）
  4. 明确验证没有服务器运行旧版本：`for server in servers; do curl $server/health | grep "2.4.0" || echo "MISMATCH: $server"; done`

**回滚流程：**

  1. 如果检测到问题：使用相同的分批流程部署上一版本
  2. 自动回滚触发器：如果部署后 15 分钟内错误率超过基线 2x，则自动回滚
  3. 回滚后：验证所有服务器都处于上一版本

**关键原则：** 部署流程永远不让服务器停留在混合版本状态。更新要么完全完成，要么完全回滚。

**Q2.** 受 Knight Capital 案例启发，为你的代码库设计一个“死代码审计”流程。你会如何识别可能被意外重新激活的休眠代码？你会用什么标准决定是否删除它？

**答案：**

**识别方法：**

  1. **Feature flag 清单：** 列出所有 feature flag。对每个 flag，确定：上一次切换是什么时候？它后面是否仍有受控代码？如果一个 flag 已经 6+ 个月没有被切换，并且被它控制的代码不是活跃路径，它就是删除候选。
  2. **代码覆盖率分析：** 运行带代码覆盖率的完整测试套件。所有测试中从未执行的代码可能是死代码。（注意：有些代码合理地很少使用但并非死代码——错误处理器、fallback paths。）
  3. **静态分析：** 像 `deadcode`（Go）、`vulture`（Python）或 IDE inspections 这样的工具可以检测从未被调用的函数和类。
  4. **Git archaeology：** `git log --all -- path/to/file`——如果一个文件或函数多年没有修改并且未被调用，它很可能是死代码。
