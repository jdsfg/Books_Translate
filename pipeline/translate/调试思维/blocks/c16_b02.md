### 16.2 分布式计算的谬误

1994 年，Peter Deutsch 和 Sun Microsystems 的其他人整理了一份开发者会对分布式系统作出的假设清单——这些假设全都是错的。理解这些谬误可以防止一大类缺陷：

  1. **网络是可靠的。** 它不是。数据包会丢失，连接会中断，网络分区会发生。
  2. **延迟为零。** 它不是。一次网络调用需要毫秒到数百毫秒，而不是微秒。
  3. **带宽是无限的。** 它不是。通过网络传输大型数据集很慢。
  4. **网络是安全的。** 它不是。传输中的数据可能被截获或篡改。
  5. **拓扑不会变化。** 它会。服务器会被添加、移除和迁移。
  6. **只有一个管理员。** 并不是。不同团队管理不同服务。
  7. **传输成本为零。** 它不是。每一次网络调用都有计算成本和财务成本。
  8. **网络是同质的。** 它不是。不同部分使用不同协议、速度和可靠性级别。

你无意中假设的每一个谬误，都会导致只在真实网络条件下的生产环境中出现的缺陷——在一切都位于 localhost 的开发环境中从不出现。


### 16.3 分布式追踪：跨服务跟随一个请求

在单个程序中，堆栈跟踪会告诉你执行路径。在分布式系统中，你需要一种跨越多个服务的类似东西：**分布式追踪**。


#### 定义：分布式追踪

分布式追踪会跟随一个请求穿越多个服务，记录每个服务花费的时间，以及各操作之间的因果关系。每个服务都会向追踪中添加一个“span”，从而创建请求旅程的完整画面。

用通俗的话说：当用户点击“Buy”时，请求会触及 API 网关、订单服务、支付服务、库存服务和通知服务。分布式追踪把所有这些步骤连接成一条时间线，准确显示请求把时间花在哪里，以及在哪里失败。

关键机制是**关联 ID**（也称为 trace ID）——在请求开始时生成的唯一标识符，并传递给请求触及的每个服务。每个服务都在日志中包含这个 ID。
    
    
    API Gateway → Order Service → Payment Service → Inventory Service
       trace-id: abc-123        trace-id: abc-123    trace-id: abc-123
       span: 2ms                span: 150ms          span: 45ms
    

现在，当请求失败时，你搜索日志中的 `trace-id: abc-123`，就能看到每个服务对该请求的视角——它收到了什么，做了什么，花了多长时间，返回了什么。

没有关联 ID，调试分布式失败就意味着在 10 个服务的日志中按时间戳和内容匹配事件——这是一场噩梦。
