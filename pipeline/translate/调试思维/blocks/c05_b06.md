### 5.9 调试谜题：破坏登录的提交

**调试谜题：它是什么时候坏的？**

你们团队的登录功能在过去两周的某个时间停止工作了。期间有 64 个提交。使用 git bisect，你用 6 步把范围缩小到一个标题为“Update user model serialization”的提交。diff 显示：
    
    
    - return { id: user.id, name: user.name, email: user.email }
    + return { id: user.id, name: user.name, email: user.email, role: user.role }
    

这个提交所做的只是向序列化后的 user object 添加 `role`。添加一个字段怎么会破坏登录？

**你的任务：** 想一想。添加字段看起来完全无害。可能出什么问题？

**解答：** 认证系统使用序列化后的 user object 来生成 session token（JWT）。token 有最大大小限制，或者 token 被签名后再验证——但另一个服务上的验证使用的是旧 schema（没有 `role`）。当 token 在另一个服务上被反序列化时，额外字段导致验证失败："unexpected field: role." 另一种情况是，某些用户的 `role` 字段可能是 `null` 或意外值，导致下游代码失败。关键教训是：在互联系统中，添加字段并不是“安全”的变更，因为其他组件可能对数据形状有严格预期。二分查找找到了确切提交；理解系统找到了机制。
