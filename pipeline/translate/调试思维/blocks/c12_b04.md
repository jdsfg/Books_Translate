### 12.5 重新审视 Ampersand Bug：架构会防止缺陷类别

在第 8 章，我们解决了 Ampersand Bug（与号缺陷）：包含 `&` 的密码会被截断，因为它们使用 URL 编码但没有正确转义。修复方法是添加 `encodeURIComponent()`。

但这里有一个关于环境和架构的更深层经验教训。Ampersand Bug（与号缺陷）之所以存在，是因为应用使用 URL 编码的表单数据（`application/x-www-form-urlencoded`）来提交密码。在这种编码中，`&` 是保留字符。

一个架构选择可以防止整个类别：

* **使用 JSON bodies**（`application/json`）：在 JSON 中，`&` 没有特殊含义。密码 `correct&safe` 会作为 `{"password": "correct&safe"}` 传输，没有编码问题。
* **使用 POST with`multipart/form-data`**：这种编码对特殊字符的处理方式不同，并且不使用 `&` 作为分隔符。

重点是：修复眼前缺陷（添加编码）是必要的，但选择一种根本不存在该缺陷类别的架构更好。环境和架构决策——使用哪种数据格式、哪种 HTTP 方法、哪种 content type——决定了哪些类别的缺陷是可能的。Ampersand Bug（与号缺陷）不是代码缺陷——它是一个架构层面的决策，创造了一类漏洞。

这与火星气候轨道器案例研究（第 13 章）相连：缺陷是接口边界上的单位不匹配。修复方法是添加单位转换。架构性预防方式是使用一种让单位不匹配不可能发生的类型系统。


### 12.6 调试谜题：CRLF 破坏者

**调试谜题：手动运行成功但在 CI 中失败的脚本**

一个 shell 脚本在你本地执行（`./deploy.sh`）时运行完美，但在 CI 中失败，并报错：`bash: /deploy.sh: /bin/bash^M: bad interpreter: No such file or directory`。

**线索 1：** `/bin/bash` 末尾的 `^M` 很可疑。`^M` 是什么？

**线索 2：** 最后编辑这个脚本的开发者使用 Windows。CI 运行 Linux。

**你的任务：** 是什么导致了失败？

**解答：** `^M` 是 `\r`（回车）的显示表示。这个脚本以 Windows 风格换行符（`\r\n` 而不是 Unix `\n`）保存。shebang 行 `#!/bin/bash\r\n` 会被 Linux 解释为"运行解释器 `/bin/bash\r`"——回车符成为文件名的一部分。由于不存在名为 `bash\r` 的文件，于是发生错误。

修复：把文件转换为 Unix 换行符（`dos2unix deploy.sh`，或配置编辑器使用 LF 换行符）。预防：添加一个 `.gitattributes` 文件，强制 shell 脚本使用 LF 换行符，无论开发者的 OS 是什么：`*.sh text eol=lf`。
