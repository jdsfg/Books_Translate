进一步追踪后：产品列表页会规范化 API 响应——把 `Price` 映射为 `price`。但 cart 的 `addItem` 在一条代码路径中接收的是规范化_之前_的 product，在另一条代码路径中接收的是规范化_之后_的 product。产品列表页上的 “Add to Cart” 按钮传入规范化数据（小写 `price`），但搜索结果页上的 “Quick Add” 按钮传入原始 API 数据（大写 `Price`）。cart 的 `addItem` 期望小写，所以对于 quick-add 产品，`product.price` 是 undefined，而 `undefined` 被存为 `undefined`，在算术中通过类型强制转换变成 `0`。

从显示的 0.00 USD 反向追溯七步，到达两个入口点之间的数据规范化不一致。每一步都缩小了调查范围。如果从“用户点击 Quick Add”开始正向追踪，就必须先理解整个数据流，才知道该看哪里。


### 8.3 隔离变量：一次改变一件事

反向追溯告诉你问题在_哪里_。隔离变量告诉你_具体是什么_导致它。

#### 定义：变量隔离

变量隔离是调试中的一条原则：测试假设时，每次只改变一件事。如果你改变了三件事，bug 消失了，你并不知道是哪一个改变修复了它（另外两个改变还可能引入新问题）。

用直白的话说：科学实验有控制组是有原因的。在调试中，_你_就是科学家，_你的_系统就是实验对象。改变一个变量，观察结果，然后再改变下一个。

这听起来显而易见。实践中却极其困难，因为：

**不耐烦。** 你看到三个可能的修复，就想一次全部应用，因为“这样更快”。其实不是——当 bug 仍然存在（或出现新 bug）时，你完全不知道哪个改变负有责任。

**“既然都进来了……”** 你修复了疑似 bug，_又_重构了一些代码，_又_更新了一个依赖。现在有三件事变了，你已经失去了实验控制。

**隐藏变化。** 你改了一行代码，但 IDE 也自动格式化了文件，改变了另外 50 行。或者你编辑了一个配置文件，但部署工具也重建了 assets。你以为自己只改了一件事，实际上改了更多。


### 8.4 调试中的受控实验

调试中的受控实验遵循与科学实验相同的结构：

  1. **基线：** 记录当前行为。“API 对这个特定请求返回 500。”
  2. **假设：** “bug 是由新的 validation middleware 引起的。”
  3. **单一改变：** 只移除 validation middleware。不要改变其他任何东西。
  4. **观察：** “API 现在返回 200。bug 消失了。”
  5. **确认：** 把 validation middleware 放回去。“API 又返回 500。” bug 与这个特定改变可复现地关联起来。
  6. **在改变内部继续隔离：** validation middleware 有 50 行。是哪一部分？继续隔离。

步骤 5——反转——经常被跳过，但它至关重要。它确认你的改变负有责任，而不是巧合（比如某个短暂网络问题在你修改期间自行恢复）。
