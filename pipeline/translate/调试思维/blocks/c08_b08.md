#### 概念检查

**Q1.** 解释反向追溯这种调试技术。为什么它通常比正向穿过代码更高效？

**答案：** 反向追溯从观察到的症状（错误输出、崩溃）开始，逆向追踪因果链——在每一步都问“是什么直接产生了这个结果？” 它通常更高效，因为：(1) 症状具体明确，给你一个清晰起点。(2) 从具体结果反向追踪时路径更少——通常只有一条操作链产生了这个确切的错误值。(3) 正向追踪需要探索许多可能正确的代码路径，把时间浪费在无关分支上。(4) 每一个反向步骤都会排除所有不会导致该症状的代码，把注意力精确聚焦。

**Q2.** 变量隔离的原则是什么？为什么在确认修复后还要回滚你的改变？

**答案：** 变量隔离意味着在测试调试假设时，每次只改变一件事。如果你改变多件事，就无法确定是哪一个改变导致了行为变化。确认修复后回滚很重要，有两个原因：(1) 它确认是_你的_改变导致改善，而不是巧合（比如短暂问题自行恢复或缓存过期）。(2) 它验证这种关系是因果关系，而不是相关关系——回滚时 bug 应该回来，重新应用修复时 bug 应该消失。

**Q3.** 在 Ampersand Bug（与号缺陷）的解法中，为什么用多个特殊字符测试很重要（而不是只测试 `&`）？

提示

测试多个字符能告诉你什么，而只测试 `&` 不能？

**答案：** 测试多个特殊字符会把 `&` 隔离为具体原因。如果只有 `&` 会导致 bug，那么原因必然与 `&` 的某种特殊性有关——这会把你引向 URL 编码（其中 `&` 是参数分隔符）。如果_所有_特殊字符都会导致 bug，原因就会不同——也许服务器完全拒绝非字母数字字符。通过测试 `=`、`+`、空格和其他字符，并发现它们都能正常工作，我们确认了这个 bug 只与 `&` 在 URL 编码中的角色有关，而不是一般的特殊字符处理问题。这就是变量隔离应用于输入空间。

**Q4.** 回想第 2 章中的缓存 bug（错误用户资料数据）。反向追溯如何应用到那次调查？

**答案：** 在资料缓存 bug 中进行反向追溯：(1) Alice 看到 Bob 的数据 → (2) 显示的数据来自 API 响应 → (3) 尽管请求的是 Alice，API 响应却包含 Bob 的数据 → (4) 但 curl 返回正确数据，所以 API 是正确的 → (5) 浏览器正在返回缓存响应 → (6) 缓存没有区分用户，因为 Cache-Control header 写的是 `public` → (7) 服务器为用户特定数据设置了错误的 cache header。每一步都从症状（错误显示）向根因（错误 cache header）反向追踪，并不断缩小调查范围。
