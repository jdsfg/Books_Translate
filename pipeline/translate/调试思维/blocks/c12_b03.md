### 12.3 Docker 和容器化：减少表面积

容器（Docker、Podman 等）通过把代码和它的环境一起打包，显著减少环境缺陷。
    
    
    FROM node:20.11.0-slim
    WORKDIR /app
    COPY package*.json ./
    RUN npm ci
    COPY . .
    CMD ["node", "server.js"]
    

这个 Dockerfile 表示："在 Debian-slim Linux 上，用 Node.js 20.11.0 和这些精确的包运行这段代码。"无论这个容器运行在开发者的 Mac、CI 服务器还是 Kubernetes 集群中，容器内部的环境都是相同的。

**容器能消除什么：**

* 运行时版本不匹配（版本固定在镜像中）
* OS 差异（容器内部始终是 Linux）
* 依赖差异（`npm ci` 从 lock file 安装精确版本）
* "但我的系统有不同的包"（容器自带它需要的包）

**容器不能消除什么：**

* secrets 和环境变量（运行时注入，可能不同）
* 网络拓扑（容器之间的连接、DNS、防火墙）
* 资源限制（内存和 CPU 限制在外部设置）
* 持久数据（数据库内容、上传文件随环境不同）
* 外部服务行为（你依赖的 API 可能表现不同）

回想第 9 章的讨论：容器化提高了环境缺陷的_层级_，但没有消除它们。你不再调试"哪个 OpenSSL 版本？"，而开始调试"哪条 Kubernetes ingress 规则？"


### 12.4 调试 CI/CD 流水线失败

CI/CD 流水线是环境调试的一个特殊情况：代码运行在一个没人直接交互的自动化环境中。

**常见 CI 特有问题：**

**干净初始状态 vs. 脏状态** ：你的本地环境会积累状态——缓存包、构建产物、之前测试运行留下的数据库状态。CI 每次都从零开始。这意味着被本地状态隐藏的缺陷会在 CI 中暴露。

**文件系统内容不同** ：CI 只检出仓库。你的本地机器在仓库外有额外文件（全局 npm 包、本地工具、个人脚本）。如果代码意外依赖这些，它会在 CI 中坏掉。

**时序差异** ：CI 运行在共享基础设施上。你的构建可能因为其他项目争抢 CPU 而变慢。依赖时序的测试会间歇性失败。

**网络访问差异** ：CI 可能无法访问你的内部服务，或可能通过不同网络路径路由。本地能工作的 API 调用可能因 CI 中的防火墙规则而失败。

**调试方法：**

  1. **仔细阅读 CI 日志**——它们包含如果你运行同样命令会出现在屏幕上的错误消息
  2. **用干净状态在本地复现**——删除 `node_modules`，清理缓存，克隆一个全新 repo，并手动运行 CI 命令
  3. **SSH 进入 CI 环境**（如果你的 CI 提供商支持）以检查实际状态
  4. **比较 CI 运行命令和你的本地命令**——标志、环境变量或执行顺序上的细微差异
