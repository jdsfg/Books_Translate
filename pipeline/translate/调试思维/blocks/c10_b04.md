### 10.6 选择观察什么的艺术

更多可观测性通常更好，但并不总是如此。它也有成本：

**太多噪声会遮蔽信号。** 如果你记录每一次函数调用，日志每小时就会有数百万行，有用条目会被埋掉。噪声比沉默更糟，因为它制造了可观测性的幻觉——你_有_日志，但你在里面找不到任何东西。

**观察可能改变行为。** 在量子物理中，这是观察者效应。在软件中，它表现为海森堡缺陷——当你添加调试时就消失的缺陷。添加一条日志语句可能足以改变时序，从而隐藏一个竞态。调试器的断点会改变执行速度。要意识到你的仪器可能会扰动实验。

**性能成本。** 每次日志写入、每次指标记录、每次追踪采集都会消耗 CPU、内存和 I/O。在高吞吐系统中，这个成本很重要。解决方法是采样（记录 100 条追踪中的 1 条）和分层日志（只在需要时开启 DEBUG，正常运行时使用 INFO）。
指导原则：**在边界处观察，用能回答调试问题的最小细节。** 你随时可以在需要时临时增加细节。


### 10.7 主动式与反应式可观测性

在缺陷出现_之后_添加可观测性（反应式）和在缺陷出现_之前_构建可观测性（主动式）之间，有一个关键区别：

**反应式可观测性**："API 返回了错误数据。让我添加一些日志语句并部署，看看发生了什么。" 这能奏效，但需要一个部署周期，会延迟诊断，而且临时仪表化通常会在之后被移除。

**主动式可观测性**："每个 API 端点都会以 INFO 级别记录输入、输出和处理时间。我无需修改任何东西，就能看到失败请求期间到底发生了什么。" 这需要前期投入，但回报巨大——未来每个缺陷都更容易诊断。

添加可观测性的最佳时间是你编写代码的时候。第二好的时间是现在。每一个你在缺乏足够可观测性的情况下调试的缺陷，都是你的系统需要更多仪表化的信号。

一条实用规则：**修复一个缺陷后，添加本可以让你更快找到它的可观测性。** 如果你需要添加 print 语句才能找到这个缺陷，就在关闭工单前把它们转成永久性的结构化日志。随着时间推移，这会有机地构建出一层全面的可观测性——每个缺陷都会让系统比以前更可观测。

同样的原则也适用于软件之外。一个坚持写症状日记的病人——记录疼痛程度、用药、食物、睡眠和活动——会给医生提供丰富的诊断数据。一个只能凭记忆诊断的医生（"我最近感觉更糟了"）几乎没有任何可用信息。主动记录在医生需要它之前就已经存在，这意味着诊断可以立即发生。这就是可观测性：在调查之前构建记录，而不是在症状出现后匆忙添加仪表化。
