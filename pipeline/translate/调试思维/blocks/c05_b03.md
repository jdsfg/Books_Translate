### 5.3 历史中的二分查找：Git Bisect

二分查找最强大的应用之一，是找出哪个提交引入了 bug。Git 为此内置了一个工具：`git bisect`。

场景是：你的应用两周前运行良好。今天它坏了。中间有 100 个提交。是哪个提交弄坏了它？

没有二分查找：检出每个提交并测试。100 次检查。

使用 `git bisect`：7 次检查（⌈log₂ 100⌉ = 7）。
它的工作方式如下：
    
    
    # 开始二分定位
    git bisect start
    
    # 将当前（已损坏的）提交标记为 bad
    git bisect bad
    
    # 将一个已知正常的提交标记为 good
    git bisect good abc1234
    
    # Git 会检出中点提交
    # 你测试它——它坏了吗？
    
    # 如果中点处已经坏了：
    git bisect bad
    
    # 如果中点处可以正常工作：
    git bisect good
    
    # Git 会检出剩余范围的新中点
    # 重复，直到找到确切的破坏性提交
    

经过 7 轮迭代后，`git bisect` 会告诉你：“第一个坏提交是 `def5678`。” 现在你确切知道哪个变更破坏了功能。阅读那个提交的差异，bug 就会直直地盯着你。

**专业提示** ：如果你有一个能检测该 bug 的自动化测试，就可以完全自动化二分定位：
    
    git bisect start
    git bisect bad HEAD
    git bisect good abc1234
    git bisect run npm test
    

Git 会自动测试每个中点，并在零人工干预的情况下找到破坏性提交。这是所有编程命令中最令人满意的命令之一。

#### 常见误解

**“Git bisect 只适用于回归——也就是过去能工作、现在坏了的 bug。”** 虽然这种二分定位最自然地适合回归，但你可以把它用于对提交进行的任何二分查找。例如：“包体积是在什么时候超过 1MB 的？”或“这个性能回归是从什么时候开始的？”——任何能表达为通过/失败测试的条件，它都能找到拐点。


### 5.4 系统中的二分查找：前端还是后端？

二分查找并不限于代码和提交。它是一种适用于任何具有层次或组件的系统的思维工具。

用户报告你的 Web 应用有问题。bug 在哪里？请求会流经：浏览器 → 网络 → 负载均衡器 → API 服务器 → 应用代码 → 数据库。
二分查找：检查中点。数据离开 API 服务器时是正确的吗？

* 如果 API 响应是正确的：bug 在浏览器、网络或负载均衡器中（客户端侧或网络侧）。
* 如果 API 响应是错误的：bug 在 API 服务器、应用代码或数据库中（服务器侧）。

你只用一次检查就排除了半个系统。对剩下的一半，再检查它的中点。

这就是第 2 章缓存演练中应用的同一种技术——通过 curl 直接检查 API，就是一次把系统分成“浏览器侧”和“服务器侧”的二分查找。

Web 应用的一些实用“中点”：

如果你在寻找... | 检查这个中点...  
---|---  
bug 在前端还是后端？ | 直接检查 API 响应（curl、Postman）  
bug 在应用还是数据库？ | 直接检查数据库（SQL 查询）  
bug 在服务器还是网络？ | 检查服务器日志（它收到请求了吗？）  
bug 在你的代码还是依赖中？ | 用硬编码数据替换依赖调用
