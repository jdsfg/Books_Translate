#### 深入思考

**Q1.** AI 助手（如 ChatGPT 或 Claude）越来越常被用作“小黄鸭”——程序员向它们解释 bug，并获得反馈。这会如何改变小黄鸭调试法的动态？它比原始技术更好还是更差？分别体现在哪些方面？

**讨论：** AI 助手以几个重要方式改变了动态：

**获得了什么：**

* AI 可以用相关问题回应，捕捉程序员可能没有注意到的缺口
* AI 可以提出程序员尚未考虑的假设，带来某种“新鲜视角”
* AI 总是可用，不像人类同事
* AI 可以立刻查阅文档、错误信息和常见解决方案

**失去了什么：**

* 程序员做的认知工作更少。面对橡皮鸭时，_你_必须完成所有思考——鸭子迫使你表达。面对 AI 时，你可能会含糊描述问题，然后让 AI 来推理。认知收益来自_你的_表达，而不是来自收到一个答案。
* 程序员可能形成依赖。他们学会的不是独立调试，而是把问题描述给 AI——这是一种不同的（也可以说迁移性更弱的）技能。
* AI 可能是错的，而它听起来很自信的回答会把程序员锚定在错误假设上（第 3 章）。

**最佳做法：** 首先把 AI 当作小黄鸭使用——像它什么都不知道一样，向它解释问题，说清楚每一步——让解释过程发挥认知作用。然后，如果你仍然没有找到 bug，再把 AI 的建议视为额外的待测试假设（而不是可以盲目信任的答案）。最糟糕的做法是：不思考就把代码和错误信息粘贴给 AI，然后接受它说的任何内容。

**Q2.** 本章把小黄鸭调试法与第 3 章讨论的认知偏差连接起来。针对四种主要偏差（确认偏差、锚定、可得性启发、过早停止），分别具体说明小黄鸭调试法如何帮助抵消它。

**讨论：**

**确认偏差：** 当你大声解释问题时，你必须描述所有证据，而不只是支持你理论的证据。走完整个数据流的动作，经常会让被默想过滤掉的矛盾证据浮现出来。“等等，我刚刚说 API 返回的数据是对的——那 API 怎么会是问题？”

**锚定：** 小黄鸭调试法要求从头开始解释完整上下文。这会稀释锚点，因为你被迫考虑整个系统，而不只是最先进入脑海的区域。结构化解释会防止你围绕初始假设产生隧道视野。

**可得性启发：** 通过一步一步解释问题，你会自然考虑记忆中新近内容之外的组件。“请求经过负载均衡器，然后 API gateway，然后 service……”——你在列出所有组件，而不只是最近处理过的那些。

**过早停止：** 小黄鸭过程不会在你找到第一个可疑点时结束。因为你在解释完整流程，所以会自然越过第一个异常继续下去：“好，我发现了这个问题，但让我继续解释，确保它完全解释了症状……”这种继续推进经常会揭示，第一个发现只是症状，而不是根因。
