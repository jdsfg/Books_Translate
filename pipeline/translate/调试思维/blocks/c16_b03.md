#### 超时不匹配

服务 A 以 5 秒超时调用服务 B。服务 B 调用服务 C，而 C 很慢——需要 7 秒。服务 B 还在等待 C，但服务 A 已经超时了。从 A 的视角看：“B 挂了。”从 B 的视角看：“我还在等 C。”从 C 的视角看：“我正在处理。”

这个 bug 在于：整条调用链上的超时值不一致。调用方的超时时间必须长于所有下游超时时间之和，否则调用方会在下游工作仍在进行时放弃。

**诊断**：请求因超时错误而失败，但下游服务最终成功了（你可以在下游服务的日志中看到成功响应，只是它在调用方放弃之后才到达）。检查整条服务链上的超时配置。


#### 重试风暴

服务 A 调用服务 B。B 很慢（负载过高）。A 超时并重试。现在 B 必须同时处理原始请求和重试请求，负载变得更高。A 再次超时并再次重试。B 的负载继续增加。这个正反馈循环可能拖垮整个系统。

**诊断**：某个本来已经很慢的服务突然出现流量峰值。流量增加与上游服务中的超时错误相关。“恢复”机制（重试）正在放大故障。

**预防**：指数退避（每次重试之间等待更久）、抖动（随机化等待时间，避免所有客户端同时重试）、断路器（超过阈值后停止重试），以及重试预算（限制重试总次数）。


#### 最终一致性的意外

在许多分布式数据库中，更新是最终一致的——一个节点上的写入需要时间传播到其他节点。这意味着写入后立即读取，可能会返回旧值。
    
    
    1. 用户把个人资料名称更新为 “Alice”
    2. 服务器写入数据库节点 A：name = "Alice"
    3. 用户立即刷新页面
    4. 服务器从数据库节点 B 读取：name = "Bob"（还没有收到更新）
    5. 用户看到自己的旧名字，以为更新失败了
    

**诊断**：“我刚更新了 X，但它仍然显示旧值。如果我等几秒再刷新，它就是正确的。”这种模式强烈指向最终一致性。

**预防**：从你刚写入的同一个节点读取（读己之写一致性），在 UI 中显示乐观更新（立即显示新值，等读取追上后再用服务器数据更新），或者在正确性很重要时使用强一致读取。


#### 消息顺序与重复

消息队列可能乱序投递消息，也可能不止一次投递同一条消息。如果你的消费者假设严格顺序或恰好一次投递，就会出现 bug：
    
    
    预期：CREATE_ORDER → PROCESS_PAYMENT → SHIP_ORDER
    实际：PROCESS_PAYMENT → CREATE_ORDER → SHIP_ORDER
    

试图为一个尚不存在的订单处理付款会失败。

**预防**：把消费者设计成**幂等**的（同一条消息处理两次会产生相同结果），并能处理乱序投递（处理前检查前置条件是否满足）。


### 16.5 调试数据：错误数字、缺失记录、编码问题

数据 bug 是一个特殊类别，横跨单系统调试和分布式系统调试。症状包括：报表显示错误数字、记录缺失、出现重复，或文本显示不正确。
