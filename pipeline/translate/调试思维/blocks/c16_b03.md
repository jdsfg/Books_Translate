#### 超时不匹配

服务 A 调用服务 B，超时时间为 5 秒。服务 B 调用服务 C，而 C 很慢——需要 7 秒。服务 B 等待 C，但服务 A 已经超时。从 A 的视角看：“B 挂了。” 从 B 的视角看：“我还在等 C。” 从 C 的视角看：“我正在处理。”

缺陷是：链路中的超时值不一致。调用方的超时时间必须长于所有下游超时时间的总和，否则调用方会在下游工作仍在进行时放弃。

**诊断**：请求以超时错误失败，但下游服务最终成功（你可以在下游服务日志中看到成功响应，它在调用方放弃后才到达）。检查整个服务链路中的超时配置。


#### 重试风暴

服务 A 调用服务 B。B 很慢（过载）。A 超时并重试。现在 B 必须同时处理原始请求和重试请求，使它更加过载。A 再次超时并重试。B 上的负载更多。这个正反馈循环可能拖垮整个系统。

**诊断**：某个已经很慢的服务流量突然激增。流量增加与上游服务中的超时错误相关。“恢复”机制（重试）正在放大故障。

**预防**：指数退避（每次重试之间等待更久）、抖动（随机化等待时间，避免所有客户端同时重试）、熔断器（达到阈值后停止重试）和重试预算（限制重试总数）。


#### 最终一致性意外

在许多分布式数据库中，更新是最终一致的——一个节点上的写入需要时间传播到其他节点。这意味着写入后立即读取，可能返回旧值。
    
    
    1. User updates their profile name to "Alice"
    2. Server writes to database Node A: name = "Alice"
    3. User immediately refreshes the page
    4. Server reads from database Node B: name = "Bob" (hasn't received the update yet)
    5. User sees their old name and thinks the update failed
    

**诊断**：“我刚更新了 X，但它仍然显示旧值。如果我等几秒再刷新，它就是正确的。” 这种模式强烈指向最终一致性。

**预防**：从你写入的同一个节点读取（读己之写一致性），在 UI 中显示乐观更新（立即显示新值，等服务器读取赶上后再更新），或者在正确性很重要时使用强一致读取。


#### 消息顺序和重复

消息队列可能乱序投递消息，也可能多次投递同一条消息。如果消费者假设严格顺序或恰好一次投递，缺陷就会出现：
    
    
    Expected: CREATE_ORDER → PROCESS_PAYMENT → SHIP_ORDER
    Actual:   PROCESS_PAYMENT → CREATE_ORDER → SHIP_ORDER
    

试图为一个还不存在的订单处理付款会失败。

**预防**：把消费者设计成**幂等**（处理同一条消息两次会产生相同结果），并且能够处理乱序投递（处理前检查前置条件是否满足）。
