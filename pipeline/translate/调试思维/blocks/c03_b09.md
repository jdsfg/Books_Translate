#### 应用题

**Q1.** 对下面每个场景，识别主要起作用的认知偏差，并解释它会如何误导调试工作：

(a) 你在 2 PM 部署了一次代码改动。3 PM 收到一个 bug 报告。你立刻调查自己 2 PM 的部署。

(b) 一位资深开发者看了错误后说：“哦，我以前见过这个一模一样的错误——它总是线程问题。”团队接下来的两天都在调查线程。

(c) 你发现一个配置值被设置成一个不寻常的数字（比如 timeout 是 30000ms，而不是通常的 5000ms）。你宣布这就是你正在调查的慢性能问题的原因。

(d) 你已经调查一个关于内存损坏的理论三个小时了。你的同事提出它可能是一个更简单的输入验证问题。你驳回这个建议，因为“我已经在内存分析上挖得太深了。”

提示

对每个场景，问：是什么让调试者关注这个特定嫌疑对象？是证据，还是别的东西？

**答案：**

(a) **可得性启发。** 你最近的部署在记忆中很生动，所以你首先怀疑它。但 bug 可能在你部署之前就已经存在，只是现在才被注意到/报告。对策：检查 bug 是否存在于你部署之前的版本中（git bisect，或把旧版本部署到测试环境）。

(b) **锚定**（结合权威偏差）。资深开发者的说法变成了整个团队的锚。“我以前见过这个”同时触发了锚定（听到的第一个假设）和可得性（资深开发者的过去经验）。但“一模一样的错误”几乎从不是真正的一模一样——上下文很重要。对策：团队本应在听到资深开发者的诊断之前独立分析错误，并且应该给线程调查设置时间盒。

(c) **过早闭合。** 你发现了一个看起来不寻常的东西，并在没有测试的情况下宣布它是原因。一个不寻常的配置值是_可疑的_，但不是_有罪的_。也许 30000ms timeout 是为一个缓慢的外部 API 有意设置的，而性能问题完全在别处。对策：测试把 timeout 改成 5000ms 是否真的修复性能问题（并注意意外副作用）。

(d) **沉没成本谬误。** 三个小时的调查让你不愿意改变方向，即使有人提出了一个可能更简单的解释。“挖得太深”是沉没成本论证——过去调查的深度并不会让内存损坏理论更可能正确。对策：根据输入验证理论本身的价值评估它。如果它可以快速测试（5 分钟），就测试它——相较于潜在回报，时间投入很小。
