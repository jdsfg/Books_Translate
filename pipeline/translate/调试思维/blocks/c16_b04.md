#### 把数据验证作为调试

当数据看起来不对时，调试方法是沿着数据流水线反向追溯（第 8 章）：
    
    
    Wrong output ← Aggregation ← Transformation ← Filtering ← 
      Joining ← Loading ← Raw source
    

在每个阶段都验证：这里的数据正确吗？数据第一次出错的阶段会告诉你是哪一次转换引入了错误。

**实用技术**：在每个阶段，统计记录数量并汇总关键指标。如果源有 1,000 条记录，而输出有 950 条，就说明某处丢了 50 条记录。对流水线做二分查找，找到丢失发生的位置。


#### 常见数据缺陷

**编码问题**：文本看起来像 `Ã©` 而不是 `é`，表示 UTF-8/Latin-1 不匹配。数据是 UTF-8，但流水线中的某个环节把它解释成了 Latin-1（或相反）。检查每个阶段的编码：数据库编码、应用编码、HTTP Content-Type 头。

**静默类型强制转换**：JavaScript 的 `"5" + 3 = "53"`（字符串拼接）与 `"5" - 3 = 2`（数值减法）。从 CSV 文件读取的数据通常是字符串；对字符串做算术会产生错误结果。始终显式转换类型。

**时区缺陷**：没有时区信息的时间戳是有歧义的。`2024-03-15 14:30:00`——这是 UTC 吗？本地时间吗？哪个本地时间？用带有时区信息的 UTC 存储时间戳，并在显示时转换。

**重复记录**：数据在输出中出现两次。常见原因：作业运行了两次（超时后重试——作业成功了但响应丢失，所以发生了重试）、JOIN 产生重复（多对多关系），或者导入运行了两次。

**校验和与断言**：给数据流水线添加校验和。每次转换后：统计记录数，汇总关键列，验证约束。一个写着“这一步之后，总收入应该等于所有行项目之和”的断言，可以立即捕获数据损坏。


### 16.6 调试谜题：缺失的订单

**调试谜题：订单正在从仪表板消失**

一个仪表板显示过去 24 小时的订单。用户报告说，过去一小时内下的某些订单没有出现在仪表板上，尽管订单确认已经成功发送。

**线索 1：** 订单服务确认订单已保存到 Database A。仪表板从 Database B（一个只读副本）读取。

**线索 2：** Database B 是 Database A 的只读副本，复制延迟“通常低于 1 秒”。

**线索 3：** 监控显示，在高峰时段（也就是缺失订单被报告的时段），复制延迟飙升到 30-60 秒。

**你的任务：** 订单为什么缺失，修复方法是什么？

**答案：** 仪表板查询 Database B（只读副本），而它在高峰时段落后于 Database A（主库）。过去 30-60 秒内下的订单不会出现在仪表板上，因为它们还没有被复制过去。这是一个最终一致性缺陷：写入发生在 A，读取来自 B，而在高负载下，复制延迟超过了用户预期。

**修复：** (1) 对仪表板的“最近订单”查询，从主数据库（A）读取，而不是从副本（B）读取。主库上轻微增加的负载值得换取一致性。(2) 显示提示：“仪表板数据最多可能延迟 60 秒。” (3) 实现混合方案：最近 2 分钟的数据从主库读取，更早的数据从副本读取。
