### 7.4 小黄鸭调试法 vs. 结对调试

小黄鸭调试法使用的是没有回应的听众。结对调试使用的是会回应的人。两者都有效，但作用方式不同：

小黄鸭调试法 | 结对调试  
---|---  
没有打断——你沿着自己的思路走 | 搭档可以提出问题，重新引导你的思考  
没人可用时也能进行 | 需要占用另一个人的时间  
你承担 100% 的思考 | 搭档可能带来你缺少的领域知识  
最适合你已经掌握所有知识、只是看不见问题的 bug | 最适合你需要新鲜视角或缺失知识的 bug  
免费——只用一只鸭子 | 消耗同事的时间  
  
混合方法通常最理想：先使用小黄鸭调试法（免费、随时可用、迫使你自己思考）。如果 15-20 分钟后仍然无效，再升级为与同事结对调试，让对方带来新鲜视角和不同知识。

结对调试时，要克制一上来就说“我觉得 bug 在 X 里”的冲动。相反，从头开始解释整个情况。如果你先给出自己的假设，就会锚定你的搭档（第 3 章），他们也会失去让结对调试有价值的那种新鲜视角。


#### 常见误解

**“小黄鸭调试法是给不知道如何正确调试的新手用的。”** 事实恰恰相反。经验丰富的调试者更多而不是更少使用小黄鸭技巧，因为他们已经学到：专业知识会制造盲点——他们会无意识地跳过步骤，因为他们“知道”事情如何运作。你越是专家，就越能从小黄鸭调试法提供的强制表达中获益，因为你有更多深深嵌入、需要浮出水面的假设。


### 7.5 调试日志：书面版小黄鸭

本书一直提到**调试日志**——记录你遇到过的 bug 以及你从中学到的东西。日志承担着小黄鸭的功能：写下 bug 的细节，会迫使你经历与大声解释相同的认知过程。

但日志拥有橡皮鸭没有的额外力量：**积累**。随着时间推移，你的日志会变成一座模式库：

* “我最近三次遇到这个 API 的 bug，全都是由错误的 content type 引起的”
* “每次我看到这个错误，真正的问题其实都是时序问题，而不是数据问题”
* “当我发现第一个看起来可疑的东西时，总会陷入过早停止”

这些模式——包括技术模式和个人偏差模式——如果没有记录，就会不可见。你的记忆并不可靠（还记得第 3 章的可得性启发吗），但你的日志是持久的。

一个有用的日志条目格式：
    
    
    日期：2024-03-15
    Bug：用户资料更新静默失败
    初始怀疑：数据库写入失败
    实际原因：API 响应处理器检查 response.ok，
      但服务器返回 200，同时在 body 中带有错误
      （非标准 API）
    我是如何发现的：小黄鸭调试法——解释数据流时，
      我意识到自己没有检查服务器实际返回了什么
      （而不是我假设它返回了什么）
    发现的偏差：确认偏差——我没有检查，
      就假设 API 遵循 REST 约定
    教训：始终检查实际响应，
      不要只检查状态码
    

定期回顾你的日志——每月一次就很好。你会发现单个条目无法揭示的趋势。
