#### 概念检查

**Q1.** 二分查找需要多少步才能在包含 500 个提交的代码库中找到 bug？展示你的计算。

**答案：** ⌈log₂ 500⌉ = ⌈8.97⌉ = 9 步。每一步都会把剩余搜索空间减半：500 → 250 → 125 → 63 → 32 → 16 → 8 → 4 → 2 → 1。最多 9 步就能从 500 个提交中找到确切提交。把这和线性检查全部 500 个提交相比。

**Q2.** 解释代码中的二分查找调试法（在中点打印）与历史中的二分查找（git bisect）以及系统中的二分查找（检查层边界）之间的差异。三者的共同原则是什么？

**答案：** 在**代码**中，你在数据处理管道的中点添加检查点（print 语句），以判断数据在该点是否仍然正确。在**历史**中，你检出中点提交并测试 bug 是否存在。在**系统**中，你在层边界（例如 API 响应）检查数据，以判断哪一层引入了问题。共同原则是：在这三种情况下，你都检查一个大致将搜索空间一分为二的中点，判断哪一半包含 bug，丢弃干净的一半，然后重复。“搜索空间”不同（代码行、提交、系统层），但策略完全相同。

**Q3.** 给出两种二分查找调试法无效的情况，并解释原因。

提示

想想二分查找所做的假设：一个可拆分的单一维度、一个单一 bug，以及确定性行为。

**答案：** (1) **多个相互作用的 bug** ：如果两个 bug 相互作用，使得修复一个会改变另一个的行为，二分定位可能给出误导性结果。例如，提交 A 引入一个 bug，而提交 C 引入另一个不同变更并意外掩盖它——二分定位可能指向 C 而不是 A。(2) **非确定性 bug** ：如果 bug 随机出现（例如，一个 30% 概率显现的竞态），你的中点测试可能因为偶然给出错误答案。二分定位假设“好”和“坏”之间有清晰边界，但非确定性 bug 会模糊这个边界。你需要多次测试每个中点并使用统计置信度，这会让过程慢得多，也不那么干净。

**Q4.** 对于第 1 章登录谜题中的登录 bug，你会如何应用二分查找？你会沿着哪个维度进行二分查找？

**答案：** 你可以沿着_数据路径_进行二分查找——也就是密码从用户键盘到比较点的旅程。路径可能是：用户输入密码 → 浏览器捕获它 → JavaScript 读取输入字段 → HTTP 请求发送它 → 服务器接收它 → 服务器将它与数据库值比较。检查中点：密码到达服务器时是什么样子？如果它与用户输入匹配，bug 就在比较逻辑中。如果不匹配，bug 就在传输过程中——浏览器和服务器之间有什么东西修改了密码。（剧透：沿着这个维度进行二分查找，并结合第 8 章的技术，将解决这个谜题。）
