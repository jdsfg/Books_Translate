#### N+1 查询问题

这是 Web 应用中最常见的性能缺陷之一：
    
    
    # Fetch all orders
    orders = db.query("SELECT * FROM orders")
    
    # For each order, fetch the customer (separate query!)
    for order in orders:
        customer = db.query(f"SELECT * FROM customers WHERE id = {order.customer_id}")
        display(order, customer)
    

有 100 个订单时，这会运行 101 次查询（1 次查询订单 + 100 次查询客户）。有 10,000 个订单时，它会运行 10,001 次查询。每次查询都有网络开销（连接数据库、发送请求、等待响应），所以即使每次查询都很快（5ms），10,001 次查询也要花 50 秒。

修复方法：一次查询取回所有客户：
    
    
    orders = db.query("SELECT * FROM orders")
    customer_ids = [o.customer_id for o in orders]
    customers = db.query(f"SELECT * FROM customers WHERE id IN ({','.join(customer_ids)})")
    customer_map = {c.id: c for c in customers}
    
    for order in orders:
        display(order, customer_map[order.customer_id])
    

现在无论订单数量是多少，都只有 2 次查询。

**诊断模式**：数据库密集型页面很慢。查询数量会随着展示的数据项数量增长。添加日志来统计每次页面请求的查询数量，就能揭示这个问题。


#### 内存泄漏

内存泄漏发生在程序分配了内存却从不释放的时候。程序的内存使用会持续增长，直到内存耗尽，或者垃圾回收器的开销拖慢性能。

回想第 10 章的“慢性毒药”谜题：应用每天都变得更慢，因为不断增长的会话缓存导致了垃圾回收暂停。这就是内存泄漏在起作用。

**诊断模式**：内存使用随时间增长，而且不会进入平台期。重启应用会暂时修复性能。性能是逐渐恶化的，不是突然变差。

**调查**：使用内存分析工具在不同时间获取堆快照并进行比较。正在增长的对象就是泄漏点。常见来源包括：添加后从不移除的事件监听器、没有淘汰策略的缓存、捕获并保留大型对象的闭包。


#### 不必要的工作

有时代码并不是算法上错了——它只是做了比必要更多的工作：
    
    
    // Recalculates the entire dashboard every time ANY data changes
    function updateDashboard(data) {
        const metrics = calculateAllMetrics(data);      // Expensive
        const charts = renderAllCharts(metrics);          // Expensive
        const tables = formatAllTables(metrics);          // Expensive
        return { metrics, charts, tables };
    }
    

如果只改变了一个指标，重新计算所有图表和所有表格就是浪费。**缓存**（保存结果，只在输入变化时重新计算）和**增量计算**（只更新发生变化的部分）是解决方案。

**诊断模式**：性能分析器显示时间花在一些计算上，而这些计算的结果与上一次调用完全相同。加入缓存后，这部分时间会完全消失。
