#### 应用题

**Q1.** 一个数据管道按顺序通过 8 个转换函数处理 CSV 文件。输出文件中 "total" 列的值不正确。设计一个二分查找调试策略。写出每一步：你会在哪里检查、会看什么，以及如何决定接下来搜索哪一半。

提示

你需要定义每个中点上“正确”和“错误”是什么样子。选择一行具体数据，并追踪它的 "total" 值在管道中的变化。

**答案：**

**设置：** 选择输出中 "total" 错误的一行。记录该行预期的正确值。这给了我们一个具体测试：在任何中点，我们都可以检查这一行的 "total" 是否仍然正确。

**Step 1（中点 = function 4 之后）：** 检查第 4 个转换之后的数据。查看目标行的 "total" 值。

* 如果 step 4 之后正确 → bug 在 functions 5-8
* 如果 step 4 之后错误 → bug 在 functions 1-4

**Step 2（假设 step 4 之后正确，所以搜索 5-8；中点 = function 6 之后）：** 检查第 6 个转换之后。

* 如果 step 6 之后正确 → bug 在 functions 7-8
* 如果 step 6 之后错误 → bug 在 functions 5-6

**Step 3（假设 step 6 后变成错误，所以搜索 5-6；检查 function 5 之后）：** 检查第 5 个转换之后。

* 如果 step 5 之后正确 → bug 在 function 6
* 如果 step 5 之后错误 → bug 在 function 5

**总计：3 次检查即可从 8 个函数中找到确切函数。** 每次检查时，记录中间 DataFrame 或把它写入临时文件。关键纪律是：在检查之前精确定义“正确”（某个已知行的预期值），这样结果才明确无歧义。

**Q2.** 有人告诉你“网站上周一还能工作，但现在坏了”。从上周一到今天之间有 40 个提交。但其中 5 个提交是来自功能分支的大型 merge（每个都包含许多变更），其余都是小而聚焦的提交。这会如何影响你的 git bisect 策略？你会做哪些不同的事？

**答案：** Git bisect 仍然可用，并且会在 ⌈log⁡240⌉=6\lceil \log_2 40 \rceil = 6⌈log2​40⌉=6 步内找到破坏性提交。不过这里有一个细微点：

**如果 bisect 识别出的是一个小而聚焦的提交：** 很好——diff 很小，原因应该很明显。这是理想情况。

**如果 bisect 识别出的是一个大型 merge commit：** 你已经从 40 个提交缩小到 1 个，但这个 1 个提交可能包含跨许多文件的数百个变更。现在你需要在 merge 内部继续收窄。选项包括：

  1. **Bisect merge 分支。** merge commit 有两个 parent。检出该 merge 的 feature branch，并在_它_里面 bisect——该分支很可能有自己的更小提交历史。`git bisect` 可以在 merge 内沿着 first-parent chain 跟踪。

  2. **在 diff 内做二分查找。** 如果该 merge 是 squash 的（没有内部历史），就把二分查找应用到代码变更本身。merge 修改了 N 个文件——检查这些文件的中点。回滚一半变更并测试。

**预防教训：** 这种情况凸显了为什么小而聚焦的提交很有价值——它们让 bisect 的用处大幅提升。只改变一件事的提交是精确的诊断结果。改变 50 件事的提交仍然需要进一步调查。
