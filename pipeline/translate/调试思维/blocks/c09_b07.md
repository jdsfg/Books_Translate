#### 应用题

**Q1.** 一个团队在周二部署了一次变更。周三，用户报告图片上传失败。周二的部署修改的是支付处理模块——与图片无关。使用五类变化，制定一个系统化调查计划。你会针对每一类检查什么，按什么顺序检查？

提示

不要仅仅因为时间相关就假设是部署导致的。检查所有类别。

**答案：**
**调查顺序（结合这个场景，从最可能到最不可能）：**

  1. **环境变化**（先检查——考虑到与部署时间相关，这是最可能的）：部署是否改变了服务器配置？是否改变了磁盘空间分配？新的部署容器是否有不同的文件权限？部署是否改变了上传目录挂载？检查服务器磁盘空间、上传目录的文件权限，以及伴随部署发生的任何基础设施变化。

  2. **依赖变化：** 部署期间的 `npm install` 是否拉取了图片处理库（例如 `sharp`、`multer`）的新版本？对比部署前后的 `package-lock.json`。即使代码变化发生在支付模块，部署流程也可能更新了所有依赖。

  3. **配置变化：** 部署期间是否有环境变量发生变化？新部署可能使用了另一个配置文件，其中上传路径、文件大小限制或存储桶引用不正确。

  4. **代码变化：** 即使部署被称为"只改支付"，也要验证：对整个部署做 `git diff`。支付模块的变化是否意外导入或修改了某个共享组件？是否有重构触碰了影响上传的共享中间件？
  5. **数据变化：** 是否是某种特定类型的图片触发失败？用户是否正在上传一种以前没有使用过的格式？检查：是所有图片上传都失败，还是只有特定图片失败？

**关键原则：** 部署时间会造成锚定偏差（第 3 章），让人倾向于怀疑代码变化。但代码变化（支付）与图片无关。最可能的原因是伴随部署发生的环境变化或依赖变化，而不是支付代码本身。

**Q2.** 你接手了一个生产系统，它没有部署日志、没有监控，也没有一致的 git 历史（提交很大且不频繁）。系统当前已经坏了。在没有良好变更记录的情况下，你会如何进行版本对比？你会设置什么来防止未来再次出现这种情况？

**答案：**

**没有记录时的即时调查：**
  1. **尽可能重建信息。** 检查 `git log`，看现有提交。检查服务器文件修改时间（`ls -la`）。检查系统日志（`/var/log/syslog`、应用日志）。检查云提供商审计轨迹（AWS CloudTrail、GCP Audit Logs）。检查容器镜像创建日期。即使没有正式记录，产物也会留下时间戳。

  2. **把当前状态与已知参照对比。** 有没有 staging 环境？备份？旧容器镜像？把当前生产状态与任何可用的、以前可工作的快照进行对比。

  3. **访谈团队。** "最近是谁碰过生产？你做了什么？有没有任何东西看起来不一样？" 人的记忆并不可靠（第 3 章），但总比没有好。
