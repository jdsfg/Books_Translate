### 15.7 调试谜题：其实很快的慢 API

**调试谜题：API 50ms 响应，但页面需要 5 秒**

一个网页调用 API 来加载用户数据。API 响应时间始终是 50ms（已通过 API 自身指标验证）。但用户导航到该页面后，页面需要 5 秒才显示数据。

**线索 1：** 浏览器的 Network 选项卡显示 API 请求耗时 50ms。

**线索 2：** 浏览器的 Performance 选项卡显示 API 响应到达后有 4.5 秒的 JavaScript 执行。

**线索 3：** JavaScript 正在渲染一个包含 10,000 个条目的列表。

**你的任务：** 这 4.5 秒花到哪里去了？

**答案：** API 很快，网络也很快。瓶颈是客户端渲染：浏览器的 JavaScript 正在构建 10,000 个 DOM 元素，每个条目一个。创建和追加 DOM 元素代价很高，做 10,000 次会花几秒钟。主线程在这段工作期间被阻塞，所以页面看起来冻结了。

**修复：** (1) **虚拟化：** 只渲染屏幕上可见的条目（约 20-30 个），而不是全部 10,000 个。`react-virtual` 或 `react-window` 等库可以做到这一点。(2) **分页：** 每页显示 50 个条目，而不是一次显示全部 10,000 个。(3) **Web Worker：** 把计算移出主线程，这样 UI 就不会冻结。

**调试教训：** 最初的假设——“API 很慢”——是错的。性能分析揭示瓶颈在前端，而不是后端。把二分查找（第 5 章）应用到系统层次（API → Network → Client）会很快找到这一点：API 响应在 50ms 到达，所以在那之前的一切都很快。缓慢完全发生在响应到达之后。
