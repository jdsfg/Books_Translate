### 6.5 “这一部分必要吗？”测试

构建 MRE 的核心心智纪律是对每个组件都问：**“这一部分对 bug 是必要的吗？”**

这个问题有四种可能答案：

  1. **明确不必要。** 该组件完全无关（例如，email sending module 与 CSS layout bug 无关）。移除它。

  2. **明确必要。** 移除该组件后 bug 消失。保留它。

  3. **可能必要。** 你不确定。测试它——移除组件并检查。

  4. **必要但可简化。** 组件是需要的，但更简单的版本也能工作。用 in-memory store 替换真实 database。用 mock 替换真实 API。用 10 行能产生相同数据的代码替换 1000 行 business logic。

第 4 类是大部分力量所在。很多时候，一个 bug 需要数据库连接，但它不需要你的数据库和你的数据。一个只有一张表、一行数据的 mock database 可能同样能复现 bug——而且更容易推理。


#### 常见误解

**“构建 MRE 是浪费时间——我应该直接修 bug。”** 这几乎总是错误的。构建 MRE 通常需要 15-30 分钟，并且常常会在过程中_揭示_ bug。“直接修 bug”而不理解它，常常要花数小时，而且经常得到的是解决症状而不是根因的修复。MRE 的投入会获得许多倍回报。这样想：你是愿意在干草堆里找针，还是先把所有干草移走？


### 6.6 不同 bug 类型的 MRE


#### Web 应用 bug

把应用剥离到：一个页面、无 authentication、硬编码数据，以及所需的最少 CSS/JS。
    
    
    <!-- MRE: button click handler doesn't fire on mobile -->
    <!DOCTYPE html>
    <html>
    <body>
      <div onclick="alert('clicked')">Click me</div>
    </body>
    </html>
    

这个 MRE 揭示出：带有 `onclick` handler 的 `<div>` 在移动设备上不会可靠触发。修复方法是：添加 `cursor: pointer` CSS，或者改用 `<button>` element。在一个包含数百个 elements 的完整应用中，你永远找不到这一点——但在一个 5-line MRE 中，它显而易见。


#### API bug

剥离到：一个 endpoint、无 middleware、硬编码 response。
    
    
    // MRE: API returns empty body despite data
    const express = require('express');
    const app = express();
    app.get('/data', (req, res) => {
      res.json({ items: getItems() });
    });
    app.listen(3000);
    
    function getItems() {
      const items = fetchFromDB();
      // Bug: forgot to return!
      // items is fetched but not returned
    }
    

MRE 让缺失的 `return` statement 变得明显。在包含 50 个 endpoints 和多层 middleware 的完整应用中，这会难发现得多。
