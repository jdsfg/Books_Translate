### 6.5 “这一部分必要吗？”测试

构建最小可复现示例的核心心智纪律，是对每个组件都问：**“这一部分对缺陷是必要的吗？”**

这个问题有四种可能答案：

  1. **明确不必要。** 该组件完全无关（例如，邮件发送模块与 CSS 布局缺陷无关）。移除它。

  2. **明确必要。** 移除该组件后缺陷消失。保留它。

  3. **可能必要。** 你不确定。测试它——移除组件并检查。

  4. **必要但可简化。** 组件是需要的，但更简单的版本也能工作。用内存存储替换真实数据库。用模拟 API 替换真实 API。用 10 行能产生相同数据的代码替换 1000 行业务逻辑。

第 4 类蕴含着大部分力量。很多时候，一个缺陷需要数据库连接，但它不需要你的数据库和你的数据。一个只有一张表、一行数据的模拟数据库可能同样能复现缺陷——而且更容易推理。


#### 常见误解

**“构建最小可复现示例是在浪费时间——我应该直接修复缺陷。”** 这几乎总是错误的。构建最小可复现示例通常需要 15-30 分钟，并且常常会在过程中_揭示_缺陷。不理解缺陷就“直接修复”，常常要花数小时，而且经常得到的是解决症状而不是根因的修复。最小可复现示例的投入会获得许多倍回报。可以这样想：你是愿意在干草堆里找针，还是先把所有干草移走？


### 6.6 不同缺陷类型的最小可复现示例


#### Web 应用缺陷

把应用剥离到：一个页面、无身份验证、硬编码数据，以及所需的最少 CSS/JS。
    
    
    <!-- 最小可复现示例：按钮点击处理程序在移动端不触发 -->
    <!DOCTYPE html>
    <html>
    <body>
      <div onclick="alert('已点击')">点我</div>
    </body>
    </html>
    

这个最小可复现示例揭示出：带有 `onclick` 处理程序的 `<div>` 在移动设备上不会可靠触发。修复方法是：添加 `cursor: pointer` CSS，或者改用 `<button>` 元素。在一个包含数百个元素的完整应用中，你永远找不到这一点——但在一个 5 行最小可复现示例中，它显而易见。

剥离到：一个端点、无中间件、硬编码响应。

    const express = require('express');
    const app = express();
    app.get('/data', (req, res) => {
      res.json({ items: getItems() });
    });
    app.listen(3000);
    
    function getItems() {
