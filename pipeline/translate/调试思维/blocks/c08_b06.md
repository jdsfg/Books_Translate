### 8.6 对数据进行反向追溯

反向追溯对数据 bug 尤其强大——也就是输出数据错误，但代码没有崩溃的情况。

方法是：**沿着数据的转换过程向后追踪数据。**
    
    
    Final output (wrong) ← formatting ← aggregation ← filtering ← 
      joining ← transformation ← raw input
    

在每个阶段检查：数据在这里是否正确？如果正确，就向输出方向移动一步。如果不正确，就向输入方向移动一步。这是沿着数据管道进行的二分查找（第 5 章），由已知错误的输出引导进行反向追溯。

处理数据 bug 的一个实用技巧：**在每个转换步骤打印数据**，然后从右侧（输出）向左侧（输入）扫描，找出数据第一次变错的步骤。
    
    
    raw = load_data()
    print(f"After load: {raw[:3]}")       # Check
    
    cleaned = clean_data(raw)
    print(f"After clean: {cleaned[:3]}")  # Check
    
    filtered = filter_data(cleaned)
    print(f"After filter: {filtered[:3]}") # Check
    
    # ... and so on
    

是的，这就是“print 调试”。它也是追踪数据如何在管道中被破坏的最有效方法之一。


### 8.7 超越代码的变量隔离

一次只改变一件事这条原则，远远不只适用于代码：

**调试一道食谱：** 蛋糕没有发起来。你用了不同的面粉，_又_用了不同的烤箱温度，_又_把黄油替换成了油。到底是哪一个改变导致问题？你无法知道。下次：改变一件事，烘烤，评估。然后再改变下一件。

**调试一个健康问题：** 你开始服用一种新药，_又_改变了饮食，_又_开始锻炼。症状改善了。是哪一个改变起作用？医生会建议：一次停止一项改变并进行监测。

**调试一个团队流程：** 团队速度下降了。你更换了项目管理工具，_又_重组了团队，_又_改变了 sprint 长度。是哪一个改变造成伤害？一次回滚一项。

这就是线索 B——同一项技术应用于代码、系统和生活。变量隔离就是受控实验，而受控实验是人类在任何领域可靠学习因果关系的方式。


#### 常见误解

**“在复杂系统中，我不可能只改变一件事——一切都是相互连接的。”** 没错，组件是相互连接的，但你的_改变_不必如此。你仍然可以一次只修改一个配置值、一个函数或一个依赖，并观察效果。如果一个改变在系统中产生级联反应，那么这个级联本身就是信息——它告诉你系统的依赖关系。在复杂系统中隔离变量很困难，这正是更谨慎地去做它的理由，而不是放弃的理由。
