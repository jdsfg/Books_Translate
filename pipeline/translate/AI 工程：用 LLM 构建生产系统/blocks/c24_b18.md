关键设计点：

* **可配置模式**：标记（检测 + 记录；让内容通过）适用于误报会干扰合法用户的生产环境。严格模式（阻止）用于高风险上下文。
* **结构化日志**：每次检测产生带模式名称和上下文片段的安全事件供分析师审查。
* **按模式命名的匹配**：而非仅"检测到"，结果包含哪个模式匹配。允许对攻击类型分布随时间的分析。
* **无正则恐慌**：模式使用简单构造，不会在对抗输入上导致指数回溯。

生产扩展会添加：按来源速率限制（命中多个模式的来源升级到调查）；来自威胁情报馈的模式更新；管理员界面审查标记内容。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_编写基于模式的 prompt 注入筛查生产代码：检测 5 个模式、记录检测、支持标记 vs 严格模式。_ 你验证 (a) 模式不会导致正则 DoS（对抗输入的灾难性回溯；LLM 有时写出易受攻击的正则），以及 (b) 日志结构匹配安全团队可调查的（结构化字段，非自由格式字符串）。

**Q2.** _设计跨租户隔离强制执行_。草拟工具执行层的跨租户数据隔离强制执行。指定：(a) 检查在哪里发生；(b) 检查什么；(c) 什么失败；(d) 审计追踪。

**答案：**

(a) **检查在哪里发生**：在工具执行层（第 13 章 §13.4），具体是任何工具实际访问数据前运行的策略门控中间件。

检查发生在 LLM 决定调用工具 _之后_ 但工具实际执行 _之前_。LLM 提议工具调用；策略层验证；如验证通过，执行继续；如验证失败，结构化错误返回给 LLM。

(b) **检查什么**：

对每个数据访问工具调用（如 `get_customer(customer_id)`、`lookup_order(order_id)`、`query_records(filter)`）：

* 从请求上下文（已认证的 agent 会话）提取 tenant_id。
* 从工具参数提取 _目标_ tenant_id（order_id 属于哪个租户；customer_id 由哪个租户拥有）。这要求工具的数据层知道租户归属。
* 验证：`request.tenant_id == target.tenant_id`。

对基于过滤的查询：确保过滤器显式包含 tenant_id；工具不应执行租户未限定的查询。

(c) **什么失败**：

如跨租户检查失败（租户 A 的请求尝试访问租户 B 的数据）：

* 工具执行被阻止。
* 抛出异常（或返回结构化错误给 LLM，取决于架构选择）。
* 记录高严重性安全事件：谁尝试、尝试了什么、何时。

运维含义：系统不应静默失败；失败应响亮（告警安全值班）但不应对客户可见（LLM 获得通用权限拒绝错误）。

(d) **审计追踪**：
