#### 概念检查

**Q1.** 解释 _LLM 提议，应用处置_ 原则（§13.4 原则 3 / §13.9）。为什么策略强制在工具执行层而非 prompt 层是正确架构？

**答案：** LLM 的工具使用行为受训练、prompt 和工具 schema 治理，无一严密。足够聪明的用户输入可诱导 LLM 调用 prompt 禁止的工具；LLM 是概率条件器，非确定性策略引擎。说"不要处理超过 500 美元退款"的系统 prompt 可被 prompt 注入攻击、模型未泛化的异常用户措辞或微妙改变行为的模型版本变更颠覆。

工具执行层的策略强制意味着：LLM 对 `process_refund` 的调用在实际退款发出前经过确定性检查（对照租户规则、金额限制、用户权限）。违反策略的调用被拒绝；LLM 收回结构化错误并调整。

确定性检查以 prompt 不具备的方式严密。说 `if amount > tenant.refund_limit: raise PolicyViolation` 的代码没有概率失败；每次都工作。

原则是第 2 章 §2.11 _将模型与产品分离_ 在工具层的应用。LLM 是智能路由组件；策略强制在应用手中。两层都需要；模型的策略推理有帮助但确定性检查使系统安全。

**Q2.** 为什么代码执行应总在沙箱中运行？识别在应用自身进程中运行 LLM 生成代码的三个具体风险。

**答案：** 三个风险：

1. **数据渗出**。LLM（可能受 prompt 注入）生成代码读取应用环境的敏感数据——API 密钥、数据库凭证、客户数据——并要么打印（泄漏到 LLM 上下文，再回到用户）要么外部发送（通过出站网络调用）。无网络访问且无凭证的沙箱无法渗出。
2. **持久妥协**。LLM 生成代码写文件、修改状态或在应用运行时安装持久后门。下一个用户的会话受影响。每次调用后销毁的沙箱重置状态；无跨调用攻击面。
3. **资源耗尽**。LLM 生成带无限循环、内存炸弹（分配巨大数组）或 fork 炸弹的代码。应用进程变得无响应；其他用户受影响。有 CPU 和内存限制的沙箱在影响更广泛系统前被杀死。

缓解：每个 LLM 代码执行路径在隔离、临时、资源受限的容器中运行。E2B、Modal、gVisor、Firecracker——无论哪种具体工具——架构模式是通用的。_永远_不要在应用自身进程中执行 LLM 生成代码。
