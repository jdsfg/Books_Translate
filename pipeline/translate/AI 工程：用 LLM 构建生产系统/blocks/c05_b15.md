#### 覆盖审查：流程

当你起草了量表后，在接入 CI 之前通过这个四步审计运行它。输出不是裁决；它是候选维度列表，你然后对每个做出包含或排除的决定并写下理由。

**步骤 1：利益相关者维度。** 走查工程之外对输出有利益的人，对每个问，_如果他们在评分这个，他们会评什么？_ 产品关心输出是否推进用户的工作。法务关心声明、免责声明和许可内容边界。客服关心语气和降级。领域专家（临床医生、律师、会计师，谁拥有正确性）关心他们惯语中的实质准确性。每个利益相关者通常产生一两个工程否则会遗漏的候选维度。

**步骤 2：故障模式维度。** 对于你正在构建的系统类别，走查已知故障模式目录并检查量表是否评分了每一个。对于 agent 系统，第 14 章将列出螺旋/无界循环/内存损坏模式；对于暴露于不可信输入的系统，第 23 章将列出 prompt 注入和泄露模式。Hallucination、拒绝不匹配和引用编造是通用的。存在于文献中但不在你量表中的故障模式是候选维度。

**步骤 3：成本和节奏维度。** 质量不是用户注意到的唯一轴。输出长度、p95 延迟和拒绝率本身是维度，它们可以在质量分数保持稳定时静默退化。一个在六个月内悄悄将平均输出长度翻倍的摘要器已经转移了用户体验而没有任何质量分数标记它。与质量一起评分这些，带显式阈值。

**步骤 4：对抗性 eval 扩展。** 花十分钟列出三个你 _尚未_ 在生产中看到但系统可能遇到的输入类别：新地区、标签外使用、高级用户利用 prompt。每个是添加到 golden set 的候选切片。你还没有它们的 ground truth；将它们记录为探索性案例并在下次生产采样后重新审视。

一旦你有了候选列表，对每个做出显式包含/排除决定。_排除：不适用；格式约束了它_ 是一个有效处置（也是 Beacon 的量表在 §4.10 中如何处理语气的方式）。纪律不是每个维度都必须被评分；纪律是每个维度都必须被 _考虑_，且考虑被记录。

第二个缓解措施是 _对抗性 eval 扩展_：在生产事件后，失败输入被添加到 golden set 并附适当标签，eval 随时间增长。golden set 是活文档。你见过的故障模式是你可以在下次变更时防范的；你尚未见过的故障模式是开放问题，覆盖审查是你缩小它们的工具。
