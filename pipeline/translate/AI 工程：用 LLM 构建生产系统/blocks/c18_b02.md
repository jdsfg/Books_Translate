**模型选择**：决定为给定请求调用哪个模型。可以是配置驱动的（按特性开关路由）、策略驱动的（按请求类型路由），或

**回退处理**：当主模型失败时（提供商宕机、速率限制、错误），路由到回退。回退链可以是多级的（主 → 次

**每租户预算强制**：追踪每个租户的支出并在其预算耗尽时拒绝进一步调用（或在接近预算时路由到更便宜的模型）。

**速率限制协调**：跨公司账户追踪剩余速率限制预算；在限制接近时对请求施加背压；预防性 shedding 负载。

**成本归因**：记录每次调用带成本、租户、功能、模型，以便成本追踪层（第 18 章）有它需要的数据。

**提供商抽象**：暴露统一接口使应用代码不需知道调用的是哪个提供商。应用代码调用 `router.complete(model="claude-sonnet-4", ...)`；路由器处理路由、回退、归因。

路由器不做所有事。它不管理 prompt（第 6 章层）；不管理编排（第 14 章层）；不管理 eval（第 5 章层）。路由器是 _模型调用层的_ 策略强制；它保持聚焦。

### 17.3 2026 年路由器格局

四个入选者主导 2026 年的讨论：

**LiteLLM**：开源，单二进制或服务。在模型特定 API 格式（Anthropic、OpenAI、Google 等）和统一接口间转换。配置驱动：YAML 文件定义模型、回退链、预算。事实上的 OSS 默认。

_适用_：任何想要 OSS 路由器的团队；偏好自托管基础设施的团队；想要简单聚焦工具的团队。

_注意事项_：与任何 OSS 一样，团队拥有运维关注；配置在非常大规模系统时变得复杂。

**Portkey**：SaaS 网关。提供路由层加内置可观测性界面、prompt 管理和策略引擎。卖点：不仅仅是路由；完整的 LLM 运维平台。

_适用_：想要托管网关和集成可观测性的团队；没有专门平台工程能力的团队。

_注意事项_：SaaS 成本；数据驻留考虑；对 Portkey 的 prompt 管理抽象有一定锁定。

**Cloudflare AI Gateway**：Cloudflare 的 AI 感知网关。位于任何 AI 提供商 API 前面；提供缓存、速率限制、分析。如你已在 Cloudflare 生态中则很强；对延迟敏感应用有性能优势。

_适用_：在 Cloudflare 上有其他基础设施的团队；延迟敏感应用；想要轻量网关而无 prompt 管理界面的团队。

**Kong AI Gateway**：Kong 的 AI 扩展网关。在成熟的 API 网关平台上添加 AI 感知策略（成本追踪、prompt 验证）。适合已在运行 Kong 处理非 AI API 的企业团队。

_适用_：有现有 Kong 部署的大型企业；想要统一 API 和 AI 网关管理的团队。

2026 年大多数团队的默认：**LiteLLM（OSS，自托管）用于路由层**。专门选项在特定规模或功能需求时回报。
