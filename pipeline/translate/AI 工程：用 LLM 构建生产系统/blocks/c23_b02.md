#### LoRA 作为现代默认

LoRA 微调更新小适配器层（通常占总参数的 0.1-5%）而非整个模型。优势：

* 训练成本低得多（更少参数；更少计算）。
* 多个 LoRA 可从同一基础模型服务（不同任务的不同专业化）。
* 热交换：通过加载不同 LoRA 切换任务而无需重新加载基础模型。

LoRA 主导 2026 年微调生态系统；全量微调（更新所有模型权重）保留给最大规模的最大专业化投资。

### 22.2 半衰期问题（线索 B 失败 4）

这是核心警示。**微调模型有半衰期**：它最终在其被调优的任务上变得比当前基础模型更差，因为基础模型改进速度比你的微调质量优势更快。

机制：

1. 你微调模型 V1 做任务 X。微调得分 92%；基础 V1 在任务 X 上得 78%。你发布微调。
2. 提供商发布 V2。基础 V2 在任务 X 上得 88%（显著改善）。你的 V1 微调仍得 92%。微调仍领先。
3. 提供商发布 V3。基础 V3 在任务 X 上得 94%。你的 V1 微调 92% 现在 _落后_ 基础。
4. 你一直在为 V1 微调承担维护开销（数据流水线；训练运行；eval 纪律）。现在你的微调是负债，非资产。

线索 B 失败 4 复合：一个团队的 GPT-4 微调在 GPT-5 发布第一天就变得比 GPT-5 基础模型更差。团队不得不手忙脚乱：维持微调（在 GPT-5 上继续训练；重新验证 eval）；切换到基础 GPT-5（失去曾有价值的专业化）；或重新调优（数工程师季度的工作）。

半衰期问题教的教训：**仅当价值在模型预期生命周期内证明维护负担合理时才微调**。该生命周期比团队通常假设的更短：2026 年前沿发布每 6-12 个月到达，每次都可能使先前微调过时。

缓解模式：

* **微调可行的最小模型**：更小模型在基础更新时重新调优更便宜。
* **维护微调数据流水线**：不仅是训练好的模型。流水线是让你在基础更新时重新调优的关键；没有它，微调不可复现。
* **计划每 6-12 个月重新调优**：预算工程时间；如你不能持续此承诺，一开始就不要微调。
