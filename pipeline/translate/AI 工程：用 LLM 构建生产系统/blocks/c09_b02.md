### 8.2 什么进入窗口：预算工作表

一个有用的心智模型：每次调用有 _上下文预算_，每个组件竞争其中一部分。工程师的工作是分配预算以最小成本最大化回答质量。

主要预算项，按稳定性排列：

**稳定（缓存，很少变化）**：

* 系统 prompt
* 工具定义
* 标准少样本示例
* 稳定指令和策略

这些是 **prompt 缓存**（第 18 章，绑定工作流 #9）的候选：provider 缓存编码前缀；共享前缀的后续调用在这些 token 上支付少 10 倍。对于稳定的 1500 token 系统 prompt，这是大收益。

**半稳定（按用户或按会话）**：

* 用户画像/偏好
* 对话历史
* 会话特定状态

这些不跨用户共享但在用户会话内稳定。一些缓存有帮助（按用户缓存前缀）；预算通常被随时间增长的对话历史消耗。

**动态（每次调用变化）**：

* 用户当前消息
* 检索到的 RAG 上下文（每次查询不同文档）
* 当前轮次的工具输出
* 最近的 agent 中间状态

这些是可变成本。动态预算是上下文工程工作集中的地方。

对每个预算项，工程问题是：

1. **它必要吗？** 许多系统在系统 prompt 中有过时指令，或包含在此流程中从不使用的工具的工具定义。审计和修剪。
2. **它能压缩吗？** 对话历史可以摘要（§8.4 详述）；检索到的块可以摘要；长工具输出可以截断。
3. **它能缓存吗？** 稳定项应缓存。对高量系统成本节省大。
4. **它在窗口中的位置？** 中间丢失是真实的；放置很重要（§8.5）。

### 8.3 从 prompt 工程到上下文工程的转变

三年前，主导词汇是 _prompt 工程_，主导问题是 _我应该在系统 prompt 中写什么？_ 今天的主导问题是 _什么应该进入上下文窗口，以什么顺序，以什么成本？_

转变不是表面的。它反映了三个实质性变化：

1. **工具和结构化输出意味着 prompt 不再只是指令。** 它是指令加 schema 加工具定义加检索内容。工程表面更大。
2. **长上下文现在是真实的。** 4K token 窗口强制每个字节有用。200K token 窗口允许团队选择放入什么（以及花多少预算）。选择变成工程。
3. **成本现在可见。** 推理经济学（第 18 章）使上下文窗口中的每个 token 成为一行成本。不跟踪上下文成本的团队在账单上发现它。

上下文工程是更广泛的学科；prompt 工程是其子技能之一。第 6 章覆盖 prompt 特定战术；本章覆盖更广泛的工程。
