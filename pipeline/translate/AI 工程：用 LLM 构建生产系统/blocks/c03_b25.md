重新设计的布局，从最稳定到最可变：`[system_prompt (600)] + [house_style (1800)] + [retrieved_context (4000)] + [user_question (200)]`。system prompt 和内部风格指南跨查询相同；那是每查询 2400 token 的可缓存前缀。检索上下文因查询而异，不会缓存。用户问题很小且在尾部。

每次查询成本，当前布局（无缓存）：

* 全部输入：(600 + 1800 + 4000 + 200) = 6600 token 按 3.00 美元/1M = 0.0198 美元
* 加输出（假设 800 token 按 15.00 美元/1M）= 0.012 美元
* 每次查询总计：约 0.0318 美元
* 10,000/天：318 美元/天，约 9,540 美元/月

每次查询成本，重新设计布局（前 2400 token 缓存命中）：

* 缓存前缀：2400 × 0.30 美元/1M = 0.00072 美元
* 新输入：(4000 + 200) × 3.00 美元/1M = 0.0126 美元
* 输出：800 × 15.00 美元/1M = 0.012 美元
* 每次查询总计：约 0.0253 美元
* 10,000/天：253 美元/天，约 7,590 美元/月

月节省：约 1,950 美元，约占账单的 20%。如果检索上下文也可缓存，节省会大得多，但它是按查询的，所以保持新输入。对于同一文档被多次查询的情况（例如律师整天处理一个案件），以 `(system_prompt + house_style + retrieved_context)` 为键的第二级缓存会捕获另一大比例；那是第 18 章将形式化的那种优化。

团队应该 eval 的风险：**用户问题在 6600 token prompt 的 _末尾_，可能受到 lost-in-the-middle 现象（§2.4）的反向影响——模型可能锚定在检索上下文上并回答与所问问题略有不同的问题**。eval 是在固定 golden set 上比较两种布局的答案质量；如果质量回归，团队需要在问题之前立即添加显式的"用户的实际问题是："框架，或将问题移回模型可靠 attend 的位置，即使付出一些缓存成本。
