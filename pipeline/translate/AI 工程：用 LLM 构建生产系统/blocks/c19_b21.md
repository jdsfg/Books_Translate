* 量激增：确认；检查租户的合同预算（按第 17 章 Q6）；如超出，策略强制启动且对话转移到客户团队。
* 功能回归：确认；回滚 prompt 或功能变更；部署恢复成本概况的修复；回填 eval 套件以在未来捕获此类回归。
* 路由回归：确认；恢复路由器变更；调查为何层分类器错误分配了该租户的流量。
* 缓存回归：确认；修复 prompt 恢复前缀稳定性；缓存命中率应在数小时内恢复。
* 滥用：确认；客户团队联系租户；如模式有害，考虑在预算内对该租户设速率限制。
* 测试流量：确认；修复标记使测试流量使用 `dev` 租户标识，非生产租户的。

调试纪律：从追踪查询开始；不从假设开始。数据快速缩小假设。在检查数据前以"我打算是新 prompt"开始的团队常调查错误原因数小时。

此练习揭示的模式：成本仪表板用于 _检测_；追踪存储用于 _诊断_；工程行动用于 _解决_。运维栈的每层有不同目的。混淆它们（用仪表板调试，或用追踪做监控）浪费团队时间在错误工具上。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_租户 Y 的成本昨日激增 4.7 倍 vs 基线。带我走查追踪查询、假设、验证和解决。_ 你验证 (a) LLM 从数据查询开始而非假设（跳到"可能是失控 agent 循环"而不检查追踪的 LLM 在犯团队必须避免的同样错误），以及 (b) 假设覆盖代码侧（功能回归）和租户侧（量激增、滥用）原因，而非仅一个类别。
