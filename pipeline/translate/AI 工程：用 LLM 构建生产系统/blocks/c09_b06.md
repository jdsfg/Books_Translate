### 8.7 Beacon Health AI：临床笔记摘要器的上下文决策

一个实例。Beacon 的临床笔记摘要器接受：

* 一份口述笔记（约 3K token）
* 患者最近就诊历史（最近 3 次就诊摘要；约 2K token）
* 患者当前用药清单（约 500 token）
* 一小组标准临床词汇参考（约 1K token，缓存）
* 带 EHR schema 的系统 prompt（约 1.2K token，缓存）

每次调用总上下文：约 7.7K token，其中约 2.2K 缓存。

团队考虑将患者的 _整个_ 病历（长期患者最多约 100K token）放入上下文。他们在 eval 上测试了两种方法。发现：
* 完整历史（100K token）：在深度历史重要的罕见案例上略微更好（量表 +0.3）。成本显著更高（约 0.30 美元/调用 vs 约 0.018 美元/调用）。延迟显著更高（约 2400ms vs 约 850ms）。
* 仅最近就诊（2K token）：在 eval 上质量几乎等同；更便宜；更快。

团队选择仅最近就诊作为默认，带回退：如果模型的 `confidence` 字段返回低于 0.6 _且_ 模型标记 `medications_unclear: true`，将调用路由到带完整历史的长上下文版本。这是 _升级模式_：大多数调用获得便宜版本；需要深度的小部分获得它。

模式是可移植的。许多生产系统受益于分层上下文策略：便宜上下文作为默认；昂贵上下文作为便宜版本不确定时的升级。

#### 常见误解

_更多上下文总是更好_ 是破坏第一轮上下文预算的假设。长上下文施加三种成本：货币（按 token 计费）、延迟（更多 token 需关注）、质量风险（中间丢失、不相关内容分心）。给定 100K token 其中 5K 相关的模型在任务上通常比仅给定相关 5K 的模型表现 _更差_，因为模型的注意力被不相关内容稀释。正确的上下文是包含相关信号的 _最小_ 上下文，加小余量。超过最小是浪费；有时有害。
