**本应捕获它的 eval**：eval 的 _语气切片_，在事件之前不存在。事后添加它在未来关闭了差距，但这里的故障模式是元级别的：故障是 _构建覆盖不足的 eval_。eval 设计纪律（§4.2 的六个组件，严格应用；§4.3 的 golden set 特征；§4.4 的参考标准组合）是捕获它的东西。覆盖审查是纪律的操作形式；运行它的团队将在 eval 设计时而非客户事件时捕获语气差距。

### 章节小结

eval 是没有唯一正确输出的系统的测试，AI 工程是在那个差距内专业运作的领域。没有 eval，每个工程决策是猜测，每次生产变更是风险，每次回归在客户发现之前是不可见的。有了 eval，工程决策变成数据驱动的，回归变成可检测的，纪律变成可教的。

eval 有六个组件：golden set、参考标准、指标、运行器、阈值、节奏。参考标准有五种常见形态：规范答案、量表、偏好对、行为测试、端到端任务指标。LLM 作为评判者革命了细微输出评分的经济学，但引入了必须对人工校准的相关失败风险。标注者间一致性（Cohen's kappa 或其多标注者类似物）是告诉你人工标签是否足够可靠以在其上构建的纪律。

有四个场景 eval 纪律让步于凭感觉：一次性原型；eval 自我吞噬的创意任务；挑战 golden set 的 agent 轨迹；参与指标足够的极低风险任务。这些是真实但有界的；默认是 _写 eval_，例外比看起来更小。

生产循环是 eval 作为 CI：eval 在每次变更时运行，回归阻止合并，分数历史对团队可见。第 5 章构建 GitHub Actions 工作流作为绑定工作流 #1。

Beacon Health AI 临床笔记摘要器 eval 是工作示例：三个工程师月的工作；四轴量表由对人工校准的 LLM 评判者评分；CI 门禁；生产采样。成本高；成本是公司可以发布的功能的代价。第一个 eval 昂贵；后续 eval 摊销。

如果你跳过本书其他所有内容，不要跳过这个：**eval 就是规范。** 没有它，下游的工程没有立足之处。第 5 章将纪律变成具体工具链。
