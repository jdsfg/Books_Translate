**支持演变**：chat-completions 形态承载的假设可能无法在能力转变中存活。该形态假设逐轮离散交互；有许多内部步骤的 agent 循环尴尬地映射到它上，通常被建模为嵌套工具调用块，这是权宜之计而非原生原语。该形态假设文本优先多模态；原生语音/视频模型不能干净地适应角色类型内容块结构。该形态假设一次一条消息；推测或并行解码可能需要不同的请求-响应语义。这些压力中的任何一个都可能触发后继 API 形态，历史上 API 形态比人们预期更快地替代了前驱。

我预期最先改变的具体表面元素是 **streaming**。当前基于 SSE 的 streaming，带 `message_start` / `content_block_delta` / `message_stop` 事件，是为发射一个 token 流的模型设计的。随着模型变得更 agentic（模型自己决定暂停、思考、调用工具、恢复，都在单个"轮次"内），streaming 表面要么接受更复杂的事件分类法（它已经开始这样做了，`tool_use` 事件与文本 delta 交错），要么转向不同传输（通过持久连接的双向 streaming，客户端和模型异步交换事件）。我预期那个压力是表面首先破裂的地方。

诚实的答案是 _概念形态_（角色、工具、streaming 作为概念）比 2030 年更长寿；_特定线格式_ 可能在 2027–2030 窗口获得一次大修订。本书的纪律（固定版本、记录一切、将 API 视为你用路由器抽象的移动目标）比任何特定规范更持久。

一个常见的对冲模式：**在单一 provider 上构建直到你越过翻转点，但你的代码针对薄抽象层编写，使以后添加第二个 provider 变得简单。** 薄层可以是你上面 Q1 的 _call_llm_ 封装：如果你所有代码都调用 _call_llm_（而非直接调用 _client.messages.create_），以后换入路由器是单文件变更。这是 _推迟工作，但为变更设计_，是对大多数公司的务实答案。
