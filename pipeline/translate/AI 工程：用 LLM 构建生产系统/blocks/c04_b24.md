1. **增量竞争。** 如果一个租户在接近上限时有 100 个并发在途请求，增量是交错的。朴素设计（读、计算、写）可能让多个请求超过上限。缓解：使用事务性 `UPDATE tenant_budget SET spent_dollars = spent_dollars + $cost WHERE tenant_id = $t AND month = $m RETURNING spent_dollars`，让速率限制层检查 _返回_ 值是否超过上限。或者，在调用前借记上限（预留预算），然后在响应时用实际用量结算；这以更复杂的流程为代价防止超支。
2. **数据存储不可用。** 如果 Postgres 宕机，速率限制层无法读写。两个选项：(a) **失败关闭**：以 HTTP 503 拒绝所有请求，优先考虑预算安全而非可用性；(b) **失败开放**：放行请求，接受超支风险。正确答案取决于 Helios 与 Acme 的合同：如果 Acme 宁可接受中断也不接受预算超支，失败关闭；如果可用性是 SLA 优先级，失败开放并在事后对账。记录选择；不要让它在事件期间成为意外。

值得提及的第三个故障模式：**成本计算必须与 provider 的计费精确匹配**，否则你会系统性地多计或少计。正确的纪律是使用集中定价表，在 provider 定价变更时更新，并针对几个已知调用做回归测试。第 18 章将在成本仪表盘纪律下回到这个话题。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_设计一个每租户 LLM API 预算上限层。要求：80% 软告警，100% 硬上限，处理并发请求的竞争条件，处理数据存储中断。_ LLM 会产生草图和代码。你验证 (a) 提议的竞争条件缓解是否实际有效（LLM 有时在说是竞争安全的同时提出易竞争代码；手动追踪并发场景来确认），以及 (b) 失败开放/失败关闭的选择是显式和文档化的；LLM 经常跳过这个设计决策，静默默认为其中之一。强制要求答案。

**Q5.** _实现尊重 provider 提示的速率限制感知重试_。朴素重试使用纯指数退避（`2^attempt` 秒）。然而，provider 通常发送 `retry-after` 头（以秒为单位，或作为 HTTP 日期）告诉你速率限制窗口何时打开。编写一个重试助手，在存在时优先使用 provider 的提示，否则回退到有上限的指数退避，并在两种情况下应用抖动。然后指出如果你在大规模时忘记抖动会出现的 bug。

提示

将 `retry-after` 解析为整秒值或 HTTP 日期并转换为距现在的秒数。将指数退避限制在，比如，60 秒。"惊群"是没有抖动时发生的事情。
