(c) **失败信号**：top-K 中任何来自非允许列表来源类型的块 → 立即告警。新来源率 >5% → 漂移告警。来源类型分布周环比偏移 >20% → 分布告警。

(d) **节奏**：每周对生产流量样本批量审计；硬故障（非允许列表来源）立即告警。纪律是持续的：团队成员每月审查来源 ID 列表确认语料库是他们期望的。

这是运营工程而非研究；成本小（一个工程师日构建，持续审查每月 30 分钟）；价值大（在客户注意到之前捕获 Google AI Overviews 式故障）。

**Q3.** _在长上下文和 RAG 间决策_。你的团队在 600K token 内部 HR 策论语料库上构建问答系统。应用第 8 章 §8.6 的决策树到此场景。推荐架构并用 §9.3 的四个 RAG 杠杆论证。

**答案：** 600K token 在 _判断决策层_（500K–10M）边界。两种架构都可行。

**长上下文论证**：HR 策略稳定（低更新频率）；语料库适合 Gemini 2.5 Pro 2M 上下文有余量；查询可从语料库任何地方拉取所以 RAG 分块需要小心；团队小（5 工程师）可节省 RAG 管道工程成本。

**RAG 论证**：延迟：600K 输入的长上下文调用约 3+ 秒 TTFT（第 8 章 §8.8）；HR 聊天机器人是交互式的 3 秒等待痛苦；成本：每次查询支付 600K 输入 token，即使有缓存动态每次调用成本有意义；查询精度：RAG 返回用户想读的特定段落，支持 HR 策略查询常需的引用接地（"育儿假策略的 X 节说..."）。

**推荐**：**RAG**。（交互式使用的延迟）+（HR 策略式答案的引用接地）+（每次调用成本经济学）的组合将决策推向 RAG 即使语料库可以适合长上下文。HR 策略的四个 RAG 杠杆：

* _分块_：文档结构感知（按策略章节拆分；每节一块；典型块 500–1500 token）。
* _嵌入_：标准 text-embedding-3 即可；HR 策略不需要专用嵌入。
* _检索_：混合（BM25 捕获精确策略名查询；向量捕获改述查询）。
* _排序_：Cohere Rerank 或 BGE-Reranker 在 top-15 → top-3 块。

团队约 2 个月构建此；生产延迟 p50 约 1.2 秒；每次查询成本约 0.008 美元。在交互式 HR 聊天机器人关心的每个维度上优于长上下文替代。
