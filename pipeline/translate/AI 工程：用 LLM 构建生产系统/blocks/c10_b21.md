**模式 3（附加）：RAG 用于引用纪律**。即使模型能从训练回答，客户常想要带显式引用的 _接地_ 答案。RAG 机械地提供接地；从训练的长上下文不能。对于受监管行业（法律、医学、金融），RAG 仍是审计友好的架构。

到 2030 年，RAG 更窄（更少的 _我需要给模型新鲜信息_ 案例）但未消失。它专门用于：非常大的语料库；实时数据；按租户个性化；可审计性。纪律（检索作为主导杠杆；多轴 eval；来源溯源）在架构转变中存活。

**Q3.** _RAG 七步循环是永久抽象还是过渡性的？_ 本章将 RAG 呈现为七步（§9.2）：查询、嵌入、搜索、重排序、构建 prompt、生成、后处理。今天每步是独立工程制品。推测：到 2030 年，七步结构会持续、某些步骤会融合、还是新步骤会出现？论证你预期看到的对七步循环的一个具体变化。论证为何该变化先于其他发生。

**讨论：** 七步循环反映今天的工程现实：每步是独立组件有自己的工程表面、自己的 eval、自己的运维。结构短期持久因为组件没有自然融合压力：向量数据库和重排序器做不同的事；分块器和嵌入模型做不同的事。

**候选融合**：**嵌入 + 搜索 + 重排序融合为单一检索 API**。到 2030 年，_检索即服务_ API 可能在单一端点后处理嵌入、索引、搜索和重排序，团队指定 _检索什么_ 而无需工程每一层。Pinecone、Vespa 和一些 2026 年的产品已朝此方向移动。此融合先发生的原因：

1. **它有最强的融合运维压力。** 嵌入模型选择、索引调优和重排序器调优紧密耦合；分开工程产生协调开销，融合服务可消除。
2. **接口干净。** 输入：文档 + 查询。输出：相关文档。内部（嵌入、索引、重排序）从应用视角是实现细节。
3. **成本经济学偏向整合。** 将嵌入服务 + 向量数据库 + 重排序器作为独立组件运行在延迟和运维上昂贵；融合为单一服务减少两者。

**其他可能或可能不变更的步骤。**

* _分块_：保持独立。分块是语料库特定的（法律文档 vs 代码 vs 记录）；统一 API 无法在无语料库知识下做出正确选择。分块保持工程表面。
* _构建 prompt_：保持独立。应用拥有 prompt；这是代码级关注非服务级。
* _生成_：保持独立（它是 LLM 调用）。形状可能演化（第 8 章 Q3 的模型原生检索）但步骤存在。
* _后处理_：保持独立。引用渲染、schema 验证、片段提取是应用逻辑。
