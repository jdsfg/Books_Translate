这与 §1.6 对 AI 工程本身所做的练习相同，现在应用于一个具体的架构模式。四个答案中的每一个都应特定于引用验证，而非通用的。

**答案：** 引用验证后处理器的四个答案：

1. **模式**：针对确定性真相来源的事后输出验证。模型产生草稿输出；确定性验证器提取声明（此处：被引用的参考文献），对照权威来源检查它们（此处：引用数据库或 DOI 查询），并在输出到达用户之前标注、编辑或拒绝输出。这是更广泛的 _用代码检查模型_ 模式的特例，以多种形式出现（结构化输出的 schema 验证、查询生成的 SQL 验证、工具调用参数验证）。第 7 章（结构化输出）和第 23 章（生产安全）是系统化处理这一模式的地方。
2. **eval**：约 100 个已知会从模型引出引用密集输出的 prompt 的 golden set，每个手动标注哪些引用是真实的哪些不是。指标是 _hallucination 捕获率_：在模型产生的 hallucinated 引用中，后处理器标记了多少比例？加上 _误报率_：后处理器多久将一个真实引用标记为 hallucinated 因为验证器遗漏了它？阈值：捕获率 ≥0.95，误报率 ≤0.05。回归检查：每次 prompt 变更、每次模型版本变更、每次验证器源语料库变更时重新运行。第 4 章构建 eval 纪律；第 5 章将其接入 CI。
3. **故障模式**：验证器的真相来源不完整。模型引用了一篇真实但冷门的论文；验证器数据库中没有这篇论文；后处理器将其标记为 hallucinated 并移除。用户失去了一个有效引用。工程缓解措施是设计验证器具有 _优雅的未知_ 响应：而非二元的已验证/未验证，返回已验证、未验证且未找到、或未验证且不匹配，并在面向用户的呈现中区别对待 _未验证且未找到_ 和 _未验证且不匹配_。第 23 章涵盖这种分层故障模式处理。
4. **成本**：后处理器增加两项成本。第一是到引用验证器的 API 调用（CrossRef 对中等流量免费；商业来源按查询收费）。第二是延迟：每次验证增加 100–500 毫秒取决于验证器；如果引用频繁，这会在输出管道上串行化。美元成本通常可忽略；延迟成本对交互式功能可能显著，可能需要并行验证或流式友好架构。第 17 章（多模型路由）和第 18 章（成本熔断器）是将这些每次调用成本转化为规模化可管理预算的章节。

这个练习说明了四问题准则如何从章节级概念（§1.6 将其应用于 AI 工程本身）缩小到模式级决策：同样四个问题告诉你你有一个真正的工程计划还是只是一个直觉。
