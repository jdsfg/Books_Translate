关于 Aiyana 发布的量表的一个诚实说明：它有四个轴（临床准确性、完整性、格式、简洁性），它 _没有_ 评分 _语气_。这正是下一节要讲的遗漏故障模式。Beacon 的试点没有暴露语气问题（临床笔记摘要是格式化文档，由临床医生阅读，而非给患者的对话响应），但 _我们没有测量什么维度？_ 这个问题应该在 eval 设计时被显式提出，量表应该记录关于语气的决策（在这个案例中，_不适用于此输出格式；格式约束了风格_）而非让缺失隐含。§4.11 传达的教训是 eval 的沉默很重要，这里的示例也不例外。

### 4.11 How This Breaks：你没写的指标

**命名的故障模式**：你没写的指标。一个团队构建 eval，对 golden set 评分，达到阈值，发布。六周后，功能在生产中对团队未包含在 golden set 中的一类特定输入失败，未评分，未检测，因为他们的 eval 没有测量该故障模式。eval 给了团队信心；信心是错位的，因为 eval 不完整。

**真实或复合事件**：一个来自整个行业的复合例子。一个构建客服助手的团队构建了一个专注于 _助手是否正确回答了问题？_ 的 eval。eval 有 300 个案例；助手在 eval 上得分 91% 并发布。在生产中，助手偶尔粗鲁（对沮丧客户使用简短、轻蔑的语气），因为 prompt 被调优为简洁，而模型从中提取的训练数据有简洁响应在情感输入上滑向粗鲁的例子。eval 没有测量语气，所以 eval 没有看到它。客户看到了；投诉到达；团队将语气加入 eval，发现回归，修复 prompt。修复花了一周。期间的客户损失是真实的。

**工程缓解措施**：每个 eval 应该有 _覆盖审查_。在 eval 接入 CI 之前，一个高级工程师（理想情况下还有工程团队外的利益相关者）审查 eval 的切片并问：_什么故障模式不在这个列表中？_ 常见遗漏要检查：语气；文化/语言边缘案例；安全（拒绝、prompt 注入）；成本纪律（prompt 是否产生合理长度的输出？）；跨用户段的公平性；在罕见但重要输入上的表现。覆盖审查在发布前暴露差距。
