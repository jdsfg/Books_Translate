**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_设计退款工具的策略门控：检查、顺序、拒绝响应、审计轨迹。_ 你验证 (a) 检查顺序高效（便宜检查先，清晰序列），以及 (b) 拒绝响应实际帮助 LLM 恢复（LLM 可能建议通用"策略违规"消息；坚持可操作细节）。

**Q4.** _诊断工具误用模式_。你的 Helios agent 日志显示 LLM 频繁调用 `search_knowledge_base`，即使用户问题是关于其特定订单的（`lookup_order` 更合适的情况）。模式增加延迟并产生更低质量答案。诊断并提出三个修复。

**答案：** 诊断：LLM 未区分 _一般问题_（知识库正确）和 _订单特定问题_（订单查找正确）。可能原因：

1. **工具描述不清晰**：描述未使区别明显。LLM 默认到更熟悉的工具（知识库搜索）。
2. **prompt 未引导工具选择**：系统 prompt 未告诉模型何时偏好一个工具而非另一个。
3. **用户问题模糊**：像"我的包裹在哪？"的问题没有明确订单 ID；LLM 回退到知识库。

三个修复：

**修复 1：改进工具描述**。

更新 `search_knowledge_base` 描述：

> 搜索通用知识库以获取关于政策、流程和 FAQ 的答案。不要用于关于特定客户订单、账户或交易的问题；改用 lookup_order、get_customer_history 或其他特定工具。

更新 `lookup_order` 描述：

> 查询特定客户订单的详情。当用户提及或暗示关于其特定订单的问题（包裹状态、商品详情、退款资格、配送）时使用。如用户未提供订单 ID，在调用前询问。

更清晰的边界帮助模型正确选择。

**修复 2：在系统 prompt 中添加路由前缀**。

添加到系统 prompt：

> 当用户提问时，首先识别问题是一般的（用 search_knowledge_base）还是订单特定的（用 lookup_order）。如问题提及"我的订单"、"我的包裹"、"我的退款"、"在哪"或类似短语，视为订单特定。

显式路由引导塑造 LLM 的工具选择。

**修复 3：添加查询分类步骤**。

用小 LLM（Haiku 或 mini）在主 agent 循环前将用户查询分类为 _一般_ vs _订单特定_。将分类作为上下文传给主 agent：

    分类：订单特定
    建议首选工具：lookup_order


分类便宜（约 0.0001 美元）且显著改善首选工具选择准确性。

**推荐顺序**：先试修复 1（最低工程成本；通常影响最大）。如仍误触发，添加修复 2。修复 3 留给 LLM 尽管有更好描述和 prompt 仍持续在模糊查询上失败的情况。

通过 eval 测量改进：跟踪 _首次工具调用正确性_ 作为指标；修复前后应显示可测量增益。
