**推荐序列**：

* 首先，修复 prompt（便宜、快、通常最大收益）。
* 运行 eval。如忠实性提升到 >0.85，停止。
* 如不，添加引用强制。
* 如不，在部分查询上升级模型层级。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_我们的 RAG 检索 recall@10 = 0.85 但忠实性 = 0.62。客户报告声明不在检索块中。诊断并优先排序修复。_ 你验证 (a) 优先排序对你的 eval 证据合理（LLM 可能建议先升级模型层级；那通常错误，prompt 修复更便宜），以及 (b) 提议的 prompt 变更足够具体以实现（LLM 可能给通用"接地"指令；坚持操作细节如引用要求）。

**Q5.** _调试重排序器造成损害的质量回归_。你的团队向纯向量 RAG 管道添加了 Cohere 重排序器。eval 显示：检索 recall@10 从 0.78 升到 0.82（小幅提升，如预期）；答案忠实性保持 0.81；但总体通过率 _下降_ 从 0.73 到 0.68。客户报告答案感觉"更薄"且遗漏以前包含的上下文。诊断回归并提出修复。

提示

重排序器缩窄了上下文。想想那对 LLM 的输入做了什么。

**答案：** 诊断：重排序器正确做其评分工作（recall 提升确认）。通过率下降来自下游的 _缩窄_ 步骤：之前 LLM 看完整 top-10；现在看重排序器的 top-N（通常 3-5）。重排序器的 top-N _每块更相关_ 但 _总块更少_。对于需要跨多块综合的查询（生产 RAG 中常见情况："X 和 Y 的区别是什么？"、"总结三个相关条款"），LLM 现在有更少上下文并产生更薄答案。

忠实性数字不捕获此因为忠实性测量 _声明是否被检索块支持？_——而检索块（现在更窄）被良好支持。变薄是 _完整性_ 问题，非 _忠实性_ 问题。多轴量表（上面的 Q5）会捕获它；如果你的团队只评分总体通过和忠实性，完整性轴缺失。

根因：过于激进的 top-N（例如重排序器 → top-3 当许多查询需要 top-7 的综合材料）。重排序器的分数是每块相关性，非 _这 N 个块一起覆盖查询吗？_

修复，按成本排序：

1. **加宽 top-N**：从 3 提到 7（或 5 到 10）。让 LLM 看更多重排序器的高置信选择。重跑 eval；如完整性恢复，停止。成本：更多 token 给 LLM（约 0.001 美元/查询）。
2. **使用分数阈值而非固定 top-N**：保留所有高于重排序器分数阈值（例如 0.4）的块。对于多块相关的查询，保留更多；对于一个明确答案的查询，保留更少。自适应。
3. **向 eval 量表添加完整性轴**：按 Q5，RAG eval 需要忠实性和完整性。没有该轴，你看不到此类回归。添加它是永久 eval 纪律；无论重排序器是否保留都做。
