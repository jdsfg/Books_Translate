#### 定义：Eval

对系统输出质量在固定输入集合上、对照已定义的 _好_ 的概念的可重复测量。测量产生数值分数（或分数向量），可在系统版本间比较以检测改进或回归。

用通俗语言说：eval 接受你的系统，在已知输入集合上运行它，对输出评分，给你一个你可以信任的数字。信任来自输入是固定的、评分是可操作的、指标是跨运行可比较的这一事实。

六个组件：

1. **golden set**：一个精选的输入（以及通常的参考输出）集合，eval 在其上运行。有时称为 _测试集_、_基准_ 或 _eval 套件_。
2. **参考标准**：对于 golden set 中的每个输入，什么算好的输出？可以是单一规范答案（抽取式 QA）、一组可接受答案（开放式 QA）、评分量表（作文评分），或与基线的比较（偏好对 eval）。
3. **指标**：接受系统输出和参考标准并产生分数的函数。精确匹配、F1、BLEU、ROUGE、语义相似度、LLM 作为评判者、人工评分：菜单很长；选择很重要；我们将在 §4.5 中逐步讨论。
4. **运行器**：接受系统、golden set 和指标并产生报告的代码。在生产中这是 `pytest-evals` 或 `ragas` 或 `inspect-ai` 或你自己的内部工具（第 5 章）。
5. **阈值**：最低可接受分数。低于阈值，变更不发布。设置阈值是纪律的一部分。
6. **节奏**：eval 何时运行？每次 PR（CI 门禁）？每晚计划（漂移检测）？发布前手动？在生产中，采样（实时 eval）？不同节奏服务于不同目的；生产级系统使用多种。

如果你只有其中五个，你有一个不完整的 eval。最常见的遗漏是 (3)：团队收集输入但从未将评分操作化；以及 (5)：团队测量分数但从未就 _足够好_ 的含义达成一致，所以 eval 变成没人行动的报告。两种遗漏都是相同的失败：半构建的基础设施不改变行为。
