理由：5 人团队工程带宽有限，难以承受框架复杂性。Pydantic AI 的轻量人体工程学匹配团队可能的 Python 类型化代码库；框架小到团队可在需要时调试进去。MCP 给团队可移植的工具层（团队的工具适用于任何 LLM provider，对未来 provider 变更免疫）。组合：足够框架提高生产力，不多到团队与框架对抗。

相反选择（重型 LangChain 栈）对此规模错误：太多抽象开销；太多东西要在提高生产力前学习。

如团队增长超过 30 人并开始有多个 AI 工程团队：重新评估。LangGraph 的可视化和基于图的调试可能在该规模证明其价值。

**Q4.** 计算机使用（§15.5）的"如能构建真正 API，就做那个"启发式是什么？团队何时应违反它？

**答案：** 启发式：当 agent 需要与外部系统交互时，偏好构建 API 集成而非使用计算机使用，因为 API 比计算机使用更可靠、更快、更便宜、更易审计。

违反在以下情况合理：

1. **API 不存在且无法构建**。外部系统无 API；系统供应商不愿添加；逆向工程非官方 API 脆弱。计算机使用是唯一路径。
2. **集成成本超过用例价值**。构建自定义 API 集成需工程师周；用例是一次性或低量；计算机使用更高的每任务成本低于工程师周。常见于长尾企业集成。
3. **无障碍/面向用户自动化**。用户希望 agent 在其环境中操作 _自己的应用_。API 不适用因为应用没有用户可访问的 API；计算机使用让 agent 代表用户行动。

启发式的优势：它正确识别大多数生产集成工作应是 API，非计算机使用。启发式的劣势：有真实长尾其中计算机使用是正确答案，教条的 API 偏好错过这些情况。正确纪律：针对启发式评估具体用例；不盲目跟随。

**Q5.** 第 14 章引入单 agent 系统的四界模式。多 agent 系统用系统级界扩展有界工程（本章 §15.7 和上面 Q4）。每 agent 界即使每个都正确实现，为何无法在多 agent 系统中提供充分安全的根本原因是什么？识别两个每 agent 界单独无法防止的具体多 agent 故障模式。

**答案：**

根本原因：**每 agent 界对单独 agent 强制安全，但多 agent 系统在系统级有涌现行为，没有单独 agent 的界能约束**。每个 agent 可能在自身界内完全运行而 _系统_ 整体超出合理行为。有界 agent 的组合本身不是有界的，除非施加显式系统级界。
