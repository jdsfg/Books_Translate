思考团队实际会运行的查询：过去 60 天的趋势、跨所有运行按单个 eval 案例过滤的分数、运行与使用的 prompt 版本之间的连接。SQL 给你什么扁平文件不能给的？

**答案：** SQLite 解锁的三个能力：

1. **带 SQL 语义的跨运行查询**。一个典型问题是"显示自 prompt 版本 1.4.0 以来案例 Y 在维度 X 上的分数趋势。"对扁平 JSON 文件这需要写自定义脚本打开每个文件、解析 JSON、过滤案例并聚合。对 SQLite 这是四行 SQL 查询。能力不是新的（你总可以写脚本）但摩擦低得多以至于团队实际运行查询而非跳过它。需要每次查询自定义工具的纪律倾向于萎缩；SQL 是标准工具。
2. **运行、prompt 版本、golden set 版本和作者之间的连接**。一旦存储有运行、prompt、数据集和作者的表，你可以问"哪些工程师的 PR 产生了最大的回归-然后-恢复模式？"或"哪些 prompt 版本在对抗性分层上表现最好？"这些多表连接是 SQLite 的原生惯语；对扁平文件重现它们需要手动重新实现关系查询模式。
3. **绑定工作流的索引查找**。§5.6 GitHub Actions 工作流需要高效获取当前 main 分支 HEAD 的基线运行。用 JSON 文件，这意味着扫描文件直到找到正确的。用 SQLite，(branch, commit_sha, dataset_version) 上的索引在微秒内返回行。在低量时差异不可见；在每周数百次运行时，这是 30 秒完成的工作流和向分钟爬行的工作流之间的区别。

应该超出 SQLite 的情况：当 eval 存储成为跨组织多个团队使用的共享系统，有来自大规模 CI 运行的并发写入者（数十个同时 PR 运行），以及包括来自仪表盘的重分析查询的读取模式。SQLite 的单写入者模型在该规模附近成为瓶颈，团队应迁移到 Postgres 或托管分析存储（Snowflake、BigQuery、ClickHouse）。如果 schema 从一开始就合理设计，迁移是直接的；从 SQLite 开始的纪律正确恰恰因为迁移路径容易。在小规模时过早迁移到 Postgres 是更常见的错误。
