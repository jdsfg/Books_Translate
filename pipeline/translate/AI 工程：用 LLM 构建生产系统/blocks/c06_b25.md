到 2030 年净效果：可能相同的总体框架（受监管的自建、通用的购买、中间混合），但两侧的 _劳动力_ 都显著下降。eval 基础设施可能从中等规模团队 10-20% 的工作降至 5% 的工作。eval 驱动工程的纪律将保留；成本将压缩。

一个变数：**如果 2030 年前沿模型可靠地比当前 LLM 作为评判者更好？** 那么校准纪律（对人工的 kappa）也压缩，因为评判者比人工彼此之间更可靠地与人工对齐。这将是一个不同的世界；eval 设计工作从 _校准评判者_ 转向 _设计评判者将应用的量表_，这是有意义的但更小的变化。纪律存活；实现改变。

诚实的总结：工具比纪律变化更快。eval 驱动工程的纪律是本章教授的持久东西。具体工具名是时间戳的。

**Q3.** _eval 作为 CI 本身应该被 eval 吗？_ 绑定工作流 #1（§5.6）是一段工程：一个 GitHub Actions 作业、一个比较脚本、一个门禁规则。第 4 章论证任何有后果行为的工程制品都值得 eval。递归地应用那个推理：eval 作为 CI 工作流本身需要 eval 吗？论证你的立场。如果是，勾勒元 eval 会测量什么；如果否，指出与 eval 纪律其余部分的不类比。

**讨论：** **支持是**：eval 作为 CI 工作流有后果行为。它阻止 PR 合并，这有真实成本（被阻止的工程时间）和真实收益（防止的回归）。它可以以特征性方式失败：误报（阻止了实际上未回归生产行为的 PR，也许因为 LLM 作为评判者噪声）和漏报（让通过了 golden set 未覆盖的切片中回归的 PR）。这些故障模式正是第 4 章纪律论证应该被测量的那种。元 eval 会随时间测量：误报率（被门禁阻止的 PR 后来被判定为无回归，要么通过撤销门禁裁决要么通过回顾性审查生产行为），漏报率（门禁未捕获的生产回归，事后当客户投诉或 AI 运维升级时识别），以及真实回归的检测时间。这些是可操作化的；每季度运行元 eval 是可行的。工作流的故障模式变得可见，团队可以基于数据而非直觉调整门禁阈值。
