#### 深入思考

**Q1.** _RAG 的终结_。推测：到 2030 年，如果上下文窗口在工作马层级达到 10M+ token，RAG 还必要吗？论证双方。指出一个你预测在 2030 年即使上下文窗口巨大仍会使用 RAG 的特定应用。

**讨论：** **终结论证**：10M token 上下文窗口将使 RAG 对几乎所有中小型语料库过时。当今大多数生产系统的语料库远低于 10M token；如果放得下，直接放入上下文。工程简化是戏剧性的：无嵌入模型、无向量数据库、无分块、无重排序、无检索 eval 管道。成本故事在高量系统上可能偏向 RAG，但有了 prompt 缓存和更便宜的工作马层级模型，甚至成本也可能偏向长上下文。

**RAG 存活论证**：某些应用有内在的大语料库且无限增长。Strata Research 的法律语料库数亿 token 且在增长；即使 10M 上下文窗口也无帮助。Helios 的按租户知识库跨客户总计数十亿 token。Web 搜索作为长上下文不合理（Web 是数万亿 token）。RAG 在非常大的一端存活。

**特定 2030 年应用**：持续更新的实时语料库（新闻、社交媒体、金融数据）。即使有 100M token 上下文，你不能在每次调用中包含刚更新的新闻语料库：语料库变化比你重新编码快。对最近更新索引的检索是自然模式。RAG 为新鲜度是持久的。

**净预测**：RAG 在 2030 年缩小，应用于更窄的案例集（巨大静态语料库；实时更新；按租户隔离）。长上下文扩展。决策树的层级边界急剧移动；_结构_（基于语料库大小的分层架构）持续。上下文工程作为更广泛框架的纪律——甚至更重要。

**Q2.** _上下文即架构_。本章论证上下文工程是独立学科，区别于 prompt 工程。扩展这个：论证上下文预算是 _架构性_ 学科，不仅是编码学科。这对团队应如何围绕它组织意味着什么？

**讨论：** 将上下文框架为 _架构性_ 关注（而非按功能关注）有组织含义。

当上下文是按功能的，每个发布 LLM 功能的产品团队自己处理上下文工程。它们做局部决策：prompt 中放什么、如何处理历史、何时摘要。局部决策累积成难以推理的全公司图景：按租户成本差异巨大；一些团队发现 prompt 缓存，其他没有；相同的检索上下文模式按团队重新实现。

当上下文是架构性的，公司有 _上下文平台_：主要手段的共享基础设施（一致应用 prompt 缓存；标准摘要库；共享检索管道；标准化工具加载模式）。各团队使用平台；跨团队改进复合。

这是 2026 年起的模式。在小公司，上下文是按功能的（平台投资超过收益）。在有 5+ AI 工程团队的公司，平台投资回本：按团队重复下降；成本纪律上升；全公司上下文策略可见且可改进。
