#### 模式 7：Eval-as-CI 门控

**解决什么问题。** prompt 变更、模型升级或 RAG 重构静默回归质量。回归在数周后通过客户投诉发现；违规变更埋在二十个无关提交下且回滚昂贵。Eval-as-CI 将质量检查移到变更时刻。

**拓扑。** 团队维护黄金 eval 集——100 到 1000 个输入/预期输出对，在 git 中与代码一起版本化，带文档化刷新节奏（通常季度，在 eval 提交中带"什么变了及为什么"注释）。触及 prompt 文件、模型标识符或 LLM 调用路径上任何代码的 PR 触发 CI 作业。作业对黄金集运行候选，计算指标（结构化任务的精确匹配；开放式任务的 LLM-as-judge，judge 对照人工标注子集校准），并将结果作为 PR 评论发布带与合并基线基线的差异。如任何指标回归超过已发布阈值——通常主指标 2-5 个百分点，或固定不可回归子集上的任何下降——CI 失败且 PR 被阻止。阈值和固定子集本身版本化；放宽阈值需自己的带理由的 PR。成本通过每次推送运行便宜可重现子集且仅在合并基线更新或显式 `/run-full-eval` 评论时运行全集来界定。

**何时用。** 你后悔过至少一个到达客户的静默回归。CI 基础设施就位（GitHub Actions、Buildkite、Jenkins）。eval 集可策划——团队能以足够具体性表达"好"以写 100 个示例。

**何时不用。** 你尚未弄清好看起来像什么——校准前的 eval-as-CI 会因噪声阻止 PR。或产品太早使 prompt 每天变且无稳定目标。先投资 eval（第 5 章）；当集稳定时翻转 CI 门控。
