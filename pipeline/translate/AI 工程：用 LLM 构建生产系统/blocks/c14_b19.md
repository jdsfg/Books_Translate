关键元素：

* **结构化错误类别**（success / code_error / timeout / infrastructure_error）。不同路径供 LLM 恢复。
* **仅基础设施错误重试**。代码错误是确定性的（重跑无帮助）；超时是确定性的（代码太慢）。
* **有界输出**（`stdout[-4000:]`）用于 LLM 上下文预算。
* **日志**带 request_id 用于可追溯性。
* **成本计数器**集成：每次调用成本分配到请求（第 18 章 / 第 19 章）。
* **超时验证**在执行前。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_编写围绕 E2B 的生产级代码执行包装器：结构化错误、日志、基础设施（非代码）重试、成本跟踪。_ 你验证 (a) 重试策略正确区分基础设施和代码错误（LLM 可能默认重试一切），以及 (b) 成本分配调用匹配你的成本跟踪系统 API。

**Q3.** _设计退款工具的策略门控_。Helios 退款工具敏感。设计策略门控。指定：(a) 策略层执行的检查；(b) 检查顺序；(c) 策略拒绝时 LLM 看到的响应格式；(d) 审计轨迹。

**答案：**

(a) **检查**：

1. 金额在租户的退款金额限制内（`amount <= tenant.refund_limit_cents`）。
2. 客户的终身退款次数低于此租户的阈值。
3. 订单存在且匹配客户（`order.customer_id == customer.id`）。
4. 订单可退款（状态是 `delivered`、`shipped` 之一，非 `cancelled` 或已退款）。
5. 退款理由非空且在长度限制内。
6. 客户已在对话中显式确认（agent 必须先通过单独的 `confirm_refund_intent` 工具设置的状态标志）。

(b) **检查顺序**：便宜的确定性检查先（输入验证、订单存在），然后业务逻辑检查（限制、资格），然后状态检查（客户确认）。早失败避免昂贵工作。

(c) **拒绝时的响应格式**：


    {
        "status": "policy_rejected",
        "reason": "amount_exceeds_limit" | "order_not_refundable" |
                  "confirmation_required" | ...,
        "detail": "1500 美元退款超过租户每次退款限制 1000 美元。"
                  "通过 escalate_to_supervisor 工具升级。",
        "suggested_action": "escalate_to_supervisor",
    }


结构化拒绝告诉 LLM 什么失败了及推荐的下一步是什么。模型然后可调用 `escalate_to_supervisor` 或组合面向客户的解释；两种响应都优雅。

(d) **审计轨迹**：

* 每次策略检查，通过或失败，记录：request_id、customer_id、order_id、请求金额、所有检查结果、最终决定。
* 每次成功退款记录：谁（agent 的 request_id）、什么（退款详情）、为什么（LLM 提供的理由加策略推导的事实）。
* 审计日志进入防篡改存储（仅追加；签名条目）。可供合规和客户支持监督使用。

这满足 §13.4 的原则：LLM 可以想发任何退款，但策略层强制实际允许的；审计轨迹完整；LLM 的不当行为或 prompt 注入无法绕过策略。
