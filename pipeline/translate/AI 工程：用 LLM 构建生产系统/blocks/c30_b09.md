上表指向哪个。

* 对每个生产 AI 功能，我们有每次变更都运行并在回归时阻止合并的 eval。
* 我们今天能说出每个生产功能每活跃用户每天和每活跃租户每月的成本。
* 每个 LLM 调用返回带可辨识成功/错误/拒绝变体的结构化响应，类型系统强制我们处理。
* 每个 LLM 调用被追踪；我们的 agent 有轨迹级可观测性。
* 生产中的每个 agent 有 {迭代上限、成本断路器、按工具断路器、工具调用去重、观察验证} 的全部。
* 我们的 prompt 存在版本化注册表中，非作为内联字符串散布在代码库中。
* 我们的 LLM-as-judge 已在 ≥ 50 案例上对照人类校准且 κ ≥ 0.6，且我们在每次模型升级时重新校准。
* 我们有多提供商路由层；我们非单提供商锁定。
* 我们在处理不可信内容的每个地方都有 §23.3 的全部四层 prompt 注入防御。
* 我们在功能范围界定时有 _能否 eval_ 门控，且我们在此门控终止过功能。
* 我们至少执行过一次真正的模型升级工作流且不会被下一次弃用惊讶。
* 我们有事件事后复盘文化；每个 Sev-2 或更严重的事件产生至少一个新 eval 案例。

十二个 _是_ 是 2026 生产 AI 工程能力水平。多数团队回答 _是_ 到六或七个并有明确的修复清单。检查清单的目的不是给团队打分；而是使缺口具体到可以分配人员。

### 关于反向反模式的说明

并非每个团队都面临全部七个的风险。面临反模式 2（用框架过度工程）的团队常是 _不_ 面临反模式 1（无 eval 就发布）的同一团队：他们到处过度构建，包括 eval 层，他们的问题是速度，非质量。面临反模式 1 的团队常 _不_ 面临反模式 2：他们精简快速发布且不伸手框架；他们的问题是缺少能告诉他们 _快_ 何时变成 _坏_ 的测量层。

同样的反转出现在反模式 6（工作流足够时构建 agent）和未陈述的反向——欠构建的团队，通过坚持刚性工作流而将有界 agent 能更好服务用户的能力留在桌上。多数故障模式有镜像故障模式，工程判断是识别你的团队在镜子哪一侧。

速查表是筛查工具，非需满足的检查清单。选出你的团队真正面临风险的两三个反模式——通常它们按团队文化聚集：谨慎的团队面临 2 和 6 的过度工程形式；快速移动的团队面临 1、3 和 7 的欠工程形式；几乎每个团队都面临 4 和 5 因为成本和 eval 校准是不自我宣告的安静故障——然后专门工程对抗那些。试图均等地防御全部七个本身就是反模式 2 的一种形式。
