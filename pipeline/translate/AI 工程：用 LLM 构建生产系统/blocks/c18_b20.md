* 在强制系统中将每租户上限配置为合同约定的 1500 美元/月。激活它。未来超过预算的调用返回 429 带清晰错误："月度预算已超出；请联系您的客户经理。"
* 对当前月，4200 美元是沉没成本。按合同向租户计费（1500 美元保留费 + 按合同超额条款的超上限费用，如有）。如无超额条款，损失被吸收；团队吸取教训。
* 通知客户团队使他们拥有与租户 X 的对话。

(d) **策略级修复**（2 周内）：

* 审计全部 200 租户：对每个，验证合同预算匹配强制系统配置。预期发现：更多像 X 这样的租户存在配置错误的上限。
* 构建租户上线检查清单包含"验证每租户预算已在强制系统中配置"。将此作为发布门控；无租户在未配置前上线。
* 添加季度审计：将合同预算（来自 CRM）与强制系统上限比较。不匹配被标记。
* 添加告警：租户超过其上限 80% 时触发对客户团队和工程值班的告警。意外是系统性的；团队必须尽早知道。

(e) **客户沟通**：客户团队给租户 X 的一封有分寸的信：

* "您本月的使用已超出合同推理预算。按合同，[条款]。具体而言：占平台容量 28% vs 您合同约定的 4% 份额。"
* "我们已实施预算上限；今后超出合同限制的进一步调用将返回速率限制错误。"
* "如您的业务需求已变化且需要更高预算，我们可以讨论升级。否则，我们建议审查您的使用模式；我们的诊断团队可以帮助识别 API 调用可能不是正确模式的地方（例如，对我们观察到的简单案例使用 regex 而非 LLM）。"

客户关系基调坚定但建设性：我们在执行合同；我们也愿意帮助。一些租户合理需要更高预算且愿意支付；其他在不知成本情况下过度使用；对话浮现哪种。

更深的教训：预算强制不仅是技术控制；它是需要 CRM 到平台数据流、审计频率和客户团队协调的 _合同执行_ 纪律。工程的角色是使控制可用且数据正确；运维纪律是跨职能的。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_一个租户超出合同推理预算约 3 倍。设计立即行动、策略修复和客户沟通。_ 你验证 (a) 立即行动和策略修复是分开的（LLM 可能合并它们；坚持既有当前行动也有系统性预防），以及 (b) 客户沟通坚定但不对抗（目标是合同执行，非惩罚；LLM 可能在任一方向过度）。
