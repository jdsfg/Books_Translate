#### 常见误解

hallucination 无法通过 prompt 消除。"告诉模型不要 hallucinate，它就不会"是一个诱人但不可靠的信念。模型没有 _不要 hallucinate_ 的开关。你有时可以通过提示模型表达不确定性（"如果你不知道，就说不知道"）来降低 hallucination 率，但模型对这一指令的遵从本身就是训练行为，且随 prompt 和主题而变化。对 hallucination 的可靠缓解是 _架构性的_：用检索到的事实来 ground 模型（RAG），结构化输出（强制 JSON schema 使模型必须提交到带验证的特定字段），给模型工具来查找信息（第 13 章），以及设计系统在置信度低时优雅拒绝（第 23 章）。仅靠 prompt 的 hallucination 控制不是工程级的。

### 2.7 为什么 LLM 对 prompt 敏感

对 prompt 措辞的小改动可能产生明显不同的输出。这对习惯确定性接口的工程师来说很震惊。在架构层面的解释很简单。

模型的下一个 token 分布是通过用学习到的 attention 机制 attend 到输入序列中的每个 token 来计算的。不同的 token 对分布的影响不同。当你改变 prompt（比如，把 _请总结这个_ 换成 _总结以下内容_）时，你在改变输入序列，模型对该序列的 attention 模式会不同。对输出的下游影响可能比 prompt 表面变化所暗示的更大。

这 _不是 bug_。这是模型按设计行事。模型不是将你的 prompt 解析为语义意图然后对意图采取行动；它是在计算以你提供的具体 token 为条件的下一个 token 分布。意图隐含在 token 中，改变 token 就改变了条件。

几个实际后果：

**prompt 是版本化工件。** 如果一个 prompt 在你的生产系统中，它就是代码，它值得与任何其他生产代码相同的版本控制、代码审查和回归测试。第 6 章将把这个变成 prompt 注册表模式。

**prompt 变更需要 eval 回归检查。** prompt 变更可能在没有任何明显用户可见症状的情况下微妙地退化输出质量。唯一可靠的检测是 eval 套件。第 5 章构建工作流。

**few-shot 示例很重要。** 在 prompt 中向模型展示 2-5 个你想要的示例通常比详细的自然语言指令产生更大的行为变化。模型对示例的模式匹配比对抽象指令的解读更可靠。第 6 章将展开这个技术。
