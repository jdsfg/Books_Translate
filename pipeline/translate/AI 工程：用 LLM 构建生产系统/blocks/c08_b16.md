**集群 A：schema 太刚性（可能）。** 签名是兜底值飙升。模型选择 `unspecified` 因为没有其他变体适合；schema 的类别集对模型所见太窄。可能原因：输入分布偏移；源文档中出现原始 schema 未预料到的新类别。修复：(1) 采样产生 `unspecified` 的输入；聚类它们；识别缺失类别。(2) 添加新变体或拓宽现有变体以覆盖新类别。(3) 重新运行 eval 确认新变体解决飙升而不回归其他维度。

值得检查的替代诊断：模型本身偏移了（provider 发布了新版本）。如果输入分布看起来未变但模型在兜底上的校准变了，修复在 prompt 上（重新迭代以加强何时用 `unspecified` vs. 特定变体）。

**集群 B：schema 太宽松（可能）。** 签名是 schema 验证通过但内容错误。验证器不捕获会捕获错误内容的东西。可能原因：字段接受一系列值其中某些语义错误（例如 `severity: str` 字段应为 `Literal["critical", "major", "minor"]` 但留为 `str`；或日期字段接受未来日期而只应出现过去日期）。修复：(1) 审计最近失败；识别错误内容案例集中的字段。(2) 通过 Pydantic 约束收紧字段类型：`Literal`、`Field(pattern=...)`、`Field(le=...)`。(3) 如果约束依赖内容则添加自定义验证器（按 §7.4 的两个非显而易见验证器）。(4) 重新运行 eval 确认更紧的验证器捕获新失败。

**区分两者的诊断动作：** 集群 A 出现在 _输出值分布_ 中（某值频率飙升）；集群 B 出现在 _质量 eval_ 中（验证通过，评判者拒绝）。不同诊断数据，不同修复。生产系统需要两个监控层：值分布仪表板捕获集群 A；在生产样本上运行的质量 eval 捕获集群 B。本章的结构验证器 + 内容评估器模式是基础。

**附加：联合故障。** 两个集群也可能来自单一原因：输入分布偏移，schema 将新输入接受到错误变体中（足够宽松以接纳，足够刚性不判别）。那种情况下值分布和质量 eval 一起移动。通过阅读实际输出诊断；联合案例从数据可识别。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_带判别联合 schema 的生产提取器。集群 A：兜底值 18%，从 4% 上升。集群 B：验证通过但人工正确率从 0.91 降到 0.79。诊断每个为太刚性或太宽松；识别可能原因和修复。_ 你验证 (a) LLM 从签名区分两个故障模式，而非从通用建议（弱回答只对两者说 _迭代 prompt_），以及 (b) LLM 提出 _监控_ 角度（你需要值分布仪表板 + 质量 eval；LLM 经常只给修复而跳过下次更早捕获这些的检测层）。
