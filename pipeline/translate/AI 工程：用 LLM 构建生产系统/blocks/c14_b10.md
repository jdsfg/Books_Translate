### 13.8 Triangle Trade-off 侧栏：工具增强 agent 延迟（延迟分解格式）

典型 Helios 客户支持工具增强调用的延迟分解（4 步轨迹）：

阶段 | 延迟（ms） | 累计（ms）
---|---|---
初始 LLM 调用（决定第一个工具） | 800 | 800
工具执行：`lookup_order`（DB 查询） | 80 | 880
第二次 LLM 调用（决定如何处理订单信息） | 700 | 1580
工具执行：`search_knowledge_base`（向量检索） | 300 | 1880
第三次 LLM 调用（决定退款 vs 升级） | 700 | 2580
工具执行：`process_refund`（策略 + 事务） | 250 | 2830
最终 LLM 调用（组合响应） | 600 | 3430
**总 p50 感知延迟** | | **约 3.4 秒**

要解读的：

1. **LLM 调用主导**（3400ms 中的 2800ms = 约 80% 延迟）。每次工具调用需要后续 LLM 调用来解释；LLM 往返是延迟预算。
2. **工具执行快**（3400ms 中的 630ms = 约 20%）。单个工具调用通常快；慢在循环。
3. **减少迭代次数是最大延迟杠杆**。从 4 次迭代降到 2（通过并行工具调用或更好 prompt）将延迟大约减半。第 14 章探索此。
4. **更快模型线性帮助**。工作马模型（Haiku、mini）将 LLM 调用延迟从 700ms 降到约 400ms；总降至约 2.4 秒。权衡是质量（工作马可能做更差工具选择；同时 eval 成本/质量/延迟）。

对于 Helios 的交互客户体验，3.4 秒可接受；对于亚 1 秒语音 agent（第 20 章），此架构需要重大重做。
