### 2.8 为什么 LLM 无法可靠地数字母

这是 _模型擅长什么和不擅长什么_ 的一个经典问题。如果你问 Claude 或 GPT-4o _strawberry 这个词里有几个 r？_，你可能得到正确答案，也可能得不到。这不是单个模型的缺陷；这是 tokenization 的后果。

回忆 §2.1，模型从不看到文本。它看到整数 token。单词 _strawberry_ 在许多 tokenizer 中是一个单一 token，所以模型收到一个整数。要回答 _这个 token 里有几个 r？_，模型必须做一些不能自然从其架构中产生的事情：它必须内省一个其内部结构模型不直接处理的 token 的 _拼写_。模型有时可以做到这一点，通过利用训练数据中关于单词拼写的讨论，但这不可靠。模型的强项是 token 序列上的模式补全；模型的弱项是需要对这些 token 进行字符级访问的操作。

这可以泛化。LLM 不可靠的方面：

- 数字词中的字符数
- 数句子中的词数
- 确定子串的位置（一个 token 的第三个字符等）
- 反转一个词
- 字母重排
- 多位数的算术（现代 tokenizer 实际上将数字每位的拆分为一个 token 来帮助——但 transformer 架构仍然缺乏专用的进位传播电路，其有限的深度意味着多步算术超出了模型在单次前向传递中可靠完成的范围）
- 数列表中的项目，尤其是长列表

对工程师的缓解措施是 _不要要求模型做需要对 token 进行字符级访问的任务_。如果你需要数字符，在模型外的代码中做。如果你需要做算术，给模型一个计算器工具（第 13 章）。如果你需要反转字符串，在代码中做。模型擅长对序列的高级推理；模型不擅长字符级机制。知道区别是心智模型的工作。
