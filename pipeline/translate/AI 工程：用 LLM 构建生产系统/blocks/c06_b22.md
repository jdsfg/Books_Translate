**经常绊倒团队的 schema 决策**：决定 `case_scores` 应该每案例一行（所有维度作为列）还是每（案例，维度）对一行（长格式，如上所写）。团队经常以宽格式开始因为它感觉更自然（"每个案例是一行"），然后发现添加新量表维度需要 `ALTER TABLE`，这与并发写入交互不佳并使历史数据与当前 schema 不一致。长格式是正确的：维度是数据，不是 schema。转换为宽视图用于分析只需一个 SQL `PIVOT` 或 Python pandas `pivot_table`。预先支付长格式的小人体工程学成本以避免后来的 schema 迁移成本。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_设计一个支持运行、prompt 版本、数据集版本和每案例每维度分数的 eval 存储 SQLite schema。包括 CI 工作流的"获取分支 X 在提交 Y 的基线"查询所需的索引。论证 case_scores 的长 vs 宽格式选择。_ 你验证 (a) 外键实际强制引用完整性（SQLite 需要在连接打开时 `PRAGMA foreign_keys = ON`；LLM 常常忘记这个；没有它，外键声明是装饰性的）；(b) 索引匹配 CI 工作流将实际运行的查询模式（在代表性查询上运行 `EXPLAIN QUERY PLAN` 确认它使用索引）；以及 (c) 长格式论证是显式的（LLM 有时静默默认宽格式）。

**Q6.** _端到端构建快速套件/完整套件拆分_。按照上面 Q4 的第三个修复步骤，绘制将团队 eval 套件拆分为快速套件（门禁合并）和完整套件（每夜 + 发布前）的工程工作。覆盖：(a) 案例如何被标记以包含在每个套件中；(b) CI 工作流变更；(c) 在完整套件中检测到但快速套件中未检测到的回归如何呈现给团队；(d) 团队如何避免快速套件最终成为唯一有人看的套件的故障模式。在答案中引用至少一个第 4 章概念。

提示

快速套件是代表性子集；_如何选择子集_ 的问题很重要。对生产输入分布的分层抽样是一种方法；选择历史上区分 prompt 版本的案例是另一种。

**答案：**

(a) **套件成员资格的案例标记**：golden set 中的每个案例获得一个 `suite` 标签，值在 `{fast, full}` 中（一个案例可以仅在 `full` 中，或两者都在）。快速套件的选择标准：(i) 跨第 4 章 §4.6 覆盖审查识别为关键的维度的分层表示（无分层未表示）；(ii) 偏好历史上在 prompt 版本间产生大每维度分数变化的案例，这标志着判别价值；(iii) 目标规模 60-80 案例使快速套件并行化后在 30 秒内完成。标记为 `fast` 的案例每季度审查；上一季度产生低信号的案例轮出，其他案例轮入。
