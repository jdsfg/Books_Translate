**支持否**：不类比在于 eval 作为 CI 工作流的价值不在平均案例而在尾部。大多数 PR 不产生回归；门禁的大多数调用是无趣的。门禁的价值集中在如果不被捕获就会回归的小部分 PR 上。统计评估这个尾部集中的价值需要要么比实际可行的大得多样本量（运行数千个 PR 以检测门禁对少数本会回归的效果），要么比通常可得的更强 ground truth（你需要知道没有门禁时生产中会发生什么，这是反事实的）。eval 纪律对照代表性 golden set 测量不能干净地适配。工作流的正确纪律不是对自身的 eval 作为 CI，而是运营纪律：事后审查、被阻止 PR 的定期审查、偶尔的对抗性测试练习（提交已知坏变更以验证门禁捕获它）。

诚实的答案是 eval 作为 CI 工作流的 _某些_ 部分是可 eval 的而某些不是。比较脚本是一段有确定性行为的小代码；它值得单元测试（希望它有）但不值得 eval。门禁的阈值设置是可调参数；其对误报和漏报率的影响随时间经验上可测量，团队应将调优视为常规运营纪律，而非一次性的设置。评判者模型的校准（已被第 4 章 §4.5 覆盖）是可 eval 的部分。工作流的接线（GitHub Action 是否正确获取基线、运行比较、评论 PR？）可通过 CI 元测试测试（在带已知回归的合成 PR 上运行工作流，确认它产生预期的门禁裁决）。原则是：eval 行为概率性的部分，测试行为确定性的部分，接受某些运营纪律（事后审查、阈值调优）是既非概率也非确定部分的正确纪律。

递归问题（元 eval 需要 eval 吗？）在此终止。在某个点，工程纪律依赖于判断而非测量。第 24 章将回到那条线在哪里以及为什么正确画它是高级工程实践的一部分。
