### 6.8 How This Breaks：昨天还工作的 prompt

**命名的故障模式**：昨天还工作的 prompt。团队的 prompt 已稳定数月。Eval 通过；生产行为良好。Provider 发布了一个小版本模型更新——相同模型名、相同日期版本，但有微妙的后端变更（也许是分词器更新，也许是安全微调轮次）。Prompt 的行为偏移了。Eval 如果运行会捕获它；eval 如果不运行会让它通过。团队在客户抱怨新语气或意外拒绝模式时注意到。

**真实或复合事件**：一个复合例子。一个客服团队的 prompt 产生约 2% 的稳定拒绝率（模型拒绝回答的案例）。Provider 侧更新后，拒绝率跳到约 7%。Prompt 未变；API 调用中的模型标识符未变；行为偏移了因为 provider 的部署在固定版本下更新了。团队的 eval 每周运行，在下一次运行中捕获了偏移；变更和捕获之间的滞后是四天，期间客户投诉累积。

**工程缓解措施**：以比每周更细的节奏持续 eval。对于高量生产 prompt，每夜 eval 是工作下限；对于最高风险 prompt，每几小时运行一次 eval。成本小（每夜 eval 在典型规模下每 prompt 10–100 美元/月）；捕获时间从天降到小时。第 21 章构建生产 eval 模式。

第二个缓解措施：**订阅 provider 发布说明**并在任何小版本模型更新时主动重新运行 eval。这更多是运营纪律而非工程，但它重要；忽略发布说明的团队比阅读它们的团队更频繁地被惊讶。

**本应捕获它的 eval**：生产 prompt golden set 上的每夜 eval。Eval 已存在（按第 5 章）；故障是运营节奏，非 eval 设计。收紧节奏关闭差距。
