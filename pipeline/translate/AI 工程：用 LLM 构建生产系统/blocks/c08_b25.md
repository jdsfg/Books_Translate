设计选择 2：**不确定性是字段还是独立变体**。`confidence: float` 字段将不确定性嵌入成功；`HumanReviewRequired` 变体使不确定性成为自己的类型化结果。下游后果不同：`confidence` 字段要求下游代码在每个消费者上检查值（并知道什么阈值重要）；变体自动将输出路由到不同代码路径，无需消费者侧阈值逻辑。变体模式在 schema 中更重但在下游代码中更轻；字段模式在 schema 中更轻但将复杂性推给每个消费者。

通用原则：**schema 设计是下游设计**。隐藏失败的 schema 强制每个消费者发明自己的失败处理；结构化暴露失败的 schema 让消费者专注于成功。Schema 纪律的成本是真实的（更多变体、更多验证器）；下游的节省也是真实的且通常更大。高级工程师学会从下游代码想如何消费输出向后设计 schema，而非从模型能产生什么字段向前设计。

**Q3.** _收敛问题：结构化输出库在模型改进后存活吗？_ 2026 年，`instructor`、`outlines` 和 provider 原生 JSON schema 模式是必要的，因为没有这些工具的 LLM 产生的 JSON 有时无法解析或有时不符合。推测 2030 年：如果前沿模型自行达到有效完美的 JSON 一致性，这些库会过时，还是在其他理由上存活？论证双方。指出即使字面 _约束解码_ 问题被解决后仍存活的函数。

**讨论：** **过时论证。** 这些库解决特定技术问题：模型的下一 token 分布有时在会产生无效 JSON 的 token 上放置非平凡质量。到 2030 年，前沿模型可能通过更好的训练消除这个（针对 schema 违规的后训练强化、基础模型中的原生结构化输出能力）。那时，约束层在解决非问题。Pydantic 作为类型系统留下；约束强制库消退。

**存活论证。** 即使 _语法_ 问题消失，这些库服务于不会消失的函数：

1. **类型感知 Python 人体工程学。** `instructor.from_anthropic` 返回 Pydantic 对象，非 JSON 字符串。库的价值是 _LLM 输出和 Python 类型之间的绑定_，不仅是约束强制。只要 Python 代码库使用 Pydantic（它们会的），从 LLM 调用产生 Pydantic 对象的库即使在完美 provider JSON 下也增加生产力。
2. **Provider 抽象。** `instructor` 与 Anthropic、OpenAI、Google 等合作。生产代码库重视抽象层；相同代码路径在单一 API 后支持多个 provider。库的价值部分是可移植性，独立于约束强制。
3. **重试 + 验证反馈循环。** 即使有完美语法一致性，_语义_ 错误持续（§7.7 故障模式 3）。拒绝模型输出并用错误消息重新 prompt 的字段验证器是库级工作。没有库，每个代码库重新发明这个循环。库打包了这个循环。
