### 4.5 LLM 作为评判者：强大、危险，以及如何在不被烧的情况下使用它

对于形态 1（规范答案）和形态 4（行为测试），评分可以由代码完成：字符串比较、正则表达式、schema 验证。对于形态 2（量表）和形态 3（偏好对），以及越来越多地对于形态 5 的细微版本，评分传统上需要人工，这既昂贵又慢。

LLM 作为评判者登场。想法：使用一个单独的（通常更强大的）LLM 来评分你系统的输出，使用量表作为 prompt。不是临床医生手动评分 200 个输出，一个 LLM 在两分钟内评分 200 个输出花费 5 美元。经济学是变革性的。

故障模式也是。**LLM 作为评判者与 LLM 作为系统有相关失败。** 如果你的系统是 Sonnet 4 而你的评判者也是 Sonnet 4，你有 _评判者因为共享偏见而同意系统_ 的有意义风险。评判者更可能将包含评判者自己会产生的相同模式的输出标记为正确。eval 是过度乐观的，在乐观 eval 上发布的团队发布的是比他们以为更不诚实的信号。

缓解措施是真实和可操作的：

1. **使用不同模型家族作为评判者。** 如果你在 Anthropic 上运行系统，使用 OpenAI 或 Google 作为评判者。跨家族评判打破最强的相关失败路径。在不同 provider 上运行评判者的成本溢价相对于 eval 诚实性收益很小。
2. **使用更强的模型作为评判者。** 如果你的系统运行在 Haiku（工作马梯队）上，使用 Sonnet 4 或 GPT-4o 作为评判者。评判者需要至少与系统同等能力，加上足够余量来捕获系统的故障模式。
3. **在校准集上对评判者与人工进行验证。** 取 50–100 个案例的子集，用评判者和至少两个人工评分，计算一致性（二值的 Cohen's kappa；量表分数的加权 kappa 或相关系数）。如果评判者不以可辩护水平与人工一致（生产使用通常 kappa ≥ 0.6），不要信任评判者。校准是负责任地使用 LLM 作为评判者的代价；它不是可选的。
4. **使用带显式量表的结构化评判者 prompt。** 一个说 _从 1 到 10 评分此输出的质量_ 的评判者 prompt 会产生嘈杂、不一致的分数。一个说 _在以下四个维度上评分此输出：(a) 临床准确性 [0–3]，3 = 无临床错误，2 = 一个轻微错误，……；(b) 完整性 ……_ 的评判者 prompt 会产生更一致的分数，因为标准被明确列出且评判者有更少的漂移空间。结构镜像你会给人的量表；不要给评判者更少的指导。
5. **检查长度偏见。** LLM 评判者在量表未指定长度时倾向于偏好更长输出而非更短输出。这个偏见可以测量（按输出长度四分位数计算平均分数；如果单调，评判者有长度偏见）并纠正（通过在量表中添加长度中立性、按输出长度分层 eval，或切换到偏见更少的评判者）。
