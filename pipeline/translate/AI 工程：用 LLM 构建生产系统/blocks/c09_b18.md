_第二层：即时加载（9 到 11 个工具）_。低频工具 agent 按需加载。模式：元工具 `list_available_tools(category)` 返回匹配类别（订阅、退款、升级）的工具 schema。当 agent 意识到需要更新订阅时，它调用 `list_available_tools("subscription")`，获取 `update_subscription` 的 schema，调用它。完整工具集从不同时在上下文中。

**延迟-成本权衡。**

* _全部加载_：更简单，每次调用额外 1-2K token 上下文，延迟中性。高量时，每次调用额外 1-2K 累积：每月 1 亿次调用，0.30 美元/1M 输入 token，那是每节省 1K token 额外约 50 美元/月。不大。
* _即时加载_：更复杂（agent 必须学会发现工具），需要 tier-2 工具时一次额外往返（延迟 +300 到 800ms），未调用元工具时每次调用节省 2K 到 3K 输入 token。在很高量或更大工具库存（50+ 工具）时，节省复合。

**14 工具 agent 的推荐。** _混合_。五个最高频工具始终加载；其余通过元工具即时加载。混合模式在常见路径上保持低延迟，在长尾上保持成本效率。模式可扩展：当工具库存增长到 50，始终加载集保持 5 个（仍然高频的）；即时加载集增长。Agent 的工具发现是规模获胜的工程表面。

**与第 13 章的联系。** 第 13 章将把工具选择（给定任务向 agent 呈现哪些工具）视为一等关注。此 Q 是该决策的上下文窗口角度：甚至在第 13 章的策略逻辑之前，agent 上下文的 _预算_ 形态在规模上偏向分层模式。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_为有 14 个工具、200K 窗口、30K 历史、4K 输出的客服 agent 分配上下文预算。哪些工具驻留上下文 vs. 即时加载？延迟-成本权衡是什么？_ 你验证 (a) LLM 正确计算预算（手动做数学；LLM 经常跳过预算计算跳到推荐），以及 (b) LLM 提议 _分层_ 模式而非全部加载或全部即时（混合是生产答案；LLM 有时在混合模式正确时给二元推荐）。
