1. 将模型固定到之前正常工作的特定日期版本。从日志中识别：回归前上周生产调用映射到哪个日期版本？固定到那个。重路由逆转。
2. Diff 昨天命中 API 的 prompt 与今天的。如果 prompt 相同，原因是模型重路由（原因 1）。如果 prompt 不同，原因是 prompt 变更（原因 2）。
3. 为受影响切片提交回归 eval，这样下次这种切片特定回归触发告警，而非客户投诉。

第三个可能原因（根据给定证据不太可能）：检索语料库漂移（第 9 章），索引的法律文档以影响特定条款类别检索的方式变化。这可以通过比较受影响切片上的检索上下文相似度分数来测试；如果那些稳定，不是检索问题。

这个练习说明第 2 章和第 3 章如何作为诊断工具包协同工作：架构心智模型（第 2 章）告诉你 _模型对什么敏感_；API 纪律（第 3 章，尤其是 §3.11）告诉你 _哪些 API 层事件可以触发那些敏感性_。日期固定纪律（§3.6，上面 Q4）本可以完全防止原因 1。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_我在诊断 RAG 产品切片上的突然 7 个点质量回归。模型在别名上，而非固定版本。prompt 未变更。带我走一遍诊断，从最可能到最不可能排列原因，借鉴 RLHF 驱动的训练行为偏移、prompt 敏感性、检索漂移和静默重路由。_ 你通过检查排列是否匹配证据来验证（LLM 应该重度权衡别名使用，因为用户提到了它；如果没有，反驳），以及诊断步骤是否包含 _检查日志以识别别名在回归前后解析到哪个日期版本_——这是单个最具诊断性的步骤，LLM 可能将其埋在列表中而非命名为第一个行动。强制 LLM 显式命名最具诊断性的步骤。
