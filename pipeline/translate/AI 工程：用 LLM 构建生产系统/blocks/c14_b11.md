### 13.9 How This Breaks：摧毁生产的工具

**命名的故障模式**：摧毁生产的工具。团队构建了一个工具权限超过应有范围的 agent。用户（或 prompt 注入攻击）诱导 agent 破坏性地调用工具。损害是真实的且有时不可逆。

**真实或复合事件**：复合。某公司的内部 AI 助手有 `delete_record` 工具无门控：LLM 可直接删除数据库行。对抗性用户输入导致 LLM 对不应删除的行调用 `delete_record`。恢复需要从备份恢复；自上次备份以来修改的记录发生数据丢失。总业务影响：显著；法律审查随之而来；事件成为案例研究。

**工程缓解措施**：三层。

1. **工具级授权**。破坏性工具（删除、修改、发送、收费）需要显式策略批准才能执行。确定性策略层对照规则检查 LLM 的提议调用；被拒绝的调用返回结构化错误而非执行。
2. **按用户角色门控工具**。agent 的可用工具目录按用户权限范围化。只读用户的 agent 没有写工具，到此为止。
3. **高影响工具的 dry-run 和确认模式**。LLM 对破坏性工具的首次调用是 dry-run；dry-run 返回 _会_ 发生什么；LLM 被要求在真实执行前与用户确认（或通过包含用户确认的确定性策略检查）。模式在应用层强制，非在 prompt 层（可绕过）。

**本应捕获它的 eval**：_对抗性工具调用 eval_。eval 的一个切片包含设计来诱导 LLM 不当调用破坏性工具的输入。如 LLM 被正确门控，调用被阻止（或需要通过确认）；eval 验证。eval 设计纪律（第 4 章的覆盖审查）应在发布前浮现此切片。

此故障模式也是 prompt 注入威胁（第 23 章）在工具层的上演。防御模式相同：假设 LLM 可被欺骗；假设 prompt 级指令不严密；在工具执行层强制策略。
