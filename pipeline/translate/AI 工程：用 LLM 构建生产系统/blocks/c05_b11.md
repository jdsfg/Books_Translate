### 4.8 Eval 作为 CI：生产循环

eval 在 _自动_ 运行、在系统每次变更时运行、阻止回归变更时最强大。这是 _eval 作为 CI_。第 5 章将构建 GitHub Actions 工作流作为绑定工作流 #1；本节设置原因。

结构：

1. **golden set 存活在仓库中**（或在外部存储中按版本索引），与代码一起版本控制。
2. **CI 作业在每个 PR 上运行 eval 套件**。eval 套件产生分数（或分数向量）。
3. **CI 作业将分数与基线比较**（通常是 `main` 上的分数）。
4. **如果分数低于阈值回归，CI 作业阻止合并。** PR 无法合入直到 (a) 工程师修复回归，或 (b) 授权审查者以显式理由覆盖阻止。
5. **分数历史被存储** 并在 PR 描述、仪表盘和模型升级工作流（第 21 章）中可见。

这产生的纪律：

* 每次 prompt 变更在合入前经过回归测试。
* 每次模型升级在合入前经过回归测试。
* 每次检索语料库变更在合入前经过回归测试。
* 每次依赖变更在合入前经过回归测试。

这防止的纪律：

* _无害 prompt 微调静默回归行为_ 故障。
* _模型升级微妙偏移拒绝模式_ 故障。
* _新检索源引入 hallucination 模式_ 故障。

eval 作为 CI 是 _在写代码前写测试_ 纪律的生产版本。eval 不是可选的；它是门禁。第 5 章用真实 GitHub Actions 工作流使其具体化。
