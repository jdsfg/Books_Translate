1. **数据敏感性排除 SaaS。** PHI、律师-客户特权内容、国防数据：SaaS BAA 可能存在但数据驻留和供应商人员审查的顾虑可能使自建成为更安全的选择。_反驳_：许多 SaaS 供应商提供专用实例或本地部署。在假设 SaaS 不可能之前先与供应商沟通。
2. **技术栈不寻常。** 自定义编排、专有内部服务、你想扩展的现有内部评估系统：这些可能使 OSS 或 SaaS 工具集成成本高。_反驳_：大多数团队高估了他们技术栈的独特性。在承诺自建之前先尝试 SaaS 集成。
3. **规模摊销**。超大规模团队可能发现 SaaS 定价超过内部成本。_反驳_：在超大规模时，你也有非常大的 eval 工程需求，SaaS 中编码的纪律可能比重新发现更便宜的许可。仔细计算；不要假设规模自动倾斜自建 vs 购买。

值得命名的第四个条件：**集成到现有内部平台**。如果你的公司有成熟的内部平台带共享仪表盘和团队工作流，集成 SaaS 的摩擦可能超过自建的摩擦。_反驳_：同上，在假设不合适之前先尝试集成。

**Q4.** 为什么本章主张 _每 prompt 版本的 golden set_ 而非单一演变的 golden set？版本化解决什么问题，引入什么成本？

**答案：** 版本化解决的问题：**同类对同类的回归比较**。如果 golden set 持续演变，今天对 _当前_ golden set 检测到的回归与六个月前对旧 golden set 检测到的回归不可直接比较：golden set 本身不同。版本化使比较显式：候选 prompt 版本对与其对齐的 golden set 版本评分，对基线（先前 prompt 版本对相同 golden set 版本）的 delta 有意义。

版本化解决的第二个问题：**golden set 变更和 prompt 变更捆绑时的清晰性**。如果 PR 同时更改两者，团队可以独立看到各自的影响——新 prompt 对旧 golden set（prompt 变更的影响）、旧 prompt 对新 golden set（golden set 变更的影响）、新 prompt 对新 golden set（组合效果）。没有版本化，两个效果混合。

成本：**维护开销**。每个 prompt 版本需要自己的 golden set 清单。当添加案例时，团队必须决定它仅属于当前版本还是回溯到旧版本。版本化数据集比单一演变数据集稍重管理。

trade-off 在回归检测非平凡的任何团队中偏向版本化。对于有单一 prompt 和小 golden set 的微型团队，单一演变数据集可以足够；对于发布多个 prompt 变体并跟踪长期趋势的生产团队，版本化是正确纪律。
