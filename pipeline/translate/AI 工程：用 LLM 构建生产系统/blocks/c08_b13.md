#### 概念检查

**Q1.** 为什么判别联合优于普通联合用于结构化输出？给出两个具体原因。

提示

想想验证器做什么和下游代码做什么。

**答案：** 两个原因：

1. **验证确定性。** 普通 `Union[SuccessResponse, ErrorResponse]` 要求验证器尝试每个变体并选一个适合的。如果 `SuccessResponse` 和 `ErrorResponse` 共享字段名（例如都有 `detail` 字段），验证器可能选错变体或歧义失败。判别联合用 `kind` 字段直接选变体；验证无歧义。
2. **下游类型安全。** 有判别联合时，类型检查器（mypy、pyright）理解 `if result.kind == "success"` 将类型缩窄为 `SuccessResponse`，给予对其字段的访问。有普通联合时，检查器要么接受歧义要么在每次访问时要求显式 `isinstance` 检查——两者都丑。判别模式是下游代码的正确人体工程学形态。

第三个值得注意的原因：**优雅失败是结构化的而非异常的**。模型对"这不可回答"情况有定义的输出路径；下游代码在类型化变体上分支而非捕获异常。这更可维护且更易测试。

**Q2.** 什么是 _约束解码_，为什么比礼貌地要求模型产生 JSON 更可靠？

**答案：** 约束解码修改 LLM 的 token 生成步骤。在每步，模型的下一 token 概率分布被掩码：会产生无效输出（按 schema、正则或文法）的 token 在采样前被置零。模型字面上不能发出无效输出，因为无效 token 不可采样。

这比 prompt 更可靠因为 prompt 是概率偏向，非保证。说 _输出有效 JSON_ 的 prompt 将模型分布向有效 JSON token 偏移但不消除无效发出的机会，尤其在边缘情况下（长输入、对抗输入、prompt 注入尝试）。约束解码机械地消除机会。Provider 的原生 JSON schema 模式和 `outlines` 都实现约束解码（范围和人体工程学不同）；前者是 API 级模式，后者是库级模式。

约束解码 _不_ 解决的：语义正确性。输出在 _语法上_ 有保证；_内容_ 正确性仍在模型。符合 schema 的 JSON 对象可包含错误值；只有 eval 捕获那个。见 §7.7 故障模式 3。

**Q3.** 指出两个 `outlines` 是比 `instructor` + 原生 JSON schema 模式更正确工具的场景，和两个反向为真的场景。

**答案：**

`outlines` 正确时：

1. **你在自己的基础设施上服务开源模型**（通过 vLLM、llama.cpp 等）没有原生 JSON schema 模式。`outlines` 提供 API 不提供的约束层。
2. **你需要超越 JSON schema 的约束**：正则约束、上下文无关文法约束（例如输出必须是有效 SQL）或自定义逻辑。原生模式仅限 JSON schema；`outlines` 更通用。
