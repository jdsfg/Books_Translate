补充 eval：**schema 紧度检查**。对于 schema 太宽松故障，测量验证器多常拒绝模型输出且人工标记被拒绝的输出为"反正也是错误内容"。高拒绝且错误内容率暗示验证器在做有用工作；低拒绝且错误内容率（验证器拒绝但内容没问题）暗示 schema 太紧。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_设计一个捕获 schema 太刚性故障模式的 schema 覆盖 eval。指定输入集、测量、失败信号和 CI 集成。_ 你验证 (a) 提议的输入集实际锻炼 schema 的边缘案例（LLM 产生通用输入列表；你调整到你特定 schema 的故障模式），以及 (b) 失败信号阈值（上面答案中的 5%）对你的领域合适（高风险管道更紧；低风险更松）。

**Q4.** _从散文 + 正则解析迁移到结构化输出_。你的遗留管道用散文 prompt 调用 LLM 并用正则解析响应。设计一个用 `instructor` + 原生 JSON schema 替换散文+正则管道的迁移，保持相同下游接口。指出两个特定于迁移的风险。

提示

下游代码消费正则解析的输出。迁移必须保持该接口稳定。

**答案：** 迁移步骤：

1. **定义 Pydantic schema** 精确捕获正则提取的字段。如果正则解析 `severity: high`，schema 有 `severity: Literal["critical", "major", "minor"]` 字段。如果正则宽松（将缺失字段视为 None），schema 将字段标记为 Optional。
2. **构建适配器** 取 Pydantic 对象并产生正则解析输出有的相同字典形态。下游代码不变。
3. **在生产流量样本上并行运行两个管道** 1-2 周。记录两个输出；逐调用比较。差异是：正则搞错的案例（结构化管道修复，好）；正则搞对但结构化管道搞错的案例（需要调查）。
4. **通过功能标志分阶段切换**。从低风险调用开始；观察；扩展。迁移对高量管道可能需要一个月；那没问题。
5. **当结构化管道在几周内达到平价或更好且团队对 eval 有信心时停用正则管道**。

两个特定于迁移的风险：

1. **边缘案例中的微妙行为差异。** 正则管道可能吸收了某些行为（例如修剪空白、接受替代拼写）结构化管道不复现。并行运行期捕获这些；没有它，迁移导致静默回归。
2. **原生 JSON schema 模式的成本增加。** 某些 provider 的结构化输出模式有小开销（约束解码步骤增加延迟，有时几毫秒）。对于很高量的管道，这可能重要。在并行运行期间测量；如果重要，评估可靠性增益是否证明它合理（通常是；有时按量路由到更便宜的散文管道处理最简单案例是答案）。
