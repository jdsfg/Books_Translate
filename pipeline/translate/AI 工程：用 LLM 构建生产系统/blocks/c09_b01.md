> **截至 2026 年。** 这里老化最快的元素是上下文窗口数字本身：Claude 200K、GPT-4o 128K、Gemini 2.5 Pro 2M，以及围绕它们构建的层级边界（<500K、500K–10M、>10M）。如果你在模型发布将前沿推过 10M token 后阅读此内容，按大致相同比例重新计算层级边界；决策树本身仍然成立。

第 6 章关于什么进入 prompt。本章关于什么进入 _上下文窗口_：一个更广泛的问题。系统 prompt、对话历史、检索到的文档、工具输出、之前的助手消息、少样本示例、用户当前消息、结构化输出 schema：所有这些一起放入（或放不下）模型可用的上下文窗口。

词汇转变——从 _prompt 工程_ 到 _上下文工程_——是 2024–2025 年领域的转向，反映了生产 LLM 系统的生死取决于其上下文预算如何分配的现实。将上下文窗口视为 _放 prompt 的地方_ 的团队主要在做小功能。将上下文窗口视为 _在竞争需求间预算的有限资源_ 的团队在做严肃的 AI 工程。

本章设定框架，走一遍生产团队使用的主要技术，以绑定工作流 #4 结束：长上下文 vs RAG 决策树，矩阵形式，层级边界标注日期。

### 8.1 上下文窗口作为有限资源

上下文窗口是模型单次推理调用的工作记忆。截至 2026 年：

* Claude Sonnet 4：200K token
* GPT-4o：128K token
* Gemini 2.5 Pro（长上下文配置）：2M token
* 工作马层级模型（Haiku、mini、Flash）：128K–1M token

200K token 听起来巨大。确实。200K token 大约 15 万英文单词，比整本书还多。你可以将整部 _联邦党人文集_ 放入单次 Claude Sonnet 4 API 调用并要求模型概括其中的宪法理论。

但 200K token 也很紧。一个典型生产系统这样填充它：

组件 | 典型 token
---|---
系统 prompt | 500–2,000
工具定义 | 200–2,000
对话历史（长聊天） | 5,000–50,000
检索到的 RAG 上下文 | 2,000–20,000
少样本示例（如使用） | 500–5,000
当前用户消息 | 50–2,000
输出预算（`max_tokens`） | 500–4,000

Helios 的一个真实客服 agent，完全加载，约占 50K–80K token。添加更多检索、更多历史、更多工具定义，那个 200K 上限就接近了。而且成本故事残酷：200K 输入 token 按 3 美元/1M 计算是每次调用 0.60 美元，输出之前。每月 1000 万工单，完全加载的上下文是 _推理账单上的一个真实数字_。

所以上下文工程是 **以最少成本和最少模型焦点损失将最有用的上下文放入窗口** 的学科。权衡是真实的；手段是有限的；工程很重要。
