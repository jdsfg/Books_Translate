**答案：** 有用的 prompt：_我有一个分类 prompt 每月运行 4000 万次调用，成本 8160 美元。预算是 5500 美元。质量下限是 0.82。在成本上限下提出三个 prompt 变体；预测每个的 eval 和成本。_ 你验证 (a) 算术（LLM 在每 token 数学上犯错；手动重算），(b) eval 预测不过于乐观（LLM 倾向于预测压缩保留质量；对照 §6.6 的 V1 到 V4 弧交叉检查，其中每次压缩实际移动了分数），以及 (c) 一个变体以余量落在质量下限之上，而非在下限；在下限边缘的变体在流量偏移时在生产中回归。

**Q6.** _跨章节：给定第 4 章 eval 套件的 prompt 迭代循环_。你继承了一个代码审查 bot，其系统 prompt 在项目 eval 上得分 0.73。Eval 有四个维度：正确性（0.78）、具体性（0.65）、误报率（0.71）和语气（0.79）。团队想提升具体性和误报率而不回归其他维度。设计 prompt 迭代循环。使用第 4 章的 eval 纪律（golden set、多轴量表）作为基础。

提示

每个 prompt 变更应针对特定维度；eval 告诉你变更是否在不无意中回归其他维度的情况下奏效。§6.5 和 §6.6 是工作流模板。

**答案：** 循环：

1. **按维度诊断故障模式。** 拉取 20 到 30 个具体性低分的 eval 示例和 20 到 30 个误报发生的示例。阅读它们。故障类别塑造 prompt 变更：_具体性低_ 可能意味着模型给通用建议（_考虑错误处理_）而非指向具体行；_误报_ 可能意味着模型将风格问题标记为 bug。
2. **假设针对诊断模式的 prompt 变更。** 对于具体性，添加指令：_每个发现必须引用具体行号并引用被批评的确切代码。_ 对于误报，添加：_区分 (a) 确定 bug（会行为异常的代码）和 (b) 风格偏好（可行但可以更干净的代码）。用严重性标记每个发现：critical、suggestion 或 nit。_
3. **对新 prompt 运行完整 eval。** 不仅是针对的维度；完整多轴量表。风险：为具体性添加的指令（例如 _引用代码_）可能减慢输出（回归延迟）或改变语气（回归语气）。第 4 章纪律是每次运行评分 _所有_ 维度，因为维度 trade-off 是 prompt 迭代的主导故障模式。
4. **与基线比较有统计显著性。** 如果 eval 规模是 80，具体性上 0.02 的提升可能是噪声。如果 eval 是 200+，0.03 的提升是有意义的。使用第 4 章的 eval 置信度框架；不要在噪声内提升上推广 prompt。
5. **迭代：如果维度回归了，修改变更。** 通常第一次改善具体性的尝试增加了回归语气的冗长；下一次迭代重构冗长（项目符号替代散文、行引用替代长引用）以保留语气。
6. **推广和版本化。** 当候选通过多轴标准（目标维度上升，无其他维度超出噪声回归）时，在 prompt 注册表（§6.4）中推广；将 diff 和 eval 分数保留在 prompt 的版本历史中，使下一个维护者看到此版本存在的原因。
