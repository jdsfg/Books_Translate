#### 概念检查

**Q1.** _prompt 工程_（第 6 章）和 _上下文工程_（本章）的区别是什么？区别何时重要？

提示

§8.3 有框架。

**答案：** Prompt 工程关注 _你在 prompt 中放什么_：系统 prompt、用户指令、少样本示例。上下文工程更广泛：它覆盖 _什么进入上下文窗口的全部_，包括对话历史、检索内容、工具输出、结构化输出 schema，以及影响模型在给定调用中行为的一切。

区别在你设计带长对话、检索或工具使用的生产系统时重要。仅以 prompt 工程术语思考的团队优化静态部分但错过动态部分（历史压缩、检索分块、即时工具加载）。以上下文工程术语思考的团队将整个窗口视为工程表面并在竞争需求间预算。

对于简单的一次性 LLM 调用，区别坍缩：prompt 就是整个上下文。对于多轮、工具增强、RAG 支持的系统，区别是承重的。

**Q2.** 指出 §8.4 的四个主要上下文工程手段并给出每个是正确主要工具的一个生产场景。

**答案：**

1. **摘要对话历史**：长多轮客服对话，累计历史否则无限增长。约 10 轮后，摘要恢复上下文预算而不丢失对话要点。
2. **积极分块检索上下文**：任何 RAG 支持的系统。Strata Research 的法律 RAG 检索 top-10 _段落_（非 top-10 _文档_）；检索时分块意味着模型仅看到相关切片，非完整文档。
3. **分层上下文（摘要然后下钻）**：大变更集上的代码审查系统。Agent 首先看到变更的高层摘要，然后下钻到特定文件。操作大型代码库的编码助手工具常规使用此模式。
4. **即时工具加载**：客服 agent 不预加载客户账户数据而是通过 `get_customer_field` 工具获取特定字段。这是最高上下文效率模式；它将上下文加载推到推理时和按需。

真实系统经常组合多个手段。四手段分类是菜单；生产系统根据流量模式和成本约束从中选择。

**Q3.** 解释长上下文 vs RAG 决策树（§8.6）。对每层，指出典型用例并解释为何层推荐方法适合。

**答案：**

* **< 500K token（长上下文胜）**：单个产品的小型技术文档聊天机器人。完整文档适合 100K token。构建 RAG 管道增加工程复杂性（分块、嵌入、向量数据库、重排序）而无质量增益于将整个文档放入上下文。长上下文以简单性胜。
* **500K–10M token（判断决策）**：覆盖约 5M token 策略、运行手册、设计文档的公司内部知识库聊天机器人。两种架构都可行。用 Gemini 2.5 Pro（2M 上下文）的长上下文需要将语料库分块为 2-3 个查询时部分，这很混乱。RAG 干净地检索相关 5-10 块。eval 驱动选择；通常 RAG 在此规模上因工程整洁性成为答案。
