(a) **长上下文**。40K token 远低于 500K 阈值。为此构建 RAG 管道是过度工程；将完整文档放入系统 prompt（对稳定部分使用 prompt 缓存）。

(b) **RAG**。25M token 无法放入任何 2026 年上下文窗口；即使 Gemini 2.5 Pro 的 2M 也装不下。决策树说 _> 10M = RAG_。工程投入分块医学文献、为医学文本选择嵌入、构建引用溯源。

(c) **判断决策**。3M token 适合 Gemini 2.5 Pro 的 2M 上下文（需要一些分块），但不舒适。RAG 在此更干净：嵌入策略文档，每次查询检索相关 5–10 块，策略聊天机器人更简单。推荐 RAG 除非团队有强现有长上下文基础设施或查询可靠地触及可适合 2M 的更小子集。

(d) **长上下文友好带混合**。500K token 正好在边界。对于大多数查询，代码库的精选子集（例如变更文件 + 其导入 + 其测试）小得多且舒适适合。组合方法：基于工具的文件检索（第 13 章）而非纯长上下文或纯嵌入 RAG。代码库搜索是已知专业案例，通用 RAG 效果不如工具增强长上下文。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_我有四个不同语料库大小的场景；哪些应该用长上下文 vs RAG？论证每个。_ 你验证 (a) LLM 使用正确的 2026 年上下文窗口数字（它可能用 2024 年数字；检查 Gemini 2.5 Pro 是 2M 非 1M），以及 (b) 推荐考虑查询时动态（不仅是语料库大小而是典型查询触及语料库的多少）。

**Q3.** _设计对话历史摘要_。Helios 的客服 agent 有 200K 上下文预算。对话历史在长会话中可增长到 50K token。设计摘要策略。指定：(a) 摘要何时触发；(b) 什么被摘要 vs 逐字保留；(c) 摘要内容捕获什么；(d) 你选择的成本 vs 质量权衡。

提示

§8.4 手段 1 有结构。

**答案：**

(a) **触发**：当累计历史超过 20K token 时，摘要运行。20K 阈值远低于 50K 增长上限，给余量；也足够大使摘要不持续运行。

(b) **什么摘要 vs 逐字保留**：

* _逐字保留_：最近 6 轮（典型用于完整对话连贯）；客户原始问题描述（第 1 轮）；客户声明的任何显式目标或约束。
* _摘要_：从对话底部起的第 7+ 轮。摘要一旦触发每 5 轮运行，处理下一个 5 轮块。

(c) **摘要内容**：

* 客户至今提出的痛点
* Agent 调用的工具及其返回
* 做出的决策及其理由
* 待解决问题或未解决项
* 客户情绪轨迹（沮丧、满意、中立）

摘要是结构化的（非自由散文）：可能是 200–400 token 的项目符号摘要，由小 Haiku/Flash 调用生成使摘要本身便宜。
