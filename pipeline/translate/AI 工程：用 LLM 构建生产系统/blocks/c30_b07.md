#### 反模式 6：工作流足够时构建 agent

**模式。** 团队对简单确定性工作流能更好处理的问题伸手多 agent 或 agentic 架构。将 _agentic_ 视为本质上比 _工作流_ 更高级，这恰好颠倒：工作流是 agent 对可分解为已知步骤任务的生产加固版本。

**团队如何落入。** Agent 令人兴奋。团队刚读了一篇论文。产品经理想发布听起来现代的东西。架构决策由审美而非任务结构驱动。一旦承诺，团队累积编排、重试、有界和可观测性复杂性，而工作流本会隐含这些。

**症状。** 无界循环。不该触发时触发的工具调用。无人能预测的成本飙升。涉及重放轨迹而非读日志的调试会话。事后复盘中的短语 _agent 决定_——agent 被视为准员工，其决策被描述而非诊断。

**纪律。** 首先问任务是否根本是 agent（第 14 章）。多数生产任务不是：它们是每步至多一个 LLM 调用的确定性步骤序列，这正是工作流的定义。如你确实需要 agent，有界它：迭代上限、成本断路器、按工具断路器、工具调用去重、观察验证——全部在任何生产流量前就位（第 14 章）。对多 agent 特别地，编排者-工作者在几乎所有生产案例中胜过点对点（第 15 章）。

**锚定。** 同一故障类的两个不同规模锚定。5.2 万美元隔夜 agent（线索 B 故障 5，第 14 章）是单 agent 案例：无迭代上限、无成本断路器、无工具调用去重；agent 运行 14 小时发出相同昂贵调用才被注意。2026 年 agentic 递归事件（线索 B 故障 6，第 15 章）是多 agent 案例：编排者-工作者系统收敛到错误中间答案并每重试循环翻倍 token 消耗。两个故障形状相同——一个无确定性工作流本会隐含的有界的 agentic 系统——在不同架构规模上浮现。

**终止标准。** 如你能将任务指定为每步至多一个 LLM 调用的确定性步骤序列，你有工作流；不要 agent 化它。如你确实有真正 agent，{迭代上限、成本断路器、按工具断路器、工具调用去重、观察验证}的每一个必须在 agent 见到生产流量前就位。缺一个不是"下个冲刺加"——它是发布门控。
