#### 深入思考

**Q1.** _prompt 工程作为职业_。2022 年，_prompt 工程师_ 是一个有真实薪资的可行职位。2026 年，这个头衔更罕见了；技能已被吸收进更广泛的 AI 工程职责。推测 2030 年：prompt 工程作为离散技能会作为职位存在，还是会成为基线 AI 工程能力？指出两个可能塑造答案的力量。

**讨论：** 两个力量：

1. **模型能力持续吸收 prompt 级技巧。** 每一代前沿模型减少特定 prompt 咒语的价值。到 2030 年，_prompt 工程_ 作为战术纪律（知道魔法短语）可能价值近零；模型处理它。_Prompt 工程_ 作为战略纪律（版本化、评估、结构化输出、工具引出、安全）可能是核心 AI 工程能力，非单独角色。
2. **AI 工程内的专业化持续分化。** 随着领域成熟，子专业化出现（eval 工程；agent 设计；AI 运维；安全工程）。_Prompt 工程_ 作为独立头衔可能不存活，但 _eval 驱动的 prompt 迭代_ 可能作为团队内的专业持续，类似于 _性能工程师_ 和 _安全工程师_ 是更广泛工程团队内的专业角色。

净预测：到 2030 年，_prompt 工程师_ 很少是独立头衔；_AI 工程师_ 和 _AI 平台工程师_ 是主导头衔，prompt 工程能力嵌入其中。本章教授的纪律（prompt 作为版本化代码、eval 驱动迭代、结构化输出、安全加固）作为更广泛 AI 工程工具包的一部分存活。2022 年在 _prompt 工程_ 中窄专业化的人的职业路径已与更广泛的 AI 工程职业路径汇合；技能仍有价值但不再有差异化。

**Q2.** _DSPy 和抽象 trade-off_。DSPy 将 prompt 从代码中抽象出来（你写签名；框架写 prompt）。这对正确场景是有意义的生产力增益但对其他场景是有意义的损失。指出两个抽象是正确 trade-off 的场景，和两个它是错误的。

**讨论：** 抽象是正确 trade-off 的地方：

1. **大规模 eval 驱动系统**。运行数十个类似 prompt 的团队（例如，每个客户 prompt 略有不同的多租户 SaaS）受益于框架：签名干净地参数化；MIPRO 对每个客户的 prompt 对照其 eval 优化。在此规模下手调是禁止的。
2. **_签名_ 是制品且 _prompt_ 是实现细节的任务**。一些任务有清晰规范（输入字段 → 输出字段）且特定 prompt 措辞无趣。对照规范的代码生成、从文档的结构化抽取和分类任务都受益于 DSPy 的抽象。

抽象是错误的地方：

1. **利益相关者可见的 prompt**。如果合规审查者、监管机构或非技术高管需要阅读和批准 prompt，DSPy 的优化输出可能不透明或风格上不同于人类会写的。抽象与利益相关者可访问性对抗。
