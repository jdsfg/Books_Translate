1. **内联 prompt 漂移**：埋在代码中的 prompt 在调用间无跟踪地漂移。注册表展示每个版本。
2. **跨环境一致性**：生产和预发布环境可以显式使用不同 prompt 版本，在清单中可见。_预发布通过了；生产失败了因为它用了旧 prompt_ 的风险降到零。
3. **审计和回滚**：每个 prompt 版本有 eval 基线；提升和回滚是带完整历史的清单变更。
4. **无耦合重构**：使用 prompt 的代码从注册表加载，将重构工作与 prompt 演变解耦。

它 _不_ 解决的问题：

1. **坏 prompt**。注册表跟踪 prompt；它不改进它们。使用注册表但 prompt 质量差的团队仍在发布质量差的 prompt，只是更有组织。改进层是 eval 驱动迭代（§6.6）。
2. **跨团队 prompt 语义协调**。如果多个团队共享有细微变化的系统 prompt，注册表有帮助但不强制对齐。需要单独的治理纪律（prompt 审查流程、共享量表、变更批准）。

没有 eval 纪律，prompt 注册表是官僚主义。有了 eval 纪律，它是工程。注册表单独是必要但不充分的。

**Q4.** DSPy 何时是 prompt 优化的正确工具，何时是过度的？指出各两个具体场景。

**答案：** DSPy 正确时：

1. **你有强 eval 集和良好定义的任务。** MIPRO 需要评分函数来优化。有了好的 eval 和有边界任务（抽取式问答、分类、结构化生成），DSPy 的优化有意义地改进手动调优的 prompt。
2. **你处于自动 prompt 优化摊销的规模。** 运行许多类似任务的大公司受益于系统搜索 prompt 空间的框架；小团队手动调优一次然后继续。

DSPy 过度时：

1. **第一个手写 prompt 已经有效的简单任务。** 一个在 eval 上达到 92% 的 30 行 prompt 不需要 MIPRO 来找一个以一周优化器运行为代价达到 93% 的 31 行 prompt。
2. **prompt 为利益相关者可见性被刻意手动调优的任务。** 合规审查、面向高管的 prompt、必须可被非工程师阅读的 prompt：优化器的输出可能不透明；审计成本超过优化收益。

通用测试：框架的每工程师周 eval 分数增益是否超过框架的开销？在小规模时，否。在大规模时，通常是。
