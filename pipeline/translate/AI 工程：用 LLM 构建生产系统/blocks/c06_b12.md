### 5.8 Triangle Trade-off 侧栏：选择 eval 工具（经典格式）

工具 | 成本（2026） | 设置投入 | 最适合
---|---|---|---
`pytest-evals`（OSS） | 0 美元（仅开发时间 + 运行的 LLM API） | 数小时，如果团队已使用 pytest | Pytest 原生团队；数据敏感团队
`inspect-ai`（OSS） | 0 美元（开发时间 + API） | 数天（更陡曲线） | 安全 eval 重的团队；审计跟踪重的团队
`ragas`（OSS） | 0 美元（开发时间 + API） | 数小时，嵌入 RAG 管道 | RAG 专家团队（Strata）
`braintrust`（SaaS） | 每项目约 100–2000 美元/月 | 数小时（基于 Web 的入门） | 中等规模团队；需要跨团队 eval 可见性
`langsmith`（SaaS） | 约 50–2000 美元/月 | 如果是 LangChain 技术栈则原生 | LangChain 原生团队
自建（自定义） | 高工程成本（首年 100K 美元+） | 数月 | 超大规模团队；深度不寻常的技术栈

从这个表格可以读出的三个 trade-off：

1. **OSS 在美元上免费但在工程时间上不免费**。设置成本是真实的；维护成本是真实的；仪表盘是自带的。对于小团队，在 OSS 上构建仪表盘的时间成本可能超过 SaaS 成本。
2. **SaaS 是生产力赢但数据敏感性失**。对于没有受监管数据的团队，SaaS 在非平凡团队规模时通常是正确答案。对于 HIPAA/法律科技/国防团队，SaaS 更难。
3. **大多数团队最终采用混合**：OSS 作为 CI 门禁（免费、本地），SaaS 用于跨团队 UI（付费、可见）。混合在 2026 年比任一纯策略更常见。

### 5.9 How This Breaks：没人读的 eval

**命名的故障模式**：没人读的 eval。团队构建 eval，接入 CI，将绿/红信号视为二元的。通过 eval 的 PR 合并；未通过的 PR 让工程师重试直到通过。没人读 eval 结果详情。随时间推移，eval 变成没人看的仪表盘上的数字，报告的实际内容（哪些案例失败、哪些维度退化）被忽略。

**真实或复合事件**：一个复合例子。一个团队的 eval 平均 9.4 持续六个月，同时团队一个接一个地发布功能。每个 PR 通过门禁（无低于阈值的回归）。三个月时，一位高级工程师偶然注意到每维度分解显示稳定漂移：_语气_ 从 2.8 降到 2.4，_简洁性_ 从 2.7 降到 2.3，_完整性_ 上升（补偿）。摘要分数保持在安全范围因为维度平衡了。漂移是真实的、累积的，且未被门禁捕获。团队回滚了几个 prompt 变更，最终达到一个维持每维度分数在之前稳定水平的 prompt。

**工程缓解措施**：门禁必须读 _每维度_，而非仅摘要。§5.6 的示例工作流有每维度下限（无维度低于 2.5）；这在漂移累积前捕获它。加上：_每周 eval 审查_ 会议（一位工程师，30 分钟，滚动浏览本周的 eval 报告，寻找每 PR 门禁遗漏的模式）。成本小；价值真实因为人工注意力捕获自动化门禁不能的东西。

**本应捕获它的 eval**：每个 PR 的每维度下限检查，加上每周人工审查。这里的故障模式是运营的，非技术的；门禁在通过，纪律在松懈。缓解恢复两层。
