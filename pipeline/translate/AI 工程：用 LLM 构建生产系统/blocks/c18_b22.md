具体的 2030 年预期：**多提供商路由成为入门基础设施，通过多个网关产品可用**，但有专门路由需求的公司继续内部构建。本章教的纪律持续；实现工具演化。

**Q3.** _分类器即 eval 设计_。本章引入分类器（小型 Haiku 级调用用层级标记每个请求）作为路由机制。但分类器本身是做判断的 LLM 调用；它在功能上是路由时应用的 _eval_。论证设计分类器与设计 eval（按第 4 章）是相同的工程纪律，生产团队应如此对待。eval 设计的哪些实践应转移到分类器设计？

**讨论：** 结构类比是精确的：

* eval 定义 _rubric_（什么使输出好的标准）并运行 LLM 评判器按 rubric 对输出评分。
* 分类器定义 _分类法_（每个请求属于哪个层的标准）并运行 LLM 将请求分配到层。

两者都是带高下游后果的 LLM 判断系统。误判 5% 输出的 eval 给团队 5% 错误的质量信号。误判 5% 请求的分类器将那 5% 路由到错误层，要么过度支出要么服务质量不足。

eval 设计（第 4 章）中直接转移的实践：

1. **Golden 集**。正如 eval 有标注示例测试评判器行为，分类器需要带正确层级的标注请求集。几百个示例足以初始校准。
2. **评分者间一致性**。eval 纪律检查人类评分者在宣布有效前对 rubric 达成一致。分类器 rubric 应通过相同检查：两个工程师标注相同 50 请求应在高比率（>85%）上一致。如不一致，分类法模糊需锐化。
3. **回归测试**。eval 回归套件捕获 prompt 变更降低 eval 时。分类器需要相同回归套件：稳定测试集检测分类器 prompt 以意外改变层分布的方式变更时。
4. **周期性校准**。eval 定期对新鲜生产数据重新验证（数据漂移关注）。分类器需要相同校准：生产流量组合偏移；分类器对当前流量的准确性可能偏离对原始 golden 集的准确性。
5. **边缘案例纪律**。eval rubric 指定如何处理边界案例；分类器需要相同。分类器在置信度模糊时做什么？（按 §17.4 答案是"升级一层"，等同于 eval rubric 的"如不确定，保守评分"。）
