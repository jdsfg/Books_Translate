**Q5.** 区分 `stop_reason` 在典型 chat-completions API 上可以取的五个值（`end_turn`、`max_tokens`、`stop_sequence`、`tool_use`，加上 provider 特有的 `refusal` 或 `content_filter`）。对于每个，描述一个如果你的代码不检查 `stop_reason` 而无条件信任返回文本时会被隐藏的生产故障模式。

提示

每个值告诉你模型 _为什么_ 停止生成。模型因非"我完成了"的原因而停止的情况是返回文本可能不是你假设的情况。

**答案：** 五个值及各自隐藏的故障：

* **`end_turn`**：模型自然完成。这里没有隐藏故障；这是正常路径。值得检查仅因为该值的 _缺失_ 告诉你走不同路径。
* **`max_tokens`**：模型在句中用完输出预算。隐藏故障：你的下游解析器收到截断字符串。如果你在提取结构化输出（第 7 章），JSON 不完整，`json.loads` 会抛异常；如果你将文本返回给用户，他们看到一句话在词中间结束。没有检查，你静默地将截断当作完整答案发布。
* **`stop_sequence`**：模型发射了配置的 stop 字符串并被截断。隐藏故障：stop sequence 出现在期望内容内部（一个代码块包含你用作 stop 的相同分隔符），你比预期更早截断了输出。用户得到一个 _看起来_ 完整的部分答案。诊断是 stop_reason 为 `stop_sequence` 但内容在结构上不完整。
* **`tool_use`**：模型决定调用工具并等待你的工具响应。隐藏故障：你忽略响应中的工具调用块，将空（或部分）文本内容视为模型的答案，而模型从未真正返回答案。用户什么也看不到或看到无关内容。第 13 章构建正确处理此情况的循环。
* **`refusal` 或 `content_filter`**（provider 特有）：模型拒绝响应，或安全系统拦截了输出。隐藏故障：你记录"模型说了 X"而模型实际上拒绝了。更糟的是，下游业务逻辑可能将拒绝文本（"我无法帮助处理该请求"）视为真实答案并据此行动，例如将拒绝字符串作为支持回复邮件发给客户。第 23 章构建安全感知的响应处理。

通用原则：`stop_reason` 是告诉你 _得到了什么类型的响应_ 而非仅仅是 _是否得到了响应_ 的字段。生产代码应显式分支：成功路径处理 `end_turn` 和 `tool_use`；恢复路径处理 `max_tokens`；告警在 `refusal`/`content_filter` 上触发；断言捕获意外值。将 `response.content[0].text` 视为答案而不检查停止原因是一类 bug，它在相同症状（文本看起来合理）背后隐藏多个故障模式。
