2. **高度交互的微调**。在快速原型或生产热修复中，工程师需要快速做精确 prompt 变更。DSPy 的编译-优化循环给编辑周期增加延迟；对于快速迭代，直接 prompt 访问更快。

通用原则：当被抽象的制品是 _实现细节_ 时抽象是生产性的；当被抽象的制品是 _利益相关者接口_ 时抽象与你对抗。决定你的 prompt 是实现细节还是接口，并相应选择框架。

**Q3.** _prompt 即代码 vs. prompt 即内容_。第 6 章将 prompt 框定为工程管道内的版本化制品。有一个竞争框架：prompt 作为 _内容_，由领域专家（律师、临床医生、客服主管）而非工程师编写，由内容管理工作流治理。Strata 的律师写法律研究 prompt；Beacon 的临床医生写摘要器 prompt。论证双方。指出一个解决张力的混合模式，并解释什么组织结构使混合可行。

**讨论：** **prompt 即代码论证。** Prompt 是 LLM 的指令；其行为是工程行为；prompt 中的 bug 产生工程团队待命的生产故障。将 prompt 视为代码（在 git 中、带代码审查、推广前 eval、回滚纪律）给工程团队所需的运营工具。本章的纪律（注册表、eval、A/B 测试、清单）是应用于 prompt 的工程纪律。竞争的 _内容_ 框架通过将 prompt 视为任何人可不经测试编辑的 wiki 页面来削弱这个，这正是生产 prompt 回归发生的方式。

**prompt 即内容论证。** Prompt 的 _内容_ 编码工程师不具备的领域专业知识。写 _不要在未显式检查的情况下混淆州和联邦管辖权_ 的律师在编码一个工程师无法创作的真实法律实践规范。将 prompt 视为工程制品、由工程师拥有的框架，排除了有知识使 prompt 真正工作的人。一些生产中最好的法律 RAG prompt 主要由律师而非 AI 工程师编写。

**混合解决。** 将 prompt 视为 **运营纪律中的代码，创作中的内容**。注册表、eval、版本控制、部署基础设施是工程拥有的（_代码_ 部分）。实际 prompt 文本协作创作，领域专家为主要作者，工程师为实现细节审查者（token 预算、结构约定、eval 信号）。每个 prompt 有两个审查者：领域审查者（法律正确性、临床正确性）和工程审查者（运营正确性）。推广需要两者。
