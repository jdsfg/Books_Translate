#### Self-Refine — Madaan 等 2023

模式：模型产生输出，然后批评自己的输出，然后基于批评修订。重复直到满意或直到预算耗尽。

2026 年，Self-Refine 以两种形式出现在生产中：

* **批评者 + 修订者循环**用于高风险输出（法律起草、临床摘要、代码生成）。批评者调用花费额外推理；质量提升在微妙错误上是有意义的。
* **前沿推理模型中的推理轨迹**（OpenAI 的 o3 系列、Claude Sonnet 4 的扩展思考）：模型作为推理的一部分做内部自我精炼。模式已被部分吸收进模型架构。

Self-Refine 被高估的地方：模型首轮输出已经足够的常规任务。额外推理成本使调用价格翻倍；如果质量提升小，trade-off 是差的。

### 6.3 DSPy 与 prompt 即代码的兴起

`DSPy` 是一个起源于斯坦福的框架，将 prompt 视为 _程序_ 而非自然语言字符串。程序员编写 _签名_（输入字段、输出字段、任务描述）；框架使用自己的优化技术将签名编译为 prompt。


    import dspy

    class CodeReview(dspy.Signature):
        """审查代码差异并产生结构化审查。"""
        diff: str = dspy.InputField()
        review: str = dspy.OutputField(desc="带严重性、文件、行号、问题、建议修复的结构化审查")
    reviewer = dspy.Predict(CodeReview)
    result = reviewer(diff="...").review


框架将 prompt 从代码中抽象出来。你写签名；框架写 prompt。框架然后可以 _优化_ prompt：对 eval 集运行签名，尝试变体措辞，选择 eval 分数最好的变体。这是 **自动 prompt 优化**，DSPy 的 MIPRO（多 prompt 指令提案优化器；Opsahl-Ong 等，2024）是 2026 年的领先实现。

DSPy 是正确工具的时候：

* **你有清晰的 eval 集。** MIPRO 是优化器；它需要评分函数来优化。没有 eval 集，DSPy 不比手写 prompt 好。
* **任务有良好边界。** 优化在有可辩护 _更好_ 指标的任务上工作。有开放式质量标准的任务更难优化。
* **你愿意放弃对 prompt 的直接控制。** 优化的 prompt 可能看起来不像你会写的样子。如果 eval 分数好，那可能没问题；如果你需要直接调试或修改 prompt，抽象可能与你对抗。

DSPy 过度的时候：

* **手写 prompt 已经有效的简单任务。** 框架开销对一次性 prompt 不值得。
* **prompt 需要为合规或审计原因人类可读的任务。** 优化的 prompt 可能变得不透明；如果监管者或高级审查者需要读 prompt，框架可能引入摩擦。

2026 年，DSPy 已建立但不普遍。最重度使用它的团队是研究相关群体和有成熟 eval 基础设施的大公司。跳过它的团队是小型创业公司（框架开销在小规模上超过收益）和 prompt 因面向利益相关者原因被刻意手动调优的团队。
