### 15.7 Helios "计算机使用 agent"的 2026 年现实

Helios 已在一个特定用例中试点计算机使用：处理解决需要 agent 操作供应商客户门户 UI 的工单（供应商不暴露特定操作的 API）。试点的发现说明生产现实：

* **成功率**：约 74% 轨迹完成任务。其余 26% 以各种方式失败：点击错误 UI 元素；卡在多步流程上；供应商 UI 变更时失败。
* **延迟**：每任务约 12-25 秒（比 API 等价任务长 5-10 倍）。基于视觉的屏幕分析慢。
* **成本**：每任务约 0.40-0.80 美元（vs API 等价 0.10 美元）。视觉 token 和更长轨迹驱动成本。
* **维护**：当供应商在 2025 年中更新 UI 时，约 30% 轨迹失败两周直到 agent 训练数据跟上。UI 变更风险是真实的。

Helios 的姿态：**谨慎使用计算机使用，在替代是无自动化时；只要有真正 API 就偏好；始终有人工回退路径**。试点在窄用例（约 0.5% 流量）中生产；更广泛部署以更好可靠性或更高价值用例为门控。

### 15.8 Triangle Trade-off 侧栏：多 agent vs 单 agent（质量增量 eval 格式）

经典 Helios 决策：对给定工单类型用单 agent 还是编排器-工作器？在其生产多问题工单 golden 集（约 150 案例）上：

架构 | 解决准确率 | 客户满意度（LLM 评判） | 延迟 p50（秒） | 成本 p50（美元）
---|---|---|---|---
单 agent（完整目录） | 0.68 | 3.4/5 | 3.8 | 0.13 美元
单 agent + 专业 prompt | 0.74 | 3.7/5 | 4.0 | 0.14 美元
编排器 + 2 工作器（并行） | 0.83 | 4.2/5 | 5.5 | 0.27 美元
编排器 + 3 工作器（并行） | 0.85 | 4.3/5 | 6.2 | 0.33 美元
编排器 + 顺序工作器 | 0.85 | 4.3/5 | 9.1 | 0.34 美元

要解读的：

1. **编排器-工作器在质量上胜出**（比单 agent +0.17 准确率和 +0.9/5 满意度）。对多问题工单，分解价值是真实的。
2. **并行 vs 顺序对延迟重要**，对质量不重要。3.6 秒延迟节省偏向并行；两种方式结果相同。
3. **成本溢价有意义**（2 倍单 agent）。在 Helios 的规模上，那是多问题工单份额每天 1.4K 美元。
4. **2 个工作器在质量上接近 3 个工作器**。递减回报快速出现。大多数分解不受益于 4+ 个工作器。

决策：多问题工单用编排器 + 2 工作器并行；单问题工单用单 agent + 专业 prompt。路由决策（用哪种架构）由编排器在第一轮基于工单分类做出。eval 驱动；非架构信念。
