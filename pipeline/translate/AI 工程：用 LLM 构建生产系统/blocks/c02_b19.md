**Q5.** _对真实工程师的技能层级自诊断_。§1.2 介绍了五级技能层级（基础、LLM 素养、模式、纪律、判断力）。选择你认识的一个团队中的真实工程师（你自己、一个队友、你最近面试的一个候选人）。对于五个层级中的每一个，写一两句话命名将他们置于该层级之上、之中或之下的具体证据。然后识别他们不扎实的最低层级，并概述一个四周学习计划使他们达到该层级的扎实水平。

提示

诊断是操作性的，不是愿望性的。证据是"我上个月在代码审查中看到他们做了 X"，不是"他们说他们理解 Y"。如果你无法命名证据，那本身就是该层级不扎实的证据。

**答案：** 一个关于假设的中级后端工程师 Priya 的示例，她六个月前加入 AI 团队（你的真实答案应该来自你自己的工作）：

* **基础（通用软件工程）**：扎实。证据：她拥有团队的 CI 工作流，写地道的 Python，能读 tcpdump trace。
* **LLM 素养（模型是什么、prompt 如何表现、输出为何随机）**：扎实。证据：在上个月的事件复盘中，她正确解释了为什么 temperature 0 在不同运行中仍产生不同输出（API 即使在 temperature 0 也不保证确定性，因为 GPU 非结合性）。
* **模式（RAG、结构化输出、agent 循环等）**：部分。证据：她交付过一个 RAG 功能但从未构建过结构化输出管道；她无法在 `outlines` 和 JSON-schema 模式之间独立选择。
* **纪律（eval 驱动 CI、成本工程、prompt 版本管理）**：弱。证据：她交付的 RAG 功能除了手动抽查没有 eval；她从未将 `pytest-evals` 接入 CI；她的 prompt 是内联字符串，不是注册表条目。
* **判断力（何时交付、何时投入 eval、何时砍掉）**：弱（在团队六个月时这是预期的）。证据：在最近的一次规划对话中，她默认"我们先原型看看"，这是本章警告的凭感觉交付姿态。

不扎实的最低层级：**纪律**。四周计划：第一周，让她与一位资深工程师配对，在她已交付的 RAG 功能上回溯加装 `pytest-evals`（让她在自己拥有的代码上体验纪律）；第二周，她引入 prompt 注册表模式（第 6 章预览）并将团队的内联 prompt 迁移上去；第三周，她负责她功能的成本仪表盘推出（第 18 章预览）；第四周，她对 PM 提出的新功能运行 _我们能 eval 这个吗？_ 门槛。四周结束时，她在纪律层级的三个子技能（eval-as-CI、prompt 注册表、成本仪表盘）各交付了一个有形工件，差距缩小。

诊断是诚实的因为证据是具体的。计划是可实现的因为每周的交付物很小。同样的形态适用于任何层级的任何队友：命名差距，命名能缩小差距的工件，排列工件的顺序。
