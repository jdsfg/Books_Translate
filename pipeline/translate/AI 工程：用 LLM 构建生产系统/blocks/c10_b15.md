**答案：** 有用的 prompt：_600K token 内部 HR 策略语料库，交互式聊天机器人。长上下文还是 RAG？用四个 RAG 杠杆论证。_ 你验证 (a) 延迟推理匹配实际 provider 数字（长上下文 TTFT 估计在 LLM 生成的回答中有时乐观），以及 (b) 推荐反映特定用例（交互式 vs 批处理是不同决策；反思你产品的实际延迟预算）。

**Q4.** _将真实 RAG 故障映射到其检索层根因_。以下是三个 RAG 故障描述。对每个，指出检索层根因（非 LLM 层根因）和工程修复。

(a) "聊天机器人用 2023 年定价回答了关于 2025 年定价的问题，尽管我们几个月前更新了定价文档。" (b) "当用户询问功能 X 时，聊天机器人有时描述功能 Y，它相似但不同。" (c) "聊天机器人的答案引用了在我们文档中任何地方都不存在的来源 URL。"

**答案：**

(a) **根因**：陈旧索引。定价文档更新时检索索引未更新。陈旧内容的向量嵌入留在索引中；聊天机器人检索陈旧块。**修复**：增量索引管道检测文档变更（例如通过 git 钩子或内容哈希）并重新嵌入变更章节；定期全量重新索引作为安全网。

(b) **根因**：嵌入模型不够好地区分功能 X 和功能 Y；它们在嵌入空间中语义接近。Top-K 检索返回混合块（一些来自 X，一些来自 Y）；LLM 困惑。**修复**：更强嵌入（如有领域特定的）；添加重排序器使用交叉编码器注意力在排序步骤更锐利地区分功能 X 和功能 Y；添加混合搜索使精确功能名查询获得额外权重。

(c) **根因**：LLM 在编造看起来可能存在的 URL（引用层的幻觉，即使检索正确）。这严格说是生成层故障，但检索层可以帮忙。**修复**：在 prompt 中强制按 _chunk-id_（非 URL）引用，并有后处理步骤将 chunk-id 转换为检索元数据中的规范 URL。LLM 无法编造不存在于检索集中的 chunk-id；后处理器将有效 chunk-id 转为有效 URL。（还有：验证输出中的 URL 并拒绝返回带非验证 URL 的答案。）

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_三个 RAG 故障：陈旧答案、混淆功能答案、编造 URL 答案。对每个，给出检索层根因和修复。_ 你验证 (a) 修复专门针对检索层（LLM 可能默认 _做更好的 prompt_；推回到检索层，本章框架适用），以及 (b) 修复在你的技术栈中可实现（每个修复是真实工程项目；合理性检查工作量估计）。
