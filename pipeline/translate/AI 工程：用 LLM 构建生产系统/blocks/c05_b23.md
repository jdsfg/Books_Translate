4. **成本意识行为**。eval 是否包含 agent 是否做出适当工具调用（不多不少）和产生适当长度响应的信号？Helios 每月 1M 美元的推理账单对 agent 冗长敏感。_差距处理_：如果缺失，添加一个结构 eval（形态 4）标记超过 token 预算阈值或做冗余工具调用的 agent 运行。
5. **多轮连贯性**。eval 是否包含多轮对话，还是只有单轮输入？真实 Helios 流量主要是多轮的（客户追问）。_差距处理_：如果缺失，添加 30 个多轮案例，eval 评分 agent 跨轮的连贯性和一致性。

对于发现的每个差距，行动相同：添加案例，在需要时扩展量表，在新维度上重新校准 LLM 评判者，然后将扩展的 eval 接入 CI。覆盖审查是反复的纪律；预期每年重复并在任何重大事件后重复。

**AI 协作子问题**：你会如何请 LLM 帮助完成这个练习，你会在它的回答中验证什么？

**答案：** 有用的 prompt：_我有一个 200 案例的客服 agent eval。我应该检查哪些覆盖维度，每个差距我该怎么做？_ 你验证 (a) 提议的维度匹配你产品特定的故障模式（LLM 会产生通用列表；你调到 Helios 的实际配置，例如，每租户变异性是 Helios 特定维度，通用答案会遗漏），以及 (b) 提议的补救有现实的工作量估计。LLM 倾向于过度泛化；你适配你的产品。

**Q4.** _eval 阈值设置_。你的团队构建了一个 12 分量表的 eval。当前生产版本在 golden set 上的平均分是 9.4。你在决定回归阈值：什么最低平均分应阻止 PR 合并？推理 trade-off 并提出具体阈值及理由。

提示

阈值太紧阻止合法改进；太松允许回归通过。考虑自然 eval 噪声（同一 prompt 的分数在运行间变化多少？）。

**答案：** 推理：

阈值是 (a) 捕获真实回归（更低阈值 = 更敏感）和 (b) 避免阻止合法改进的误报（更低阈值 = 对团队更多摩擦）之间的 trade-off。

步骤 1：测量自然 eval 噪声。对当前生产版本运行 eval 套件三次（temperature 0；如果有 LLM 作为评判者组件，即使 temperature 0 它们也引入噪声）。假设三次运行产生 9.42、9.36、9.41——范围 0.06。这是噪声下限；比这小的回归与噪声不可区分。

步骤 2：选择大于噪声下限但小于你认为 _真实_ 回归的阈值。常见经验法则是 _阈值 = 基线减 2×噪声标准差_。如果噪声大约 ±0.05，阈值是 9.4 - 0.1 = 9.3。PR 评分低于 9.3 可能显示值得调查的真实回归。
