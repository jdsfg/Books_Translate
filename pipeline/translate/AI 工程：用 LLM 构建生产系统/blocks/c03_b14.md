### 2.11 How This Breaks：将模型与产品混淆

**命名的故障模式**：将模型与产品混淆。一个团队将 LLM 当作产品本身，而非产品内部的一个概率性组件。需要保证的行为（某些话题的拒绝、特定输出格式、来源归因、升级路径）完全委托给模型的训练行为，在模型之外没有执行层。

**真实或复合事件**：一个来自整个行业的复合例子。一个创业公司交付了一个 LLM 驱动的客户服务功能，按照 system prompt，它 _应该_ 拒绝代表公司做出承诺：定价、退款、政策例外。system prompt 在三个地方说了这件事，还附了示例。上线六周后，一个用户构造了一个利用模型解释嵌套指令方式的怪癖的 prompt，模型发出了一个承诺（"是的，我们将为您退款 500 美元以补偿不便"）。用户截图。法务团队介入了。

失败不在于模型不好。失败在于 _工程团队将 system prompt 当作保证，而实际上 system prompt 是一个概率性条件器，它偏置模型的行为但不执行它_。没有输出验证层。没有对输出的拒绝分类器。没有工具调用中介来将任何 _退款承诺_ 路由通过确定性策略检查。

**工程缓解措施**：将 _模型_ 与 _产品_ 分离。system prompt 做它的工作（偏置模型行为）。一个单独的输出验证层执行硬约束：它运行拒绝分类器，检查承诺金额是否超过阈值，并验证响应形状。对于带工具调用的 agent 式流程，确定性策略检查发生在工具层，而非模型的自然语言中。模型是组件；产品是你围绕组件封装的东西。第 16 章将把这个原则构建为 9 层参考架构。第 23 章将以 _生产安全_ 为标题回到这个话题。

**本应捕获它的 eval**：一个 _prompt 注入鲁棒性_ eval。一个包含 100+ 对抗性输入的 golden set，旨在从模型中引出拒绝违规。在每次 prompt 变更和每次模型升级时运行。如果 system prompt 是唯一防线，这种规模的对抗性 eval 会在一天内暴露差距。如果输出验证层到位，即使模型本身偶尔被欺骗，eval 也应显示稳健的 0% 拒绝违规率，因为验证层捕获了模型遗漏的东西。eval 的存在就是本应捕获它的东西；失败在于上线前没有这样的 eval。
