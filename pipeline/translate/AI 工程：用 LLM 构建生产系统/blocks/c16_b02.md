### 15.1 何时多 agent 有帮助（何时没有）

一个设计良好的单 agent 配好的工具目录能做很多。何时使用多 agent 的问题有具体形状：

**多 agent 有帮助时**：

* _任务自然分解为专业子任务_，每个需要不同知识或能力。需要技术调试（一个专业）、计费政策分析（另一个）和退款处理（第三个）的客户支持工单受益于专业 agent。单 agent 可被指示处理全部三个，但 prompt 变成科学怪人；专业 agent 有更清晰的职责。
* _子任务可并行化_。如三个子任务独立（无数据流），并行运行三个 agent 节省墙上时钟时间。单 agent 串行执行浪费并行机会。
* _工具目录对单 agent 不可管理_。Helios 的完整工具目录是 40 个工具；如果是 200 个（多垂直平台的情况），单 agent 的 prompt 无法有效展示。每个垂直的专业 agent 有更窄的工具目录。

**多 agent 无帮助时**：

* _任务串行且短_。单上下文线程上的 5 次迭代任务无并行机会；生成多个 agent 增加协调开销。
* _子任务大量共享状态_。多 agent 在独立子任务上出色；依赖彼此输出的子任务反正要串行，agent 间通信开销主导并行收益。
* _团队缺乏多 agent 调试的运维成熟度_。多 agent 系统更难观察、更难调试、更难有界（第 14 章 §14.7）。未掌握单 agent 运维的团队未准备好做多 agent。

2026 年常态：大多数生产 AI 使用单 agent。多 agent 保留给价值增值证明复杂性税合理的情况。陷阱是过度工程：团队读多 agent 论文，决定自己的问题看起来类似，构建精心多 agent 架构，产生比调好的单 agent 更差的结果。

### 15.2 协调模式：编排器 + 工作器、辩论、层次分解

三种模式主导 2026 年多 agent 实践。


#### 模式 1：编排器和工作器

2026 年主导模式。一个 _编排器_ agent 分解任务并分配子任务给 _工作器_ agent。工作器做其子任务；编排器聚合结果并产生最终输出。

    [用户输入]
         ↓
    [编排器]
         ↓ 分解
    [工作器 A] [工作器 B] [工作器 C]  （通常并行）
         ↓        ↓         ↓
         [编排器聚合]
         ↓
    [最终输出]


适用情况：有自然并行子任务的任务；工作器可专业化（不同系统 prompt、不同工具目录）；编排器的推理关于 _分解和综合_，而非子任务内容。

Helios 对复杂工单使用此模式：编排器将工单分类为子任务（账户问题 + 技术问题 + 退款资格），生成专业工作器，聚合其发现为客户面向响应。
