#### 深入思考

**Q1.** _RAG vs 微调 vs 长上下文决策_。2026 年，你可以用三种方式给模型新信息：RAG、微调或长上下文。比较它们。什么用例下每个是正确答案？指出混合最优的用例。

**讨论：** 三种方法：

**RAG**：信息存在外部索引中；查询时检索；模型无需重新训练即看到新鲜信息。优势：新鲜、可引用、可扩展到巨大语料库、与模型生命周期解耦。劣势：需要检索工程；延迟成本；块边界问题。

**微调**：信息通过额外训练烤入模型权重。优势：信息是模型内在的；查询时无检索。劣势：更新昂贵（每次变更都是微调）；_半衰期_ 问题（第 22 章）：微调在下一次主要发布后变得比基础模型更差；有损（模型不忠实地保留所有训练内容）。

**长上下文**：信息每次调用直接放入上下文窗口。优势：简单；忠实（模型看到确切内容）；无检索工程。劣势：每次调用成本（每次调用为完整内容付费）；大内容延迟；语料库大小上限。

每个的正确答案：

* **RAG**：Strata 的法律语料库。数亿 token；需要新鲜度；引用重要。
* **微调**：需要一致使用特定品牌声音的聊天机器人。声音稳定；烤入权重产生一致语调无需 prompt 预算。
* **长上下文**：小型产品文档聊天机器人（第 8 章的第一层示例）。语料库适合；最简单答案。

混合：**微调语调 + RAG 事实 + 长上下文当前对话最近状态**。客服 agent 一致以品牌声音说话（微调），通过 RAG 检索客户特定事实（按租户索引），在长上下文历史中保持最近对话。此组合在成熟生产 AI 团队中越来越常见。

**Q2.** _2030 年 RAG 的轨迹_。推测：随着上下文窗口在工作马层级成本下增长到 10M+ token，RAG 会减少还是转变？论证转变而非减少。指出如果上下文便宜且大时出现的两个新 RAG 模式。

**讨论：** 减少论证：长上下文覆盖更多案例；RAG 变小众。

转变论证：RAG 不消失；其 _角色转变_。

**模式 1：RAG 用于实时数据**。即使有 10M token 便宜上下文，你不能包含每分钟更新的数据（新闻、股价、传感器数据）。在持续更新索引上的 RAG 成为新鲜层；长上下文是策展内容层。

**模式 2：RAG 作为个性化选择层**。按用户数据（"你过去 3 年的客户交互"）可能适合 10M 上下文，但你不想每次查询发送 10M token，因为成本累积。RAG 每次查询选择用户历史的相关子集；长上下文模型处理策选子集。
