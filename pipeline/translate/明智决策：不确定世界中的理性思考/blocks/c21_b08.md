1. **低估营运资本：** 餐馆在达到现金流盈亏平衡前需要 3–6 个月营运资本。若她在初始装修与开业成本后没有足够跑道，缓慢起步就会致命。_事前复盘问题：_"我第 6 个月的现金流是什么样，当我用完储备时发生了什么？"

  2. **区位客流低于预测：** 客流预测出了名地乐观。若她的模型假定每天 80 桌而现实是 45，财务就会崩塌。_事前复盘问题：_"实际日客流 vs. 我的预测是什么，我在假设中哪里错了？"

  3. **关键员工在关键时刻离职：** 餐馆运营关键依赖主厨或总经理。若那人离开——而餐馆离职率非常高——运营可能迅速恶化。_事前复盘问题：_"谁离开了，为什么？有什么我本可以做来留住他们的吗？"

  4. **概念差异化不够：** 市场比预期有更多竞争，或她的概念没有提供足够理由选择她而非既有替代。_事前复盘问题：_"顾客为什么去别处？竞争对手提供了什么我没有的？"

  5. **成本结构爬升：** 食品成本、劳动力成本与租金一起迅速吞噬利润率。小成本增加会复合。_事前复盘问题：_"我实际的食品成本 % 和劳动力成本 % 结果是多少，相对我的预测？"

**复盘：** 对每个失败模式评估：这有多可能？若发生，会有多糟？我现在能做什么来降低其概率或影响？

**Q3.** 一个软件开发团队即将开始一个有固定交付截止日期的 6 个月项目。项目经理进行事前复盘。两个失败模式突出出现：（1）对第三方 API 的关键依赖未及时解决，以及（2）客户在第 3 个月后的范围变更打乱时间线。PM 应如何把这些发现纳入项目计划？

提示

对每个失败模式，识别它是可预防的（降低概率）还是仅可管理的（若发生则降低影响）。然后设计具体计划变更，不只是通用监测。

**答案：** 按失败模式分析：

**(1) 第三方 API 依赖：** 性质：大体可预防且可管理。PM 既可以降低概率也可以降低影响。计划变更：（a）_风险降低：_ 在前两周内显式识别所有第三方 API 依赖；按关键性与已知可靠性分类。在承诺时间线前与 API 提供商协商 SLA 或测试访问。（b）_后备设计：_ 对每个关键 API 依赖，设计抽象层，若第三方未能交付，允许用不同 API 或内部实现替代。这前期花费工程时间，但把不可管理风险转换成可管理风险。（c）_早期集成测试：_ 把 API 集成测试安排在第 4–6 周，而非第 20–24 周。早发现问题允许恢复；晚发现则不行。（d）_合同条款：_ 若第三方提供商有合同参与，纳入交付里程碑与救济。
