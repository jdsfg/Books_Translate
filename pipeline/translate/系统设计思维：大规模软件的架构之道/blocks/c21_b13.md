#### 应用问题

**Q1.** 详细设计已读回执流程。用户 A 给用户 B 发消息。用户 B 的客户端收到消息。追踪从消息收到到用户 A 的 UI 出现双勾的完整事件序列，包括所有网络调用、数据库写入和服务器间通信。

提示

追踪投递状态机：已发送 → 已送达 → 已读。每个状态转换都需要一次数据库写入和一个实时事件回发发送者。思考连接服务器在步骤间崩溃会怎样。

**答案：**

**状态：已发送**

1. 用户 A 的客户端通过 WebSocket 向连接服务器 S1 发送 `{type: "message", to: B, content: "Hey!", client_msg_id: "c123"}`。
2. S1 转发给消息服务。
3. 消息服务生成 `server_msg_id = M456`，持久化 `{message_id: M456, conv_id: C1, sender: A, content: "Hey!", sent_at: T1, state: SENT}` 到消息数据库。
4. 消息服务发送 `{type: "send_ack", client_msg_id: "c123", server_msg_id: M456}` 回 S1 → S1 推送给 A 的客户端。
5. A 的客户端更新 M456 显示单勾（已发送到服务器）。

**状态：已送达**
6. 消息服务在注册表查 B 的连接服务器：`GET user:B:server` → S3。 7. 消息服务经服务器间 RPC 发送 `{type: "new_message", message_id: M456, from: A, content: "Hey!", sent_at: T1}` 给 S3。 8. S3 通过 WebSocket 把消息推送给 B 的客户端。 9. B 的客户端显示消息，并立即通过 WebSocket 回发 `{type: "delivery_ack", message_id: M456}`。 10. S3 收到 ack，写数据库：`UPDATE messages SET delivered_at = NOW() WHERE message_id = M456`。 11. S3 查 A 的连接服务器：`GET user:A:server` → S1。 12. S3 经服务器间 RPC 发送 `{type: "delivery_receipt", message_id: M456}` 给 S1。 13. S1 把回执推送到 A 的 WebSocket。 14. A 的 UI 更新 M456 为双勾（已送达接收者设备）。

**状态：已读**
15. B 打开包含 M456 的对话。 16. B 的客户端发送 `{type: "read_ack", conversation_id: C1, read_up_to: M456}` 给 S3。 17. S3 写入：`UPDATE conversation_participants SET last_read_at = NOW() WHERE conv_id = C1 AND user_id = B`。同时：`UPDATE messages SET read_at = NOW() WHERE message_id = M456`。 18. S3 经服务器间 RPC 发送 `{type: "read_receipt", message_id: M456}` 给 S1。 19. S1 推送给 A 的 WebSocket。 20. A 的 UI 更新 M456 为蓝色双勾（接收者已读）。

**崩溃恢复：** 如果 S3 在第 10 步和第 12 步之间崩溃，数据库已有 `delivered_at` 时间戳但 A 没收到回执。当 A 的客户端下次轮询消息状态（定期兜底，每 30 秒），它从 API 拉取最近消息当前状态，发现 `delivered_at` 已设置，于是更新 UI。最终一致。
