#### 概念检测

**Q1.** 解释为什么增加更多读副本对写重的数据库工作负载没有帮助。

**答案：** 读副本从主库接收并应用变更，但不接受直接写入。无论有多少副本，所有写都进入主库。如果主库被写压垮，副本无助于减少该负载——它们实际上还会略微增加主库负担，因为主库必须向更多副本流式传输写日志。要扩展写，要么垂直扩展主库（有限），要么通过分片把写负载分区到多个主库实例。

**Q2.** 什么是复制延迟，举一个它给用户造成可见问题的场景。

**答案：** 复制延迟是主库上应用写入与副本反映该写入之间的时间延迟。因为复制是异步的——主库写入，然后流式传输变更，副本应用——总会有一个窗口期，副本看到的是旧视图。

一个经典可见问题：用户提交表单（写入主库），然后被重定向到从副本读取的确认页，却看不到自己的更新。这导致困惑的用户以为操作丢失，常常引发重复提交。

**Q3.** 基于范围和基于哈希的分片有什么区别？各举一个优点。

**答案：** 基于范围的分片按 shard key 的值范围分配记录（例如 user ID 1–1,000,000 在 Shard 1）。优点：支持高效范围查询——查找 key 范围内的所有记录只需接触一个或几个 shard。基于哈希的分片对 shard key 应用哈希函数并用结果选择 shard（例如 `user_id % N`）。优点：使数据在 shard 间大致均匀分布，消除单调递增 key 造成的热 shard。

**Q4.** 为什么重分片昂贵，减少重分片频率的一种策略是什么？

**答案：** 重分片昂贵，因为改变 shard 数量会改变大部分或全部记录的哈希映射。8 个 shard 时 `user_id % 8` 下在 Shard 3 的记录，加 1 个 shard 到 `user_id % 9` 后可能属于 Shard 6。几乎每条记录都需要评估并可能移动。数据量数百 GB 或 TB 时，这是大型、高风险、耗时的实时迁移。

一种常见缓解是早期配置远超当前需要的 shard（例如 8 台物理机上的 64 个逻辑 shard）。需要更多容量时，把逻辑 shard 移到新物理机，而不改变逻辑 shard 数量或哈希映射。一致性哈希也能在容量变化时减少数据移动。
