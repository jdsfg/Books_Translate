#### 方案 1：粘性会话（错误）

最简单的修复：配置负载均衡器，让同一用户总是路由到同一台服务器。Alice 的会话在 Server A 创建后，她后续所有请求都路由到 Server A。问题解决了吗？

并不完全。

**IP 哈希问题：** 基于 IP 哈希的粘性按客户端 IP 路由。但很多用户共享 IP 地址（公司 NAT、移动运营商 NAT）。一家大公司的所有员工可能显示为同一个 IP 地址——他们全都会被路由到同一台后端服务器。

**服务器故障问题：** 如果 Server A 宕机，Alice 的所有会话都丢失了。她（以及所有会话在 Server A 上的其他用户）必须重新登录。粘性会话把服务器故障变成强制登出。

**扩展问题：** 如果 Server A 积累了很多活动会话（重度用户），它比 Server B 或 C 得到更多流量——分布不均。负载均衡器失去了平衡负载的能力。

**部署问题：** 如果你需要重启 Server A（部署新代码），所有粘着 Server A 的用户都会被登出或经历中断。零停机部署变得困难得多。

粘性会话解决了症状（请求到达知道它们的会话），却保留了根本问题（状态在服务器间碎片化）。这是错误架构。只应在实现正确方案前作为临时 workaround。


#### 方案 2：服务器间共享会话（脆弱）

另一种方案：使用分布式共享文件系统或数据库，三台服务器都把会话数据写进去。Server A 把 Alice 的会话写到共享存储；Server B 和 C 可以读取。

原则上可行。实践中，这正是在重新发明分布式会话存储——而方案 3（正确答案）就提供这个。用 NFS 共享文件系统存会话数据很慢、运维脆弱，并增加新的单点故障。

正确做法是使用为此工作负载专门设计的键值存储——Redis。
