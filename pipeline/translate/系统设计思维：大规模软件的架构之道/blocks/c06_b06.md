#### 定义：BASE

**BASE** 代表 **Basically Available, Soft state, Eventually consistent（基本可用、软状态、最终一致）。**

* **基本可用（Basically Available）：** 系统始终可用（没有“服务不可用”错误），但响应可能是旧的或基于部分数据。
* **软状态（Soft state）：** 即使没有新写入，系统状态也会随时间变化，因为副本在收敛到一致性。
* **最终一致（Eventually consistent）：** 如果没有新写入，系统最终会在所有副本上收敛到一致状态。

plain 语言：BASE 系统优先保证可用性而非正确性，把临时不一致作为保持可用的代价。

BASE vs ACID 不仅是技术选择——它关乎对用户什么更重要的哲学。ACID 说：“正确性至上。如果我们不能正确，宁可不可用。” BASE 说：“可用性至上。与其给用户看错误页面，不如给他们看略旧的数据。”

对社交媒体 Feed，旧数据可接受。对银行，不可接受。这就是为什么两种哲学都有一席之地——以及为什么复杂系统常同时包含 ACID 和 BASE 组件，各自服务适合其哲学的数据类型。


#### 常见误解

“NoSQL 意味着没有一致性。” 错误。许多 NoSQL 数据库提供可调一致性级别。Cassandra 允许你要求写入被所有副本确认（强一致性，类似 ACID），代价是降低可用性；或只被一个副本确认（最终一致性，最大可用性）。DynamoDB 也提供“强一致读”选项。区别不是 ACID 或没有；而是一个可以调节的谱系。

同样，“关系型数据库总是一致的”也错误。正如第 5 章讨论：使用异步复制时，复制型关系数据库可能从副本提供旧读。ACID 适用于单节点；分布式会削弱保证。


### 6.7 如何选择——决策框架

有了这套分类法，如何为新组件选择数据库？按顺序应用以下问题：

**第 1 步：主要访问模式是什么？**

* “按 ID 取实体” → 键值存储或文档存储
* “按多属性复杂过滤查询” → 关系型数据库
* “跨多跳遍历关系” → 图数据库
* “写入时间序数据、按时间范围查询” → 列族存储

**第 2 步：schema 稳定性如何？**

* 稳定、定义清晰的 schema → 关系型数据库
* 演进 schema、异构数据 → 文档存储

**第 3 步：一致性要求是什么？**

* 需要强一致性（金融数据、认证） → 关系型数据库
* 可接受最终一致性 → NoSQL 选项打开

**第 4 步：预期规模如何？**

* < 100 万行、< 1,000 写入/秒 → 关系型数据库能处理
* > 1 亿行或 > 10,000 写入/秒 → 考虑分布式 NoSQL

**第 5 步：团队经验如何？**

* 有成熟的 PostgreSQL 经验 → 除非出现明确需求，否则继续用它
* 有强大的 Cassandra 团队 → 在合适工作负载上利用它

实践中，大多数大型系统使用多种数据库：关系型数据库用于核心事务数据，键值存储用于缓存和会话，文档存储用于非结构化内容，列族存储用于高容量事件数据。
