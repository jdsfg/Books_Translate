Saga 编排器拥有行为耦合——它知道 API 调用序列。这类似于任何按顺序调用多个 API 的客户端。Web 浏览器加载页面时会调用 CDN、用户服务、feed 服务——它在“知道”它们 API 的意义上与它们耦合。我们不认为这 problematic。

对编排器有意义的问题是：编排器包含的是*业务逻辑*（这是否有效升级？是否应打折？）还是*工作流逻辑*（调用 Payment，然后 User，然后通知）？业务逻辑在编排器中是问题——它应属于拥有该业务的服务。工作流逻辑在编排器中是合适的——这正是编排器存在的意义。


### 本章总结

本章构建了可靠分布式工作流的工具集。任务队列把工作从请求路径卸载，实现重试逻辑并把生产者与消费者解耦。定时任务处理周期性工作。至少一次投递保证消息被处理，但引入了幂等性需求——设计操作使其多次执行安全。

幂等键让非幂等操作变得幂等：每次操作尝试的唯一标识符让服务器检测并去重重试。Outbox 模式解决双写问题，无需分布式事务即可可靠发布事件。

Saga 模式用补偿事务代替回滚，协调无需 2PC 的多服务工作流。编舞通过事件把协调逻辑分布到各服务；编排把它集中在编排器服务。两种方法各有适用场景。

SocialSnap 开篇的“向用户收费并发送确认邮件”问题——本章开头的 Thread A 例子——现在完全可解：saga 配编排器、每次服务调用带幂等键、用 Outbox 模式可靠发布事件、用补偿事务（用户升级失败则退款）恢复失败。

第 16 章把视角拉大到全系统失败。本章构建的所有异步处理让失败处理更容易——消息队列在故障期间缓冲流量。SocialSnap 将面临第一次生产故障，我们将看到熔断、舱壁和优雅降级如何决定这次故障是灾难还是可控的小插曲。
