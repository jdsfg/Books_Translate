#### 深入思考

**Q1.** 本章主张选择数据库应从访问模式开始，而不是从技术偏好开始。但许多工程师有一个“默认数据库”（通常是 PostgreSQL 或 MongoDB），只有遇到问题才切换。这是务实还是冒险？务实的默认何时变成技术陷阱？

**讨论：** 务实的默认方法在开始时通常是正确的。起步就用 PostgreSQL 很少错——它成熟、易懂、胜任多种工作负载、工具丰富。同样，对文档密集型应用默认用 MongoDB 也不算错。

务实的默认在两种情况下会变成陷阱：

**1. 访问模式明显不匹配。** 如果你从一开始就构建时间序列 IoT 平台（启动负载就是每秒 50,000 次写入），选择 PostgreSQL 并计划“以后出问题再迁移到 Cassandra”，意味着你将在生产事故中而不是平静规划期遇到这些问题。如果访问模式明显超出关系型模型，不要从那里开始。

**2. 数据建模决策把你锁定。** 一个带复杂外键关系、触发器和存储过程的关系型 schema 很难迁移到 NoSQL。如果建模时假设永远要关系型 join，然后在规模下发现查询模式不匹配，“默认 PostgreSQL”就变成陷阱。这不是避免 PostgreSQL 的理由——而是应该带着未来访问模式来建模。

纪律：选数据库前花 30 分钟思考访问模式。不用想太多，但足以避开明显错配。目标不是选出完美数据库——而是避免选出明显错误的数据库。

**Q2.** 本章识别了四种 NoSQL 家族，各为不同访问模式优化。但考虑一个真实产品如 Instagram：用户资料（可变属性）、社交图（朋友和关注关系）、照片存储（大二进制文件）、热门 hashtag（实时计数器）、私信（每对话按时间序）。你会把哪种数据库家族分配给每个关注点，为什么？有哪种数据库家族能同时胜任多个关注点吗？

**讨论：** Instagram 的架构是同时对一个产品内多个关注点应用决策框架的有用练习。

**用户资料：** 文档存储（MongoDB 或类似）自然合适——每份资料有可变的可选属性集合（简介、网站、商业类别、关联账户）。灵活 schema 无需迁移即可处理。或者，带 JSONB 列的关系型数据库（PostgreSQL 的混合方案）给你 schema 灵活性和关系查询能力。
