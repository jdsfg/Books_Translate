#### 深入思考

**Q1.** 写时扇出方法在 Redis 中预计算 timeline。Redis 是内存存储——Redis 重启或故障时，所有这些预计算 timeline 会怎样？架构如何从冷 Redis 缓存恢复？

**讨论：** 这就是预热问题——Redis 故障后空启动，预计算 timeline 消失。用户请求 feed 时缓存未命中，feed 组装回退到读时扇出——正是我们设计要避免的昂贵路径。对 500 万（5 million）并发 feed 观看者同时冷缓存，这是 500 万次完整 feed 组装查询同时打数据库——可能是压垮性的突发。

**恢复策略：**

**Redis 持久化（RDB 或 AOF）：** Redis 可配置持久化到磁盘（RDB 快照或 append-only log）。重启后 Redis 从快照重载。对频繁更新的 timeline 数据，每 60 秒 RDB 快照可能丢失最多 60 秒扇出写入。对 60 秒新鲜度 SLO，这是可接受的——恢复后用户可能看到 60 秒前的 feed，仍在 SLO 内。

**Redis 复制（Redis Cluster 或 Sentinel）：** 运行带副本的 Redis。主库故障时提升副本，只丢失几秒在途写入。这是第 11 章和第 16 章的标准生产做法。

**渐进式缓存预热：** Redis 全集群故障后冷启动时，限制每秒触发数据库回退的冷未命中请求数。使用请求队列或限流器防止 500 万用户同时触发昂贵兜底查询。每个用户最初几个请求预热其 timeline；后续请求命中缓存。5–10 分钟内大多数活跃用户 timeline 被重新填充。

**从数据库预预热：** 后台进程从数据库读取最近帖子和用户关注关系，为最活跃用户（日活前 10%）重建 timeline。预热在数分钟而非数小时内完成。

教训：Redis（或任何用作预计算状态主数据源的内存存储）必须被视为关键组件，配置主-备故障转移和持久化，而不是可丢弃的缓存。第 16 章可靠性模式完全适用。

**Q2.** 考虑以下观察：新闻 feed 排序算法创建反馈循环。用户与高排名内容互动，这发出信号表明该内容应排名更高，算法把它展示给更多用户，产生更多互动。这个反馈循环对 feed 内容多样性的长期影响是什么，哪些机制可能抵消它？

**讨论：** 反馈循环产生“互动引力”——早期获得互动的内容排名更高，展示给更多用户，收到更多互动，进一步攀升。这是富者愈富的动态，网络理论中也称优先连接。
