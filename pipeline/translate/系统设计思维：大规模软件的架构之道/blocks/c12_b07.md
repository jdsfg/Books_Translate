### 12.7 分布式事务——深层的痛

SocialSnap 中有一个操作需要原子更新：当用户被收取高级订阅费时，两件事必须一起发生——`payments` 表中创建一条支付记录，`users` 表中把该用户的 `is_premium` 标志设为 TRUE。

单数据库时，这是一个 SQL 事务：


    BEGIN;
    INSERT INTO payments (user_id, amount, ...) VALUES (42, 9.99, ...);
    UPDATE users SET is_premium = TRUE WHERE user_id = 42;
    COMMIT;


如果任一操作失败，事务回滚——支付记录消失，用户仍是非高级。数据库保证原子性。

分片后，`payments` 和 `users` 可能在不同 shard（如果按不同 key 分片），也可能在同一 shard（如果都按 `user_id` 分片）。SocialSnap 的情况中，两张表都按 `user_id` 分片，因此同一用户的数据落在同一 shard——这个特定问题被避免了。

但考虑转账操作：用户 Alice（Shard 1）给用户 Bob（Shard 3）送礼。扣减 Alice 余额，增加 Bob 余额。这些更新必须原子——不能扣了 Alice 却没加到 Bob，让钱消失在虚空中。Alice 在 Shard 1、Bob 在 Shard 3，这就是**分布式事务（distributed transaction）**。


#### 定义：分布式事务

**分布式事务**是跨越多个独立数据存储（数据库、shard、服务）的事务，必须是原子的——要么所有操作都提交，要么都回滚——即使这些存储是独立系统。

plain 语言：你想对多个独立数据库施加一系列变更，就像它们是一个数据库一样，并保证永远不会看到部分状态。


#### 两阶段提交（2PC）

分布式事务的经典协议是**两阶段提交（two-phase commit，2PC）**。一个**协调器（coordinator）**编排事务：

1. **第一阶段（准备）：** 协调器向每个参与 shard 发送“准备”消息。每个 shard 把拟议变更写到临时区域，并承诺（投“yes”）可以提交。如果任何 shard 不能提交（如约束冲突或故障），它投“no”。

2. **第二阶段（提交）：** 如果所有 shard 都投“yes”，协调器发送“提交”。每个 shard 应用已准备的变更并释放锁。如果任何 shard 投“no”，协调器向所有 shard 发送“中止”，它们丢弃已准备的变更。

如果协调器在第一阶段后、第二阶段前故障会怎样？参与 shard 会卡在持有已准备数据的锁上，等待永远不会到达的提交或中止。系统处于**阻塞**状态——其他触及相同数据的事务必须等待。

2PC 是分布式事务标准，但它慢（需要多次网络往返）、故障时阻塞、正确实现复杂。对高容量操作，2PC 本身会变成性能瓶颈。
