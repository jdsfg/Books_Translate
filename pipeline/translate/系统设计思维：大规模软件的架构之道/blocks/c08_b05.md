#### 为什么日志模型改变一切

**多个消费者组独立推进：** 三个不同团队可以各有自己的消费者组读取同一个 Kafka 主题。每个消费者组维护自己的 offset。A 团队的分析管道可以落后 2 小时，而 B 团队的实时通知系统读取相同消息但有自己的日志位置，不受影响。

**可重放：** 因为消息被保留，消费者可以重置 offset 重放历史事件。当你部署一个以新方式处理相同事件的新消费者（如新的推荐算法）时，可以让它从日志开头处理所有历史事件。在传统队列中，那些消息首次消费后就被删除——已经没了。

**顺序保证：** 在一个分区内，消息严格有序。如果你需要某个实体的顺序保证（用户 123 的所有事件必须按顺序处理），可以按用户 ID 分区——用户 123 的所有事件进入同一分区，并在那里按顺序消费。

**规模：** Kafka 分区可分布在许多服务器上。一个 100 分区的主题可支持 100 个并行消费者实例，每个处理一个分区。Kafka 集群 routinely 处理每秒数百万条消息。


#### Kafka 的代价

Kafka 运维复杂。搭建 Kafka 集群、调整分区数、管理消费者组 offset、维护协调服务（历史上是 ZooKeeper，现在是 KRaft）都需要专业知识。日志保留模型意味着必须仔细配置保留期——保留太久消耗存储；保留太短暂无法重放。

对更简单的用例（单个消费者从队列读取），托管服务如 Amazon SQS 或 Google Cloud Pub/Sub 通常是正确选择。Kafka 在你需要高吞吐、多个独立消费者组或事件重放能力时才配得上它的复杂度。
