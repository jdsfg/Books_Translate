* 队列深度连续 10 分钟增长 → page on-call（消费者可能崩溃）
* 邮件投递成功率 5 分钟低于 95% → page 邮件团队（第三方邮件提供商问题）
* 消费者滞后超过 50,000 条消息 → page on-call（处理速度相对于流量太慢）
* 死信队列有消息 → 非紧急工单（调查无法投递通知的根因）

注意基于症状的告警框架：告警针对用户可见症状（通知未投递、滞后增长意味着用户等待太久）而不是基础设施指标（CPU、内存）。

**Q3.** 一次用户登录请求的分布式追踪显示以下 spans：API Gateway（10ms）、认证服务（380ms）、认证服务下无子 span。认证服务对该 trace ID 的日志条目为：`INFO validate_jwt (5ms)`、`INFO fetch_user_from_db (370ms)`、`INFO cache_user_profile (2ms)`。利用第 3 章的侦探纪律，你的诊断是什么，下一步会调查什么？

提示

回想侦探方法：从证据形成假设，然后设计测试在行动前证实或证伪它。

**答案：** 已收集证据：登录请求总耗时 390ms，其中 380ms 在认证服务。认证服务内部，JWT 验证很快（5ms），用户资料缓存很快（2ms），但数据库获取很慢（370ms）——几乎占了观察到的全部延迟。

**假设：** 获取用户资料的数据库查询是瓶颈。最可能原因：(a) 查询查找列（用户 ID 或邮箱）缺少索引，(b) 数据库高负载导致查询排队，(c) 数据库连接池饱和，认证服务在执行查询前等待连接。

**下一步调查：**

1. 检查认证服务数据库连接池指标——池利用率是否高？
2. 检查该时段数据库慢查询日志——是这条特定查询慢，还是数据库整体慢？
3. 检查 `SELECT * FROM users WHERE email = ?` 的 `EXPLAIN` 输出——是否使用索引？
4. 检查这是孤立事件（一次慢追踪）还是系统性（该时段所有认证服务 DB 查询都慢）。

这就是应用的侦探纪律：证据足够具体以形成假设，假设产生可证伪的测试，只需一个测试结果就考虑下一个假设。这比随机在系统中找错快得多。
