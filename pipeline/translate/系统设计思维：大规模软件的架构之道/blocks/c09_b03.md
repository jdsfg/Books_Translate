### 9.3 第 4 层 vs 第 7 层——两种负载均衡

负载均衡器工作在网络协议栈的不同层，层数决定它们能用什么信息做路由决策。

理解这些层前先简单介绍：OSI 模型（Open Systems Interconnection model）把网络通信描述为七层栈。与我们相关的是：

**第 4 层——传输层：** TCP 和 UDP 所在层。在第 4 层，负载均衡器能看到源 IP、目的 IP、源端口、目的端口和传输协议（TCP 或 UDP）。它看不到传输数据的内容。

**第 7 层——应用层：** HTTP、HTTPS、SMTP 等应用协议所在层。在第 7 层，负载均衡器能看到 HTTP 请求的实际内容：URL 路径、HTTP 头、cookie 和请求体。


#### 第 4 层负载均衡

第 4 层（L4）负载均衡器基于网络层信息（IP 地址和 TCP 端口）路由请求。它不看 HTTP 内容。它的工作本质上是 IP 数据包（packet）转发——因为只需极少检查，所以极快。

**如何工作：** TCP 连接到达 L4 负载均衡器的 IP。负载均衡器选择一台后端服务器，把 TCP 流转发给它。后端服务器终止 TCP 连接并读取 HTTP 请求。

**优点：** 非常快（不解析 payload）。低延迟。处理任意 TCP 或 UDP 协议，不只 HTTP。

**局限：** 不能做基于内容的路由决策。如果你想把 `/api/video` 路由到视频处理服务器、`/api/search` 路由到搜索服务器，L4 负载均衡器帮不上忙——它不读 URL。


#### 第 7 层负载均衡

第 7 层（L7）负载均衡器读取请求的应用层内容——具体来说，是 HTTP 请求，包括 URL、头，有时还有 body。这实现了**基于内容的路由（content-based routing）**。

**基于内容的路由示例：**

* 把 `/api/video/upload` 路由到视频上传服务器集群（使用大内存实例处理大 payload）
* 把 `/api/search` 路由到搜索服务器集群（运行 Elasticsearch）
* 把带 `Beta-User: true` 头的请求路由到 beta 应用服务器集群
* 把来自移动应用（`User-Agent: SocialSnapMobile`）的请求路由到为移动 API 响应优化的服务器集群
* 按地理区域路由（通过 IP 地理位置）

**SSL 终止：** L7 负载均衡器通常在自身终止 TLS。浏览器与负载均衡器建立加密 HTTPS 连接。负载均衡器解密请求、检查，然后（通常不加密）转发到内部网络的后端服务器。这把计算昂贵的 TLS 处理从应用服务器卸载到负载均衡器。

**优点：** 基于内容的路由、SSL 终止、头操作、限流（9.7 节会讲）。

**代价：** L7 比 L4 慢（必须解析完整 HTTP 请求），运维更贵。它们还是协议相关的——HTTP L7 负载均衡器没有 gRPC 专门支持就不能路由 gRPC 流量。

对大多数 Web 应用，L7 负载均衡是正确选择：基于内容的路由和 SSL 终止收益超过性能开销。
