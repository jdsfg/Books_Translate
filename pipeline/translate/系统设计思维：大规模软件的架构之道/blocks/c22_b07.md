#### Feed 读取流程

1. **用户 F 请求 feed：** `GET /feed` 到 Feed Service。
2. **获取预计算 timeline：** `ZREVRANGEBYSCORE user:F:timeline +inf -inf LIMIT 0 200` —— 从 Redis 获取 F 的 timeline 中前 200 个帖子 ID。很快（Redis 中 O(log N + 200)，约 2ms）。
3. **识别名人关注：** 从 F 的关注列表中找出关注者数 ≥ 1,000,000 的账号，获取他们最近帖子：`SELECT post_id FROM posts WHERE author_id IN (...celebrities...) ORDER BY created_at DESC LIMIT 20`。
4. **合并候选：** 把 200 个 timeline 帖子 ID 和名人帖子合并成约 220 个候选集合。
5. **获取帖子详情：** 对候选集合中每个帖子 ID，从帖子服务获取帖子内容。先走缓存（第 7 章 cache-aside）：大多数帖子在 Redis 中有 24 小时 TTL 缓存。
6. **用用户专属信号重新排序：** 对每个候选帖子，用 F 与作者的亲密度、帖子当前质量指标、F 最近行为信号计算最终排序分。按最终分数排序。
7. **返回前 20 条帖子** 给 F 的客户端。

该流程端到端延迟：Redis timeline 读取（2ms）+ 名人帖子获取（10ms，并行）+ 帖子内容缓存获取（5ms，并行批量）+ 重新排序（5ms）+ 序列化（2ms）≈ **约 24ms** 总计。远低于 200ms p99 要求。


#### Fanout Service 架构

Fanout Service 是一个 Kafka 消费者，处理 `post_created` 事件——与第 8 章为 SocialSnap 通知队列引入的基于 Kafka 的异步解耦模式相同，现在应用于 feed 投递规模。它是扇出架构的心脏：

* **水平可扩展：** 多个 Fanout Service 工作节点并行消费 Kafka topic。如果某帖子有 50 万（500,000）关注者，工作被分散到多个工作节点。10 个工作节点各处理 5 万（50,000）次关注者更新。
* **限速：** 50 万关注者帖子的扇出无法瞬间完成。Fanout Service 以受控速率处理扇出，把 Redis 写入负载分散到数秒而非数毫秒。这防止扇出不受控地飙升 Redis 写入吞吐。
* **异步：** `POST /posts` 处理器在写入数据库并发布 Kafka 事件后立即返回。扇出在后台发生。这意味着关注者可能不会立刻看到帖子——但新鲜度 SLO（“99% 关注者在 60 秒内看到帖子”）被满足，因为 Fanout Service 在数秒内追上典型关注者数。

对 50 万（500,000）关注者用户，以每个 Fanout 工作节点每秒 1 万（10,000）次 Redis 写入，单个工作节点 50 秒完成扇出——刚好在 60 秒新鲜度 SLO 内。10 个工作节点并行：5 秒。Fanout 工作节点数量是新鲜度延迟的直接杠杆。
