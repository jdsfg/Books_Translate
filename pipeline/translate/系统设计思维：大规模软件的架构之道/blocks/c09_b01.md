七章以来，我们一直在讨论数据中心内部发生的事：存储数据的数据库、快速服务数据的缓存、把生产者与消费者解耦的消息队列。但有一个问题我们一直默默回避了：Singapore 用户浏览器发出的请求，到底是如何到达 SocialSnap 应用服务器的？

答案涉及多层基础设施，每层承担特定职责。理解这些层不只是学术意义——网络层的决定直接决定系统如何扩展、如何失败，以及你能构建什么类型的应用。

让我们从头到尾追踪一个请求。


### 9.1 请求的旅程

用户在浏览器输入 `www.socialsnap.com` 并按回车。会发生什么？

**第 1 步：DNS 解析。** 浏览器询问 DNS（Domain Name System）服务器：“`www.socialsnap.com` 的 IP 地址是什么？” DNS 是互联网的电话簿——把人类可读的域名翻译成机器可读的 IP 地址。DNS 服务器返回一个或多个 IP 地址。

**第 2 步：TCP 连接。** 浏览器与其中一个 IP 地址建立 TCP 连接。TCP（Transmission Control Protocol）是面向连接的协议：在发送任何数据前，它执行三次握手（SYN → SYN-ACK → ACK）以建立可靠连接。

**第 3 步：TLS 握手。** 对 HTTPS 连接，额外的 TLS（Transport Layer Security）握手协商加密密钥。这增加 1–2 次往返延迟。

**第 4 步：HTTP 请求。** 浏览器通过加密连接发送 HTTP GET 请求。

**第 5 步：路由到应用。** 浏览器连接的 IP 地址不一定是单个应用服务器。它可能是负载均衡器的 IP——一个中间件，把请求转发给多个应用服务器之一。

**第 6 步：应用处理。** 应用服务器处理请求（查询缓存、数据库等）。

**第 7 步：响应。** 响应沿同一条链路返回。

在小型系统中，第 1–4 步由互联网基础设施（ISP、DNS 服务器）处理，第 5 步微不足道（只有一台服务器）。但在 SocialSnap 的规模下，第 5 步才是有趣的系统设计决策所在。


### 9.2 负载均衡器——分配工作

假设 SocialSnap 运行 5 台应用服务器。哪个服务器应该处理 incoming 请求？答案不能是“总是 server 1”——server 1 会被压垮，而 servers 2–5 闲置。你需要一个组件，智能地把请求分发给可用服务器。

这个组件就是**负载均衡器（load balancer）**。


#### 定义：负载均衡器

**负载均衡器** 是一个接收 incoming 请求并将其分发给一组后端服务器的组件，目标是最大化吞吐、最小化延迟，并避免压垮任何单台服务器。

通俗语言：负载均衡器是服务器农场门口的交警。每个请求先到负载均衡器。负载均衡器决定哪个服务器处理它，然后把请求转发过去。
