#### 一个简单系统的组成部分

我们来具体化。当你的朋友在浏览器中输入 `https://socialsnap.com/posts/42` 并按下回车时，一连串事件就开始了：

1. 浏览器向 DNS 服务器发问：“socialsnap.com 的 IP 地址是多少？”
2. DNS 服务器回答：“是 203.0.113.7。”
3. 浏览器向 203.0.113.7 发送 HTTP 请求：“给我第 42 号文章。”
4. 203.0.113.7 上的 Web 服务器收到请求，调用你的 `get_post(42)` 函数。
5. 函数向数据库查询第 42 号文章。
6. 数据库返回文章数据。
7. Web 服务器把它格式化成 HTML 并发送回去。
8. 浏览器渲染 HTML。

你的朋友看到了一篇博客文章。但背后有八个不同的系统参与了——浏览器、DNS 基础设施、网络、Web 服务器、应用代码、数据库、HTTP 协议，以及 HTML 渲染引擎。其中大多数不受你控制。但你要对中间那部分负责。

这就是系统：一条组件链，每个只做自己那一小部分，却共同完成一个目标。

#### SocialSnap v0：一个能放进笔记本电脑的系统

在本书中，我们会跟随一个贯穿始终的例子：**SocialSnap**，一个从极小开始成长的社交平台。现在，在 v0 版本，它已经是系统能简单到的样子：

* 一个 Python/Flask 应用
* 一台运行在同一台机器上的 PostgreSQL 数据库
* 托管在一台笔记本电脑（或廉价 VPS）上
* 三个用户：你和两个朋友

    [ Browser ] ──HTTP──> [ Flask App + PostgreSQL ] (one machine)

这是一个完全有效的系统。它完成了目标。它有组件（浏览器、应用、数据库），通过明确边界（你的机器）进行交互（HTTP、SQL）。它无法承受一百万用户，这不意味着它错了——只意味着它与一百万用户需要的不是同一个系统。

从 SocialSnap v0 到能服务一百万用户的架构，这一旅程就是本书要讲的故事。

### 1.2 为什么规模改变一切

这是一个诱人的谎言：扩展只是把同样的东西做得更大。

如果一台服务器能处理 10 个用户，那么 100 台服务器就能处理 1,000 个用户。对吗？

并非如此。规模不只是放大问题——它还会改变问题的性质。在小规模下运行完美的东西，在大规模下会以全新的方式崩溃；而那些在小规模下看起来很糟的主意，有时在大规模下却变得必要。我们来看看为什么。
