#### 概念检测

**Q1.** 为什么 URL 短链服务被描述为“读多写少”，这一属性如何影响架构？

**答案：** URL 短链服务约每创建一个 URL 有 100 次重定向——100:1 的读写比。“读多写少”意味着主导操作是读取已有数据（查找短码找长 URL）而非写入新数据。这以几种关键方式影响架构：(1) 缓存极有价值——即使只缓存最热的 1% URL，也能处理 60-70% 流量而不访问数据库，大幅降低读负载。(2) 读副本很自然——可添加读副本，把所有读流量导过去，主库只负责写。(3) 重定向路径（读）的延迟要求（p99 100ms）比创建路径（写）严格得多，因此优化预算花在读上。(4) 写吞吐（1,157/秒）足够低，单个数据库主库可轻松处理，而读吞吐（116,000/秒）没有缓存会压垮单库。

**Q2.** 解释 URL 短链服务中 301 和 302 HTTP 重定向状态码的权衡。

**答案：** 301（Moved Permanently）指示浏览器缓存重定向：首次访问后，浏览器直接去长 URL，不再联系短链服务。优点：重复访问零服务器负载、重复访问延迟更低。缺点：分析失效（浏览器不调用服务，因此不计点击），且浏览器缓存后重定向无法更改或禁用。302（Found）指示浏览器不缓存：每次访问都联系短链服务。优点：分析正常工作，重定向可随时更改或禁用。缺点：服务器负载略高，重复访问延迟略高。对有分析需求的短链服务，302 正确。我们通过服务端缓存（Redis）缓解服务器负载担忧——浏览器仍联系服务，但服务从缓存约 5ms 响应，而不是命中数据库。

**Q3.** 什么是 base-62（BASE）编码，为什么短码用它而不是 base-16（hex）？

**答案：** base-62（BASE）编码用 62 个可能字符表示数字：数字 0–9（10 个）、小写字母 a–z（26 个）、大写字母 A–Z（26 个）。用于短码因为它在相同字符长度内最大化可能码数量。7 个字符时：base-16 给出 16^7 ≈ 2.68 亿（268 million）个码；base-62 给出 62^7 ≈ 3.5 万亿个码——在相同 7 字符空间内多出约 13,000 倍。每字符更多码意味着在码变长前更短的码就够用了。base-64 会更多，但它包含 `+` 和 `/`，在 URL 中有特殊含义，需要 percent-encoding，使短 URL 外观变复杂。base-62 是实用甜点：高码密度且仅 URL 安全字符。
