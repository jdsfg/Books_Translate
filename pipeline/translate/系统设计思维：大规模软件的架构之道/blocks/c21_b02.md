#### 短轮询

最简单方法：客户端每秒向服务器发一次请求：“有新消息吗？” 如果有，服务器返回；如果没有，返回空响应。

短轮询概念上 trivial——使用普通 HTTP 请求，无需特殊基础设施。但缺点严重：

* **浪费带宽：** 如果用户 5 分钟没收到消息，客户端已发 300 个请求并收到 300 个空响应。
* **延迟：** 1 秒轮询间隔下，消息最迟 1 秒才到。100ms 轮询则带宽消耗乘以 10。
* **服务器负载：** 50 万（500,000）并发用户每秒轮询 = 聊天服务器 50 万 RPS，大多数返回空响应。对零用户价值而言这是巨大负载。

短轮询仅适用于更新频率极低的场景（例如每分钟查一次 job 状态）。对 200ms 延迟要求的实时聊天，不可行。


#### 长轮询

长轮询通过把请求保持打开直到消息到达来改进短轮询：

1. 客户端发送：“有给我的新消息吗？”
2. 服务器保持连接打开（不立即响应）
3. 消息到达时，服务器用它响应
4. 客户端立即再发一次请求（循环）

这消除了大部分浪费带宽：服务器只在有话要说时才响应。但它维持每个客户端一个打开 HTTP 连接——50 万并发用户意味着服务器同时保持 50 万个打开连接。HTTP/1.1 连接加打开线程开销高（每个线程通常 1MB 栈内存）。50 万线程 × 1MB = 500 GB 内存仅用于连接处理。

长轮询对小型系统或不值得上 WebSocket 基础设施的系统是合理方法，但它不能优雅扩展。


#### WebSockets——实时聊天的正确答案

**WebSockets** 提供客户端与服务器之间持久、双向、全双工连接。初始 HTTP 握手把连接升级到 WebSocket 协议后，双方可在任何时候发消息，无需 HTTP 请求/响应帧开销。

WebSocket 模型：

1. 客户端打开到 `wss://chat.socialsnap.com/ws` 的 WebSocket 连接
2. 服务器无限期维持该连接
3. 用户 A 给用户 B 发消息时，服务器立即通过用户 B 的 WebSocket 连接推送消息
4. 客户端收到消息并显示，无需发起任何请求

WebSocket 连接是有状态的：服务器知道哪个用户在哪个连接上。连接本身持有用户身份上下文。这很优雅，但也带来我们之前提到的扩展挑战——服务器不能是无状态的。


#### 定义：WebSocket

**WebSocket** 是一种网络协议，通过单一 TCP 连接在客户端与服务器之间提供持久、全双工通信通道。与 HTTP 不同——HTTP 中客户端必须发起每个请求——WebSocket 允许连接建立后任何一方随时发送数据。

plain 语言：WebSocket 是电话线。HTTP 是一系列单独电话呼叫。WebSocket 让线路保持开放，任何一方有话就说。
