**答案：**

**端到端架构：**

**第 1 步：记录 like 事件** Bob 赞了 Alice 的帖子。应用服务器：

* 把 like 插入 PostgreSQL（`likes` 表）
* 发布 `post.liked` 事件到消息队列（第 8 章）
* 立即向 Bob 返回 HTTP 200

**第 2 步：通知服务消费事件** 通知服务（第 8 章的消息队列消费者）从队列读取 `post.liked` 事件。它：

* 在数据库中创建通知记录
* 在 Redis 中自增 Alice 的未读通知计数：`INCR user:1:notification_count`
* 从 Redis 查找 Alice 的活动 WebSocket 连接：`GET user:1:ws_connections`

**第 3 步：通过 WebSocket 推送** 如果 Alice 在线（在 Redis 注册了活动 WebSocket 连接）：


    { "type": "notification_count_update", "count": 7 }


该消息通过 Alice 的 WebSocket 连接推送。Alice 的浏览器毫秒级收到并更新角标。

如果 Alice 离线：不推送。等她下次加载页面时，获取通知计数的 HTTP 请求从 Redis 读取已更新的计数器——已经是最新值。

**WebSocket 连接管理：** Alice 登录时，她的浏览器与通知服务器建立 WebSocket 连接。服务器注册：`SADD user:1:ws_connections "server3:conn_4821"`。断开时移除注册。多个标签页或设备会产生多个连接条目。

**WebSocket 流量的限流：** HTTP 层限流（API 网关处的令牌桶）适用于 WebSocket 升级请求——在连接建立之前。一旦连接建立，WebSocket 流量是服务器向客户端推送，而不是客户端猛烈请求服务器。相关限流在服务端：如果通知服务每秒收到 10,000 条 `post.liked` 事件，它不应向同一用户推送 10,000 条 WebSocket 消息/秒（这是名人的病态场景）。通知服务可以合并消息：发送“你有 N 条新通知”，而不是 N 次单独推送。
