* Kafka topic `url_clicks` 接收点击事件（已有）
* 消费者 1（已有）：批量事件写入数据仓库（用于历史查询，5 分钟延迟）
* 消费者 2（新增）：把事件写入 Redis sorted set 或时序数据库（如 InfluxDB 或 Redis TimeSeries），滚动 5 分钟窗口

**实时仪表盘：** `url_clicks` Kafka 消费者（消费者 2）按 `short_code` 为键把事件写入 Redis sorted set，score 为时间戳，member 为点击事件。要获取最近 5 分钟点击：`ZRANGEBYSCORE url:abc1234:clicks (NOW-300) NOW`。返回该时间窗口内所有带时间戳的点击。

实时国家聚合：维护 Redis hash `url:abc1234:countries:5min`，用 `HINCRBY` 累加各国数量。每个国家码是 hash 字段，值为计数。该 hash TTL 5 分钟；每 5 分钟重置。

**一致性模型：** 实时分析（5 分钟窗口）使用最终一致性——事件发生后数秒内出现即可。历史分析（30 天查询）也使用最终一致性——3 个月前的点击不会变，仓库以数分钟延迟累积事件。两条路径都不需要强一致性，因为分析数据本质上是时间性和累加的——漏掉一个点击是可接受的精度损失。

这是第 8 章 CQRS 模式在分析上的应用：写路径（Kafka）与读路径（历史查询走数据仓库、实时查询走 Redis）分离，各自为特定查询模式优化。

**Q3.** SocialSnap 营销团队想创建自定义短链（例如 `ssnap.io/summer-sale`），除自动生成的码外。用户可声明最长 20 字符的任意可用自定义别名。这会如何改变码生成和存储系统设计？引入了什么新攻击向量，如何缓解？

提示

思考现在谁控制命名空间，以及如果用户尝试声明 “login”、“api” 或 “admin” 作为自定义别名会发生什么。

**答案：** 自定义别名打破了键空间由系统控制的假设。需要三处改变：

1. **存储：** 自定义别名进入与自动生成码相同的 `url_mappings` 表，用 `type` 列区分。不需要 schema 变更，但短码列的唯一约束必须对两者都成立。
2. **验证：** 接受自定义别名前，系统必须检查：(a) 别名未被占用，(b) 别名不与保留系统路径冲突（例如 `/api（API）`、`/admin`、`/login`、`/healthz`）。维护显式保留词黑名单，每次创建请求都检查。
3. **滥用向量——域名抢注：** 恶意行为者可以声明 `ssnap.io/google`、`ssnap.io/apple` 等高价值名称，然后把它们重定向到钓鱼页。缓解：自定义别名功能必须在已验证账户后才可用；按账户限流自定义别名创建；允许商标持有者通过滥用流程举报并收回被抢注别名。这关联第 11 章限流模式和第 19 章认证模型。
