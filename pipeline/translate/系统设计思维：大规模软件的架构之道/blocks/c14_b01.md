第 13 章画了一条硬线：每个微服务拥有自己的数据库，没有服务能越过这条线。用户服务拥有用户数据。支付服务拥有支付数据。帖子服务拥有帖子数据。这条线给了每个服务自主和隔离。

但数据不尊重架构师画的线。业务操作需要来自多个服务的数据。用户查看账单历史：需要用户资料（用户服务）和支付记录（支付服务）两者。有人点赞帖子触发通知：通知服务需要知道谁点了赞（来自帖子服务）和收件人邮箱（来自用户服务）。数据被分开了；需要它们的业务逻辑却没有。

在这项挑战之下，还有一个自第 7 章缓存陈旧性问题以来一直悄然酝酿的更深层次问题：在任何数据存储在多处（副本、缓存、分片数据库、独立服务数据库）的系统中，不同副本对某物的当前值总有产生分歧的可能。分布式系统如何处理这种分歧？它能提供什么保证？要提供更强保证，又必须牺牲什么？

这些问题处于计算机科学家所谓**分布式一致性（distributed consistency）**的核心，理解它们将改变你对大型系统中数据的看法。


### 14.1 根本问题——两个副本，两个真相

从最简单版本开始。

你有一个数据库，里面一条记录：计数器初始为 0。你把数据库复制到两个节点：Node A 和 Node B。两个节点初始计数器都是 0。

现在两个事件同时发生：

* 服务器 1 向 Node A 发送“递增计数器”的写操作。
* 服务器 2 从 Node B 读取计数器。

Node A 收到写并把计数器更新为 1。但 Node B 还没收到这个更新——复制是异步的。服务器 2 从 Node B 读到 0。

服务器 2 该如何理解？它读到 0。这是真正的当前值吗？还是真正当前值已经是 1，只是 Node B 落后了？

答案取决于你的**一致性模型（consistency model）**——系统对读操作相对于已完成写操作可以返回什么值的保证。


#### 定义：一致性模型

**一致性模型（consistency model）** 是分布式数据存储与其应用之间的契约，说明读操作相对于先前写操作可以返回什么值。越强的一致性模型越容易推理，但实现越慢越难。越弱的一致性模型越快、越可用，但要求应用容忍并处理陈旧或不一致的数据。

plain 语言：一致性模型回答这个问题：“我现在写一个值，什么时候读能返回这个值？”
