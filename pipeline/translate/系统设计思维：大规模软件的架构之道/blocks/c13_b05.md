#### 同步通信——HTTP 与 gRPC

在**同步通信**中，服务 A 向服务 B 发出请求并等待响应后才能继续。这模拟了单体中熟悉的函数调用模型，只是通过网络。

两种主流协议是 HTTP/REST（服务 A 向服务 B 的 URL 发送 HTTP 请求）和 gRPC（服务 A 调用由共享契约定义生成的函数，用 Protocol Buffers 序列化参数并通过 HTTP/2 发送）。

gRPC 通常更快（Protocol Buffers 比 JSON 更紧凑），提供强契约（`.proto` 文件定义接口，客户端和服务器生成代码确保一致），并支持双向流。HTTP/REST 更简单、支持更广泛（任何 HTTP 客户端都能调用 REST API，无需特殊工具）。

同步通信的关键特性：**服务 A 的可用性依赖于服务 B 的可用性。** 如果服务 B 宕机，服务 A 的请求失败。如果服务 B 慢，服务 A 的请求也慢。这在服务间造成**时间耦合（temporal coupling）**。

想象一条链：服务 A 调用服务 B，B 调用服务 C，C 调用服务 D。如果每个服务独立可用概率为 99%，四个服务同时可用的概率是 `0.99 × 0.99 × 0.99 × 0.99 ≈ 96%`。这就是**级联故障（cascading failure）**问题：同步链中服务越多，整体可用性越低。


#### 异步通信——消息队列

在**异步通信**中，服务 A 向队列发消息（回想第 8 章的消息队列）。服务 B 从队列读取并独立处理。服务 A 不等待服务 B 完成。

异步通信的关键特性：**服务 A 的可用性不依赖于服务 B 的可用性。** 如果服务 B 宕机，消息在队列中堆积，等 B 恢复后处理。服务 A 继续运行。

tradeoff（权衡）：异步通信意味着服务 A 不能立即得到服务 B 的结果。它是发后即忘。对结果不需要立即可用的操作（发送通知、生成报告、后台处理支付）没问题，但对需要立即响应的操作不合适（查询用户资料以显示在屏幕上）。
