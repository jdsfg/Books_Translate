每个已登录用户需要定期向服务器发送“心跳（heartbeat）”以保持在线标记。想想心跳应该多频繁触发、总写入量是多少、哪种存储类型能在自动过期前提下处理这个写入量。第 7 章的 TTL 概念直接适用。

**答案：**

**在线状态数据模型：**

每个用户的在线状态是一个带 TTL 的 Redis key：


    Key:   presence:{user_id}
    Value: {last_seen: timestamp, status: "online"}
    TTL:   5 minutes (300 seconds)


如果 presence key 存在，用户就是“在线”的。5 分钟无活动后 key 自动过期——不需要后台清理任务。Redis 原生 key 过期精确处理这一点。

**写入量：**

为了让在线状态生效，客户端必须周期性发送心跳来刷新 TTL。30 秒心跳间隔可确保只要用户活跃，5 分钟 TTL 的在线状态得以维持：

* 100,000 并发在线用户 × 每 30 秒 1 次心跳 = 约 3,333 次写入/秒

每次写入是 `SET presence:{user_id} {payload} EX 300`——一条 Redis 命令，亚毫秒级。单个 Redis 节点可轻松处理每秒 100,000+ 次写入。这是键值存储（第 6 章 6.3 节）的合适工作负载。

**API 设计：**

两个端点：


    POST /api/presence/heartbeat
      → 需要认证。刷新 presence:{user_id} 的 TTL。返回 200。
      → 活跃客户端每 30 秒调用一次。

    GET /api/users/{user_id}/presence
      → 返回 { "online": true/false, "last_seen": "..." }
      → 检查 Redis：EXISTS presence:{user_id}


**客户端更新协议：**

如果客户端已经打开 WebSocket 连接（用于通知，见 9.6 节），心跳可以作为 WebSocket 消息发送——避免每个心跳都走完整 HTTP 请求-响应周期。WebSocket 服务器处理 `{ "type": "heartbeat" }` 消息，刷新 Redis TTL。这复用了现有 WebSocket 基础设施，而不是新增 HTTP 端点。

如果客户端没有 WebSocket，每 30 秒发一次 HTTP POST 也完全可接受。

**为 feed 渲染查询在线状态：**

渲染 feed 头像时，客户端可以批量查询所有可见用户的在线状态：`MGET presence:42 presence:107 presence:88 ...`——一次 Redis 多 key 读取。响应指出哪些 user ID 有 presence key（在线），哪些没有。
