#### 隔离级别——ACID 的旋钮

完全隔离（好像事务一个接一个运行）非常昂贵——它要求在行被处理时锁定行。大多数数据库提供**隔离级别**，用正确性换性能：

| 级别 | 脏读 | 不可重复读 | 幻读 | 用例 |
|---|---|---|---|---|
| Read Uncommitted（读未提交） | 可能 | 可能 | 可能 | 很少有用 |
| Read Committed（读已提交） | 防止 | 可能 | 可能 | 大多数 Web 应用（PostgreSQL 默认） |
| Repeatable Read（可重复读） | 防止 | 防止 | 可能 | 事务内的金融读取 |
| Serializable（可串行化） | 防止 | 防止 | 防止 | 最高正确性要求 |

大多数 Web 应用使用 **Read Committed**——它防止读到另一个事务未提交的更改，同时保持良好并发。只在正确性要求时才用 Serializable，因为它会显著降低吞吐。


#### 常见误解

许多开发者认为“我在用关系型数据库，所以我的数据总是一致的”。这错在两个原因：

1. **ACID 一致性 ≠ CAP 一致性。** ACID 一致性意味着单个数据库内没有约束违反。CAP 一致性意味着所有分布式副本达成一致。复制型关系数据库可以在每个副本上 ACID-一致，但跨副本不是线性一致的。
2. **隔离级别很重要。** 如果你在 Read Committed 隔离下运行（常见默认），仍可能遇到不可重复读——请求开始时读到的值在结束时可能已经改变。这是否重要取决于应用逻辑。
