### 16.5 舱壁模式

熔断器解决一个失败依赖的级联问题。但线程池耗尽本身呢？即使使用熔断器，如果依赖频繁失败，每个失败请求仍会消耗熔断器打开前的那段时间的线程。在此期间，线程耗尽是可能的。

**舱壁模式（Bulkhead pattern）** 通过划分资源来解决这个问题：系统某一部分失败不能耗尽另一部分所需的资源。


#### 定义：舱壁

**舱壁模式（bulkhead pattern）** 是一种通过给每类资源分配独立资源池，把关键资源与非关键资源隔离（partitioning，分区）的技术。某类失败耗尽一个池的资源不会影响其他池。

通俗语言：这意味着不是用一个共享资源桶给所有东西使用，而是把桶分成独立隔间——一个失控的消费者不能抽干整个桶。

名字来自船舶建筑：船体被分成多个水密隔间（舱壁）。如果一个隔间进水，其他隔间仍防水，船继续漂浮。没有舱壁，船体任何破损都会让整艘船沉没。

在软件系统中，最常见的应用是线程池隔离。不是为所有请求使用一个共享线程池，而是为不同类别维护独立线程池：

* **关键路径线程池（200 线程）：** 用于应用核心请求——浏览 feed、发帖、登录。这些必须始终有线程可用。
* **社交功能线程池（50 线程）：** 用于非关键功能——热门话题、推荐用户。它们失败不影响核心功能。
* **外部 API 线程池（20 线程）：** 用于调用第三方服务——广告网络、分析、支付处理器。隔离使得慢速第三方服务不会影响内部请求处理。

如果外部 API 线程池填满（支付处理器慢），外部 API 请求开始失败。但关键路径线程池不受影响——用户仍可以浏览 feed、发帖、登录。失败被限制在外部 API 池中。

对 SocialSnap 的 Redis 失败：有了舱壁隔离，依赖 Redis 的会话验证可以有自己独立的线程池。Redis 失败时该池耗尽，但不需要会话验证的请求（未登录浏览公开帖子、静态页面）使用关键路径池，不受影响。


### 16.6 优雅降级——失败也要优雅

熔断器和舱壁控制失败。优雅降级决定用户在组件失败时的体验。
