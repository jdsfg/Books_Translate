案例研究章节展示了某一时刻的系统：白板上的 URL 短链服务设计；自成一体的限流模块；经过仔细推理的新闻 feed 架构。但真实系统从不是一次性设计出来的。它们是在压力下、信息不完整、由自身也在不断变化的团队，一次一个决策地成长起来的。

第 27 章展示它们如何到达这里。

为此，我们将回顾 SocialSnap 从最开始的完整旅程——第 1 章笔记本电脑上的一个 Python 函数——到第 26 章分布式基础设施的每一次架构拐点。重新审视 SocialSnap 团队做出的每个决策，并以后见之明来看。

目标不是庆祝他们的好决策或嘲笑早期决策。而是理解决策在团队当时所知信息下为何正确，以及哪些信号表明是时候改变。

### 27.1 SocialSnap 完整演进——完整回顾

让我们按顺序追踪 SocialSnap 的每个架构版本。


#### v0 —— 第 1 章：笔记本电脑上的一个函数（第 1–4 周）

**它是什么：** 开发者笔记本电脑上运行的一个 Python Flask 应用。单个端点。没有数据库——数据存在内存 Python 字典里。服务器重启后所有数据丢失。

**为什么正确：** 创始人需要测试是否有人使用产品，而非产品能否扩展。此阶段正确的工程问题不是“我们如何支持 100 万用户？”而是“我们有用户吗？”一个没用户的可扩展系统是在浪费时间和金钱。

**权衡：** 零持久化、零可用性、零扩展性。零用户时可接受。

**变革信号：** 用户开始问为什么第二天回来帖子就消失了。


#### v1 —— 第 5 章：添加数据库（第 1–3 个月）

**它是什么：** 栈中加入 PostgreSQL 数据库。用户、帖子、关注关系按关系模型存储。ACID 事务。数据现在跨重启持久化。

**关键决策：**

* Schema：`users(id, email, username, created_at)` 和 `posts(id, user_id, content, created_at)`，带外键关系
* 部署在与应用同一台虚拟机上
* 用环境变量存储数据库凭证（一个早期安全决策，养成好习惯）

**为什么正确：** PostgreSQL 成熟、可靠、对有关系的数据非常出色。1000 用户时，一台索引良好的 PostgreSQL 实例有巨大余量。关系型数据库的开销在此规模可忽略；收益（数据完整性、查询灵活、ACID 保证）显著。

**技术债务：** 数据库和应用在同一服务器意味着它们竞争资源。应用 CPU 繁忙时，数据库查询变慢。

**变革信号：** PostgreSQL 和应用竞争 CPU 导致高峰使用期间偶尔页面加载变慢。数据库需要自己的机器。
