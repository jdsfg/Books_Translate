#### Redis

Redis（Remote Dictionary Server）是功能更丰富的内存数据结构存储服务器。它支持字符串、列表、集合、有序集合、哈希、位图、HyperLogLog、地理空间索引等。对这些类型的操作是原子的——Redis 在核心中是单线程处理命令的，因此数据结构操作没有竞态条件。

**有序集合支持：** 排行榜、限流（score = 时间戳）、热门标签（score = 计数）。

**列表支持：** 队列、活动 Feed（从头部 push，从头部/尾部读取）。

**原子计数器操作：** `INCR counter_key` 原子递增计数器，无竞态条件。非常适合浏览数、点赞数、session ID。

**持久化选项：** Redis 支持两种持久化模式——RDB 快照（定期完整快照到磁盘）和 AOF（Append-Only File，记录每条写入命令）。这使 Redis 在重启后能不丢失所有缓存数据，尽管有一定恢复时间。

**复制：** Redis 支持主-从/副本复制（primary-replica replication），提供读扩展和故障转移能力。

对 SocialSnap，Redis 是正确选择。我们不仅需要简单字符串缓存——还要点赞计数器、热门帖子有序集合，以及最终会话存储（第 11 章）。Redis 原生处理所有这些。

回想第 6 章应用问题中，Redis 的地理空间索引被用于司机位置问题。那是 Redis 作为专门数据库而非只是缓存。Redis 足够多功能，可同时充当两者。


### 7.7 SocialSnap v2——加入缓存层

让我们看看缓存如何在实践中改变 SocialSnap。

SocialSnap v1（第 5 章）只有一台 PostgreSQL 数据库。最常见的查询是：

1. 加载用户资料（按 `user_id`）——占所有请求的 70%
2. 加载用户最近帖子（按 `user_id`）——占 20%
3. 所有其他查询（关注、搜索等）——占 10%

流量达到 8,000 请求/秒时，数据库每秒约收到 5,600 次资料查找和 1,600 次帖子查找。单台 PostgreSQL 实例为此挣扎。

SocialSnap v2 架构把 Redis 加为分布式缓存：


    User Request
        ↓
    Application Server
        ↓ (check cache first)
    Redis Cache
        ↓ (on miss only)
    PostgreSQL Database


**资料缓存：**


    def get_user_profile(user_id):
        cache_key = f"user:{user_id}:profile"

        # Check cache
        cached = redis.get(cache_key)
        if cached:
            return json.loads(cached)  # Cache hit

        # Cache miss — query database
        profile = db.query("SELECT * FROM users WHERE id = %s", [user_id])

        # Store in cache with 5-minute TTL
        redis.setex(cache_key, 300, json.dumps(profile))

        return profile

    def update_user_profile(user_id, new_bio):
        # Write to database first
        db.execute("UPDATE users SET bio = %s WHERE id = %s", [new_bio, user_id])

        # Invalidate cache
        redis.delete(f"user:{user_id}:profile")


**影响：** 如果 95% 的资料请求是针对资料已缓存的用户（最流行用户和最近活跃用户），数据库现在每秒只收到 280 次资料查找而非 5,600 次——数据库负载降低 20 倍。
