#### 应用问题

**Q1.** SocialSnap 增加一个“@提及”功能：一篇帖子可以通过用户名提及最多 10 个其他用户（如“@alice 和 @bob”）。设计支持此功能所需的 schema 扩展，包括合适的索引。然后写一条 SQL 查询“给我看所有提及 Alice 的帖子，按最近排序”。

提示

把提及存成帖子表里的逗号分隔字符串（“@alice,@bob”）违反关系模型，也让查询很难。想想提及是什么实体，以及它如何与帖子和 users 关联。

**答案：**

**Schema 扩展：**

    CREATE TABLE mentions (
        post_id     INTEGER REFERENCES posts(id) ON DELETE CASCADE,
        user_id     INTEGER REFERENCES users(id) ON DELETE CASCADE,
        created_at  TIMESTAMP DEFAULT NOW(),
        PRIMARY KEY (post_id, user_id)
    );
    
    -- 快速找到提及某用户的所有帖子
    CREATE INDEX idx_mentions_user_id ON mentions(user_id);
    -- 快速找到某篇帖子提及的所有用户
    -- 已由 PRIMARY KEY (post_id, user_id) 覆盖

**为什么这样设计？** 提及是帖子与用户之间的关系——它应该有自己的表（称为“junction table”或“association table”）。把提及存成文本字段（“@alice,@bob”）会：

* 让“找所有提及 Alice 的帖子”需要全文本扫描（慢，O(n)）
* 违反引用完整性（如果被提及用户改了用户名怎么办？）
* 让删除用户变复杂（必须扫描所有帖子内容找用户名）

**查询——所有提及 Alice 的帖子，最新在前：**

    SELECT posts.id, posts.content, posts.created_at, author.username AS author
    FROM mentions
    JOIN posts ON mentions.post_id = posts.id
    JOIN users AS author ON posts.user_id = author.id
    WHERE mentions.user_id = (SELECT id FROM users WHERE username = 'alice')
    ORDER BY posts.created_at DESC
    LIMIT 20;

有了 `idx_mentions_user_id`，数据库先找到 Alice 的 `user_id`，再用索引只取 `mentions` 中 Alice 的行——O(log n + k)，k 是 Alice 被提及的次数。随后与 `posts` 和 `users` 的 join 很快，因为它们在主键上 join。

**Q2.**（联系第 3 章估算）SocialSnap 的 `likes` 表快速增长：每天 300 万新点赞。一年后 `likes` 表约有 1.1 billion（11 亿）行。查询“帖子 12345 有多少赞？”现在花 500ms。诊断可能原因并提出修复方案，同时考虑 tradeoff（权衡）。

提示

想想没有特殊数据结构时，“统计该帖子点赞数”需要做什么。然后考虑基于索引的方案和基于反规范化的方案及其 tradeoff（权衡）。

**答案：**

**诊断：** 查询是 `SELECT COUNT(*) FROM likes WHERE post_id = 12345`。在 1.1 billion（11 亿）行下，如果 `post_id` 没有索引（或索引已碎片化/低效），这就在做全表扫描或很大的索引扫描。即使有索引，统计所有匹配行也要读很多索引页——对有几百万赞的热门帖子尤其如此。

**方案 1：在 `post_id` 上添加/修复索引**

    CREATE INDEX idx_likes_post_id ON likes(post_id);
