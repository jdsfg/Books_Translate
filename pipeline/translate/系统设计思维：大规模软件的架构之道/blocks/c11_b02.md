### 11.2 根本原因——有状态的应用服务器

Alice 登录。轮询负载均衡器把她的登录请求路由到 Server A。Server A 在本地 `sessions` 字典中创建会话记录并设置 cookie。Alice 的浏览器现在有了会话 cookie。

Alice 点击“我的资料”。负载均衡器把该请求路由到 Server B（轮询序列中的下一个）。Server B 收到带 cookie `sess_a7b3c9d2e4f1` 的请求。Server B 在**它自己的** `sessions` 字典中查找 `sess_a7b3c9d2e4f1`。

这个 key 不在那里。Server B 没有处理登录——Server A 处理的。会话只存在于 Server A 的内存中。

Server B 认为这是未认证请求，返回错误或重定向到登录页。

Alice 实际上因为点击“我的资料”而被登出。

这就是有状态应用服务器问题。应用服务器维护着**状态**（session 数据），这些状态特定于每个服务器实例。当负载均衡器把请求分发给服务器时，状态是碎片化的——每台服务器只知道自己创建的会话。被路由到另一台服务器的请求找不到匹配的会话。


#### 定义：有状态 vs 无状态

**有状态（stateful）** 服务保存过去交互的信息（状态），这些信息影响它如何处理未来请求。同一个客户端请求由不同服务器处理会产生不同结果，因为服务器有不同的内部状态。

**无状态（stateless）** 服务不包含每个客户端的状态。每台服务器对世界有完全相同的视图。任何服务器都能处理任何客户端的任何请求，因为请求包含处理它所需的所有信息。同一个请求路由到任何服务器都产生相同结果。

通俗语言：无状态服务器是可互换的。像自动售货机——你用哪台都一样；按同一个按钮，它们都给你同样的可乐。有状态服务器像认识你的收银员——只有找那个了解你的人，你才能获得个性化体验。


#### 为什么无状态是水平扩展的先决条件

**关键洞察：** 你可以随意添加无状态服务器，无需协调。每台新服务器都能立即处理任何用户的任何请求。添加第十台无状态服务器就增加十分之一的容量。

使用有状态服务器，除非你确保每个客户端总是到达同一台服务器（粘性会话——马上讲到），或者找到服务器间共享状态的方法，否则增加服务器没有帮助。两种方案都有显著成本。

这就是**无状态要求（stateless imperative）** 作为水平扩展核心原则的原因：要扩展出去，应用服务器必须无状态。所有每个客户端的状态都必须存在于应用服务器外部——数据库、缓存或专用会话存储中。
