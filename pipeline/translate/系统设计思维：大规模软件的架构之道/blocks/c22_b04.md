#### 常见误解

关于名人问题的常见误解是“名人”是二元标签——用户要么要么是名人。现实中，关注者数量是连续的，扇出成本随关注者数平滑变化。50 万（500,000）关注者的用户产生的扇出写入是 10 万（100,000）关注者用户的 5 倍，而 10 万（100,000）关注者用户又是 1 万（10,000）关注者用户的 10 倍。

带阈值的混合策略是一种简化，实用之处在于它只需识别关注者最多的前 0.01% 用户做特殊处理。精确阈值不如拥有该机制重要。工程实现良好的系统可根据观察到的写入成本动态调整阈值。


### 22.3 Timeline 存储——预计算 Feed 存在哪里

对写时扇出路径，每个用户有一个 **timeline** —— 预计算的、属于其 feed 的帖子 ID 列表。


#### Timeline 里存什么？

Timeline 应存最少数据：仅帖子 ID（每个 8 字节）和排序分数（每个 4 字节）。完整帖子内容在 feed 渲染时从帖子数据库或缓存获取。这种分离有两个好处：

1. **Timeline 内存效率：** 存帖子 ID 而非帖子内容，可把 timeline 存储降低 100-1000 倍。为 5000 万（50 million）用户每人存 1000 个帖子 ID：50,000,000 × 1000 × 12 字节 = 600 GB——可放入大型 Redis 集群。
2. **Timeline 一致性：** 帖子更新（编辑）或删除时，只需在一个地方更新（帖子数据库）。timeline 存储的帖子 ID 始终指向当前版本。如果 timeline 存帖子内容，帖子更新后必须跨所有 timeline 更新每一份副本——不可管理的失效问题。


#### Timeline 作为有序列表

Timeline 是按排序分数排序的帖子 ID 有序列表。Redis sorted set 非常合适：`user:F:timeline` 是一个 sorted set，每个 member 是 `post_id`，score 是排序分数。Feed 获取即 `ZREVRANGEBYSCORE user:F:timeline +inf -inf LIMIT 0 20` —— 分数最高的 20 条帖子。

写时扇出：用户 U 发帖 P 时，系统把 P 加入每个关注者 F 的 sorted set：`ZADD user:F:timeline <ranking_score> <post_id>`。插入后，若 sorted set 超过最大大小（如 5000 条），删除最低分条目：`ZREMRANGEBYRANK user:F:timeline 0 -(max_size+1)`。

最大大小决定预计算 timeline 能回溯多远。每个被关注用户平均每天 5 条帖子的 5000 条，可覆盖 1 位关注者 1000 天历史——远超需要。实践中 1000 条对大多数用例足够。
