### 6.2 文档存储——灵活 Schema，嵌套数据

文档存储解决产品目录问题。它不再把每个产品硬塞进僵硬的表 schema，而是把每个产品存为一个**文档（document）**——一个类似 JSON 的对象，包含该特定产品所需的任意字段。


    // t-shirt product
    {
      "_id": "prod_001",
      "name": "Classic Tee",
      "price": 29.99,
      "category": "apparel",
      "attributes": {
        "sizes": ["S", "M", "L", "XL"],
        "colors": ["black", "white", "gray"],
        "material": "100% cotton"
      }
    }

    // laptop product
    {
      "_id": "prod_002",
      "name": "ProBook 15",
      "price": 1299.99,
      "category": "electronics",
      "attributes": {
        "processor": "Intel i7",
        "ram_gb": 16,
        "storage_gb": 512,
        "warranty_years": 2
      }
    }


两个文档共存于同一个集合（collection）。当另一个文档增加新属性类型时，两者都不需要 schema 迁移。应用读取 `attributes` 子文档并处理其中存在的任何字段。


#### 文档存储何时胜出

**灵活或演进的 schema：** 内容管理系统、具有不同可选字段的用户资料、异构产品类型的产品目录。

**作为单元读取的层次数据：** 如果一篇博客帖子在展示时总是连同作者信息、标签和评论一起出现，把它们存在一个文档中比 4 表 JOIN 更高效。文档可以一次读取操作取回。

**自然的数据局部性：** 文档存储允许直接嵌套相关数据——用户文档可以嵌入一组社交链接数组，避免单独的表和 JOIN。


#### 文档存储的 Tradeoffs

**收益：** schema 灵活性、层次数据的自然表达、通常单文档读取很快。

**代价（一致性）：** 大多数文档存储提供比关系型数据库更弱的一致性。MongoDB 的默认隔离级别相当于“读已提交”，多文档事务直到 4.0 版（2018 年）才加入——并且伴随性能开销。跨多个文档建模数据可能带来一致性挑战。

**代价（查询灵活性）：** SQL 的任意 JOIN 能力很难复制。如果你需要频繁跨多个文档集合 join 数据，文档存储很笨拙。它们适合符合文档形状的查询，不适合不符合的查询。

**代价（冗余）：** 因为你经常把相关数据嵌入文档而不是规范化，所以会产生数据冗余。如果 Alice 的用户名出现在每篇帖子的文档中（作为作者嵌入），改 Alice 的用户名就需要更新每篇帖子。这就是文档存储版的规范化 tradeoff（权衡）。


#### 侦探测试

选择文档存储前，问自己：“我能否通过按 ID 或简单过滤取回一个或少量文档来回答 90% 的查询？” 如果是，文档存储很合适。如果你发现自己频繁跨多种文档类型 join，你可能在对抗数据模型——关系型数据库可能更适合你。
