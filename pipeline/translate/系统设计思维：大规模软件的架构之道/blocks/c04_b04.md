#### 用 PACELC 对真实系统分类

| 系统 | P 选择 | EL 选择 | 说明 |
|---|---|---|---|
| PostgreSQL 同步复制 | C | C | 分区期间拒绝写入；等待所有副本确认 |
| Cassandra（默认设置） | A | L | 分区期间继续服务请求；单节点确认即接受写入 |
| DynamoDB | A | L | 默认最终一致性；强一致读可用，但延迟更高 |
| Zookeeper | C | C | 用于协调；为正确性牺牲可用性 |
| MySQL 异步复制 | A | L | 立即接受写入；副本落后 |

PACELC 迫使你在系统设计时回答两个问题，而不是一个。


### 4.4 一致性模型——一个谱系

真实系统不只是选择“强”或“最终”一致性——它们选择谱系上的一个点。理解这个谱系能让你把一致性级别与用户的真实需求匹配。

从最强到最弱：


#### 线性一致性（最严格）

如上定义：所有操作看起来都在某个单一时刻原子执行，顺序与真实时间顺序一致。如果操作 A 在操作 B 开始前完成，则 A 的效果在 B 执行时可见。

成本：每次操作都需要所有副本之间协调。在地理分布式系统中非常慢。

示例用例：分布式锁、领导者选举。任何两个进程必须就一个单一值达成一致的场景。


#### 顺序一致性

所有操作看起来按某种顺序执行，且所有节点看到的顺序相同。但该顺序不必尊重真实时间顺序——一次在另一次开始前完成的写入，在顺序中可能看起来“后”发生。

成本：比线性一致性略低，因为不需要墙钟时间协调。


#### 因果一致性

因果相关的操作在所有节点上以相同顺序出现。如果你看到一条回复，你也会看到原帖（因为回复因果依赖于原帖）。因果无关的操作在不同节点上可能以不同顺序出现。

成本：需要跟踪因果关系（通常用 vector clock，见第 14 章）。比顺序一致性便宜。

示例用例：评论线程（回复必须出现在原评之后）。一个动作引发另一个动作的社交 Feed。


#### 读己之写一致性（读己之写）

你写入一个值后，再查询时（从任何节点）总会读回该值。其他用户可能看到旧数据，但你总是立即看到自己的更新。

成本：相对便宜——系统需要把你的读路由到拥有你写入的副本，或在你的写传播完之前等待再让你读。

示例用例：个人资料更新（我更新简介后，我应该立即看到新简介，即使我的朋友几秒后还看到旧的）。


#### 最终一致性（最弱的有用保证）

如果没有新的写入，所有副本最终会收敛到同一个值。“最终”多久没有规定。对期间你看到什么没有任何保证。

成本：实现最便宜。任何副本无需协调即可响应任何请求。

示例用例：社交媒体“点赞”数（你看到 1000 赞，朋友看到 999 赞片刻是可以接受的）、DNS 记录、CDN。
