**Q2.**（联系第 5 章 ACID 讨论和第 6 章 BASE 哲学）一个团队为 SocialSnap 的关注计数提出如下缓存架构：不再把 `follower_count` 存在 PostgreSQL users 表中，而是只存在 Redis 里，每次新关注用 `INCR`。Redis 禁用持久化（无 RDB 或 AOF）。这个设计是否符合第 5 章讨论的 ACID 属性？它会产生什么故障场景，如何修复？

提示

想想 ACID 中的 D：Durability（持久性）。Redis 进程崩溃时数据会怎样？再想想关注计数是否属于必须持久的数据，还是可以重建。

**答案：** 这个设计违反了 ACID 的**持久性（Durability）**保证。第 5 章我们明确，持久性意味着已提交数据在失败中幸存——一旦告诉用户“已记录你的关注”，即使服务器随后立即崩溃，数据也必须保留。

无持久化的 Redis 把所有东西存在内存中。如果 Redis 进程崩溃，所有数据丢失。如果 SocialSnap 用 Redis 作为关注计数的唯一存储且禁用持久化，Redis 崩溃可能让所有用户的关注计数归零。一个拥有 100,000 名粉丝的用户在 Redis 重启后显示 0 粉丝。这既错误又用户可见。

**故障场景：** Redis 凌晨 3:00 崩溃。SocialSnap 自动重启 Redis。所有关注计数为 0。用户加载资料时，应用向 Redis 查询关注计数，每个人都得到 0。网站在线，但数据错误。

**修复选项：**

选项 A：启用 Redis 持久化（AOF，配 `fsync=always`）。每次 `INCR` 在确认前写入磁盘。恢复持久性，代价是写入吞吐（每次写入都磁盘 I/O）。

选项 B：保留 PostgreSQL 的 `follower_count` 列作为事实来源。Redis 只作缓存（用 TTL 或写通）。Redis 失败时回退到 PostgreSQL。这利用第 5 章关系型数据库的持久性保证，只为读性能加 Redis。

选项 C：从 `follows` 表重建计数。因为 `follows` 是规范化的事实来源（`SELECT COUNT(*) FROM follows WHERE followed_user_id = X`），计数总能重新计算。Redis 启动时，为所有活跃用户运行此查询预热缓存。小规模可行，数百万用户时昂贵。

选项 B 是生产安全的做法，反映一个关键原则：**Redis 用于速度，关系型数据库用于持久性**。
