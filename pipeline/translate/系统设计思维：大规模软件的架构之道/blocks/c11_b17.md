**Q2.** 本章主张应用服务器应无状态，但 Redis——持有会话和缓存状态——本身是有状态（stateful，有状态的）服务。Redis 现在成为关键依赖：如果 Redis 故障，所有会话丢失，用户全部登出。SocialSnap 应如何设计 Redis 部署以避免 Redis 成为单点故障？如果 Redis 主节点故障，副本提升前有短暂中断，活跃会话会怎样？

**讨论：** 这个问题探问无状态要求是否真正得到满足，还是只是把有状态问题往下推了一层。

Redis 本身必须冗余运行，以避免成为 SPOF。标准配置是 **Redis Sentinel** 或 **Redis Cluster**：一个 Redis 主节点处理写入；一个或多个副本节点持续从主节点复制；Sentinel 进程监控主节点，并在主节点故障时自动提升副本（通常在数秒内完成）。应用服务器配置为使用 Sentinel 地址而非直接 Redis 地址——故障转移后 Sentinel 告诉它们当前主节点在哪里。

这种配置下，Redis 故障变成短暂事件：主节点宕机，Sentinel 检测到故障（通常 10-30 秒，取决于配置），提升副本，应用服务器重连到新主节点。这个窗口内会话会怎样？

被提升的副本拥有主节点故障前已复制的所有会话数据。因为 Redis 复制是异步的，可能有少数最近毫秒写入的会话（在主节点故障前最后一次成功复制之后写入）尚未复制。那些特定会话会丢失——那些用户必须重新登录。数量通常非常小：只有在最后一次成功复制到主节点故障之间窄窗口内创建的会话。

对大多数应用，这是可接受的 tradeoff（权衡）。故障窗口是秒级；受影响会话数量极小；替代方案（同步复制，阻塞每次写入直到副本确认）会给每次登录增加延迟。SocialSnap 以极小的会话丢失风险换取低延迟会话写入。

更深教训：无状态要求并未消除有状态——它只是把状态移入专门构建、可冗余的基础设施，这些基础设施可以比普通应用服务器更高的可用性水平运行。Redis 配合 Sentinel 达到 99.99% 可用性，比应用服务器的 99.9% 强得多。
