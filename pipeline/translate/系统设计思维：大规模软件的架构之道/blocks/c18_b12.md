#### 应用问题

**Q1.** SocialSnap 想部署新功能“Reactions”（用户可以用 emoji 对帖子反应，而不仅是点赞）。这需要数据库迁移（添加 `reactions` 表和 posts 上的新 `reaction_count` 列）、新 API 端点，以及 feed 渲染服务的变更。设计部署计划，包括迁移策略、功能开关使用和回滚计划。

提示

思考操作顺序：数据库必须先满足什么，应用代码才能运行？应用必须先满足什么，用户才能看到功能？对数据库迁移使用 expand-contract 模式，并考虑三个阶段是否需要协调。

**答案：**

**阶段 1——数据库 Expand（第 1 周）：**

* 部署迁移：添加 `reactions` 表（id, post_id, user_id, reaction_type, created_at）和 posts 上的 `reaction_count` 列（默认 0，NOT NULL）。
* 该迁移向后兼容：现有代码不知道这些表，但存在它们也不会破坏。
* 暂不更改应用代码。

**阶段 2——后端部署，功能开关关闭（第 1 周）：**

* 部署新 API 端点 `POST /posts/{id}/reactions`——代码存在，但在功能开关打开前返回 404。
* 部署 Feed Service 变更，在功能开关开启时响应中包括 `reaction_count`。
* 功能开关“reactions”默认关闭。
* 运行数天，确认新代码路径没有意外错误。

**阶段 3——内部测试（第 2 周）：**

* 仅对内部 SocialSnap 员工用户 ID 启用功能开关。
* 手动测试所有 reaction 流程。
* 监控新端点错误率。

**阶段 4——金丝雀（第 2 周）：**

* 对 5% 用户启用功能开关。
* 监控：reaction API 错误率、Post Service 延迟（`reaction_count` join 是否增加开销？）、数据库写吞吐（`reactions` 表新写入）。
* 如果指标健康，5 天内逐步 ramp：20% → 50% → 100%。

**回滚计划：**

* 触发条件：reaction API 错误率 5 分钟 > 1%，或 `reactions` 表迁移出现任何错误。
* 动作：对所有用户禁用功能开关（即时，无需部署）。新 API 端点返回 404。Feed 停止显示 reaction 计数。
* 数据库：`reactions` 表和 `reaction_count` 列保留——不影响现有功能。如果功能取消，可在未来单独迁移删除它们。
* 验证：确认禁用功能开关后 2 分钟内错误率回到基线。

功能开关是关键安全机制：它允许无需部署即即时回滚，并把代码部署与用户可见发布分离。
