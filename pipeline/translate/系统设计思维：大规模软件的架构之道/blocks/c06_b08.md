#### 概念检测

**Q1.** 一家初创公司在构建客户关系管理（CRM）工具。销售代表为客户记录添加备注，每条备注的形状各不相同：有的有附件，有的有通话录音，有的只是文本，有的是带元数据的邮件。你会推荐哪种数据库存储这些备注，为什么？

**答案：** **文档存储**（如 MongoDB 或 Firestore）是合适选择。指向它的关键特征：

1. **异构 schema：** 每条备注形状不同——附件备注有 `file_url` 和 `file_type` 字段，通话录音备注有 `duration` 和 `transcript`，邮件备注有 `from`、`to`、`subject`、`body`。在关系型数据库中，你要么需要一张有很多可空列的表（丑陋、难扩展），要么需要复杂的 EAV（entity-attribute-value）schema（更难查询）。文档存储把每条备注存为 JSON 文档，只包含它需要的字段。

2. **作为单元读取：** 客户的备注通常一起展示。把每条备注存为文档意味着取回“客户 123 的所有备注”是单次查询，而不是跨表 JOIN。

3. **schema 演进：** 新的备注类型会随时间增加（视频通话、AI 工具的会议纪要）。给文档 schema 添加新字段是零停机非事件；给关系型数据库加列需要 schema 迁移。

需要注意的问题：如果 CRM 后来需要复杂的跨客户分析（“找出过去 30 天有通话录音且交易在第 3 阶段的所有客户”），文档存储可能吃力。许多 CRM 对在线应用用文档存储，再同步数据到关系型数据库或数据仓库做分析。

**Q2.** 用通俗语言解释为什么图数据库能高效处理多跳遍历而关系型数据库不能。使用每种数据库物理上如何查找相关数据的概念。

**答案：** 在关系型数据库中，每个关系都是表中的一行。要找 Bob 的朋友，数据库必须搜索 `friendships` 表中所有 `user_id = bob_id` 的行。这在有索引时很快，但仍必须从磁盘或内存读取匹配行。

要找朋友的朋友（2 跳），数据库必须先找到 Bob 的朋友（查找 1），然后对每个朋友再找到他们的朋友（N 次额外查找，每个朋友一次）。有合适索引时，每次查找都快，但总工作量与 Bob 的朋友列表大小乘以每个朋友的朋友列表大小成正比。3 跳或更多跳，工作量再次成倍增加。

根本问题：**关系型数据库把关系存为数据**（表中的行），访问这些数据每次都要回到数据库引擎。

在图数据库中，节点有**直接指针**指向它们连接的节点。找 Bob 的朋友意味着直接跟随 Bob 节点中存储的指针——没有表查找，只有指针解引用。找朋友的朋友意味着从每个朋友的节点跟随指针——仍然是指针解引用。每一跳都是直接内存访问，而不是数据库查询。
