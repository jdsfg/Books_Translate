这会把计数查询降到 O(log n + k)，k 是该帖子的点赞数。对 10,000（1 万）赞的帖子，这快得多。但对有 50 million（5000 万）赞的病毒帖，即使索引扫描也要花不少时间。

**方案 2：反规范化计数器（更适合点赞数这种场景）**

在 `posts` 表里加一个 `like_count` 列（我们在 5.4 节的 schema 中已经勾勒过）。每次点赞时在事务内原子递增：

    BEGIN;
    INSERT INTO likes (user_id, post_id) VALUES (456, 12345);
    UPDATE posts SET like_count = like_count + 1 WHERE id = 12345;
    COMMIT;

现在“帖子 12345 有多少赞？”变成：

    SELECT like_count FROM posts WHERE id = 12345;

这是 O(1) 主键查找——微秒级而非毫秒级。tradeoff（权衡）：你现在把计数存在两个地方（`likes` 表和 `posts.like_count`）。如果你批量删除点赞（如清理垃圾），也必须更新计数器。如果计数器与真实 `likes` 表不同步，就出现不一致。这就是反规范化 tradeoff（权衡）：以写入复杂度和不一致风险换取读速度。

**选哪个方案？** 对点赞数这种场景，方案 2（反规范化计数器）是行业标准选择。大表上的计数查询很贵，而点赞数一天被读数百万次。一致性风险通过把计数器与 insert/delete 放在同一事务中更新来管理。这遵循与 SocialSnap v1 的 `follower_count` 和 `following_count` 列相同的原理——预计算聚合是一项基础优化模式。
