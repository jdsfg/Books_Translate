#### 核心思想

不把会话数据存在服务器上再给客户一个不透明 ID，如果把会话数据以不可篡改格式存在客户端会怎样？

JWT 是一个紧凑、URL 安全的字符串，包含：

1. 一个 **header**（算法和 token 类型）
2. 一个 **payload**（claims——会话数据：user_id、username、roles、过期时间）
3. 一个 **signature**（服务器用 secret key 生成的加密签名）

服务器在登录时签发 JWT：

1. 创建 payload：`{"user_id": 42, "username": "alice", "exp": 1709510400}`
2. 用 secret key 签名：`HMACSHA256(base64(header) + "." + base64(payload), secret_key)`
3. 把 JWT 返回给客户端

客户端存储 JWT（在 cookie 或 localStorage 中）并在每个请求中附带发送。服务器通过验证签名来验证 JWT（用 secret key 重新计算并比对 token 的签名）。如果签名有效，payload 数据就可信——服务器无需任何数据库或 Redis 查找就知道 user_id 和 username。


#### JWT 收益

**真正无状态：** 不需要 Redis 会话存储。每个请求都不需要外部查找。服务器用加密方式验证 JWT——这是 CPU 操作，不是网络操作。与每次请求约 1ms 的 Redis 查找相比，这是 0ms 网络延迟。

**水平扩展：** 任何服务器都能验证任何 JWT，因为所有服务器共享同一个 secret key（或使用公钥密码学：验证 key 共享，签名 key 私有）。不需要共享会话状态。

**可移植：** JWT 可跨域和跨服务使用。如果 SocialSnap 开发了独立 API 服务，它可以验证主应用签发的同一个 JWT——无需跨服务会话共享基础设施。


#### JWT 成本与撤销问题

JWT 听起来是完美方案。为什么还要用 Redis 会话？

**撤销问题是致命局限。**

考虑：Alice 的账户被入侵。SocialSnap 安全团队强制登出 Alice 的账户。用 Redis 会话，这很简单：`DEL session:alice_session_id` 或 `DEL user:42:sessions`。Alice 的下一个请求找不到会话，被重定向到登录。

用 JWT，Alice 有一个 `"exp": 1709510400` 的 JWT（24 小时后过期）。24 小时内服务器没有任何办法让 JWT 失效，因为服务器没有已签发 token 的中心记录。“登出”只是删除客户端 cookie，但如果攻击者窃取了 Alice 的 JWT，他们会一直用到过期。

存在 workaround：

* 短 JWT 过期时间（15 分钟）——需要 refresh token（自身带来复杂度）
* Redis 中的“撤销列表”（被撤销 token ID 的集合）——但你重新引入了对 Redis 的依赖，部分抵消了无状态收益
* 轮换 secret key——让所有用户的所有 token 失效（强制全局登出）

这些 workaround 都不如 Redis 里的 session ID 干净，因为 session ID 可以一条命令删除。
