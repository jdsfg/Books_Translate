#### 概念检测

**Q1.** 一个 Web 服务报告中位数（p50）延迟为 50ms，p99 延迟为 2,000ms。这告诉你关于系统行为的什么信息？为什么工程师即使大多数请求很快也要关心 p99？

**答案：** p50（50ms）和 p99（2,000ms）之间的巨大差距告诉你延迟分布高度倾斜——大多数请求处理很快，但有一小部分请求的性能明显更差。这通常意味着存在特定的慢代码路径、资源争用（锁等待、垃圾回收停顿），或者某个依赖（数据库查询、外部 API 调用）偶尔比平常慢得多。

为什么 p99 重要：在规模下，“1% 的请求”是绝对数量很大的数。一个每天处理 100 万请求的服务，每天有 10,000 个请求经历 2 秒延迟。那 10,000 个请求代表 10,000 次用户体验。此外，对延迟高度敏感的操作（比如用户点击“支付”）可能正好走这条慢路径——2 秒的情况并不均匀分布在请求类型上。只看中位数延迟的工程师会错过一整类用户体验问题。

**Q2.** 你的系统有三个串行组件：负载均衡器（99.9% 可用）、应用服务器（99.5% 可用）、数据库（99.8% 可用）。近似系统可用性是多少？你会如何提高它？

**答案：** 系统可用性 ≈ 0.999 × 0.995 × 0.998 ≈ 0.992，即约 99.2%。这意味着即使每个组件本身都高度可用，系统每月仍会宕机约 7 小时。

最弱的环节是 99.5% 的应用服务器。要提高整体可用性：

1. **运行多台应用服务器**——只要任意一台能处理请求，服务只有全部同时失败时才不可用。两台可用性 99.5% 的服务器同时失败的概率是 0.005 × 0.005 = 0.000025，即该层的可用性为 99.9975%。
2. **为数据库添加读副本（读副本）**——数据库是下一个瓶颈。读副本可提升读操作的可用性。
3. **添加备用负载均衡器**——负载均衡器已经 99.9%，优先级较低，但主动-被动（active-passive）故障转移可以进一步提升。

更广泛的教训：链式依赖会乘性放大不可用性。每层的冗余是标准解法。

**Q3.** 解释 consistency（一致性）和 durability（持久性）的区别。分别举一个持久但不强一致、以及强一致但持久性保证有限的系统例子。

**答案：** 一致性是对不同读者在同一时刻看到什么的保证——它关乎跨节点的共识。持久性是数据在故障后是否幸存并可检索的保证——它关乎随时间的持久化。

**持久但不强一致：** Apache Cassandra 在默认设置下。每次写都持久化到磁盘（durable）并复制到多个节点。但如果你配置成优先可用性（replication factor 3，读取一致性 ANY，写入一致性 ONE），不同节点可能暂时对同一个键显示不同值。数据不会丢失（durable），但不同读者可能短暂看到不同版本（not strongly consistent）。
