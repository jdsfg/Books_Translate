#### 深入思考

**Q1.** 短码生成策略（随机码 + 冲突检查）在数据库只填充 3.5 万亿可能码的一小部分时效果很好。但随着数据库接近填满，渐近会发生什么？冲突检查何时成为问题，你会怎么做？

**讨论：** 随机码生成尝试的冲突概率是 `N / 3.5T`，N 为现有码数。让我们追踪降级：

* N = 10 亿码（1B / 3.5T ≈ 0.03%）：单次尝试冲突概率 0.03%。几乎所有生成第一次就成功。
* N = 350 亿码（35B / 3.5T ≈ 1%）：1% 冲突率意味着平均每代需 1.01 次尝试——仍可忽略。
* N = 3500 亿码（350B / 3.5T ≈ 10%）：10% 冲突率意味着平均每代 1.11 次尝试。生成效率略降但仍可用。
* N = 1.75 万亿码（50% 满）：冲突率 50%，平均每代 2 次尝试。 noticeable 但可管理。

真正问题不是尝试次数——即使 1,157 次创建/秒下每代 10 次尝试也只是 11,570 次数据库读/秒， easily 处理。问题是接近容量意味着码空间几乎耗尽。按每天 1 亿（100 million）码，3.5 万亿码可用 95 年。这不是近期担忧。

当它成为担忧时（也许 50 年后），解决方案是迁移到 8 字符码：62^8 ≈ 218 万亿个码，按当前速率再买约 6000 年（218 万亿 / 1 亿每天 ≈ 218 万（2.18 million）天 ≈ 5980 年）。旧 7 字符码仍然有效（该列支持最长 16 字符）。迁移成本为零——只需让码生成器产生 8 字符码。

更深教训：即使当前长度足够，也要把码长度设计为可扩展（可变长列，而非 CHAR(7)）。这是第 27 章“为演进设计”原则（state principle，状态）。

**Q2.** URL 短链常用于营销活动。一家公司可能创建单个短 URL，并向 1000 万收件人大规模邮件发送。约 1000 万收件人同时打开邮件并点击链接。该流量模式与稳态 116,000 RPS 假设有何不同，你会如何设计？

**讨论：** 这是第 7 章惊群问题在 URL 级别的表现。单个短码在邮件发送触发点击波时收到 1000 万同时请求。稳态假设的 116,000 RPS 分布到所有 URL，现在变成几分钟内一个 URL 1000 万请求。

**该流量模式特征：**

* 高度集中：所有流量到一个键
* 总体上可预测（公司知道邮件发送时间）
* 时间受限：点击波急剧达到峰值然后快速衰减
