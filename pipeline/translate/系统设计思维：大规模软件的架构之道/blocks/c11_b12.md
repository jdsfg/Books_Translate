**答案：** **JWT（JSON Web 令牌）** 是一个紧凑、加密签名的令牌，直接把会话 payload（user ID、username、过期时间等）包含在令牌自身中。服务器在登录时创建 payload 并用 secret key 签名。后续请求中，服务器通过重新计算签名并比对来验证 JWT——无需外部存储查找。

**它解决的问题：** 服务端会话需要在每次认证请求时查找 Redis（或数据库）。这增加每次请求约 1ms 网络延迟，并需要 Redis 基础设施依赖。JWT 验证是本地 CPU 操作（加密签名检查），零网络延迟、零外部依赖。

**根本局限——撤销：** JWT 在过期前一直有效，无论服务器做什么。如果 Alice 的账户被停用或入侵，删除服务端会话会在下一次请求立即生效。但有效 JWT 无法在不采取以下措施之一前失效：

* 等待过期时间（如果令牌有效期 24 小时则不可接受）
* 维护撤销列表（Redis 中失效令牌 ID 的集合）——重新引入 Redis 依赖
* 轮换签名密钥——让所有用户的所有令牌全局失效

撤销列表 workaround 部分抵消了 JWT 的无状态收益。对于安全事件需要立即终止会话的应用（金融服务、存在账户入侵场景的社交平台），撤销问题使 JWT 不适合作为主要会话机制。

**Q4.** 解释垂直扩展和水平扩展。各自的优点是什么？生产系统中通常如何组合？

**答案：**

**垂直扩展（scale up）：** 增加单台机器容量。更多 CPU、更大 RAM、更快存储。机器无需增加复杂度即可处理更多负载。

优点：简单（无需改代码）、无协调开销、对任何瓶颈都立即有效。

局限：物理上限（没有无限资源的机器）、成本超线性（好 10 倍的机器贵 10 倍以上）、仍是单点故障。

**水平扩展（scale out）：** 增加更多并行运行相同软件的机器。在机器集群间分发负载。

优点：理论上无上限（可不断加机器）、普通硬件、内置冗余（一台机器故障不会结束服务）、可独立扩展特定层。

局限：需要无状态应用设计、协调开销、更难调试、并非所有组件不经特殊技术就能水平扩展。

**如何组合：** 生产系统先用垂直扩展——在增加分布复杂度前最大化单服务器。当垂直到极限（或需要高可用性）时，再加水平扩展。不同层扩展方式不同：应用服务器水平扩展（无状态），数据库先垂直再水平扩展（读副本和分片，第 12 章），缓存通过集群水平扩展。
