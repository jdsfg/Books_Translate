#### 主主故障转移（Active-Active Failover）

在**主主（active-active）**配置中，多个实例同时处理流量。一个失败时，剩余实例吸收其流量——它们已经活跃，所以没有故障转移延迟。

例子：

* 负载均衡器后的多台应用服务器（第 11 章）。这是主主：所有服务器都处理流量。一台失败时，负载均衡器停止向它路由，把负载分配给其他服务器。
* 多区域数据库设置中两个区域都接受读（第 14 章的跨区域读副本）。

主主更高效——所有实例都在工作——并提供更快故障恢复（无故障转移时间；负载均衡器只需把失败实例移出轮询）。复杂度：对写操作，主主需要仔细协调以避免第 14 章的冲突场景。这就是为什么多主数据库（多节点接受写）需要第 14 章的一致性机制——quorum 写、冲突解决、CRDT。


### 16.4 熔断器模式

现在我们回到 SocialSnap 的周二的故障。根因是级联：部分 Redis 失败阻塞应用线程，耗尽线程池，导致整个应用失败。

级联发生是因为应用服务器在 Redis 明显失败后仍不断尝试连接 Redis。每个新请求都尝试连接 Redis，等待 30 秒，超时，然后释放线程——但只在线程被占用 30 秒后才释放。Redis 的小幅降级（30% 错误率）慢慢消耗所有可用线程。

修复：应用应检测到 Redis 失败并**停止尝试**。不是每个请求独立等待 Redis 超时，而是系统识别到 Redis 失败模式后立即拒绝需要 Redis 的新请求——甚至不尝试连接。

这就是**熔断器模式（Circuit Breaker pattern）**。
