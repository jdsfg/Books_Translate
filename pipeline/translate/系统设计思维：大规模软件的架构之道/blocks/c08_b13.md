在第 7 章的 SocialSnap v2 中，资料缓存 key `user:{user_id}:profile` 存储 users 表的数据：用户名、简介、头像 URL、加入日期等稳定字段。通知计数不是 users 表的一部分——它来自 notifications 表，频繁变化（每次点赞、评论、关注等）。

如果通知计数被包含在资料缓存 key 中，每个 incoming 通知都会要求使整个资料缓存失效——迫使数据库重新取回没变化的简介、头像 URL 和其他稳定数据。这是缓存失效浪费：你因为页面上显示的一个快速变化字段而驱逐并重新取回缓慢变化的数据。

**正确的缓存 key 设计（粒度分离）：**

* `user:{user_id}:profile` → 稳定字段（bio、photo_url、username）——长 TTL（30–60 分钟），只在资料编辑时失效
* `user:{user_id}:notification_count` → 易变计数器——短 TTL（10–30 秒）或通过 Redis `INCR`/`DECR` 作为事实来源

更广泛的教训：**缓存 key 粒度应匹配数据变化频率**。如果字段 A 每周变化一次，字段 B 每秒变化 100 次，把它们存在同一个缓存 key 中意味着 B 的每次变化都会驱逐 A 的缓存值—— defeats 缓存 A 的目的。

这是第 5 章反规范化讨论在缓存中的对应：你为了优化访问模式而结构化数据。缓存 key 设计就是缓存 schema 设计。粒度错了，命中率就受影响。
