第 12 章中，SocialSnap 对数据库分片以处理写入量。跨分片查询问题立即出现：查询跨越多个 shard 的数据需要在应用代码中写扇出逻辑，跨 shard JOIN 在单次 SQL 查询中基本不可能。团队发现自己在写数据库过去自动做的事。

但想想：如果问题不是分片策略而是共享本身呢？如果多个不相关功能争夺同一个数据库——同样的表、同样的索引、同样的连接池、同样的 CPU——才是脆弱的根本原因呢？

这就是微服务背后的直觉。不是一个大应用配一个大数据库，而是很多小服务，每个有自己的数据存储，独立部署，各自按需求扩展。照片上传暴涨不会影响消息服务。支付功能的数据库 schema 变更不需要全公司部署冻结。用户资料团队不需要与搜索团队协调。

这是承诺。现实更复杂——这些复杂性值得精确理解，因为它们决定微服务会拯救你的组织，还是慢慢勒死它。
