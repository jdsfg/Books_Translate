* 选择把用户 ID 存成 32 位整数（今天便宜，但到 5 十亿用户时无法在不痛苦迁移的情况下更改）
* 把业务逻辑完全放在数据库里（存储过程、触发器），这些在分布式架构里需要改动
* 选择只适用于关系型查询的数据模型（会让之后的 NoSQL 迁移非常困难）
* 不加密静态用户数据（等用户有了数据后再加密需要迁移所有现有数据）

正确的心态：**可逆的决策快速做，不可逆的决策慢点做。** 快速上线。但对于那些需要迁移千兆字节数据或重写核心基础设施才能更改的决策，现在多花一小时思考。

**Q3.** SocialSnap 在一个周五下午上线了新的“热门帖子”功能。一位名人在电视直播里提到 SocialSnap，60 秒内流量从往常 500 并发用户飙升到 50,000。单服务器单体应用完全垮掉——用户看到 502 错误。重启服务器后，在大量重连客户端的冲击下几秒后又崩溃。

找出在下次流量尖峰时为了让服务器活下来，你会最先做的**两个最有影响力的改动**，并解释为什么是先做这两个，而不是别的。

提示

想想单台机器上的单体应用在流量尖峰时实际耗尽的是什么：CPU、内存、数据库连接，还是三者都有？把“最先崩溃的是什么？”与“长期架构修复是什么？”分开。前两个改动应该便宜且可快速部署——不是耗时数周的重构。

**答案：**

**第一步：识别实际失败的是什么。** 100 倍流量尖峰压垮单体应用的过程是可预测的：首先，并发连接耗尽 Web 服务器的线程或进程池（每个请求都持有一个线程等待数据库响应）。其次，数据库连接池饱和——每个线程持有一个打开的连接，数据库连接数耗尽。应用开始返回错误，或将请求无限期排队，消耗内存直到进程崩溃。

**改动 1：在服务器前尽快加上限流器（rate limiter）或请求队列（几分钟内）。** 这是最快的杠杆。配置 Web 服务器（例如 Nginx）拒收或排队超过阈值的请求——比如 1,000 个并发连接——而不是让它们全部堆在内存里。阈值之外的用户会立即得到干净的“服务繁忙”错误，而不是 30 秒后才超时。仅此一项就能阻止崩溃循环：服务器处理它能处理的，安全地丢弃多余负载。这是关于**限制爆炸半径**，而不是解决扩展——但它让服务器活下来。

**改动 2：为最热、重复执行的查询加上读穿透缓存（read-through cache，Redis 或 Memcached）（几小时内）。** 流量尖峰期间，大部分请求往往只命中少量资源——在这个场景里，是热门帖子和那位名人的主页。这 5 万用户每个人都在触发相同的数据库读。添加缓存意味着第一个请求支付数据库成本；后续对同一份数据的请求都在微秒级从内存服务。这可以在不改变应用基本架构的情况下，把尖峰期的数据库读负载降低 80–90%。
