#### DNS 如何工作

DNS 是一个分层的、分布式的域名 → IP 地址映射数据库。解析过程：

1. 浏览器检查本地缓存（最近解析的域名按 TTL 缓存）。
2. 操作系统检查本地缓存（类似）。
3. 查询被发送到配置的 DNS 解析器（通常由 ISP 或企业网络提供）。
4. 如果解析器缓存了答案，就返回它。
5. 如果没有，解析器查询根域名服务器（它们知道每个顶级域如 `.com` 的权威服务器）。
6. 根域名服务器指向 `.com` 的 TLD 域名服务器。
7. TLD 域名服务器指向 SocialSnap 的权威域名服务器（注册域名时配置）。
8. SocialSnap 的权威域名服务器返回 IP 地址。

最终答案在各层按 DNS 记录的 TTL 缓存。常见 TTL：300 秒（5 分钟）用于频繁变化的记录，86400 秒（24 小时）用于稳定记录。


#### DNS 作为负载均衡器

DNS 记录可以包含多个 IP 地址。客户端解析域名时会收到多个 IP。客户端通常尝试列表中的第一个；如果失败，再试下一个。不同客户端收到不同顺序的列表（轮询 DNS），把负载分散到多个数据中心或负载均衡器 IP。

DNS 负载均衡是粗粒度工具——它运行在地理层面（把亚洲用户路由到 Singapore 数据中心，欧洲用户到 Frankfurt 数据中心）。数据中心内部的负载均衡使用专用负载均衡器。


#### DNS TTL 与缓存失效

DNS TTL 制造了一个熟悉的陈旧问题（回想第 7 章缓存 TTL）。如果 SocialSnap 需要改 IP 地址（迁移到新数据中心），DNS 记录变更传播很慢——缓存了旧 IP 的客户端会继续使用旧 IP，直到它们的 TTL 过期。TTL 为 24 小时时，一小部分用户可能在迁移后长达 24 小时内仍被指向旧 IP。

迁移期间，DNS 工程师通常在变更前先把 TTL 降低（从 24 小时降到 5 分钟），完成变更，观察传播，再提回 TTL。这就是 DNS TTL 管理——它与第 7 章缓存中看到的新鲜度与性能 tradeoff（权衡）完全相同。


### 9.6 HTTP、TCP 与 WebSocket——协议层

HTTP 是 Web 的协议，大多数应用流量通过它传输。但 HTTP 有多个版本，性能特征各不相同，有些应用需要完全不同的协议。


#### HTTP/1.1

HTTP 的传统版本。每个 HTTP/1.1 请求通过 TCP 连接发送。连接可复用（持久连接），但单个连接上的请求必须顺序完成——在第一个响应收到前不能发送第二个请求。浏览器通过打开多个并行连接解决这个限制（通常每个域名 6 个），但这浪费资源。
