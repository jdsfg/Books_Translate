#### 实践中的日志级别

DEBUG 日志详尽。数据库服务中，DEBUG 日志可能记录执行的每条 SQL。API 处理器中，可能记录每个请求的每个 header。开发和调试时 invaluable，但生产环境产生巨大体量——通常是 INFO 日志的十到一百倍。大多数生产系统默认关闭 DEBUG，只在调试特定服务时按需开启。

INFO 日志记录正常、预期但有意义粒度的事件：“用户登录”、“支付处理完成”、“key X 缓存未命中”。它们讲述正常操作的故事。

WARN 日志记录预期但值得注意的事件：“缓存未命中率超过 50%——可能缓存踩踏”、“用户 Y 触发限流器”。WARN 不是失败，但值得调查。

ERROR 日志记录失败：“数据库查询失败”、“下游服务返回 500”、“通知重试 3 次后仍失败”。每条 ERROR 都应可行动——如果一个错误经常发生却没人处理，它可能被误分类或配置错误。

FATAL 日志记录进程无法恢复并即将退出的失败：“无法绑定端口 8080”、“配置文件损坏”。FATAL 日志应触发 pager 告警。


#### 侦探与日志

回想第 3 章的福尔摩斯估算方法——从部分证据推理到确信结论。同一纪律适用于事故调查。

SocialSnap 监控面板周二下午变红时，第一个问题是：“什么变了？”有经验的事故响应者不会随机搜索日志。他们形成假设并用日志证实或证伪：

**假设 1：** 部署出了问题。检查：“最近 30 分钟是否有服务部署？”（查看部署日志。）结果：没有部署。

**假设 2：** 流量高峰。检查：“请求量是否增加？”（查看请求率指标。）结果：请求量正常。

**假设 3：** 依赖失败。检查：“是否有引用外部服务的 ERROR 日志？”（查询过去 30 分钟 ERROR 日志，过滤 `upstream` 字段。）结果：多条日志显示 `"upstream": "redis", "error": "connection timeout"`。

每条日志都是一条线索。好的调查者系统化地阅读线索，而不是淹没其中。侦探纪律——形成假设、收集证据、排除替代方案——正是有效事故响应者的工作方式。
