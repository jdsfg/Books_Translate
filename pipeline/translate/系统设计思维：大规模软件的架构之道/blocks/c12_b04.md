#### 定义：分片

**分片**是把数据库数据划分成互不相交的子集（shards），每个子集存在独立数据库实例上的做法。每个 shard 包含一部分数据，所有 shard 合起来构成完整数据集。写被路由到拥有相关数据的 shard；读被路由到包含所请求数据的一个或多个 shard。

plain 语言：不是一家图书馆藏所有书，而是十家图书馆，每家藏十分之一的书。请求被路由到持有相关书的那家。

每个 shard 通常是完全独立的数据库实例，常常有自己的读副本。这意味着读副本和分片策略可以组合：每个 shard 有一个主库和副本，同时获得水平写扩展（分片）和水平读扩展（副本）。


#### 分片策略

如何决定哪些数据去哪个 shard？有三种主要策略，各有 tradeoff（权衡）。

**基于范围的分片（range-based sharding）** 根据 shard key 列的值范围分配数据。例如：user ID 1–1,000,000 到 Shard 1；user ID 1,000,001–2,000,000 到 Shard 2；依此类推。这简单直观，也支持高效的范围查询（查找 user ID 在 500,000 到 600,000 之间的所有用户——显然全在 Shard 1）。

基于范围分片的问题是**热 shard**。如果 user ID 顺序分配且不断有新用户，新用户总是去最高 shard。所有注册写都命中 Shard N，而 Shard 1 到 N-1 几乎空闲。负载分布不均——一个 shard 热（过载），其他 shard 冷（利用不足）。

**基于哈希的分片（hash-based sharding）** 对 shard key 应用哈希函数，用结果决定 shard。例如，`shard_number = hash(user_id) % num_shards`。8 个 shard 且哈希函数好时，user ID 大致均匀分布到所有 8 个 shard。没有热 shard（假设没有热用户——见下文）。

基于哈希分片的问题是范围查询变贵。想找上周注册的所有用户？如果用户按 user ID 哈希分片，这些人分布在所有 shard——你必须查询所有 shard 并合并结果。

**基于目录的分片（directory-based sharding）** 维护一个独立的查找表（目录），把每个 shard key 映射到它的 shard。想找 user 12345？在目录里查 12345：它说“Shard 4”。这是最灵活的策略——你可以把个别 key 重新映射到不同 shard，而不必遵循公式。

目录分片的成本是目录本身。目录查找给每次操作增加延迟，目录成为单点故障（它必须高可用）。对非常大的数据集，目录本身可能也需要分布。
