#### Serverless 的权衡

Serverless 并不严格优于传统基于服务器的部署——它只是权衡曲线上的不同点：

**好处：**

* 零服务器管理运营开销
* 从 0 自动扩展到数百万请求
* 按使用付费（无请求时无成本）
* 强制隔离：每个函数都是干净、无状态的单元

**成本：**

* 冷启动延迟：函数若近期未被调用，云 provider 必须启动新容器——延迟 100ms–2 秒（100ms–2s），取决于运行时和包大小。这对延迟敏感路径不可接受。
* 执行时间限制：AWS Lambda 函数最多运行 15 分钟（15 minutes）。长时间运行工作负载（视频转码、机器学习训练）不适合该模型。
* 运行时控制有限：你无法配置内核、网络栈或硬件。对有特殊性能要求的情况是约束。
* 厂商锁定：serverless 函数深度绑定特定云 provider 的 API、事件模型和触发机制。迁移到不同 provider 需要重写集成层。
* 可观测性挑战：追踪跨 5 个串行调用的 serverless 函数请求需要仔细设置分布式追踪——与微服务相同挑战，但没有同等级别的运行时控制。

**Serverless 适用场景：** 低流量 API 和 webhook（“空闲时零成本”收益最大）；事件驱动数据处理（文件上传到 S3 时处理）；定时任务（每晚午夜运行清理作业）；快速原型（无需配置基础设施即可部署新功能）。

**Serverless 不适用场景：** 延迟敏感 API（冷启动延迟是问题）；长时间运行工作负载；有状态的（stateful）处理；需要细粒度性能调优的系统。

对 SocialSnap，serverless 适用于：图片处理（上传时调整照片大小）、定时数据导出、第三方集成 webhook 处理器。不适用于：feed 服务（延迟敏感）、匹配服务、计费服务。
