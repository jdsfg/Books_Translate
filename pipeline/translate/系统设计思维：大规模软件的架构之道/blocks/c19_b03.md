#### OAuth 2.0 流程（概念）

当用户把第三方应用（“PostScheduler”）连接到 SocialSnap 时，发生如下过程：

1. PostScheduler 把用户重定向到 SocialSnap 的授权页：“PostScheduler 希望访问：读取你的帖子、代表你发帖。允许或拒绝？”
2. 用户点击“允许”。SocialSnap 生成一个 **authorization code**，并把用户重定向回 PostScheduler。
3. PostScheduler 把这个 authorization code 发到 SocialSnap 的 token 端点（server-to-server，不经过用户浏览器）。SocialSnap 返回一个 **access token** 和一个 **refresh token**。
4. PostScheduler 在 API 请求中使用 access token：`Authorization: Bearer eyJhbGciOi...`。SocialSnap 验证 token 并按用户权限处理请求。
5. Access token 过期（通常 1 小时后）。PostScheduler 用 refresh token 获取新 access token，无需用户再次登录。

关键洞见：用户密码永远不会与 PostScheduler 共享。PostScheduler 只持有 access token——它是 scoped 的（只授予用户批准的特定权限）且 time-limited 的（会过期）。如果 PostScheduler 被入侵，攻击者只获得 access token——它们可被用户撤销，且不能用来改用户密码。


#### JWT——Token 格式

**JSON Web Tokens（JWT）** 是现代系统中 access token 的主要格式。JWT 是 Base64url 编码、密码学签名的字符串，编码一个 JSON payload。

JWT 由点分隔的三部分组成：

**Header**（用于签名 token 的算法）：`{"alg": "RS256", "typ": "JWT"}`

**Payload**（claims——关于用户和 token 的断言）：


    {
      "sub": "user_8821934",
      "name": "Alex Chen",
      "iat": 1704067200,
      "exp": 1704070800,
      "scope": "read:posts write:posts"
    }


**Signature**：用服务器私钥对 header 和 payload 做的密码学签名。

完整 token 形如：`eyJhbGci...eyJzdWIi...SflKxwRJSMeKKF2...`

Feed Service 收到带 JWT 的请求时，用对应公钥验证签名。如果签名有效，payload 中的 claims 可信——token 由 SocialSnap 认证服务器创建且未被篡改。Feed Service 可以从 payload 中提取 `user_id` 和 `scope` 而无需每次都调用 auth 服务器——密码学签名提供了信任。

这就是无状态认证：服务器不需要查数据库来验证 token。token 是自包含的。


#### JWT 安全考虑

JWT 有一个重大限制：一旦签发，除非到期，否则无法单独撤销。如果用户账户被入侵，你想立即失效其 token，除非维护 token 黑名单（每次请求都要查数据库，失去无状态优势）或使用非常短的过期时间，否则做不到。

实践中：使用短生命周期的 access token（15–60 分钟）和较长生命周期的 refresh token。用户登出或账户被入侵时，使 refresh token 失效（存储在数据库中）。未来的 token refresh 尝试失败，用户实际上无法获得新 access token——现有 token 在剩余短生命周期内仍有效，但损害有限。
