### 12.2 读副本——第一个泄压阀

第一个观察：大多数生产系统中，读远多于写。SocialSnap 的工作负载很典型：每有一个人创建帖子（一次写），就有大约五十个人浏览 feed、资料或帖子（读）。比例可能是 10:1、50:1，甚至 100:1，取决于应用。Twitter 著名的读写比极端到大部分工程精力都放在读优化上。

如果读是主要负载，那把读路由到额外的数据库实例会怎样？

这就是**读副本（read replica）**模式。一个数据库实例——**主库（primary）**（也叫 master 或 leader）——接受所有写。一个或多个**副本（replica）**实例持续接收主库的变更流并应用，保持数据最新。应用服务器可以把读查询路由到副本，分发读负载。


#### 定义：读副本

**读副本**是从主数据库持续接收并应用变更、保持最终一致副本的数据库实例。副本通常是只读的——所有写都到主库，副本通过复制机制异步接收这些写。

plain 语言：主库是原始笔记本；每个副本都是一个人，在原始记录写完后几秒钟把它抄下来。读者可以查任何一份副本。写者必须总是找原始本。

复制机制本身值得理解。PostgreSQL、MySQL 和大多数关系型数据库用**预写日志（write-ahead logging，WAL）**做复制。每次改变数据的写都先记录到日志（WAL），然后再应用到实际数据文件。这个日志被流式传输给副本，副本重放它以在自己的数据文件上重现相同变更。副本本质上在按顺序重新执行主库做过的每一次写。


#### 复制延迟问题

问题是：复制不是瞬时的。主库写日志；副本通过网络接收；副本应用。这需要时间——健康网络中通常毫秒级，但负载或网络分区下可能是秒级甚至更长。

在这个窗口内，副本的世界观比主库稍旧。这个差距称为**复制延迟（replication lag）**，它造成微妙但危险的处境。

想象这个序列：

1. Alice 发布一条状态更新。写进入主库。帖子已存。
2. Alice 的浏览器立即请求自己的资料页查看新帖子。应用服务器把该读路由到副本。
3. 副本还没应用 Alice 的写入——复制延迟 500 毫秒。
4. Alice 的资料页加载出来，没有她的新帖子。
5. Alice 以为帖子丢了，又发一遍。
6. 现在她有了重复帖子。

这与第 7 章 Redis 缓存中看到的陈旧性问题一样，但 stakes 更高。缓存陈旧通常是表面问题——你几秒钟内看到略旧的数据。复制延迟的陈旧性会造成真实数据异常：写入丢失、重复提交、困惑的用户。
