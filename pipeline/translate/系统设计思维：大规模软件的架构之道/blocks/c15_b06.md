#### 编舞（Choreography）——Saga 中的服务共舞

在**编舞**中，没有中央协调器。每个服务监听事件，知道发生这些事件时该做什么。saga 的逻辑分布在这些服务之间：

1. Checkout Handler 发布 `user.upgrade.initiated` 事件。
2. Payment Service 监听 `user.upgrade.initiated`，扣款，并发布 `payment.charge.succeeded`（或 `payment.charge.failed`）。
3. User Service 监听 `payment.charge.succeeded`，把用户更新为高级版，并发布 `user.upgraded.to.premium`。
4. Notification Service 监听 `user.upgraded.to.premium`，发送邮件。

补偿：如果 User Service 失败并发布 `user.upgrade.failed`，Payment Service 监听 `user.upgrade.failed` 并发起退款。


#### 定义：编舞

**编舞（Choreography）** 是一种 saga 协调风格：每个服务独立对事件做出反应并发布自己的事件。没有中央控制器。整体 saga 行为由各个服务交互涌现出来。

plain 语言：编舞就像爵士乐队即兴演奏。没人指挥。每个乐手倾听别人，根据听到的演奏自己的部分。音乐从他们互动中涌现。

编舞优点：松耦合（服务只需知道它们监听的事件）、没有单点故障（没有中央协调器会宕机）、天然适合事件驱动架构（第 8 章的消息队列）。

缺点：saga 逻辑**隐式且分散**。要理解 saga 做什么，你必须读所有服务并追踪跨所有服务的事件流。调试失败 saga 需要在多个服务间关联日志。增加新步骤要确定监听哪个服务的事件、在哪个服务加监听器——并确保不漏掉任何情况。


#### 编排（Orchestration）——中央指挥

在**编排**中，一个中央组件——**编排器（orchestrator）**——协调 saga。编排器显式按顺序调用每个服务，接收结果，决定下一步做什么。

高级版升级编排器：

1. 调用 Payment Service：扣 9.99 USD。等待结果。
2. 若成功：调用 User Service：设置 `is_premium = true`。等待结果。
3. 若成功：调用 Notification Service：发送邮件。等待结果。
4. 若任一步失败：按相反顺序调用补偿。
