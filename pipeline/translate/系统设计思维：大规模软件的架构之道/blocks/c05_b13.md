#### 深入思考

**Q1.** SocialSnap v1 schema 把 `follower_count` 和 `following_count` 直接存在 `users` 表上，而不是在查询时用 `SELECT COUNT(*)` 计算。这是经典的反规范化 tradeoff（权衡）。描述一种计数器与真实 `follows` 表不同步的场景——具体包括哪些操作序列（含一次失败）会导致这种不一致？然后解释把这些操作包在事务里如何防止它。

**讨论：** 不一致场景：假设处理“关注”动作的代码按顺序执行两步——先向 `follows` 插入一行，再更新 `users` 的 `follower_count`。如果应用在第 1 步和第 2 步之间崩溃，或数据库连接断开，`follows` 表已记录新关系，但 `follower_count` 没有递增。现在 `follows` 显示 Alice 关注了 Bob，但 Bob 的 `follower_count` 少了 1。

在规模下，类似的部分失败会累积。例如删除垃圾账号的后台任务可能从 `follows` 删除行，但在递减计数器前失败，或相反。随着时间推移，计数器偏离真实值。

事务通过让两个操作原子化来防止：

    BEGIN;
    INSERT INTO follows (follower_id, followed_id) VALUES (1, 2);
    UPDATE users SET follower_count = follower_count + 1 WHERE id = 2;
    UPDATE users SET following_count = following_count + 1 WHERE id = 1;
    COMMIT;

如果事务中任何操作失败——包括 INSERT 和 UPDATE 之间崩溃——数据库会在重启时利用预写日志回滚所有更改。`follows` 表和计数器总是一起更新，要么都不更新。ACID 的原子性正是让反规范化计数器可以安全使用的保证。

剩余风险：即使有事务，如果存在不经过计数器直接修改 `follows` 的代码路径——例如直接删除行的管理员脚本——计数器仍可能漂移。事务只在单一代码路径内强制执行一致性，而非所有可能路径。这就是 ACID 的“一致性”性质在工作：应用负责定义什么叫“有效”（计数器与 follows 匹配），数据库只在所有写入都通过维护该不变量的路径进行时才能强制执行。

**Q2.** 关系型数据库已主导数据存储 50 年，但 2000–2010 年代一波 NoSQL 数据库挑战了其主导地位。NoSQL 并没有取代关系型数据库——今天两者共存。这告诉了你工程 tradeoff 的什么本质？面对新项目应如何评估用哪个？

**讨论：** 关系型 vs NoSQL 的故事说明了一个基本原理：**每种技术都是特定情境下的正确工具，任何工具的主导地位都反映了它被设计时的情境。**

关系型数据库被设计时：

* 磁盘昂贵（规范化尽量减少冗余数据）
* 计算昂贵（SQL 的声明式模型比手写遍历更高效）
* 主导工作负载是事务处理（银行、库存、工资）
* schema 灵活性次于正确性
