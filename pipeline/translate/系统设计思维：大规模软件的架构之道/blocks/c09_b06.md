#### HTTP/2

HTTP/2 引入**多路复用（multiplexing）**：单个 TCP 连接上可同时交错多个请求和响应。浏览器可以通过一条 HTTP/2 连接发送 100 个请求，并按完成顺序任意接收响应。这消除了 HTTP/1.1 的队头阻塞问题。

HTTP/2 还支持服务器推送（server proactively 发送客户端将需要的资源）、头压缩和流优先级。对 Web 应用，HTTP/2 通常比 HTTP/1.1 减少 15-30% 页面加载时间。


#### HTTP/3 与 QUIC

HTTP/3 在传输层用 QUIC（Quick UDP Internet Connections）取代 TCP。QUIC 基于 UDP，但添加了 TCP 的可靠性保证，并提升性能：更快的连接建立（HTTPS 的 1-RTT 而非 3-RTT）、更好的丢包处理（传输层队头阻塞消除），以及原生连接迁移（如果你从 Wi-Fi 切换到蜂窝网络，QUIC 保持连接）。

HTTP/3 部署越来越广，但还不如 HTTP/2 普及。HTTP 版本选择通常由 Web 服务器和 CDN 层处理，而非应用代码。


#### TCP vs UDP

对应用开发者来说，传输层的基本选择是 TCP 还是 UDP。

**TCP（Transmission Control Protocol，传输控制协议）：**

* 面向连接（数据传输前三次握手）
* 可靠：每个数据包（packet）都被确认；丢数据包会重传
* 有序：数据按发送顺序到达
* 流量控制：根据接收方容量调整发送速率

**UDP（User Datagram Protocol，用户数据报协议）：**

* 无连接：没有握手，直接发数据包（packet）
* 不可靠：包可能丢失、重复或乱序且不通知
* 无顺序保证
* 无流量控制
* 开销更低、延迟更低

**何时用 UDP：** 能容忍一些数据丢失但需要低延迟的应用。视频流：丢一帧视频可接受；等待重传会造成可见卡顿。网络游戏：丢一个位置更新会被下一个覆盖；重传会让玩家角色跳变。DNS 查询：小、快、尽力而为（如果查询丢了就重试）。语音通话：短暂的音频掉线比 TCP 重传的延迟更不 disruptive。

**何时用 TCP：** 任何不能容忍数据丢失的应用——网页、文件传输、邮件、数据库连接、API 调用。

对 SocialSnap 的 API，TCP（通过 HTTP）是正确选择。对未来的实时功能（直播、多人游戏），UDP 可能合适。
