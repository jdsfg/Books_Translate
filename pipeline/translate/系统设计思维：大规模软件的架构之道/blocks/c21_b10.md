### 21.7 SocialSnap v7——架构回顾

DM 功能把 SocialSnap 带到 v7。让我们退一步，追溯全书 SocialSnap 架构的完整演进，看每一章的决策如何累积成当前架构。

**v0（第 1 章）：** 笔记本上的单个 Python 函数。无数据库、无规模、无容错。整个系统状态在内存中。

**v1（第 5 章）：** 加入 PostgreSQL。用户和帖子表。首次持久化存储。应用现在无状态的（stateless，任何节点重启后数据都在），但数据库是单点故障。

**v2（第 7 章）：** 加入 Redis 缓存用于资料查找。首次尝到缓存降低延迟的甜头——也出现首个陈旧缺陷：用户更新资料后一小时内 feed 仍显示旧版本。加入基于 TTL 的失效作为修复。

**v3（第 8 章）：** 加入通知队列。欢迎邮件从 HTTP 请求处理器移到异步消费者。首次体验最终一致性：邮件在注册数秒后到达而非同步。用户没注意到；架构显著更 resilient。

**v4（第 11 章）：** 水平扩展加入三台应用服务器。首个分布式 session 缺陷：session 存在某台服务器，用户下一请求被另一台处理时却登录了。通过把 session 移到 Redis 修复。无状态（stateless）要求被内化。

**v5（第 12 章）：** 数据库成为瓶颈。加入读副本处理 feed 日益增长的读负载。最终按 `user_id` 分片。首个跨分片查询问题：“查找 Alice 关注的所有用户的帖子”需要查所有分片。引入反规范化预连接频繁共现数据。

**v6（第 16 章）：** 首次重大故障——Redis 降级级联到整个应用失败。加入熔断器。实现优雅降级：Redis 不可用时 feed 回退到数据库，提供略陈旧内容而非报错。意识到可靠性需要面向失败设计，而非避免失败。

**v7（第 21 章）：** 加入 DM 功能。引入全新架构域——实时、有状态的（stateful）、基于 WebSocket 的通信——与现有无状态的（stateless）基于 HTTP 的 feed 和帖子系统并行运行。DM 系统与核心 feed 系统隔离（独立连接服务器、独立数据库集群），以满足 DMs 不得降低核心体验的约束。

当前架构长什么样？SocialSnap v7 拥有：

* **API gateway + 负载均衡器（load balancer）** 处理所有入站流量
* **应用服务器**（无状态的，stateless，水平扩展）服务 feed、帖子、用户资料
* **连接服务器**（有状态的，stateful，管理 DMs 的 WebSocket 连接）
* **PostgreSQL 集群**（按 `user_id` 分片）存储帖子和用户数据
* **PostgreSQL 集群**（按 `conversation_id` 分片）存储 DM 消息
* **Redis 集群** 用于缓存（资料、feed、session 数据）和连接注册表
* **消息队列（Kafka）** 用于通知投递和分析事件
* **通知服务** 消费 Kafka，投递推送通知和邮件
* **对象存储（类 S3）** 用于媒体附件
* **CDN** 用于静态资源和媒体
