#### Pager 测试

评估告警的一个简单启发：问“如果这个告警凌晨 3 点响起，是否需要立即人工处理？”如果答案是否定的——如果告警只是信息性的、可以等到早上、代表正在自动处理的状态——那它就不应该 page 任何人。它应该去仪表盘、工单或非紧急通知渠道。

凌晨 3 点为一个非紧急告警叫醒人，会侵蚀对告警系统的信任。信任被侵蚀后，工程师会开始静音告警“只想睡一觉”。最终抓住真正 outage 的告警可能和那些噪声一起被静音。

理想的 on-call 体验：每次 page 都是真实的用户可见问题，每次 page 都需要无法自动化的人类判断，page 相对不频繁，因为好的监控在问题还没 page 级严重时就及早发现。


#### 告警路由与 Runbook

当告警响起，on-call 工程师需要知道：这个告警是什么、为什么重要、我首先该做什么？

**Runbook**（也称 playbook）是附加到告警的预写响应流程。一个“Redis 错误率高”的 runbook 可能说：

1. 在 Redis 仪表盘检查 Redis 集群状态
2. 检查问题是否限于一个 shard 还是影响所有 shard
3. 如果是一个 shard：把副本提升为主库（链接到流程）
4. 如果是所有 shard：检查最近 Redis 部署；如果 30 分钟内部署过，回滚
5. 如果最近没有部署：上报数据库团队；把 Redis 客户端熔断器设为 OPEN

Runbook 编码机构知识。资深工程师第一次遇到某个告警时学到正确响应。初级工程师 on-call 遇到不熟悉告警时，runbook 防止他们犯下灾难性错误。当同一告警一个月内第三次响起，runbook 会更新：“如果再次发生，在关闭前先修复根因。”


#### 权衡矩阵：SLI/SLO 与可观测性

回想第 2 章引入的权衡矩阵。SLI/SLO 框架和可观测性基础设施给矩阵增加了一个重要的新行：

策略 | 延迟 | 一致性 | 可用性 | 运营复杂度
---|---|---|---|---
无监控 | 无 | 无 | 无改进 | 无
基于症状的告警 | 略高（指标开销） | 无变化 | 显著提高（更快 MTTR） | 中（仪表盘、on-call 轮值）
完整可观测性栈（指标 + 日志 + 追踪） | 小开销 | 无变化 | 最高（快速根因分析） | 高（工具、埋点、维护）

可观测性成本真实：运行 Prometheus、Grafana、日志流水线（Elasticsearch 或类似）和分布式追踪后端增加了必须部署、维护和监控的基础设施。（这里有个值得注意的观察：你的监控基础设施本身也必须被监控。谁来监视监视者？）

但收益在几乎任何规模都超过成本。盲目飞行的团队——依赖用户报告来发现 outage——的 MTTR 和每次事故影响范围始终高于具备良好可观测性的团队。
