#### 绞杀榕（Strangler Fig）模式

当你需要替换一个大型系统组件——比如把单体迁移到微服务时——诱惑是 **大爆炸重写**：关闭旧系统，构建新系统，切换。这几乎从不奏效。大爆炸重写以超出预算、超出时间著称，并且会复制被替代系统的 bug（因为团队正在重新学习旧系统隐式处理的所有边界情况）。

替代方案是 **strangler fig** 模式：让新系统与旧系统并存，逐步将流量从旧系统路由到新系统，每块验证后再继续。

隐喻：绞杀榕围绕寄主树生长，逐渐接管，直到寄主树死亡，绞杀榕成为自支撑结构。寄主树（旧系统）被“绞杀”——不是突然被砍死，而是逐渐被取代。

SocialSnap 把单体分解为微服务时使用了该模式。他们从提取 Notification Service 开始——风险低、边界清晰的功能。单体继续处理所有其他请求。Notification Service 稳定后，提取 User Service，然后是 Post Service。每次提取都是一个离散、低风险的迁移。

关键纪律：在新系统完全验证前保持旧系统运行。永远不要一次性切换所有流量。使用功能开关（第 18 章）和金丝雀部署逐步转移流量。如果出错，立即回滚。

### 27.3 权衡矩阵作为活文档

回忆第 2 章：Tradeoff Matrix 作为跨四个维度比较设计选择的工具被引入。全书过程中，每新增一个构建块、扩展模式和案例研究，我们都往矩阵里加行。

对 SocialSnap，Tradeoff Matrix 不是写一次就归档的文档。它是架构团队每次重大设计决策都更新的活工件。看它是如何演变的：

**v1（添加数据库）时：** 团队加了一行：“PostgreSQL 存储用户和帖子数据——以写吞吐限制为代价获得强一致性和持久性。”

**v2（添加缓存）时：** “Redis cache-aside 用于 profile——以陈旧和缓存失效复杂度为代价获得低延迟读。”

**v5（分片）时：** “User 表分片（mod N）——写吞吐随分片扩展；跨分片查询需要应用层 join；分片数难以改变。”

**v6（微服务）时：** “微服务分解——独立部署和团队 owning；需要分布式追踪；更高运营复杂度。”

维护这个矩阵的力量：新工程师加入团队时，可以读 Tradeoff Matrix，不仅理解决策是什么，还理解决策为什么做。矩阵捕获推理，而不仅仅是结论。

到第 26 章，SocialSnap 的 Tradeoff Matrix 已有数十行。第 28 章呈现完整版——全书完整参考卡。
