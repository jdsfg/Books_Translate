#### 组合策略

实践中，生产系统会组合两种策略：

**先垂直扩展：** 在增加水平复杂度前，先看单节点能走多远。一台大 PostgreSQL 实例每秒可服务数千请求。在增加分布开销前，先优化机器。

**垂直到极限后再水平扩展：** 一旦最大的单台机器也不够——或需要高可用性（无单点故障）——再加水平扩展。

**不同层不同扩展方式：** 应用服务器容易水平扩展（无状态）。数据库先垂直扩展，再水平扩展（分片——第 12 章）。缓存通过集群水平扩展（Redis Cluster、Memcached consistent-hashing cluster）。

回想第 3 章的粗略估算：理解问题规模才能判断需要垂直还是水平扩展。预期 10,000（10000）名并发用户的初创公司可能只需一台大实例。预期 10 million（1000 万）并发用户的平台需要跨多台实例水平扩展。


### 11.7 协调开销——分布式系统的成本

水平扩展产生一个容易被低估的问题：**协调开销**。

单台服务器不需要与任何人协调。它可以用内存锁、本地事务和直接函数调用。一群服务器必须通过网络协调——网络更慢、更不可靠，并引入新的故障模式。

考虑一个简单操作：给帖子的“点赞数”加 1。

**单台服务器：** `post.like_count += 1`。如果两个请求同时到达，进程内锁可防止两个请求都读到 `0`、各加 1、再都写回 `1`（结果应为 `2` 却成了 `1`）。

**多台服务器：** Server A 读到 `like_count = 100`。Server B 也读到 `like_count = 100`。Server A 写回 `like_count = 101`。Server B 也写回 `like_count = 101`。正确答案是 102。这是**竞态条件（race condition）**，由缺少共享锁导致。

解决点赞数竞态的方案：

**数据库原子操作：** `UPDATE posts SET like_count = like_count + 1 WHERE id = 101`。数据库的行级锁让这条语句原子化，无论多少应用服务器同时执行。数据库的 ACID 保证处理协调。（这就是为什么我们在第 5 章说数据库值得用——它们解决了你自己难以解决的分布式协调问题。）

**Redis INCR：** `INCR post:101:likes`。Redis 单线程处理命令，所以 `INCR` 是原子的。多台应用服务器可同时安全调用。

**乐观并发控制：** 读取当前计数和版本号，加 1，仅当版本号没变时写回。如果已变（别人在读写之间加过 1），重试。

协调开销的教训：**分布式系统比单服务器系统更难**。不是不可逾越地难，但更难。任何多个服务器必须并发更新的共享资源都需要仔细协调——通常委托给一个权威单点存储（数据库或 Redis），它提供原子操作。
