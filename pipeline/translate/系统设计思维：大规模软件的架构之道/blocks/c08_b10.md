#### 概念检测

**Q1.** 在分布式系统背景下，同步通信与异步通信有什么区别？各举一个适合的使用场景。

**答案：** 在**同步通信**中，调用者等待被调用者完成后再继续。调用者被阻塞直到收到响应。这是函数调用和 HTTP 请求的常见模型：你发送请求并等待回复。

在**异步通信**中，调用者发送消息后不等候就继续。被调用者独立、按自己的节奏处理消息，不向原调用者返回响应。调用者不知道（实时）处理何时完成或是否完成。

**同步用例：** 用户登录。应用必须针对数据库验证密码。这必须同步——用户在认证确认前不能继续。把认证委托给异步流程就意味着告诉用户“你可能登录了，稍后再查”，这显然不对。

**异步用例：** 登录后，系统记录登录事件用于安全审计。审计日志写入是否成功不应影响用户登录能力。审计日志可以异步写入——登录事件进入队列，用户立即认证，审计记录后台写入。如果审计系统暂时慢，用户登录不会被延迟。

**Q2.** 三种消息投递保证是什么？用 plain 语言解释每种含义，并说明每种在故障场景下会发生什么。

**答案：**

**最多一次：** 消息被投递零次或一次——绝不超过一次。如果投递和消费者确认之间发生网络故障或消费者崩溃，消息被丢弃。不再重投。

故障场景：消费者收到消息、处理（发送邮件），然后在向队列确认前崩溃。队列不重试。消息丢失。

结果：无重复处理，但消息可能静默丢失。

**至少一次：** 消息被投递一次或多次。队列重投直到收到消费者确认。消费者确认前崩溃会导致重投。

故障场景：消费者收到消息、处理（发送邮件），然后在确认前崩溃。队列在消费者恢复后重投。消费者再次收到并处理（又发一封邮件）。

结果：不丢失消息，但消费者必须处理重复（幂等性）。

**正好一次：** 消息正好投递一次——不丢失、不重复。

故障场景：理论上不存在坏场景。实践中，跨分布式系统实现正好一次需要协调（分布式事务），昂贵且复杂。大多数“正好一次”系统通过幂等的至少一次投递实现。

结果：理想状态，但实践中通过仔细的幂等设计而非真正正好一次基础设施实现。
