#### 100 用户 vs 1 亿用户

让我们追踪 SocialSnap 在压力下的演进，不是为了现在理解所有解决方案，而是为了理解挑战的本质。

**100 用户时：** SocialSnap v0 没问题。一台机器。响应毫秒级。宕机只是小麻烦。出问题时重启笔记本就好。

**10,000 用户时：** 笔记本开始吃力。数据库查询变慢，因为数据库文件变大了，而且有很多并发连接（concurrent connections）。你换到一台专用服务器。你给数据库加了索引（index）。事情还行。

**100 万用户时：** 单台服务器不堪重负。你加了更多服务器——但现在，当用户在 A 服务器登录后，下一个请求到了 B 服务器，B 服务器不知道他已经登录。会话断了。你需要外部化会话状态（externalize session state）。与此同时，数据库仍是一台单机。每个写入都涌向它。在高流量下，它成为瓶颈（bottleneck）。你需要把读取复制（replicate）到其他机器。但现在你有了两份数据——当一份改变时，另一份何时追上？你的用户看到的是旧数据（stale data）。

**1 亿用户时：** 你有几十台应用服务器、多个数据库副本（database replicas）、数据库前面的缓存（caches）。但现在数据大到单机放不下。你必须把数据库拆到多台机器上——但跨机器的 SQL JOIN 慢得灾难。你的部署流程要花一小时。生产环境的一个缺陷几分钟内影响 1 亿人。每个工程决策现在都有复合后果（compounding consequences）。

注意发生了什么。每一层的问题不只是上一层问题的放大版——它们是根本不同的问题。100 用户时问题是性能；100 万用户时问题是状态协调；1 亿用户时问题则是组织和架构层面的。

这就是为什么系统设计是与编程不同的学科。编程教你让一台计算机正确做事。系统设计教你让成千上万台计算机可靠地协同工作。

#### 常见误解：扩展是以后才考虑的问题

许多工程师认为，不该在需要之前担心扩展。“过早优化是万恶之源”，这句名言如是说。

这话部分正确，部分危险。你不该为三个用户建一个分布式系统。但你应该从开始就理解每个选择对扩展的影响。有些决策以后改起来便宜，有些则不然。

第一版选 PostgreSQL 而非 MySQL？需要时容易改。把用户 ID 存成 32 位整数？一旦你有 5 十亿用户且 ID 耗尽，就极难改动。把业务逻辑深埋在数据库存储过程（stored procedures）里？当你需要把数据库分布化（distribute）时，重构会极其困难。

系统设计的学科不是过早地为扩展而构建。它要求在清楚理解决策扩展影响的前提下做选择——这样当增长到来时，前进的道路已经存在。
