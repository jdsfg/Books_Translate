#### 常见误解

一个常见误解是 geohashing 保证附近点总是共享相同前缀。并非如此——它只是让这“很可能”。二分边界问题意味着任何使用 geohashing 的地理匹配系统必须在搜索中包含邻接单元格。忽略邻接单元格会导致匹配系统偶尔找不到最近司机，因为他们位于二分边界另一侧 10 米处。

### 25.2 位置追踪——每秒 125 万（1.25 million）次写入

每秒 125 万（1.25 million）次位置更新是巨大的写入吞吐。回忆第 8 章，位置数据库被提到是高吞吐写入的目的地。现在我们设计它。


#### 写入路径

每 4 秒，每位活跃司机的移动应用发送一个 HTTP 请求：

    POST /driver/{driver_id}/location
    { "lat": 37.7749, "lng": -122.4194, "timestamp": 1714000000 }

位置更新流水线：

1. **负载均衡器**（第 9 章）：把 125 万请求/秒分布到 API 服务器
2. **API 服务器层**（无状态、水平扩展——第 11 章）：验证请求，用计算出的 geohash 富化
3. **位置存储写入：** 写入 `(driver_id → current_location)` 并更新 geohash 索引
4. **发布到位置事件流：** 向事件流（Kafka topic——第 8 章）发出更新，供下游系统消费（ETA 计算、动态加价计算、乘客地图显示）

位置存储本身必须以低于 10ms 的写入延迟处理 125 万写入/秒（以保持端到端更新流水线 < 100ms）。标准关系型数据库无法直接处理该吞吐；即使重度优化的 PostgreSQL 单节点也艰难于每秒 5 万（50,000）次写入以上。

合适技术是内存键值存储（Redis）或列族存储（Cassandra）。Redis 单节点每秒可处理 50 万（500,000）+ 操作；10 节点的分片 Redis 集群轻松处理 500 万操作/秒。司机当前位置存为简单键值：`driver:{id}:location → {lat, lng, geohash, timestamp}`。


#### Geohash 索引

为让匹配服务找附近司机，系统维护反向索引：`geohash:{cell} → 该单元格中的司机 ID 集合`。司机从 geohash 单元格 A 移动到 B 时：

1. 从 A 单元格集合中移除该司机
2. 把该司机加入 B 单元格集合
3. 更新司机位置键

用 Redis sorted set，单元格可用精确坐标作为分数存储司机 ID，实现单元格内细粒度距离排序。Redis 原生 `GEOADD` 和 `GEORADIUS` 命令直接在坐标 sorted set 编码上实现地理空间查询——本质上是内置的 geohash 类空间索引。


#### 位置数据新鲜度

位置更新只有最近才有用。司机 10 分钟前的位置对匹配无意义——司机可能已移动数英里。位置存储应让条目过期：若司机 30 秒未更新，可能已离线，应从可用司机索引中移除。Redis TTL（Time-To-Live）自动处理：每次更新重置 TTL；过期把陈旧司机从候选中移除。
