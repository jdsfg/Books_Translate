#### 限流——防止滥用

**限流（rate limiting）** 是对单个客户端在某一时间窗口内可发起请求数设置上限的做法。

为什么要限流？

* **防止滥用：** 爬取你整个用户数据库的机器人会发送数百万请求。限流阻止它。
* **防止意外过载：** 重试循环配置错误的客户端可能在无意中每秒发送数千请求。
* **确保公平访问：** 任何单个用户都不应降低其他用户的服务质量。
* **保护后端服务：** API 网关处的限流防止级联过载。

**常见限流算法：**

**固定窗口（fixed window）：** 统计每个时间窗口内的请求数。如果用户每分钟发送超过 100 个请求，就拒绝多余的。简单，但存在“窗口边界突发”问题：100 个请求在 11:59:59，另外 100 个在 12:00:00——2 秒内 200 个请求，而声明的限制是 100/分钟。

**滑动窗口（sliding window）：** 追踪每条最近请求的时间戳。在任何给定时刻统计过去 60 秒内的请求数。更准确，但需要为每条请求存储一个时间戳。

**令牌桶（令牌桶）：** 桶中保存令牌（最多有最大容量）。令牌以固定速率加入（如每秒 10 个）。每个请求消耗一个令牌。如果桶空，就拒绝请求。令牌桶允许短暂突发（最多到桶容量），同时强制执行平均速率（补充速率）。这符合大多数真实用户行为：一阵活动，然后空闲。

**漏桶（leaky bucket）：** 请求进入一个队列（“桶”），并以固定输出速率处理。突发被平滑。多余请求排队或被拒绝。无论输入突发如何，都保证稳定输出速率。

实践中，令牌桶是 API 限流最常见的算法：它允许合法突发，同时强制执行持续速率限制。

**限流的存储：** 限流计数器必须在所有 API 网关实例间共享（否则用户可以把请求路由到不同实例来绕过限制）。这通常存在 Redis 中——使用每个用户的令牌桶状态，配合原子 `INCR` 和过期命令。注意这个模式：Redis 再次出现，这里用于其原子计数器和亚毫秒级访问时间，正如第 7 章 SocialSnap 缓存中那样。


### 9.9 权衡矩阵——负载均衡与 API 设计

权衡矩阵新增两行：

架构选择 | 延迟 | 一致性 | 可用性 | 运维复杂度  
|---|---|---|---|---  
L7 负载均衡器 | ↑ 轻微（+1-2ms 解析） | ↔ | ↑↑ 高（健康检查、流量分配） | ↑（SSL 终止、路由规则、L7 检查）  
API 网关 | ↑ 轻微（每请求 +1-5ms） | ↔ | ↑（集中式滥用防护） | ↑（额外组件、配置）  
用 gRPC 替代 REST | ↓ 降低（消息小 3-10 倍、解析更快） | ↔ | ↔ | ↑（Protobuf schema 管理、工具）  
用 GraphQL 替代 REST | ↑ 轻微（resolver 开销） | ↔ | ↔ | ↑（schema 设计、查询复杂度管理）  

注意，负载均衡器和 API 网关增加了一点延迟成本（请求必须穿过它们），以换取显著的可用性和运维收益。这通常是值得的——2ms 开销换一个能消除整类故障的组件。
