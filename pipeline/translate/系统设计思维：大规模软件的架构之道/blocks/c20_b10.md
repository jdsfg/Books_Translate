#### 应用问题

**Q1.** SocialSnap（第 5 章的平台）想增加短链功能。用户发帖时，SocialSnap 自动创建短版本。工程团队争论把它做成独立微服务还是集成到现有帖子服务。用本章设计证据论证两种方案，然后做决定。

提示

回想第 13 章的服务边界启发式：当不同扩展要求、不同部署节奏或不同运营特征时，服务应分离。考虑 URL 短链与帖子服务是否共享这些属性。

**答案：**

**支持独立微服务的论点：**

* 不同扩展画像：URL 短链读多写少（100:1），帖子服务写多（发帖内容）。独立服务可独立扩展——短链服务获得更多读服务器和更大缓存，帖子服务获得写优化基础设施。
* 不同数据存储：URL 短链数据库主要是追加（URL 创建后很少修改），而帖子频繁更新（点赞、评论、编辑）。
* 可复用：独立 URL 短链服务可被帖子服务、DM 功能（第 21 章）、通知服务和第三方开发者通过 API 使用。
* 不同 SLO：重定向延迟（p99 100ms）与帖子获取要求不同。

**支持集成到帖子服务的论点：**

* 更少网络跳数：创建包含链接的帖子需要同步调用 URL 短链服务。如果短链服务宕机（即使短暂），帖子创建失败。集成消除了这个依赖。
* 初始实现更简单：为快速上线功能，构建独立服务及其数据库、部署流水线、监控和 on-call 轮换是重大开销。
* 规模还没到：SocialSnap 当前阶段每天不会收到 1 亿个链接创建——独立扩展的好处可能不值得其复杂度。

**决策：** 先集成到帖子服务（使用模块/库，而非直接放在请求处理器），以快速交付功能。当 (a) 扩展要求显著分化，或 (b) 其他服务需要 URL 缩短能力时，再规划提取为独立服务。这是第 27 章绞杀榕模式的主动应用——以清晰边界设计集成实现，使未来提取可行。

**Q2.** 重新设计 URL 短链的分析子系统以支持新查询：“显示我所有 URL 在过去 30 天内按国家聚合的点击。” 当前设计（Kafka 队列 feeding 数据仓库）能处理，但团队想添加实时仪表盘显示最近 5 分钟点击。
