#### 跨站请求伪造（CSRF）

SocialSnap 用户登录后，浏览器存储会话 cookie。每个 SocialSnap 请求都自动包含该 cookie——浏览器对所有发往该域的请求都会发送它，无论请求来源何处。

CSRF 攻击利用这一点。攻击者在 `evil.com` 创建页面：


    <img src="https://socialsnap.com/posts/delete?id=12345" style="display:none">


当登录的 SocialSnap 用户访问 `evil.com` 时，浏览器加载这个“图片”——实际上是向 SocialSnap 发 GET 请求。SocialSnap 看到带有有效会话 cookie 的请求（浏览器自动发送）并删除帖子 12345。

修复方法：**CSRF 令牌**。SocialSnap 渲染每个表单时生成一个随机的、用户特定的令牌，并作为隐藏字段包含。浏览器提交表单时附带该令牌。SocialSnap 处理请求前验证令牌。由于 `evil.com` 无法读取 SocialSnap 表单中的 CSRF 令牌（被同源策略阻止），它无法伪造有效请求。

**SameSite cookie 属性** 是现代防御：在会话 cookie 上设置 `SameSite=Strict` 或 `SameSite=Lax`，告诉浏览器不在跨源请求上发送 cookie。这基本消除了现代浏览器的 CSRF 风险。


#### 常见误解

常见误解是这些漏洞是“已解决的问题”——现代框架自动处理。这部分正确：现代 ORM 默认使用参数化查询，现代模板引擎默认转义 HTML。但开发者仍会通过以下方式引入漏洞：为“方便”使用原始字符串拼接、在想要“渲染 HTML”时明确选择不转义，或认为“我们使用 JSON 而非 SQL”所以 API 层不会注入。

注入漏洞存在于用户输入到达解释器的任何地方——SQL、JavaScript、shell 命令、XML 解析器。原则始终相同：把代码与数据分开。
