#### 第 2 层：重定向服务

重定向服务收到 `GET /abc1234` 请求，在数据库（或缓存）中查找 `abc1234`，返回重定向响应。

**HTTP 状态码选择——301 vs 302：**

* **301 (Moved Permanently)：** 浏览器缓存该重定向，不再调用短链服务。未来访问 `short.ly/abc1234` 直接去往长 URL，完全绕过服务。这对延迟和服务器负载极好——但意味着分析失效（浏览器不再调用服务，无法记录点击），且重定向无法更改或禁用。
* **302 (Found / Temporary Redirect)：** 浏览器不缓存该重定向。每次访问短 URL 都调用服务。分析正常工作。重定向可以更改或禁用。代价：对服务的请求略多。

对需要做分析的公开短链服务，**302** 是正确默认。想要 301 行为的用户可以 opt in（知道会失去分析和更改能力）。内部我们用第 7 章的模式把查找缓存到自己的服务器——不需要浏览器缓存来避免数据库负载。

**缓存策略：**

热数据集（最热的 1% URL = 约 100 万条记录 = 250MB）可放入内存。我们用 Redis 配合 cache-aside 模式（第 7 章）：

1. 请求到达短码 `abc1234`
2. 检查 Redis：缓存命中 → 立即返回重定向（约 5ms）
3. 缓存未命中 → 查询数据库 → 写入 Redis 并设 TTL（24 小时）→ 返回重定向（约 50ms）

该工作负载的缓存命中率：如果最热 20% URL 占 80% 流量，我们缓存最热的 1% URL（100 万条，250MB），仅缓存命中率约 60-70%，剩余 30-40% 从数据库以合理延迟返回。

TTL 设多久？大多数 URL 24 小时合适。有自定义过期时间的 URL，TTL 设为 `min(24h, time_until_expiry)`。URL 被删除或目标变更时，显式失效缓存键（从 Redis 删除）。这就是第 7 章的缓存失效问题：我们通过写时显式失效解决，TTL 作为安全网。


#### 第 3 层：写路径——URL 创建

URL 创建是写路径。1,157 次创建/秒，单个数据库主库可管理。流程：

1. 收到 `POST /urls`，body `{"long_url": "https://..."}`
2. 验证 URL（语法有效？是否可 fetch？可选，会增加延迟）
3. 检查限流（该用户 IP 每小时最多创建 100 个 URL）
4. 生成随机 7 字符 base-62（BASE）码
5. 尝试插入 `urls` 表
   * 如果 INSERT 成功（无冲突）：返回 `{"short_url": "short.ly/abc1234"}`
   * 如果因唯一约束冲突失败：回到步骤 4
6. （异步）预写缓存，把新 URL 写入 Redis

写路径上，限流至关重要：单个 IP 可产生大量创建请求，消耗存储并可能耗尽码空间。在 API gateway 层限流——每小时每 IP 100 次创建——防止滥用。
