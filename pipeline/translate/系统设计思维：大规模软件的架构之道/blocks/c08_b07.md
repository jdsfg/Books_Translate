### 8.7 SocialSnap v3——通知队列

让我们回到本章开头 SocialSnap 的具体问题：同步注册流程。

SocialSnap v3 为注册流程、更广泛地为所有生成通知的事件引入消息队列。队列系统是一个简单的（概念上：由数据库或 Redis 支撑的持久队列）——还不是 Kafka，但原理相同。

新注册流程：


    User submits signup form
        ↓
    Application Server (HTTP handler)
        ↓ 1. Insert user into PostgreSQL (REQUIRED — user must exist)
        ↓ 2. Publish "user.signup" event to message queue (fast, ~2ms)
        ↓
    Return HTTP 200 "Account created!" to user
        ↓
    (Meanwhile, in the background...)
    Queue Consumer: Email Service
        ← reads "user.signup" event from queue
        ← sends welcome email (300ms — doesn't block the user)

    Queue Consumer: Analytics Service
        ← reads "user.signup" event from queue
        ← logs the event (50ms — doesn't block the user)

    Queue Consumer: Contact Notification Service
        ← reads "user.signup" event from queue
        ← notifies connected friends (200ms — doesn't block the user)


用户体验到瞬时注册（PostgreSQL 插入 + 队列发布约 25ms）。后台工作——邮件、分析、通知——异步发生。


#### “如果邮件服务器宕机怎么办？”时刻

引入队列前，邮件服务器宕机意味着用户注册失败。现在，如果邮件服务器宕机：

1. 注册事件仍被发布到队列。
2. 队列持久保存消息。
3. 邮件服务消费者离线——不再从队列读。
4. 消息在队列中累积（积压增长）。
5. 邮件服务恢复后，从队列读取并处理所有累积消息。
6. 欢迎邮件被投递，也许晚一小时——但它们终究会到。

注册流程从未失败。用户从未看到错误。邮件延迟多半不会被大多数用户注意到。

这就是消息队列的可用性故事。SocialSnap 的注册可用性现在变成：


    注册可用性 ≈ P(DB 正常) × P(队列正常)


邮件、分析和通知服务不再在关键路径上。它们的可用性影响下游动作是否快速发生，而不影响用户能否创建账户。
