#### 应用问题

**Q1.** SocialSnap 想实现“关注用户”功能。关注用户 B 会触发三件事：(a) 在社交图服务中插入 `friendship` 记录；(b) 在用户服务中更新用户 B 的关注者数；(c) 通过通知服务发送“你有新关注者！”通知。把这个设计成基于编舞的 saga，画出服务间流动的事件。

提示

从初始触发事件开始，追踪每个服务的反应及它发布的事件。

**答案：** 基于编舞的“关注用户”Saga：

**触发：** “关注”按钮的 HTTP 处理器收到请求。在 API Gateway 数据库中插入 pending 的 `follow_request` 记录，并通过 Outbox 模式发布 `follow.requested` 事件，payload 为 `{follower_id: 42, followed_id: 77, request_id: "req_a1b2c3"}`。

**第 1 步——Social Graph Service：** 监听 `follow.requested`。在 `friendships` 表中插入 `{follower: 42, following: 77}`（幂等：先检查关系是否已存在）。发布 `follow.graph.updated` 事件，带上 `request_id`。

**第 2 步——User Service：** 监听 `follow.graph.updated`。为用户 77 递增 `follower_count`。（使用 CRDT 风格递增，或幂等语句（幂等性） `INCREMENT ... WHERE follower_count_idempotency_key != 'req_a1b2c3'`）。发布 `follow.follower.count.updated` 事件，带上 `request_id`。

**第 3 步——通知服务：** 监听 `follow.follower.count.updated`。获取用户 77 的通知偏好（用户 77 是否希望收到新关注者邮件通知？）。若合适则发送通知。发布 `follow.notification.sent` 事件。

**补偿流：**

如果第 1 步失败（Social Graph Service 宕机）：`follow.requested` 消息留在队列中重试。如果重试耗尽，编排器（或监控告警）把关注标记为失败。无需补偿——还没有任何变更。

如果第 2 步在第 1 步成功后失败：Social Graph Service 发布 `follow.graph.update.failed`。User Service 监听该事件（它已从第 1 步事件知道请求）——但此情况下第 2 步尚未执行，所以无需补偿。`follow.graph.updated` 事件被重试。

如果第 3 步在第 1、2 步成功后失败：关注者数已更新，但通知没发送。这是可接受的（通知失败可容忍——关注本身成功了）。通知重试逻辑单独处理通知。saga 即使通知失败也被视为“成功”。

**观察：** 这个 saga 设计认识到通知是补充的——核心关注动作（图更新 + 计数更新）才是必要部分。通知失败不触发补偿。并非所有失败都需要回滚一切。
