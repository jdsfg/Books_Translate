URL 短链很干净。请求到达，发生查找，返回重定向。服务器不记住客户端。客户端不维持与服务器的连接。每个请求独立。这是第 11 章理想状态——服务因无每客户端状态而可轻松扩展。

聊天与这一切相反。

打开聊天应用时，你的设备与服务器之间建立持久连接。该连接只要你在线就存在——几分钟、几小时，有时甚至几天。朋友发消息给你时，服务器必须通过该连接把消息推送到你设备，实时，无需你轮询。服务器必须跟踪：哪些用户在线、他们连到哪个服务器、哪些消息已送达、哪些消息用户尚未阅读。

这是有状态的世界（stateful，有状态的）——架构挑战与第 20 章设计的任何东西都完全不同。

SocialSnap 工程团队在 v7 面临这个挑战。SocialSnap 已增长到 5000 万用户，产品路线图要求增加 Direct Message（DM）功能。决策：构建简单收件箱模型（像带聊天 UI 的邮件）还是构建带送达回执、已读回执和在线状态的实时聊天系统。团队选择实时。本章设计该系统。


### 侦探简报

**客户：** SocialSnap v7——为拥有 5000 万（50 million）注册用户、500 万（5 million）日活用户的社交平台增加 DM 功能。

**线索（需求）：**

* 用户可一对一发送文本消息（最初无媒体）
* 接收者在线时消息实时送达
* 接收者离线时消息存储并可取回（收件箱）
* 用户可看到消息是否“已送达”和“已读”（delivery receipts 和 read receipts）
* 用户可看到对方是否“在线”（presence）
* 消息历史保留，用户可搜索最长 1 年
* 群聊最多 100 名成员
* DM 系统不得降低 SocialSnap 核心 feed 体验（隔离要求）

**约束（证据）：**

* 500 万（5 million）日活用户；峰值并发用户约 50 万（500,000）
* 平均每用户每天发 20 条 DM → 每天共 1 亿条消息
* 每条消息平均 200 字节
* 消息送达延迟：在线接收者低于 200ms
* 历史读多写少（用户回滚对话），活跃聊天写多
* 在线状态更新高频但低价值（可容忍一定陈旧）

**问题：** 如何为 50 万并发用户设计持久连接上的实时送达，而不像第 20 章那样享有无状态扩展的简单性？

### 21.1 传输问题——如何把消息推送到浏览器

URL 短链接收 HTTP 请求并响应。每次交互由客户端发起。但聊天中，服务器必须在新消息到达时发起交互：无需接收者先请求，就把消息推送到接收者。

三种服务器主动通信方法存在，代表复杂度-效率曲线上的不同点。
