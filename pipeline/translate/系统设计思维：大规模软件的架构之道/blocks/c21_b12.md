#### 概念检测

**Q1.** HTTP 与 WebSocket 通信的根本区别是什么，为什么对聊天应用重要？

**答案：** HTTP 是由客户端发起的请求-响应协议。客户端发送请求；服务器恰好返回一个响应；连接关闭（或复用于下一个请求，但总是客户端发起）。服务器没有客户端先请求就无法向客户端发送数据。WebSocket 是持久、双向协议。初始握手后，客户端和服务器都可以在任意时间发消息。服务器可以无需等待请求就向客户端推送数据。对聊天，这一区别至关重要：有人发消息给你时，服务器需要立即把它推到你设备。用 HTTP，你就需要持续轮询（“有新消息吗？”），浪费带宽并增加延迟。用 WebSocket，消息在服务器收到瞬间到达你设备，无需轮询。

**Q2.** 为什么消息必须先持久化再经 WebSocket 投递，这防止了什么故障模式？

**答案：** 先持久化规则确保消息不会因基础设施故障而丢失。考虑替代方案：先投递，再持久化。如果 WebSocket 投递成功但数据库写入失败（数据库不可用、网络分区），接收者已在屏幕上看到消息但从未存储。当他关闭并重新打开应用，消息没了——历史无法获取，因为它从未持久化。用先持久化：如果数据库写入成功但 WebSocket 投递失败（接收者离线、连接断开、服务器崩溃），消息已存在数据库。接收者重连时拉取。如果数据库写入失败，发送者收到错误可重试。先持久化的最坏情况是“消息延迟”——永远不会“消息丢失”。

**Q3.** 解释在线状态检测的心跳机制，以及为什么移动网络约束下它必不可少。

**答案：** 心跳工作如下：用户客户端连接时，连接服务器周期性刷新 Redis 键 `user:X:online`，设短 TTL（例如 60 秒）。每 30 秒服务器发送一次心跳刷新。如果客户端连接干净断开（用户关闭应用），服务器收到断开通知并立即删除键。但移动网络不可靠——连接可能在无通知情况下丢失（手机进隧道、没电、OS 杀应用）。此时服务器永远收不到断开事件。没有 TTL，用户将永远显示在线。有 TTL 后，键在 60 秒无心跳后过期，标记用户离线。60 秒的 presence 陈旧窗口是可接受的权衡：替代方案（更快检测断开）需要更频繁心跳，增加 Redis 写入负载和移动设备耗电。
