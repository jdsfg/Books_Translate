#### 应用问题

**Q1.** SocialSnap 工程团队正在决定是否把 User Service 拆成两个独立服务：个人资料服务（处理用户个人资料和设置）和认证服务（处理认证和会话管理）。他们应问哪些问题来判断这次拆分是否值得？拆分引入哪些权衡？

提示

思考耦合、团队 owning 和部署独立性。服务间通信方式需要改变什么？会引入哪些新故障模式？

**答案：** 应问的问题：(1) 个人资料数据和认证数据是否以不同速率或因不同原因变化？认证（登录会话、凭证）安全关键且对变化敏感；个人资料数据（用户名、简介、照片）对产品功能敏感。不同变化速率暗示不同服务。(2) 不同团队是否负责这些职责？若安全团队拥有认证、产品团队拥有个人资料，拆分遵循自然团队边界——主动应用康威定律。(3) 是否有显著运营差异？认证需要始终高可用性（availability）（登录失败是灾难性的）；个人资料数据可容忍短暂中断。不同 SLO 暗示不同服务。(4) 是否有性能差异？认证在每次 API 调用的关键路径上（每次调用都验证令牌）；个人资料数据不需要那么频繁。认证可能受益于不同缓存策略。拆分的权衡：好处：独立部署；安全团队可在不涉及产品团队的情况下迭代认证；可为每个服务设置不同可靠性目标；不同 on-call 轮值。成本：认证调用个人资料或 vice versa 时新增网络 hop；分布式追踪现在覆盖两个服务；任一服务故障都需要仔细降级设计（认证宕机时 User Service 显示什么？）；两个数据库管理；两条部署流水线。对安全与产品职责明确分离的 80 人团队，这次拆分可能值得。

**Q2.** SocialSnap 团队决定因性能原因把通知服务从 Python 重写成 Go。设计一个 strangler fig 迁移计划，让他们能在生产流量中验证新的 Go 服务，同时保持即时回滚能力。

提示

思考如何同时把流量路由到两个服务、如何验证正确性、回滚长什么样。考虑通知服务的具体角色——它发送邮件和推送通知。
