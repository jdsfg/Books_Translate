#### Join 的力量

关系模型的强大之处在于，你可以通过 **join（连接）** 表来回答复杂问题——基于匹配键值把它们的行组合起来。

“给我看 Alice 的所有帖子，连同 Alice 的用户名：”

    SELECT users.username, posts.content, posts.created_at
    FROM posts
    JOIN users ON posts.user_id = users.id
    WHERE users.username = 'alice'
    ORDER BY posts.created_at DESC;

这条查询：

1. 从 `posts` 取所有行
2. 把每个帖子 join 到 `users` 中匹配的行（`user_id` 等于 `id`）
3. 过滤出 Alice 的帖子
4. 返回用户名、内容和创建时间

你没有写循环。你没有遍历树。你声明你想要什么，数据库自己想办法取回。这就是关系型数据库的魔力——**声明式查询**运行在**灵活 schema** 之上。

在理解它为什么快（索引）以及为什么最终崩溃（规模）之前，我们先看看 SQL 是如何执行的。


### 5.2 幕后——SQL 查询如何执行

当你发出一条 SQL 查询到结果返回之间实际发生了什么——为什么根据查询写法不同，毫秒级差异可达百万倍？

运行 SQL 查询时，数据库并不会简单地读每一行再过滤。它使用**查询优化器（query optimizer）**——一段为你的查询寻找最高效执行计划的软件。理解查询执行的基础，能解释为什么有些查询快、有些查询灾难性慢。


#### 朴素方法：全表扫描

假设你运行：

    SELECT * FROM posts WHERE user_id = 1;

没有任何特殊结构时，数据库读取 `posts` 表的每一行，检查 `user_id = 1`。对 100 万行的表，就是 100 万次比较。1 亿行就是 1 亿次比较。

这就是**全表扫描（full table scan）**。它正确但慢。如果帖子存在磁盘上（每次读取约 10ms 寻道），每页存 1000 行，那么扫描 1 亿行需要 100,000 页 × 10ms = 1,000 秒。

这对 Web 应用显然不可用。修复方案：索引（index）。
