### 5.4 SocialSnap v1——加入关系型数据库

让我们把所有这些应用到给 SocialSnap 第一个真正的数据库。架构从：


    [ Browser ] ──HTTP──> [ Flask App + in-memory dict ] (one machine)


升级到：


    [ Browser ] ──HTTP──> [ Flask App ] ──SQL──> [ PostgreSQL ] (one machine)


仍然是一台机器，但现在数据在重启后持久化，并且可以灵活查询。

**SocialSnap v1 schema：**

    CREATE TABLE users (
        id          SERIAL PRIMARY KEY,
        username    VARCHAR(50) UNIQUE NOT NULL,
        email       VARCHAR(255) UNIQUE NOT NULL,
        password_hash VARCHAR(255) NOT NULL,
        follower_count INTEGER DEFAULT 0,
        following_count INTEGER DEFAULT 0,
        created_at  TIMESTAMP DEFAULT NOW()
    );
    
    CREATE TABLE posts (
        id          SERIAL PRIMARY KEY,
        user_id     INTEGER REFERENCES users(id) ON DELETE CASCADE,
        content     TEXT NOT NULL,
        like_count  INTEGER DEFAULT 0,
        created_at  TIMESTAMP DEFAULT NOW()
    );
    
    CREATE TABLE follows (
        follower_id INTEGER REFERENCES users(id) ON DELETE CASCADE,
        followed_id INTEGER REFERENCES users(id) ON DELETE CASCADE,
        created_at  TIMESTAMP DEFAULT NOW(),
        PRIMARY KEY (follower_id, followed_id)
    );
    
    CREATE TABLE likes (
        user_id     INTEGER REFERENCES users(id) ON DELETE CASCADE,
        post_id     INTEGER REFERENCES posts(id) ON DELETE CASCADE,
        created_at  TIMESTAMP DEFAULT NOW(),
        PRIMARY KEY (user_id, post_id)
    );
    
    -- Indexes for common queries
    CREATE INDEX idx_posts_user_id ON posts(user_id);
    CREATE INDEX idx_posts_created_at ON posts(created_at DESC);
        CREATE INDEX idx_follows_followed_id ON follows(followed_id);

**为什么这样设计 schema：**

`users` 表上的 `follower_count` 和 `following_count` 是**反规范化计数器（denormalized counters）**——这个计数本来可以通过 `SELECT COUNT(*) FROM follows WHERE followed_id = user_id` 推导，但规模上去后这个查询会变贵。我们直接存储计数，并在每次关注/取消关注时更新它（在事务内）。这是系统设计中一个关键模式的预演：预计算昂贵的聚合。

`follows` 表上的 `PRIMARY KEY (follower_id, followed_id)` 有两个作用：它创建唯一约束（你不能关注同一个人两次），并创建复合索引，让 “Alice 是否关注 Bob？” 能快速查找。

**主页 Feed 查询**——“给 Alice 看她关注的人最近 20 条帖子”：

    SELECT posts.id, posts.content, posts.created_at, users.username
    FROM posts
    JOIN follows ON posts.user_id = follows.followed_id
    JOIN users ON posts.user_id = users.id
    WHERE follows.follower_id = 1  -- Alice 的 user_id
    ORDER BY posts.created_at DESC
    LIMIT 20;

这条查询 join 三张表。如果 `follows.follower_id` 和 `posts.created_at` 上有合适的索引，当 Alice 关注的人数合理（几百人）时，它很快。当 Alice 关注 10,000（1 万）人、她的 Feed 跨越数百万帖子时，join 会变成大型排序操作。我们将在 Feed 案例研究（第 22 章）解决这个问题。
