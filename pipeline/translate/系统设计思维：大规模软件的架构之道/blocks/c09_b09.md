#### gRPC——高性能服务间通信

gRPC 是 Google 开发的高性能 RPC（Remote Procedure Call）框架。它使用 Protocol Buffers（protocol buffer 协议，Protobuf）做序列化——一种二进制协议格式，比 JSON 紧凑得多、解析更快。

gRPC 的 Protobuf 服务定义示例：


    service UserService {
      rpc GetUser (GetUserRequest) returns (User);
      rpc UpdateBio (UpdateBioRequest) returns (User);
    }

    message GetUserRequest {
      int64 user_id = 1;
    }

    message User {
      int64 id = 1;
      string username = 2;
      string bio = 3;
    }


基于这个定义，gRPC 自动生成多语言（Go、Python、Java、Node.js 等）的客户端和服务器代码。客户端调用 `userService.GetUser(request)` 并返回 `User` 对象——就像调用本地函数一样。

**gRPC 的优点：**

* 极快：二进制 Protobuf 序列化比 JSON 小 3-10 倍，解析更快
* 强类型：schema 定义每个字段和类型；类型不匹配在编译时捕获
* 自动生成客户端代码：无需手动构造 HTTP 客户端或解析 JSON
* 内置流支持：gRPC 支持 HTTP/2 上的服务端流、客户端流和双向流
* 极适合微服务架构中的服务间通信

**gRPC 的缺点：**

* 二进制格式人类不可读——调试需要工具
* 浏览器支持有限（gRPC 需要 HTTP/2 特性，浏览器仅通过 gRPC-Web 部分支持）
* Protocol Buffers schema 管理需要工具
* 对简单外部 API 杀鸡用牛刀

**何时选 gRPC：** 内部服务间通信，性能重要且两端都由你控制。在微服务架构中，用户服务、帖子服务、通知服务每秒互相调用数千次——gRPC 在如此体量下相对 REST 的性能优势显著。


#### 侦探的选择——读取 API 线索

回想第 3 章线索 C（侦探的纪律）。API 风格选择直接取决于读取访问模式线索：

**线索：外部 API，由第三方开发者消费** → REST。它通用、文档完善、与 HTTP 工具友好。

**线索：许多不同客户端（Web、iOS、Android、智能电视）需要相同数据的不同形态** → GraphQL。它消除了“为每个客户端建不同端点”的问题。

**线索：内部服务间高频调用** → gRPC。性能和强类型值得设置成本。

**线索：简单 CRUD 操作，API 表面小且稳定** → REST。GraphQL 的复杂度不合理。

**线索：实时双向通信** → WebSocket（标准 REST、GraphQL、gRPC 形式都不是，尽管 gRPC 流是一个选项）。

大多数生产系统使用多种：REST 供公共消费者，gRPC 供内部服务，WebSocket 供实时功能。
