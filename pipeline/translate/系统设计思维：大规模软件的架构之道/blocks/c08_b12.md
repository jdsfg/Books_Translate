#### 应用问题

**Q1.** SocialSnap 想增加“帖子被赞”通知：当 Alice 点赞 Bob 的帖子，Bob 在通知中心收到通知。这是高容量事件（每天数百万赞）。用消息队列为该功能设计消息流。包括：事件 schema、谁发布和谁消费、你会选择哪种投递保证、以及如何处理幂等性要求。

提示

想想通知服务需要哪些信息来构建 Bob 的通知。然后想故障情况：如果通知被投递两次，Bob 会看到两条“Alice 赞了你的帖子”通知吗？

**答案：**

**事件 schema：**


    {
      "event_type": "post.liked",
      "event_id": "evt_a7f2b9c1",
      "timestamp": "2024-03-15T14:23:01Z",
      "actor_user_id": 42,
      "target_user_id": 7,
      "post_id": 1001,
      "like_id": 88921
    }


`event_id`（UUID）是幂等性 key。`like_id` 是数据库中点赞的主键——也对去重有用。

**生产者：** SocialSnap 应用服务器中的“点赞”API 端点。当 Alice 点赞帖子时，服务器：

1. 在 `likes` 表中插入一行（含 `like_id`）
2. 发布 `post.liked` 事件到消息队列
3. 向 Alice 的客户端返回 HTTP 200

**消费者：** 通知服务，读取 `post.liked` 事件并：

1. 为 Bob（`user_id=7`）创建通知记录
2. 如果 Bob 在线，推送通知计数更新（通过 WebSocket，第 9 章会讲）

**投递保证：** 至少一次。我们不能丢失点赞通知（用户会注意到通知缺失）。 duplicates 在适当幂等性下可接受。

**幂等性设计：**

通知服务在插入前检查：


    INSERT INTO notifications (user_id, type, source_event_id, post_id, actor_id)
    VALUES (7, 'post_liked', 'evt_a7f2b9c1', 1001, 42)
    ON CONFLICT (source_event_id) DO NOTHING;


`source_event_id` 列有唯一约束。同一事件处理两次时，第二次 `INSERT` 静默什么都不做。这是幂等插入——数据库级唯一约束无需显式先检查后行动代码就强制幂等。

这种用事件 UUID 作幂等性 key 加数据库唯一约束的模式，是生产安全的幂等消息处理方法。

**Q2.**（联系第 7 章陈旧性讨论）SocialSnap 工程团队争论：“post liked”通知消费者更新 Redis 计数器（`user:{user_id}:notification_count`）以在 UI 显示未读通知。一个工程师说：“通知到达时我们也应该使用户缓存的资料失效，这样资料页才能显示正确通知数。” 另一个说：“通知计数不存在资料缓存里——它们是分开的。” 谁对？关于缓存 key 设计有什么更广泛的教训？

提示

想想每个缓存 key 实际存什么。资料缓存（第 7 章）存哪些字段？通知计数属于那里吗？这暗示了粒度该如何？

**答案：** 第二个工程师对。这个争论揭示缓存 key 设计的关键原则：**缓存 key 应限定在单一、内聚的数据片段**。
