#### 应用问题

**Q1.** 某拼车服务在主要大都市区有 50 万（500,000）活跃司机，每人每 4 秒更新一次位置。估算位置追踪系统所需吞吐和存储容量，并设计处理该负载的 Redis 集群拓扑。

提示

先计算写入吞吐，再计算每个司机键的存储，再计算所需集群大小。记住每个 Redis 节点每秒约处理 50 万（500,000）操作，每节点通常 64–128GB 内存。

**答案：** 写入吞吐：500,000 司机 ÷ 4 秒 = 125,000 写入/秒。每司机存储：`driver:{id}:location` 存 lat（8 字节）、lng（8 字节）、geohash（8 字节）、timestamp（8 字节）≈ 32 字节/键。加上 geohash 索引开销（每个司机出现在一个 geohash 集合中）。总存储估算：500,000 × ~200 字节（含 Redis 开销）= 100 MB——微不足道，远小于单个 Redis 节点内存。吞吐是约束：125,000 写入/秒。单个 Redis 节点 500,000 操作/秒对写入 alone 有充足余量，但还要处理读取（乘客查询附近司机）和 geohash 索引更新（每次位置变化 2 次集合操作 = 3 次总操作）。总操作/秒：500,000 × 3 = 150 万（1.5M）。集群设计：3–4 个 Redis 节点，使用 consistent hashing（第 9 章）跨节点，每节点一个副本以保证可用性。每节点 375,000–500,000 操作/秒——在单节点限制内且有边际。生产设计：使用 Redis Cluster，6 节点（3 主 + 3 副本），每主节点峰值约 500,000 操作/秒。这同时提供写入吞吐和故障转移能力。

**Q2.** 旧金山乘客在动态加价期间（2× 倍数）请求用车。系统匹配到 3 分钟外的一位司机。司机接近过程中，该区域供需比改善，动态加价降到 1×（正常价）。乘客应按请求时锁定的 2× 价格付费，还是按行程开始时 1× 价格付费？设计正确处理且一致的数据模型和业务规则。

提示

思考价格在何时“锁定”，以及锁定价格存在哪里。考虑系统在请求到计费之间崩溃会怎样。
