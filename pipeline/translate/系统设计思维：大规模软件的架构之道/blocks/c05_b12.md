* `users.id` 是代理主键（`SERIAL` 生成自增整数）。它稳定——即使用户改名或改简介，ID 不变，所以 `posts` 中的外键引用仍然有效。
* `posts.user_id` 是引用 `users.id` 的外键。`ON DELETE CASCADE` 子句意味着如果用户账户被删，其所有帖子自动删除——防止孤儿行。
* `image_urls` 存成 PostgreSQL 字符串数组。另一种方案是单独的 `post_images` 表（完全规范化），但对始终与帖子一起读、从不单独查询的简单 URL 列表，数组列在这个规模下是实用选择。

**查询与索引需求：**

    SELECT id, content, image_urls, created_at
    FROM posts
    WHERE user_id = 42
    ORDER BY created_at DESC
    LIMIT 20;

**为什么需要索引：** 如果没有 `user_id` 索引，数据库会执行全表扫描——读取 `posts` 的每一行来找到属于用户 42 的。10 million（1000 万）帖子、10,000（1 万）用户，平均每个用户只有约 1,000 行。数据库读 1000 万行来返回 1000 行——浪费比 10000:1。

`ORDER BY created_at DESC` 又增加第二个问题：即使过滤后，数据库也必须按时间戳排序匹配行，除非索引已经按顺序返回它们。

**最佳索引：** `(user_id, created_at DESC)` 复合索引：

    CREATE INDEX idx_posts_user_created ON posts(user_id, created_at DESC);

这个索引用一个结构服务查询的两部分。数据库找到 B-tree 中 `user_id = 42` 的部分（O(log n)），然后按 `created_at` 降序读取条目（索引里已排序），并在 20 行后停止。查询成本从 O(n)（扫描整张表）降到 O(log n + 20)，与总表大小无关。

这与 5.2 节为 SocialSnap 帖子表引入的复合索引 `(user_id, created_at)` 原理相同。复合索引中选择正确的列顺序（过滤列在前，排序列在后）是许多工程师直到生产环境遇到慢查询才意识到的关键细节。
