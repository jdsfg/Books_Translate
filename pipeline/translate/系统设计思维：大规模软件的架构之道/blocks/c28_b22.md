**答案：** 五个为什么追溯：症状：Feed API p99 延迟超过 10 秒（10 seconds）；负载均衡器健康检查超时；1500 万（15 million）用户 45 分钟（45 minutes）内看到空白 feed。为什么？Feed 查询在 `posts` 表上执行全表扫描，耗尽数据库 CPU。为什么？索引 `posts_user_id_created_at_idx` 缺失——迁移脚本包含了一个非预期的 `DROP INDEX` 语句。为什么？迁移脚本本意删除重复索引，但作者把索引名与主 feed 查询索引搞混。为什么？两个索引名相似（`posts_user_id_idx` 和 `posts_user_id_created_at_idx`），且迁移没有交叉引用生产查询计划。为什么？SocialSnap 的 staging 环境没有运行 `EXPLAIN ANALYZE` 回归测试；迁移只测试了语法正确性，没测试查询计划影响。根本原因：CI/CD 流水线中没有自动查询计划回归测试；staging 无法验证关键索引查询在迁移后仍高效。事后复盘行动项：(1) **在 CI/CD 中添加查询计划回归测试**（负责：Platform 团队，期限：2 周）：每次数据库迁移，流水线对 10 个最高流量查询运行 `EXPLAIN ANALYZE`，若任何查询计划从索引扫描变成顺序扫描，则拒绝迁移。(2) **强制索引命名规范**（负责：Database 团队，期限：1 周）：标准化索引名以编码覆盖列和用途（例如 `posts_by_user_chronological_idx`），使命名混淆不可能。(3) **所有删除对象的迁移需两名工程师审查**（负责：Engineering leads，期限：立即）：包含 `DROP INDEX`、`DROP TABLE` 或 `DROP COLUMN` 的迁移需要 senior 工程师的第二次批准才能合并。(4) **在生产中预迁移 dry-run**（负责：Platform 团队，期限：3 周）：实现迁移影子模式，先在生产副本上运行迁移 SQL 并分析查询计划，再实际执行。这确保索引删除在影响真实用户前被发现。
