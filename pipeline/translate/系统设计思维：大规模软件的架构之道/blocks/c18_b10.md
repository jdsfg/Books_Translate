#### 概念检测

**Q1.** 测试“不稳定（flaky）”是什么意思？为什么不稳定测试在分布式系统 CI 流水线中特别危险？

**答案：** 不稳定测试是指有时通过、有时失败，且与被测代码无关的测试——通常因为它依赖时间（测试假设数据库写 100ms 内完成，但有时需要 150ms）、外部服务可用性，或被其他测试修改的共享测试数据。在 CI 流水线中，不稳定测试很危险，因为它们侵蚀对测试套件的信任。工程师学会重新运行失败测试而不是调查失败，因为“可能只是不稳定测试”。当真正的 bug 导致真正测试失败时，它会被重跑并可能碰巧通过——让缺陷到达生产。文化后果比技术后果更糟：频繁误失败的 CI 流水线教会工程师不把测试失败当回事。

**Q2.** 解释蓝绿部署和金丝雀部署在管理部署风险方面的区别。

**答案：** 蓝绿部署通过维护完整并行环境来管理风险：所有流量去一个环境（blue），新版本部署到另一个（green），切换是瞬时的——零用户看到新版本，直到切换后所有用户同时看到。回滚瞬时：切回 blue。风险是二元的：要么所有用户在旧版本，要么所有用户在新版本。

金丝雀部署通过逐步把一小部分流量切到新版本来管理风险：1% 用户看到新版本，如果他们指标良好，再 5%，然后 10%，等等。风险是渐进的：任何时刻，最多 X% 用户暴露于新版本 bug。回滚意味着对新版本路由 0% 流量。蓝绿更适合需要在暴露任何用户前在全生产规模测试的变更（例如性能敏感变更）。金丝雀更适合想观察真实用户行为和指标再下决定的变更。

**Q3.** 为什么数据库 schema 迁移是部署中最难的部分，expand-contract 模式为什么比直接 schema 变更更安全？

**答案：** 直接 schema 变更危险，因为数据库 schema 是运行中的应用代码与存储数据之间的共享状态。如果你在数据库里重命名列，而运行中的应用代码仍查询旧列名，每个查询都会失败——可能瞬间影响所有用户。回滚需要反向重跑迁移，如果数据已按新 schema 写入，这可能不可能。

expand-contract 模式更安全，因为它同时保持旧和新 schema 状态有效，允许旧代码和新代码在迁移窗口期间共存。应用可以部署、回滚、再部署，而没有任何状态不一致。代价是迁移需要几天或几周内分三次单独部署，而不是一次。这对高可用系统是值得的，因为即使短暂查询失败也不被接受。这种安全与速度的取舍是部署中的典型权衡（tradeoff，权衡）。
