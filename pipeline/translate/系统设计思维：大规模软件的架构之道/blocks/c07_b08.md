#### 第一个陈旧性缺陷

SocialSnap v2 上线后表现很好。数据库负载大幅下降，延迟改善，原本会压垮 v1 的病毒式流量尖峰现在被缓存吸收。

但随后收到一个缺陷报告。用户 Carlos 在 14:07 更新了他的简介。他的朋友 14:08 访问他的资料，看到的是旧简介。到 14:13（TTL 过期后），所有人都看到新简介。

这是缺陷吗？严格来说，缓存按设计工作。`update_user_profile` 函数在资料更新时会使缓存失效。但报告揭示了一个微妙之处：Carlos 用手机应用更新简介，而手机应用使用不同的代码路径，它更新了数据库但没有使 Redis 缓存失效。

这是 SocialSnap 历史上第一个陈旧性缺陷。但不会是最后一个。

修复办法是确保所有修改用户数据的代码路径都使相关缓存 key 失效。但这次事故揭示了关于缓存的基本事实：**给系统加缓存不只是性能改动——它是一项架构改动，会创造一类新的正确性缺陷。** 任何写入数据库的代码路径都必须同时管理缓存状态。

这就是为什么工程师有时说计算机科学只有两个难题：缓存失效和命名。


#### “缓存失效”到底是什么？

缓存失效是确定缓存值何时已变陈旧并采取行动的问题。挑战在于，“陈旧”并不总是显而易见：

* Carlos 的简介更新：写入后缓存立即陈旧
* 热门帖子列表：随着新帖子创建和点赞而变陈旧
* 汇率：市场每次变动就变陈旧
* 渲染好的 HTML 页面：当它的任何数据源变化时变陈旧

越难检测陈旧性，失效就越难。对简单实体更新（用户资料、帖子内容），失效很直接：实体变化时删除缓存 key。对派生数据（热门列表、聚合统计、推荐结果），失效需要知道哪些缓存条目依赖哪些底层数据——而这个依赖图可能很复杂。

TTL 是逃生舱：如果失效逻辑太复杂，就设短 TTL。数据不会完全新鲜，但绝不会比 TTL 更旧。对新鲜度要求宽松的数据（如计数、热门列表），这通常是务实的正确选择。
