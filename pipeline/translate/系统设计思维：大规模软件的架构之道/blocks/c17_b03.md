#### 定义：SLO——服务等级目标

**服务等级目标（Service Level Objective，SLO）** 是 SLI 的目标值。它是工程团队对自己承诺的服务应达到怎样的水平。

通俗语言：SLO 是你要命中的数字——“99.9% 请求成功”或“p99 延迟低于 200ms”。它是内部的，不是合同。

例子：

* “99.9% HTTP 请求应返回非 5xx 响应”——可用性 SLO
* “99 百分位延迟应低于 200ms”——延迟 SLO
* “feed 中不应有超过 60 秒陈旧的帖子”——新鲜度 SLO

SLO 不是完美目标。为每个端点设置“99.999% 成功率”适得其反——它要求运营完美，成本压垮。SLO 应足够雄心勃勃以确保用户满意，但又要现实到无需英雄式努力就能达成。


#### 定义：SLA——服务等级协议

**服务等级协议（Service Level Agreement，SLA）** 是服务提供商与客户之间的合同，定义 SLO 未达成时的后果。SLA 是外部的；SLO 是内部的。SLA 通常承诺得比内部 SLO 略低，以便服务触发罚金条款前留有余量。

通俗语言：SLA 是你对客户有法律承诺的东西，违反会有财务或法律后果。它总是设置得比内部 SLO 宽松，这样内部目标略有下滑时合同才被破坏。

如果 SocialSnap 在 SLA 中向企业客户承诺 API 99.9% 可用性，内部 SLO 可能目标 99.95%——留出 0.05% 缓冲，避免违反合同义务。


#### 错误预算

SLI/SLO 框架产生的最有力概念：**错误预算（error budget）**。

如果你的可用性 SLO 是 99.9%，那么你有 0.1% 请求——你的错误预算——允许失败。在 30 天、10 亿（1 billion）请求的月份里，预算是 100 万（1 million）次允许失败。

如何花费这个预算是业务决策。如果你激进地发布新功能——每天部署多次——你会更快消耗预算，因为每次部署都带一些引入失败的风险。如果你处于“稳定模式”，则通过谨慎部署节省预算。

错误预算在开发团队（想发功能）和可靠性团队（想降低风险）之间创造了共同激励。预算健康时，开发团队可以激进部署。预算快耗尽时，组织放慢部署直到预算补充。错误预算不是惩罚——它是一种量化的许可结构。


#### 常见误解

常见错误是把 SLI、SLO、SLA 混为一谈——把它们当作不同正式程度的同一个东西。它们服务的根本目的不同：

* SLI 回答“我们如何衡量质量？”
* SLO 回答“我们目标是什么质量？”
* SLA 回答“我们向客户承诺了什么质量，有什么后果？”

另一个常见错误是为所有可想象的指标设 SLO。实践中，每个服务三到五个精心选择的 SLO 远比二十个没人监控或行动的 SLO 有用。选择直接代表用户体验的 SLO：用户收到响应了吗？够快吗？数据正确吗？
