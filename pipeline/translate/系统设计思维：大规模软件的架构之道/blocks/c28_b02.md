#### 逆康威机动

如果康威定律是描述，那么 **Inverse Conway Maneuver** 就是处方：有意按照你想要的架构来 structuring 你的组织。

如果你想要一个具有清晰服务边界的微服务架构，就先把团队围绕这些服务边界组织起来——在写代码之前。每个团队拥有一个服务，与其他团队有清晰的 API 契约，并独立部署。最终涌现的架构将与你建立的组织结构匹配。

SocialSnap 在 v6 有意识地这样做：在把单体分解为微服务之前，CTO 围绕预期的服务边界重组团队。Feed Team、User Team、通知 Team 和帖子团队成立。然后，每个团队的第一个项目就是从单体中提取自己的服务。最终的服务与团队边界干净地映射——因为团队结构正是为了产生这种架构而设计的。

这一机动有一个识别架构问题的推论：如果系统在特定接口处长期存在集成问题——跨越两个组件的缺陷、需要同时改变两者的性能问题、突破所谓清晰边界的安全事件——调查团队结构是否也跨越了同一边界。两个组件之间接口处的混乱架构往往反映了同一边界上团队沟通的混乱。


#### 常见误解

关于康威定律的一个常见误解是它是一种缺陷——需要克服的东西。事实上，它是一个有用的信号。感觉自然且易于维护的架构边界通常反映了真实的组织边界。不断被违反的架构边界——每个功能都需要改动两侧——通常反映了与组织实际结构不匹配的人为划分。反过来读康威定律，可以诊断组织失调。
