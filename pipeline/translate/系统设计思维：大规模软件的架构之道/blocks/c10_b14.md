这种架构意味着 SocialSnap 应用服务器在初始上传后不处理任何视频字节。所有视频带宽都走对象存储 → CDN → 用户浏览器。

**Q2.**（联系第 5 章索引讨论和第 7 章缓存）SocialSnap 把用户头像照片的对象存储 URL 存在 PostgreSQL `users` 表的 `photo_url` 列。该列包含在第 7 章的资料缓存中（key `user:{id}:profile`）。用户更新头像时，确保以下目标的正确操作顺序是什么：(a) 新照片已存储，(b) 数据库有正确 URL，(c) 缓存失效，(d) 旧照片最终被清理？指出每步可能出错的故障场景。

提示

想想部分失败：如果数据库写入成功但缓存失效失败会怎样？如果对象存储上传成功但数据库更新失败？把操作排序，以最小化用户可见不一致窗口。

**答案：**

**正确操作顺序：**


    1. 上传新照片到对象存储（key: users/42/photo_v4.jpg）
    2. 更新 PostgreSQL 的 users.photo_url 为新 URL
    3. 使 Redis 缓存 key user:42:profile 失效
    4. （异步，通过消息队列）从对象存储删除旧照片


**为什么这个顺序重要：**

第 1、2 步必须在第 3 步之前。如果我们先使缓存失效，然后数据库更新失败，下一次读取会缓存未命中，然后从数据库读到旧 URL，再把旧 URL 重新缓存——缓存“修好”了，但带着陈旧数据。先更新数据库，可保证权威存储在缓存失效前总有新 URL。

**故障场景：**

**第 1 步失败（对象存储上传失败）：** 操作在这里停止。用户看到错误。数据库仍有旧照片 URL。缓存未失效。这是干净失败——正确行为。

**第 2 步失败（数据库更新失败）：** 新照片已在对象存储，但数据库仍指向旧照片。用户看到错误。缓存未失效。对象存储中的新照片成为“孤儿”——无人引用。一个 eventually 清理作业（列出没有对应数据库条目的对象存储 key）会删除它。这就是最终一致性的定义：对象存储和数据库暂时不一致，但后台进程会协调它们。

**第 3 步失败（缓存失效失败）：** 数据库已有新 URL，但 Redis 缓存仍有旧 URL。用户在 TTL 分钟内会看到旧照片。这正是 SocialSnap 在第 7 章遇到的陈旧性 bug。缓解：重试缓存失效；使用短 TTL 作为安全网（即使失效失败，旧 URL 缓存最终也会过期）。

**第 4 步（异步清理旧照片）：** 因为这步通过消息队列异步（第 8 章），失败不影响用户体验。如果删除消息丢失，旧照片会无限期留在对象存储。一个独立的“孤儿对象清理”作业（比较对象存储 key 与数据库 URL）可以发现并删除真正的孤儿对象。
