#### 方案 1：对 URL 做哈希

取长 URL，计算哈希（MD5 或 SHA-256），取前 7 个 base-62 字符。

乍看很吸引人：同一 URL 总是生成同一短码，这是有用属性（同一 URL 不会重复）。但它有严重问题：

**哈希冲突：** 两个不同 URL 可能产生相同 7 字符哈希前缀。按每天 1 亿 URL 和 3.5 万亿可能码，使用生日悖论的预期冲突率是：大约 √(3.5 万亿) ≈ 187 万（1.87 million）个 URL 后，至少一次冲突的概率超过 50%。到 1 亿 URL 时，冲突几乎确定。我们需要冲突处理。

**冲突解决：** 检测到冲突时（短码已存在另一个长 URL），可追加计数器或重新哈希。这可行但增加复杂度，并要求每次 URL 创建都查数据库。


#### 方案 2：自增计数器

维护全局计数器。每个新 URL 获得下一个计数器值，编码为 base-62（BASE）。计数器值 1 → "0000001"，计数器值 61 → "000000z"，计数器值 62 → "000001"。

保证唯一（构造上无冲突）。问题：单一全局计数器在 1,157 写/秒下是瓶颈。更重要的是，顺序码泄露系统创建速率——竞争对手可以看到 “abc1234” 在 T1 创建、“abc1238” 在 T2 创建，推断该窗口内创建了 4 个 URL。排序短码还泄露创建顺序，用户可能不希望。


#### 方案 3：预生成码池

提前生成所有可能的 7 字符 base-62（BASE）码（或批量生成），洗牌，存入“未用码”池。URL 创建时从池中 pop 下一个码。每个码只用一次。

保证唯一。无需冲突检查。码是随机的（非顺序）。池可分布式：多个应用服务器可从池中批量请求码（例如一次 1,000 个），减少码生成器上的竞争。每台服务器用完自己的批次再请求新批次。

这是大多数生产 URL 短链服务采用的方法。一个独立的“码生成器”服务管理池。它定期批量生成新码，写入队列，应用服务器从队列中批量拉取。


#### 方案 4：随机码 + 冲突检查

生成随机 7 字符 base-62（BASE）码。检查数据库中是否已存在。如果存在，再生成一个随机码并重复。

实现简单。对任何一次生成尝试，冲突概率是 `current_database_size / 3.5_trillion`。当数据库有 100 亿 URL（按当前速率 100 年增长）时，概率仍只有 10B / 3.5T ≈ 0.3%。实践中几乎所有码生成都能一次成功。

成本：每次 URL 创建一次数据库检查——存储 URL 本来就要做，所以开销只是变成一次读的写。对不需要预生成码的系统，这是最简单的正确方案。

本设计采用**方案 4（随机码 + 冲突检查）**作为基础，如果创建吞吐需要，可以迁移到方案 3（预生成池）。在 1,157 次创建/秒下，方案 4 完全可行。
