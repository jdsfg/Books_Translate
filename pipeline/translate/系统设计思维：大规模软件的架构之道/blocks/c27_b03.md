#### v4 —— 第 11 章：水平扩展（第 9–15 个月）

**它是什么：** 三台应用服务器在负载均衡器（Nginx）后。会话从服务器本地内存移到 Redis。团队发现“只加服务器”要求应用设计成无状态。

**关键决策：**

* 基于 JWT 的会话 token 用于认证（无状态——token 包含用户 ID 并通过加密验证）
* 或服务器端 Redis 会话（集中状态，但快速）
* 团队最终两者都用：JWT 用于读多 API 调用，Redis 会话用于需要立即撤销的管理操作

**为什么正确：** 三台应用服务器使高峰 CPU 利用率降至 30%。负载均衡器增加健康检查——一台服务器崩溃时，30 秒内流量绕开它。

**第一次故障：** 向水平扩展迁移期间，团队因负载均衡器配置错误导致 45 分钟故障，所有流量被路由到一台服务器。这是 SocialSnap 第一次生产故障，也让团队开始接触 post-mortem（第 28 章详述）。

**技术债务：** 数据库现在成为单一瓶颈——三台应用服务器产生的数据库负载超过单个 PostgreSQL 实例能处理的。

**变革信号：** PostgreSQL CPU 达 95%。日志中出现慢查询。值班工程师每周两次被告警数据库性能。


#### v5 —— 第 12 章：数据库扩展（第 15–24 个月）

**它是什么：** 添加 PostgreSQL 读取副本（最初两个）以卸载读查询。随着写负载增长，users 表被分片——SocialSnap 数据首次跨多个数据库分割。

**关键决策：**

* 读取副本用于 feed、profile 读取和搜索查询
* 所有写入使用一个主库
* 分片键选择：`user_id mod 8` —— 用户分布在 8 个数据库分片
* 团队尽可能推迟分片（副本在分片不可避免前支撑了 6 个月）

**分片创伤：** 实现分片是团队做过的最艰难的工程项目。跨分片查询（如“找出所有关注用户 X 的用户，而 X 和其关注者可能在不同分片”）需要应用层 join 逻辑。团队花了 3 个月完成这次迁移，包括 6 小时维护窗口执行数据迁移。

**为什么等待：** 分片增加巨大运营复杂度。团队在绝对必要时才做，这是正确的。规则：只在更简单的方案 demonstrably 不足时才增加复杂度。

**技术债务：** 分片键选择（`user_id mod 8`）意味着以后加更多分片需要重新映射所有键（mod 8 变 mod 16，每个键可能改变分片）。团队本应从一开始就使用一致性哈希——但当时他们还不知道。

**变革信号：** 单体变得难以部署——通知代码中的 bug 需要部署整个应用，包括关键 feed API。部署时间 15 分钟；部署期间系统降级。
