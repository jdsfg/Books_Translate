#### 自定义别名

用户可以请求自定义别名（`short.ly/my-brand`）。自定义别名与生成码存在同一张表。创建自定义别名时，系统检查是否已被占用。如果是，返回错误（别名已被占用）。自定义别名完全绕过码生成——用户提供码，系统验证并存储。

安全考虑：自定义别名不能允许用户声明与系统保留路径（`/api（API）`、`/admin`、`/login`）冲突的码。维护保留路径黑名单，并在创建别名时检查。


#### 常见误解

**"随机 base-62（BASE）码在实践中永远不会冲突。"**

这过于乐观。62^7 ≈ 3.5 万亿个可能码，冲突看似遥远——但生日问题讲了不同故事。生成大约 √(3.5 万亿) ≈ 190 万（1.9 million）个码后，至少一次冲突的概率就超过 50%。按 1000 次 URL 创建/秒，运营不到 32 分钟就跨过该阈值。修复方法不是依赖随机性，而是预生成并洗牌码（从池中移除保证唯一），或使用计数器方案（自增 ID 转 base 62）使冲突在结构上不可能。纯随机生成需要冲突检测和重试逻辑——增加延迟和复杂度。设计短链服务时，绝不要没有这些保证之一。


### 20.3 系统设计——逐层搭建

现在我们有足够信息设计系统。我们将逐层构建，从最简单设计开始，只在证据要求的地方增加复杂度。


#### 第 1 层：核心数据模型

两张表。从显然的开始：

**`urls` 表**（核心）：

* `short_code` (VARCHAR(16), PRIMARY KEY) — 短码或自定义别名
* `long_url` (TEXT, NOT NULL) — 目标 URL
* `created_at` (TIMESTAMP, NOT NULL)
* `expires_at` (TIMESTAMP, NULLABLE)
* `created_by_ip` (INET) — 用于限流
* `user_id` (BIGINT, NULLABLE) — 如果用户已认证

**`clicks` 表**（分析）：

* `id` (BIGINT, AUTO-INCREMENT PRIMARY KEY)
* `short_code` (VARCHAR(16), NOT NULL, FK → urls)
* `clicked_at` (TIMESTAMP, NOT NULL)
* `referrer` (TEXT, NULLABLE)
* `user_agent` (TEXT, NULLABLE)
* `country_code` (CHAR(2), NULLABLE)

`urls` 表是事实来源。`clicks` 表是分析存储。立刻产生一个问题：它们应在同一个数据库吗？

116,000 次重定向/秒，每次产生一次 `clicks` 插入，`clicks` 表每秒收到 116,000 次写入。这对关系型数据库来说是非常高的写速率。相比之下，`urls` 表只有 1,157 次写入/秒——完全可管理。

把高写入分析与低写入核心数据放在一起会产生问题：分析写入消耗写 I/O 预算，可能拖慢 `urls` 表的读延迟。把它们分开——`urls` 放在写优化的主数据库，`clicks` 放在高写入存储（时序数据库或 Kafka topic  feeding 数据仓库）——才是正确架构。

初始设计中，我们使用同一个数据库，但让 `clicks` 写入异步（通过队列），不阻塞重定向路径。
