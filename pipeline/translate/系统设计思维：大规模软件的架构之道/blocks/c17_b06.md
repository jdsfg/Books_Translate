### 17.3 分布式追踪——在分布式系统中跟踪一次请求

指标和日志回答不同问题。指标回答“多少？”和“多频繁？”。日志回答“发生了什么细节？”。但还有一个问题两者都不能完整回答：“这次特定请求的端到端路径是什么，它把时间花在哪里？”

SocialSnap 早期单体架构（第 1 章）中，回答这个问题很容易：一个进程，一个日志文件。但到了第 13 章的微服务架构，单次用户请求加载 news feed 可能调用五个服务：

1. API Gateway——接收请求，通过 Auth Service 认证用户
2. Auth Service——验证 JWT token
3. Feed Service——决定展示哪些帖子
4. Post Service——为每个 post ID 拉取帖子内容
5. User Service——为每个帖子拉取作者资料

每个服务都有自己的日志。如果请求慢，你需要知道哪个服务贡献了延迟。如果请求失败，你需要知道哪个服务返回错误。没有关联机制，你得在五股不同日志流中猎取，脑中重建时间线。

**分布式追踪（distributed tracing）** 通过在所有服务调用中传播 **trace ID** 来解决。


#### 定义：分布式追踪

**分布式追踪（distributed trace）** 是单次请求通过分布式系统的端到端旅程记录。它由 **spans** 组成——每个 span 是一个工作单元，带开始时间和持续时间——以树形结构组织，每个 span 可能有子 span 代表下游调用。

plain 语言：追踪是一个完整时间线，准确显示哪些服务按什么顺序处理请求、每一步花多久—— stitched together 跨越触碰请求的每个服务。

以下是 SocialSnap feed 请求追踪的文本形式示例：


    Trace ID: abc123
      [0ms - 245ms]  API Gateway: handle GET /feed
        [5ms - 20ms]   Auth Service: validate_jwt (15ms)
        [22ms - 240ms] Feed Service: get_feed (218ms)
          [25ms - 50ms]  Redis: get cached_feed (25ms) → MISS
          [52ms - 200ms] Post Service: fetch_posts (148ms)
            [55ms - 80ms]  Database: SELECT posts WHERE id IN (...) (25ms)
            [85ms - 195ms] User Service: fetch_authors (110ms)
              [88ms - 190ms] Database: SELECT users WHERE id IN (...) (102ms)
          [202ms - 235ms] Redis: set cached_feed (33ms)


这一条追踪讲述了指标无法讲述的故事：总请求耗时 245ms，大部分（148ms）在 Post Service，其中大部分（102ms）等待 User Service 的数据库查询。feed 缓存未命中。知道这些，工程师立刻知道该看哪里：User Service 的数据库查询是瓶颈。
