到目前为止我们讨论的每一种失败都是无意的。硬件失败是因为零件磨损。软件崩溃是因为 bug。网络分区是因为配置错误。级联是因为意外交互。系统不是想失败——它尽管每个人都尽最大努力防止，还是失败了。

安全失败不同。它们由主动、聪明、持续试图让你的系统异常行为的对手造成。研究你 API 的攻击者不在乎你的 SLO。探测你数据库的攻击者不在乎你的部署流水线。窃取用户凭证的攻击者不在乎你的熔断器。

攻击者是反向工作的侦探。第 3 章我们把估算框定为“从线索推理到结论”。第 17 章我们把事故调查框定为“把日志当线索读”。攻击者应用同样纪律——收集关于你系统的线索（API 响应、错误消息、时序信号、开放端口）并推理如何利用它。设计安全系统意味着设计一个从外部难以推理的系统。

本章介绍每个系统设计师必须理解的基础安全概念。它不全面——安全工程有整本专著——但涵盖设计系统时避免幼稚错误所需的词汇和心智模型。


### 19.1 认证与授权——两个不同问题

每个安全系统对每个请求都必须回答两个不同问题：

1. **你是谁？**——认证（Authentication）
2. **你被允许做什么？**——授权（Authorization）

这两个问题听起来相关，但概念和架构上分离。混淆它们是最常见的安全漏洞来源之一。

**认证** 建立身份。当你用邮箱和密码登录 SocialSnap 时，系统认证你：它验证你声称的身份。成功认证后，系统信任带有你凭证的请求来自你。

**授权** 决定权限。SocialSnap 知道你是谁后，必须决定允许你做什么。你可以编辑自己的帖子，但不能编辑别人的。你可以查看公开资料，但不能查看未与你建立联系用户的私密资料。你可以访问 `/feed` 端点，但不能访问 `/admin/users` 端点。


#### 区分具体例子

这个场景说明区分为何重要：

SocialSnap 推出第三方开发者 API。一个开发者构建读取用户公开帖子的应用。用户向 SocialSnap 认证——这建立了身份。但第三方应用不应访问用户的私信、账户设置或代表用户发帖。

认证回答“这是正确用户吗？”——是的。但授权还必须回答“该用户是否授权这个特定应用读取他们的消息？”——没有。没有细粒度授权，任何认证实体都能访问一切，这过于宽松。
