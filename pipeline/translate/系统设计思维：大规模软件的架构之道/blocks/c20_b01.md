我们花了十九章构建词汇表。分布式系统有组成部分：数据库、缓存、队列、负载均衡器、副本、CDN。分布式系统有失败模式：级联、脑裂、热分片、惊群。分布式系统有运营关注点：可观测性、部署安全、安全。我们分别检视了每个领域——缓存是什么、分片如何工作、为什么熔断器必要。

现在词汇表与综合相遇。第五部分关于把所有内容同时应用于真实问题。

第一个问题最简单：设计一个 URL 短链接服务。你给服务一个长 URL，它给你一个短 URL。有人访问短 URL 时，被重定向到长 URL。`bit.ly/xyz123` → `https://www.example.com/very/long/path/that/nobody/wants/to/type`。

每个经历过系统设计面试的工程师都遇到过这个问题。它被认为很简单，是“真正”设计挑战前的热身。这种看法错了。URL 短链接服务简单到你能理解完整设计——没有隐藏——但又足够丰富，几乎触及本书每个概念：容量估算、存储 schema、缓存策略、一致性模型、读写不对称、分析架构和容错。它是观察综合的完美镜头。

在设计任何东西之前，好工程师会仔细倾听问题。第 3 章我们引入了侦探框法：需求是线索，设计师的工作是从线索推理到架构。这里我们把它形式化为可重复格式。


### 侦探简报

**客户：** 一家初创公司想为公众构建 URL 缩短服务，类似 bit.ly。用户通过 Web 界面和 API 缩短 URL。缩短链接将出现在社交媒体帖子、邮件和营销活动中。

**线索（需求）：**

* 用户可以把任何有效 URL 缩短为唯一短码
* 访问短 URL 时浏览器在 100ms 内被重定向到原 URL（越快越好）
* 短码必须唯一——两个不同 URL 绝不能得到相同短码
* 短 URL 默认不过期（某些用户想要可选自定义过期时间）
* 用户可以提供自定义别名（例如 `short.ly/my-brand`）
* 系统应追踪每个短 URL 被点击次数（基础分析）
* 服务对读取公开且无需认证（关注短链接无需登录）
* 需要简单的程序化 URL 创建 API

**约束（证据）：**

* 读多写少：重定向与 URL 创建比例约 100:1——每创建一个 URL 大约被访问 100 次
* 规模：峰值每天创建 1 亿个新 URL；每天 100 亿（10 billion）次重定向请求
* 存储：短 URL 永久——系统必须无限期保留它们（除非明确删除）
* 可用性：重定向应高可用（99.99%）；URL 创建可容忍短暂宕机（99.9%）
* 延迟：重定向延迟是用户可见指标；p99 目标 100ms

**问题：** 什么架构能解释所有这些线索？
