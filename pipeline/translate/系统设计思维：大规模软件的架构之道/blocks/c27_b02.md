#### v2 —— 第 7 章：添加缓存（第 3–6 个月）

**它是什么：** Redis 作为缓存层引入。Profile 查找带 TTL 缓存。第一次陈旧 bug：用户更新了用户名，但缓存版本最多 60 秒仍显示旧名。

**关键决策：**

* Cache-aside 模式：应用先查缓存，未命中回数据库，回写缓存
* Profile 数据 TTL 60 秒
* Redis 部署在独立服务器

**为什么正确：** 1 万（10000）用户时，数据库每分钟收到数千次相同 profile 查询。缓存使数据库负载降低约 80%，响应时间回到可接受水平。

**技术债务：** 缓存失效策略不一致——某些写路径在写入时失效缓存，另一些没有。三个月内，团队遇到影响约 3% 用户的缓存不一致 bug（编辑后用户仍看到旧 profile 数据）。

**调试教训：** 团队花了三天调试这个缓存不一致。修复后，他们确立规则：缓存失效代码必须与写入方法在同一服务方法中。这种纪律只在尝到痛苦后才会出现。

**变革信号：** 邮件通知投递耗时最多 10 秒，因为通知服务阻塞帖子创建 API 调用。用户报告的延迟在上升。


#### v3 —— 第 8 章：用消息队列解耦（第 6–9 个月）

**它是什么：** Celery（Python 任务队列），后端先由 Redis 支持，可靠性要求提高后换成 RabbitMQ。通知发送、邮件投递、feed 更新计算移到异步 worker。

**关键决策：**

* 欢迎邮件、帖子通知、关注通知都变成异步任务
* API 响应再次即时——通知“发后不管”
* Worker 运行在独立服务器，独立可扩展

**为什么正确：** 通知和邮件不应在用户动作的关键路径上。通过队列解耦使团队能独立扩展每个关注点，并让系统对邮件提供商故障有韧性（邮件排队并重试，不丢失）。

**技术债务：** Worker 任务失败开始静默。团队没有对队列深度或任务失败率做充分监控。两周内，一个 subtle bug 导致 15% 欢迎邮件静默失败——团队直到有用户发邮件给客服问为什么没收到欢迎邮件才发现。

**监控教训：** 每个队列都需要监控。队列深度、处理速率、错误率都必须可见。

**变革信号：** 单个应用服务器在高峰时段 CPU 使用率达 90%。添加第二台服务器暴露了 sticky session 问题：用户被随机路由到没有其会话的服务器。
