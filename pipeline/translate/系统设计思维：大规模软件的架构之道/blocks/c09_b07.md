#### WebSocket——全双工实时通信

HTTP 是请求-响应协议：客户端发送请求，服务器返回响应。服务器不能在没有客户端先请求的情况下主动发送数据。

但 SocialSnap 的通知功能需要服务器实时把通知推送给在线用户。当有人点赞 Alice 的帖子，Alice 应该立即看到通知角标更新——而不是等她下次加载页面。

**WebSocket** 提供全双工通信：经过初始 HTTP 握手（把连接升级到 WebSocket 协议）后，客户端和服务器可以随时互相发送消息。连接保持打开。服务器可以在任何时候推送数据。

**HTTP 轮询（不用 WebSocket）：** 客户端每 5 秒发送 `GET /notifications/count` 检查新通知。实现简单，但浪费：99% 的轮询请求发现没有新内容，却消耗服务器资源并增加延迟（通知最多延迟 5 秒才出现）。

**长轮询（long polling）：** 客户端发送 `GET /notifications/count`，服务器在没有新通知前一直挂着连接不响应。新通知到达时服务器立即响应，客户端随即再发一个请求。比轮询好（没有空响应），但仍是单向的（服务器不能独立于客户端请求主动推送）。

**WebSocket：** 客户端打开 WebSocket 连接。当通知产生时（由第 8 章的消息队列 like 事件处理器），通知服务直接通过 WebSocket 推送给 Alice 连接的浏览器。亚秒级延迟。没有轮询开销。

WebSocket 的代价：它们是有状态的长连接。服务器必须为每个连接客户端维护连接状态。100,000 个并发 WebSocket 连接用户意味着单台服务器要管理 100,000 个打开连接——每个都消耗内存。扩展 WebSocket 服务器需要仔细的会话管理（与第 11 章将探讨的有状态会话问题类似）。


### 9.7 REST、GraphQL 与 gRPC——API 设计问题

当两个服务通信时，它们需要约定接口：有哪些操作、用什么数据格式、如何表达错误。这个接口就是 **API（Application Programming Interface）**。

三种 API 风格主导现代系统设计：REST、GraphQL 和 gRPC。选择它们需要第 6 章侦探方法：从访问模式线索推理。
