分析：这显著降低 outage 严重程度。用 500 毫秒超时，每个卡住的 Redis 请求最多占用线程 500 毫秒而不是 30 秒。线程池从每次失败中恢复的速度快 60 倍。如果 Redis 返回 30% 错误，线程被占用 500 毫秒后释放。稳态下，系统处理相同数量并发在途请求所需线程数减少 60 倍。以 200 线程池，用 500 毫秒超时可在池耗尽前处理约 400 请求/秒（200 线程 / 0.5 秒 = 卡住请求吞吐 400 req/s）——相比之下，30 秒超时约 7 req/s。

新问题：如果 Redis 只是慢（高负载而非故障），某些请求确实需要 500–1000 毫秒，500 毫秒超时会造成不必要失败。任何耗时 501 毫秒的 Redis 操作都会返回错误，即使它再过 50 毫秒就能成功。超时调优需要仔细分析 Redis 调用实际延迟分布——把超时设在正常延迟的 99 百分位，而不是任意短值。

最佳修复：熔断器 + 500 毫秒超时。短超时防止部分失败期间线程被长期占用。熔断器在达到失败阈值后打开，消除后续请求的 500 毫秒等待。两者结合，完全防止级联。

**Q3.** 为 SocialSnap 应用服务器设计一个健康检查端点（`/health`）。它应该检查什么、返回什么，以及负载均衡器如何使用这些信息？

提示

区分“应用服务器进程是否运行”与“它是否真能正确服务请求”。

**答案：** 健康检查设计：

**应检查的内容：**

1. **数据库连通性：** 应用服务器能否连接 PostgreSQL 并执行一条简单查询？（`SELECT 1`——返回结果但不触碰用户数据，快速且低影响。）
2. **Redis 连通性：** 应用服务器能否连接 Redis 并执行 `PING`？Redis 对简单连通性检查返回 `PONG`。
3. **线程池余量：** 应用服务器线程池是否低于关键阈值（例如少于 90% 线程在使用）？如果线程占用 > 90%，服务器可能健康但无法接受更多流量。
4. **应用服务器进程状态：** 进程本身是否运行且响应？（HTTP 请求正在被处理本身就 trivially 回答了这个问题。）

**不应检查的内容：** 第三方支付处理器、外部 API 等。应用服务器的健康检查应反映服务器自身服务请求的能力，而不是它无法控制的依赖健康。如果支付处理器宕机，服务器仍能服务 99% 请求——不应被标记为不健康。

**响应格式：**


    {
      "status": "healthy" | "degraded" | "unhealthy",
      "checks": {
        "database": {"status": "ok", "latency_ms": 2},
        "redis": {"status": "ok", "latency_ms": 1},
        "thread_pool": {"status": "ok", "used": 45, "max": 200}
      },
      "timestamp": "2024-01-15T14:47:23Z"
    }


HTTP 状态码：

* 200：healthy 或 degraded（负载均衡器继续路由）
* 503：unhealthy（负载均衡器将其移出轮询）
