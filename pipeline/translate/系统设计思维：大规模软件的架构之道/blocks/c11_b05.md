### 11.4 SocialSnap v4——水平扩展达成

会话存储迁移到 Redis 后，SocialSnap v4 开始运行 3 台应用服务器。

v4 架构：


    Internet
        ↓
    CDN (static assets, public pages)
        ↓
    L7 Load Balancer (round-robin, health checks)
        ↓
    ┌──────────┬──────────┬──────────┐
    │ App      │ App      │ App      │
    │ Server A │ Server B │ Server C │
    └──────────┴──────────┴──────────┘
        ↓           ↓           ↓
        ├───────────┼───────────┤
        ↓           ↓           ↓
     Redis Cache       Redis Session Store
        (cache)            (sessions)
             ↓
        PostgreSQL
             ↓
        Object Storage (photos, videos)
             ↓
        消息队列（通知、邮件）


实践中，“Redis 缓存”和“Redis 会话存储”可以是同一个 Redis 实例，用不同 key 命名空间（`cache:*` vs `session:*`）隔离，也可以是独立实例以获得隔离。独立实例可防止缓存驱逐压力（来自高容量缓存流量）把会话数据挤出去——会话对驱逐比缓存条目更敏感。

每台应用服务器现在相同且可互换。负载均衡器可以把任何请求路由到任何服务器。Server A 因代码部署重启时，负载均衡器通过健康检查把它标记为不健康，把流量路由到 Server B 和 C，等它恢复后再标记为健康。对用户零影响。


#### 扩展到三台以上

有了无状态应用服务器，扩展就像配置更多服务器并把它们注册到负载均衡器那么简单。负载均衡器分发流量；会话存储处理会话连续性；缓存和数据库平等服务所有服务器。

极限在哪里？无状态应用服务器的限制转移到共享组件：**数据库和 Redis 集群**。数据库接收来自 50 台应用服务器的查询，负载是一台应用服务器时的 50 倍。

这是下一个瓶颈——也是第 12 章的主题。目前，SocialSnap v4 可以独立于数据库容量扩展应用服务器容量，这是一个显著的架构改进。
