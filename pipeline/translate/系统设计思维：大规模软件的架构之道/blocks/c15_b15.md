#### 深入思考

**Q1.** 本章指出 saga 中的不可补偿步骤（如发邮件）应尽可能放在最后。这一规则是否总是正确？能否构造一个场景，使该规则与另一重要设计原则冲突？

**讨论：** “把不可补偿步骤放最后”规则在其既定目标上正确：最小化操作后续失败却已发邮件的情况。如果邮件是 3 步中的第 3 步，且第 1、2 步成功，邮件才在完全成功的事务路径上发送。

但该规则可能与**客户沟通与透明性**原则冲突。考虑电商订单 saga：第 1 步信用卡扣款（可退款补偿），第 2 步预留库存，第 3 步发起发货，第 4 步发送“您的订单已下单！”邮件。按规则，邮件在第 4 步（最后）。

但如果第 3 步（发货）失败呢？客户已被扣款，库存已预留，但发货无法启动（仓库系统宕机）。Saga 补偿：退款、释放库存。客户从未收到邮件。他们不知道订单曾被尝试、扣款、然后取消。他们只看到信用卡账单有一笔不明扣款。从客户体验看，第 1 步就发邮件（“我们已收到您的订单，正在处理”）可能更好——尽管它不可补偿。

更深层原则：“把不可补偿步骤放最后”规则对具有永久业务后果的操作（扣款、承担法律义务）正确。对透明性重要的客户沟通，必须权衡沉默带来的客户体验成本。更好的规则：设计 saga，使面向客户的沟通匹配业务状态——先发送“订单处理中”（试探性）邮件，只在所有可补偿步骤成功后才发送“订单已确认”（确定性）邮件。

**Q2.** Saga 编排把流程逻辑集中在一个服务中。怀疑者争论：“这只是重新创建单体里的集中逻辑——我们转向微服务就是为了摆脱这个。编排器知道所有服务太多细节。”评价这一争论。

**讨论：** 怀疑者指出了一个真实张力。一个知道其他五个服务 API、数据模型和失败模式的 saga 编排器确实与它们耦合。如果 Payment Service API 改变，编排器也要改。编排器不能独立于它编排的服务部署。

然而，这个争论混淆了两种不同类型的耦合：

**数据耦合**（微服务中坏的耦合）：服务 A 直接读取服务 B 的数据库，使它们在 schema 层耦合。B 的任何 schema 变更都会破坏 A。这违反“每个服务一个数据库”。

**行为耦合**（工作流协调必要的耦合）：服务 A 知道要完成工作流 W，必须调用服务 B，然后 C，然后 D。这是服务*接口*（API）的耦合，而不是*内部*（数据库）的耦合。接口应该是稳定且带版本的。与 API 耦合可接受；与数据库 schema 耦合不可接受。
