**编排器状态机：** 编排器在自己的数据库中保存 `saga_state` 记录：


    saga_id: "saga_7f3a9b2c"
    user_id: 42
    current_step: "PAYMENT_PENDING" | "USER_PENDING" | "EMAIL_PENDING" | "COMPLETE" | "COMPENSATING" | "FAILED"
    payment_idempotency_key: "saga_7f3a9b2c_charge"
    user_idempotency_key: "saga_7f3a9b2c_upgrade"
    payment_result: null | {charge_id: ..., amount: 9.99}


**幸福路径：**

1. 开始：设置 `current_step = PAYMENT_PENDING`。用幂等键调用 Payment Service。等待（超时 30 秒）。
2. 支付成功：设置 `current_step = USER_PENDING`，保存 `payment_result`。用幂等键调用 User Service。等待。
3. User Service 成功：设置 `current_step = EMAIL_PENDING`。调用通知服务。等待。
4. 邮件已发：设置 `current_step = COMPLETE`。返回成功给轮询客户端。

**失败场景 (a)：支付扣款失败。** Payment Service 返回错误（无效卡、余额不足等）。编排器记录 `current_step = FAILED`。无需补偿——没有任何状态被改变。向客户端返回失败原因。

**失败场景 (b)：支付成功，User Service 不可用。** 编排器设置 `current_step = USER_PENDING`。调用 User Service——超时或报错。编排器以指数退避重试最多 5 次。如果全部失败，转入 `current_step = COMPENSATING`。向 Payment Service 发起退款（幂等键 `saga_7f3a9b2c_refund`）以补偿扣款。记录 `current_step = FAILED`。向客户端返回错误：“您的升级未能完成。任何已扣款项已退款。”

**失败场景 (c)：所有步骤成功后，编排器在标记 COMPLETE 前崩溃。** 重启后，编排器的恢复进程查询所有 `current_step != COMPLETE AND current_step != FAILED` 的 saga。它发现 `saga_7f3a9b2c` 仍处于 `EMAIL_PENDING`（COMPLETE 之前的最后一步）。它重试邮件步骤（使用通知服务的幂等键）。邮件已发送——通知服务的幂等检查返回“已发送”而不发送重复邮件。编排器设置 `current_step = COMPLETE`。Saga 正确完成。

**关键设计决策：**

* 发起调用前先持久化状态转换（以便崩溃恢复知道当前位置）。
* 所有服务调用都使用幂等键（幂等性）保证重试安全。
* 启动时运行恢复进程以恢复被中断的 saga。

**Q3.** 团队正在为 API 实现幂等键（idempotency keys，幂等性）。一位工程师提议：“我们将对请求体做哈希。如果相同请求体发送两次，就检测为重复并跳过处理。”指出该方法至少两个问题。

提示

想想合法的重复请求体，以及两个不同请求恰好有相同请求体会发生什么。

**答案：** 用请求体哈希作为幂等键的问题：

**问题 1：合法重复请求与重试无法区分。** 如果用户 42 升级、取消、再升级，两次升级请求的请求体可能完全相同（相同用户 ID、相同金额、相同操作类型）。两次请求体的哈希相同。第二次升级被误判为第一次重复的请求而永远不处理。用户第二次尝试不会被扣款——计费失败。

**问题 2：有意重试若修改了请求体就会逃避去重。** 如果客户端发送请求后超时未收到响应，给请求体加一个非关键字段（如时间戳）再重试，哈希改变。服务器把这次重试当作新请求处理。重复执行仍然发生。

**问题 3（加分）：哈希冲突，尽管概率极低。** 两个不同请求恰好哈希到相同值会被错误去重。虽然加密哈希冲突极为罕见，但该设计永远依赖这一假设对所有输入成立。

正确做法：客户端用 UUID 或类似高熵随机值生成幂等键，并通过请求头显式传递（例如 `Idempotency-Key: 7f3a9b2c-...`）。键由客户端控制，绑定到特定重试尝试，与请求体无关。服务器存储 key → result。客户端为每次不同操作生成新键，对同一操作的重试复用同一键。
