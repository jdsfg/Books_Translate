**讨论：**

**为什么 PostgreSQL 对该分析工作负载不够：**

PostgreSQL 是面向行的 OLTP（Online Transaction Processing，联机事务处理）数据库。它的存储布局把一行所有列写在一起。对“统计标签为 #systemdesign 且国家为 US 且时间戳在 30 天内的独立用户数”这类分析查询，PostgreSQL 必须读取 view events 表的每一行（或索引覆盖部分），然后在内存中过滤。每秒 50,000 事件 × 86,400 秒 × 30 天 = 约 1300 亿（130 billion）行。在 PostgreSQL 中扫描或索引 1300 亿行需要巨型机器，或耗时数分钟的查询——对分析看板都不可接受。

此外，每秒 50,000 持续写入已接近重度优化 PostgreSQL 实例的上限。在同一数据库上混合高频写入与重度分析读取会同时拖垮两种工作负载：分析查询持有锁并消耗 I/O，与 incoming 写入竞争。

**为什么对象存储（S3）不够：**

对象存储优化了按 key 读取或写入整个对象。“统计标签为 #systemdesign 的独立用户数”这类查询需要读取 bucket 中每个对象（或大范围前缀扫描）并在应用代码中过滤——没有查询引擎、没有索引、没有把过滤下推到存储层。即使批量读取，以每条约 1ms 从 S3 读取 1300 亿（130 billion）事件也需要天文时间。

对象存储适合作为**中间层**——存储原始事件文件（Parquet 或 Avro 格式），由查询引擎批量读取——但不适合作为直接回答查询的层。

**正确架构——列式分析存储：**

这个工作负载属于列式 OLAP（Online Analytical Processing）数据库。例子：Amazon Redshift、Google BigQuery、Spark 或 Trino 查询的 Apache Parquet 文件、ClickHouse。

列式存储把每列单独写。对上述查询，数据库只读取 `user_id`、`tags`、`country`、`timestamp` 列——完全跳过 `post_id` 和其他无关列。配合压缩（同类型列压缩效果好），1300 亿事件可能只占行式存储一小部分空间。而且由于相关列顺序读取而非分散在页面上，I/O 很高效。

**典型管道：**

1. 浏览事件以每秒 50,000 条流经消息队列（Kafka，第 8 章）。
2. 流处理器（Spark Streaming、Flink）从 Kafka 读取，把事件批量写成 Parquet 文件，每几分钟写入对象存储（S3）。
3. 分析数据库（Redshift、BigQuery 或 Athena）在查询时从 S3 读取 Parquet 文件，使用列式访问和谓词下推，在数秒内回答“#systemdesign 按国家浏览量”。
4. 频繁访问的聚合（每个标签的日活跃用户）预计算并存入更小的汇总表，供看板亚秒级查询。

这种架构把高频写入路径（Kafka → 对象存储）与分析读取路径（Parquet 上的列式引擎）分离，避免了会拖垮 PostgreSQL 的争用。本章的存储层级洞察解释为什么：原始事件存在便宜的对象存储；预聚合摘要存在更快（更贵）的列式存储；实时计数器（如果需要）存在 Redis。
