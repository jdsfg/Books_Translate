#### 用户 B 离线时怎么办？

注册表查找发现用户 B 没有活跃连接（离线）。消息服务必须：

1. 持久化消息（上面步骤 2 已完成）
2. 可选，通过 APNs（Apple）或 FCM（Google）向 B 的移动设备发送推送通知，提醒有未读消息

当 B 上线并打开应用，客户端从 API 拉取消息历史以补回漏掉的消息。

关键架构原则：实时推送路径与持久化路径独立。消息总是先持久化；实时投递只是持久化之上的优化。如果实时投递失败（用户离线、连接断开），持久化确保消息永不丢失。


### 21.3 消息存储——Schema 设计问题

聊天数据模型看起来简单：消息有发送者、接收者、内容和时间戳。但读访问模式带来有趣的 schema 挑战。


#### 有哪些查询？

设计 schema 前，先确定访问模式（将侦探纪律应用于数据建模）：

1. **加载对话历史：** 给定用户 A 和用户 B，获取他们之间最近 50 条消息，按时间戳降序。
2. **加载收件箱：** 给定用户 A，显示 A 参与的所有对话，每个对话附带最新一条消息，按最近程度排序。
3. **标记消息已读：** 当 A 读了 B 的消息，标记这些消息已读。
4. **未读计数：** 给定用户 A，每个对话有多少条未读消息？

查询 1（对话历史）最频繁且对延迟最敏感。围绕它设计 schema。
