1. 登录状态不能影响渲染内容（缓存版本不能包含“你已关注 Alice”指示）
  2. 没有个性化的“为你推荐”区块
  3. 响应体中不能包含 CSRF token 或其他 per-user 安全令牌

已登录用户不能直接使用 CDN 缓存版本，因为他们期望页面显示他们与 Alice 的关系（关注/取消关注按钮、共同帖子）。常见解决方案：提供 CDN 缓存的“公开外壳”资料页，然后通过不被缓存的第二次 Ajax 调用“水合”个性化元素。CDN 承担为通过搜索引擎访问 Alice 的匿名访客提供资料页的重活，而登录用户获得由 CDN 缓存和服务器渲染内容混合构成的略有不同的页面。


### 本章总结

缓存是系统设计师工具箱中最强大的工具之一——也最具欺骗性。它看起来简单：存储答案，快速提供。但缓存从根本上改变了系统的正确性模型，引入了陈旧数据和失效 bug 的可能性，这些问题可能比性能问题更 damaging。

本章关键概念：

**缓存命中率**是主要性能杠杆。90% 命中率降低数据库负载 90%；99% 命中率降低 99%。每多一个百分点带来的价值随流量增长。

**缓存放置**选择（客户端、CDN、应用级、分布式）各有 tradeoff（权衡）。对大多数多服务器应用，Redis 或 Memcached 这类分布式缓存是正确默认。

**Cache-aside** 是最常见模式：先查缓存，未命中时取数据库，填充缓存，返回。它是懒加载的（只缓存被请求的内容），并把失效责任交给应用。

**Write-through** 每次写入都保持缓存与数据库同步，消除陈旧但增加写入开销。**Write-behind** 批量写入，提升写性能但 risking 数据丢失。

**TTL** 是主要新鲜度旋钮。短 TTL 偏向一致性；长 TTL 偏向性能。正确 TTL 取决于数据变化频率和可接受的陈旧程度。

**驱逐策略**（LRU、LFU、TTL）决定缓存满时什么被移除。LRU 是最常见默认。

**惊群** 是缓存过期导致数据库查询同步激增的故障模式。抖动、加锁和后台刷新是缓解手段。

SocialSnap v2 加入了 Redis 缓存层，显著降低数据库负载。它的第一个陈旧性 bug 说明，缓存不只是性能改动——它产生需要仔细失效逻辑的新一类正确性问题。

权衡矩阵中缓存这一行捕捉了核心交易：以更好延迟和有效可用性为代价，换取一定一致性和更高运维复杂度。这笔交易是否值得，取决于你的工作负载是否有让缓存有效的重复读取——以及用户能否容忍 TTL 允许的 stale 程度。

在第 8 章，我们将遇到一种不同的解耦系统部分机制：消息队列。如果说缓存把读路径与数据库解耦，消息队列则把事件生产者与消费者解耦——而这种解耦创造了完全不同的一组 tradeoff（权衡）。
