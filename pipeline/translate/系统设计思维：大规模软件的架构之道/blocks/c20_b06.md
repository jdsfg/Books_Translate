#### 第 4 层：分析路径

116,000 次重定向/秒，同步写 `clicks` 表一行不现实——需要数据库能维持 116,000 次写入/秒，时序数据库可行，通用关系型数据库不行。

正确做法：把分析写入从重定向响应解耦。重定向发生时：

1. 立即返回 302 重定向（不等待分析）
2. 向消息队列（第 8 章）发布事件：`{short_code: "abc1234", timestamp: ..., ip: ..., user_agent: ..., referrer: ...}`

后台消费者从队列读取并批量写入分析数据库。批量写入关键：不是每秒 116,000 次单独插入，而是消费者把 10,000 个事件批量一次 INSERT——把写放大降低 10,000 倍。

分析数据库可用专门工具：Apache Kafka（队列） feeding  Apache Clickhouse 或数据仓库（分析存储）。用户通过分析 API 查询点击数，而不是查主数据库。

这种架构展示了第 8 章的原则：消息队列把主请求路径与次要操作解耦，防止次要写入负载影响主读性能。


#### 第 5 层：扩展与可靠性

核心设计确定后，如何扩展以在 99.99% 可用性下处理 116,000 RPS？

**负载均衡器后的无状态重定向服务器：** 重定向服务无状态——所有状态在 Redis 和数据库。可按需运行任意多台重定向服务器，并在负载均衡器后添加更多。这是第 11 章的水平扩展模式。

**数据库扩展：** 1,157 次写入/秒和数十万/秒读（考虑缓存未命中后），主数据库处理写入，读副本（第 12 章）处理缓存未命中的读负载。`urls` 表相对较小（10 年 91TB——虽大，但有好索引仍可扫描）。`short_code` 上的主键索引使查找 O(log N) 且快速。

**如果需要分片：** 自然分片键是 `short_code`。一致性哈希（第 14 章）把码分布到各分片。由于短码随机生成，分布近似均匀——没有热分片。然而 1,157 次写入/秒下，单主库多年内完全足够。分片在单主库出现压力前增加复杂度——除非必要，避免分片。

**可用性：** 重定向路径要求 99.99% 可用性。这意味着 Redis 缓存和数据库都必须高可用。Redis Sentinel 或 Redis Cluster（第 11 章）提供 Redis HA。主-副本自动故障转移（Patroni 或 AWS RDS Multi-AZ）提供数据库 HA。熔断器（第 16 章）防止数据库失败级联到 Redis 层或应用服务器。

**优雅降级：** 如果 Redis 和数据库同时不可用（在冗余下极不可能），重定向服务应做什么？返回 503？还是返回通用“URL 未找到”加提示？答案取决于场景，但对延迟关键的短链服务，返回 503 和“暂时不可用”比挂起请求更好。熔断器跳闸并快速失败。
