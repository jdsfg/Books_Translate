#### 追踪如何工作

当请求进入系统（在 API 网关或负载均衡器），生成一个 **trace ID**——通常是随机的 128 位 ID。这个 ID 附加到请求上（HTTP header：`X-Trace-ID: abc123`）。

处理请求的每个服务读取这个 header，记录一个 span，并在所有下游调用中传播 trace ID。每个 span 记录：trace ID、span ID（该 span 唯一）、parent span ID、服务名、操作名、开始时间戳、结束时间戳，以及附加到 span 的标签或日志。

Spans 被发送到一个集中式追踪后端（Jaeger、Zipkin、Honeycomb、Datadog APM），它通过 trace ID 拼接 span 树，重建追踪。工程师可以查询：“显示所有总时长超过 500ms 的追踪”或“显示请求 ID abc123 的追踪。”


#### 常见误解

常见误解是分布式追踪只在大型复杂微服务架构中才需要。实际上，即使只有两到三个服务的系统也能立即受益。请求一旦跨越服务边界，你就有了分布式系统，问题“这次请求把时间花在哪里？”就变得非平凡。尽早安装追踪—— retrofit 远比一开始就构建难。


### 17.4 告警哲学——什么值得把人叫醒

指标、日志和追踪是可观测性的原材料。告警是把“有坏事正在发生”转化为“能修复它的人被通知”的机制。

糟糕的告警是生产运营中最常见、最有害的问题之一。告警疲劳——工程师被低质量告警淹没，开始忽略或静音——会导致真正的 outage 未被察觉。


#### 基于症状 vs 基于原因的告警

存在两种告警哲学，结果截然不同。

**基于原因的告警** 对可能指示问题的基础设施指标触发：“CPU 使用率超过 80%”、“磁盘 I/O 超过阈值”、“内存使用率超过 70%”。推理：CPU 高可能导致响应慢，所以 CPU 高时告警。

问题：这些告警经常在用户没问题时频繁触发。CPU 可能因为大型批处理作业而高，但没有用户影响。内存可能因为缓存——这是故意的。基于原因的告警满是误报。

**基于症状的告警** 对用户可见症状触发：“错误率超过 1%”、“99 百分位延迟超过 500ms”、“成功请求比例低于 99.5%”。这些直接测量你关心的事情：服务对用户是否正常工作？

Google SRE 著作把它表述为：对**四个黄金信号**告警：

1. **延迟**——请求耗时多久？（99 百分位超过 SLO 阈值时告警）
2. **流量**——系统承受多大需求？（异常下降可能表示客户端坏了；峰值可能表示 DDoS）
3. **错误**——多大比例请求失败？（错误率超过 SLO 阈值时告警）
4. **饱和度**——系统有多满？（队列深度或资源利用率接近极限时告警）
