#### 应用问题

**Q1.** SocialSnap 工程团队正在争论该缓存什么。以下是他们在考虑的三种数据类型。对每种，分析访问模式，估算合适 TTL，并选择缓存策略（cache-aside、写通或写回）：

(a) 用户头像照片（照片 URL 存在 users 表中）
(b) 用户的未读通知数（新事件发生时频繁更新）
(c) 全站“已创建帖子总数”计数器

提示

想想每种数据多久变化一次、多少用户访问它、旧数据如何影响用户体验。对计数器，想想写通是否会造成数据库瓶颈。

**答案：**

**(a) 用户头像照片：**

访问模式：读密集型。用户的照片出现在他们发的每篇帖子、每条评论、粉丝 Feed 的每一页。变化很少——用户一年可能只更新几次头像。旧数据后果：刚更新头像的用户几分钟内看到旧照片——有点烦人，但可接受。

缓存策略：**Cache-aside**，长 TTL（30–60 分钟）。照片更新时使缓存 key 失效。长 TTL 可接受，因为更新少且陈旧影响低。

缓存 key：`user:{user_id}:photo_url`

**(b) 未读通知数：**

访问模式：每个登录用户的每次页面加载都读。写入频繁——每个新关注、每个点赞、每条评论都创建通知。用户期望计数近实时更新。旧数据后果：显示“3 条未读”而实际有 7 条，如果持续超过几秒会令人沮丧。

缓存策略：**写通或直接 Redis 计数器**。因为这个数字变化频繁且准确性重要，短 TTL（10–30 秒）加 cache-aside 可行，但会导致频繁未命中。更好的方法：直接把计数存为 Redis 整数，用 `INCR`/`DECR` 操作（原子、亚毫秒）。Redis 成为该计数的事实来源，数据库作为备份。这本质上是写通：每个通知事件同时更新数据库和 Redis 计数器。

缓存 key：`user:{user_id}:unread_count`

**(c) 全站帖子总数：**

访问模式：显示在网站的“关于”或“统计”页面。多半是虚荣指标。每篇新帖子都会改变它。如果 SocialSnap 有 100 万帖子，一篇新帖子把它从 1,000,000 变到 1,000,001——0.0001% 的变化，没有用户会注意。

缓存策略：**写回或 cache-aside 加长 TTL（10–60 分钟）**。这个计数本质上是近似的——没人需要实时看到精确当前数字。用 cache-aside，10 分钟 TTL。未命中时运行 `SELECT COUNT(*) FROM posts`（大表上可能慢——可改用 Redis 中的物化计数器预计算）。写回模式在此完美：每次创建帖子递增 Redis 计数器，并定期把计数同步到数据库。用户始终看到 Redis 计数器，它精确（不陈旧），但如果 Redis 故障可能丢失最近几次递增。
