#### 概念检测

**Q1.** 有状态和无状态应用服务器有什么区别？为什么无状态是水平扩展的先决条件？

**答案：** **有状态（stateful，有状态的）** 应用服务器在自己内存（或本地存储）中保存每个客户端的数据。该服务器上的数据——会话、缓存、进行中的计算——特定于该服务器，不与其他服务器共享。同一客户端的请求必须到达同一台服务器，才能找到该客户端需要的状态。

**无状态** 应用服务器不保存每个客户端的状态。每个请求都携带处理它所需的所有信息（或服务器能从共享外部存储取回所需状态）。任何服务器都能处理任何请求。

**为什么无状态是水平扩展的先决条件：**

水平扩展通过增加更多服务器并让负载均衡器把请求分发到它们来工作。负载均衡器不能保证特定客户端的请求总是到达同一台服务器——也不应该这样做，因为这会把服务器故障变成强制会话终止，并阻止真正的负载均衡。

如果应用服务器有状态，跨服务器分发请求就会产生不匹配：Alice 的会话状态在 Server A，但她的请求可能到 Server B，而 Server B 没有她的状态。系统要么 (a) 把 Alice 的所有请求都路由到 Server A——消除负载均衡的收益；要么 (b) 接受错误行为（Alice 随机被登出）——显然错误。

无状态服务器彻底消除问题：没有需要路由绕开的每个客户端状态。任何服务器都能处理任何请求。

**Q2.** 描述 SocialSnap v4 初始部署中的会话管理 bug。根本原因是什么，修复是什么？

**答案：** 当 SocialSnap 在轮询负载均衡器后增加三台应用服务器时，用户遇到随机登出：点击任何链接都可能把他们登出，他们不得不反复重新登录。

**根本原因：** 会话数据存在每台应用服务器的内存字典（本地 Python dict）中。Alice 登录时，请求到 Server A，它在 Server A 的本地内存中创建了她的会话。但 Alice 的后续请求被轮询负载均衡器分到 Server B 或 C，它们检查自己的本地会话字典——其中没有 Alice 的会话。Server B 没找到 Alice cookie 对应的会话，把她当作未认证。

**修复：** 把会话存储从应用服务器本地内存移到共享外部 Redis 实例。三台应用服务器都从同一个 Redis 读写会话。Alice 在 Server A 登录时，会话存在 Redis 中。她的下一个请求到 Server B 时，Server B 查询 Redis，找到会话，认证 Alice。应用服务器现在无状态——不保存任何每个会话的数据。
