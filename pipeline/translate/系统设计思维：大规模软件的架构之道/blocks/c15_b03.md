### 15.2 至少一次投递——创造问题的保证

消息队列和任务队列提供不同的投递保证。最常见的是**至少一次投递（at-least-once delivery）**：每条消息都会投递给消费者至少一次，但可能投递多次。

为什么是“至少一次”而不是“恰好一次”？因为分布式系统中实现**恰好一次投递（exactly-once delivery）**本质上很难。

考虑：工作节点收到任务，处理它，然后——就在向队列确认消息前——工作节点崩溃。队列没收到确认。从队列视角，任务从未成功处理。超时后，队列把消息重新投递给另一个工作节点。

现在任务被执行了两次。如果任务是“给用户 42 发邮件”，用户 42 收到两封邮件。如果任务是“给用户 42 信用卡扣 9.99 USD”，用户 42 被扣两次。重复投递是真正的问题。

**恰好一次处理**（每条消息只处理一次，不多不少）在分布式系统中不能作为原生原语实现。有些系统所谓“恰好一次”——例如 Kafka Streams 的 exactly-once 语义——是结合至少一次投递与幂等生产者和事务写来实现的，所以*效果*上像每条消息只处理一次。底层机制仍涉及重试和去重。跨系统边界（工作节点与支付处理器、邮件 API 或其他数据库交互）时，即使这种受限保证也会瓦解——外部系统可能不支持幂等 API，也不参与协调协议。

既然不能保证恰好一次，你就必须设计操作，使它们多次执行也安全。这就是**幂等性（idempotency）**的概念。


### 15.3 幂等性——可以安全运行两次


#### 定义：幂等性

如果一个操作执行多次产生的效果与执行一次相同，它就是**幂等的（idempotent）**。后续执行没有额外效果。

通俗语言：你按一次电梯按钮，电梯会来。你再按十次，电梯仍然只来一次。按按钮是幂等的——多按不会召唤更多电梯。

有些操作天然幂等：

* `SET user 42's name to "Alice"`——做两次结果仍是 "Alice"。幂等。
* `GET user 42's profile`——读没有副作用。幂等。
* `DELETE post 99 WHERE it exists`——第一次删除后，后续删除找不到任何内容，什么都不做。幂等（若写正确）。

有些操作天然非幂等：

* `CHARGE user 42's credit card 9.99 USD`——执行两次就扣两次。
* `INCREMENT post 99's like count`——执行两次就加两次。
* `SEND email to user 42`——执行两次就发两封。

对依赖至少一次投递的系统，你必须要么使用天然幂等操作，要么让非幂等操作变得幂等。后者的标准机制是**幂等键（idempotency keys）**。
