#### 概念检测

**Q1.** 什么是 geohashing，为什么拼车匹配服务需要查询 9 个单元格而不是 1 个？

**答案：** Geohashing 把地理坐标（纬度、经度）编码成一个识别矩形单元格的短字符串。附近位置倾向于共享 geohash 前缀——同一单元格内所有位置共享相同完整 geohash 字符串。匹配服务用 geohash 作为键找区域内司机。然而，两个点可能地理相邻但位于 geohash 单元格边界两侧，从而得到完全不同的哈希字符串。司机可能离乘客只有 10 米，却在单元格 “9q8yy” 而乘客在 “9q8yz”。只查乘客单元格会漏掉该司机。查询周围 8 个邻接单元格（以乘客单元格为中心的 3×3 网格）保证大约 10km 内没有司机被遗漏，无论边界效应。

**Q2.** 为什么拼车系统用 Redis 等内存数据库存储司机位置而非关系型数据库？

**答案：** 司机位置更新达到每秒 125 万（1.25 million）次写入。一台典型 PostgreSQL 在强力硬件下理想条件约处理 5 万（50,000）–10 万（100,000）写入/秒。即使重硬件投资，单个关系型数据库实例也无法持续该写入吞吐。Redis 是内存数据结构存储，单节点每秒处理 50 万（500,000）+ 操作，延迟 < 1ms。10 节点 Redis 集群每秒处理 500 万操作——远高于 1.25M 要求。此外，司机位置不是需要 ACID 属性的永久记录：它是频繁覆盖的当前值，带 TTL。Redis 原生支持基于 TTL 的过期、用于地理空间索引的 sorted set 以及原子更新操作，是天然选择。持久化权衡（若 Redis 丢数据，最后 5 秒位置更新丢失）可接受，因为位置数据会被下一次司机更新重新生成。

**Q3.** 行程计费服务在其 SQL 事务中使用 `FOR UPDATE` 锁。解释这把锁防止什么，以及没有它会发生什么。

**答案：** `FOR UPDATE` 在事务开始时获取行程记录的行级排他锁。没有这把锁：两个计费服务实例可能同时读到同一条行程记录（都发现 `status = 'COMPLETED_UNBILLED'`），都计算车费并插入计费记录——乘客被重复扣款。有锁：第一个执行 `SELECT ... FOR UPDATE` 的实例获得锁。第二个实例的 `SELECT ... FOR UPDATE` 阻塞到第一个事务提交。第二个实例继续时发现 `status = 'BILLED'` 并跳过计费。锁 + 状态检查共同实现防止重复扣款的幂等性。这就是第 5 章 ACID 保证中的隔离性：并发事务看到一致的数据视图，看不到彼此未提交的变更。
