**用限流代替信息隐藏：** 与其隐藏邮箱是否已注册（这会使 UX 复杂化——忘记用了哪个邮箱的用户无法确定），一些系统允许“邮箱未找到”消息，但 aggressively 对登录端点限流。这意味着攻击者可以枚举邮箱，但按允许的速率需要数月而非数分钟。

**开发者 API 透明性：** 第三方开发者文档和 API 响应需要足够信息才能集成。这里的防御是 API 本身的认证和限流，而不是错误消息中的信息隐藏。如果只有认证应用能调用你的 API，那么“攻击者从 API 响应中学习”的威胁模型就限于被入侵或恶意应用——这是一种不同的威胁，有不同的缓解措施。

一般原则：为合法受众的需求设计信息披露，把每种信息类型的访问限制在最小必要受众，并用限流和异常检测作为不需要向合法用户隐藏信息的防御措施。


### 本章总结

安全是整个系统的属性，不是最后添加的功能。它的基础概念——认证、授权、最小权限原则——是必须早期做出的架构决策。

认证和授权是独立关注点。认证建立身份；授权决定权限。OAuth 2.0 支持第三方访问的委托授权。JWT 支持密码学可验证 claims 的无状态认证。

加密保护数据在两种场景：传输中（TLS/HTTPS 防止窃听）和静态（卷级或应用级加密防止磁盘被盗或未经授权的数据库访问）。密码不被加密——它们用故意很慢的算法哈希。

三种经典 Web 漏洞——SQL 注入、XSS、CSRF——都共享一个根因：把用户输入当作可信代码或可信状态。防御措施——参数化查询、HTML 转义、CSRF 令牌——都共享同一原则：把代码与数据分开。

零信任架构放弃边界模型，要求每次服务调用都进行认证和授权。攻击者作为对抗性侦探的框法帮助系统设计师思考系统泄露了什么信息，以及如何在不破坏可用性的情况下限制泄露。

安全权衡与所有系统设计权衡一样可量化。威胁模型决定哪些防御是必要的。大多数基础实践（参数化查询、TLS、CSRF 令牌）运营成本可忽略，应普遍采用。昂贵的防御（零信任 mTLS、字段级加密）应在风险证明成本合理的地方应用。
