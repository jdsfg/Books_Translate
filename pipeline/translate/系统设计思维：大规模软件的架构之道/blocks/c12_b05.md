#### 热 shard 问题

即使基于哈希分片，特定模式也会造成热 shard：**热 key**。想象 SocialSnap 有一位名人用户——叫她 @nova——有 2000 万（20 million）粉丝。每次 @nova 发帖，都会触发 2000 万条 feed 更新。所有 @nova 的数据哈希后落到比如 Shard 3。Shard 3 被一个用户相关的操作洪流淹没。

shard 热不是因为多数人分布不均，而是因为少数人的极端集中。

处理热 shard 需要对热 key 特殊处理：更激进地复制热 key 的数据、从缓存服务（如 SocialSnap 第 7 章已做的 Redis），或在应用层把热 key 跨多个 shard 拆分。这些都不简单。


#### SocialSnap v5——按 user_id 分片

SocialSnap 团队决定对 `users` 和 `posts` 表按 `user_id` 做哈希分片，共 8 个 shard。user ID 对 8 取模决定用户的资料存在哪个数据库实例。

应用代码更新：涉及用户的每个数据库操作先计算 `shard_number = hash(user_id) % 8`，然后把查询路由到对应数据库实例。

写延迟大幅改善。每个 shard 处理八分之一的写负载。8 个 shard 下，每个主库现在大约处理每秒 625 次写入—— comfortably 在舒适范围内。

但部署几小时内，新问题出现。


### 12.4 跨分片查询问题

团队想实现一个功能：“本周全球点赞数最高的 10 条帖子”。这个查询需要找到所有用户中点赞最多的帖子。但用户按 `user_id` 分片。user 1234 的帖子在 Shard 1；user 5678 的帖子在 Shard 3。“全球最受欢迎的帖子”需要来自全部 8 个 shard 的数据。

分片前简单至极的查询：


    SELECT post_id, like_count
    FROM posts
    ORDER BY like_count DESC
    LIMIT 10;


现在需要查询全部 8 个 shard，从每个 shard 取前 10，再在应用层合并结果找出真正全球前 10。应用必须编排 8 个并行查询并自己执行合并逻辑，因为没有一个数据库知道其他 shard 的情况。

这就是**跨分片查询问题（cross-shard query problem）**，也是分片最显著的成本之一。

分片前是 O(1) 查找的简单查询，分片后变成 O(shards) 的扇出操作。按不同 key 分片的表之间 JOIN 在单次查询中变得不可能——你必须执行多次查询，然后在应用代码中合并结果。

再举个例子：“找出 user 1234 的所有朋友。”`friendships` 表可能存 user ID 对。User 1234 在 Shard 1，但 1234 的朋友可能在任何 shard。分片前有效的简单 JOIN，现在需要先查询 Shard 1 拿到朋友 user ID 列表，再扇出到所有 shard 查找每个朋友的资料。

跨分片查询问题不仅是性能问题——更是设计约束。它迫使团队仔细考虑需要什么查询，并据此设计分片策略。一个能消除大多数跨分片查询的常见访问模式的 shard key，值得在其他地方付出显著 tradeoff（权衡）。
