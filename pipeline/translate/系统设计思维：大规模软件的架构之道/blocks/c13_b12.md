当链中任一服务失败，失败会沿同步链向上游传播。如果服务 D 失败，服务 C 对 D 的请求超时或报错。服务 C 向 B 返回错误。服务 B 向 A 返回错误。服务 A 向用户返回错误。用户看到失败——错误页或超时——即使服务 A、B、C 都完全健康。失败对用户实时可见。

这说明了长同步服务链为何危险。解决方法是减少链长度（不要有不必要的同步跳数）、用熔断器（第 16 章）快速失败而不是等待超时，以及尽可能把同步链转为异步。

**Q3.** SocialSnap 团队决定拆分单体。帖子功能和通知功能当前纠缠在一起：帖子创建代码直接在创建帖子的 SQL 事务中向 `notifications` 表插行。描述一个把它们拆成两个服务而不在迁移期间造成服务停机的分步计划。

提示

绞杀者无花果模式（Strangler Fig pattern）相关：你逐步围绕旧系统构建新系统，而不是一次性替换。

**答案：** 使用绞杀者无花果模式的分步计划：

**第 1 步：定义契约。** 在写任何服务代码前，先定义通知服务将暴露的 API。帖子 Service 如何通知它帖子已创建？通过消息队列（推荐）还是直接 HTTP 调用？决策：使用第 8 章的消息队列——帖子创建时发布 `post.created` 事件到队列；通知服务消费该事件。

**第 2 步：增加事件发布但不删除旧代码。** 修改帖子创建代码，在直接插入 `notifications` 表的同时，也发布 `post.created` 事件到队列。两条路径同时运行。这很安全，对用户无影响。

**第 3 步：构建通知服务。** 通知服务消费 `post.created` 事件并插入自己的 `notifications` 表。部署它并验证它正确创建通知。`notifications` 表现在可能被重复创建（旧代码和新服务都在插入），但过渡期可接受。

**第 4 步：验证通知服务正确。** 并行运行两条路径一段时间（几天或几周）。监控旧路径和新路径创建的通知差异。修复通知服务中的缺陷。

**第 5 步：移除旧直接数据库访问。** 确信通知服务正确后，从帖子创建代码中删除直接插入 `notifications` 表的逻辑。帖子创建代码现在只向队列发布事件。通知服务现在是通知表的唯一写入者。

**第 6 步：迁移通知数据存储。** 由于单体的 `notifications` 表现在只由通知服务读写，把它迁移到通知服务自己的数据库实例。更新通知服务的连接配置。帖子 Service 不再引用 `notifications` 表。

迁移全程没有停机。迁移是增量的，每一步都有安全的回滚路径。
