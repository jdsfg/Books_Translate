#### 深入思考

**Q1.** Sam 主张：“我们应该现在就拆成微服务，在出现扩展问题之前做好准备。”Alex 主张：“我们应该保持单体，直到扩展问题迫使我们拆分。”谁对？

**讨论：** 两种立场都捕捉了真实真相，正确答案取决于上下文。

Sam（早拆）有道理：把大单体重构成微服务明显更难、风险更高，而从一开始就构建服务则不然。上面描述的绞杀者迁移可行，但复杂且缓慢。如果你**知道**组织会成长且领域已充分理解，早拆可以避免未来痛苦的迁移。

Alex（等扩展问题）也有道理：过早分解的最大代价是服务边界搞错。在真正构建和运维之前你不会完全理解领域。如果拆分太早，会沿错误边界拆分，形成分布式单体。重构服务边界甚至比初始拆分更难。

务实综合：先构建**结构良好的模块化单体**。强内部模块边界、模块内清晰数据所有权、有纪律的模块间接口。当某个模块出现明确抽取信号（独立扩展需求、独立团队、独立部署节奏）时，再把它抽取成服务。模块化单体提前支付了设计成本，同时把运维成本推迟到有理由时。

最糟结果是过早为了组织声誉而非工程需要拆成微服务，发现十二人团队现在把一半时间花在运维开销和服务间协调上，而不是构建产品。

**Q2.** gRPC 使用 Protocol Buffers（protocol buffer 协议，二进制序列化格式），而 REST 使用 JSON（文本格式）。一位同事说：“JSON 就行——计算机够快，序列化开销不重要。”评估这个说法。序列化格式在什么条件下是 meaningful 的性能考量？

**讨论：** 这位同事的说法对小负载和低流量大致正确。一次传输几百字节、每秒几百次的请求，JSON 和 Protocol Buffers 在端到端延迟上差别可忽略。

在特定场景下这个说法会崩：

**高容量服务间通信：** 如果 User Service 每秒处理 100,000 次请求，每次都需要序列化和反序列化中等复杂度的 JSON 对象（比如 2-5 KB），JSON 解析消耗的 CPU 时间会累积。Protocol Buffers 对同等数据的解析速度是 JSON 的 3-10 倍。在这个规模上，差异是可测量的。

**大负载：** JSON 把数字表示成字符串（`"count": 12345` 占 12 字节；Protocol Buffers 编码同样整数只需 1-2 字节）。对包含数千条记录的响应，这种差异会放大。100 KB 的 JSON 响应用 Protocol Buffers 可能只要 30 KB——影响带宽和反序列化时间。

**流场景：** gRPC 支持单条 HTTP/2 连接上的双向流。HTTP/1.1 上的 REST 每次请求需要新连接。对实时 feed 或实时更新，REST 的连接开销显著。
