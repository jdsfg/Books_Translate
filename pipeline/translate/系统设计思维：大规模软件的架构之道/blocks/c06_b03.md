### 6.3 键值存储——极致速度，最大简单性

最简单的数据模型：一个 key 映射到一个 value。value 是不透明的——数据库存储它而不理解其结构。你通过 key 取回它。


    SET user:1:session_token "abc123xyz"
    GET user:1:session_token → "abc123xyz"

    SET post:101:like_count 14322
    INCR post:101:like_count → 14323


这就是 Redis。操作是亚毫秒级，因为 Redis 把整个数据集放在内存中。没有索引、没有 schema、没有 join。只有 key 和 value。


#### 键值存储何时胜出

**缓存：** 第一大用例。用 TTL（time-to-live，生存时间）存储频繁访问的数据库结果。把用户资料缓存 60 秒；下次请求直接返回缓存版本，无需命中数据库。

**会话存储：** 按 session ID 存认证 token 和会话数据。任何应用服务器都能快速查找任何用户的会话，无需数据库查询。

**计数器和限流器：** Redis 的原子 `INCR` 操作非常适合点赞数、浏览数和限流（“用户 X 这分钟已调用 47 次 API”）。

**实时数据：** 排行榜（Redis sorted set）、pub-sub 消息、实时在线状态（“谁现在在线”）。


#### 键值存储的 Tradeoffs（权衡）

**收益：** 微秒级读写。极致简单——无 schema、无迁移、无查询计划。可水平扩展（scalability，可扩展性）。

**代价（查询）：** 只能按精确 key 查找数据。Redis 里没有“找出本周登录的所有用户”——那需要扫描每个 key。如果你的访问模式超出 key 查找，键值存储本身不够用。

**代价（持久性）：** 传统键值存储是内存型的，崩溃可能丢数据。Redis 通过可选持久化（RDB 快照和 AOF 日志）来缓解，但这增加复杂度和延迟。

**代价（数据关系）：** key 之间没有关系概念。你必须在应用代码中管理这些——这可能复杂且容易出错。

Redis 几乎从来不是系统中唯一的数据库。它与关系型或文档数据库一起使用，处理高速查找和缓存层，而关系型数据库提供持久性和复杂查询。


### 6.4 列族存储——用于时间序列和分析的宽行

考虑另一种工作负载：你在监控服务器指标。每秒 10,000 台服务器各上报 50 个指标（CPU、内存、磁盘 I/O、网络 I/O……）。那就是每秒 500,000 次写入，持续不断。你需要查询：“给我过去 24 小时 A 集群服务器的 CPU 利用率，1 分钟粒度。”

这对关系型数据库来说是 terrible 的匹配：

* 每秒 500,000 次写入超过单节点 PostgreSQL 能力
* 查询是对特定行集合的时间范围扫描——不是复杂 join
* 数据是仅追加的（你从不更新历史指标）

列族数据库（如 Apache Cassandra）正是为这种场景设计。
