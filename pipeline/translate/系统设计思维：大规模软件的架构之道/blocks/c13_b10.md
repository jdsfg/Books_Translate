#### 概念检测

**Q1.** 用你自己的话解释“每个服务一个数据库”。为什么这条规则被认为是真正微服务独立性的关键？

**答案：** “每个服务一个数据库”意味着每个微服务拥有自己的数据存储——它的 schema、它的表、它的数据——不允许其他服务直接读写该数据存储。任何服务需要其他服务拥有的数据时，必须通过那个服务的 API 请求。

这条规则至关重要，因为数据库是耦合点。如果服务 B 直接读取服务 A 的数据库，那么服务 A 改 schema（重命名列、拆分表、改数据类型）就可能破坏服务 B。两个服务现在必须协调 schema 变更，意味着它们不能真正独立部署。数据库变成了共享接口——一种隐藏耦合，破坏了微服务架构的全部意义。

**Q2.** 什么是康威定律（Conway's Law）？举一个它如何适用于 SocialSnap 团队结构的例子。

**答案：** 康威定律指出，任何设计系统的组织，其产生的设计都会镜像该组织的沟通结构。系统由构建它们的团队的沟通模式塑造。

对 SocialSnap：如果公司有专门的支付团队、通知团队、用户资料团队——每个团队有自己的 Slack 频道、路线图和 on-call 轮值——他们产生的系统自然会有 Payment Service、Notification Service 和 User Service。这些团队主要通过定义好的接口（API、工单）沟通，所以他们的软件组件也通过定义好的接口沟通。反之，如果工程组织是一个大团队，没有专门所有权，他们产生的系统很可能是单体，一切都纠缠在一起。

**Q3.** 服务间通信有哪两种类型？各举一个适合场景。

**答案：** 同步通信（如 HTTP/REST、gRPC）要求服务 A 等待服务 B 响应后才能继续。适合场景：在屏幕上显示用户资料——页面必须等到数据返回才能渲染，因此需要同步通信。

异步通信（消息队列）允许服务 A 发送消息后继续，无需等待。适合场景：用户发帖后触发其关注者的通知更新——这可以后台发生；用户不需要等所有通知都发出去才看到自己的帖子。

**Q4.** 什么是“分布式单体”反模式？举两个具体症状。

**答案：** 分布式单体是一种微服务架构，表面看起来独立（独立代码库、独立部署），但实际上紧密耦合，消除了微服务方法本应带来的独立性。

症状：(1) 服务 B 直接读取服务 A 的数据库——服务 A 的任何 schema 变更都需要与服务 B 协调。(2) 部署服务 A 必须同时部署服务 B，因为它们共享定义共同数据模型的库。两种情况中，服务都必须协调变更和部署，就像单体一样。
