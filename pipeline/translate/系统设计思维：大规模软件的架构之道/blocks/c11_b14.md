想想“local_cache”在三台服务器中意味着什么。如果 Alice 在 Server A 更新资料，失效需要到达哪些缓存？

**答案：** 问题：`local_cache` 是每个应用服务器实例本地的进程内 Python 字典。三台服务器部署中，每台服务器有自己的独立缓存。这违反无状态要求——每台服务器持有未与同伴共享的状态（缓存的资料数据）。

**缺陷类别：缓存失效不一致。** 当 Alice 更新资料时：

1. 更新请求由 Server A 处理。
2. Server A 把新资料写入 PostgreSQL。
3. Server A 从**它自己的** `local_cache` 中删除 `user:42:profile`。
4. Server B 和 Server C 仍缓存着旧资料。

在接下来的 5 分钟（缓存 TTL）内，任何路由到 Server B 或 C 的 Alice 资料请求都返回旧资料。Alice 在当前浏览器会话（由 Server A 服务）中看到更新，但她的朋友可能看到旧资料。

**修复：** 把 `local_cache` 换成共享 Redis 缓存，使用第 7 章的 cache-aside 模式：


    def get_user_profile(user_id):
        cache_key = f"user:{user_id}:profile"
        cached = redis.get(cache_key)          # 共享 Redis，不是本地 dict
        if cached:
            return json.loads(cached)
        profile = db.query("SELECT * FROM users WHERE id = %s", [user_id])
        redis.setex(cache_key, 300, json.dumps(profile))  # 共享 Redis
        return profile

    def update_user_profile(user_id, new_data):
        db.execute("UPDATE users SET ... WHERE id = %s", [..., user_id])
        redis.delete(f"user:{user_id}:profile")  # 一次删除对所有服务器失效


因为所有服务器共享同一个 Redis 实例，任何服务器的 `DEL` 命令都同时对所有服务器失效缓存条目。不一致缓存问题被消除。这就是第 7 章同一个 Redis 缓存——现在由 SocialSnap v4 的三台应用服务器共享。

**Q3.** SocialSnap 把头像照片存在对象存储中（第 10 章）。一位工程师建议在应用服务器本地内存中缓存对象存储预签名 URL，以避免每次请求重新生成。缓存条目是：`{user_id → presigned_url, expires_at}`。在三台服务器部署中，这个本地缓存造成什么问题，应如何修复？

提示

想想当用户在 Server A 更新照片后预签名 URL 被重新生成时，哪些服务器拿到更新后的 URL，哪些仍服务旧 URL？

**答案：** 每台服务器本地内存中缓存预签名 URL 会造成与 Q2 资料缓存相同的不一致问题——但还有一个额外问题：预签名 URL 会过期。如果 Server A 重新生成了新 URL（因为旧的过期或用户上传了新照片），只有 Server A 的本地缓存有新 URL。Server B 和 C 仍服务旧 URL，而旧 URL 可能已过期或指向旧照片。

更新自己资料照片的用户在请求命中 Server A 时看到新照片，但她的朋友（由 Server B 服务）看到旧照片——或者一个破碎图像（如果旧预签名 URL 已过期）。两种结果都错误。
