#### 投递状态机

每条消息经历状态转换：

    SENT → DELIVERED → READ

* **SENT：** 发送者客户端把消息提交到服务器。服务器已持久化。
* **DELIVERED：** 接收者客户端收到消息（客户端通过 WebSocket 发送投递确认）。
* **READ：** 接收者打开对话，消息被显示（客户端发送已读确认）。

这些状态转换发生在不同设备上。发送者在 S1。接收者在 S3。S3 的确认必须传播回 S1，发送者客户端才能更新显示。

**投递回执流程：**

1. 服务器通过 S3 上的 WebSocket 把消息 M 投递给接收者 R
2. 接收者客户端发送 `{type: "delivered", message_id: M}` 回 WebSocket
3. S3 收到该确认并写数据库：`UPDATE messages SET delivered_at = NOW() WHERE message_id = M`
4. S3 查注册表找出发送者 S 连哪台服务器
5. S3 发送 `{type: "delivery_receipt", message_id: M}` 给 S（发送者所在服务器 S1）
6. S1 把回执推送到发送者 WebSocket 连接
7. 发送者 UI 更新：消息勾选从单勾（已发送）变双勾（已送达）

**一致性挑战：** 如果 S3 在步骤 3 和 4 之间崩溃，数据库里已有投递确认，但发送者没收到回执。发送者 UI 显示“已发送”，但消息实际已送达。这是良性不一致——发送者客户端周期性轮询回执状态时，它自会解决。

已读回执是最终一致性（第 4 章）应用于用户可见状态的完美例子。“真实”状态是消息在时间 T 被读。显示状态通过实时投递路径在数秒内收敛到该事实，周期性轮询作为兜底。对多数用户，这无法察觉。
