#### 功能开关

**功能开关（feature flags，也称 feature toggles）** 把部署与发布解耦。代码部署到生产，但新行为由配置开关控制。开关关闭时，代码走旧路径；开关打开时，走新路径。

功能开关启用强大工作流：

* 在功能准备好发布前几周部署代码，使部署本身不是风险时刻
* 先对内部用户启用（dogfooding），然后是小比例外部用户，最后所有用户
* 如果功能导致问题，无需回滚部署即可立即禁用
* 通过把不同用户段路由到不同开关状态进行 A/B 测试

功能开关实现为数据库查询或配置服务调用：`if feature_flags.is_enabled("new_feed_algorithm", user_id): use_new_algorithm()`。开关状态可以不改代码就变更。

功能开关的成本：它们增加代码复杂度，会随时间积累（从未清理的旧开关产生 dead code 路径），并为请求处理增加一次远程调用（或缓存查询）。优秀工程团队把开关视为临时的：功能完全推广后，移除开关并删除旧代码路径。


#### 数据库迁移策略

数据库 schema 迁移是大多数部署中最危险的部分。增加新列的迁移通常安全。重命名列不安全——每个引用旧列名的查询都会失败，直到代码也更新。

高可用（high-availability，可用性）系统最安全的迁移模式是**expand-contract**，也称**parallel change**：

**阶段 1（Expand）：** 在旁边添加新状态。如果你需要把列从 `author` 重命名为 `author_id`，先不删除 `author` 而添加 `author_id` 列。更新应用代码同时写两个列，并从新列读取。部署此变更。现在两个列都存在，旧代码（如果有）仍能工作。

**阶段 2（Migrate）：** 运行后台迁移，为 `author_id` 填充新代码部署前已写入的所有现有行。

**阶段 3（Contract）：** 一旦所有行都有 `author_id` 且旧代码路径已消失，在单独迁移中删除 `author` 列。

这种三阶段方法意味着任何时候 schema 都与运行中的代码兼容。每个阶段都可独立部署和回滚。


#### 回滚规划

每次部署前，定义回滚流程。回滚计划应明确：

1. **触发条件：** 什么条件触发回滚？（例如“错误率 5 分钟超过 0.5%”或“p99 延迟超过 SLO 阈值”）
2. **回滚动作：** 部署上一版本？翻转功能开关？把负载均衡器切回 blue？
3. **回滚负责人：** 谁决定回滚？On-call 工程师？发布经理？
4. **回滚验证：** 回滚后如何确认系统恢复健康？
5. **数据库考虑：** 如果部署包含迁移，回滚能否处理已迁移数据？（这就是 expand-contract 迁移如此宝贵的原因——旧代码在新旧 schema 状态下都能工作。）

只存在于脑海中的回滚计划不是回滚计划。在部署前把它写下来。
