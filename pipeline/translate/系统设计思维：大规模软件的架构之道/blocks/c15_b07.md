#### 定义：编排

**编排（Orchestration）** 是一种 saga 协调风格：中央编排器服务驱动 saga，显式调用每一步并处理失败。编排器维护 saga 状态并知道完整工作流。

通俗语言：编排就像有指挥的管弦乐队。指挥告诉小提琴何时演奏、双簧管何时进入、铜管何时休止。指挥拥有完整乐谱；乐手按指示演奏自己的部分。

编排优点：saga 逻辑**显式且集中**。要理解 saga 做什么，读编排器即可。调试更简单——编排器的状态揭示哪一步失败。增加新步骤只需在一个地方更新编排器。

缺点：编排器是一个需要构建、部署和运维的新服务。它可能成为瓶颈（所有 saga 协调都经过它）。它引入了对其他服务的了解——编排器“知道”Payment Service、User Service 和通知服务的细节，造成耦合。


#### 选哪个？

选择取决于 saga 多复杂，以及你需要多大可见度。

简单 saga（3-4 步、不频繁、容易追踪）：编舞。松耦合和无需管理新服务的好处超过调试复杂度。

复杂 saga（多步骤、频繁、需要显式状态追踪）：编排。中央编排器的可调试性和显式性证明耦合与运维开销合理。

实践中，大多数大型系统两者都用：简单事件驱动编舞用于常规服务间交互，编排器用于少数关键、复杂、必须可见的业务流程。


### 15.6 Outbox 模式——可靠事件发布

上面描述的 saga 模式依赖服务可靠发布事件。但考虑 Payment Service：


    BEGIN;
        INSERT INTO payments (user_id, amount, ...) VALUES (42, 9.99, ...);
        -- commit the payment record to the database
    COMMIT;
    // Publish event to message queue: "payment.charge.succeeded"


数据库提交与事件发布之间存在空隙。如果服务在此间隙崩溃，支付记录已保存但事件从未发布。Saga 卡住——没有事件意味着下一步永远不运行。

另一种顺序：


    // Publish event to message queue: "payment.charge.succeeded"
    BEGIN;
        INSERT INTO payments (user_id, amount, ...) VALUES (42, 9.99, ...);
    COMMIT;


现在如果服务在发布事件与提交数据库事务之间崩溃，事件已发布但数据库记录未提交。下一步以为支付成功运行，但支付记录不存在。

无论哪种顺序，失败间隙都会产生不一致状态。这就是**双写问题（双写 problem）**：不通过分布式事务，就不可能原子地写入两个独立系统（数据库和消息队列）。

**Outbox 模式**通过只写入一个系统——数据库——然后由独立进程发布事件来解决。
