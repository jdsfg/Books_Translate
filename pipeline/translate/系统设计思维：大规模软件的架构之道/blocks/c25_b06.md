### 25.5 行程计费——钱的强一致性

行程完成时，系统必须向乘客收取正确金额并准确支付给司机。这些都是金融交易事务（transaction）。

要求严格：

* **Exactly once：** 每张信用卡每笔行程只扣一次
* **Atomicity：** 对乘客扣款与给司机账户入账必须同时发生或都不发生
* **Durability：** 事务一旦提交，就经受住后续任何系统故障
* **Correctness：** 计费金额必须严格等于行程价格（距离 × 费率 + 动态加价倍数 × 起步价）

这是关系型数据库上 ACID（而非 BASE）事务的领域——正是第 5 章介绍的属性。计费服务使用事务型关系型数据库（PostgreSQL 或类似）处理事务（transaction），事务如下：

    BEGIN;
      -- 锁定行程记录，防止并发计费
      SELECT * FROM trips WHERE trip_id = X FOR UPDATE;
    
      -- 验证该行程尚未计费
      IF trip.status = 'COMPLETED_UNBILLED' THEN
        -- 计算最终车费
        INSERT INTO billing_ledger (trip_id, amount, type) VALUES (X, fare, 'CHARGE');
        INSERT INTO billing_ledger (trip_id, amount, type) VALUES (X, driver_payout, 'CREDIT');
        UPDATE trips SET status = 'BILLED' WHERE trip_id = X;
      END IF;
    COMMIT;

`FOR UPDATE` 锁防止两个并发进程同时计费同一行程。状态检查实现幂等性（idempotency）：若计费被触发两次（如因网络超时导致计费服务重试），第二次发现 `status = 'BILLED'` 后什么都不做。

实际对乘客信用卡扣款通过外部支付处理器（Stripe、Braintree）完成。外部调用有自己的故障模式：支付处理器可能慢、拒卡或超时。计费服务必须优雅处理这些故障而不重复扣款。

模式：**Two-Phase Commit（概念上）：** 首先在自己的数据库中记录扣款意图（幂等性，idempotency）。然后调用支付处理器。若支付处理器调用失败，用幂等意图记录重试——扣款尝试有唯一 ID，即使多次发送同一请求，支付处理器也不会重复扣款。这就是 **idempotency key（幂等性键）** 模式，在分布式系统中对 exactly-once 金融操作至关重要。
