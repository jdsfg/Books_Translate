#### 应用问题

**Q1.** 为 SocialSnap 的第三方开发者 API 设计认证与授权系统。开发者可以构建访问用户帖子和资料的应用。用户必须能控制哪些应用可以访问其账户，并随时撤销访问。

提示

思考完整生命周期：应用如何注册？用户如何授予应用访问？应用如何发起认证请求？用户如何撤销访问？什么存在哪里？概念上使用 OAuth 2.0（OAuth 2.0）流程。

**答案：**

**应用注册：** 开发者向 SocialSnap 注册应用（名称、描述、允许的 redirect URI）。SocialSnap 颁发 `client_id`（公开）和 `client_secret`（私密，仅 server-side 用于令牌交换）。

**授权流程（OAuth 2.0 授权码）：**

1. 用户点击第三方应用中的“Connect to SocialSnap”。
2. 应用把用户重定向到 `socialsnap.com/oauth/authorize?client_id=...&scope=read:posts,read:profile&redirect_uri=...&state=random_string`。
3. SocialSnap 显示同意页：“App X 想读取你的帖子和资料。允许？”
4. 用户批准。SocialSnap 重定向到 `redirect_uri?code=AUTH_CODE&state=random_string`。
5. 应用服务器把 `client_id`、`client_secret` 和 `AUTH_CODE` 发到 `socialsnap.com/oauth/token`（server-to-server，永远不在用户浏览器中）。
6. SocialSnap 返回 `access_token`（JWT，1 小时过期）和 `refresh_token`（不透明，长期，存于数据库（状态）中）。

**发起 API 请求：** 应用在每个请求中包含 `Authorization: Bearer <access_token>` header。SocialSnap 验证 JWT 签名并检查 `scope` claim，确保请求操作在授予范围内。

**令牌刷新：** 访问令牌过期时，应用把刷新令牌发到令牌端点。SocialSnap 在数据库（服务器（server）端状态）验证刷新令牌，签发新访问令牌。如果刷新令牌被撤销，刷新失败。

**用户撤销：** 用户访问 SocialSnap 设置，看到“Connected Apps”，撤销特定应用访问。SocialSnap 从数据库删除刷新令牌。应用无法获得新访问令牌。现有访问令牌在最长 1 小时内（或下次轮换前）仍有效——考虑到短生命周期，这是可接受的。

**OAuth 令牌数据库 schema：**

* `oauth_apps`：client_id, client_secret_hash, allowed_scopes, redirect_uris
* `oauth_authorizations`：user_id, client_id, granted_scopes, refresh_token_hash, expires_at, revoked_at

**最小权限：** Feed Service 验证 JWT 并检查 scope。具有 `read:posts` scope 的应用即使持有有效 JWT 也不能调用 Direct Messages 端点——授权检查会拒绝它。

**Q2.** SocialSnap 存储用户手机号用于双因素认证。设计手机号的数据存储策略，兼顾安全和运营需求（支持人员偶尔需要验证用户手机号以进行账户恢复）。

提示

考虑：需要对手机号执行哪些操作？哪些操作需要看到实际号码 vs 哈希？静态加密 vs 哈希——这里哪个合适，为什么？

**答案：** 手机号是敏感 PII，必须保护。但与密码不同，它们不能哈希——因为运营需要显示它们（支持需要验证“该用户号码是否以 5234 结尾？”），系统也必须向实际号码发送 SMS。
