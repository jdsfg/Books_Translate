#### 应用问题

**Q1.** 一位 SocialSnap 工程师提议用“粘性会话”解决会话问题——配置负载均衡器让把用户 42 的请求始终路由到 Server A，用户 7 到 Server B，等等。路由基于 IP 哈希。分析这个提案：它是否解决眼前问题？它引入了哪三种具体故障模式或运维问题？

提示

想想 Server A 宕机时发生什么。想想需要重启 Server A 部署代码时发生什么。想想很多用户共享同一个 IP 地址时（比如公司 NAT 后）。

**答案：** 粘性会话确实解决了眼前问题——Alice 的请求到持有她会话的同一台服务器，所以她保持登录。但该方案表面，并引入严重问题：

**故障模式 1：服务器故障导致强制登出。** 如果 Server A 宕机，所有“粘”在 Server A 上的用户在负载均衡器把流量故障转移到 Server B 时都会登出。Server B 不知道他们的会话。这把基础设施故障（服务器崩溃）变成用户可见的认证故障——Server A 上每个用户崩溃后都必须重新登录。用外部会话存储（Redis）时，服务器崩溃不会丢失会话。

**故障模式 2：负载分布不均。** IP 哈希路由把同一 IP 的所有请求路由到同一服务器。在公司环境中，所有员工可能看起来有同一个外部 IP 地址（NAT 网关后）。如果一家大公司使用 SocialSnap，1000（1000）名员工都显示为同一 IP，他们全被路由到 Server A。Server A 负载达到 300%；Server B 和 C 基本空闲。负载均衡器理论上“平衡”了，实际上严重不均。

**故障模式 3：零停机部署变得不可能。** 要给 Server A 部署新代码，必须排空它的流量（停止向它路由新请求），等进行中的请求完成，再部署、重启。粘性会话下，“排空 Server A 的流量”意味着中断当前在 Server A 上的所有活跃用户——他们要么在排空期间出错，要么丢失会话。滚动部署（逐台重启不停机）要求用户能安全地在服务器间移动——这需要粘性会话绕过的无状态设计。

**结论：** 粘性会话是创可贴，不是修复。它保留有状态（stateful，有状态的）设计并增加路由复杂度和故障模式。正确修复是外部会话存储。
