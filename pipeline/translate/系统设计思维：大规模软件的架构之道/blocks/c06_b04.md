#### 列族模型

在列族存储中，数据组织成可能拥有数百万列的行。行由一个**分区键（partition key）** 标识，并可选地有一个**聚类键（clustering key）**。属于同一分区键的所有数据一起存在同一节点上——这使分区内的范围扫描非常快。

对服务器监控用例：


    Row key: server_id + date (e.g., "server-001:2024-01-15")
    Columns: timestamps → metric values
      "09:00:00" → {cpu: 45, mem: 72, disk_io: 12, ...}
      "09:00:01" → {cpu: 47, mem: 72, disk_io: 14, ...}
      ...
      "09:59:59" → {cpu: 43, mem: 71, disk_io: 11, ...}


某台服务器某天的所有指标连续存储。查询“给我 server-001 在 2024-01-15 09:00 到 10:00 之间的所有指标”就是单行范围扫描——极快。


#### 列族存储何时胜出

**时间序列数据：** IoT 传感器读数、应用指标、金融 tick 数据、事件日志。数据按时间顺序写入，按时间范围读取。

**高写入吞吐：** Cassandra 为写入而设计。其日志结构合并树（LSM-tree）存储引擎把写入接收到内存缓冲区，再批量刷到磁盘——比高容量写入下的 B-tree 更新快得多。

**地理分布、高可用读写：** Cassandra 使用对等架构，一致性可调。你可以配置它优先可用性（即使部分节点宕机也服务读）或一致性（要求多个节点同意）。这使其在全球应用中流行，区域故障不应导致完全不可用。


#### 列族存储的 Tradeoffs（权衡）

**收益：** 卓越的写入吞吐、分区内高效时间范围查询、可调一致性、优秀的水平可扩展性。

**代价（查询灵活性）：** Cassandra 有 CQL，看起来像 SQL，但深受限制。你只能按分区键和聚类键查询。跨分区查询（相当于跨分区 join）很贵，通常不推荐。在 Cassandra 中数据建模需要预先知道你的查询——你围绕访问模式设计 schema，而不是围绕数据关系。

**代价（一致性）：** Cassandra 的默认一致性模型是最终一致性。如果需要更强一致性，必须显式调整，代价是写入可用性。

**代价（复杂度）：** Cassandra 的数据模型比 SQL 更复杂。分区键、聚类键以及数据共置的含义需要相当专业知识才能正确使用。


#### 侦探测试

选择列族存储前，问自己：“我的数据是否自然组织成行，且访问模式按时间顺序或其他可预测方式？我是否有超过单节点能力的写密集型工作负载（>5,000 次写入/秒）？” 如果两者都是，研究 Cassandra 或类似系统。如果你的查询不可预测或需要跨多个维度 join，要三思。
