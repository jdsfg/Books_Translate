**讨论：** 很多答案都站得住脚，但最有说服力的答案是 **用权衡而非解决方案来思考。** 每一章都表明不存在正确架构，只有在特定约束下合适的选择。问“我们应该用关系型数据库还是文档存储？”的工程师问错了问题。正确问题是：“这个系统的访问模式、一致性要求和规模参数是什么，哪种存储模型最适合这些参数，成本各是多少？”这种习惯——从需求和约束出发，而不是从偏好技术出发——是 Thread B（Tradeoff Matrix）作为一种思维方式的应用。它也是 Thread C（侦探纪律）作为一种认识论立场：先收集证据再下结论。这种习惯比任何具体知识都更持久，因为技术会变（2030 年的数据库不会是今天的数据库），但仔细权衡推理的要求不会变。培养这种习惯的工程师能够根据优缺点评估真正的新技术，适应架构变化，并以一种超越其制度记忆存留的方式沟通设计决策。权衡矩阵（Tradeoff Matrix）不仅是一张参考卡——它是这种思考习惯的外化表达。


### 本章总结

本章通过考察系统设计的人文层面收尾。

**康威定律** 解释为什么组织与架构相互映射。**逆康威机动** 把这一观察变成处方：先按你想构建的架构设计组织。SocialSnap 在微服务迁移前的团队重组就是这一原则的有意应用。

**无责备 post-mortem** 和 on-call 文化决定团队如何从失败中学习。把失败视为系统问题而非个人问题的文化以复利速度积累学习，使每次事件后的系统更坚韧。

**Serverless** 和 **边缘计算** 代表抽象前沿：serverless 完全移除基础设施管理（代价是冷启动和执行限制）；边缘计算把计算带到用户附近（代价是可访问资源有限）。两者都适用于特定用例，而非全部。

**完成的权衡矩阵（Tradeoff Matrix）** 是本书总结：每个模式、构建块和设计选择映射到其在延迟、一致性、可用性和运营复杂度上的成本。把它当作参考，更重要的是，当作思考任何新模式的模型。

SocialSnap 的最后一章最具人文色彩：80 名工程师、8 个团队、一对仍记得笔记本电脑上 Python 函数的创始人。系统不是通过宏大设计，而是通过为每个观察到的具体问题积累具体解决方案而成长——每一次都是侦探收集线索、团队审查权衡、工程师承诺当时最不错误答案的结果。

侦探的工作——也是工程工作——永远不会结束。
