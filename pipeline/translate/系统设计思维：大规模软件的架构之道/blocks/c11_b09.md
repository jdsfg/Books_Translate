#### 常见误解

“水平扩展自动让系统更快。”更多服务器并不意味着更多吞吐。如果瓶颈是数据库（数据库没有水平扩展），加应用服务器只会让数据库收到更多并发请求——不会让它更快。不加解决数据库容量就给应用服务器扩容，实际上会因为增加数据库锁争用和队列深度而变慢。

应用层的水平扩展只让应用层更快。它不能修复其他层的瓶颈。识别瓶颈（通过分析、第 3 章估算技术、监控）始终是有效扩展的先决条件。


### 11.8 无状态要求——原则的泛化

会话是会破坏水平扩展的一种状态。无状态要求泛化到会话之外：

**任何存在应用服务器实例上、且每台服务器不同的状态都会造成水平扩展问题。**

常见导致此问题的状态类型：

**内存缓存：** 如果应用服务器维护自己的内存缓存（不是 Redis），不同服务器有不同缓存内容。到 Server A 的请求看到缓存值；同一请求到 Server B 缓存未命中并访问数据库。这既造成不一致（两个用户看到不同数据），也造成负载不均。

**本地文件系统状态：** 如果应用生成文件并存在本地（临时报告、生成缩略图、缓存模板），这些文件在其他服务器上不存在。下载 Server A 生成文件的请求若路由到 Server B 会失败。

**WebSocket 连接状态：** 如果应用服务器把 WebSocket 连接存在本地内存（第 9 章讨论过），一个客户端的 WebSocket 连接只属于一台服务器。该服务器重启，连接丢失。客户端重连到不同服务器，新服务器没有先前连接的上下文。

**后台作业状态：** 如果应用服务器运行后台作业并本地追踪状态，服务器重启会丢失作业状态。

无状态要求规定：**把所有状态从应用服务器推到共享基础设施**。会话 → Redis。文件 → 对象存储。缓存 → Redis。后台作业状态 → 数据库或队列系统。WebSocket 连接状态 → Redis pub/sub 或 WebSocket 网关服务。

遵循无状态要求的应用服务器是纯计算节点：接收请求，从共享基础设施读取状态，计算结果，把状态写回共享基础设施。服务器本身不保存持久状态。它可以在任何时候被杀掉并替换为新实例，而不会影响用户。

这种设计是 Kubernetes 等容器编排系统的基础，它们把应用服务器当作可互换计算单元——启动新的、杀掉旧的、在机器间迁移——因为它们都不持有唯一状态。
