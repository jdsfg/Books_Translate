在关系型数据库中，hashtag 计数来自聚合查询（COUNT + GROUP BY）。想想这个查询在 50 million（5000 万）帖子表上运行时会发生什么。然后想想键值存储如何用有序集合增量维护计数。

**答案：**

**关系型方案：**

Schema（加入 SocialSnap v1）：


    CREATE TABLE hashtags (
        post_id     INTEGER REFERENCES posts(id) ON DELETE CASCADE,
        tag         VARCHAR(100) NOT NULL,
        created_at  TIMESTAMP DEFAULT NOW()
    );
    CREATE INDEX idx_hashtags_tag ON hashtags(tag);
    CREATE INDEX idx_hashtags_created_at ON hashtags(created_at);


热门 hashtag 查询：


    SELECT tag, COUNT(*) as count
    FROM hashtags
    WHERE created_at > NOW() - INTERVAL '24 hours'
    GROUP BY tag
    ORDER BY count DESC
    LIMIT 10;


**Tradeoff（权衡）：** 如果每天有 50 million（5000 万）帖子、每个帖子约 2 个 hashtag，这个查询扫描过去 24 小时的 1 亿行。即使有 `created_at` 索引，聚合和排序也很昂贵。在规模下，这个查询可能花几秒——对每分钟刷新一次的热门功能来说太慢。

**Redis 方案（sorted set，有序集合）：**

帖子创建时，原子递增其 hashtag 在有序集合中的 score：


    ZINCRBY trending_hashtags:2024-01-15 1 "#systemdesign"
    ZINCRBY trending_hashtags:2024-01-15 1 "#engineering"


取当天 Top 10 热门 hashtag：


    ZREVRANGE trending_hashtags:2024-01-15 0 9 WITHSCORES
    → ["#systemdesign", "45231", "#engineering", "38204", ...]


对跨两天的 24 小时滚动窗口，查询两个日桶再在应用代码中合并。

**Tradeoff（权衡）：** 有序集合在每次帖子创建时增量更新——每个 hashtag 更新 O(log n)。读取查询是 O(log n + k)，k 为 10。两者都在内存中，耗时微秒。代价：Redis 有序集合默认持久性有限（需配置 AOF），且数据是反规范化的（帖子的 hashtag 存在两个地方：关系型 `hashtags` 表和 Redis 有序集合）。如果它们不同步（如 Redis 崩溃且未持久化），趋势计数会丢失，必须重建。

**这运用了第 5 章反规范化讨论的相同原理**——在写入时预计算昂贵聚合以换取快速读取。Redis 有序集合是一种持续更新的聚合：不是在读取时计算“过去 24 小时这个 hashtag 用了多少次？”（昂贵），而是在帖子创建时实时维护答案。
