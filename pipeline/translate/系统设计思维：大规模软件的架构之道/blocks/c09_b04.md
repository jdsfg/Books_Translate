### 9.4 一致性哈希——解决缓存亲和性问题

轮询和最少连接算法均匀分发请求，这对无状态应用服务器很好（每台服务器都能处理任何请求）。但它们给缓存带来问题。

想象 SocialSnap 的 Redis 缓存是一个三节点集群：Redis-1、Redis-2、Redis-3。应用对每个缓存 key 哈希以决定存在哪个节点：`hash(key) mod 3`。Key `user:42:profile` 存在节点 `hash("user:42:profile") mod 3 = 1` 上——Redis-1。

这没问题，直到某个 Redis 节点故障或新增节点。如果 Redis-1 故障，现在只剩两个节点。公式变成 `hash(key) mod 2`。突然，大多数缓存 key 路由到不同节点——缓存失效了。每个原本会去 Redis-1 的 key 现在都路由到不同节点。你迎来大规模缓存未命中。

新增节点同理：4 个节点而不是 3 个，`hash(key) mod 4` 会让几乎每个 key 都路由到不同节点。

**一致性哈希（consistent hashing）** 解决这个问题。


#### 定义：一致性哈希

**一致性哈希** 是一种分布技术：缓存节点和缓存 key 都映射到一个概念环（哈希空间）上的位置。每个 key 存在从它所在位置顺时针第一个节点上。

通俗语言：想象一个从 0 到 2^32-1 的圆形数轴（32 位哈希空间）。每个缓存节点按节点名哈希放在环上某个位置。每个缓存 key 按 key 哈希放在环上某个位置。一个 key 被分配给从它位置顺时针最近的节点。

一致性哈希的关键性质：当节点加入或移除时，只有映射到该节点的 key 需要重新分配。其他所有 key 都留在现有节点上。

**用 3 个节点和普通取模哈希：** 加入第 4 个节点会使约 75% 的缓存 key 失效（大多数 key 在新取模下哈希到不同服务器）。

**用一致性哈希：** 加入第 4 个节点只影响约 25% 的 key——那些落在环上新节点负责区段的 key。其余 75% 留在当前节点。

这就是分布式缓存（Redis Cluster、Memcached 客户端）用一致性哈希做 key 分布的原因。负载均衡器在为缓存亲和性重要的 IP 哈希路由时也用它。
