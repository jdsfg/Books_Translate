### 13.6 分布式单体——最糟糕的两者结合

这是微服务迁移特有的失败模式：**分布式单体（distributed monolith）**。

分布式单体表面看起来像微服务——有多个服务、独立代码库、独立部署。但服务间的耦合方式消除了微服务本应提供的独立性：

* 服务 A 直接查询服务 B 的数据库（违反“每个服务一个数据库”）
* 服务 A 和服务 B 必须一起部署，因为它们共享定义共同数据模型的库
* 服务 B 的 API 变更需要同时修改其他七个服务
* 服务 B 一宕机，服务 A、C、D、E 都跟着宕机

分布式单体集两者之恶：分布式系统的运维复杂度（网络调用、服务发现、独立部署），却没有独立性（一个服务变更需要与许多其他服务协调；失败级联）。

分布式单体如何产生？通常来自迁移过急。团队在没有仔细考虑数据所有权、API 契约、故障隔离的情况下把代码库拆成多个仓库。服务技术上独立，概念上纠缠。

解药是严格执行微服务规则：服务边界间不直接访问数据库，API 契约明确且带版本，没有共享可变状态。这说起来容易，做起来难，尤其是“同时了解”两个服务的工程师觉得走捷径很方便。
