#### 应用问题

**Q1.** SocialSnap 考虑把移动 API 从 REST 换成 GraphQL。移动应用现在渲染 home feed 需要 4 个 REST 调用：`GET /users/{id}`、`GET /feed`、`GET /users/{id}/following_count`、`GET /notifications/count`。用 9.7 节的决策框架分析 GraphQL 是否是正确选择。它会带来什么收益，需要接受什么成本？

提示

想想移动应用目前需要多少次往返。然后想想 GraphQL 的单一端点模型会改变什么。REST 和 GraphQL 的缓存分别是什么样的？服务器端实现成本如何？

**答案：**

**应用侦探框架：**

**支持 GraphQL 的线索：**

移动应用渲染一个屏幕需要 4 个独立 REST 调用。每次调用在移动网络上都是一次独立往返（每个约 50-100ms）。串行请求时 home feed 可渲染前的总时间：200-400ms；即使并行也需要约 100-150ms。GraphQL 会把这 4 个调用合并成一个查询：


    query HomeFeed {
      me {
        username
        photoUrl
        followingCount
        unreadNotificationCount
      }
      feed(limit: 20) {
        postId
        author { username photoUrl }
        content
        likeCount
        createdAt
      }
    }


一个请求、一次往返、只取需要的字段。移动带宽因消除过度取回字段和额外请求开销而节省。

**反对 GraphQL 的线索（或需要小心处理）：**

缓存：REST 的 `GET /feed` 可在 CDN 或浏览器层缓存（HTTP 层缓存）。GraphQL 查询是带自定义 query body 的 POST 请求，HTTP 缓存不适用。缓存必须在应用层处理——要么在 GraphQL 客户端（如 Apollo Client 的规范化缓存），要么在服务器 resolver 层（用 Redis，见第 7 章）。

服务器端复杂度：REST 端点是简单的数据库查询。GraphQL 服务器需要 schema 定义、每个字段的 resolver，以及防止深嵌套查询（查询深度限制、复杂度限制）的保护，避免产生巨大数据库负载。

**推荐：**

GraphQL 对移动 API 是正确选择，但有两个条件：

1. 实现查询深度和复杂度限制，防止滥用查询。
2. 为 feed resolver 实现应用层缓存（用短 TTL 缓存渲染后的 feed，如第 7 章讨论），弥补失去 HTTP 层缓存的影响。

4→1 的请求减少在移动网络上是显著胜利。服务器端复杂度是一次性投资。缓存策略需要思考，但第 7 章的积木可以直接套用。
