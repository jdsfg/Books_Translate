### 17.2 结构化日志——系统行为的文本记录

指标告诉你总体发生什么。出问题时，你需要详细了解发生了什么。这就是日志的角色。

考虑请求失败时产生的两种日志消息：

**非结构化日志：**


    ERROR: Failed to load user profile for request from 192.168.1.45


**结构化日志：**


    {
      "timestamp": "2024-01-15T14:47:23.441Z",
      "level": "ERROR",
      "service": "profile-service",
      "event": "profile_load_failed",
      "user_id": "user_8821934",
      "request_id": "req_9f2a1b3c",
      "upstream": "redis",
      "latency_ms": 30012,
      "error": "connection timeout"
    }


结构化日志机器可读。你可以查询它：“显示最近 10 分钟 `upstream == 'redis'` 的所有错误。”你可以计数：“每分钟每个服务发生多少次 `profile_load_failed` 事件？”你可以用 `request_id` 与其他日志关联。

非结构化日志是人类可读的字符串，需要正则解析、人工检查、在大规模时仔细看。当你有 1,000 台应用服务器每秒各产生 10,000 条日志时，它几乎没用。


#### 一条好日志条目的结构

每条结构化日志条目应包含：

1. **Timestamp**——毫秒精度、UTC 时区。来自不同服务的日志时间戳必须可比；时区歧义会造成抓狂的调试会话。
2. **Severity level**——DEBUG、INFO、WARN、ERROR、FATAL。级别让你过滤噪声：生产环境通常只看 INFO 及以上；调试时临时开启 DEBUG。
3. **Service and version**——哪个服务产生这条日志，以及运行代码的哪个版本。当缺陷部署然后修复后，你需要把日志事件与代码版本关联。
4. **Request ID（trace ID）**——每个用户请求入口生成的唯一标识符，并通过每次服务调用传播。这是跨服务关联日志的关键字段。
5. **Contextual fields**——任何与理解该事件相关的信息：`user_id`、`endpoint`、`upstream_service`、`latency_ms`、`error_code`。
