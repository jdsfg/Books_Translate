#### REST——Representational State Transfer

REST 是公共 Web API 的主流风格。它用 HTTP 动词（GET、POST、PUT、DELETE、PATCH）对由 URL 标识的资源表达 CRUD 操作。


    GET  /users/42                   → fetch user 42
    POST /users                      → create a new user
    PUT  /users/42                   → replace user 42's data
    PATCH /users/42                  → partial update of user 42
    DELETE /users/42/posts/101       → delete post 101 by user 42


响应通常是 JSON。REST 是无状态的：每个请求包含处理它所需的全部信息。

**REST 的优点：**

* 通用易懂——每个 HTTP 客户端都能消费 REST API，无需特殊工具
* 人类可读（URL 描述性强，JSON 可检查）
* 可缓存——GET 请求可在任何层缓存（CDN、浏览器、代理）
* 适合外部开发者会消费的公共 API

**REST 的缺点：**

**过度取回（Over-fetching）：** REST 端点返回完整资源。如果你只需要用户名和头像 URL，`GET /users/42` 会返回所有字段（简介、邮箱、粉丝数、加入日期等）。额外字段浪费带宽。

**取回不足（Under-fetching）：** 一个页面可能需要多个资源的数据。要展示 Alice 的资料页（含最近帖子和粉丝数），你可能需要：


    GET /users/42           → Alice's profile
    GET /users/42/posts     → Alice's recent posts
    GET /users/42/followers → Alice's follower count


三个独立 HTTP 请求，每个都有一次网络往返。


#### GraphQL——以查询作为 API

GraphQL 由 Facebook 开发，2015 年公开发布，专门用于解决 REST 的过度取回和取回不足问题。

在 GraphQL 中，客户端在查询中精确指定想要什么数据：


    query {
      user(id: 42) {
        username
        photoUrl
        posts(limit: 5) {
          title
          createdAt
        }
        followerCount
      }
    }


这个单一查询只返回请求字段——不多不少——在一个 HTTP 请求内完成。服务器从数据所在之处（数据库、缓存、另一个服务）解析每个字段。

**GraphQL 的优点：**

* 消除过度取回和取回不足
* 所有查询和变更都走单一端点
* 自文档化（schema 描述所有可用类型和操作）
* 极适合复杂嵌套数据获取（社交图、内容层级）
* 对带宽有限的移动客户端理想

**GraphQL 的缺点：**

* 服务器实现更复杂（需要 schema、每个字段的 resolver）
* 缓存更难——因为查询是带自定义 query body 的 POST 请求，HTTP 层缓存不适用；缓存必须在应用层做
* 过于灵活的查询可能成为安全问题（客户端可构造深嵌套查询，产生巨大数据库负载）
* 给服务器增加 GraphQL 运行时层
* 对习惯 REST 的 API 消费者学习曲线更陡

**何时选 GraphQL：** 当许多不同客户端（Web、移动、第三方开发者）需要以不同形态获取相同底层数据时。例如 Facebook 的 news feed 在 Web、Android、iOS 上渲染不同——但底层数据（帖子、用户、互动）相同。GraphQL 让每个客户端从单一 API 请求它需要的精确数据。
