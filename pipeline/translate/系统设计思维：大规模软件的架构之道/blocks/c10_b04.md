### 10.4 对象存储——媒体的可扩展方案

最适合 SocialSnap 头像照片的存储类型是**对象存储（object storage）**——一种完全不同的范式。

对象存储不使用分层目录结构。相反，它把**对象**（任意二进制数据 blob）存在扁平命名空间中，通过唯一 key 访问。把它想象成存储任意二进制数据的巨型键值存储。


#### 定义：对象存储

**对象存储** 将数据存为离散的**对象**，每个对象包含：

* 二进制数据本身（文件、图片、视频、文档——任何字节）
* 一个 **key**（唯一标识符——通常像路径：`users/42/profile-photo.jpg`）
* **元数据**（content type、自定义属性、标签）

对象通过 HTTP API 访问：用 `PUT /bucket/key` 上传，用 `GET /bucket/key` 下载。没有目录层次——“类路径”的 key 只是字符串。

典型例子：Amazon S3（Simple Storage Service）。概念模型：


    Bucket: socialsnap-media
        Object key: users/42/profile-photo.jpg
        Object key: users/42/cover-photo.jpg
        Object key: posts/1001/photo-1.jpg
        Object key: posts/1001/photo-2.jpg
        Object key: posts/1001/photo-3.jpg


这些 key 看起来像路径，但只是字符串——没有真实目录结构。列出“用户 42 的所有对象”是前缀搜索：`LIST objects WHERE key STARTS WITH "users/42/"`。


#### 为什么对象存储能扩展

**无限容量：** 对象存储在成千上万个存储节点上水平扩展。从用户视角看没有实际容量限制——你只管存更多对象。存储供应商处理分布式扩展。

**高持久性：** S3 宣传 99.999999999%（十一个 9）的持久性。对象自动复制到多个可用区（availability zone，保障可用性的物理独立数据中心）。如果一个数据中心故障，你的对象幸存。这比单服务器磁盘持久得多。

**直接 HTTP 访问：** 对象通过 HTTP 直接提供。你的应用服务器不需要从存储流式传输文件——你生成一个签名 URL，客户端浏览器直接从对象存储获取图片。这意味着应用服务器的带宽不被媒体文件服务消耗。

**大规模便宜：** 对象存储每月约 0.02–0.03 USD/GB。一个 SocialSnap 用户上传 50 次头像照片（每次 2 MB），每月存储成本约 0.002 USD。经济学与把同样数据存在 SSD 数据库中根本不同。
