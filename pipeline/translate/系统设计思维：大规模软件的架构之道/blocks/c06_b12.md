医疗数据有严格的监管和正确性要求（美国 HIPAA），但记录结构确实是异构的。考虑记录的哪些部分需要强一致性（药物列表），哪些部分更自然呈文档形状（临床笔记）。答案可能是“使用关系型数据库，但为灵活部分使用 JSON/JSONB 列”——这是一种常见的混合模式。

**答案：**

**第 1 步：访问模式。** 读：医生打开一份患者记录，同时看到所有组成部分——人口统计、笔记、药物、最近实验室结果。这主要是“按 ID 取一名患者记录”的操作。写：笔记和实验室结果频繁追加；药物更新（开始/停止）。复杂查询：“找出所有正在服用药物 X 且肌酐升高的患者”——这需要跨记录聚合，是关系型查询。

**第 2 步：schema 稳定性。** 人口统计和药物部分是稳定的（固定字段）。临床笔记是异构的（可变部分）。实验室结果有定义好但可变的测试代码集合。

**第 3 步：一致性要求。** **不可谈判：药物列表的强一致性。** 医生看到旧的药物列表（漏掉最近处方或显示已停药）可能导致有害的药物相互作用。同样，实验室结果值必须准确。这排除了默认最终一致的系统，如 Cassandra 或默认配置的 DynamoDB。任何影响治疗决策的数据都需要 ACID 保证。

**第 4 步：规模。** 一家拥有数千名患者的医疗初创公司数据量很小——单节点 PostgreSQL 可轻松处理多年。

**推荐：关系型数据库（PostgreSQL），为临床笔记使用 JSONB 列。**


    CREATE TABLE patients (
        id              SERIAL PRIMARY KEY,
        name            VARCHAR(200) NOT NULL,
        dob             DATE NOT NULL,
        insurance_id    VARCHAR(100)
    );

    CREATE TABLE medications (
        id              SERIAL PRIMARY KEY,
        patient_id      INTEGER REFERENCES patients(id),
        drug_name       VARCHAR(200) NOT NULL,
        dosage          VARCHAR(100),
        frequency       VARCHAR(100),
        started_on      DATE NOT NULL,
        ended_on        DATE  -- NULL means still active
    );

    CREATE TABLE clinical_notes (
        id              SERIAL PRIMARY KEY,
        patient_id      INTEGER REFERENCES patients(id),
        note_type       VARCHAR(50),
        author_id       INTEGER REFERENCES users(id),
        created_at      TIMESTAMP DEFAULT NOW(),
        body            TEXT,
        metadata        JSONB  -- variable fields per note type
    );


`clinical_notes` 上的 `JSONB` 列处理可变元数据，无需单独文档存储。如果需要查询特定属性，PostgreSQL 可以为 JSONB 字段建索引。ACID 事务确保药物条目及其对应临床笔记（如果一起写入）要么都提交，要么都不提交。

**为什么不用纯文档存储？** 跨记录分析查询（“服用药物 X 且肌酐升高的患者”）需要跨多名患者 join 药物记录和实验室结果。文档存储需要扫描每个患者文档并在应用代码中过滤——慢且复杂。在关系型模型中，这是 SQL join。
