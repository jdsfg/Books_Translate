### 16.8 侦探线索链——读取日志和指标

事故发生时，第一个挑战不是修复——而是理解发生了什么。系统发出的日志和指标就是证据。正确读取它们是把快速修复事故的工程师与手忙脚乱的工程师区分开的侦探技能。

SocialSnap Redis outage 中，关键线索一直存在于监控数据中：

**线索 1——Redis 错误率攀升。** Redis 客户端库记录连接错误和超时。Redis 错误率随时间变化的图显示下午 2:47 开始急剧上升。这是最早信号——事故开始时根因已经可见。

**线索 2——应用服务器延迟增加。** 应用服务器 P99 延迟（第 99 百分位响应时间——最慢 1% 请求）从 200ms 增加到 30 秒。这与 Redis 超时时间一致。应用在等待 Redis。延迟增加比 Redis 错误率滞后约 30 秒——一次完整超时循环所需时间。

**线索 3——线程池饱和。** JVM（或 Python WSGI）监控显示活跃线程数接近线程池上限。这是机制线索：为什么延迟增加？因为线程被等待的请求占用。

**线索 4——错误率激增。** 负载均衡器“503 响应”指标飙升至接近请求 100%。这是用户可见影响——事故“被宣布”的信号。

线索时间线：Redis 错误 → 应用延迟增加（滞后 30 秒）→ 线程池饱和 → 503 错误。每条线索解释下一条。实时阅读该序列的工程师可以反向追踪级联：503 错误由线程池耗尽导致，线程池耗尽由 Redis 超时延迟导致，Redis 超时由 Redis 错误导致。

原则：**监控领先指标，而不只是滞后指标。** 错误率和延迟是滞后指标——它们在系统已经影响用户后才告诉你失败。Redis 错误率是领先指标——它在用户受影响前告诉你失败正在开始。良好的可观测性意味着监控用户可见失败之前的依赖项和内部指标，而不仅仅是用户可见失败本身。
