#### Cache-Aside 算法

读取一个值：


    1. Look up the key in the cache
    2. If cache HIT:
       - Return the cached value
    3. If cache MISS:
       - Query the database for the value
       - Store the value in the cache with a TTL
       - Return the value to the caller


写入新值：


    1. Write the new value to the database
    2. Invalidate (delete) the old cached value — OR — update it in the cache


让我们用 SocialSnap 走一遍。用户请求 Alice 的资料时：

**第一次请求（冷缓存）：**

1. 应用检查缓存 key `user:1:profile` —— 未命中
2. 应用查询数据库：`SELECT * FROM users WHERE id = 1`
3. 应用把结果存入缓存，key `user:1:profile`，TTL = 5 分钟
4. 应用返回 Alice 的资料

**第二次到第 N 次请求（热缓存）：**

1. 应用检查缓存 key `user:1:profile` —— 命中
2. 应用立即返回缓存的资料——无需数据库查询

**Alice 更新简介：**

1. 应用把新简介写入数据库
2. 应用从缓存中删除（使失效）`user:1:profile`
3. 下一次请求 Alice 的资料触发未命中，从数据库取回新鲜数据


#### 为什么使失效而不是更新？

Alice 更新简介时，为什么删除缓存条目而不是用新值更新它？

因为失效更简单也更安全。如果你更新缓存，必须保证缓存写入和数据库写入原子成功——而跨两个独立系统这是不可能的。如果数据库写入成功但缓存更新失败（或相反），它们就不同步了。通过在写入时使缓存条目失效，你确保下一次读取从数据库取回新鲜数据。缓存条目永远不会陈旧；它只是过期或被显式删除。

代价：失效后的第一次请求总是缓存未命中。但这是正确的 tradeoff（权衡）——短暂性能下降比无限期提供错误数据更好。


#### 定义：TTL（生存时间）

**TTL（Time-to-Live，生存时间）** 是一个时长，超过该时长后缓存条目自动视为过期并从缓存中移除。客户端请求过期条目时，缓存返回未命中，应用重新取回新鲜数据。

通俗语言：TTL 是缓存数据的过期日期。5 分钟（或 1 小时、1 天——由你选择）后，缓存值被丢弃，下一次请求会拉取新鲜数据。

TTL 是确保缓存数据不会偏离真相太远的主要机制。但它引入了一个基本性质：**在 TTL 窗口内，用户可能看到旧数据**。因此设置 TTL 是一个直接调节新鲜度与性能 tradeoff（权衡）的旋钮。
