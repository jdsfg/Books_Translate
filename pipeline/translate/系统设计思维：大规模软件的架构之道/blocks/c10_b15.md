**关键洞察：** 通过把第 4 步设为异步，旧照片删除失败永远不会造成用户可见错误。通过把第 1 步设为首个操作，失败总是干净中止（权威存储还未提交任何内容）。

**Q3.**（联系第 7 章缓存和第 9 章 CDN 讨论）SocialSnap 把头像照片存在对象存储并通过 CDN 服务。用户上传新头像后，即使新照片已上传到对象存储，仍有哪些缓存可能继续提供旧照片？描述如何使每层缓存失效。包括：对象存储 URL 模式、Redis 资料缓存、CDN、浏览器缓存。

提示

每个缓存层有不同的失效机制。对象存储本身不是缓存，但存在 PostgreSQL 中并被 Redis 缓存的 URL 是。CDN 按 URL 缓存图片文件。浏览器按 URL 用 HTTP 缓存头缓存。如果每次上传 URL 都改变，这对其他缓存意味着什么？

**答案：**

**关键洞察——URL 版本化消除了大多数失效问题：**

用户上传新头像时，应用生成包含版本标识的新对象 key：


    旧 key: users/42/profile_photo_v3.jpg  → URL: https://cdn.socialsnap.com/users/42/profile_photo_v3.jpg
    新 key: users/42/profile_photo_v4.jpg  → URL: https://cdn.socialsnap.com/users/42/profile_photo_v4.jpg


因为每次上传 URL 都变，旧 URL 的 CDN 和浏览器缓存根本不会再被请求——它们会通过 TTL 自然过期，不需要主动失效。新资料请求使用数据库中的新 URL，指向新照片。

**逐层缓存：**

**1. 对象存储（不是缓存，而是源）：** 新照片作为新对象、新 key 上传。旧对象在异步清理作业删除前一直存在。这里不需要失效——两个对象无害共存。

**2. PostgreSQL `users.photo_url` 列：** 在上传序列第 2 步同步更新。现在存新 URL。这是权威记录——所有其他缓存都源自它。

**3. Redis 资料缓存（`user:42:profile`）：** 包含序列化用户资料（含旧 `photo_url`）。必须显式失效（上传序列第 3 步：`DEL user:42:profile`）。删除后，下一次资料读取从 PostgreSQL 取新数据（现在含新 URL），并重新缓存正确条目。如果 Redis 失效失败（网络闪断），资料缓存会在最多 TTL 分钟内继续服务旧 URL——这是第 7 章的陈旧性 bug 模式。

**4. CDN 对旧图片 URL 的缓存：** 由于旧 URL（`profile_photo_v3.jpg`）在资料缓存失效后不再被任何应用代码引用，没有用户会再请求它。CDN 中旧 URL 条目会简单地通过 TTL 过期（对不可变媒体文件通常设为小时或天）。不需要主动 CDN purge，因为 URL 已经改变。
