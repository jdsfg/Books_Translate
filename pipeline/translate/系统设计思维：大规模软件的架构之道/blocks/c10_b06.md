### 10.5 SocialSnap 的媒体问题——头像照片放哪里？

让我们把这个框架应用到 SocialSnap 的具体问题。

**需求：**

* 为（最终）数百万用户存储头像照片
* 向查看资料的用户提供头像照片——高读取量、低延迟重要
* 照片上传不频繁（用户很少更新头像），但读取非常频繁
* 照片应能经受服务器故障和数据中心问题
* 头像照片大小从 50 KB 到 5 MB

**方案评估：**

**方案 1：把照片作为 bytea（blob）列存在 PostgreSQL 中**


    ALTER TABLE users ADD COLUMN profile_photo BYTEA;


这对少量用户有效。大规模下多方面失败：

* PostgreSQL 的 B-tree 索引优化小值。在表中存 2 MB blob 会降低索引性能——页面巨大，缓冲池（RAM 缓存）被大 blob 填满，而不是索引页面和对查询性能重要的行数据。
* 每次用户资料查询都会加载整个 blob，即使查询只需要用户名。
* 向浏览器提供照片需要：从 PostgreSQL 读取 → 加载到应用服务器内存 → 流式传输到浏览器。应用服务器的网络带宽被照片服务消耗。
* PostgreSQL 的持久化模型（WAL、fsync）对文件数据增加了不必要开销。

**方案 2：存在应用服务器本地文件系统**


    /var/socialsnap/photos/user_42_profile.jpg


这比数据库有改进，但引入不同问题：文件在某一台特定服务器上。当 SocialSnap 增加应用服务器（第 11 章）时，哪台服务器有用户 42 的照片？如果存照片的服务器宕机，照片不可用。如果 SocialSnap 有 10 台服务器，你需要某种方式把照片请求路由到存文件的特定服务器——应用路由与存储位置紧耦合。

**方案 3：存在对象存储中（正确答案）**


    Bucket: socialsnap-media
    Key: users/42/profile_photo_v3.jpg


照片上传工作流：

1. 用户通过浏览器上传照片。
2. 应用服务器接收上传。
3. 应用服务器处理图片（调整大小、压缩、生成缩略图——这些是通过消息队列的后台操作，第 8 章）。
4. 应用服务器把处理后的照片上传到对象存储：`PUT users/42/profile_photo_v3.jpg`。
5. 应用服务器在 PostgreSQL 中存储对象存储 URL：`UPDATE users SET photo_url = 'https://storage.socialsnap.com/users/42/profile_photo_v3.jpg' WHERE id = 42`。
6. 使用 Redis 使该用户资料缓存失效（第 7 章）：`DEL user:42:profile`。

照片服务工作流：

1. 用户请求 Alice 的资料页。
2. 应用返回资料页，包含 `<img src="https://storage.socialsnap.com/users/42/profile_photo_v3.jpg">`。
3. 用户浏览器直接从对象存储获取图片——完全绕过应用服务器。
4. 对高流量资料，对象存储 URL 经过 CDN（第 9 章），图片从最近边缘节点提供。
