#### 写通缓存

在 **写通缓存** 中，每次写入同时进入数据库和缓存。缓存始终与数据库保持同步。

**写入路径：**


    1. Write value to database
    2. Write value to cache
    3. Return success


**读取路径：**


    1. Check cache — almost always a HIT (cache is always up to date)
    2. On miss (first access or cache restart): fetch from database


**收益：** 缓存从不过期。读取几乎总是命中缓存。

**代价：** 每次写入需要两个操作（数据库 + 缓存）。写入延迟增加。如果你写入的数据永远不会被读取，就浪费了缓存空间和写入开销（“写放大”问题）。

写通在读写比高且能承受写入开销时表现良好。用户资料——读数千次、很少更新——是好候选。


#### 写回缓存

在 **写回缓存** 中，写入立即进入缓存，并在延迟后异步刷到数据库。

**写入路径：**


    1. Write value to cache (fast, in-memory)
    2. Mark the entry as "dirty" (pending flush to database)
    3. Return success immediately
    4. [Background process] Flush dirty entries to database at regular intervals


**收益：** 写入以缓存速度完成——毫秒级。如果一个 key 每秒更新 100 次，数据库只接收最新值（合并写入），大幅降低数据库负载。

**代价：** **持久性风险。** 如果缓存服务器在脏条目刷盘前失败，数据就丢失了。你已经向用户返回成功，但数据从未持久化。

写回用于特定的高写入场景，其中一些数据丢失可接受（分析事件、计数器、非关键指标）。它几乎从不用于需要持久性的事务数据。

回想第 5 章，ACID 的 D——**持久性（Durability）**——意味着已提交事务在失败中幸存。写回缓存用持久性换取写入性能。这正是权衡矩阵追踪的 tradeoff（权衡）类型。


#### 常见误解

许多工程师假设 cache-aside 总是正确的默认。它是最常见模式，但有一个隐藏成本：**惊群问题（thundering herd）**。当缓存 key 过期（或被失效）时，所有原本在缓存命中后等待的请求现在同时命中数据库。如果某个缓存条目每秒服务 5,000 个请求，它过期时，5,000 个请求会在同一秒落到数据库。数据库此前几乎不处理这个 key 的负载，突然收到流量尖峰。

写通避免这个问题：写入时缓存立即重新填充，所以条目从不真正缺失。对热 key（被巨量请求访问的数据），写通通常更可取，正因为它消除了惊群。


### 7.5 驱逐——缓存满了怎么办

缓存驻留在内存中。内存昂贵且有限。最终缓存会满。当你尝试添加新条目时，必须移除某些东西。决定移除什么的策略就是**驱逐策略（eviction policy）**。
