### 6.5 图数据库——关系作为一等公民

回想本章开头的第二个谜题：一个有 50 billion（500 亿）条友谊边、需要高效回答“Alice 的朋友的朋友都有谁？”的社交网络。

在关系型数据库中，友谊是一张表：


    CREATE TABLE friendships (user_id INTEGER, friend_id INTEGER, PRIMARY KEY (user_id, friend_id));


“Alice 的朋友”是：`SELECT friend_id FROM friendships WHERE user_id = alice_id`

“Alice 的朋友的朋友”需要自 join：


    SELECT DISTINCT f2.friend_id
    FROM friendships f1
    JOIN friendships f2 ON f1.friend_id = f2.user_id
    WHERE f1.user_id = alice_id
      AND f2.friend_id != alice_id;


50 billion（500 亿）行的情况下，这个 join 极其昂贵。“朋友的朋友的朋友”（3 跳）需要三次自 join——基本不可用。

图数据库把数据原生存为节点（node，实体）和边（edge，关系）。每条边直接指向它连接的节点。从 Alice 到她的朋友就是跟随指针——而不是表扫描或 join。


    Node: Alice (id: 1)
      → FRIENDS_WITH → Node: Bob (id: 2)
      → FRIENDS_WITH → Node: Carol (id: 3)
      → FRIENDS_WITH → Node: Dave (id: 4)

    Node: Bob (id: 2)
      → FRIENDS_WITH → Node: Eve (id: 5)
      → FRIENDS_WITH → Node: Alice (id: 1)


找 Alice 的朋友：跟随 Alice 节点的所有 `FRIENDS_WITH` 边。O(Alice 的度数)——与图总大小无关。

找朋友的朋友：从每个朋友再跟随边。仍是 O(k²)，k 是平均度数——比全表扫描好得多。


#### 图数据库何时胜出

**社交网络：** 好友推荐、“你可能认识的人”、社区发现。

**推荐引擎：** “买了 X 的人也买了 Y”是图遍历。

**欺诈检测：** 金融交易/事务图（transaction graph；transaction 即“事务”）中可疑模式是环或不寻常路径。

**知识图谱：** 实体之间复杂关系网（搜索引擎用它驱动“相关问题”和相关概念建议）。


#### 图数据库的 Tradeoffs（权衡）

**收益：** 高效多跳遍历、关系型数据自然建模、表达力强的图查询语言（Neo4j 的 Cypher）。

**代价（规模）：** 图数据库通常不如其他 NoSQL 类型容易分布。一个放不进单台机器的图很难分片——因为任何边都可能连接不同机器上的节点，让每次遍历都变成网络调用。大多数图数据库在中小型图上表现良好（数百亿节点和边是表现良好的前沿）。

**代价（查询类型）：** 图数据库为遍历优化。聚合查询（“本周有多少用户注册”）在图数据库中通常比在关系型数据库中慢。它们是专门工作负载的专用工具。
