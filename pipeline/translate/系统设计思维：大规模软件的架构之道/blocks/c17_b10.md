#### 概念检测

**Q1.** Gauge 和 Histogram 有什么区别，各自何时使用？

**答案：** Gauge 测量某时刻当前状态，可增可减——适合“现在值是多少？”的问题，如当前内存用量、当前队列深度、当前活跃连接数。Histogram 记录许多观察值在预定义桶中的分布——适合“这个测量值的分布如何？”的问题，如请求延迟、响应大小、队列等待时间。当你关心当前水平时用 gauge；当你关心大量测量值的分布和尾部行为时用 histogram。

**Q2.** 当 CPU 使用率超过 80% 时触发监控告警。这是什么类型告警，有什么弱点？

**答案：** 这是基于原因的告警——它对可能指示问题的基础设施指标触发，而不是用户可见症状。弱点：(1) CPU 高可能出于良性原因（批处理作业、JVM 垃圾回收、缓存预热）而没有任何用户影响，产生误报。(2) CPU 低不能保证服务良好——服务可能有 20% CPU 但因返回错误很快的 bug 而完全失败。(3) 它不直接测量用户体验。更好的替代是告警“错误率超过 1%”或“p99 延迟超过 SLO 阈值”——这些症状直接表明用户正在经历问题。

**Q3.** 什么是错误预算？它如何改变开发与运维团队的关系？

**答案：** 错误预算是给定 SLO 下允许失败的请求（或时间）比例。对于 99.9% 可用性 SLO，0.1% 请求可以失败——这就是预算。它通过量化部署的可接受风险改变团队动态。预算健康时，开发团队有权激进部署。预算快耗尽时，组织放慢部署以保护可靠性。这创造了共同激励：开发团队不能无限制要求部署速度而不接受失败会消耗预算；运维团队也不能以稳定之名阻止所有部署而不量化成本。

**Q4.** 为什么 `request_id` 字段是调试分布式系统时结构化日志中最重要的字段？

**答案：** `request_id` 是关联键，让你把参与处理同一用户请求的多个服务的日志条目缝合起来。没有它，你有多股日志流，却无法确定服务 B 中哪些日志条目对应服务 A 中看到的某个特定错误。有了它，你可以过滤所有服务中单个 `request_id` 的日志，看到该特定请求被完整处理的 chronological 记录——它触碰了哪些服务、每个服务做了什么、时间花在哪里、哪里出错。这是分布式追踪的人工等价物，在完整追踪基础设施就位前 indispensable。
