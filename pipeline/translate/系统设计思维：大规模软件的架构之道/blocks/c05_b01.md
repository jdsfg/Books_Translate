我们离开 SocialSnap v0 时，它还是笔记本电脑上的一个 Python 函数。这个函数返回博客帖子，数据住在……某个地方。也许是 Python 字典，也许是 JSON 文件。三个用户时怎么都行。

现在我们需要给 SocialSnap 的数据一个真正的家。而有一样东西已经主导软件工程五十年：关系型数据库。

为什么是五十年？因为关系模型解决了一个真正的问题——它赋予数据一种结构，可以用灵活的方式查询，而不必每次问题变化都改代码。在关系型数据库之前，数据的存储方式把应用与存储格式紧紧耦合。如果你把数据存成树（层次模型），每次查询都要遍历树。问题变了，遍历代码就得改。关系模型打破了这种耦合。你定义一次数据，SQL 让你问任何问题。

但关系模型不是魔法。它做出了特定的 tradeoff（权衡），使其对某些工作负载极佳，对其他工作负载不适用。理解这些 tradeoff（权衡）是本章的目标。

让我们给 SocialSnap 它的第一个数据库。


### 5.1 关系模型——数据即表

在文档存储、图数据库、键值存储都曾承诺要取代它之后，是什么让关系模型如此持久？

想象你在设计 SocialSnap 的存储。你要存用户、他们的帖子，以及它们之间的关系。怎么组织？

关系模型的答案：**表（table）**。每张表代表一种实体类型。每一行代表该实体的一个实例。每一列代表一个属性。

SocialSnap 的初次尝试：

**users 表**

| id | username | email | password_hash | created_at |
|---|---|---|---|---|
| 1 | alice | alice@example.com | `$2b$12...` | 2024-01-15 |
| 2 | bob | bob@example.com | `$2b$12...` | 2024-01-20 |
| 3 | carol | carol@example.com | `$2b$12...` | 2024-02-01 |

**posts 表**

| id | user_id | content | created_at |
|---|---|---|---|
| 101 | 1 | "Just launched SocialSnap!" | 2024-01-15 |
| 102 | 2 | "Hello world from Bob" | 2024-01-21 |
| 103 | 1 | "Second post!" | 2024-01-22 |

注意 posts 表里的 `user_id` 列。Post 101 的 `user_id = 1`，指向 users 表中的 Alice。这就是**外键（foreign key）**——一张表中的列引用另一张表的主键。外键是关系模型表达关系的方式。


#### 定义：关系模型

**关系模型** 把数据组织成**关系（relation）**（即表），其中：

* 每张表有一个 **schema**（定义好的列集合及类型）
* 每一行都满足该 schema
* 表之间的关系通过 **外键** 表达（一张表中的列引用另一张表的主键）
* 数据使用 **SQL**（Structured Query Language，结构化查询语言）查询，SQL 可以组合、过滤、聚合多张表的数据

plain 语言：数据存在表里，表之间通过共享 ID 关联，你用 SQL 向数据提问。
