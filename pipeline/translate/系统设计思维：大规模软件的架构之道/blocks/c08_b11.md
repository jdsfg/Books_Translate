**答案：** 在**点对点队列**中，每条消息正好投递给一个消费者。多个消费者竞争队列中的消息——这对并行化工作有用（多个工作节点处理同一队列的订单）。但每条消息只到一个工作节点。

在 **pub-sub** 中，发布到主题的消息投递给所有订阅者。每个订阅者得到自己的副本。订阅者相互独立——新增订阅者不影响现有订阅者，发布者也不需要知道谁在订阅。

**选择 pub-sub 当：** 一个事件有多个独立消费者感兴趣。SocialSnap 的注册事件对邮件服务、分析、联系人通知和 onboarding 都感兴趣。如果你用点对点队列，需要四个单独队列（每个消费者一个），注册服务要向四个队列发布。Pub-sub 把它合并：一个主题、四个订阅者、一次发布。

**选择点对点当：** 你想让多个工作节点处理同一队列以并行化工作。十个邮件服务工作节点都读同一队列意味着十封邮件并行处理——每封邮件只由一个工作节点处理。Pub-sub 会给每个工作节点自己的订阅，十个工作节点都会发送每封邮件。

常见组合：在 fan-out 层用 pub-sub（一个事件 → 多个消费者），在每个消费者类型内部用点对点（该类型的多个工作节点共享一个队列）。

**Q4.** 消息消费者“幂等”是什么意思？为什么幂等性对至少一次投递系统是必需的？

**答案：** 如果一个操作执行多次的效果与执行一次相同，它就是**幂等的（idempotent）**。门锁是幂等的：门已经锁着时按“锁”不会有什么新效果。发送欢迎邮件不是天然幂等的：按“发送”两次会发两封邮件。

**为什么至少一次投递需要幂等：** 至少一次投递通过重投未收到确认的消息来保证不丢失消息。这意味着消费者偶尔会多次收到同一条消息（如崩溃恢复后）。如果消费者不幂等，重复消息造成重复效果：重复邮件、重复扣款、重复记录。

让“发送欢迎邮件”消费者幂等：


    def process_signup_event(event):
        user_id = event['user_id']

        # Check if we already sent the welcome email
        already_sent = db.query(
            "SELECT 1 FROM sent_emails WHERE user_id = %s AND type = 'welcome'",
            [user_id]
        )

        if already_sent:
            return  # Idempotent: do nothing on duplicate

        # Send the email
        email_service.send_welcome_email(user_id)

        # Record that we sent it
        db.execute(
            "INSERT INTO sent_emails (user_id, type) VALUES (%s, 'welcome')",
            [user_id]
        )


先检查后行动的模式把非幂等操作变成幂等操作。代价：每条消息多一次数据库读。收益：在至少一次投递下保证安全。
