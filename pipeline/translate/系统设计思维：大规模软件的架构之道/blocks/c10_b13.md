#### 应用问题

**Q1.** SocialSnap 想增加视频上传：用户可以上传短视频（最长 60 秒，每个最大 100 MB）。上传后，视频应转码为多种分辨率（360p、720p、1080p）以供自适应流播放。设计该功能的存储和处理架构。说明：原始上传存在哪里、如何触发转码（联系第 8 章）、转码后文件存在哪里、以及如何向用户提供服务。

提示

想想上传路径：上传后视频首先去哪里？然后想转码：计算密集，不应在上传时同步发生。第 8 章的模式适用。最后想服务：用户如何播放 100 MB 视频而不等待整个文件下载？

**答案：**

**上传路径：**

1. 用户在 SocialSnap 应用中选择视频文件。
2. 应用向应用服务器请求**预签名上传 URL**（视频上传 API）：`POST /api/videos/upload-url`。服务器生成一个有效期 1 小时的签名 S3 URL，允许直接上传到对象存储。
3. 应用使用签名 URL 直接把原始视频**上传到对象存储**——完全绕过应用服务器。100 MB 视频上传不消耗应用服务器带宽。
4. 原始视频存于：`raw-uploads/user_42/video_abc123.mp4`。
5. 对象存储触发事件（通过 SNS/webhook），或上传完成信号通知应用服务器，服务器发布 `video.uploaded` 事件到消息队列（第 8 章）。

**转码路径（异步，通过消息队列）：**


    消息队列事件：{
      "event_type": "video.uploaded",
      "user_id": 42,
      "raw_key": "raw-uploads/user_42/video_abc123.mp4",
      "video_id": "vid_abc123"
    }


视频转码服务（消息队列消费者）读取该事件并：

1. 从对象存储下载原始视频。
2. 转码为 360p、720p、1080p 分辨率（计算密集，可能需要数秒到数分钟）。
3. 上传转码后文件到对象存储：
   * `videos/vid_abc123/360p.mp4`
   * `videos/vid_abc123/720p.mp4`
   * `videos/vid_abc123/1080p.mp4`
   * `videos/vid_abc123/playlist.m3u8`（HLS 自适应流清单）
4. 更新 PostgreSQL 的 `videos` 表：标记视频状态为 `status = "ready"`。
5. 发布 `video.transcoding_complete` 事件给任何下游消费者（通知上传者、搜索索引更新等）。

多个转码工作节点并行读取队列（点对点队列，第 8 章）：10 个工作节点可同时转码 10 个视频，为计算密集型步骤提供水平扩展。

**服务路径：**

视频使用 **HLS（HTTP Live Streaming）** 提供：视频被切成小片段（每段 2-10 秒），一个清单文件（`.m3u8`）列出每个分辨率的片段。播放器下载清单，然后按需请求片段，网络带宽下降时自动切换到更低分辨率。

所有视频文件通过 CDN 提供（第 9 章）。CDN 在边缘节点缓存视频片段。观看同一热门视频的用户从最近 CDN 边缘节点服务——每个 CDN 区域每个视频只访问一次源对象存储，而不是每个观看者都访问。
