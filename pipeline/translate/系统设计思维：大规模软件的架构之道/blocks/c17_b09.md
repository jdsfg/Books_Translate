### 17.5 SocialSnap v6 复盘

让我们回到第 16 章的周二故障，用可观测性视角审视。具备合适可观测性基础设施的 SocialSnap v6 会经历同样的 Redis 降级——但响应将截然不同。

下午 2:47，Redis 集群开始降级。30 秒内：

* Redis 连接的**错误率计数器**开始攀升，2:47:30 超过告警阈值（2% 错误率）。告警触发。
* Redis 操作的**延迟直方图**显示 99 百分位超过 5 秒。另一条告警触发。
* 应用服务器的**结构化日志**开始积累 `ERROR` 条目，`"upstream": "redis", "error": "connection timeout"`。
* **分布式追踪**显示所有长耗时请求都有 Redis 超时的 span。

到 2:48——降级开始一分钟——on-call 工程师收到 page：“Redis 错误率 18%，p99 延迟 28 秒。”Runbook 说：检查 Redis 集群状态，检查熔断器是否已打开。

第 16 章的熔断器已经开始触发。应用正通过数据库回退提供降级 feed 内容，而不是从 Redis 缓存提供。用户看到略陈旧的 feed，但应用没有返回 503 错误。

工程师查询日志：“显示过去 5 分钟 `upstream == 'redis'` 的 ERROR 日志。”他们看到 847 条错误。查看 Redis 仪表盘，发现有一个 Redis 节点——shard 2 的主库——内存压力异常高。他们发起 shard 2 到其副本的故障转移。

到 2:51——降级开始四分钟——Redis shard 2 恢复健康。错误率回到正常。熔断器闭合。feed 恢复完整质量。用户总影响：数据在 shard 2 上的用户经历 4 分钟略陈旧的 feed。没有 503 错误。没有完整故障。

未观测到的周二故障（20 多分钟完全失败）与观测到的版本（4 分钟优雅降级）之间的差异不是架构差异——而是认知差异。知道正在发生什么是响应它的前提。
