#### 测试金字塔再审视

经典“测试金字塔”建议：大量单元测试（快速、廉价、隔离），较少集成测试（较慢、更贵、测试组件交互），更少端到端测试（最慢、最贵、测试完整系统）。该模型为单体应用设计，其中“集成”意味着测试几个模块一起工作。

对分布式系统，金字塔增加额外层级：

1. **单元测试**——隔离测试单个函数和类
2. **服务集成测试**——在测试环境中用真实依赖（真实数据库、真实缓存、真实队列）测试单个服务
3. **契约测试**——测试两个服务之间的 API 契约兼容（该服务产生的响应格式是否符合服务 B 的期望）
4. **端到端测试**——测试完整系统中的完整用户旅程
5. **性能/负载测试**——在真实流量水平下测试系统行为
6. **混沌测试**——以受控方式测试依赖失败时的系统行为

每一层捕获不同类别的缺陷。针对真实 PostgreSQL 实例的服务集成测试能捕获“这条 SQL 查询在 SQLite 单元测试中通过，但在 PostgreSQL 上有语法错误”。契约测试捕获“feed 服务改成返回 `authorName`，但渲染服务仍期望 `author_name`”。负载测试捕获“Redis 连接池设为 10 个连接，5000 RPS 时我们耗尽它。”


#### 常见误解

分布式系统最常见的测试误解是：全面的单元测试覆盖率足以支撑对生产的信心。工程师有时把单元测试覆盖率当作整体质量的代理。它不是。一个单元测试覆盖率 95% 但没有集成测试的代码库，可能在每次数据库交互、每次 API 响应解析、每次超时配置中都存在未检测到的缺陷。覆盖率衡量测试期间执行了多少代码，而不是测试了多少失败模式。


### 18.2 集成与负载测试——测试交互


#### 集成测试

服务集成测试让单个服务针对真实（或真实感）的依赖实例运行。对 SocialSnap 的 Feed Service，集成测试可能：

1. 启动一个 PostgreSQL 实例（测试环境用 Docker）
2. 填充测试数据（10 个用户、50 条帖子）
3. 启动一个 Redis 实例
4. 启动配置为指向这些测试实例的 Feed Service
5. 向 Feed Service 发 HTTP 请求
6. 断言响应

这种测试比单元测试慢得多——可能 5–30 秒——但它捕获单元测试完全遗漏的一类缺陷：真实数据库查询缺陷、真实序列化错误、真实认证流程问题。

集成测试应在 CI（持续集成）中运行——每次 pull request 自动运行——但因为速度较慢，不必作为本地开发循环的一部分。
