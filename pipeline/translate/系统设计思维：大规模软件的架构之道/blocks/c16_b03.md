#### 定义：单点故障

**单点故障（single point of failure，SPOF）** 是任何故障会导致整个系统失败的组件。如果移除该组件系统就宕，它就是 SPOF。

plain 语言：如果你某个东西只有一份，它失败整个系统就失败。一个数据库、一台服务器、一条网络路径——在添加冗余前都是 SPOF。

SocialSnap 早期架构（第 1 章）中，每个组件都是 SPOF：一台笔记本、一个数据库、一个进程。随着架构演进，SPOF 被逐步消除：

* 负载均衡器后的多台应用服务器（第 11 章）消除了应用服务器 SPOF。
* 带自动故障转移的读副本（第 12 章）减少了数据库 SPOF（主库失败时提升副本为主库）。
* Redis Sentinel 或 Redis Cluster（第 11 章）消除了 Redis 会话存储 SPOF。
* 云基础设施的多个可用区消除了数据中心 SPOF。

消除 SPOF 是高可用性（high availability）的第一步。但仅冗余不够——冗余组件必须独立失败。如果两台服务器共享同一电源，失去电源会同时让两台“冗余”服务器宕机。这就是**共模故障（common mode failure）**：一个原因同时影响多个 supposedly 独立的组件。

真正冗余的实践原则：

* 在不同可用区运行冗余组件（独立电源、网络、散热基础设施）
* 尽可能使用不同硬件厂商或实例类型
* 把数据副本存在不同物理磁盘阵列
* 通过独立网络路径路由流量


### 16.3 故障转移——主备与主主

冗余提供备份组件。故障转移是从失败组件切换到备份的过程。


#### 主备故障转移（Active-Passive Failover）

在**主备（active-passive）**故障转移中，一个实例活跃（处理流量），一个或多个实例被动（待命，准备接管）。被动实例在正常条件下不服务任何流量。

活跃实例失败时，**故障转移机制**检测失败并把被动实例提升为活跃。流量被重定向到新活跃实例。

例子：

* PostgreSQL 主库加热备副本。副本实时复制主库。主库失败时，副本被提升为主库（PostgreSQL 流复制自动故障转移 via Patroni，或使用 AWS RDS Multi-AZ）。
* 一主一备负载均衡器。主负载均衡器失败时，备用接管（使用在它们之间漂移的虚拟 IP）。

主备故障转移更容易推理——同一时刻只有一个活跃实例，所以不存在两个实例同时接受写并产生冲突的风险。代价：被动实例在正常操作中“浪费”——你为它付费，但故障发生前不处理流量。此外，故障转移不是瞬时的——活跃实例失败与被动实例变活跃之间存在窗口，期间系统不可用。这个窗口（**故障转移时间**）直接贡献 MTTR。
