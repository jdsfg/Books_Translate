### 3.5 用 Interactive Rebase 讲故事

一个准备 push 的 PR 分支应该讲一个连贯的故事。故事有时是提交实际发生的顺序；更多时候，是一个*整理后*的版本——死胡同、WIP、typo 修正提交都缺席。

Interactive rebase 就是整理工具。命令 `git rebase -i HEAD~10` 会打开编辑器，列出最近 10 个提交，每个前面有一个动词：

    pick a1b2c3d Extract Permission type
    pick d4e5f6a fix typo in Permission
    pick b7c8d9e Add PermissionService
    pick c1d2e3f WIP getting tests to pass
    pick f4a5b6c Wire PermissionService into AccessGuard
    pick g7h8i9j fix the actual bug from the WIP
    pick j0k1l2m address review comments

你可以通过修改动词来重塑历史：

* `pick` 保持提交原样。
* `reword` 保持提交，但打开提交信息编辑。
* `squash` 把提交合并进前一个，并提示你写合并后的信息。
* `fixup` 与 squash 类似，但丢弃提交信息。
* `edit` 在该提交处停下，以便修改。
* `drop` 完全删除该提交。
* 移动行可以重排提交顺序。

整理后可能是：

    pick a1b2c3d Extract Permission type
    fixup d4e5f6a   # typo 修正悄悄合进 Extract
    pick b7c8d9e Add PermissionService
    fixup c1d2e3f   # WIP 合进 PermissionService
    pick f4a5b6c Wire PermissionService into AccessGuard
    fixup g7h8i9j   # bug 修复合进 Wire
    fixup j0k1l2m   # 审查意见合进 Wire

3 个提交，3 个概念，干净的故事。这就是审查者和未来的 bisect 看到的故事。


#### 叙事原则

原则是：**你发布的历史是定稿文章，不是工作草稿。** 你的 reflog 里有工作草稿，这没问题。一旦 push，发布历史就是团队阅读的东西。请相应对待。

有些团队有更严格版本：每个 PR 必须 rebase 并 squash merge，让 `main` 每个 PR 只有一个提交。这合理；但也会对 bisect 稍微不利（你丢失 PR 内部提交，只能看到 PR 级粒度）。其他团队保留每个 PR 提交，也合理。团队的选择应该明确（第 4 章）；而个人在自己分支内的纪律是通用的。


### 3.6 AI 层：在 Git 中指挥智能体

2026 年，运行在 agent-PR 模式（第 22 章）的 AI 智能体会自己提交。这些提交有时是原子的，经常不是。提交信息有时有用，经常模板化。本章的纪律同样适用于智能体提交。
