#### 概念检查

**Q1.** 一个团队报告测试套件有 95% 行覆盖率。你加入团队，想知道套件是否真的好。你问什么、测什么？

提示

覆盖率是输入；断言强度是输出。

**答：** 问：(a) 分支覆盖率是多少，不只是行覆盖率？(b) 上次生产环境出现、但套件漏掉的真实 bug 是什么时候？(c) 最关键模块的变异分数是多少？测量：(a) 在代表性模块上跑变异测试工具（第 6 章）；如果变异分数比覆盖率低很多（例如覆盖率 95%，变异杀灭率 40%），测试就是覆盖率填充；(b) 抽查最近测试的断言强度启发式（§5.4：这个测试能抓住什么？）；(c) 看测试文件结构：是否 arrange-act-assert？名字是否描述性？是否有明显重复？

一个 95% 覆盖率套件如果同时满足 (a) 高变异分数、(b) 近期生产事故通过加测试修复、(c) 测试代码干净，才是好套件。任一不满足都值得怀疑。

**Q2.** 快照测试何时适合，何时是错误工具？

提示

§5.3 四条适用条件和三条失效模式。

**答：** 适合：输出大、结构复杂、确定性、团队有批准前阅读快照 diff 的文化。示例：React 组件渲染、解析器输出、稳定 API 响应载荷。

错误工具：输出很小（直接断言）、输出非确定性（团队加过滤导致不可维护）、团队不读就批准快照更新（快照只认证发生了什么，违背目的）。

深层测试：想象队友 PR 改了一个快照。团队会读 diff 并发现变化是否错误吗？如果是，快照在工作。如果不是，快照就是纯仪式；删除它，写真实断言。

**Q3.** 解释倒金字塔反模式。它通常怎么产生，团队该怎么做？

提示

§5.1 讨论团队为何倒置。

**答：** 倒金字塔（很多 E2E、很少单元）产生原因：(a) 产品只有经过 E2E 测试才感觉“真实”；(b) 团队有 E2E 工具（Selenium、Cypress）专长，但缺乏单元测试底层代码的能力；(c) 单元测试基础设施从没建起来或很难用。后果是 CI 慢、flaky、bug 离原因很远才浮现。

团队应：(a) 盘点现有测试，按 U/I/E2E 分类；(b) 识别顶层过度代表的类别；(c) 对每个 E2E 测试，问它抓的 bug 是否可以用集成或单元测试抓；如果可以，写更低层的版本并考虑删除 E2E 测试；(d) 投资单元测试基础设施（fixtures、factories、快速 DB），让新测试默认落在金字塔底层。

过渡通常需要一个季度。要关注的指标是各层数量和比例；目标是单调地向金字塔形状移动。
