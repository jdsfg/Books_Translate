### 3.3 把 `git bisect` 当作系统化调试

本章开篇的故事是具体的。`git bisect` 是对历史的二分查找：你告诉 Git bug 在提交 X 存在、在提交 Y 不存在，Git 切出中点，问你 bug 是否出现，缩窄范围，重复。结果是*对数级*搜索：1,000 个提交的历史大约 10 步就能得到答案。


#### 基本 bisect 工作流

    # 用已知的坏提交和好提交启动 bisect
    git bisect start
    git bisect bad HEAD               # 当前提交有 bug
    git bisect good v2.4.0            # 这个 tag 没有

    # Git 切出中点；测试它
    npm test -- some-failing-test
    # 测试通过：
    git bisect good
    # 测试失败：
    git bisect bad

    # 经过 log2(N) 步，Git 告诉你首个坏提交：
    # "abc1234 is the first bad commit"

    git bisect reset

这项纪律要求对“bug 存在”有一个*确定性测试*。一个只在生产环境每周二出现的 bug 很难 bisect；一个会让特定测试失败的 bug 则轻而易举。因此，当你怀疑出现回归时，第一步是先写出会失败的测试（第 6 章的变异测试会深化这一点）。


#### 用 `git bisect run` 自动化

一旦有了确定性测试，你就可以把 bisect 完全自动化：

    git bisect start
    git bisect bad HEAD
    git bisect good v2.4.0
    git bisect run npm test -- some-failing-test
    # 走开；Git 自动执行二分查找

20 分钟后，Git 报告首个坏提交。Asher 在 Trellis 就用这个技术找到了 6 周前引入的线索评分回归；整个 6 周团队都在错误子系统上找原因。一次自动化 bisect 用 20 分钟墙上时间和约 0 分钟工程师注意力就解决了问题。


#### Bisect 何时失败

Bisect 可能在以下情况失败：

* 范围内的每个提交不能单独构建（这又是*原子提交*论证；非原子提交会产生坏的中点）。
* Bug 非确定性（flaky 测试、竞态条件、时间依赖）。缓解：在每个中点多次运行测试，或先修 flaky（第 5 章）。
* Bug 由仓库*外部*变化引起（依赖更新、数据库模式变更、外部 API 变更）。缓解：单独 bisect 依赖版本。

当 bisect 因第二个原因失败时，失败本身也有信息：你知道 bug 是非确定性的，这大大缩小了怀疑空间。
