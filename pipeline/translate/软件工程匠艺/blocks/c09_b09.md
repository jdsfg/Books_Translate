#### 概念检查

**Q1.** 队友说：“我做 TDD！我先写一个功能的所有测试用例，然后写实现，然后跑测试。” 这是 TDD 吗？为什么？如果你想把他引向标准实践，会建议工作流做什么具体改变，为什么这个改变重要？

提示

TDD 有三部分：test-first、*一次一个*、*最小实现*。队友缺了什么？

**答：** 不完全是 TDD；它是没有循环的 *test-first*。队友缺少*一次一个*和*最小实现*。先写所有测试再写所有代码是“先把猫头鹰画完再写测试”模式；它失去了 TDD 的主要收益。

具体改变：让他写*一个*失败测试，然后写*让它通过的最少代码*（即使明显不完整），然后写*下一个*失败测试，依此类推。“最少代码通过”规则是关键；它防止过度工程。当测试要求“零天逾期返回 0”时，实现就返回 `0`。测试变绿；你写下一个测试。实现随测试增量增长，而不是凭预测。

为什么重要？三个原因：

* **认知负荷保持小。** 一个测试 = 一个决定。一次写 20 个测试需要同时脑中装 20 个规格。
* **实现随测试演化，而不是工程师的预测。** 过度工程是 test-first-without-cycle 的自然失效模式。
* **重构步骤有活干。** 一个测试通过且是最小代码时，重构步骤有一个小而具体的改进。如果 20 个测试已经写好，重构步骤会变成“重写全部”。

循环才是纪律，不是顺序。

**Q2.** 给出一个 TDD 适合的任务类型和一个不适合的任务类型，并分别说明理由。

提示

§8.6 矩阵对任务做了分类。

**答：** 适合：`calculate_late_fee` 这种已知规格的纯函数。测试精确（一个输入，一个期望输出）；循环快（写测试、写代码、重构、重复）；test-first 纪律迫使澄清规格（正好 30 天怎么办？25.5% 怎么办？）。摩擦低；价值高。

不适合：新产品功能的视觉 UI 工作，规格是“让它看起来对”。先为“看起来对”写测试比先写 UI 并视觉迭代更难。Test-after 配视觉回归工具是自然选择。

原则：TDD 适合测试是精确规格的地方；不适合规格是涌现、视觉或探索性的地方。
