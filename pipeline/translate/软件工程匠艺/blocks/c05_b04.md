#### 定义：特性开关

特性开关是一个受外部控制的运行时条件，允许一条代码路径在未激活状态下发布到生产环境，并在部署后逐步或选择性地激活。

直白地说：特性开关把*部署代码*与*发布功能*解耦。你可以安全地部署半成品，因为半成品路径是关闭的；你可以把完成版本发布给 1% 用户，然后 10%，再 100%，每一步都观察指标。


#### 为什么它能启用主干开发

主干开发之所以能在高节奏下工作，原因就是特性开关。特性开关让耗时 6 周的长功能被拆成许多小 PR，每个都合到 `main` 但处于关闭状态。功能是*持续部署*的，而只在开关拨到 100% 时才*发布*一次。团队获得小 PR 的集成收益（小冲突、快审查、快 CI），却没有长分支的发布协调成本。


#### 选择特性开关系统

2026 年有四个严肃系统：

* **LaunchDarkly**：市场领导者；成熟；规模大了贵；富 targeting 规则。
* **Statsig**：实验优先；内置 A/B 测试；受运行实验的产品团队青睐。
* **Unleash**：开源；可自托管；受基础设施强或有数据驻留要求的团队青睐。
* **Flipt**：开源；轻量；受小团队或测试环境使用青睐。

选择取决于团队规模、预算，以及实验功能是否重要。Carmen 为 Currents 选了 LaunchDarkly，因为团队重视成熟的 targeting 规则及其与现有分析流水线的集成。


#### 开关腐烂问题

特性开关会累积。一个为 2024 年重设计加的开关，到 2026 年仍在代码里，仍在每个请求上求值，而“关”分支已是死代码。开关腐烂是真实的技术债形式（第 19 章）；缓解办法是文档化的生命周期：

  1. 加开关时附带 `kill_by_date`，例如从现在起 1 个季度后移除。
  2. 当开关达到 100% 推出且稳定后，开一个 issue 要求移除。
  3. 移除 PR 从代码和服务中删除开关，并正常审查。

没有这项纪律，一个 5 年代码库会有数百个死开关，而任何人读的代码路径都会与没人理解的条件交织。


### 4.5 把 PR 作为工作单元

PR（pull request，或 merge request）是 2026 年团队审查和合并工作的单元。把 PR 当作工作单元的纪律塑造了何为好工作。


#### 规模

PR 应小到能在一次专注的 sitting 内仔细审查。已发表研究在这里趋同：Caitlin Sadowski 等人 2018 年的论文 “Modern Code Review: A Case Study at Google”（ICSE）和 SmartBear 的《Best Kept Secrets of Peer Code Review》（Cohen，2006 年起）都把有效性甜点放在 200–400 行实质性改动，不含测试和生成代码。超过 600–800 行，审查质量可测量地下降；审查者批得更快、漏掉更多 bug、合并后缺陷率上升。Currents 在 Carmen 的过渡后也内部追踪到同样模式，这是团队测量自己数据时通常的发现。

一个 1,500 行的 PR 不是一个 PR；它是三件 PR 穿了一件风衣。拆分它。
