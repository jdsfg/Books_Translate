### 22.5 AI 代码审查工具（再论）

第 15 章介绍了 AI 代码审查工具（Greptile、CodeRabbit、Copilot Review）。在 2026 工作流中，这些工具是 spec 驱动周期的一部分：智能体产出 PR；AI 审查工具检查；人类在 AI  surface 战术问题后审查。


#### 工具如何融入工作流

* **Greptile**：深度代码库索引；理解跨文件上下文；善于抓住代码库一致性 issues。
* **CodeRabbit**：逐行反馈；周转快；适合 null 检查、错误处理、常见 bug 模式等战术问题。
* **Copilot Review**：与 GitHub Workflows 集成；与平台紧耦合。

每种工具有强项和弱项；团队通常根据集成和 PR 形状选一个。选择主要取决于路径依赖（团队现有工具）和工作流依赖（PR 典型内容）。


#### 组合审查工作流

2026 年由实现智能体和审查 AI 工具参与的 PR：

  1. 人类写 spec。
  2. 智能体实现；开 PR。
  3. CI 运行；测试通过。
  4. AI 审查工具在 PR 上评论。
  5. 人类读 AI 审查评论；处理容易的（常让智能体修订）。
  6. 人类实质性审查 PR，应用线索 C checklist（第 15 章）。
  7. 人类满意后合并。

总时间显著少于人类实现、人类审查的 PR。瓶颈是人类的审查；其他都很快。


### 22.6 智能体提交 PR 的工作流

2025–2026 年浮现的模式：智能体不仅实现代码，还开 PR。


#### 工作流

  1. 人类写 ticket 或 spec。
  2. 人类用 PR mode 调用智能体，带上 spec。
  3. 智能体在分支上工作、做 commit、运行测试、写 PR 描述、开 PR。
  4. 人类像审查任何 PR 一样审查。
  5. 人类和智能体通过 PR 评论迭代。
  6. 人类合并。

智能体扮演从队列取 ticket 并产出 PR 的初级工程师。人类扮演审查并护送 PR 合并的资深工程师。


#### 它带来什么

运行此工作流的团队可让多个 PR 并行进行，每个由智能体驱动，每个由人类审查。团队吞吐量倍增；人类角色集中在审查。


#### 它要求什么

团队必须拥有：

* 清晰的 ticket 写作纪律（智能体的输入是 ticket；模糊 ticket 产生差 PR）。
* 强约定的 CLAUDE.md（智能体输出反映约定）。
* 强审查纪律（人类审查是质量门；弱审查会泛滥 pattern-tax PR）。
* 多并行分支的基础设施（CI 容量、合并队列、冲突管理）。

没有这些，工作流产生数量而非质量。有了它们，产生吞吐量。


#### 何时不适合

* 需要人类作者的关键变更：安全修复、复杂架构变更、业务关键功能。
* Spec 不确定的新颖工作：智能体按被告知做；不确定 spec 产生不确定输出。
* 无法扩展审查的小团队：更多 PR 需要更多审查者；三个工程师的团队无法一天审查 30 个智能体 PR。

对这些，人类作为实现者的工作流保留。智能体提交 PR 是一种模式，不是通用默认。
