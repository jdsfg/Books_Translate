2002 年，Joel Spolsky 写了题为《Things You Should Never Do, Part I》（第 1 部分）的文章，论证对可工作软件进行大型重写几乎总是错误。文章主要例子是 Netscape，它在 1998–2000 年（1998–2000）间从头重写了浏览器，并在大重写期间把浏览器市场实际输给了 Internet Explorer。Spolsky 的观点很强：重写可工作的软件会丢弃代码库中最有价值的东西，即*多年来累积的 bug 修复*。即使丑陋的代码也包含了来之不易的教训；为了从头开始而扔掉它们，就丢失了这些教训。

这篇文章被反复阅读和争论 20 年（2 个十年）。许多工程师分享过“重写失败”的经历：花数月或数年重建系统，积累原系统已经修复的新 bug，最终要么放弃重写，要么发布一个比原版更糟的版本。

较小数量的工程师分享过“重写成功”的经历：重写是正确选择、并产出显著优于原系统的系统的罕见案例。Netflix 2010–2012 年从 Oracle 迁移到 Cassandra 是一个。Apple 的芯片迁移是另一个。这些案例有特定共同属性；识别它们是纪律的一部分。

本章讨论这个问题：大型重写何时有效、何时失败，为什么绞杀者无花果是更安全默认。有了第 19 章（理解债务）和第 20 章（增量模式），本章完成第八部分。


### 21.1 Spolsky 的论点

Spolsky 的论点分三部分：


#### 第一部分：代码体现 bug 修复

已在生产运行多年的代码库已被许多 bug 击中。每个 bug 都曾被发现、调试、修复；修复现在就在代码中。修复往往不可见（一个特例、一个防御性检查、一个小心排序），但举足轻重（没有它，bug 就会复发）。

重写从系统*应该做什么*的概念开始，而不是从系统实际如何被使用所累积的*学习*开始。重写产出概念上干净但未被原系统 bug 击中的代码库。这些 bug 会在新代码库中一个接一个被击中；每个都要从头调试；累计调试成本可观。


#### 第二部分：重写消耗团队产能

一次 18 个月的重写就是 18 个月不发布。产品没有新功能；竞争对手继续发布；用户要么等待，要么转向替代品。机会成本真实。

在 Spolsky 的 Netscape 例子中，重写消耗了 1998–2000 年，而 Internet Explorer 继续发布。结果是 IE 近十年主导。重写的技术优点无关紧要，因为重写发布时市场已经变了。
