### 2.3 把 `git blame` 当作历史文档

每一行代码都有历史。在 Git 管理的代码库里，那条历史只需一个命令。`git blame` 不是找人背锅的工具；它是阅读一行代码背后*意图*的工具，而意图往往从行本身看不见。

看一个来自 Trellis 虚构文件的真实形状示例（Asher 第 5 天的阅读）：

    // src/scoring/legacy-rounding.ts
    export function legacyRoundScore(score: number, accountCreatedAt: Date): number {
      if (accountCreatedAt < new Date('2021-03-15')) {
        return Math.round(score * 10) / 10 - 0.05;
      }
      return Math.round(score * 100) / 100;
    }

这个函数根据日期做两件不同的事。为什么？行本身没说。引入它的 PR 可能会说。引入它的提交信息几乎肯定会说。写它的作者（现已退休）肯定知道。`git blame` 就是通往那扇门：

    git blame -L 3,5 src/scoring/legacy-rounding.ts
    ^abc1234 (Priya Mehta 2021-03-22 14:02:11) if (accountCreatedAt < new Date('2021-03-15')) {
    ^abc1234 (Priya Mehta 2021-03-22 14:02:11)   return Math.round(score * 10) / 10 - 0.05;
    ^abc1234 (Priya Mehta 2021-03-22 14:02:11) }

提交 `abc1234`，2021 年 3 月，作者 Priya Mehta。`git show abc1234` 揭示提交信息：

    fix(scoring): preserve pre-migration rounding for legacy accounts

    Before the March 2021 schema migration, scores were stored as
    single-decimal floats with a 0.05 rounding bias from the v0
    spec. Post-migration scores are stored as double-decimal floats
    without the bias. Customer dashboards display historical scores,
    so the rounding must match the storage epoch.

    Refs: TRELLIS-1842

突然间，这行代码合理了。这个偏移不是 bug；它是 v0 规格。2021 年迁移改变了存储格式，但没改变显示的历史。减去 0.05 是为了复刻旧显示，让客户仪表盘随时间保持一致。

没有 `git blame`，这个函数看起来像 bug。有了 `git blame`，它是一块需要在理解后果前不要碰的后向兼容代码。


#### `git blame` 纪律

这项纪律是：**只要一行代码让你惊讶，先跑 `git blame`，再下判断。** “惊讶”包括：

* 没有注释的魔数。
* 谓词晦涩的条件。
* 名字与所作所为不符的函数。
* 看起来没必要的临时方案（workaround）。
* 与周围代码明显不一致的地方。

每种情况下，惊讶都是数据。数据在问你一个问题：*它为什么在这儿？* `git blame` 加上提交信息常常就是答案。有时不是（提交信息为空或没用）；这时你可以升级到 `git log --all --full-history` 查看文件历史，或 `git log -S "specific string"` 找出字符串何时引入。
