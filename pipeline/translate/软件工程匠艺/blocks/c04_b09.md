#### 概念检查

**Q1.** 一位队友的 PR 只有一个提交，标题是 “fix payment bug + small refactor + extract helper”，380 行、跨 11 个文件，其中一半是一个与新支付修复无关的新 util 函数的单元测试。你正在审查它。3 周后回归测试失败，有人需要 bisect 找到它何时开始失败。这个提交的形状会对未来的 bisect 造成什么具体问题？你今天会要求作者改什么？

提示

应用 §3.1 的三属性（单一改动、可构建、描述性信息）和 §3.3 的失效模式。

**答：** 当 bisect 落在这个提交上时，会遇到三个问题：

  1. **表面积太大。** Bisect 只会告诉你“bug 出现在这 380 行、11 个文件里的某处。” 这和不 bisect 差不多；你仍然要读 380 行才能找到真正原因。原子提交会把表面缩小到一个概念性改动（通常 30–80 行）。
  2. **混合关注点让诊断混乱。** Bisect 落在一个做三件事的提交上；真正引发 bug 的改动是其中之一。不读完整 diff 你不知道是哪一个。
  3. **回退粒度错误。** Bisect 完成后，“回退这个提交”会同时回退支付修复、重构和辅助函数。你可能需要手动把想保留的部分 un-revert，这很慢且容易出错。

要求作者拆分：一个提交修复支付 bug（带 bug 测试）、一个提交做小重构、一个提交提取辅助函数。每个提交都应让 tree 可构建，这样未来 bisect 不必跳过中点。拆分开销今天 10 分钟；第一次需要 bisect 时就省小时。

**Q2.** 一位队友提议：“我们应该在合并前总是把所有 PR 提交 squash 成一个，因为 `main` 应该每个功能一个提交。” 用 §3.5 的叙事原则辩护或反驳。

提示

想想谁读 `main` 的历史，以及为什么读。

**答：** 这个提议有优点也有代价。优点：`main` 上一个 PR 一个提交，用 `git log --oneline` 扫描很方便，按 PR 粒度回退也简单。代价：bisect 粒度降到 PR 级。一个 1,500 行 PR 被 squash 成一个提交，给 bisect 的表面比拆成 7 个原子提交大得多。

一个可辩护的折中是*带保留历史的合并提交（merge-commit-with-preserved-history）*：PR 以 merge commit 合入，但 PR 内部提交在 `main` 上保留。`git log --first-parent` 显示 PR 级历史（每次 merge 一条）；不加 `--first-parent` 的 `git log` 显示完整粒度，便于 bisect。这样两种视角都有。

强烈版提议（总是 squash）用 bisect 能力换取整洁。对经常 bisect 的团队，这是笔糟糕交易。对从不 bisect 的团队（因为回归在合并前就被测试套件抓住，或代码库很小）也许可以。选择应该明确；教条不该。
