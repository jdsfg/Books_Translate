### 16.7 团队沟通约定

内化了异步优先和结对/群体纪律的团队，会从明确沟通约定中受益。Currents 的约定：

* **代码反馈走 PR 而不是聊天**：如果你对代码有反馈，写到 PR 评论里，而不是 DM。PR 评论可持久且对他人可见。
* **架构决策走 ADR 而不是会议**：如果一个决策影响团队代码，写 ADR；异步审查；共识浮现时合并。
* **bug 和功能请求走 Issue 而不是邮件**：如果你发现 bug 或想要功能，建 issue；tracker 是可持久记录。
* **日常状态更新以书面形式**：standup 如果进行，也通过每日频道更新异步完成。格式：昨天、今天、阻塞。
* **同步时间只用于同步需求**：会议明确排期并说明产出；临时语音通话只用于事故和紧急结对。

这些约定把“这段对话应该在哪里发生？”简化成快速查表。新工程师在 onboarding 中学习约定；团队条件反射地使用它们。没有约定，团队沟通散落在多个渠道，没人知道哪里能找到什么。

Carmen 还有一个她主要保留给个人的额外约定：任何涉及他人决策的书面评论都以加粗标签开头。`**Decision needed:**`、`**Heads-up:**`、`**FYI:**`，加上 PR 审查中使用的四个标签（`**Blocking:**`、`**Suggestion:**`、`**Nit:**`、`**Praise:**`）。读者在读完第一行之前就知道需要做什么。
