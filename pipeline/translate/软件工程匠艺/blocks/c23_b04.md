#### 模式 5：先问计划

对非平凡工作，让智能体先提出计划再实现。“要添加 rollover-credit 功能，你会采取哪些步骤？先不要实现，只提出步骤。”

计划揭示智能体的理解。如果计划错了，在实施前 refine。如果计划对，就说“执行计划。”


#### 无效模式

* **模糊提示**：“让这更好”产生不可预测结果。
* **无上下文**：不引用代码库的提示产生不适配的泛化代码。
* **无成功标准**：没有 failing tests 或可衡量结果的提示产生人类不易评估的代码。
* **单次完成多步**：把多天项目塞进一个提示很脆弱；分步并在步骤间审查。


### 22.4 CLAUDE.md / AGENTS.md 约定

2025 年出现、2026 年巩固的模式：项目根目录放一个文件（通常叫 `CLAUDE.md`、`AGENTS.md`，或两者都有），智能体每次会话开始时读取。


#### 定义：CLAUDE.md 约定

CLAUDE.md（或 AGENTS.md）是项目根文件，捕获团队的约定、反模式和给 AI 智能体的上下文。智能体在任何会话前读取它；约定变成智能体在该项目上的默认。

直白地说：把你希望智能体知道的东西写下来；智能体读；智能体输出匹配团队期望。


#### CLAUDE.md 里放什么

有用的 CLAUDE.md 通常包括：

* **代码库定向**：项目是什么、关键文件夹在哪、如何运行测试。
* **命名约定**：§18.5 的纪律明确化。
* **测试约定**：哪个框架、fixture 在哪、用哪种 double 风格（§7.6）。
* **模式偏好**：§13.5 的纪律明确化。
* **反模式**：绝对不要做的事（使用 Singleton、使用 Visitor 等）。
* **架构形状**：六边形或其他；port 在哪、adapter 在哪（§14.6）。
* **Git 约定**：commit message 格式、分支、PR 模板（§4.6）。
* **具体 gotcha**：团队惨痛学到的代码库区域。


#### 为什么有效

没有 CLAUDE.md，智能体默认反映训练数据：泛化名字、常见模式、流行库。有了 CLAUDE.md，智能体默认转向团队特定约定。输出更一致，审查中需要修正更少。

该文件也是*持久产物*（第 17 章）：新工程师读它学约定；老工程师更新它捕捉近期决策。文件同时服务智能体和人类；它是团队活的 onboarding 文档。


#### 维护 CLAUDE.md

保持其有用的几个实践：

* **约定变化时更新**：影响代码库的团队决策应作为同一 PR 落地到 CLAUDE.md。
* **智能体产出错误输出时更新**：如果智能体做 X 而团队要 Y，这是 CLAUDE.md 缺口；更新。
* **定期审查**：每季度或每 release 通读；删除陈旧条目；合并冗余。
* **保持简短**：目标 300 行以内。太长的文件会被智能体（和人类）跳过；短的才读。
