#### 断言强度启发式

一个有用的单问题审查过滤器：*这个测试能抓住什么？* 对每个测试，说出它会抓住且否则会到达生产环境的一个 bug。如果你说不出，这个测试可能只是覆盖率填充。

示例：

* 调用 `divide(10, 2)` 但无断言：*什么都抓不住*。覆盖率填充。
* 调用 `divide(10, 2)` 并断言结果是 `5`：能抓住基本算法变化。真实测试。
* 调用 `divide(10, 0)` 并断言结果是 `ZeroDivisionError`：能抓住错误路径行为变化。真实测试。
* 调用 `divide(0.1 + 0.2, 0.3)` 并断言结果正好是 `1.0`：抓不到任何有用东西，*还会引入* flaky 测试，因为浮点运算不会正好等于 `1.0`。反测试。

AI 生成套件通常四类混合。审查者的工作是区分它们，并只保留第二、三类。


#### 审查 AI 测试 PR 的工作流

Aki 在 Helix 对开篇小插曲应用的工作流：

  1. **本地跑套件，确认通过。** 快速 sanity 检查。
  2. **带着 AI 层问题读 diff。** 每个新测试：它能抓住什么？断言强吗？是否重复？
  3. **对改动模块跑变异测试（第 6 章）。** 变异分数告诉你测试是真正在测试还是只是覆盖。如果变异分数比覆盖率低很多，测试就弱。
  4. **评论具体删除和替换。** 不是“这些很弱”，而是“删除 A、B、C（重复 D），加强 E 和 F，保留其余。”
  5. **作者处理完评论后再次请求审查。**

这个工作流可扩展，因为第 3、4 步是慢的；一旦有了变异分数数据，评论就是机械性的。没有变异测试，审查就完全依赖审查者判断。


### 5.5 构建有用的单元测试层

单元测试层数量最大，也最容易写成不测试东西的测试。几项纪律共同复利：


#### arrange-act-assert 结构

单元测试有三个部分：

    def test_calculate_refund_partial():
        # Arrange：设置输入和状态
        order = make_order(total=100, currency='USD')
        refund_request = RefundRequest(amount=30)

        # Act：调用被测函数
        result = calculate_refund(order, refund_request)

        # Assert：验证结果
        assert result.amount == 30
        assert result.currency == 'USD'
        assert result.status == RefundStatus.PARTIAL

这种结构让测试可读：读者一眼就知道在测什么、输入是什么、输出是什么。把 arrange 和 act 混在一起，或一个测试有多个 act，都会让测试难读、失败时难调试。


#### 每个概念一个断言，不是一个测试一个断言

一个测试应验证一个*概念*，可能需要多个断言。上面的 `test_calculate_refund_partial` 有三个断言，都验证退款结果同一概念的不同方面。这没问题。一个测试断言十个不相关的东西，则是在测多个概念，应拆分。
