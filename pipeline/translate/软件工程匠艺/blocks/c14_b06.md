#### Builder

逐步构造复杂对象的模式。现代替代：命名参数和 dataclass。Python 中：`@dataclass(kw_only=True)` 提供了 Builder 过去需要几十行才能做到的事。TypeScript：对象字面量语法。Builder 模式是 Java-1990 年代对 Java 缺乏命名参数的回应；现代语言有这个特性，模式不必要。

这些模式出现在遗留代码、AI 提议和旧教材中。把它们识别为过时，是 2026 年匠艺的一部分。


### 13.5 AI 层：拒绝模式税提议

LLM 从训练数据中提议模式。训练数据既包含应用得当的模式，也包含过度应用的模式。LLM 不做区分；工程师必须区分。


#### 识别模式税提议

AI 提议是模式税而非合理模式应用的信号：

* **多层工厂或 provider** 针对单一用例。
* **只有一个具体子类的抽象基类**：基类存在只是因为工程师（或 AI）预期了从未出现的第二个子类。
* **只被一个类实现的接口（或 protocol）**：如果只有一个实现，接口没有价值。
* **本可用更简单结构却叠加模式**：对不需要的问题用 Strategy + Decorator + Observer。
* **暗示未来灵活性的泛化名称**：`Handler`、`Manager`、`Processor`、`Engine` 没有领域特定名词。

在 AI 提议中看到这些时，回推。要问：“这比简单替代方案多了什么？你能给我看证明抽象合理的第二个案例吗？” 如果 AI 无法辩护，简化提议。


#### CLAUDE.md 纪律

在 CLAUDE.md 中规定团队的模式偏好（第 22 章）：

    ## Pattern preferences

    - Prefer plain functions to classes when a class has no state and one method.
    - Prefer concrete types to interfaces when there is only one implementation.
    - Prefer constructor injection (DI) to Singletons. Do not use Singleton.
    - Prefer pattern matching to Visitor. Do not implement Visitor classes.
    - Prefer named arguments to Builder. Do not implement Builder classes.
    - Introduce abstractions when a second concrete case exists, not before.
    - Pattern tax (Factory Factory, Provider Factory, etc.) is forbidden.

这些指令把 AI 默认值转向团队偏好。没有它，AI 默认会套用训练数据里的模式，包括过度应用的。


#### 常见误解（再论）

一个常见误解是“我们应该现在就应用模式以预期未来灵活性。” 错误在于预测：大多数预测中的灵活性永远不会来。模式税的成本提前并持续；预期灵活性的收益可能永远不会来。纪律是*回顾性地*应用模式——第二个案例出现之后，而不是*前瞻性地*——预期第二个案例之前。

另一个常见误解是“模式让代码更专业。” 错误在于把*复杂性*与*质量*混为一谈。包含五个模式的代码不比一个模式的好；它更复杂。质量是针对问题的正确结构，通常比堆叠模式的替代方案更简单。
