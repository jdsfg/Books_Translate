1. **读函数的调用者。** `grep -r "processData(" .` 能揭示函数在哪里被调用。调用者是函数的微型“入口点”；它们揭示函数被期待做什么。
  2. **对函数头跑 `git blame`。** 找到原始提交并读提交信息。提交信息常常比任何代码都更清楚解释原始意图。
  3. **读函数的测试，即使它们在另一个文件里。** 搜索 `describe('processData')` 或等价物。如果没有，记下这是需要修复的债务。
  4. **读输入类型和输出类型。** `data` 长什么样？返回什么？即使没有类型，函数也很可能访问特定字段；这些就是 de facto schema。
  5. **带着 §2.4 的考古模式自顶向下读函数体。** 寻找死条件、承重注释、迁移疤痕。等你读到末尾，应该能用一句话描述函数做什么。

顺序重要，因为每一步约束下一步。调用者告诉你*期待*行为；测试确认或否定；类型收窄输入空间；函数体填充机制。先读函数体（默认做法）意味着你不知道该找什么，于是每行平均用力，既慢又肤浅。

**Q4.** 在你维护的代码库中找一条承重注释（或用下面的合成示例）。解释它为什么是承重的，以及忽略它会怎样。

    # 不要在循环里调用这个函数——底层 RPC 有无限重试，
    # 会拖陷（tarpit）上游服务。
    def fetch_user_profile(user_id: str) -> UserProfile: ...

提示

注释保护的约束是什么？违反它的代价是什么？

**答：** 这条注释是承重的，因为它编码了函数的*非功能性*属性（底层 RPC 的重试行为），而这一属性从函数签名和体里完全不可见。忽略它：有人写 `[fetch_user_profile(uid) for uid in user_ids]` 这样处理 1,000 个用户的列表推导式。每次调用失败都会指数退避重试；失败会级联，因为上游现在被 1,000 个并发请求风暴冲击；上游挂掉；事故被宣布。

修复方法是加一个负载测试或一条 linter 规则来捕获循环调用模式，让约束由代码而非注释强制执行。但在此之前，注释是唯一防线，因为“注释会腐烂”就删除它很危险。把注释当作代码；像审查代码一样审查它；像保护代码一样保护它。
