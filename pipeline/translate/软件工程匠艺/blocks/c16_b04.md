#### 重新争论架构决策

如果团队已同意六边形架构（第 14 章），审查者在每个 PR 上推动不同架构只会消耗时间却无收益。架构决策属于 ADR（第 17 章）；PR 不是重新辩论它们的场所。


#### 常见误解

一个常见误解是“反馈越多越好。” 错误在于把反馈量当作指标。指标是*捕获的 bug 和保持的架构完整性*；不推进这些目标的反馈是 overhead。两条高价值评论的审查优于三十条低价值评论的审查。


### 15.4 审查者的词汇

有用的代码审查使用一个小词汇表，区分每条评论的严重性和意图。Carmen 的 Currents 团队采用了四个标签。这四个标签来自她上一份工作的 postmortem：一条未标注的“maybe consider”评论被作者理解为建议、未处理就合并，导致那个季度标志性的回归。此后，她写的每条评论都带标签，并把这一做法推广到带领的每个团队。四个标签：

* **Blocking**：不处理就不能合并。用于 bug、安全问题、契约违反、架构违反。要节制；如果什么都 blocking，就什么都不 blocking。
* **Suggestion**：审查者建议变更但不强制。作者可采纳也可不采纳。用于严格不必要的改进。
* **Nit**： minor 风格或组织注记，不一定要处理。用于作者可在后续修复或忽略的事。
* **Praise**：对做得好的地方给予正面反馈。用于优雅解决方案、充分测试、好命名。Praise 对审查者零成本，但能强化纪律；从不 praise 的团队会让工程师永远不知道自己做对了什么。

标签加快作者响应：他们知道必须修什么 vs 可选择修什么。它们也加快审查者写作：标签定下了基调。

有些团队用 GitHub 的“Approve / Request changes / Comment”按钮作为代理。“Request changes”审查至少有一条 blocking 评论；“Approve”则没有。标签词汇自然映射到这些按钮。


### 15.5 审查 AI 生成代码：线索 C checklist

2026 年越来越多的 PR 全部或部分由 AI 生成。审查它们需要把线索 C 的七个谎言（第 1 章引入，贯穿全书）作为 checklist 应用。


#### 谎言 #1：看起来合理但未测试的边界情况

扫描：代码在主路径上处理得好，但未显式处理 NaN、空列表、unicode、时区、夏令时、极大或极小数、字符串特殊字符、负数、零。

要问的问题：*如果我想破坏这段代码，我会尝试什么输入？* 如果测试套件不包含该输入，代码就暴露。


#### 谎言 #2：过度抽象（模式税）

扫描：无依据的工厂或 provider 层；只有一个具体子类的抽象基类；只有一个实现的接口；泛化名称（`Handler`、`Manager`、`Processor`）；两路条件判断的 Strategy。

要问的问题：*这个抽象比简单替代方案多了什么？是否有真实第二案例证明它合理？*
