#### 把这些纪律当成临时脚手架

最深的反模式：假设本章描述的纪律只是当前限制的变通，会随着智能体改进而变得不必要。并非如此。它们是无论智能体能力如何都能最大化团队价值的工作流。未来好两倍的智能体仍受益于清晰 spec、良好 CLAUDE.md 和纪律审查；更受益，因为智能体会产出更多需要审查的输出。纪律不会随模型改进而过时；它们会更 leverage。等待“智能体足够好”再采用纪律的团队，未来到来时却没有肌肉记忆；现在采用纪律的团队会在模型能力增长时复利优势。

**失败案例研究：智能体提交 PR 在一家虚构 fintech 出错**

本章的纪律防止特定失败模式。为具体化：虚构 fintech “Veridian”，2025 年 Q4 8 人团队，在尚未采用支持纪律的情况下采用智能体提交 PR 工作流（§22.6）。故事是 composite（每个元素都是 2025 年公开分享事后分析的团队真实发生过的），结果是教科书式失败案例。

**发生了什么。** Veridian 的 CTO 读到该工作流，很兴奋，告诉团队使用。四周内，8 名工程师每天开 40+ 个智能体生成 PR。审查轮值跟不上；PR 排队；工程师为清空队列而扫一眼就批准；合并后回退率升到 27%。第 6 周，一个智能体生成的 PR 引入支付处理改动，通过了一组薄的智能体写测试，但利息计算中有一个 subtle off-by-one（线索 C 谎言 5）。Bug 发布，周末累积，需要五位数客户赔偿。事后分析揭示：没有 CLAUDE.md（智能体每次会话都在发明约定），被改模块没有变异测试，批准该 PR 的审查者只花了不到三分钟，因为他的队列里还有 11 个等待 PR。

**团队接下来做什么。** 他们暂停智能体提交 PR 一个季度。写了 CLAUDE.md。在 payments 模块加了变异测试。恢复线索 C checklist（第 15 章）作为强制审查步骤。暂时切换为人类作为 PR 作者、智能体作为助手的 AI 结对模式（第 16 章 §16.5）。到 2026 年 Q2，他们试探性恢复智能体提交 PR，但只在变异分数高于 75% 的模块、有文档化 CLAUDE.md、强制执行 PR 大小限制（智能体 PR 超过 600 行需明确豁免）。合并后回退率降到 4%。

**教训。** 智能体提交 PR 在支持纪律到位时是力量倍增器；没有它们则是债务加速器。§22.6 建议“十人以下不适用”并非随意；它是支持纪律跟不上产出的门槛。Veridian 的错误是顺序：先采用工作流，再采用纪律。读到这里的团队应正确排序：纪律第一，工作流第二，吞吐量第三。
