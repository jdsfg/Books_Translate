Trellis 的一位高级工程师花了一整天修复一次小重构后的测试。重构把函数 `validate_customer(c)` 从 `OrderService.place_order(order, customer)` 抽到一个单独的 `CustomerValidator` 类。行为没变；只移动了 6 行。下游成本：47 个测试文件用 mock 引用了 `OrderService`，并断言了内部验证逻辑的特定调用。每个测试都因为 mock 期望现在不匹配而崩溃。修复是机械性的，但要逐个测试修改。

当天下午，同一位工程师在另一个使用 fake repository 而非 mock 的模块做了类似重构。同样是移动 6 行。崩溃测试数：零。Fake 不关心内部调用结构；它们关心行为。行为没变，测试就不变。

本章讲测试替身光谱、让替身好用的 Repository 模式，以及决定测试脆弱还是稳健的设计选择。AI 层角度：LLM 默认过度 mock；把“用 fake 替代 mock”作为对 AI 生成测试代码最高杠杆的修正之一。


### 7.1 测试替身分类

Gerard Meszaros 在《xUnit Test Patterns》中区分了五种测试替身。这套词汇在 2026 年仍然有用。


#### 定义：测试替身

测试替身是在测试中替代依赖的对象。五种替身按模拟真实依赖的丰富程度不同：dummy 只是占位无行为；stub 返回固定答案；fake 有工作逻辑但走捷径；spy 记录交互；mock 有预设期望并验证它们。


#### Dummy

Dummy 是在需要对象但测试中并不使用的地方传入的对象。它只是为了满足类型签名。

    class DummyLogger:
        def info(self, msg): pass
        def warn(self, msg): pass
        def error(self, msg): pass

用于被测函数接收一个依赖但当前测试路径并不锻炼它。例如 dummy 日志对象、绕过 auth 的测试里的 dummy 认证提供者。


#### Stub

Stub 返回固定答案，除此之外没有行为。

    class StubCustomerRepo:
        def find(self, customer_id):
            return Customer(id=customer_id, name='Test', region='US')

用于被测函数需要依赖返回特定输入、而你不想关心依赖内部如何工作时。Stub 简单、可预测、 broadly 安全。


#### Fake

Fake 有工作逻辑，但使用不适合生产的捷径。典型 fake 是内存数据库：行为像真实数据库，但把数据存在字典里而不是磁盘上。

    class FakeCustomerRepo:
        def __init__(self):
            self._customers = {}
        def find(self, customer_id):
            return self._customers.get(customer_id)
        def save(self, customer):
            self._customers[customer.id] = customer

用于被测函数以非平凡方式使用依赖：多次调用、持久化后再读取、带过滤的查询。Fake 比 stub 表达能力更强，比 mock 更稳健。
