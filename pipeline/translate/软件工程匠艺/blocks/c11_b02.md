#### 定义：特征测试

特征测试是代码之后写的、对正确性不持立场的测试，目的是锁定当前行为。测试作为回归探测器：任何改变行为的变化都会失败，即使这些变化可能是改进。

直白地说：运行代码，观察它做什么，写一个断言它正是如此的测试。不要假设行为正确，也不要假设错误。只是锁定。


#### 操作步骤

假设有一个函数 `compute_late_fee(invoice, current_date)` 没有测试。分步：

  1. **用真实输入调用函数。** 挑选覆盖不同代码路径的输入：未到期发票、逾期 30 天、逾期 100 天、部分付款发票。
  2. **观察输出。** 打印或记录它们。暂时不要断言。
  3. **对每个观察到的输出，写一个断言该输出的测试。**

    def test_characterize_late_fee_30_days():
        invoice = Invoice(total=100, due_date=date(2026, 5, 1), paid=0)
        fee = compute_late_fee(invoice, current_date=date(2026, 5, 31))
        assert fee == 5  # 观察到，锁定

  4. **重复多种输入组合**，直到有信心主要代码路径已被覆盖。用覆盖率工具验证；目标函数行覆盖 80%+。
  5. **对令人惊讶的输出，单独建 ticket**，标记为“已特征化，疑似 bug”。特征化期间不要修复；目标是锁定，不是改进。

特征化后，函数行为被编码进测试套件。重构变安全：任何改变行为的变化都会破坏测试。


#### “这是不是 bug？”问题

特征化期间，你会发现让你惊讶的输出。两类：

* **真 bug**：没人想要、且正在造成可见问题的行为（金额错误、遗漏情况）。单独记录并修复。
* **残留行为**：目前没人想要、但下游系统可能依赖的行为（特定错误信息、特定顺序、奇怪的时区行为）。暂时锁定；修复前先调查。

纪律是把两者分开，同时还不修复。边做边修的诱惑很真实；忍住。混入修复的特征化阶段不再是特征化；它是重写。重写会带来安全网本想防止的风险。
