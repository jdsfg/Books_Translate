#### 谎言 #3：与周围代码风格不一致

扫描：与周围代码不同的命名约定、不同的错误处理惯用法、不同的测试 fixture 风格、不同的导入、不同的文件组织。

要问的问题：*这个 PR 看起来像我们代码库的其余部分吗？* 如果不是，AI 没有遵循团队约定；更新 CLAUDE.md 以减少复发。


#### 谎言 #4：缺失或粒度错误的错误处理

扫描：裸 `except:` 子句、`try / except Exception` 吞掉一切、`try / catch (e) { console.log(e); return null; }` 模式、无退避的重试逻辑、无上下文的错误信息。

要问的问题：*当依赖失败时这段代码做什么？这是正确行为吗？*


#### 谎言 #5：微妙的差一或边界错误

扫描：边界附近使用 `<` vs `<=`；循环边界；数组索引；日期计算（尤其涉及时区或夏令时）；舍入行为；整数除法。

要问的问题：*边界会发生什么？*  mentally 用恰好在边界的输入运行代码；验证行为与意图一致。


#### 谎言 #6：虚构库 API

扫描：来自你不认识库名的导入；签名看起来陌生的函数调用；听起来合理但可能不存在的方法名；过时或废弃的 API 用法。

要问的问题：*这个 API 真的存在吗？* 通过查阅库当前文档或在本地运行代码验证。


#### 谎言 #7：看起来合理但不安全的代码

这个谎言不在原始 Thread C 六条中，但值得同等重视。AI 生成代码 routinely 包含安全错误，对不专门扫描安全的人来说看起来没问题：SQL 字符串拼接而非参数化、把 secrets 嵌入代码而非从 secret store 读取、弱的默认加密选择（密码哈希用 MD5、块加密用 ECB 模式）、未埋点的授权检查、名字*看起来*像 canonical 库但解析到 typosquatted 包、对受攻击者影响的输入使用 `eval` / `exec`。智能体不知道哪些调用点受攻击者可达；不知道训练后哪些包被劫持；不知道安全团队禁止了哪些加密原语。

扫描：字符串拼接到 SQL 或 shell 命令；硬编码 secrets、token 或凭证；可疑包导入（逐个字符对照权威来源验证包名）；对非静态输入使用 `eval`、`exec`、`os.system`、`child_process.exec`；新端点缺少授权检查；弱加密选择；未签名/未认证的 webhook handler。

要问的问题：*如果攻击者控制这个函数里的每个变量，他们能做的最坏的事是什么？* 如果你答不上来或答案很糟，先修复或升级到安全审查再合并。


#### 应用 checklist

对每个 AI 生成的 PR，显式过一遍七个谎言。最初几次较慢（可能增加 10 分钟审查）。熟练后变成条件反射（可能只增加 2 分钟）。bug 捕获率明显高于无辅助审查；时间投入在抓到几个 bug 后就回本。附录 D 提供可打印的整合 checklist。
