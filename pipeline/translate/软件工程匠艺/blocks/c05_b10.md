#### 应用问题

**Q5.** 你的团队正从 GitHub Flow 迁移到主干开发。写一页迁移计划，列出：(a) 团队必须先建立的前提条件，(b) 按顺序的迁移步骤，(c) 你会追踪哪些指标以判断迁移是否成功。

提示

§4.7 描述了 Trellis 的实际时间线。借鉴其结构。

**答：** 合理计划：

**(a) 前提条件**

  1. CI 必须在 15 分钟内跑完完整套件，`main` 上绿率 ≥ 95%。
  2. 必须有特性开关服务（LaunchDarkly、Statsig、Unleash 或 Flipt），团队已培训使用。
  3. 必须商定文档化的开关生命周期（创建、监控、移除）。
  4. 必须商定目标 PR 规模（例如 ≤ 400 行实质性改动）。
  5. 审查 SLA 必须文档化并被接受。

**(b) 迁移步骤**

  1. 写一份 ADR，解释变更、已满足的前提条件、预期结果。
  2. 落地前提条件：集成开关服务、收紧 CI、培训团队。
  3. 把进行中的长期分支转成基于开关的主干工作；关闭长期分支。
  4. 设立新规范：从那时起所有新工作都走主干开发。
  5. 第一个月密切关注事故；预计至少会发生一次开关相关配置错误，用流程更新回应，而不是退回模型。
  6. 在三个月节点开一次回顾。

**(c) 指标**

* PR 规模分布（目标：中位数 < 300 行，P90 < 600 行）。
* PR 审查周转时间（目标：工作时间中位数 < 4 小时）。
* `main` CI 绿率（目标：≥ 95%）。
* 功能平均交付时间（迁移前后对比）。
* 事故率（迁移前后对比；迁移期间预计短期上升）。
* 开关数量与平均开关年龄（警惕腐烂）。

如果三个月时指标没有向好，先调查再宣布成功。

**Q6.** 为你的团队写一份特性开关生命周期策略。规定：开关如何创建、谁可以翻转、如何分阶段推出、何时清理。

提示

策略应让正确的事成为容易的事。

**答：** 合理策略：

**创建**：任何工程师都可以创建开关。创建时必须包含：遵循约定 `<scope>_<feature>_<verb>` 的名称（例如 `scoring_new_algorithm_enabled`）、描述、负责人（工程师或团队）、不超过两个季度后的 `kill_by_date`，以及除本地开发外所有环境默认值 `false`。

**翻转**：开发环境任何工程师；staging 任何工程师但需通知团队频道；生产环境需两人审批（负责人加另一名工程师），并通知团队频道；影响超过 10% 用户的开关还需 on-call 工程师额外审批。

**分阶段推出**：0% → 1% → 10% → 50% → 100%。每阶段负责人至少观察一个工作日相关仪表盘，再推进。任一阶段失败立即回退到上一百分比，并在下次尝试前做事后分析。

**清理**：开关在生产环境达到 100% 两周后，自动对负责人创建 issue。负责人有 1 个冲刺时间合入移除 PR。截止日期过后 issue 上报团队 lead。已连续 1 个月处于 0% 的开关（实际已死）也适用移除。

**例外**：长期运行操作开关（kill switch、region toggle、限流器）不受清理规则约束，但必须标记为 `operational` 并每年审查。

这份策略让开关有用而不腐烂，并迫使团队审慎对待哪些开关会持续存在。
