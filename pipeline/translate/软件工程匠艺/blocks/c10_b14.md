#### 深入思考

**Q8.** 辩护或反驳：“2026 年，AI 智能体让重构如此便宜，工程师应尽可能激进地应用十二种重构。” 激进重构的成本是什么？

**讨论：** 支持：AI 让重构的机械部分几乎免费；瓶颈转移到识别和判断，两者都随练习提升；激进重构产生更干净、维护性复利增长的代码库。

反对：没有判断的激进重构是*为变而变*；每次重构都有审查成本、相邻在研分支的合并冲突成本、风险成本（即使有测试）。重构的总成本不为零；它包括人类审查和系统级涟漪。AI 驱动的激进重构可能用大量 PR 淹没团队审查能力。

综合：按代码库引导重构，不要把重构当作与工作分离的刻意项目。在改动代码时应用十二种重构；不要安排纯重构的“重构冲刺”。童子军规则（第 20 章）是有原则的版本：每次 PR 都让代码比发现时好一点，而不把重构作为全部意义。

**Q9.** 本章主张十二种重构是工作工程师的条件反射集。针对你的具体代码库，你会在十二种之外再加什么？又会把哪几种降级？

**讨论：** 2026 年可能添加的代码库特定候选：

* **用模块函数替换类**（尤其在 Rust、Go、Python 等习惯用模块级函数而非类的语境）。
* **引入 Result 类型**（在 TypeScript 或 Python 中，用显式 `Result<T, E>` 类型替代 `throw`/`raise`）。
* **抽取类型别名**（TypeScript 中，复杂类型重复时）。
* **用 Fake 替换 Mock**（按第 7 章，正在从 mock 重测试迁移的代码库）。

可能降级的代码库特定候选：

* **把函数组合成类**（如果代码库是函数式优先；自然单元是函数，不是类）。
* **用多态替换条件表达式**（如果代码库习惯用 sum type 或模式匹配；多态是错误工具）。

一般教训：十二种是起点，不是固定集合。先采纳、练习，再按代码库习惯调整。知道你的条件反射集才是持久技能；具体列表是代码库特定的实例。
