一位 Trellis 工程师被分配修复一个已有八个月没人碰的客户数据模块中的 bug。bug 是日期计算中一个小小的 off-by-one；修复三行。工程师的 PR 包含三行修复和七个额外小改动：一个误导变量重命名、删除一个死分支、抽出一个 helper 函数、更新 docstring、删除一条原 2022 年作者已离职且目标不再相关的 `// TODO`。审查者问：为什么有这些额外改动？工程师回答：“童子军规则。”

本章讲增量偿还债务的三种模式：童子军规则用于持续小改进，绞杀者无花果模式用于增量迁移，Branch by Abstraction 作为替代。每种模式都产生渐进改善，无需第 11 章大型重构的承诺。每种都比安排的债务清理 sprint 更可持续。


### 20.1 童子军规则

童子军规则源自童子军，由 Robert C. Martin 在软件领域推广，是在每次触碰代码时都比发现时更干净一点的纪律。


#### 定义：童子军规则

童子军规则规定：每次你因任何原因触碰一段代码，都要让它比你发现时更干净一点。改进很小（重命名、删除死分支、抽出 helper）；它们与实质性工作捆绑；它们在团队 PR 中累积。

直白地说：不要只修 bug；顺手修一个相邻的小问题。


#### 为什么这种纪律有效

三个操作理由：

* **每个 PR 的成本有界**：童子军改进只需几分钟；实质性工作几小时；比例开销小。
* **改进累积**：跨数年数百个 PR，代码库会显著变干净，无需任何人安排重构 sprint。
* **纪律随工程师走**：内化了规则的工程师在每个触碰的代码库都应用它；这个习惯在他们的职业生涯中复利。


#### 什么算童子军改进

合适的童子军工作：

* 把*误导变量*重命名为它代表的含义。
* *删除死分支*（分支已无法进入）。
* 从一段内联逻辑中*抽出 helper 函数*。
* *更新过时注释*，使其匹配代码。
* *删除陈旧的 `// TODO`*，原作者已离职且目标不再相关。
* 为 bug 修复触及的行为*补缺失测试*。
* *删除未使用的 import* 或未使用变量。

每个都是小改动；每个几分钟；每个都让代码可衡量地更好。


#### 什么不算

纪律是*小*改进。更大的工作应进独立 PR：

* **重构整个类**：太大，开独立 PR。
* **重写子系统**：显然太大。
* **跨多个文件重命名公共 API**：太大。
* **重排文件夹**：太大。

经验法则：童子军改进不应需要自己的 PR 描述段落。如果你需要解释它，就太大了；开独立 PR。
