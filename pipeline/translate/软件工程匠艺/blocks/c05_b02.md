#### GitHub Flow

更简单的模型。从 `main` 切分支；每个分支对应一个功能或修复；PR 就绪后合并到 `main`；`main` 始终可部署。没有 release 分支，没有 `dev` 分支。分支可以比主干开发活得长一些，但精神类似。

优点：简单、被广泛理解、与 GitHub UI 自然贴合；CI 要求低于主干开发。

缺点：鼓励比主干开发更长的分支，冲突更大；模型对发布时功能只完成一半的情况保持沉默，这导致临时采用特性开关或长期分支。

这是 2026 年最常见的模型，对 20 人以下团队是合理的默认选择。


#### Git Flow

更复杂的模型。两个长期分支（`main` 和 `develop`）；功能分支从 `develop` 切出；稳定化时从 `develop` 切 release 分支；hotfix 从 `main` 切出。每种合并类型有自己的仪式。

优点：为发布版本化产品的团队提供结构（例如可安装软件、移动应用、库），这些产品同时有多个版本在生产环境运行。

缺点：对持续交付的团队仪式过重；长期存在的 `develop` 分支容易与 `main` 漂移；该模型为每几周发布一次的世界设计，而不是每天发布多次。

2026 年，Git Flow 仍适合发布版本化产品的团队（移动应用、本地部署软件、库发布），但对大多数 SaaS Web 团队过度工程。


#### 如何选择

诚实的决策标准：

属性 | 主干开发 | GitHub Flow | Git Flow  
---|---|---|---  
最佳发布节奏 | 每天多次 | 每天到每周 | 每周到每月  
CI 要求 | 快速、可靠 | 中等 | 中等  
特性开关使用 | 普遍 | 按需 | 罕见  
分支寿命 | < 2 天 | < 2 周 | 数周到数月  
团队规模甜点 | 5–500 | 1–50 | 5–200（版本化产品）  
心智开销 | 采纳后低 | 低 | 高  

如果你的团队每天多次发布且有快速 CI，优先主干开发。如果每天到每周发布、CI 中等，优先 GitHub Flow。如果发布可安装软件的版本化产品，优先 Git Flow。把某个模型当教条套用到所有团队上是失效模式；根据上下文匹配才是纪律。


### 4.2 Conventional Commits

Conventional Commits 是提交信息格式的规范。格式：

    <type>(<scope>): <description>

    [optional body]

    [optional footer]

其中 `<type>` 来自固定词汇表（`feat`、`fix`、`docs`、`style`、`refactor`、`test`、`chore`、`perf`、`ci`、`build`、`revert`），`<scope>` 是可选的代码库区域。示例：

    feat(auth): add MFA enforcement for admin role
    fix(scoring): correct rounding for pre-2021 accounts
    refactor(billing): extract RefundCalculator from BillingService
    chore(deps): bump tokio to 1.41

破坏性改动用 `!` 或在 footer 加 `BREAKING CHANGE:` 标记：

    feat(api)!: rename /users/me to /users/current

    BREAKING CHANGE: clients calling /users/me must update to /users/current
