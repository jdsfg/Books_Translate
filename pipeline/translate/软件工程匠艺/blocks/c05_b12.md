#### 深入思考

**Q8.** 为以下命题辩护并反驳：“2026 年，所有分支模型最终都会收敛到主干开发，因为 AI 智能体让小而快的 PR 成为主导工作流。” 什么证据能终结这场辩论？

**讨论：** 支持：agent-PR 模式（§4.6）产生大量小而快的 PR；主干开发最适配这种模式；其他模型强加摩擦（长期分支、仪式），智能体不善于遵守；因此均衡点是主干开发。证据：采用 agent-PR 模式的团队越来越多地收敛到主干开发和特性开关。

反驳：分支模型选择取决于产品类型（版本化 vs SaaS）、监管背景和团队技能，这些因素不会因实施者变成智能体而改变。受监管的金融团队仍然需要 release 分支；移动应用团队仍然需要版本分支。智能体适应团队的模型；团队模型适应产品，而不是适应实施者。证据：2026 年许多重度使用智能体的团队仍然使用 Git Flow 或 GitHub Flow，因为他们的产品需要。

综合：agent-PR 模式*提升*了那些*能够*采用主干开发的团队的价值，因为它放大了节奏优势。但它没有消除*不能*采用的团队的*约束*。收敛是真实但局部的；任何一边的教条版本都是错的。能终结辩论的证据是对采用智能体的团队进行多年纵向研究，并按产品类型分段；2026 年我们只有这种数据的碎片，答案是“主干开发在增加份额，但并非普遍。”

**Q9.** 追踪第 3 章（本地 Git 匠艺）与第 4 章（团队 Git 信条）的纪律如何组合。说出三种具体组合和一种张力。

**讨论：**

组合：

  1. **原子提交 + Conventional Commits**：原子提交在格式规范化后更有用，因为 type+scope 让原子单元可查询。复利是乘法：单独原子提交有用，单独 Conventional 部分有用，两者一起则显著有用。
  2. **Interactive rebase + PR 作为工作单元**：push 前 interactive rebase 产生干净 PR；干净 PR 可作为一个单元审查；可单元审查的 PR 使 SLA 纪律可行。每一步依赖前一步。
  3. **Bisect + 主干开发**：主干开发产生大致线性历史，让 bisect 的二分查找变得简单。Bisect 的价值随历史质量复利；历史质量随团队模型复利。两者一起把调试从小时变成分钟。

张力：

  1. **Interactive rebase + 团队共享分支**：本地 rebase 纪律产生干净历史，但如果分支是共享的（别人基于其上工作），rebase 会重写他们的上下文。张力通过约定解决：在主干开发配短分支中，rebase 在 push 前完成，冲突不会出现；在长期分支模型中，团队需要关于何时允许 rebase 的明确策略。

一般教训：本地匠艺不会自动扩展到团队匠艺；团队约定必须允许本地匠艺适用。没有明确分支信条的团队，会让每个工程师个人实践好 Git 匠艺，但集体产出纠缠历史。信条是放大器。
