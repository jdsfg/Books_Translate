#### 替代它的是什么：依赖注入

依赖注入（Dependency injection, DI）把依赖显式传给使用它们的代码。如果需要“一个实例”保证，就在启动时构造一次，然后传到所有需要的地方。

    # Singleton（不要用）
    class Logger:
        _instance = None
        @classmethod
        def get_instance(cls):
            if cls._instance is None:
                cls._instance = cls()
            return cls._instance
        def log(self, msg): ...

    def process_order(order):
        Logger.get_instance().log(f'Processing {order.id}')
        # ...

    # 依赖注入
    class Logger:
        def log(self, msg): ...

    class OrderService:
        def __init__(self, logger: Logger):
            self._logger = logger
        def process_order(self, order):
            self._logger.log(f'Processing {order.id}')

    # 启动时只构造一次
    logger = Logger()
    order_service = OrderService(logger=logger)

收益：`OrderService` 在构造函数里声明依赖；测试可传 fake logger；应用可按需构造多个 `OrderService`；依赖图显式。


#### 什么时候（罕见）Singleton 仍合适

Singleton 对真正全局、真正唯一的资源仍可辩护：进程级线程池、本地句柄注册表、OS 级互斥量。每种情况下，全局唯一性由底层资源保证，而不是应用约定。这些情况稀少；大多数应用级对象，DI 是更好的默认选择。


#### 2026 年的现实

2026 年，大多数主流框架已内置 DI。Spring（Java）几十年前就有；FastAPI（Python）有内置依赖注入；NestJS（TypeScript）本质上是 DI 形状；Rust 习惯使用构造器注入。模式的机制不再是工程师的问题；框架负责构造和装配。


#### 常见误解

一个常见误解是“Singleton 对 logger 这种确实全局的东西没问题。” 错误在于把“逻辑上单一”和“应该做成 Singleton”混为一谈。一个 logger 每个进程逻辑上只有一个，但 DI 仍是更好的机制：启动时构造一个 logger，注入到各处，测试就能替换 fake 而不用碰全局状态。“逻辑单一性”保留；“全局访问”失效模式避免。
