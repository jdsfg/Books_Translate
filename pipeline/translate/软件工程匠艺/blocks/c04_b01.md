两位工程师交付同一个功能。工程师 A 合并了一个名为 “added stuff” 的单一提交，包含 1,400 行混合关注点。工程师 B 合并了 7 个提交，信息分别是 “extract Permission type from User model”、“add PermissionService with read-only methods”、“wire PermissionService into AccessGuard”，每个都少于 200 行且各自可构建。6 个月后，生产 bug 浮现。团队使用 `git bisect`。二分工程师 A 的提交时指向 “added stuff”，输出毫无用处。二分工程师 B 的提交时指向引入 bug 的确切 80 行提交。修复在 20 分钟内确认，而不是 4 小时。

本章论证：Git 不只是版本控制工具；它是一种*思考*工具。原子提交纪律、rebase 与 merge 的选择、把 bisect 当作系统化调试、把 reflog 当作撤销、用 interactive rebase 塑造连贯叙事：这些都是匠艺技能，都会复利。下一章把这些本地技能提升到团队层面。本章只停留在个人工作站。


### 3.1 原子提交纪律

Git 匠艺的第一原则是*原子提交（atomic commit）*。一个原子提交只做一件事、让代码库处于可构建状态，并附解释改动的提交信息。


#### 定义：原子提交

一个原子提交满足三个属性：(1) 做出单一概念性改动；(2) 提交时的 tree 能构建并通过测试；(3) 提交信息以祈使语气说明改了什么、为什么改。

直白地说：如果队友把你的提交 cherry-pick 到另一个分支，它应该干净应用、可构建、通过测试，并读起来是一个连贯的工作单元。三者任一失败，你的提交就不是原子的。

这项纪律产生三项下游收益：

* **可二分性（Bisectability）。** 落在原子提交上的 bisect 能把 bug 定位到小范围。落在 “added stuff” 上的 bisect 毫无用处。
* **可审查性（Reviewability）。** 每个提交可独立审查。一个包含 7 个原子提交的 PR 是 7 次小审查，不是一次大审查。
* **可回退性（Revertability）。** 出问题时，你只回退一个提交，而不是一个异质包裹。
