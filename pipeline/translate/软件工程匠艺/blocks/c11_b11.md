#### 应用问题

**Q5.** 在代码库里选一个覆盖率低的函数。为它写五个特征测试。记录发现的任何令人惊讶的行为；暂时不要修复。

提示

五个测试应覆盖不同代码路径；覆盖率工具可指导哪些路径已被触发。

**答：** 这是开放练习。常见发现：五个测试揭示函数处理边界情况（负输入、空输入、极大输入）的方式团队之前没意识到。有些是有意的；有些是 bug；有些是残留。锁定当前行为；单独记录疑似 bug。

这个练习培养特征化期间*观察而不判断*的肌肉。判断稍后；锁定在先。练习后，函数可以在安全网下自信重构。

**Q6.** 选一个低覆盖率模块，应用“先重构以启用测试，再测试，再重构”模式。在写特征测试前至少做一次小的引导重构（对纯函数重命名或抽取函数）。记录步骤。

提示

引导重构的安全性应由 IDE 或 AI 智能体保证，而不是由测试保证。

**答：** 这是开放练习。典型序列：

  1. **引导**：重命名一个名字有误导性的方法。IDE 的重命名工具保证安全。
  2. **引导**：把一个 30 行块抽成 helper 函数。只要没有外部依赖，IDE 的抽取工具保证安全。
  3. **特征化**：在新暴露的表面上写 5–10 个测试（重命名后的方法和抽取出的 helper）。
  4. **重构**：在安全网下应用更实质的重构（例如用多态替换条件表达式）。

教训：引导步骤小、近乎机械，并为测试步骤扫清障碍。没有引导，测试步骤可能不得不在一团中间状态的迷宫中特征化函数；有了引导，表面变干净。

**Q7.** 把 §10.4 的 AI 层重构工作流应用到一个真实重构上。让智能体执行十二种重构之一的机械部分。验证：智能体是否修改了任何测试文件？所有测试是否仍通过？智能体是否引入了请求范围外的改动？

提示

用 `git diff -- tests/` 和 `git diff --stat` 检查。

**答：** 这是开放练习。常见发现：

* 智能体干净地应用了请求的重构。测试通过。没有测试文件修改。diff 局限在被重构的文件内。✅
* 或者：智能体修改了一个测试，以“修复”一个断言内部调用结构的测试。⚠️ 调查：该测试是脆弱的吗（如果是，修改合法），还是智能体移动了神谕以让重构通过（如果是，修改错误，必须回退）？
* 或者：智能体引入了请求范围外的重构（例如在应用抽取函数时顺带重命名了一个无关函数）。⚠️ 丢弃范围外改动；diff 必须匹配请求。

验证步骤必不可少。没有它，智能体“重构完成”的声明未经验证。有了它，智能体的工作可以像初级工程师完成的那样审查。
