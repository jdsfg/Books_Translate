绞杀者无花果的安全来自：(a) 步骤小（每块有界），(b) 安全网（新系统 break 可走旧系统），(c) 持续发布（团队全程获得反馈），(d) 可回退（每一步可回滚）。

大型重写的风险来自相反：大步、无安全网、不发布、一次性。Joel Spolsky 的《Things You Should Never Do, Part I》（第 21 章）称之为软件工程经典失败模式。大多数大型重写耗时远超估计，最终要么放弃，要么变成比原有两者都糟的混合。

**Q3.** 三个迁移场景。对每个判断应使用绞杀者无花果还是 Branch by Abstraction。简要辩护。

(a) 你们的单体暴露 `/api/v1/reports/*` HTTP API 给外部客户。你们正从头构建一个 API 更干净的新报表服务。客户不能立即改 URL；旧 API 至少 12 个月必须继续工作。

(b) 你们内部认证模块当前用 bcrypt 做密码哈希。安全团队想迁移到 Argon2id，但调用 `auth.verify_password(...)` 的应用代码不应改变。迁移必须处理现有用户（数据库里 bcrypt 哈希）和新用户（之后 Argon2id 哈希）。

(c) 你们团队用托管队列服务（如 Amazon SQS）替换现有进程内作业队列（自定义 Python 代码）。发布作业的应用代码应保持现有 API；消费者可以改变。

提示

绞杀者无花果：在外部边界路由请求。Branch by Abstraction：在内部接口后路由操作。

**答：**

(a) **绞杀者无花果。** 迁移发生在*外部边界*（HTTP API，被客户消费）。每个 `/api/v1/reports/<name>` endpoint 独立迁移：旧单体继续服务未迁移 endpoint；新报表服务服务已迁移的 endpoint；HTTP gateway（或 DNS 路由）按 endpoint 分发。12 个月后所有 endpoint 迁移且客户已转移，单体报表代码删除。

(b) **Branch by Abstraction。** 迁移发生在*内部接口*（`auth.verify_password`）。调用该函数的应用代码不应改变；只有它背后的实现改变。定义 `PasswordHasher` 协议；bcrypt impl 处理遗留哈希；Argon2id impl 处理新哈希；编排逻辑（“根据用户存储的哈希格式用哪个 hasher？”）藏在协议后。应用在整个迁移前、中、后都调用 `auth.verify_password`。

(c) **Branch by Abstraction**（带一个小的绞杀者无花果组件）。发布侧是内部的——调用 `queue.publish(job)` 的应用代码不应改变；这是 Branch by Abstraction。*消费*侧可能是外部的（独立进程），让消费侧迁移更像绞杀者无花果（每个消费者独立迁移）。两种模式结合：发布者内部用 BBA；消费者进程边界用绞杀者无花果。
