### 17.5 Runbook

Runbook 是生产场景的操作文档。受众是凌晨 2 点 on-call 的工程师。


#### Runbook 里该放什么

* **触发条件**：如何发现该情况。什么告警触发；dashboard 长什么样。
* **诊断步骤**：如何确定具体根因。按顺序检查什么。
* **缓解步骤**：如何止损。常与修复根因不同。
* **升级**：何时、如何叫醒其他人。
* **恢复验证**：如何确认影响已解除。


#### Runbook 为何关键

Runbook 在工程师*有压力*、*非工作时间*、*可能不是作者本人*时被查阅。对读者心态、可用上下文和耐心的所有假设都必须保守。一份要求读者具备他们没有的领域知识，或要求无差错执行多步骤的 runbook，在需要时会失败。

一个有用的 2026 年 runbook 示例：

    # Runbook：数据库连接池耗尽

    ## 触发
    - PagerDuty 中 `db_pool_exhausted` 告警触发。
    - 症状：API 错误上升；P99 延迟 > 5s；日志显示 “no available connections” 错误。

    ## 诊断（5 分钟）
    1. 检查 Grafana dashboard `db-pool-health`：确认 `active_connections` 接近 `max_connections`（默认 100）。
    2. 通过 `kubectl get deployments` 检查最近部署：30 分钟内是否有增加连接使用的部署？
    3. 通过 `psql -c "SELECT query, calls, mean_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10"` 检查慢查询日志：是否有查询突然变慢？
    4. 检查应用日志中的新错误模式。

    ## 缓解
    - 立即（< 1 分钟）：通过 `kubectl scale deployment api --replicas=<new>` 把 API pods 扩容 50%。每个 pod 有自己的池，更多 pod = 更多总容量。
    - 如果怀疑近期部署：通过 `./scripts/rollback.sh <deploy-id>` 回滚。
    - 如果怀疑慢查询：用 `psql -c "SELECT pg_terminate_backend(<pid>);"` 终止对应 pid（来自 `pg_stat_activity`）上的查询。

    ## 升级
    如果 15 分钟内缓解未稳定，呼叫 DBA on-call（通过 PagerDuty schedule “db-ops”）。

    ## 恢复验证
    - `active_connections` 降至 `max_connections` 的 70% 以下。
    - P99 延迟回到基线（< 500ms）。
    - 错误率回到基线（< 0.1%）。
    - 指标正常后等待 15 分钟再关闭事故。

Runbook 具体、可操作，并在实战中 tested。on-call 工程师无需从第一原理推理即可执行。


#### Runbook 维护

Runbook 衰老很快。基础设施变；告警名变；kubectl 命令变。纪律是：影响 runbook 场景的变更也要更新 runbook：

* 每次事故触发一次 runbook 审查；如果 runbook 漏了什么，更新它。
* 每次影响 runbook 场景的基础设施变更都要更新 runbook。
* 每季度：on-call 审查所有 runbook；过时的条目被标记并修复。

没有维护，runbook 比没有更糟；它们误导 on-call 工程师采取错误行动。纪律是要么维护，要么删除。
