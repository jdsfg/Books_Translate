(c) 一家 200 人企业 SaaS 公司新雇一位 VP of Engineering，提议把 6 年历史的 Java 后端用 Rust 重写以“现代化技术栈”。新团队被雇来做重写；现有团队迁移期间继续维护 Java 代码库；时间线是“需要多久就多久”。

**答：**

**(a) 可能失败。** 只有同一团队成立。结构性不可能（不成立，RoR 对大多数公司都够 scale；重写是 hype 驱动）、可衡量改进（不成立，“不 scale”不是指标）、持续承诺（弱，12 人初创公司会让功能压力干扰）都 fail。最危险：*可衡量改进*——没有目标团队就不知道何时成功。

**(b) 强提案，历史上成功了。** 四条齐全：Oracle 许可与 Netflix 增长结构性不兼容；每次查询成本和扩展可衡量；高管明确支持；数据库团队迁移自己的工作。

**(c) 可能失败。** 四条中有三条弱。结构性不可能（不，审美）；可衡量改进（含糊）；持续承诺（重写团队与维护团队分裂）；同一团队（**不成立**——新团队被雇）。同一团队违反最直接致命：新团队不了解 Java 代码库边界情况，会在生产中发现，且发现得晚、代价高。

**一般教训**：四条属性必须齐全（§21.5）。多数失败重写只有两三条。同一团队属性最常违反，也最直接致命；如果你需要引入与维护团队分离的“重写团队”，重写已经输在起跑线。

**Q3.** 何时重写比能实现同样目标的绞杀者无花果更糟？

提示

对比风险画像。

**答：** 几乎总是。重写方差更高：项目要么壮观成功，要么灾难性失败。绞杀者无花果方差更低：每块风险有界；团队持续发布；遗留是安全网。

要让重写合理，绞杀者无花果必须*不可行*。不可行门槛很高：即使混乱的遗留系统，只要团队愿意设计抽象层，通常都适合绞杀者无花果。

重写合理的狭窄案例（§21.2）涉及真正的结构性不可能（遗留完全无法扩展）或使方差可接受的特定组织支持。大多数*感觉*值得重写的案例实际上并不值得；有纪律的答案是绞杀者无花果。
