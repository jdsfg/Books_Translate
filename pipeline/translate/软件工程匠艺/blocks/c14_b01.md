2024 年，Helix 一个 PR 加了一个叫 `CustomerRepositoryFactoryProvider` 的类。它的职责是构造 `CustomerRepositoryFactory`，而后者又构造 `CustomerRepository`。PR 作者是一位 2010 年学过设计模式的高级工程师，本能地套用了它们。审查者 Aki 只问了一个问题：“`Provider` 做了什么叫 `get_customer_repository()` 的函数做不到的事？” 作者想了几分钟，答不上来。PR 被重写成单个函数。原来的三个类消失了。

本章讲的是那些以 2026 年 hindsight 看，失败多于成功的设计模式。有些一直可疑；有些在原始语境下合理，但已被语言特性取代。三类都值得了解，因为 LLM 有时会提议它们（线索 C 谎言 #2：过度抽象），而且遗留代码库里仍可能有。知道它们为何衰老，是重构掉它们和拒绝新增它们的基础。


### 13.1 Singleton：被依赖注入取代

Singleton 模式确保一个类只有一个实例，并提供全局访问点。1995 年，这是对“我需要一个这种东西，而且想随处用”的合理回答。2026 年，它很少是正确答案。


#### Singleton 为何衰老

Singleton 的缺陷，按严重程度递增：

* **全局状态隐藏依赖。** 使用 `Logger.getInstance()` 的函数不会在签名里把 logger 列为依赖；依赖是隐式的。读者不看函数体就不知道它依赖什么。放大到整个代码库，这种隐藏耦合会变成导航问题。
* **Singleton 难测。** 使用 `Logger.getInstance()` 的函数测试时不容易替换 fake logger；singleton 就是 singleton。测试隔离受损；测试若共享 singleton 状态会互相干扰。
* **Singleton 强制全局唯一。** 真实系统常希望每个请求、每个租户或每个环境一个实例。全局唯一假设在这些情况下是错的。
* **Singleton 组合性差。** 两个互相依赖的 singleton 会产生没人想 debug 的启动顺序问题。
