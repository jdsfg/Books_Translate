#### 应用问题

**Q5.** 为你的代码库写或更新一份 CLAUDE.md。包含 §22.4 的七类内容。在写之前和之后各跑一次 AI 会话；比较输出质量。

提示

前后对比就是价值。

**答：** 这是开放练习。常见发现：

* 写之前 CLAUDE.md（如果有）是泛化的；写之后是特定于代码库约定。
* 写之前智能体输出用泛化模式和名字；写之后匹配代码库约定。
* 写之后每个 AI 生成 PR 的审查时间下降，因为需要纠正的内容变少。

写 CLAUDE.md 成本适中（首版约半天）；收益在每次后续 AI 会话。

**Q6.** 用 spec 驱动工作流实现一个小功能。先写测试，再调用智能体，再审查输出。记录每步耗时和遇到的问题。

提示

细分揭示人类时间集中在哪。

**答：** 这是开放练习。中等规模功能的典型细分：

* 写测试：30–60 分钟。
* 调用智能体并执行：人类 5 分钟（智能体运行时人类做其他事）。
* 审查：30–60 分钟。
* 迭代：15–30 分钟。
* 合并：5 分钟。

总人类时间：1.5–3 小时；没有工作流可能花一整天或更多。人类时间集中在写测试和审查；编码时间被委托。

**Q7.** 用智能体提交 PR 工作流（§22.6）处理一个小 ticket。智能体开 PR；你审查。工作流是否有效？哪里崩了？

提示

崩点才是学习点。

**答：** 这是开放练习。常见发现：

* 智能体开 PR，描述合理，commit 原子，测试通过。
* PR 可能范围蔓延（智能体决定“顺便改进”相邻代码）；人类 push back。
* PR 的测试断言可能很弱，变异测试会发现；人类加强。
* 智能体不知道团队的架构决策；人类会 catch 尚未写入 CLAUDE.md 的约定违反。

每次崩点都是更新 CLAUDE.md 的机会。迭代几次后，工作流崩溃率下降；团队 CLAUDE.md 捕获更多隐性知识。
