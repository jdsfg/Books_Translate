#### 变量

变量名应描述值*代表什么*，而不是如何计算出来的。`customer_total_after_discount` 比 `t2` 或 `final` 好。变量的生命周期决定名字值得投入多少：一行局部变量可以短（`i` 作为循环索引）；跨三十行使用的变量应具体（`unprocessed_invoices`）。


#### 参数

参数名出现在函数签名和调用点；两边都应清楚。`customer` 这样的参数名可以；`c` 对大多数情况太短。例外：类型明显时（单个明显类型的构造函数），短名可接受。


#### 常量

常量值得最多投入：它们出现在很多地方，可能是常量含义的唯一文档。`LATE_FEE_RATE = 0.05` 比 `RATE = 0.05` 或直接写内联 `0.05` 好得多。常量名应代表它所表示的概念。


#### 常见误解（再论）

一个常见误解是“短函数里的变量名可以短，因为函数小。” 错误在于忘了函数可能增长。5 行函数里的 `t` 可以；50 行函数里的同一变量就不好。既然你不知道函数何时会增长，默认使用清楚名字；代价小，未来的你受益。


### 18.7 重命名作为持续纪律

命名不是一次性活动；而是每个 PR 都要应用的持续纪律。命名好的团队永远不会“完成命名”；他们不断改进。


#### 童子军命名规则

童子军规则（第 20 章预览）说“让代码比之前好一点”。应用于命名：每个触碰函数且函数有泛化或误导性名字的 PR 都是改进机会。PR 把重命名作为实质性变更的一部分；审查者注意到改进。

Currents 的 Carmen 追踪了一年指标：用泛化模式命名的方法百分比（Manager、Handler 等）与具体名字之比。指标从 22% 泛化改善到 8%，没有专门的重命名 sprint；每个 PR 应用童子军纪律就够了。


#### 重命名作为审查的一部分

审查者在 PR 里发现泛化名字时可以建议重命名。作者要么接受（在 PR 里重命名），要么拒绝并解释。两种都可以；对话本身就是价值。跨多个 PR，团队词汇对齐；代码库收敛到更好的名字。

纪律是足够*在乎*名字，会在审查中提出来。一个审查很多 PR 却从不提名字的团队，错过了命名作为设计的杠杆。
