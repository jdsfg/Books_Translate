#### 应用问题

**Q5.** 为你的团队起草一个 PR 模板，包含 §16.2 的组件。根据团队具体需求（行业、规模、代码库形状）调整。在接下来三个你开的 PR 上测试。

提示

模板是 forcing function；调整它以有用，而非官僚。

**答：** 这是开放练习。合理模板以 §16.2 的六个组件开始，可能增加：

* **Linked artifacts**：ticket、ADR、设计文档。
* **Backward compatibility**：任何破坏性变更；迁移说明。
* **Performance notes**：任何预期性能影响。
* **Documentation**：更新了哪些文档。

调整掉团队觉得不必要的 section；目标是适合团队的形状，不是 comprehensive checklist。

**Q6.** 规划一次团队沟通模式的异步优先迁移。识别三种当前同步、可转为异步的模式，以及三种应保持或变为同步的异步模式。为每种辩护。

提示

§16.3 和 §16.7 的约定是框架。

**答：** 这是开放练习。常见迁移：

同步 → 异步：

* Standup → 频道里的异步每日更新。
* 初始架构讨论 → ADR 草稿加异步评论。
* 会议里的代码反馈 → PR 评论。

保持或转为同步：

* 事故响应 → 实时协调。
* Onboarding 1:1 → 人际对话。
* 涉及多利益相关者的高风险设计争论 → 异步准备后的一次聚焦会议。

模式是*默认*：我们首先在哪里沟通？例外是明确且有理由的。团队先试行一两个周期，然后回顾。

**Q7.** 与 AI 智能体结对编程完成一个非平凡任务（例如重构一个 200 行函数）。记录什么有效、什么无效，以及你会为将来会话采用的具体习惯。

提示

习惯是会话的可持久产出。

**答：** 这是开放练习。常见发现与习惯：

* **有效**：AI 加速机械部分（抽取 helper、重命名、应用重构）。总时间可能是单人版本的一半。
* **无效**：AI 有时提议不符合代码库约定的变更（风格漂移）；人类必须抓住这些。
* **习惯**：会话开始用代码库约定锚定（引用 CLAUDE.md，指明要遵循的模式）。锚定避免后续重复解释。
* **习惯**：长会话拆成块，每次明确回顾。AI 上下文会漂移；回顾重新锚定。
* **习惯**：每次迭代后逐行读 diff。AI 的工作通过了测试；但线索 C 谎言藏在 diff 里。

这些习惯跨会话复利；有数月 AI 结对编程实践的工程师比刚入门的明显更 productive。
