#### 示例：JSON 序列化器

考虑一个带解析器的 JSON 序列化器。基于示例的测试：

    def test_serialize_then_parse_object():
        data = {'name': 'Alice', 'age': 30}
        assert parse(serialize(data)) == data

这个测试验证一个具体输入的 round-trip。基于属性的版本：

    from hypothesis import given
    from hypothesis import strategies as st

    json_value = st.recursive(
        st.none() | st.booleans() | st.integers() | st.floats(allow_nan=False) | st.text(),
        lambda children: st.lists(children) | st.dictionaries(st.text(), children),
        max_leaves=50,
    )

    @given(json_value)
    def test_serialize_then_parse_roundtrips(data):
        assert parse(serialize(data)) == data

框架现在生成数百个 JSON 值：标量、列表、嵌套对象、混合类型。对每个，它确认 round-trip 属性。如果某输入导致属性失败，框架会报告失败输入并*shrinks*：找到仍能证伪该属性的最小输入，于是 bug 报告最小且可执行。


#### 为什么这在 2026 年重要

LLM 写测试时聚集在幸福路径（线索 C 谎言 #1）。基于属性的测试正是填补空白的技巧。一个 LLM 写 50 个示例测试覆盖 50 个具体输入；同一函数的基于属性测试覆盖数千个。两种技术互补：LLM 产出幸福路径覆盖，基于属性测试产出边界情况覆盖。

2026 年的最佳实践是让 LLM 在示例测试旁加一个基于属性的测试，提示：“使用 Hypothesis 添加基于属性的测试。属性是 round-trip 恒等式：对任意 datetime，序列化后再解析返回原值。” 当前多数 LLM 能处理好；失效模式通常是 LLM 接受弱属性陈述而不验证。


### 6.2 选择属性

基于属性测试最难的部分是挑选属性。属性必须：

* **为真**：属性本身错误不会产生 bug，只会产生误报。
* **够强**：显然为真的属性（例如“函数返回一个值”）抓不到 bug。
* **独立于输入**：硬编码具体输入值的属性只是伪装成基于属性的示例测试。


#### 属性家族

常见家族，每种在不同上下文有用：

* **Round-trip / 反函数**：`parse(serialize(x)) == x`。适用于任何编码器/解码器对。
* **幂等**：`f(f(x)) == f(x)`。适用于规范化器、格式化器、去重器。
* **交换律**：`f(a, b) == f(b, a)`。适用于集合、multiset、集合操作。
* **结合律**：`f(f(a, b), c) == f(a, f(b, c))`。适用于 monoid：字符串拼接、列表合并、加法。
* **单位元**：`f(x, id) == x`。适用于 monoid 单位元（空字符串、空列表、零）。
* **不变量**：函数保持的结构属性。例如排序“输出列表是输入列表的排列”；退款再分配“总额不变”。
* **Oracle**：慢但显然正确的参考实现。属性：快速实现与 oracle 在所有输入上一致。
