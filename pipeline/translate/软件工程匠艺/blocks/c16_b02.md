#### 定义：代码审查

代码审查是第二工程师在变更合并前检查变更的做法，目标包括：(1) 捕捉作者遗漏的 bug，(2) 确保变更符合代码库约定与架构，(3) 在团队间共享知识，(4) 维护代码库长期健康。不同审查可侧重不同目标。

直白地说：另一双眼睛用一套结构化检查项检查工作。

目标按每审查价值大致排序：

  1. **捕捉 bug**：最高即时价值。审查中捕获的 bug 成本是几分钟；同样 bug 上线后成本是几小时到几天。
  2. **架构契合**：高长期价值。违反代码库形状的 PR 会污染每个后来读它的人的思维。
  3. **知识共享**：中等价值，随时间累积。审查者向作者学习；作者向审查者学习；团队心智模型趋同。
  4. **风格与品味**：低价值，过度应用时常为负。风格通常是 linter 的事；品味分歧消耗审查时间却没有相应收益。

纪律是聚焦高价值目的；失败模式是把大部分时间花在风格和品味上。


### 15.2 该看什么

审查者可操作的 checklist，按应受关注程度排序：


#### 1. 变更是否解决了它声称的问题？

读 PR 描述。读关联 ticket。确认代码解决了所述问题。标题为“修复 EU 客户 billing 舍入 bug”的 PR 如果未修改任何舍入逻辑，就是混乱信号；批准前要问。


#### 2. 代码是否有 bug？

审查者寻找：未测试边界情况（线索 C 谎言 #1）、差一错误（谎言 #5）、错误处理错误（谎言 #4）、虚构 API（谎言 #6，在 AI 生成代码中尤其如此，但也可能是人类捏造 API）。用对抗心态阅读：什么输入或状态会破坏它？

具体要扫描的 bug 模式：

* **空和空案例**：代码是否处理 `None`、空列表、空字符串、零？
* **边界案例**：条件边界发生什么？在 0、-1、最大值处？
* **错误路径**：依赖失败时函数做什么？传播、吞掉、重试还是回退？
* **并发**：是否有竞态？共享状态是否受保护？
* **资源泄漏**：文件是否关闭、连接是否释放、事务是否完成？


#### 3. 是否有能捕获回归的测试？

测试是正在被审查的第二份代码。应用第 5 章的断言强度启发式：对每个测试，它能捕捉什么 bug？如果答案不清楚，该测试就是覆盖率填充。

具体测试模式扫描：

* **有测试吗？** 没有测试的 PR 是黄旗（有时合理，通常不是）。
* **测试是在测新代码还是在测框架？** 只断言函数被调用、不断言输出正确的测试是线索 C 谎言。
* **测试是否覆盖代码声称处理的边界案例？** 如果 PR 描述提到“处理 EU 客户”，有没有 EU 客户的测试？
* **测试层级对吗？** 一个本应是单元测试却写成 200 行端到端测试是金字塔倒置信号（第 5 章）。
