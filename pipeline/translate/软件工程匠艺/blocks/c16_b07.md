### 15.7 2026 年的审查工作流

2025 年底一个典型的 Currents PR，含 AI 辅助：

  1. **作者开 PR**：包含描述、关联 ticket、可选指定审查者。
  2. **CI 运行**：测试通过、linter 通过、类型检查通过。PR 可审查的前提。
  3. **AI 审查工具运行**：Greptile（或同类）在 PR 上发表评论。作者可立即处理部分；其余留给人类考虑。
  4. **人类审查者收到通知**：PR 现在可进入人类审查（CI 绿、AI 审查完成）。
  5. **人类审查者审查**：应用线索 C checklist；回应 AI 工具评论；添加架构和上下文反馈。
  6. **作者处理评论**：推送额外提交；对具体评论逐条回复。
  7. **审查者复阅**：通常比初次审查快；确认变更解决了评论。
  8. **合并**：blocking 评论解决后。

总时间：典型 PR 大约 2–6 小时 wall-clock，人类时间集中在第 5、7 步。SLA（第 4 章）让作者有可预期的周转。


### 15.8 常见审查陷阱

审查者应避免的模式：


#### 橡皮图章审查

两分钟内批准 PR、未真正投入的审查者没有提供价值。要么 PR 极其简单（罕见），要么审查者没在审查。纪律是投入；如果仔细阅读后确实没有反馈，明确说（“我仔细看过了，没发现可标记的；LGTM”）。


#### 因个人品味阻塞

因非团队约定的风格偏好阻塞 PR 会消耗作者时间，并让团队畏惧审查。如果你有强烈偏好，把它作为团队约定提案；在它成为约定前，不要因此阻塞。


#### 两周审查

让 PR 搁置两周才审查会破坏 SLA 和作者上下文。审查到来时作者已转向别处；反馈更难处理。SLA 纪律（第 4 章）是解法；个人纪律是每天批量审查两次，而不是被动反应。


#### 过度解释者

给每条评论附一段解释的审查者可能过度投入每条评论。评论应简洁；如果解释需要一段，链接到 ADR 或进行同步对话。PR 不是设计教育场所。


#### 每个 PR 都重辩架构

在每个 PR 上重新争论代码库架构的审查者会消耗作者时间而无进展。如果架构错了，写 ADR（第 17 章）并明确提议变更；不要阻塞遵循当前架构的 PR。

高级审查者的工作，概括：捕获团队否则会遗漏的 bug 和架构问题，同时保持团队速度。每 PR 五个高价值发现是帮助；五十个发现，其中一半是风格级，是伤害。聚焦高价值；其余留给后续 PR、文档，或干脆不管。
