#### 深入思考

**Q8.** 辩护或反驳：“2026 年，代码审查比编码更重要，因为大部分代码是 AI 生成的。团队审查容量是发货瓶颈。”

**讨论：** 正方：AI 生成代码速度超过人类编写；瓶颈转移到审查；审查不好的团队发货慢或发货差。审查纪律成为核心匠艺技能（第 1 章论点的延伸）。

反方：审查也可由 AI 辅助；瓶颈随 AI 角色移动；人类审查的相对成本大致与代码量成比例。部分审查工作（风格、机械一致性）可自动化；人类角色集中在真正困难的部分（架构、上下文）。如果 AI 处理简单部分，每 PR 审查 wall-clock 时间未必成为瓶颈。

综合：2026 年审查*更重要*，因为量更大、失效模式具特征（AI 引入的 bug、线索 C 谎言）；人类在审查中的角色*更集中*（做 AI 不能做的事），但不一定随代码量成比例增长。投资审查纪律的团队总体发货更快；不投资的团队发货更慢或更差。无论哪种，纪律都更重要，而不是更不重要。

**Q9.** 把本章（代码审查）与第三至五部分（测试、重构、模式、架构）的纪律联系起来。这些纪律如何让审查更容易？

**讨论：** 每个先前纪律都有贡献：

* **测试（第 5–8 章）**：好的 PR 有记录意图的测试套件；审查者把测试作为理解变更应该做什么的一部分读。没有测试，审查者只能从实现推断意图，更慢更不可靠。
* **重构（第 9–11 章）**：遵循十二种重构和原子提交纪律的 PR 更易读。审查者每个 commit 看到一个概念变更；认知负荷可控。打包十个无关变更的 PR 会淹没审查者。
* **模式（第 12–13 章）**：恰当使用模式的 PR 是可识别的；审查者看到 “Strategy on the tier” 就立即理解形状。使用模式税的 PR 更难读，因为每层都要 navigate。使用反模式（Singleton、Visitor）的 PR 对审查者是红旗。
* **架构（第 14 章）**：符合六边形框架的 PR 在预期位置；审查者知道核心逻辑在哪里、adapters 在哪里、测试应该在哪里。违反框架的 PR 要求审查者先理解违规，再评估变更。

复利：每个纪律都减少审查者认知负荷；合在一起，它们让审查在 AI 增强工程的规模下可行。没有它们，审查者淹没在数量中。有了它们，审查者聚焦真正困难的部分。

这就是本书章节顺序之所以如此的原因：测试、重构、模式、架构，然后审查。每章是下一章的前置；没有之前的工作，审查章无法写成。
