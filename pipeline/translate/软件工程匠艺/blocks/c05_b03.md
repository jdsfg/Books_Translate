#### 为什么有效

三项下游收益：

* **自动生成变更日志。** `conventional-changelog` 等工具通过读取提交信息生成供发布使用的 changelog。于是 changelog 天然准确；不会有人写错。
* **自动版本升级。** 结合语义化版本（§4.3），提交类型自动决定下一个版本：`feat` 升 minor，`fix` 升 patch，`BREAKING CHANGE` 升 major。
* **分类支持。** 审查者或维护工程师可以 `git log --grep=^feat` 找所有功能，或 `git log --grep=^fix` 找所有 bug 修复。历史变得可查询。


#### 哪里会出错

两个值得点名的失效模式。

*标签游戏*：工程师把琐碎改动标成 `feat`，因为工具奖励功能而非修复，导致 minor 版本号虚高。缓解：在团队契约里约定什么算功能；在 PR 审查中审查 type。

*作用域漂移*：作用域开始时具体（`auth`、`billing`、`scoring`），最后变得模糊（`misc`、`cleanup`、`various`）。缓解：在 `commitlint` 规则里提交一个允许作用域的枚举列表，新模块出现时更新。


### 4.3 语义化版本

语义化版本（semver）是关于版本号变化含义的契约：

* **MAJOR** 版本升号用于不兼容 API 变更。
* **MINOR** 版本升号用于向后兼容的新功能。
* **PATCH** 版本升号用于向后兼容的 bug 修复。

结合 Conventional Commits（§4.2），版本升级是机械的：任何带 `BREAKING CHANGE` 的提交升 major；任何 `feat` 升 minor；任何 `fix` 升 patch。`semantic-release` 等工具可从提交历史自动完成升号和打 tag。


#### semver 适合的契约

Semver 适合：库、SDK、公共 API、用户会固定版本的 CLI 工具。版本号是这些用户依赖的契约的一部分。


#### semver 不适合的契约

Semver 不适合：持续部署的 SaaS Web 应用。SaaS 的当前版本*就是*版本；用户不固定版本；版本号只是内部账簿。对这些系统，更简单的方案（基于日期、基于构建号、基于 git sha）通常更清晰。强迫 SaaS 用 semver 会产生与现实脱节的版本号，让所有人困惑。

纪律在于知道你的软件在做什么契约。对 Currents（数据平台 SaaS），Carmen 为内部产品选择基于日期的版本，为 Currents 发布的开源 CLI 选择 semver。两种契约，两种目的。


### 4.4 把特性开关作为安全发布未完成功能的信条

特性开关（feature flag，也叫 feature toggle）是一个运行时条件，决定某段代码对给定请求、用户或环境是否激活。示例：

    if (await flags.isOn('new_scoring_algorithm', { userId })) {
      return newScoringAlgorithm(input);
    }
    return legacyScoringAlgorithm(input);

两条代码路径都部署；对特定用户只运行一条。通过服务（LaunchDarkly、Statsig、Unleash、Flipt）切换开关，无需重新部署代码。
