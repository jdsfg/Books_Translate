2024 年初，Helix 一个子系统的 `PricingService` 在一个 300 行方法里做了所有事：从 Postgres 读客户、从 Yaml 配置文件评估规则、向税率提供方发 HTTP 请求、通过 Stripe 收款、把结果写到日志服务。测试这个方法需要：真实 Postgres 测试数据库、用于 Yaml 配置的真实测试 S3 bucket、特定 URL 的真实测试税率提供方 mock、真实测试 Stripe 账户、测试 logger。每个测试设置要几秒、运行要几秒；测试套件慢得无法忍受。本可在单元测试里捕获的 bug 反而需要完整集成测试；团队经常干脆不写测试。

2024 年底，Aki 重构该子系统，应用两个相关设计原则：六边形架构（Ports and Adapters）和函数式核心 / 命令式外壳（Functional Core / Imperative Shell）。同样的业务逻辑被抽成纯函数；I/O 被推至边缘；业务逻辑测试变得快速、确定、数量众多。集成测试保留，但只针对 I/O 边缘；测试套件主体现在每测试毫秒级。

本章讲的就是使这一切可能的两个相关原则：六边形架构作为高层框架，函数式核心 / 命令式外壳作为可测试设计模式。两者在 2026 年仍然有效；都与前几章的测试、重构和模式纪律复利。


### 14.1 六边形架构

六边形架构，又称 Ports and Adapters，由 Alistair Cockburn 于 2005 年命名。形状：应用的核心业务逻辑位于中心；外部系统（数据库、消息队列、HTTP API、用户界面、文件系统）位于外围；核心与外围之间的连接通过*ports*（核心定义的抽象接口）和*adapters*（桥接核心与外部系统的具体实现）完成。


#### 定义：六边形架构

六边形架构把业务逻辑放在核心，与外部系统隔离。核心为需要在它上面执行的操作定义*ports*（抽象接口）；*adapters* 针对具体外部系统实现 ports。核心只依赖自己的 ports；ports 不依赖核心的具体类；adapters 同时依赖 ports 和外部系统。

直白地说：写业务逻辑时不要让它们知道数据怎么进怎么出。把数据库、HTTP 传输、队列、UI 都作为独立的 adapter 插进来。任意 adapter 都可替换而不影响核心。
