Spec 可验证：智能体输出要么通过测试，要么不通过。提示可解释：智能体可能误解，产出与人类意图不符的代码，人类必须用自己的心智模型比较结果。

Spec 驱动产出更好结果，因为验证自动；智能体成功标准无歧义；迭代快速收敛。提示驱动更 fuzzy；迭代更难，因为每次尝试可能对提示做不同解释。

Spec 驱动工作流是第 8 章测试即 spec 应用于 AI 实现的操作化。

**Q3.** 你的团队用 Claude Code agent mode 一个月了。每个工程师每次会话开头都打类似的上下文铺垫：“我们用 pytest。用 Decimal 不用 float。不要用 Singleton。测试放在 tests/。 fake 优先于 mock。” 团队还没写 CLAUDE.md。这种每次会话铺垫提示模式会产生什么具体问题？请构建把同样内容搬进 CLAUDE.md 的理由，包括除了“省按键”之外团队还能*获得*什么。

提示

提示铺垫是会话局部、每次重新发明。CLAUDE.md 持久且团队共享。

**答：**

**提示铺垫模式的问题：**

  1. **工程师之间漂移。** 工程师 A 打“用 Decimal 不用 float；不要 Singleton”；工程师 B 打“金额值用 Decimal；除非…否则避免 Singleton”。相同意图表达略有不同，会在不同工程师会话中产出略有不同的智能体行为。代码库中 A 会话写的代码与 B 会话写的代码有微妙约定差异。
  2. **没有团队审查。** 提示内容对团队其他人不可见。如果工程师 A 漏掉关键约定（“我们 ID 一律用 ULID，不用 UUID”），团队没人能审查他的提示并发现遗漏。每个工程师的提示是他自己的。
  3. **没有版本历史。** 当约定变化（“我们正在把 money 从 float 迁移到 Decimal；新代码应用 Decimal”），没有地方落地这次更新。每位工程师以不同方式听说；有些提示更新，有些没更新。
  4. **长度压力。** 每次会话上下文有限。铺垫变长后（框架、约定、反模式、东西在哪……）会挤占实际任务上下文。铺垫越长，实际任务可用上下文越少。
  5. **丢失制度记忆。** 新工程师必须通过询问或反复试错重新推导铺垫。团队惨痛学到“不要用库 X，它有已知 bug”的知识没有沉淀在任何人提示中，会被重新学习。

**CLAUDE.md 除了省按键还带来：**

* **团队可审查、版本控制、持久。** 文件是普通 git 产物：在 PR 中审查、随时间追踪、随团队学习更新。从“工程师 A 的 lore”变成“团队的 standing context”，这是耐久性提升。
* **智能体每次会话只读一次。** 没有提示长度压力；任务上下文预算完全用于实际任务。
* **新工程师 onboarding。** 新工程师读 CLAUDE.md，从资深工程师同等起点开始；试错学习曲线压缩。
