#### 倒金字塔反模式

常见失效模式是倒金字塔：很多端到端测试，很少单元测试。团队这样走有可以理解的原因（例如产品 UI 很重，没有 UI 测试就感觉没测；团队有 Selenium 专长；单元测试基础设施从没建起来）。结果是缓慢、flaky 的 CI 流水线；bug 出现得晚、离原因远；团队逐渐不信任测试套件。多数团队在有意识地评估金字塔形状并发现倒置后，会投资把测试下压到金字塔底层。


#### 沙漏与钻石

你可能遇到的两种变体。沙漏（hourglass）有很多单元测试、很少集成测试、很多端到端测试。这发生在团队跳过集成测试，认为“有单元和 E2E 就够了”。集成层常常是真正 bug 藏身之处；沙漏容易漏掉它们。

钻石（diamond）单元测试少、集成测试多、端到端测试少。这有时适用于单元太简单、不值得单独测试的系统（例如只是数据库薄包装），而数据库集成才是有趣行为。钻石对某些系统是合理变体，但不是默认形状。


### 5.2 覆盖率作为指标：用途与滥用

代码覆盖率衡量测试套件执行到的代码行（或分支、或路径）比例。它是最容易计算的测试指标，也是最容易误用的。


#### 覆盖率告诉你什么

没有被测试覆盖到的行，是对回归没有保护的一行。如果你改了那行，没有测试会抓住结果 bug；你会在生产环境发现。因此未覆盖代码是一个*风险指标*。

覆盖率低时是有信息的。一个模块 5% 覆盖率几乎肯定有未测试行为；调查这些行为很可能发现潜伏的 bug。覆盖率以*否定*方式工作：它告诉你缺口在哪。


#### 覆盖率不能告诉你什么

覆盖率不告诉你测试是否*好*。一个测试执行了 100 行代码但什么都不断言，仍然产生 100 行覆盖。一个断言错误的测试也产生覆盖。一个只用一个恰好遍历大部分代码的输入调用函数的测试也产生覆盖，尽管它在其他所有输入上可能都失败。

经典示例：

    def divide(a, b):
        return a / b

    def test_divide():
        divide(10, 2)  # 没有任何断言

这个测试对 `divide` 产生 100% 覆盖率，却完全抓不住任何 bug。覆盖率工具不知道断言缺失；它们只知道这行被执行了。
