#### README 里该放什么

* **项目是什么**：一段。不是营销文案；而是代码做什么。
* **如何设置**：前置条件、安装命令、配置。本地跑起代码所需的最小信息。
* **如何运行**：启动应用或运行测试的最常用命令。
* **在哪里找更多信息**：docs 文件夹、ADR、runbook、部署文档链接。
* **状态指示器**：构建状态、测试覆盖率、许可证、版本。


#### 不该放什么

* **API 参考**：放在 `docs/api/` 或自动生成。
* **教程内容**：放在 `docs/tutorials/`。
* **详细架构解释**：放在 ADR。
* **贡献指南**：放在 `CONTRIBUTING.md`。

纪律是让 README 保持简短。二十页的 README 不再是 README；它成了手册。读者 skimming 时无法定向，会迷路。Helix 的 README 通常一页；其余内容放在专用文件里，从 README 链接。要内化的原则：不要把*重要*和*首次阅读*混为一谈。重要文档可以放在任何地方；README 的任务是*首次阅读*。其余从 README 链接，而不是放在 README 里。


### 17.3 ADR

ADR 记录特定架构决策。Michael Nygard 于 2011 年提出的格式，到 2026 年已成标准：

    # ADR-N: Decision title

    Status: Proposed | Accepted | Superseded by ADR-M

    ## Context
    What is the problem? What are the constraints? What forces are at play?

    ## Decision
    What we decided.

    ## Consequences
    What this decision implies. Positive, negative, neutral.

    ## Alternatives considered
    What else we considered and why we did not choose it.


#### ADR 的用途

ADR 最深层的目的是捕捉决策背后的*推理*，让未来工程师（或未来的你）在上下文变化时重新评估。决策本身在代码里；推理不在。

没有 ADR，决策做出后被遗忘。未来工程师在代码中遇到这个决策，不知道为何如此，要么不理解就接受，要么没意识到后果就推翻。有 ADR，工程师阅读它，理解上下文，要么因为上下文仍然成立而保留，要么提出替代（新的 ADR 取代旧的）。


#### 何时写 ADR

当决策满足以下条件时，写 ADR 是合理的：

* **架构性**：影响代码库如何组织，而不仅是局部实现选择。
* **跨领域**：影响多个子系统，而不是孤立在一个文件里。
* **可逆成本非微不足道**：五分钟能改的决策不需要 ADR；需要三天重构才能改的决策需要。
* **可能被重新审视**：上下文可能变化；团队应能在不重做原始分析的情况下重新评估。

不需要 ADR 的决策：选择变量名、选择小库、遵循已有模式。这些是局部的；上下文在代码里。
