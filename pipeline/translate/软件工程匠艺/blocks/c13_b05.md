#### 2026 年示例

一个订单服务在订单状态变化时发出事件。多个子系统需要响应：发送确认邮件、更新分析 dashboard、审计日志记录、触发履约：

    from typing import Callable

    class OrderEventBus:
        def __init__(self):
            self._subscribers: dict[str, list[Callable]] = {}
        def subscribe(self, event_type: str, handler: Callable):
            self._subscribers.setdefault(event_type, []).append(handler)
        def publish(self, event_type: str, event):
            for handler in self._subscribers.get(event_type, []):
                try:
                    handler(event)
                except Exception as e:
                    log.error(f'Handler {handler} failed for {event_type}: {e}')

    # 订阅者在启动时注册
    bus = OrderEventBus()
    bus.subscribe('order.placed', send_confirmation_email)
    bus.subscribe('order.placed', update_analytics)
    bus.subscribe('order.placed', trigger_fulfillment)
    bus.subscribe('order.cancelled', send_cancellation_email)
    bus.subscribe('order.cancelled', refund_payment)

    # 订单服务发布事件
    class OrderService:
        def __init__(self, bus): self._bus = bus
        def place_order(self, order):
            # ... 实际工作 ...
            self._bus.publish('order.placed', OrderPlacedEvent(order_id=order.id))

收益：`OrderService` 不知道邮件、分析或履约；订阅者独立注册；新增订阅者不用修改 `OrderService`。


#### 何时 Observer 是正确模式

* **你有一个发布者和多个不相关的响应者**。
* **响应者不应与发布者耦合**，发布者也不应与响应者耦合。
* **你想在运行时或通过配置添加或移除响应者**。
* **响应者真正独立**，一个失败不应阻止其他运行。


#### 何时 Observer 是错误模式

如果你只有一个响应者，Observer 是过度工程；直接调用更简单。如果响应者必须与发布者同步运行，且发布者需要知道它是否成功，Observer 的 fire-and-forget 语义是错的。对于紧耦合且需要成功/失败反馈的场景，直接调用或 Command（§12.6）更好。

在 2026 年分布式系统中，Observer 常演变为消息队列（RabbitMQ、Kafka、AWS SNS）：模式通过改变发布机制而扩展到进程之外，但形状保留。


### 12.5 Iterator（迭代器）

Iterator 模式让你遍历集合而不暴露其内部结构。


#### 定义：Iterator

Iterator 模式为集合提供顺序访问机制。迭代器隐藏集合内部结构（列表、树、惰性流）；调用方只看到 `next` 操作。

直白地说：当你有包含元素的东西时，暴露遍历能力而不暴露存储方式。
