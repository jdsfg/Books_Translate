Carmen Ortiz 在 2025 年初接任 Currents 的工程管理职位。Currents 是一个 50 人的数据平台工程组织，分为 5 个团队，技术栈都是 Python/FastAPI/Postgres。她继承了一种前任称为 “GitHub Flow 但带 release 分支” 的分支模型——也就是说，它其实没有定义。有些团队从 `main` 切分支，有些从 `dev` 分支，有些从上一个 release tag。Hotfix 有时走 `main`，有时走 release 分支，有时两边都走。2025 年 1 月 14 日的发布包含了一个未经任何人审批的功能，因为该功能分支被悄悄 merge 进了一个没人监控的 release 分支。

Carmen 在第一个季度重写了分支信条。她选择了主干开发（trunk-based development）+ Conventional Commits + 语义化版本 + LaunchDarkly 特性开关（feature flags）+ 明确的 PR 审查 SLA。过渡花费了团队 6 周时间，而直接结果并不戏剧性。有趣的结果在接下来的 1 年里浮现：发布节奏显著加快，触发回滚的事故大幅下降，周末 on-call 告警从常态变成罕见。（Currents 的数字是示意性的；真正的收益*形态*——它们一起到来、跨越多个季度、在前提条件落地后显现——是真实采用主干开发的团队所报告的。）

本章讨论个人 Git 匠艺（第 3 章）如何扩展到团队 Git 匠艺。原子提交、bisect、interactive rebase 这些本地纪律在团队采用共享约定时会急剧复利；没有共享约定，即使个人实践再优秀，也无法超越个人而复利。


### 4.1 三种分支模型

2026 年工作工程团队里占主导的分支模型有三种。它们并非同样好，也并非同样坏。为团队选对模型需要诚实评估。


#### 主干开发（trunk-based development）

在主干开发中，所有工程师向唯一长期分支（通常是 `main`）提交，经常一天多次；功能工作通过特性开关（§4.4）隐藏，直到就绪。即使使用分支，也是短命的（少于 2 天）且小（少于 400 行）。该模型假设测试套件快速、可靠，并有小 PR 文化。

优点：最大集成速度；冲突很小，因为分支很小；CI 信号清晰，因为每个提交都在 `main` 上；bisect 干净，因为历史大致线性。

缺点：需要快速 CI（每个提交触发完整流水线）和高质量测试；任何不能立即上线的功能都需要特性开关；需要小 PR 文化，有些团队难以采纳。

这是 Carmen 为 Currents 做的选择，也是管理良好团队中平均交付时间（mean-time-to-ship）最短的选择。
