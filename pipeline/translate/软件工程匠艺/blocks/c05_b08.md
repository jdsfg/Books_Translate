#### 概念检查

**Q1.** 你的团队目前用 Git Flow，每周发布。你相信主干开发更合适。诚实应用 §4.1 的决策标准：什么时候你会推荐变更，什么时候会建议保持？

提示

§4.1 的决策表列出 6 个属性。逐条为你的团队打分。

**答：** 如果团队 CI 快速（完整套件 < 15 分钟）且可靠（`main` 上 > 95% 绿）、愿意普遍采用特性开关（且已有开关服务）、能把典型 PR 缩小到 400 行以下、产品是持续部署（非版本化可安装），则推荐主干开发。

如果产品是版本化可安装（移动应用、本地部署软件、库），同时有多个版本在生产环境运行；或 CI 薄弱，无法承受主干每个提交的流水线压力；或监管环境要求显式 release 分支（一些金融服务团队），则建议保持 Git Flow。

纯中间情况（每周发布的 SaaS 团队，CI 中等，抵制特性开关）是 GitHub Flow 的最佳候选，而不是两个极端之一。没有先投资 CI 和开关就给这团队选主干开发，会产生摩擦，团队会把摩擦归咎于主干开发，而原因其实是缺失的前提条件。

**Q2.** 比较 Conventional Commits 与自由格式提交信息。团队得到什么、失去什么？

提示

§4.2 的三项下游收益和两项失效模式。

**答：** 收益：可查询历史（`git log --grep=^feat`）、自动生成 changelog、通过 semantic-release 自动升号、降低写什么内容的认知负荷（格式提示作者）。损失：一些表达力（格式约束你写什么）、一些灵活性（部分是 feat 部分是 fix 的提交必须拆分或近似选 type）、一些采纳摩擦（团队得学习词汇表）。

对发布库或需要 changelog 的产品，取舍对多数团队有利。对仅内部服务、changelog 无关的场景，收益更小；此时格式主要是风格选择而非功能选择。多数 2026 团队仍然采用，因为它与工具链集成，而且工程师在不同代码库之间流动时，一致性有价值。

**Q3.** 一位队友为一个小的改动加了特性开关，并在当天就 100% 推出，然后把开关留在原地“以备将来使用”。这有什么问题？团队的开关生命周期本应阻止什么？

提示

§4.4 的开关腐烂问题。

**答：** 这个开关现在成了死代码：运行时条件永远走同一条分支。它增加成本（每个请求都评估开关，付出网络或缓存查询）并造成困惑（“关”分支不可达但仍存在于代码中，会误导未来读者）。数百个这样的开关多年累积后，代码库会变得不可读。
