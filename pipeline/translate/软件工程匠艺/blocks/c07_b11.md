#### 深入思考

**Q8.** 辩护或反驳：“2026 年，基于属性的测试应成为*默认*测试风格，基于示例的测试才是例外。” 有什么证据支持每一边？

**讨论：** 支持：属性覆盖比示例更多输入；AI 容易生成示例但难以生成属性，所以属性是人类的独特贡献；属性更抽象地记录函数契约，不易过拟合具体输入。证据：采用基于属性测试的团队报告，在他们应用该技术的模块中，生产环境边界情况 bug 显著减少。

反驳：示例更可读；示例记录典型用例的行为；示例更易写、易调试；很多函数没有干净属性（属性就是“算出正确答案”，这不算属性）；写 property generator 的前期投入高。证据：2026 年多数生产测试套件仍以示例为主，基于属性只是补充。

综合：属性适合所有能套用的地方（round-trip、不变量、代数定律、oracle 关系），示例适合所有能套用的地方（文档化行为、典型边界、过去 bug 的回归测试）。默认值应是*新模块两种都写*，由工程师判断哪种对特定函数更有价值。多数纯函数两者都写。深度命令式函数主要写示例。代数运算库主要写属性。

**Q9.** 变异测试是“测试的测试”——它暴露测试是否在测试。还有没有其他技术扮演这一角色？2026 年健康的“测试的测试”纪律长什么样？

**讨论：** 其他类似技术：

* **测试代码审查**（第 15 章）也能抓住变异测试抓的缺口，但更慢、更定性。两者互补。
* **生产事故复盘**：当 bug 上线时，问为什么没有测试抓住它。每个漏网的 bug 都是测试套件缺口的信号。加回归测试能抓住那个具体 case；复盘几个同类事故能发现系统性缺口。
* **覆盖缺口分析**：按 §5.2，未覆盖行就是缺口。变异测试取代覆盖率成为主要深度信号，但不替代覆盖率作为快速负面信号。
* **混沌工程**：在测试环境故意注入失败，测试生产代码（和测试套件）能否处理。这是变异测试在集成层面的类比。

2026 年健康纪律：覆盖率作为基本底线（每个 PR 不能降低覆盖率）；变异测试作为主要深度信号（夜间/每周全量，关键模块 PR 增量）；生产事故复盘作为滞后信号（每个上线的 bug 触发回归测试，更重要的是触发“缺口是否系统性”的问题）；混沌工程作为集成层面类比，用于测试套件无法充分演练失败模式的系统。四者一起产生“测试的测试”文化；缺少任何一项都会让某类缺口无人过问。
