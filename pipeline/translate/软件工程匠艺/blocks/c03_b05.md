#### 死条件（dead conditional）

谓词永远不能再为真的条件。通常是为已被回滚的功能、已完成的迁移，或已不存在的供应商引入的。分支还在，测试（如果有）也还在，而删除它是一项没人愿意费力的琐事（yak-shave）。

诊断：给谓词加一周的埋点观察；如果分支从未进入，它就是死的。经过一个生产周期后可以放心删除。


#### 承重注释（load-bearing comment）

一条警告不要做显而易见之事的注释，附带一个容易忘记的理由。例如：

    # DO NOT use a HashMap here — order matters for downstream consumers
    # (see incident-2023-09-14)
    ordered_events = []

这条注释是承重的，因为删除注释而不删除约束，会导致 incident-2023-09-14 复发。有些团队会为该约束加自动化测试；很多不会。注释是唯一的保护。请把它当作保护对待。


#### 迁移疤痕（migration scar）

一段曾经由两段代码合并而成的代码，现在带着两个祖先的痕迹。症状：一个函数接收两个同类型参数但各自验证逻辑不同；一个类有两条 `__init__` 路径；一个 Bash 脚本里的 `case` 语句覆盖“旧格式”和“新格式”，而三年前大家 supposedly 就已经不再用旧格式。

迁移疤痕在新读者看来常常像过度工程。它们通常不是过度工程；而是一次已完成迁移的表层，旧格式仍活在某人的备份里，或旧 API 仍被某个未记录的下游消费者调用。触碰时要小心。


#### 作者的担忧（author's worry）

一段代码做了比严格所需更多的事，带着精心设计的守卫、防御性 `null`、冗余验证。诊断问题：*原作者在担心什么？* 答案通常是真实的生产事故，或他们曾经被咬过的一类 bug。`git log` 通常会在 5 分钟内证实或证伪。

如果作者的担忧仍然有效，就保留代码。如果担忧不再有效（上游服务不再返回 `null`，边界已做验证，类型系统升级已消除该类 bug），防御性代码就成了死重，可以删除。关键是*检查*，而不是假设。
