#### 应用问题

**Q5.** 在代码库里找一个业务逻辑与 I/O 纠缠的模块。把它重构为六边形架构：定义 ports、抽核心、单独实现 adapter。报告重构前后测试套件速度。

提示

对 I/O 重型模块，测试速度提升常很 dramatic（10 倍或更多）。

**答：** 这是开放练习。常见结果：

* 对一个实质性模块，重构耗时 1–3 周。
* 模块测试套件运行时间下降 5–20 倍（集成测试被纯函数单元测试替代）。
* 测试数量*增加*，因为纯函数容易测试很多情况。
* 下季度 bug 率下降，因为单元测试更早捕获问题。

复利效应：第二个模块重构比第一个快，因为团队已内化模式，支撑基础设施（fake adapter、port 约定）已到位。

**Q6.** 识别代码库一个编排中的纯决策。把它抽成纯函数。用至少一个基于属性的测试测试它（第 6 章）。

提示

决策通常是 orchestrator 中间的多行条件判断。

**答：** 这是开放练习。典型发现：一个 orchestrator 通过多个条件判断和算术运算计算一个值；这些条件只依赖输入和少数常量。把计算抽成纯函数 `compute_<thing>(inputs) -> Decision`；orchestrator 调用它；orchestrator 更短更清晰。

对抽出的函数做基于属性的测试：通常是结构不变式（“decision 的 `total` 等于各商品价格乘数量之和”）或领域规则（“应用折扣规则的 decision 的 `discount_amount > 0`”）。纯函数上的属性测试以微秒运行，测试数百种输入组合。

教训：纯函数是任何代码库中最可测试的代码。从 orchestrator 中抽出它们是杠杆最高的重构。

**Q7.** 用 AI 智能体把一个纠缠模块重构为六边形 + FC/IS 形状。在提示里明确目标形状；审查智能体输出。它是否正确应用了形状？是否把 I/O 漏进核心？

提示

§14.6 的 CLAUDE.md 规定了约定；有它时，智能体输出更一致。

**答：** 这是开放练习。常见发现：

* 有清晰 CLAUDE.md 时，智能体能产出可接受的六边形重构，port 和 adapter 命名合适。
* 没有时，智能体的 ports 和 adapter 命名不一致（`IDatabase`、`DatabasePort`、`CustomerRepository`），核心可能有小 I/O 泄漏。
* 纯函数抽取常不完整；智能体抽出了明显决策，但把 I/O 邻近逻辑留在 orchestrator。人类审查发现剩余抽取。

教训：AI 是架构工作的乘数，但需要明确约定指导。CLAUDE.md 是杠杆；没有它，智能体默认会漂移向训练数据规范。
