### 4.6 Agent 提交 PR 的工作流

2026 年，agent 模式（Cursor agent、Claude Code、Devin、v0）越来越多地是实施者；人类越来越多地是审查者和指挥者。2025–2026 年形成的工作流：

  1. 人类写规格、失败测试或清晰的 ticket 描述。
  2. 智能体在分支上工作、提交、写测试、本地跑测试套件。
  3. 智能体按团队模板打开 PR。
  4. 人类审查 PR、要求修改或合并。
  5. 智能体通过 push 更多提交来回应审查评论。
  6. 人类满意后 PR 合并。

这个工作流颠倒了传统流程：人类不再是代码作者，而是审查者和最终决策者。影响深远：

* **审查技能成为瓶颈。** 一个工程师每天 shipping 10 个 agent-PR 的团队，需要能在质量不下降的情况下每天审查 10 个 PR 的审查者。这比听起来难（第 15 章）。
* **智能体身份很重要。** 智能体提交的 Git 作者应该可区分（例如名为 `claude-agent[bot]` 的服务账号），这样 `git blame` 能揭示某行是人类写的还是智能体写的。维护时这个信息很有价值。
* **`CLAUDE.md / AGENTS.md` 文件变得承重**（第 22 章）。智能体从这个文件学习代码库约定；没有它，智能体的 PR 会充满风格不一致（线索 C 谎言 #3）。
* **智能体的提交信息需要显式规范。** 没有指令时，智能体退化成通用样式；有指令（在 `CLAUDE.md` 中）时，智能体会匹配 Conventional Commits 和团队的作用域词汇。


#### 为 Currents 配置智能体

Carmen 在 Currents 的 `CLAUDE.md` 包括：

    # 提交约定
    Use Conventional Commits format.
    Allowed types: feat, fix, refactor, test, docs, chore, perf, ci.
    Allowed scopes: auth, billing, scoring, ingest, api, db, infra.

    # PR 约定
    Open one PR per atomic change.
    Target trunk; do not branch off feature branches.
    Use the PR template at .github/pull_request_template.md.
    Behind a feature flag if user-visible.

    # 测试
    Write tests in pytest. Use the existing fixtures in `tests/conftest.py`.
    Do not introduce new test frameworks.

    # 风格
    Match the surrounding file. Do not reformat existing code.

每次智能体会话开始时都会读这个文件。Currents 智能体的 PR 看起来和团队其他 PR 一样；没有这个文件就做不到。
