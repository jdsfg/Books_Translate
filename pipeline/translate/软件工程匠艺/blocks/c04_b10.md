Rebase 场景：你独自在功能分支上工作；你做了 8 个提交，其中 4 个是 WIP 或 fixup；自你切分支以来 `main` 前进了 12 个提交。开 PR 前，你 rebase 到 `main` 上，并用 interactive rebase 把 8 个提交整理成 3 个原子提交、打磨信息。审查者看到的是基于当前 `main` 的干净 3 提交 PR；bisect 能干净工作；历史不会被 merge 提交弄乱。

Merge 场景：你的团队维护一个 `release-2.7` 分支，已与 `main` 分叉两周；两边都打了 bug 修复。你把 `main` merge 进 `release-2.7` 以让 release 与最新修复对齐，产生一个 merge commit。这个 merge commit 诚实地记录了两条工作流曾并行，现在已调和；把 `release-2.7` rebase 到 `main` 上会重写其他工程师基于其上工作的哈希，破坏他们的环境。

**Q4.** 三个场景。对每个场景判断 `git reflog` 能否救你，如果能，给出命令序列：

(a) 40 分钟前你跑了 `git reset --hard HEAD~5` 丢弃一些实验性工作，然后发现丢弃的某个提交里其实有你想要的修复。此后没有跑过 `git gc`。

(b) 昨天你 force-push 了 `feature/x` 分支，覆盖了队友对同一分支的 force-push（你没意识到他们有工作）。他们的工作已不在远端，你的本地也从没有过。

(c) 一小时前你保存了一个改动很大的文件但还没 `git add`。然后你跑了 `git checkout main`，在工作树恢复中丢失了这些编辑。

提示

Reflog 是*你本地*的 HEAD 历史，不是远端备份，也不是工作区日志。

**答：**

(a) **能，reflog 能救你。** 跑 `git reflog`，找到 `reset --hard` 之前的 `HEAD@{N}`，然后 `git reset --hard HEAD@{N}`（或 cherry-pick 你想恢复的特定提交）。孤儿提交仍在对象库里；reflog 指向它们。`gc.reflogExpireUnreachable` 清理它们之前你有 30 天。

(b) **不能，你的 reflog 帮不上忙。** 你的 reflog 记录*你的* HEAD 历史。队友的提交从未进入你的本地仓库；你的 reflog 没有它们的记录。如果他们的本地仍有这些工作，他们可能从自己的 reflog 恢复；否则提交就丢了。（这就是 force-push 在共享分支上是要问团队、而不是问 reflog 的时刻。）

(c) **不能。** 未提交的工作区改动从未进入 Git 对象库。Reflog 追踪 HEAD 移动，不记录文件内容。编辑已丢失。（有些编辑器保留自己的撤销历史，可能有帮助；检查 VS Code 的本地历史、JetBrains 的本地历史。但 Git 本身帮不上。）

一般规则：reflog 拯救的是已经从分支引用不可达的*已提交*工作。它不拯救未提交工作，也不拯救别人的工作。
