#### 应用问题

**Q5.** 在代码库里找一处 Strategy 或 Adapter 能让设计更清晰的地方。实现它。比较前后可读性和可测试性。

提示

找有 5+ 分支的条件判断，或直接从业务逻辑调用 vendor SDK 的地方。

**答：** 这是开放练习。常见 Strategy 候选：折扣计算有 5 个客户等级分支。重构为策略注册表；每个等级的折扣逻辑在自己的类里；分派是字典查找。之前是一个函数 30 行条件判断；之后是一个分派类加五个小策略类，每个可独立测试。

常见 Adapter 候选：vendor SDK 调用（Stripe、Twilio、SendGrid）内联在业务逻辑中。把 SDK 包装成暴露应用接口的 adapter；用 adapter 调用替换内联调用。业务逻辑现在可在没有 SDK 的情况下测试；切换 vendor 只需改构造参数。

两种情况下前置成本都是真实的（更多文件、更多类）；回报在第二次及以后使用中显现。

**Q6.** 给代码库里一个函数加三个 Decorator：一个日志、一个重试、一个缓存。以不同顺序组合它们并观察行为。

提示

顺序重要：外层 decorator 看到的调用少于内层。

**答：** 这是开放练习。函数 `f` 上的三个 decorator：

* **缓存最外层，重试中间，日志最内层**：缓存命中不会触发重试或日志；未命中会重试并记录日志。这是通常生产组合。
* **日志最外层，重试中间，缓存最内层**：每次调用只记一次日志（可见性好）；成功时重试后缓存；缓存命中跳过下一次调用。
* **重试最外层，日志中间，缓存最内层**：重试会看到多条日志（每次尝试一条）和多次缓存查找。适合诊断重试行为。

这个练习教顺序敏感性：decorator 不可交换。团队应为生产使用约定标准顺序并文档化。

**Q7.** 用 AI 智能体把一段代码重构为某个模式（Strategy、Adapter 或 Observer）。审查结果。智能体选对模式了吗？应用得好吗？过度应用了吗？

提示

智能体的模式选择反映训练数据；2026 年 LLM 偏向过度应用。

**答：** 这是开放练习。常见发现：

* 智能体应用了模式，但引入了人类不会加的额外层（工厂、注册表、builder）。剥除多余。
* 智能体正确应用了模式，但类名泛化（`ConcreteStrategyA`、`ConcreteStrategyB`）。用领域术语重命名。
* 智能体应用了与请求不同的模式（例如 Observer 而不是 Strategy），因为它对问题的理解不同。讨论其理解；选择合适模式；重新应用。

教训：模式是词汇。智能体知道词汇，但没有具体代码库中一种模式比另一种更合适的上下文。人类的判断是区分因素。
