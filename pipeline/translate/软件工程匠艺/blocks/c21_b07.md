#### 概念检查

**Q1.** 两位工程师在同一个 bug-fix PR（修复日期解析函数的三行 bug）上工作。他们都以不同方式理解“童子军规则”，并提议增加相邻改进：

**工程师 A 的 PR**：三行 bug 修复，加同一函数内一个变量重命名（`d` → `parsed_date`）、删除同一文件里一条陈旧的 `// TODO 2022` 注释、从 25 行块中抽出 helper。三个 commit，修复外约 30 行。

**工程师 B 的 PR**：三行 bug 修复，加重构整个日期解析模块（拆成三个文件）、重命名另一个文件中一个不相关函数、为不相关函数加 14 个新测试、更新 README。十二个 commit，修复外约 600 行。

谁正确践行童子军规则？审查者在未来类似 PR 应应用什么*诊断*？

提示

大小和对齐，两者都要。诊断：这个改进是否需要自己的 PR summary 描述？

**答：**

**工程师 A 做得对。** 三个改进，每个都小（每个几分钟工作），每个都与实质性变更*对齐*（触碰同一函数或文件）。审查者评估 bug 修复时不会被分心；改进跨 PR 复利，但不拖慢本次 PR。

**工程师 B 是范围蔓延**，不是童子军。bug-fix PR 里 600 行“既然我们都在这”的工作有三个问题：

  1. 审查者必须先评估 600 行重构，才能评估 bug 修复。审查时间膨胀 10 倍。
  2. 重构本身值得自己的审查、自己的 PR 描述、如果是结构性变更还值得自己的 ADR。把它埋进 bug fix 意味着这些都没有。
  3. 如果重构引入回归，回退“bug 修复 PR”会同时回退两者。原子提交原则（第 3 章）瓦解，因为 PR 不再关于一个概念性变更。

**应应用的诊断**（童子军与范围蔓延的分界线）：*这个改进是否需要自己的 PR summary 描述？* 如果需要，就太大，不适合童子军——开独立 PR。如果不需要（重命名、死注释、小 helper），就属于本次 PR。

第二个诊断：童子军改进与实质性变更*对齐*（同一函数、同一文件、同一概念区域）。不相关文件或不相关函数中的改进是范围蔓延；放到别处。

**审查者对工程师 B PR 的正确回应**：“请拆分。三行 bug 修复作为 PR 1（今天）；日期解析重构作为 PR 2（本周，带自己的描述）；不相关重命名和测试作为 PR 3（随便什么时候）。” 工程师 B 可能抗拒（感觉“额外工作”）；纪律是坚持。团队审查产能是瓶颈（第 15 章）；拆分保留产能。

**Q2.** 对比绞杀者无花果模式与大型重写替代方案。什么让绞杀者无花果更安全？

提示

各自的风险画像。

**答：** 绞杀者无花果分块迁移；旧系统全程作为安全网；迁移期间团队持续发布功能；每一块都可回退。大型重写构建完整新系统然后一次性切换；切换时新系统未经验证；项目承诺长期不发布；切换后旧系统不可恢复。
