Carmen Ortiz 的 Currents 工程团队跨三个时区（旧金山、柏林、班加罗尔）。同步沟通困难：会议要么排除一个时区，要么在某人睡觉时开。到 2025 年，团队已确立深度异步工作流：PR 作为工作单元，书面沟通为默认，同步沟通只保留在它回本的情况下。结果是一个尽管分布广泛却能稳定节奏交付的团队。

2026 年，AI 智能体作为第三方加入工作流。智能体与工程师结对解决难题；在 tests-as-spec 下实现功能；与人类一起审查 PR。团队的异步优先纪律自然容纳了这一点：AI 只是另一个通过书面产物（PR、评论、智能体转录）沟通的协作者。但智能体与人类、结对与群体、异步与同步之间的边界变得需要明确表述。

本章讲围绕 PR 的团队级工作流：如何结构化 PR 供审查、如何默认异步、何时同步工程回本、以及 2026 年 AI 在场时结对/群体编程如何运作。


### 16.1 PR 作为工作单元

第 4 章介绍了 PR 作为工作单元。本章在团队层面深化这一纪律。


#### PR 的生命周期

PR 经历若干状态：

  1. **起草**：作者正在写 PR；CI 可能尚未通过；审查者不被期待。
  2. **待审查**：CI 通过，描述完整，已指定审查者。
  3. **审查中**：审查者阅读并评论。
  4. **作者响应**：作者处理评论。
  5. **复阅**：审查者确认变更。
  6. **已批准**：可合并。
  7. **已合并**。

每个状态有自己的 SLA 和信号。作者应显式标记草稿（GitHub 的 “Draft” 功能，或 `WIP:` 前缀）；审查者应在团队 SLA 内响应待审查 PR；作者应在团队 SLA 内响应评论。没有这些信号，PR 会在模糊状态里漂移；有了它们，生命周期可预测。


#### 再说 PR 大小

第 4 章把 200–400 行作为实质性变更的甜点。2026 年支持这一点的数据仍然一致：超过 600–800 行，审查质量显著下降；少于 50–100 行，审查开销不成比例（每个 PR 都有上下文切换的基线成本）。

实践中，合适大小取决于变更形状：

* **Bug 修复**：通常小（10–100 行）；审查者可深度聚焦具体变更。
* **新功能**：中等（200–400 行）；审查者能在脑中容纳该功能。
* **重构**：中到大（300–600 行）；测试强时，审查者可验证行为保持。
* **文档**：可变；小文档容易，大文档需要结构性审查。
* **AI 生成 PR**：应与人类 PR 一样拆分；AI 默认可能产生更大的 PR，团队在提交前应调整大小。

纪律是开 PR 前问：*审查者能一次性仔细审完这个吗？* 如果不能，拆分。
