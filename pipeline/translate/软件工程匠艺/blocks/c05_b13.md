### 本章总结

团队 Git 匠艺是个人 Git 匠艺（第 3 章）的放大器。正确的分支模型（§4.1）取决于产品类型和团队上下文；对持续交付的 SaaS 团队，主干开发加特性开关越来越是默认，但 Git Flow 仍适合版本化产品，GitHub Flow 仍是小团队的合理默认。Conventional Commits（§4.2）让提交历史可查询，并启用自动生成 changelog 和自动升号；语义化版本（§4.3）对库和 CLI 是正确契约，对 SaaS 则不一定。特性开关（§4.4）把部署代码与发布功能解耦，让主干开发在高节奏下工作；生命周期纪律防止开关腐烂。PR 作为工作单元（§4.5）是审查和合并发生的粒度；SLA 纪律是团队文化的一部分，不是项目管理强加。Agent-PR 工作流（§4.6）颠倒传统流程：人类审查，智能体实施；`CLAUDE.md / AGENTS.md` 文件是对齐智能体产出与团队约定的承重产物。

Trellis 的过渡（§4.7）展示了模型变更跨越多个季度的形态：先前提条件，再迁移，再回顾。没有前提条件就强加正确模型，比有前提条件的错误模型更糟糕。

第三部分（第 5–8 章）迈向下一步：把测试当作纪律。主干开发假设快速、可靠的测试；特性开关假设两条代码路径都被测试；agent-PR 模式假设审查者能信任智能体的测试。没有测试纪律，团队 Git 信条就会崩塌。第 5 章将诚实评估测试金字塔：覆盖率作为指标、快照测试的窄适用、以及 2026 年 AI 生成测试通过却不测试的现实。


#### 三条要点

  1. **先采纳特性开关生命周期，再采纳主干开发。** 没有 `kill_by_date` 和移除流程的开关，腐烂代码库的速度比加快交付还快。生命周期优先；主干开发其次。
  2. **为团队设定 PR 规模目标，在 600 行处设软性警告。** 不是硬性阻塞。当警告自动出现时，审查者和作者都会调整行为；合并后缺陷率会在一个季度内下降。
  3. **把审查 SLA 合规当作工程指标，而非经理指标。** 及时审查的工程师在促成团队速度；从不审查的工程师在掐住它。让它成为团队理解自身绩效的一部分。
