#### ADR 示例

    # ADR-003: Trellis 采用 Trunk-Based Development

    Status: Accepted (2025-02-15)

    ## Context
    Trellis 已使用 GitHub Flow 六年。随着团队增长到 200 名工程师，分支生命周期越来越长；长命分支冲突增加；PR 分支 CI 慢；发布协调摩擦。

    我们考虑过：继续 GitHub Flow、迁移到 Git Flow、迁移到 Trunk-Based Development。

    ## Decision
    采用 Trunk-Based Development。所有工作通过短命分支（< 2 天）直接合并到 main。未完工功能用功能开关（LaunchDarkly）隐藏。

    ## Consequences
    - 更快的集成；更小的冲突。
    - 需要快速 CI（目标：完整套件 < 15 分钟）。
    - 任何不能立即发布的工作都需要功能开关。
    - 需要文化转向小 PR（目标：< 400 行）。
    - 初始成本：6 周迁移工作。

    ## Alternatives considered
    - 继续 GitHub Flow：被拒绝，因为团队壮大后现有痛点在加剧。
    - Git Flow：被拒绝，因为它对持续部署的 SaaS 产品仪式更重。

ADR 三分钟可读完。它记录了上下文、决策、后果和备选方案。未来工程师读到的不仅是*什么*，还有*为什么*。能留存的是“为什么”。


#### ADR 生命周期

ADR 一旦被接受就*不可变*。如果团队想改变决策，要写新的 ADR 取代旧的；旧的标记为 “Superseded by ADR-N”。决策历史就是代码库推理的历史。

这条纪律很重要。可变的 ADR 会丢失过去决策的推理；不可变的 ADR 保留它。未来工程师能看到演进：ADR-003 让 trunk-based 成为决策；2028 年的 ADR-027 可能出于某种原因取代它；ADR-027 引用 ADR-003 并解释什么变了。


### 17.4 RFC

RFC 是 ADR 的提案阶段。格式类似；状态是 “Proposed” 而非 “Accepted”。RFC 征求意见；团队讨论；做出决策。


#### RFC vs 直接 ADR

适合 RFC：

* 决策*不确定*，需要输入。
* 决策影响多个团队或利益相关者。
* 决策日后可能被质疑；记录讨论有价值。

适合直接 ADR（无 RFC 阶段）：

* 决策*明确*，团队内部已达成共识。
* 决策只影响作者所在团队。
* 讨论直截了当。

实践中，许多团队对重大决策用 RFC 阶段，小决策跳过。阈值靠判断；Helix 对影响超过一个团队的决策用 RFC；更小的决策直接走 ADR。


#### RFC 讨论格式

RFC 文档是锚点；评论在其内联进行（文档内、GitHub PR 评论、文档评论 thread）。讨论是异步的（第 16 章）；推进的阈值是“参与者没有未解决的 blocker”。

讨论收敛后，RFC 要么：

* 被接受：状态改为 Accepted，文档移到 `adrs/`，开始实现。
* 被修改并重新 circulated：发生实质性变更后进入新一轮评论。
* 被拒绝：状态改为 Rejected 并附拒绝说明；归档供未来参考。
