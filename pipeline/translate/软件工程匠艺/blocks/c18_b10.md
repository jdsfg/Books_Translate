这就是 runbook 必须：具体（不是“调查根因”而是“运行这个确切命令”）、可操作（不是“考虑是否升级”而是“15 分钟未恢复则 page DBA on-call”）、并经过测试（团队定期模拟事故以验证 runbook 有效）。

其他文档有更宽容的读者：README 读者是新鲜且好奇的；ADR 读者是深思熟虑且有时间的。Runbook 读者两者都没有。


#### 应用问题

**Q5.** 审计你代码库的文档。对四种类型各报告：你有它们吗？它们被维护吗？缺口是什么？

提示

缺口就是行动项。

**答：** 这是开放练习。常见发现：

* README 存在但过时；设置步骤不再工作。
* 少数重大决策有 ADR，但大多数架构决策无文档。
* RFC 不是常规实践；设计提案发生在聊天里并消失。
* Runbook 对最关键场景存在，但未覆盖所有告警。

缺口暗示行动项：下次触碰仓库时更新 README；每个 sprint 为最重要的无文档决策写一个 ADR；下一次重大设计采用 RFC 实践；逐个告警扩展 runbook 覆盖。工作是增量式的；目标是六个月稳步进展。

**Q6.** 为团队上季度做的一个决策写一份 ADR。使用 Nygard 格式。包含 “Why”、“Alternatives considered” 和 “Consequences”。

提示

“Alternatives considered” 部分对未来读者往往最有信息价值。

**答：** 这是开放练习。该练习在两方面产生价值：(a) ADR 本身保留决策推理；(b) 写它的过程会暴露原本不明显的决策部分。工程师经常在写 ADR 时发现，“Alternatives considered” 部分很难填，因为真实的备选方案当时没有被明确说出来。

教训：事后写 ADR 会揭示原始决策过程中的缺口。下次可以在决策做出前解决这些缺口。

**Q7.** 为你代码库的真实生产场景写一份 runbook。使用 §17.5 的模板。让队友审查；让他们想象凌晨 2 点 on-call 并按 runbook 执行。它在哪里崩溃？

提示

崩溃点就是 runbook 的 bug。

**答：** 这是开放练习。常见崩溃点：

* Runbook 假设读者知道该用什么工具；应指定确切命令。
* Runbook 的诊断步骤需要 on-call 工程师可能没有的知识；应 inline 提供足够上下文。
* Runbook 的缓解步骤有副作用，但 runbook 没提到；应加上警告。
* Runbook 的升级路径不清楚；应指定要 page 的确切人员或 schedule。

审查-迭代周期是 runbook 纪律的一部分。未被作者以外的人审查过的 runbook 是未测试的；在模拟压力下测试能揭示缺口。
