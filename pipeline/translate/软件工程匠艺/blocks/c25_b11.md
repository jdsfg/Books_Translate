    # 给 AI 智能体的项目约定
    
    ## 代码库导航
    <项目是什么。关键文件夹在哪。如何运行测试。>
    
    ## Commit 约定
    使用 Conventional Commits。
    允许类型：feat, fix, refactor, test, docs, chore, perf, ci。
    允许作用域：<枚举>。
    主题行 ≤ 50 字符。正文在 72 字符处换行。
    
    ## PR 约定
    每个 PR 一个原子改动。目标 `main`。使用 `.github/pull_request_template.md` 的模板。
    若用户可见，则在功能标志后。标志名格式 `<scope>_<feature>_<verb>`。
    
    ## 命名约定
    使用领域术语（列出几个关键：例如 `tenant` 而不是 `customer`，`renewal` 而不是 `recurring_purchase`）。
    函数名是动词短语。谓词以 `is_` 或 `has_` 开头，用肯定意义。
    禁止泛化后缀：Manager、Handler、Processor、Engine、Service（改用具体角色名词）。
    
    ## 测试约定
    框架：<pytest / vitest / jest / 等>。
    fixture 放在 <fixtures path>；不要引入新测试框架。
    对有状态依赖优先用 fake 而不是 mock。在 `tests/fakes/` 中放内存实现。
    覆盖 happy path、至少一条错误路径、至少一个边界情况。
    
    ## 模式偏好
    类没有状态且只有一个方法时，优先用普通函数。
    只有一个实现时，优先用具体类型而不是接口。
    优先构造器注入（DI）而不是 Singleton。
    语言支持时，优先模式匹配而不是 Visitor。
    第二个具体 case 出现时才引入抽象。
    
    ## 应避免的反模式
    - 不要引入新的 HTTP client；代码库使用 <现有 client>。
    - 不要引入 Singleton；使用现有 DI 容器。
    - 不要 catch 基 Exception 类型；只 catch 具体异常。
    - 模式税（Factory Factory、Provider Factory、单实现接口）禁止。
    
    ## 架构形状
    我们使用六边形架构（或适用的架构）：
    - 业务逻辑在 `src/core/`。
    - 端口（Protocols）定义在 `src/core/ports/`。
    - 适配器在 `src/adapters/<system>/`。
    - 决策逻辑应该是 `src/core/decisions/` 中的纯函数。
    
    ## 先看哪里
    - 测试在 <tests path>。
    - 领域模型在 <models path>。
    - 入口在 <entry points path>。
