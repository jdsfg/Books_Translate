### 13.2 Visitor：被 sum type 与模式匹配取代

Visitor 模式让你在不修改类的前提下为类层次添加新操作。模式的工作方式是每个类接受一个 visitor 对象并回调 visitor 中针对自身类型的方法：

    # 传统 Visitor（2026 年不要用）
    class Visitor:
        def visit_circle(self, c): pass
        def visit_square(self, s): pass

    class Shape:
        def accept(self, visitor): pass

    class Circle(Shape):
        def accept(self, visitor): return visitor.visit_circle(self)

    class Square(Shape):
        def accept(self, visitor): return visitor.visit_square(self)

    class AreaCalculator(Visitor):
        def visit_circle(self, c): return 3.14159 * c.radius ** 2
        def visit_square(self, s): return s.side ** 2

    class PerimeterCalculator(Visitor):
        def visit_circle(self, c): return 2 * 3.14159 * c.radius
        def visit_square(self, s): return 4 * s.side

原始问题：在 1995 年的 Java 里，新增操作（如周长计算）需要修改每个 shape 类。Visitor 避免了这一点；代价是笨拙的双分派 boilerplate。


#### Visitor 为何衰老

* **Boilerplate 显著**：每个操作都需要一个 visitor 类，且每个 shape 一个方法；每个 shape 还需要 accept 方法。模式比简单替代方案产生更多代码。
* **新增 shape 现在需要修改每个 visitor**，在另一个方向上破坏了开闭原则。该模式偏爱添加操作但惩罚添加 shape；是否适合取决于代码库哪个方向更常见。
* **模式难读**：双分派间接（对象 accept visitor，visitor 访问对象）对不熟悉该模式的读者不直观。


#### 替代它的是什么：sum type 与模式匹配

2026 年，有 sum type 的语言（Rust、OCaml、Haskell、Scala）或有模式匹配的语言（Python 3.10+、TypeScript 有限支持、C# `switch` 表达式）让替代方案简单得多：

    from dataclasses import dataclass
    from typing import Union
    import math

    @dataclass
    class Circle:
        radius: float

    @dataclass
    class Square:
        side: float

    Shape = Union[Circle, Square]

    def area(shape: Shape) -> float:
        match shape:
            case Circle(radius=r): return math.pi * r ** 2
            case Square(side=s): return s ** 2

    def perimeter(shape: Shape) -> float:
        match shape:
            case Circle(radius=r): return 2 * math.pi * r
            case Square(side=s): return 4 * s

收益：没有 accept 方法，没有 visitor 类，没有双分派。新增操作只需加一个函数；新增 shape 需要更新每个函数（静态类型语言中类型系统会标出缺失分支）。权衡显式，代码更短。


#### 什么时候（罕见）Visitor 仍合适

在没有模式匹配的语言里（旧 Java、C++17 之前、无 TypeScript 的普通 JS），Visitor 仍是标准方案。在必须支持深层类层次结构的多态分派代码库中，Visitor 仍可能是正确形状。两种情况都在减少；语言生态已经迁移。
