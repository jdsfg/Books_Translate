**Q5.** 取你代码库中的一个函数，用断言强度启发式为它写三个测试：第一个故意弱（覆盖率填充），第二个中等强度，第三个强。解释每个能抓住什么 bug。

提示

进阶从“执行了这行”到“验证具体输出”再到“验证跨输入范围的行为”。

**答：** 假设函数是 `def round_to_cents(amount: Decimal) -> Decimal: return amount.quantize(Decimal('0.01'))`。

弱测试（什么都抓不住）：`round_to_cents(Decimal('1.234'))` 无断言。覆盖率上升；bug 不被发现。

中等测试（抓住算法回归）：`assert round_to_cents(Decimal('1.234')) == Decimal('1.23')`。能抓住从四舍五入变成截断的变化。遗漏银行家舍入的微妙。

强测试（抓住真实 bug 类别）：参数化测试，用例 `(1.234, 1.23), (1.235, 1.24), (1.245, 1.24), (1.255, 1.26), (-1.235, -1.24)`。能抓住算法回归、边界上银行家舍入与总是进位的区别、符号处理 bug。这些用例是了解舍入代码真实 bug 长什么样后挑选的；这就是匠艺。

这个进阶说明强测试未必更长；它更*有针对性*。用例被选中以区分合理实现。

**Q6.** 审计你团队最近一个冲刺的 PR。对每个加测试的 PR，统计：(a) 新增测试总数，(b) 与现有测试明显重复的测试数，(c) 断言强度低于中等的测试数。报告比例。如果比例令人担忧，团队的下一步是什么？

提示

这是对真实样本回溯应用 §5.4 工作流。

**答：** 这是开放练习，答案取决于代码库。常见发现模式：10–30% 的 AI 生成测试是重复或近重复；20–40% 断言强度弱。如果比例这么高，团队下一步：(a) 下个冲刺引入变异测试，获得量化指标；(b) 更新 `CLAUDE.md / AGENTS.md`，指定团队测试写作约定（不要重复、强断言、arrange-act-assert 结构）；(c) 代码审查中明确点名重复和弱测试；(d) 考虑对 PR 测试数量设软上限（soft cap），以抑制数量重于质量。

时间趋势，而非快照，才是指标：随着团队采纳这些纪律，比例是否在改善？如果是，保持航向。如果不是，下一步干预是一次团队范围的结对审查，工程师互相审查最近的 AI 辅助测试 PR，讨论哪些被保留、哪些被丢弃；这能建立共享判断。
