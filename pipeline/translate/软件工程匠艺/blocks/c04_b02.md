#### 原子提交在实践中的感觉

实践中，这项纪律起初不舒服，因为它与多数工程师的工作方式冲突。典型会话是：打开 IDE，开始改文件，思路带到哪跟到哪，最后用模糊信息提交。原子提交的替代是：改文件、早提交、再改文件、再提交，推送前可能用 interactive rebase 修改或拆分提交。

心智转变是把提交当作一个*发布单元*。提交前问：*这个提交对一个读历史的人来说合理吗？* 如果答案是否定的，你还没资格提交。你可能需要拆分（用 `git add -p`）、squash（用 `git rebase -i`）或重写信息。

一个 Trellis 风格的、能自然产生原子提交的工作流：

    # 开始
    git checkout -b extract-permission-type

    # 改动 1：提取类型
    vim src/auth/types.ts
    git add -p src/auth/types.ts  # 只把本次提交的改动逐块 staging
    git diff --cached  # 审查 staged 内容
    git commit -m "Extract Permission type from User model

    Permission was an inline union in User; lifting it makes it
    reusable by the upcoming PermissionService and shrinks User
    to its domain-essential fields. No behavior change."

    # 改动 2：构建使用新类型的服务
    vim src/auth/permission-service.ts
    git add src/auth/permission-service.ts
    git commit -m "Add PermissionService with read-only methods

    First slice: read methods only. Write methods land in a separate
    PR. The service is constructor-injected so AccessGuard can
    substitute a fake in tests."

    # 改动 3：接入
    vim src/auth/access-guard.ts src/auth/__tests__/access-guard.test.ts
    git add src/auth/access-guard.ts src/auth/__tests__/access-guard.test.ts
    git commit -m "Wire PermissionService into AccessGuard

    AccessGuard now takes a PermissionService in its constructor.
    Tests updated to inject a fake. No production caller changes;
    the service is provided by the existing DI container."

3 个提交，3 个概念，3 次审查。明天如果 `AccessGuard` 出 bug，bisect 会落到提交 3，表面只有 80 行，而不是 800。


#### 常见误解

一个常见误解是：“原子提交让我变慢。” 错误在于把打字速度与交付速度混为一谈。原子提交可能给一次典型功能会话增加 10 分钟。但下次 bisect、代码审查、不可避免的回退时会省下小时。第一次队友需要 bisect 你的历史时，投资就收回了。两次之后，这项纪律能覆盖一整年。

第二个常见误解是：“我推送前再整理就行。” 这有时行得通，但它要求你在*失去*产生这些概念拆分的认知上下文之后，还记得概念拆分。多数工程师尝试事后整理时，最后得到两个提交：“WIP”和“more WIP”。边走边提交才是产生原子提交的唯一可靠方式。
