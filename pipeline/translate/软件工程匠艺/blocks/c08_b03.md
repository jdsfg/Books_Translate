#### 定义：Repository

Repository 是一个对象，它在有限接口（通常 `find`、`save`、`delete` 和少量查询）后抽象领域实体的存储。应用代码依赖 Repository 接口，而不是具体存储技术。Repository 可以替换：生产用 SQL 实现，测试用内存实现。

直白地说：Repository 是*这个实体如何存储*的一站式定义，带有类型化接口供应用其他部分调用。业务逻辑不直接访问数据库；一切都走 Repository。


#### 一个完整示例

    from typing import Protocol, Optional

    class CustomerRepository(Protocol):
        def find(self, customer_id: str) -> Optional[Customer]: ...
        def save(self, customer: Customer) -> None: ...
        def find_by_region(self, region: str) -> list[Customer]: ...

    class InMemoryCustomerRepository:
        def __init__(self): self._customers = {}
        def find(self, customer_id):
            return self._customers.get(customer_id)
        def save(self, customer):
            self._customers[customer.id] = customer
        def find_by_region(self, region):
            return [c for c in self._customers.values() if c.region == region]

`OrderService` 的测试用 `InMemoryCustomerRepository` 构造。测试不碰数据库。测试不编码 SQL 查询。重构 SQL 实现不会破坏任何测试。`OrderService` 的重构由真实 Customer 存储行为验证，而不是由可能已偏离现实的 `Mock()` 规格验证。


#### 为什么不用 ORM 直接当 Repository

ORM（SQLAlchemy、Drizzle、Prisma、Diesel）提供面向对象的数据库接口。于是有人会说 ORM *就是* Repository。这种说法有道理；很多小团队跳过显式 Repository 层，直接从业务逻辑调用 ORM。

即使有 ORM，显式 Repository 仍有价值：

* **测试替换**：写内存或简化版 Repository 实现比写完整 ORM 替代品容易。
* **接口稳定性**：业务逻辑依赖 Repository 方法，而不是 ORM 细节。从一种 ORM 迁移到另一种是 Repository 实现替换，不是业务逻辑重写。
* **领域语言**：Repository 方法用领域语言命名（`find_by_region`、`find_active_subscribers`），而不是 ORM 语言（`session.query(Customer).filter_by(...)`）。业务逻辑读起来就是业务逻辑。

小项目用 ORM-as-Repository 可以。预计存活超过两年的项目，显式 Repository 层通常值得这笔开销。
