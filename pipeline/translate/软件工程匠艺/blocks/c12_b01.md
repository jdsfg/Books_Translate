Trellis 单体仓库的 billing 子系统写于 2018 年，对接当时版本的 Stripe API，此后该 API 已弃用三次。到 2025 年，billing 代码成了一团兼容性垫片：三个历史 API 版本各一个 `if/else`、三种不同的 webhook 签名验证器、四种不同的金额格式化方式。每一层的作者都已离开 Trellis。代码能跑，但每次与 billing 相关的改动都要花数周做小心翼翼的考古。

2025 年初，Asher 提出一项为期六个月的重构：用针对当前 Stripe API 的干净实现替换 billing 子系统。标准反对意见是：“我们不能六个月不出活。” Asher 的对策是并行路径策略：新子系统与旧子系统并行构建，同时运行，比较输出，并在功能开关后逐步迁移流量。团队持续交付；旧子系统是安全网；新子系统在成为主路径前逐步建立信心。

到 2025 年底，迁移完成。旧代码路径被删除。六个月里未发生客户可见的事故。团队 billing 相关改动的平均交付时间从两周降到两天。本章讲的就是这种模式：大到不适合第 10 章测试-重构循环的多月重构，以及让它可行的技术。


### 11.1 何时六个月重构值得

不是所有遗留子系统都需要六个月重构。工作昂贵、纪律严格、团队带宽有限。决定投入的标准：


#### 重构值得的情况：

* **子系统频繁被改。** 多个团队每天触碰的子系统会通过每次改动减少摩擦而快速回本。
* **累积债务正在显著拖慢速度。** 如果该子系统的交付前置时间明显高于别处，且差距可追溯到子系统结构，重构值得。
* **当前结构阻止即将到来的变更。** 计划中的迁移、新功能或监管要求无法在现有结构内实现。
* **原始假设已经消失。** 世界变了；代码还记得旧世界。2018 年 Stripe API v2 是正确选择；2025 年不是。


#### 重构不值得的情况：

* **子系统很少被改。** 重构没人碰的代码是无的放矢。
* **团队没有带宽。** 六个月重构加上没有余量的日程会产生摩擦、冲突和烂尾。
* **替换架构不清晰。** 没有明确目标，重构就是探索性的；六个月探索性重构通常会失败。
* **中途放弃风险高。** 之前放弃过大型重构的团队不应再启动一个；他们需要更小的模式（第 20 章的童子军规则或绞杀者模式）。

Asher 的 billing 重构满足全部四个“值得”标准；团队分配了带宽；目标架构清晰（当前 Stripe API、更少的兼容层）。这个决定可辩护。
