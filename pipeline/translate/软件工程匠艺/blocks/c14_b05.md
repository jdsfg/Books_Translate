#### 替代它的是什么：直接调用构造器

2026 年的纪律是：在灵活性被真实第二个案例*证明*之前，避免构造抽象层。在此之前，直接调用构造器或用一个简单工厂函数。如果出现第二个案例，引入一个工厂；如果出现第三个不同对象族的案例，再考虑 Abstract Factory。提前加 Factory Factory 是失效模式。

    # 反模式
    class CustomerRepositoryFactoryProvider:
        def get_factory(self, env):
            if env == 'production':
                return SqlCustomerRepositoryFactory()
            else:
                return InMemoryCustomerRepositoryFactory()

    class SqlCustomerRepositoryFactory:
        def create(self, db_pool):
            return SqlCustomerRepository(db_pool)

    class InMemoryCustomerRepositoryFactory:
        def create(self):
            return InMemoryCustomerRepository()

    # 应用
    provider = CustomerRepositoryFactoryProvider()
    factory = provider.get_factory(os.environ['ENV'])
    repo = factory.create(db_pool) if hasattr(factory, 'create') else factory.create()

    # 2026 年替代
    def make_customer_repository(env='production', db_pool=None):
        if env == 'production':
            return SqlCustomerRepository(db_pool)
        return InMemoryCustomerRepository()

    # 应用
    repo = make_customer_repository(env=os.environ['ENV'], db_pool=db_pool)

2026 年版本是一个带一个 if 的函数，做了原来三层类层次同样的事。新增第三个后端只需加一个分支；没有工厂层次需要更新。


#### 模式税的框架

我们称之为*模式税*：为假设的灵活性提前应用模式所带来的开销。随着代码库老化，税会累积；每次导航、每次入职、每次重构都要付。正确纪律是拒绝提前交税；让模式从真实第二案例中浮现，而不是从预期中。

这是线索 C 谎言 #2（过度抽象）的具体化。2026 年 LLM 有时会提议模式税结构，因为训练数据里有很多教程以完整仪式演示 Abstract Factory。纪律是识别反模式并拒绝。


### 13.4 其他值得作为历史了解的模式

一些已失宠的模式小清单：


#### Template Method

GoF 模式：基类定义算法骨架，抽象方法由子类覆盖。现代替代：用策略函数或 hook 做组合。基于继承的 Template Method 脆弱（子类与基类算法紧耦合）；组合替代更灵活。


#### Memento

捕获和恢复对象状态的模式。2026 年通常由序列化（JSON、MessagePack、Protocol Buffers）或事件溯源（第 17 章会涉及）处理。显式 Memento 对象类很少需要。


#### Chain of Responsibility

请求穿过一系列处理器，每个决定处理或继续传递。现代替代：middleware（本质上是第 12 章的 Decorator 模式）或简单列表遍历。显式 Chain 类很少需要；middleware 模式更灵活、更易懂。
