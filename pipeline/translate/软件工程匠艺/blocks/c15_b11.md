#### 概念检查

**Q1.** 一个团队第一次应用六边形架构，为 pricing 服务的 port 边界画了以下条目。对每个条目判断：它是 driver port、driven port，还是都不是？

(a) `POST /api/charge` HTTP 路由处理器。(b) `CustomerRepository.find(customer_id)`；SQL 实现。(c) `StripeChargeAdapter.charge(amount, currency, token)`。(d) 每晚运行 `recompute_pricing_table()` 覆盖所有客户的定时任务。(e) 事件总线消费者响应 `customer.updated` 事件刷新缓存。(f) 纯函数 `compute_discount(customer, order, rules) -> Decimal`。

提示

Driver ports = 外部如何*进入*核心。Driven ports = 核心如何*作用于*外部。

**答：**

(a) **Driver port**；HTTP 路由是外部调用方进入核心的方式。handler 把 HTTP 请求翻译为核心方法调用；adapter 是路由/序列化层。

(b) **Driven port**；核心向 Repository 请求数据；SQL adapter 实现该请求。核心不知道 SQL；Repository 抽象持久化。

(c) **Driven port**；核心请求收款；Stripe adapter 把请求翻译成 vendor API。核心不知道 Stripe；adapter 抽象 vendor。

(d) **Driver port**；定时任务是时间（一个“外部系统”）驱动核心的方式。cron runner 是 adapter；它知道调度和时间，核心不知道。

(e) **Driver port**；事件消费者是外部事件驱动核心的方式。总线消费者是把 `customer.updated` 事件翻译为核心方法调用的 adapter。

(f) **都不是**；核心内部的纯函数就是核心。ports 是核心与外部之间的*边界*。核心内部使用的纯辅助函数不在边界上；它没有 adapter；它只是函数式核心（§14.3）里的代码。

一般规则：ports 在边界。driver ports 回答“外部怎么进来？”driven ports 回答“核心怎么伸出去？”中间纯代码不是 port，是核心。区分重要，因为核心测试连接 fake driver 输入（直接调用方法）和 fake driven 输出（内存 adapter）；核心内部纯函数根本不需要测试 fake。

**Q2.** 一位队友把关键 pricing 函数重构为所有输入都作为参数传入（好！），但函数仍内部调用一次 `datetime.now()` 来检查促销规则当前是否生效。他们说：“它没有做 I/O。六边形框架已满足；没有 port 调用。你为什么还要我注入 clock？” 请论证为什么注入 clock（让函数完全纯）值得多一个小参数。把你的论证与*只有*改变后才能写的一个具体基于属性的测试联系起来。

提示

基于属性的测试要求确定性的函数。`datetime.now()` 让函数非确定性。

**答：** 队友半对：确实没有 I/O。但“没有 I/O”不等于“纯”。读取 `datetime.now()` 的函数是*非确定性*的：给定同样的 `customer` 和 `rules` 参数，结果因调用时间而异。周二和周三结果不同；促销期间与促销结束后结果不同。
