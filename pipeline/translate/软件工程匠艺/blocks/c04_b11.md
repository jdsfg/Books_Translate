#### 应用问题

**Q5.** 取你最近合并的一个 PR（或用下面的合成 PR）。检查它的提交历史。它能否拆成更原子的提交？提交信息能否重写以更好说明 why？写出一个能改善历史的 `git rebase -i` 计划。

合成 PR：一个名为 “Add user permissions feature” 的单一提交，包含：一个新的 `Permission` 类型、一个带读写方法的 `PermissionService` 类、修改 `AccessGuard` 以消费该服务、修改三个已有路由以强制执行权限、一个无关文件里的注释 typo 修复，以及 23 个新测试。

提示

寻找可以独立审查和回退的概念性改动。

**答：** 一个合理的拆分：

    pick a1b2c3d Extract Permission type into src/auth/types.ts
    pick d4e5f6a Add PermissionService (read methods only)
    pick b7c8d9e Add PermissionService write methods
    pick c1d2e3f Inject PermissionService into AccessGuard
    pick f4a5b6c Enforce permissions in /api/leads
    pick g7h8i9j Enforce permissions in /api/accounts
    pick j0k1l2m Enforce permissions in /api/users
    drop k0l1m2n   # 无关的 typo 修复应属于单独的单提交 PR

8 个概念改动（或 7 个，去掉 typo）。每个都可独立审查、bisect 和回退。每个信息说明改了什么、为什么。Typo 修复被 drop，因为它不属于这个 PR。这次 rebase 产生的历史让 6 个月后“我们何时给用户 API 加了写权限？”这类问题只需一条 `git log --oneline | grep` 就能回答，而不需要深潜。

**Q6.** 一个生产 bug 出现。测试 `test_payout_rounding_eu` 昨天在 `main` 上开始失败，最后一个已知好版本是 6 周前的标签 `v3.8.0`。走一遍你会跑的 bisect。输入是什么、预期命令是什么、如果 bisect 落在一个不能构建的提交上你怎么办？

提示

§3.3 的基本工作流加失效模式讨论。

**答：** Bisect：

    git bisect start
    git bisect bad HEAD
    git bisect good v3.8.0
    git bisect run npm test -- test_payout_rounding_eu

预期：Git 在范围内二分查找，在每个中点运行测试，标记 good 或 bad，大约 8–10 步后报告首个坏提交。墙上时间取决于测试速度；如果测试 30 秒，bisect 在 5–8 分钟完成。

如果某个中点提交不能构建：bisect run 会以非零退出码退出，Git 可能把它解释为 bad，或标记为 `skip`。修复方法是在 bisect 命令里显式检测构建失败并退出 125（特殊“跳过该提交”码）：

    git bisect run sh -c 'npm install || exit 125; npm run build || exit 125; npm test -- test_payout_rounding_eu'

这会跳过不可构建的中点，而不是错误分类它们，bisect 继续用可构建的邻居进行。如果范围内太多提交都不可构建，bisect 可能 inconclusive；此时更深层的解是今后强制执行每个提交可构建（§3.1 的原子提交纪律）。对当前 bisect，你退回到手动阅读未解决范围内的提交。
