#### 应用问题

**Q5.** 在代码库里找出一个 mock 重的测试文件。挑一个 mock，用 fake 重写该测试。比较重写后的可读性和脆弱性。

提示

Fake 通常需要写或找内存实现；前期成本由降低脆弱性来平衡。

**答：** 这是开放练习。常见发现：基于 mock 的测试更短（5–10 行 mock 设置），但每个断言都编码调用结构。基于 fake 的测试更长（fake 占 10–20 行，测试本身 5 行），但每个断言都关于结果。重写后，测试读起来更像行为描述，而且生产代码的行为中性重构不会破坏它。

Fake 的投资是分摊的：同一个 fake 服务多个测试。三四个测试用上 fake 后，每个测试的成本就比基于 mock 的等价物更低。

**Q6.** 为代码库里一个实体实现内存 Repository。至少在三个测试中使用它。报告测试代码前后对比。

提示

从最简单接口（find、save）开始，测试需要时再添加方法。

**答：** 这是开放练习。一个合理的 Customer 内存 Repository：

    class InMemoryCustomerRepository:
        def __init__(self):
            self._customers: dict[str, Customer] = {}
        def find(self, cid: str) -> Optional[Customer]:
            return self._customers.get(cid)
        def save(self, customer: Customer) -> None:
            self._customers[customer.id] = customer
        def find_by_region(self, region: str) -> list[Customer]:
            return [c for c in self._customers.values() if c.region == region]
        def delete(self, cid: str) -> None:
            self._customers.pop(cid, None)

前：三个测试各自有三套 Mock 设置。后：三个测试共享一个 fake。前者每个测试更长且脆弱；后者每个测试更短且稳健。

Fake 本身大约 15 行。它自身也是可测试的：写几个测试验证 fake 行为符合契约（find 对缺失 ID 返回 None、save-then-find 返回保存的 customer 等）。这是一笔小投资，却在整个套件中收益。

**Q7.** 取一个使用 mock 的 AI 生成测试。按 §7.6 重定向：合适时重写为 fake 或 spy。更新 `CLAUDE.md` 中的测试替身偏好。再让 AI 对类似测试跑一次；验证它现在是否使用 fake。

提示

更新 `CLAUDE.md` 是持久修复；重写是即时修复。

**答：** 这是开放练习。`CLAUDE.md` 更新类似 §7.6 示例。更新后，用同样的测试请求提示 AI；测试现在应该从 `tests/fakes/` 构造 fake，而不是 `Mock()` 对象。如果 AI 不遵守，就把 `CLAUDE.md` 写得更具体（例如 “所有 `OrderService` 测试都使用 `tests/fakes/customer_repo.py` 里的 `InMemoryCustomerRepository`”）。

持久教训：AI 违反团队约定是 `CLAUDE.md` 缺口。修复是 `CLAUDE.md`，而不是无休无止地逐 PR 审查和重写。
