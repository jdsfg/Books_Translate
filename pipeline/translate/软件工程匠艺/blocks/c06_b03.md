#### 80% 陷阱

常见的组织目标是“80% 覆盖率”。这目标听起来合理，却产生可预测的糟糕激励。被 80% 覆盖率卡住的工程师会写测试直到指标达到 80%，不管那些测试的价值。边缘处写的测试通常价值低：简单 getter 的测试、弱断言的测试、代码路径已被充分覆盖的测试。覆盖率上升；信心不升。

更有用的框定是*覆盖率阈值作为棘轮*：一个当前 60% 覆盖率的模块，任何 PR 都不能让它低于 60%；降低覆盖率的 PR 必须明确说明理由。阈值是按模块而非全局，目标是单调改进而非固定目标。这避开了 80% 陷阱激励，同时保留了负面信号。


#### 分支覆盖率 vs 行覆盖率

行覆盖率计算执行到的行数。分支覆盖率计算决策分支被走到的数量。只要有条件判断，两者就会分离：

    def f(x):
        if x > 0:
            return 'positive'
        return 'non-positive'

用输入 `x=5` 测试，执行了 `if x > 0` 行和 `return 'positive'` 行；`return 'non-positive'` 行从未执行。这个函数行覆盖率是 2/3 ≈ 67%（有些工具不把 `def` 行算可执行；具体百分比取决于工具计数方式，但原则相同：只给实际运行的行计分）。分支覆盖率是 50%——条件的真分支走了，假分支没走。

加入第二个测试 `x=-3`，假分支也走了；行覆盖率升到 100%，分支覆盖率升到 100%。注意行覆盖率达到 100% 时仍然漏掉了 *x=0 的边界情况*；这正是变异测试暴露的缺口（第 6 章）。

分支覆盖率是稍微更诚实的指标；它让“我测试了所有分支”可测量。现在多数 CI 工具两者都报告。当代码库条件很多时，优先把分支覆盖率作为主要信号。


### 5.3 快照测试的窄适用

快照测试捕获函数在给定输入下的输出并存储；后续运行与存储输出比较，不同则失败。便利之处在于你不用写断言；框架通过比较替你写。


#### 快照测试物有所值之处

快照测试适合：

* 输出大且结构复杂（完整 HTML 页面、50 个字段的 JSON 响应、生成的 AST）。
* 目标是检测*非预期*变化，而非验证具体正确性。
* 输出是确定性的（没有时间戳、没有随机 ID、没有环境相关值）。
* 快照变化时会有人审查 diff，把 diff 当作意图测试。

React 组件渲染测试、稳定 API 的响应载荷测试、解析器输出测试是典型好用法。
