#### 4. 变更是否契合代码库架构？

根据第 14 章：变更是否在正确层？是否尊重 ports-and-adapters 边界？是否把 I/O 引入函数式核心？是否绕过 Repository 模式（第 7 章）？

具体架构臭味：

* **核心函数内联网络调用**：违反 FC/IS。
* **通过 Singleton 而非构造器注入新依赖**：违反第 13 章。
* **adapter 直接调用另一个 adapter** 而不经过核心：违反六边形。
* **在第 13 章模式**（Singleton、Visitor、Factory Factory）出现在新代码中：黄旗。


#### 5. 变更是否与周围代码一致？

命名、风格、错误处理约定、文件组织：新代码是否像代码库其余部分？不一致不是 bug，但增加未来读者的认知负荷。

具体一致性检查：

* **命名**：名字是否符合代码库约定？领域概念是否使用代码库词汇？
* **错误处理**：代码是否抛出代码库其余部分使用的异常类型？
* **导入风格**：导入是否按代码库要求分组排序？
* **测试风格**：测试结构是否像代码库其他测试？


#### 6. 变更是否原子？

根据第 3 章：PR 是一个原子概念变更，还是三个变更打包？含无关变更的 PR 应拆分。


#### 7. 变更让代码比之前更好还是更差？

童子军规则（第 20 章预览）：触碰函数的 PR 应让它稍微好一点（小重命名、修正误导注释、删除死分支）。让代码变差（加 hack、无 ticket 留 TODO、引入团队已同意移除的 workaround）的 PR 是黄旗。


### 15.3 不该看什么

审查时间有限。有些反馈类别消耗时间却无相应收益：


#### linter 已处理的风格偏好

如果代码库已配置 linter，风格是 linter 的事。审查者不应在缩进、行宽、引号风格、末尾逗号等 lint 处理的细节上花时间。作者应在开 PR 前运行 linter；CI 应强制执行；审查者不应重复工作。


#### 团队未达成一致的个人品味

“我会用不同方式写”很少是有用反馈。如果团队已通过约定（CLAUDE.md、风格指南、过往审查）达成共识，执行约定。如果没有，作者的选择可接受；不要因个人偏好阻塞 PR。


#### 投机未来灵活性

“如果我们需要支持第三个后端怎么办？”正是引入模式税的问题（第 13 章）。纪律是按当前需求评估代码；如果真出现第二个后端，那时再重构。审查者推动投机灵活性会产生过度工程。


#### 相邻代码的全面重构

修复 billing bug 的 PR 不应被要求重构整个 billing 子系统。审查者可以记录后续工作机会，但不应把 bug 修复与无关重构绑定阻塞。
