#### 为什么这个工作流有效

三个机制复利：

* **Spec 精确**：failing tests 没有歧义；智能体成功标准清楚。模糊提示产生模糊代码；测试产生具体代码。
* **循环快速**：智能体迭代以秒计；人类审查以分钟计；总反馈循环远快于人类单独编码。
* **人类注意力在正确位置**：在 spec（代码应该做什么）和审查（代码是否正确做了）。写代码的机械工作被委托；判断留在人类。


#### 常见误解

一个常见误解是“spec 驱动意味着人类只写提示。” 错误在于把*spec*和*提示*混为一谈。提示是自然语言；智能体解释并可能误解。Spec 是智能体输出必须通过的测试；没有解释 slack。Spec 驱动特指 failing tests；提示驱动是更弱的版本，产生更模糊代码。

第二个常见误解是“测试即 spec 只对纯函数有效。” 错误是从简单案例过度推广。测试即 spec 对任何有可验证行为的代码有效：HTTP endpoint、数据库操作、队列消费者。测试描述输入和期望输出；spec 就是那些测试检查的内容。


### 22.3 有效的提示模式

智能体质量取决于提示。有些模式产出更好结果；这些模式可学习。


#### 模式 1：提供上下文

带相关上下文的提示比不带的好。上下文包括：failing test、相关现有代码、团队约定（引用 CLAUDE.md）、约束（不要改文件 X，用库 Y）。

弱提示：“加一个计算滞纳金的函数。”

强提示：“添加函数 `calculate_late_fee(invoice, current_date)`，返回 Decimal。Spec 见 `tests/test_late_fee.py` 中的 failing tests。函数应遵循 CLAUDE.md 约定（用 Decimal 而非 float；坏输入抛 InvalidInvoiceError；符合 `core/decisions/` 中的纯函数风格）。不要修改 InvoiceRepository 类。”

强提示文字更多，但产出更好；智能体有了所需约束。


#### 模式 2：要求写测试

包含“并添加测试”的提示会产出测试；不包含的可能不会。测试请求应具体：“为不变量添加基于属性的测试”或“为边界情况（负数金额、零金额、货币不匹配）添加测试。”


#### 模式 3：显式迭代

当智能体首次输出部分正确时，不要重新开始。迭代：“实现正确，但货币不匹配的测试太弱；加强它以验证具体错误信息。”

智能体擅长迭代。人类角色是识别需要改进什么并具体提出。


#### 模式 4：约束范围

范围宽的提示产生宽输出，往往超出意图。范围窄的提示产生窄输出。

宽：“把 billing 模块重构得更干净。”

窄：“在 `billing/refund.py` 中对 45–72 行应用 Extract Function；新函数命名为 `compute_proration_for_partial_refund`。不要改其他文件。”

窄版本可靠；宽版本 risky。
