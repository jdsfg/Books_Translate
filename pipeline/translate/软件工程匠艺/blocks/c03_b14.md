辩护 #1：本章命名的模式（死条件、承重注释、迁移疤痕、作者的担忧）是真正普遍的。它们出现在任何超过 3 年的代码库里。一个内化它们的工程师读每个旧代码库都更快。对比语言相关技能：知道 Java 惯用法只在 Java 代码库有用，Python 代码库则不然。考古模式在哪都有用。


### 本章总结

阅读是 2026 年工程职业生涯中的主导活动，而读得好是一项会随时间复利的技能。本章的核心工具：带着意图阅读（§2.1）；遵循测试-入口-模型-细节顺序（§2.2）；把 `git blame` 当作历史文档，不是找人背锅的工具（§2.3）；识别考古模式——死条件、承重注释、迁移疤痕和作者的担忧（§2.4）；通过三遍法（广度、深度、查询驱动）建立心智模型，并把一半外化到笔记本里（§2.5）；对 AI 生成代码额外怀疑，因为它有局部正确、全局不一致的典型质感（§2.6）；当你能预测失效、能用一句话描述改动、或能先写测试时停止阅读（§2.7）。

Asher 在 Trellis 为期 4 天的阅读冲刺产出 6 行修复，是本章的工作示例。它会在第 3 章（本地 Git 匠艺，让 `git blame` 和 `git log` 更强大）和第 10 章（在测试保护下重构，读现有测试是第一步）中复利。在第 15 章它作为代码审查的基础回归：读不好的审查者不可能审查好。阅读并不光鲜，2026 年的 AI 也无法在深层意义上替你阅读。它是本书其余部分建立的基础技能。


#### 三条要点

  1. **下次遇到令人意外的代码行时，改动前先问 Asher 的问题**：*原作者在担心什么？* 跑 `git blame`、读提交信息、寻找这行代码在防御的事故。然后再决定。
  2. **进入陌生模块时，先读测试再读实现。** 即使测试很薄，它们也会告诉你团队承诺了什么。实现只告诉你团队写了什么。
  3. **为你维护的代码库开一个笔记本。** 三个栏目：词汇、谜题、地雷。每周添加。3 个月后你就有心智模型的一半外化；1 年后你就有一个个人参考库。
