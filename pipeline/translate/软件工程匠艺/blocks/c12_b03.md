#### Shadow read 比较

两条路径都运行时，比较逻辑至关重要。朴素相等可能失败，因为两条路径可能在非本质细节上不同（一个内部 ID、一个格式不同的时间戳）。比较必须聚焦*可观察契约*：

    def _compare_results(self, new, old):
        if new.amount != old.amount:
            self._log_mismatch('amount', new, old)
        if new.currency != old.currency:
            self._log_mismatch('currency', new, old)
        if new.status != old.status:
            self._log_mismatch('status', new, old)
        # 忽略内部 ID、可能无害不同的时间戳

不匹配会被记录足够的上下文以供调查（输入、两个输出、环境变量）。不匹配量突增会触发告警；调查揭示新路径有 bug，还是比较逻辑本身错了。


### 11.3 功能开关作为安全机制

§11.2 中的功能开关是安全机制。新路径的 bug 可在几秒内通过把开关拨回旧路径而中和；无需部署、无需重建、无需事故升级。

这个属性让多月重构可行。没有开关，每个阶段变更都是一次部署；团队必须协调部署、监控影响、出问题通过部署回滚。有开关，每个阶段变更都是配置变更，几秒钟可逆。


#### 大型重构的开关设计纪律

并行路径重构的开关设计比普通功能开关更复杂：

* **粒度**：开关必须允许按客户、租户、区域或样本百分比灰度。团队能够先启用一小部分 canary 再扩大。
* **独立性**：主路径开关和 shadow 开关必须独立。团队可能想要只 shadow 不 canary，或只 canary 不 shadow。
* **默认值**：生产环境中两个开关都默认关闭。新路径在显式启用前保持黑暗。
* **命名与生命周期**：开关按团队约定命名（第 4 章）；它们有与迁移完成对应的计划 `kill_by_date`；在旧路径删除后的最终 PR 中移除。


#### 常见误解

一个常见误解是“功能开关会拖慢速度，因为运行时开销。” 错误在于假设开销显著；对大多数开关服务（LaunchDarkly、Statsig、Unleash、Flipt），开关评估是缓存的本地查询，耗时微秒。开销远低于正常请求处理的波动。

功能开关的真正成本是*复杂性*：迁移期间代码库有两条路径。读代码的工程师必须理解两者。这是真实成本，但*暂时*；迁移完成后第二条路径消失。这种暂时复杂性是迁移安全的代价。
