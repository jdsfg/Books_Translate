#### 一个值得持有的立场：十人以下团队不要采用智能体提交 PR

这个工作流的收益是吞吐量；许多智能体 PR 并行飞行，每个被并行审查。低于约十名工程师时，团队没有审查产能来消费这些吞吐量；智能体的 PR 排队，审查在体量压力下退化，未经审查的可信度债务（第 19 章）累积速度超过团队偿还能力。对*小团队*看起来像是力量倍增器的工作流，实际上是债务倍增器。

建议：小团队（十人以下）应让智能体以结对编程模式（第 16 章 §16.5）工作，人类是每个 PR 的作者，智能体是助手。智能体提交 PR 模式只有在有足够人类跟得上产出时才回本。明确设定门槛；不要漂移进入。


### 22.7 AI 辅助工程的反模式

几个应避免的模式：


#### 信任智能体的“测试通过”

智能体报告测试通过。审查者扫一眼；合并。测试是 AI 生成的；它们通过是因为它们恰好测了实现做了什么，而不是需求要求什么。实现错了；测试错了；PR 错了；生产错了。

纪律：读 diff，包括测试。审查者的理解是质量门，不是智能体的。


#### 把初稿当终稿

智能体几秒产出初稿。人类因为它可工作就接受。但初稿很少是最佳版本；迭代会改善。跳过迭代以同样速度产出较低质量代码。

纪律：至少迭代一次。让智能体改善具体方面；第二稿 reliably 更好。


#### 让智能体做设计

让智能体“决定用什么架构”。智能体选默认，可能不适合团队。代码库漂向泛化模式；团队的 distinctive 设计丢失。

纪律：人类设计；智能体实现。架构决策属于 ADR（第 17 章）；智能体读 ADR 并应用决策。


#### 忽视 CLAUDE.md

团队写了 CLAUDE.md 却从不更新。智能体输出反映过时约定；审查者逐个 PR 纠正，而不是更新文件。

纪律：在新约定落地的 PR 中同时更新 CLAUDE.md。文件是活的产物，不是一次性设置。


#### 忽视智能体调用成本

大规模采用智能体提交 PR 工作流（§22.6）的团队正在做容易被低估的 recurring API 成本承诺。按 2026 年 LLM 定价，一个中等规模功能的单次智能体会话并非免费；每个工程师每周跑几十个此类会话的团队会在云账单上看到真实数字。陷阱是成本落在工程经理控制的预算之外的另一条线，因此财务问起前一直隐形。

纪律：至少按工程师每周追踪智能体会话成本，并在与生产力收益相同的 dashboard 上展示。让权衡显式。如果每个发布功能的成本远超节省的工程师时间，这个工作流对你的团队成本结构不划算；重新考虑。
