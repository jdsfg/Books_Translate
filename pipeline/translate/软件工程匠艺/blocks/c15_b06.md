### 14.5 Repository 模式作为 FC/IS 实践

第 7 章的 Repository 模式正是六边形术语中的 driven-port 抽象。应用代码（核心）依赖 `CustomerRepository` 接口；SQL 实现是 adapter；测试使用内存实现。

复利纪律链：

* 测试替身（第 7 章）→ Repository 模式 → driven ports → 六边形架构 → 函数式核心 + 命令式外壳。

每一层都建立在前一层之上。内化了较低层的工程师会自然地把较高层视为结论。跳过层次的工程师会觉得高层任意或过度工程。

这就是章节顺序重要的原因：先测试（第 5–8 章），再重构（第 9–11 章），再明智应用模式（第 12–13 章），再架构框架（本章）。顺序即依赖顺序；每章都建立在前辈之上。


### 14.6 AI 层：智能体与架构形状

2026 年的 LLM 从训练数据中知道六边形架构和 FC/IS。被询问时，它们能生成符合形状的代码。但它们在以下方面不可靠：

* **识别形状何时合适。** 智能体在小脚本上套用六边形（过度工程），或在应该使用六边形的系统上生成 I/O 纠缠的扁平代码。判断代码库是否证明该形状合理是人类工作。
* **长期保持形状。** agent-PR 模式中的智能体可能会添加违反形状的代码（从纯函数中调用 driven port、在函数式核心里有副作用）。PR 审查（第 15 章）是发现这些的地方。
* **一致命名 ports 和 adapters。** 智能体可能生成 `IDatabase` 或 `DataAccessLayer` 这类不符合团队命名约定的 port 名；CLAUDE.md 应规定约定。


#### 针对架构形状的 CLAUDE.md

把团队架构偏好写入 CLAUDE.md 的条目示例：

    ## Architectural shape

    We use Hexagonal Architecture for our backend services:
    - Business logic lives in `src/core/`.
    - Ports (Protocols) are defined in `src/core/ports/`.
    - Adapters live in `src/adapters/<system>/`.
    - Tests of the core use in-memory adapters from `tests/fakes/`.

    Within the core:
    - Decision logic should be pure functions in `src/core/decisions/`.
    - Orchestrators are in `src/core/orchestrators/` and use the gather/decide/act pattern.

    When adding a new external system, add a port first (in `src/core/ports/`),
    then an in-memory fake (in `tests/fakes/`), then the production adapter.

这些指令引导智能体生成的代码趋向该形状。约定明确时，智能体遵循；不明确时，它们生成不一致代码。
