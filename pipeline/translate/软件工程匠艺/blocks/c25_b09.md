#### 3. 与周围代码风格不一致

不同命名约定。不同错误处理习惯。不同测试 fixture 风格。不同 import。与代码库其余部分不同的文件组织。

**问：** *这个 PR 看起来像我们代码库的其余部分吗？* 如果不是，智能体漏了约定——修复这个 PR 并更新 CLAUDE.md，避免下次再漏。


#### 4. 缺失或粒度错误的错误处理

裸 `except:` 子句。`try / except Exception` 吞下一切。`try { ... } catch (e) { console.log(e); return null; }`。没有退避的重试。没有上下文的错误信息。

**问：** *当它的依赖失败时，这段代码做什么？这是正确的行为吗？*


#### 5. 微妙的 off-by-one 或边界错误

边界附近的 `<` vs `<=`。循环边界。数组索引。日期计算（尤其时区或夏令时）。舍入行为。整数除法。最糟的 bug：几乎正确。

**问：** *边界上会发生什么？* 用正好在边界的输入 mentally trace 代码；验证行为符合意图。然后做变异测试（第 6 章）。


#### 6. 幻觉的库 API

来自你不认识库名的 import。签名看起来不熟悉的函数调用。听起来合理但可能不存在的方法名。过时或废弃的 API 使用。

**问：** *这个 API 真的存在吗？* 对照当前库文档或本地运行代码验证。特别注意：看起来很像真库但字符有差异的 typosquat 包名——逐字符验证。


#### 7. 看似可信的不安全代码

拼接而非参数化的 SQL 字符串。硬编码的 secret、token、凭证。弱默认加密（MD5 密码、ECB 模式）。新 endpoint 缺少授权检查。对攻击者可控输入使用 `eval` / `exec` / `os.system` / `child_process.exec`。未签名的 webhook handler。

**问：** *如果攻击者控制这个函数里的每个变量，他们最坏能做什么？* 如果你回答不了或答案很糟，在合并前修复或升级到安全审查。


#### 两分钟 checklist（可打印）

对每个 AI 生成的 PR，按顺序过下面七个提示。每个都很快；纪律是你真的每次都过，直到变反射：

  1. **边界情况：** 什么输入能破坏它？测试了吗？
  2. **抽象：** 这里的每一层都有理由吗？
  3. **风格：** 它像代码库吗？
  4. **错误：** 依赖失败时会发生什么？
  5. **边界：** 正好在边界上会发生什么？
  6. **API：** 所有 import 和签名都是真的吗？
  7. **安全：** 攻击者控制输入能达到什么？

如果任何答案让你担忧，评论 **Blocking**（第 15 章 §15.4）。如果不确定，评论 **Suggestion** 并提问。七个提示没有干净回答之前不要合并。


#### 为什么有效

七个提示压缩了有经验审查者默默会问的问题。新手审查者一个都不问；资深审查者不假思索地问全部；持这份清单的工程师则有意地问全部，几个月内就能 ramp 到资深审查者的全面性。清单是内在纪律的外在形式。
