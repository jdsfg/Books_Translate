**Q2.** 下面是同一实际变更（auth 模块 session 处理重构）的两个 PR 描述。评价每个：哪些 section 存在、薄弱或缺失？哪个描述让审查者能高效工作？指出较弱描述中*单个最有效*的改进。

**描述 A：**

    ## Summary
    Refactored session handling.

    ## Test plan
    Tests pass.

**描述 B：**

    ## What
    Extract session storage from `AuthService` into `SessionRepository`, behind an interface.

    ## Why
    The team needs to support Redis-backed sessions for the multi-tenant migration (TRELLIS-2419).
    Inlining the storage layer into AuthService was blocking that work because tests would need
    real Redis to verify auth flows. With the Repository in place, tests use the in-memory fake.

    ## How
    SessionRepository protocol + SqlSessionRepository (existing behavior) + InMemorySessionRepository (tests).
    AuthService takes the repo via constructor injection. No production behavior change.

    ## Testing
    40 existing auth tests pass unchanged. 8 new tests use InMemorySessionRepository directly.
    Manually verified login/logout flow on staging.

    ## Risk
    Behavior should be identical. The injection wiring changes how AuthService is constructed in
    the application; verified all 3 call sites updated.

    ## Reviewer note
    The Protocol design in src/auth/session_repo.py; first time we are using Protocol over ABC
    in this codebase. Sanity-check that pattern.

提示

§16.2 的六个组件：What / Why / How / Testing / Risk / Reviewer note。每个 section 填满时，审查者准备不同。

**答：**

**描述 A** 只有 What（一行弱）和 Testing（一句无用）。缺失：Why、How、Risk、Reviewer note。审查者到达这个 PR 后必须*自己重建*所有上下文；读 diff、推断动机、猜测风险、决定重点。这消耗了审查者最昂贵的几分钟，而作者本可在五分钟内完成。

**描述 B** 六个组件齐全且充实。Why 部分最强：它链接到底层动机（多租户迁移），给出 ticket 号，解释重构解锁的上游问题。审查者到达时知道*为什么*有这个重构、*为什么现在做*；其余审查是结构性的。

**对 A 最有效的单项改进**：加 *Why*。如果 A 只能加一个 section，Why 是最高杠杆。知道底层动机的审查者能高效评估其余部分；他们知道该权衡什么、该寻找什么风险、该考虑哪些替代方案。没有 Why 的审查者先是在调试 PR 为何存在，其次才是调试 PR 是否正确——这是两倍工作量。

为什么实践中“Why”比其他更重要：大多数野外 PR 描述都有某种 What（“重构了 X”），通常有薄弱的 Testing（“tests pass”），但很少 Why。Why 是最常被跳过的 section，也是价值最高的。本书的 PR 描述纪律（§16.2）主要是认真对待 Why 的纪律。

**Q3.** 结对编程何时回本，何时是 overhead？

提示

§16.4 的分类。

**答：**

回本：

* 从两个大脑中受益的复杂问题（微妙 bug、深度重构、性能、安全）。
* 一位工程师有另一位缺乏的专业知识时的知识共享。
* 人类与 AI 一起工作的 AI 协作。

是 overhead：

* 一个人单独做更快的例行工作。
* 两位工程师知识相同且工作 straightforward。
* 心流比协作更重要的沉浸式深度工作。

纪律是选择何时结对，而不是普遍强制。强制所有工作结对的团队会让多数工作变慢；从不结对的团队会错过本会受益的场景。
