### 3.4 把 `git reflog` 当作撤销

Reflog 记录你的 `HEAD` 和分支在本地经历过的每个状态。有两个保留窗口重要，第二个会咬人：`gc.reflogExpire` 默认对仍能从引用到达的条目保留 **90 天**，而 `gc.reflogExpireUnreachable` 默认对已经不可达的条目保留 **30 天**——这正是 `reset --hard` 或 rebase 造成的孤儿提交的命运。因此，本章教你的那些破坏性操作的恢复安全网是 30 天窗口，不是 90 天。30 天加一次 `git gc` 后，孤儿就没了。尽早恢复。

经典救援：

    # 我刚做了可怕的事，比如 reset --hard 到了错误提交
    git reflog
    # 显示 HEAD 最近 N 个状态及其哈希
    # d1f3a91 HEAD@{0}: reset --hard 9a7c2d3  <- 错误操作
    # 4e2c8b5 HEAD@{1}: commit: WIP good stuff <- 想回到这里
    # ...

    git reset --hard HEAD@{1}
    # 恢复成功

Reflog 是本地的，不与远端同步。因此，如果你在远端丢失了一个 force-push 的分支，有时还能从本地 reflog 恢复——前提是你最近有本地副本。


#### Reflog 纪律

这项纪律是：**在任何破坏性操作前，查看 reflog 或记下当前提交。** 破坏性操作包括 `reset --hard`、带着未提交改动 `checkout` 其他分支、你可能想撤销的 `rebase`，以及任何 `--force` push。实践中：

    # 危险操作前，先捕获一个标签
    git log --oneline -n 1
    # abc1234 my current state

    # 做危险的事
    git rebase -i HEAD~10

    # 如果搞砸了：
    git reset --hard abc1234

标签 `abc1234` 只是一个哈希；复制它零成本；需要时救你一命。熟练后，你会在做任何还没做过一千次的操作前，条件反射地这样做。
