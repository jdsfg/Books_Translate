#### 值得建立的四个 AI Git 习惯

  1. **配置智能体的提交信息模板。** 多数智能体运行时可以接受包含提交信息格式的系统指令。指定祈使语气、50 字符主题行、解释原因的 body，以及带相关 ticket ID 的 footer。没有这些，智能体会退化成不匹配你团队风格的通用样式。
  2. **让智能体按原子改动提交，而不是会话结束时才提交。** 在 `CLAUDE.md / AGENTS.md`（第 22 章）中指示智能体：每次可独立构建的改动后都提交，而不是最后产生一个巨大提交。智能体通常会遵守；纪律必须被明确指定。
  3. **合并前，在最后一个人类提交与智能体 HEAD 之间跑 `git diff`。** 这就是第 1 章 §1.2 的*审查适配性*工作。即使你信任智能体的每个单独提交，*聚合结果*仍可能产生你不想要的形状。合并前扫一眼累积 diff。
  4. **把智能体的 `git log` 当作 push 前需要清理的东西。** 用 interactive rebase 重写模糊信息、squash WIP、删除死胡同尝试。智能体的工作历史不是你的发布历史。


#### 通过 Git 历史捕捉线索 C 谎言

智能体的提交历史是捕捉线索 C 谎言（第 15 章）的有用表面：

* 同一文件里一连串小的 fixup 提交（`fix off-by-one`、`fix import path`、`fix typo`）是谎言 #5（隐蔽边界错误）或谎言 #6（幻觉 API）的迹象；需要额外仔细审查。
* 一个提交改动很多文件、声称“一致性”却没有清晰目的，是谎言 #2（过度抽象）或谎言 #3（风格不一致）的迹象。
* 提交信息说“改进了错误处理”，却没说明哪些错误、如何处理，是谎言 #4（缺失或粒度错误的错误处理）的迹象。

阅读智能体的提交历史本身就是一项匠艺技能，也是你审查智能体工作的第一关。
