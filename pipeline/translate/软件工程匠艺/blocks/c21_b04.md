#### Branch by Abstraction vs 绞杀者无花果

两种模式形状相似，但重点不同：

* **绞杀者无花果**：在*请求*层路由旧新。决策发生在请求边界。
* **Branch by Abstraction**：在*操作*层路由旧新实现。决策发生在系统内部的抽象边界。

对无状态服务（如报表 API），绞杀者无花果自然：在 HTTP 层路由。对有状态组件（如数据库访问层），Branch by Abstraction 自然：在应用内部接口处路由。

两种模式可结合。一次迁移可能：数据库层用 Branch by Abstraction（应用调用 `IDataAccess`；新旧实现它），HTTP 层用绞杀者无花果（部分 endpoint 路由到新、部分到旧）。


#### 完整示例：Aki 把 Helix 从 Diesel 迁移到 Drizzle

Helix 原本用 Diesel（Rust ORM）做数据库访问。2024 年，团队决定迁移到使用 Drizzle 的 TypeScript 服务。Branch by Abstraction 是正确的模式：

  1. Rust 服务暴露数据库操作的类型接口（现有 Diesel 调用）。
  2. 新的 TypeScript 服务用 Drizzle 实现同一接口。
  3. Rust 服务的数据库调用通过 gateway 路由，可分发到本地 Diesel 实现或远程 TypeScript 服务。
  4. 一次一个操作，gateway 被重新配置为路由到新服务。每次迁移是一个小小的 flag flip。
  5. 所有操作迁移完成后，Rust 服务的 Diesel 代码被删除；gateway 变成新服务的简单 HTTP 客户端。

总迁移时间：约四个月。风险画像：每个操作的迁移独立；一个问题不影响其他；回滚是一次 flag flip。


### 20.5 何时机会主义重构 vs 何时安排重构

团队有两种偿还债务模式：

* **机会主义**：每个 PR 应用童子军规则。小改进与实质性工作捆绑。无专门时间。
* **安排式**：计划的重构（第 11 章规模），分配团队时间。绞杀者无花果或 Branch by Abstraction 可作为载体。

两种模式各得其所。纪律是知道哪种适合当前情况。


#### 机会主义足够时

* 债务分散在许多文件；没有单一热点占主导。
* 代码库够小，机会主义改进能明显复利。
* 团队 PR 吞吐量高；小改进累积快。
* 指标（第 19 章）稳定或改善。


#### 安排式必要时

* 债务集中在一两个大子系统；机会主义改进不会收敛。
* 代码库有结构性问题（架构债务；第 14 章），需要协调变更。
* 指标在恶化且团队产能被消耗。
* 特定即将到来的变更需要先处理债务。
