#### 常见误解

一个常见误解是“六边形架构是企业级过度工程。” 错误在于把*框架*和*仪式*混为一谈。框架是“定义你的 ports，核心针对它们编写，adapter 单独实现”。对小服务，可能只需五个 port 和五个 adapter；对大服务，可能各五十个。框架随代码库规模扩展；仪式只在它回本时出现。

一个具体测试：代码库是否有与 I/O 纠缠的业务逻辑？如果有，六边形是合理的。如果没有（小脚本、一次性工具），则不是。2024 年的 Helix 子系统严重纠缠；重构在几个月内回本。


### 14.2 Ports 与 adapters 详解

词汇：

* **Port**：核心定义的抽象接口。按核心需要的*能力*命名（`CustomerPort`、`ChargePort`），而不是外部系统。
* **Adapter**：port 的具体实现。按*外部系统*命名（`SqlCustomerAdapter`、`StripeChargeAdapter`）。
* **Driver / Driven**：port 分两类。*Driving ports* 是外部进入核心的入口（HTTP 路由、CLI 命令、事件处理器触发核心动作）。*Driven ports* 是核心对外部世界执行动作的方式（数据库访问、vendor SDK、消息发布）。术语来自 Cockburn 原始论文。


#### Driver ports

Driver ports 是核心入口。一个 web 服务为每个 HTTP 路由设有 driver port：

    class PricingDriverPort(Protocol):
        def price_and_charge(self, customer_id: str, product_id: str) -> ChargeResult: ...

    # Adapter：HTTP 路由
    @app.post('/api/charge')
    async def http_charge(request: ChargeRequest, pricing: PricingDriverPort = Depends(get_pricing)):
        result = pricing.price_and_charge(request.customer_id, request.product_id)
        return {'status': result.status, 'amount': str(result.amount)}

HTTP adapter 知道请求/响应形状、状态码、JSON 序列化。driver port（由 `PricingService` 满足）只知道领域操作。


#### Driven ports

Driven ports 是核心对外部世界执行动作的方式。§14.1 的例子都是 driven ports。

区分很重要：核心测试使用 fake driving 输入（直接调用方法，无需 HTTP）和 fake driven 输出（内存 adapter）。HTTP adapter 单独用 HTTP client 测试；数据库 adapter 单独用真实数据库测试。


#### 依赖方向

核心依赖自己的 ports（它定义的抽象类型）。ports 不依赖核心的具体类。adapters 同时依赖 ports（要实现它们）和外部系统（要完成工作）。外部系统谁也不依赖。

方向：external → adapter → port → core → port → adapter → external。核心居中；ports 是两侧的抽象。

正是这个方向让核心可以在没有外部系统的情况下测试：替换 fake adapter；核心不变。


### 14.3 函数式核心 / 命令式外壳

Gary Bernhardt 在 2012 年的一次演讲中命名了*Functional Core / Imperative Shell*（FC/IS）。其形状是六边形更严格版本：核心不仅与 I/O 隔离，而且是*纯*的。所有副作用、所有 I/O、所有变更都存在于边缘薄薄的命令式外壳里。
