#### 概念检查

**Q1.** 一位初级工程师给你看了他们为代码库起草的两个设计，问“这是 Strategy 还是 Adapter？”——两者代码形状相同（一个 Protocol + 多个实现）。告诉他们每个设计属于哪种模式，以及为什么答案会影响团队在代码审查和设计讨论中如何讨论它们。

**设计 A**：`PricingPolicy` Protocol，实现为 `FreePricing`、`ProPricing`、`EnterprisePricing`。应用按客户等级在运行时选一个使用。

**设计 B**：`PaymentProcessor` Protocol，实现为 `StripeProcessor`、`PayPalProcessor`、`AdyenProcessor`。应用配置一个默认值，运行时不再选择。

提示

两者形状相同；*意图*不同。

**答：**

**设计 A 是 Strategy。** 三个实现是*内部做同一件事的不同方式*；应用按请求根据数据（客户等级）选择。它们作为一族被设计在一起。接口组织的是这个族。

**设计 B 是 Adapter。** 三个实现是*把外部系统翻译*成应用期望的接口。应用运行时不在它们之间选择；每个环境配置一个。实现存在是因为外部 SDK 形状不同；Adapter 把它们规范化。

为什么区分在对话中重要：

* “Strategy on the tier” 告诉团队：选择是运行时、数据驱动的，每个请求不同。审查者会看分派逻辑和等级选择规则。
* “Adapter for Stripe” 告诉团队：这是一个外部 SDK 的形状被包装。审查者会看 Adapter 是否正确隐藏 SDK 怪癖。他们*不会*寻找运行时分派。

知道差异的审查者每次审查都能为团队节省几分钟，避免问错问题。没有共享词汇的团队会在两种代码上都问两类问题；其中一些问题浪费作者和审查者时间。命名模式让对话直接跳到实质。

同样代码形状，两种模式，两种审查关注点。词汇是乘数。

**Q2.** Decorator 模式与使用 middleware 或函数组合在功能上何时重叠？

提示

Web 框架里的 middleware 本质上常是 Decorator。

**答：** Web 框架 middleware（Express middleware、FastAPI dependencies、Django middleware）本质上是 Decorator 模式。每个 middleware 包裹下一个，在委托前后加行为，并形成链。接口是“处理请求并返回响应”；每个 middleware 实现它并转发给下一个。

函数组合（`compose(f, g, h)(x) = f(g(h(x)))`）是以函数式而非 OO 风格表达的同形状。行为堆叠；顺序重要；结果是单一组合函数。

差异主要是风格：middleware/decorator 强调“带方法的对象”视角；函数组合强调“函数作为值”视角。2026 年，选择通常是语言惯用法和团队偏好的问题。模式相同。
