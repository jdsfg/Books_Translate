#### Spy

Spy 记录发生的交互，以便测试结束后断言。

    class SpyEmailSender:
        def __init__(self):
            self.sent = []
        def send(self, to, subject, body):
            self.sent.append({'to': to, 'subject': subject, 'body': body})

    # 测试中：
    spy = SpyEmailSender()
    order_service = OrderService(email_sender=spy)
    order_service.place_order(order)
    assert len(spy.sent) == 1
    assert spy.sent[0]['to'] == order.customer.email

用于测试的内容就是交互本身（邮件是否发出、审计日志是否写入、队列是否入队）。Spy 是被动的记录器；不预设行为。


#### Mock

Mock 是 stub 加期望：既返回固定答案，*又*验证特定调用是否发生。

    mock_repo = Mock(CustomerRepo)
    mock_repo.find.return_value = Customer(id=1)
    mock_repo.find.assert_called_with(1)  # 若 find 没被以 1 调用，测试失败

用于测试必须验证特定交互模式时。Mock 强大但脆弱：它们把内部调用结构编码进测试，任何改变结构的重构都会让测试失败，即使行为没变。


### 7.2 何时用哪种替身

五种替身并非在所有情况下同样好。纪律是为手头测试选择合适复杂度。


#### 对有状态依赖优先用 fake

如果依赖有被测函数读写状态（数据库、缓存、队列），fake 通常是正确选择。Stub 抓不住写后读行为；mock 强迫你规定调用结构，很脆弱。


#### 对简单输入优先用 stub

如果函数只需要依赖返回一个特定值，stub 就够了。给 stub 加状态是过度工程。


#### 对行为验证优先用 spy

如果测试关注的是*是否发生了特定副作用*（邮件发送、日志写入、事件发布），spy 让你事后断言效果，而无需把测试耦合到内部调用结构。


#### 少用 mock

Mock 适合：(a) 依赖不容易 fake（内部不透明的 vendor SDK），(b) 测试*专门*关注调用结构（例如验证重试次数的熔断器测试），(c) 被测行为是与依赖的*交互协议*而非结果状态。

除了这些情况，mock 往往过度规定并产生脆弱测试。


#### 常见误解

一个常见误解是“mock 是最佳实践，因为它们隔离了单元。” 错误在于把*隔离*与*过度规定*混为一谈。使用 fake 的测试也是隔离的（测试不碰真实数据库），而且 fake 不会把内部调用结构编码进测试。这种误解之所以产生，是因为 mock 一开始设置更容易（一行 `Mock()` 对比几行 fake 类），所以成了默认；代价在重构时显现。


### 7.3 Repository 模式

Repository 模式是让 fake 好用的设计选择。Repository 是对特定实体类型抽象数据访问的对象，提供 find、save、query 等方法。
