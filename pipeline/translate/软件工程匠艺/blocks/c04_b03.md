### 3.2 Rebase vs merge：诚实比较

Git 里很少有哪个话题比 rebase 与 merge 引发更多宗派争论。诚实答案是两者各有位置；任何一边的教条都是错的。本节给出选择标准。


#### Rebase 做什么

`git rebase main` 把你当前分支的提交拿到最新 `main` 上重放。结果是*线性*历史。你的提交出现在最新 `main` 提交之后，仿佛你一开始就从这个点切出分支。

Rebase 会重写提交哈希。如果你已经 push，且队友基于你的分支工作，rebase 会要求他们处理分叉（通常用 `git pull --rebase` 或 force-with-lease push）。因此 rebase 在 push 前的本地分支是安全的；push 后（没人用）也安全（但不禁止）；在共享分支上危险。


#### Merge 做什么

`git merge main` 创建一个*合并提交（merge commit）*，把你的分支历史与 `main` 历史合并。结果是*分支*历史，可见地保留并行工作。哈希不变。任何人追踪你的分支，merge 前后看到的哈希一致。

Merge 永远是安全的，因为它不重写历史。代价是历史不再线性；你看到的是合并图，而不是变更列表。


#### 何时优先 rebase

* **在开 PR 前清理本地分支。** 这是最便宜、最安全、最有价值的 rebase 用法。Squash WIP 提交、拆分混合关注点提交、打磨提交信息。
* **让长期功能分支与 `main` 保持同步。** 每隔一两天 rebase 到 `main` 上，防止分支漂移；冲突分小解决。
* **在接收端保持线性历史。** 有些团队要求所有 PR 以 rebase 并 fast-forward 的序列合入，这样 `main` 是一条单线。这产生干净的 `git log --oneline` 和干净的 bisect。


#### 何时优先 merge

* **记录真实的分支事件。** 如果两个工作流确实并行发生，你想保留这一事实（release 分支、hotfix 分支、fork 集成），merge 诚实地保留了并行性。
* **与基于该分支工作的队友共享分支。** 如果别人也在你的分支提交，rebase 会重写他们的上下文。merge 保持每个人的哈希稳定。
* **避免重复解决 rebase 冲突。** 长期分支频繁 rebase 到快速移动的 `main` 上，可能多次重复解决同一个冲突（每个提交一次）。merge 只解决一次。


#### 实用规则

对多数工作工程师、多数场景，结果最好的规则是：

  1. **推送前的本地分支**：自由 rebase。用 interactive rebase 让历史原子化。
  2. **推送后、无人使用的 PR 分支**：rebase 或 merge，按团队偏好。force-with-lease push 没问题。
  3. **推送后、队友已基于其上工作的分支**：merge，或在 rebase 前明确协调。
  4. **在 `main` 本身**：永远不要 rebase。永远不要 force-push。这是团队共享历史；重写它就是事故。

“rebase 是邪恶的”这一教条来自第 4 类滥用；“merge 产生脏历史”来自第 1 类的懒惰。两者都不是其余情况的规则。
