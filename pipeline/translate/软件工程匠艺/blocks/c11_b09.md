区分两种情况：测试失败是因为 (a) 可观察结果变了（重构错了）还是 (b) 内部机制变了但可观察结果相同（测试脆弱）。用重构后的生产代码和测试输入运行；如果输出与测试期望一致，测试是脆弱的。如果输出不同，重构是错的。

**Q3.** 为什么“先重构以启用测试，再测试，再重构”有时必要？举个例子。

提示

有些代码按当前写法无法测试。

**答：** 当代码当前结构让测试不可能或不现实时必要，即使只是特征化。常见情况：函数直接从系统调用读取 `current time`（无法在测试中变化）、向硬编码 URL 发 HTTP 请求（无法重定向）、深层嵌套逻辑把有趣行为埋住。

示例：函数 `should_send_renewal_reminder(customer)` 直接读 `datetime.now()` 并检查客户续约日期。要测试任意当前日期，必须先重构把当前日期作为参数传入（引入参数对象或加参数）。这次小而机械的重构后，特征测试可以变化日期并锁定行为。实质重构在此之后。

第一步重构选择足够安全、不需要测试：重命名、抽取纯 helper、把副作用依赖注入为参数。这些 bootstrap 操作把不可测试代码变成可测试代码。

**Q4.** 两位工程经理争论一个 6 周项目的工作顺序，该项目要重构一个 2,500 行的遗留支付模块。经理 A 说：“花两周写测试，再花四周重构。” 经理 B 说：“要为即将改变的代码写测试是浪费工作。先重构，然后只给新形状加测试。” 哪种顺序对，每种顺序会产生或避免什么具体失效模式？围绕一种会被一种方法抓住、另一种会放过的 bug 来组织答案。

提示

测试优先/重构其次的顺序先放安全网；先重构的顺序是信仰之跃。

**答：** 经理 A 对；经理 B 在犯最常见的重构错误。

**具体 bug 示例：** 假设遗留代码有一处用 `Decimal.quantize(ROUND_HALF_EVEN)`（银行家舍入）对税额做舍入，另一处用 `round()`（Python 内置，语言层面也是银行家舍入，但有浮点怪癖）。两者在 0.125 这类边界会产生不同结果：有时是 0.12，有时是 0.13。团队多年来对实际生产数据一直收费正确，因为两条代码路径恰好对实际金额达成一致。一次“为了一致性”的重构可能会把它们统一成一个舍入函数，但选错那个，就会悄悄地对未来 0.1% 的发票重新舍入。

如果先写测试（特征化），测试会锁定当前行为：对特定输入，当前输出是什么。重构后统一舍入函数会让这些测试失败，暴露出行为变化。团队必须显式决定接受新舍入、调整测试，并通知财务/业务。这就是安全网抓住的 bug。

如果先重构，测试是重构后加的。测试会断言*新*行为（你刚刚选择的那个舍入函数）。它们会通过。没有测试能对比重构前后；行为变化会被隐藏。几个月后生产数据出现边界发票时，才发现收费金额变了。

经理 B 的“浪费”论点 missed 测试是重构的安全网，不是重构后的文档。先重构再加测试无法检测重构引入的行为变化；它只能验证最终代码是否符合它自己。
