#### PR 层面的原子提交纪律

第 3 章的原子提交纪律适用于 PR 内部。一个 400 行 PR 拆成八个原子 commit，比一个 commit 同样 400 行更容易审查。审查者可以逐个 commit 阅读，增量构建理解。

Currents 的约定：超过 200 行的 PR 应有 3 到 10 个 commit，每个原子，commit message 遵循 Conventional Commits（第 4 章）。一个巨大 commit 或二十个 WIP commit 的 PR 会被打回要求 rebase。


### 16.2 物有所值的 PR 描述

PR 描述是审查者读到的东西。好描述让审查者高效完成剩余工作；差描述让他们兜圈子。


#### 好 PR 描述的组成

有用的 PR 描述包括：

* **What**：一句话概括变更。
* **Why**：动机；要解决的问题；ticket 或 ADR 链接。
* **How**：方法，简要。实现中任何非显而易见的点。
* **Testing**：测了什么，没测什么。若做了手工测试，什么场景。
* **Risk**：可能出错什么；回滚计划；是否在功能开关后。
* **Reviewer note**：作者希望审查者重点看的任何具体区域。

模板强制这些组件。Currents 使用 GitHub PR 模板：

    ## What
    <一句话>

    ## Why
    <动机；ticket 链接>

    ## How
    <方法；非显而易见的决定>

    ## Testing
    <测了什么>

    ## Risk
    <可能出错什么；回滚计划>

    ## Reviewer note
    <如有，具体关切区域>

模板不是官僚主义。它是强制作者思考审查者需求的机制。填写每个部分的纪律会揭示工作本身的缺口。


#### “Why”里该写什么

“Why”部分最重要，却常常最弱。弱的“Why”只说“实现 TRELLIS-1234”。强的“Why”解释底层动机：“EU 客户一直报告退款偏差 0.05；本 PR 调整 2021 schema 迁移前创建账户的舍入。复现见 TRELLIS-1234。”

审查者需要底层动机来评估变更是否解决了正确问题。仅给 ticket 号会迫使审查者切换到 ticket；PR 描述里的解释让审查者留在 PR。


#### AI 生成的描述

2026 年，AI 智能体常从 commit message 和 diff 生成 PR 描述。结构上通常正确（各 section 都填了），但“Why”有时肤浅（智能体不知道客户的底层动机）。作者的工作是即使 AI 生成其余部分，也要强化“Why”。

CLAUDE.md（第 22 章）可规定：“始终包含一个解释底层动机的‘Why’部分，而不仅仅是 ticket 引用。如果动机从对话中不清楚，开 PR 前先提示工程师提供。”


### 16.3 异步工程作为默认

跨三个时区的团队不可能主要同步；数学上不通。即使单一时区团队也受益于异步优先，因为同步沟通会打断深度工作。
