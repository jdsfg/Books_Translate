1. **抹去 2025 年的真实决策**：2025 年团队选择了 Drizzle（有理由）。当时这个决策在 2025 年的上下文下是*正确的*。抹去它就没有记录显示这个决策曾做过。
  2. **隐藏过渡**：读了修改后 ADR-003 的未来工程师会认为“我们一直用 Prisma”，这是假的。我们*为什么*从 Drizzle 迁移到 Prisma 的故事才是真正有趣的东西，而编辑把它毁了。
  3. **把“当前”和“正确”混为一谈**：经理把 ADR 当作代码（必须保持 current）。但 ADR 更像*会议记录*——对写下的时间点是正确的。

**正确做法**：写一份新 ADR（例如 2028 年的 ADR-127），标题为“从 Drizzle 迁移到 Prisma”，状态为 “Accepted (2028-04-15). Supersedes ADR-003.” Context 部分解释 2025 到 2028 年间*什么变了*，使 Drizzle 不再是正确选择（例如 Drizzle 的类型改进停滞而 Prisma 成熟；团队对 X 功能不满；新需求 Y）；Decision 写迁移；Consequences 列出迁移成本。ADR-003 用一行标记：“Supersedes by ADR-127。”不要编辑 ADR-003 正文。

未来读者从这条纪律中获得：

* 清晰历史：2025 年我们因 X 选择 Drizzle；2028 年因 Y 变化迁移到 Prisma。
* 从轨迹中学习：我们团队在什么条件下会换 ORM？哪些迁移成功、哪些失败？
* 对“我们一直这么做”思维的免疫：每个决策都有上下文和有效期；ADR 链显示两者。

一般规则：ADR 是 append-only。时效性通过写新 ADR 取代旧 ADR 实现，而不是编辑旧 ADR。把它们像 Git commit 一样对待：一旦落地，不可变；前进方式是更多 commit，而不是修改历史。

**Q3.** 哪些类型的文档容易腐烂，为什么？

提示

§17.6 的区分。

**答：** 实现细节散文容易腐烂，因为代码本身就是自己的文档；散文重复并漂移。教程腐烂，因为它们依赖特定环境，环境变化后失效。FAQ 腐烂，因为问题在演进。未采纳也从未归档的设计提案腐烂，因为代码库继续前进。

共同线索：与*会变化的细节*紧密耦合的文档，会以那些细节的速度腐烂。修复方式是要么删除文档（如果没人维护，删掉 FAQ），要么自动生成（从代码生成 API 参考）。

腐烂速度不同的文档：决策（推理持久）、操作（与操作同步维护）、定向（形状变化时更新）、契约（自动生成）。纪律是写持久类型，删除腐烂类型。

**Q4.** 为什么 runbook 的受众比其他文档更苛刻？

提示

runbook 什么时候被读？

**答：** Runbook 在压力下、非工作时间、由可能没有写它的工程师阅读。读者可能疲惫、半睡或 panic。Runbook 必须为这样的读者服务；要求读者具备新鲜、知识渊博、耐心的文档会失败。
