2026 年初，一位新工程师加入 Helix，向 Aki 询问团队文档。Aki 发了三个链接：仓库根目录的 README、Architecture Decision Records（ADR）文件夹、以及 on-call 轮值的 runbook。这位新工程师一周内就 productive。上一季度加入 Trellis 的一位新工程师收到的是大得多的一套文档：一个有数百页、一半过时的 wiki，一摞两年内没人读过的设计提案，以及一份写于 2020 年的 FAQ。Trellis 的工程师花了一个月才找到真正需要的文档。

差异不在数量。Trellis 的文档比 Helix 多。差异在*纪律*：哪些文档被维护、哪些被信任、哪些服务真实需求。能持久保鲜的文档是为特定持久目的写的；会腐烂的文档是为临时目的写的、没有维护计划。

本章讲真正有帮助的文档：README、ADR、RFC、runbook。每种都有目的；每种老化方式不同；每种都需要自己的纪律。第 18 章讲命名作为并行主题；两者合起来（第七部分）就是文档匠艺。


### 17.1 四种文档类型

大多数有用的工程文档可归为四类。这些类别在范围、受众、生命周期和更新节奏上不同。


#### 定义：四种文档类型

* **README**：给第一次来到仓库的人定向。说明项目是什么、如何设置、如何运行、在哪里找更多信息。
* **ADR（Architecture Decision Record）**：记录特定架构决策、其上下文和后果。写一次；很少更新；日后决策被质疑时引用。
* **RFC（Request for Comments）**：重大变更前的提案。讨论在 RFC 评论中进行；结果要么采纳（RFC 变成 ADR），要么拒绝（附上拒绝说明归档）。
* **Runbook**：生产场景的操作文档。说明如何调试、升级、缓解或从特定情况恢复。

其他文档类型（API 参考、教程、词汇表、FAQ）也有其位置；上面四种是工程核心。这四种维护得好，团队就拥有了大部分需要的东西。


#### 实践中每种的样貌

典型 Helix 仓库的文档：

* `README.md`：一页。项目是什么、三条运行命令、关键文件夹链接。
* `docs/adrs/`：编号文件。`001-pricing-rule-engine.md`、`002-tokio-vs-async-std.md`、`003-trunk-based-development.md`。每个几页。
* `docs/rfcs/`：形状类似，但用于提案；每个在几周内被移到 `adrs/`（带采纳说明）或 `archive/`（带拒绝说明）。
* `docs/runbooks/`：操作文档。`on-call.md`、`database-failover.md`、`deploy-rollback.md`。每个聚焦一个具体场景。

整个公司结构一致；工程师在团队间移动时能在预期位置找到文档。


### 17.2 README

README 是任何人读的第一份文档。它的任务是在十分钟或更短时间内让读者*定向*。
