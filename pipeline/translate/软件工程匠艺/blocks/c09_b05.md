#### 一个值得采取的立场：测试即规格就是 TDD，只是驱动力不同

2026 年流行把测试即规格描述成一种与 TDD 不同的“新”工作流。本书不同意。TDD 的核心纪律是*先写测试，然后写最少代码让它通过，再重构*。测试即规格是 red-green-refactor 循环，只是 green 步骤委托给智能体。人类仍然写测试（red），实现被产生来让它通过（green），人类再对返回结果重构（refactor；此处的“重构”通常指“要求智能体修改”）。结构保留；劳动转移。

说“测试即规格是 TDD 的继承者”比说“它是全新事物”更有用，因为它把这个工作流置于有三十年传统的已知失败模式和复利效应中。把测试即规格当作 2026 年发明的工程师，可能会从头重新推导 Beck 的教训。把它当作 TDD 应用于新驱动力的工程师，则继承这些教训。


#### 限制

测试即规格适合*测试*是正确规格的问题：纯函数、定义良好的转换、API 契约。它不太适合规格是视觉的、探索性的或涌现的问题。UI 工作、性能优化、数据探索通常不合适。

Aki 在 Helix 对大多数后端工作用测试即规格。对 UI 工作，团队用不同工作流：AI 从描述生成 UI 草稿；人类视觉迭代；测试后加。两种工作流都适合自己的语境。


### 8.6 为任务选择模式

诚实立场是：TDD、test-after、测试即规格是三种模式；工程师根据任务选择。粗略决策矩阵：

任务类型 | 推荐模式 | 理由  
---|---|---  
已知规格的纯函数 | TDD 或测试即规格 | 测试精确；循环快  
带微妙边界的算法 | TDD 或测试即规格 | Test-first 暴露边界情况  
API 契约实现 | 测试即规格 | 契约测试就是规格  
探索性数据工作 | Test-after | 测试会锁定会被扔掉的形状  
UI 工作 | Test-after | 视觉规格更难用测试表达  
性能优化 | Test-after | 优化就是工作；基准后加  
遗留代码重构 | Test-after（特征化） | 测试在重构前锁定当前行为  
Vendor SDK 包装 | Test-after | 规格随理解 SDK 而涌现  
有清晰复现的 bug 修复 | TDD | 测试复现 bug；修复让它通过  
标准 CRUD 端点 | 测试即规格或 test-after | 两者皆可  

这个矩阵是启发式；原则是*适合目的*。教条立场（“永远 TDD”或“TDD 已死”） missed 这一点；纪律是知道这些模式并明智选择。
