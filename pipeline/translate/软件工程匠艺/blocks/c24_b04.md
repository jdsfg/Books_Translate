**线索 B；`calculateRefund` 阶段 5：五年后（2031）**

我们在第 2、10、15、19 章跟踪的 `calculateRefund` 函数演化到 2031 年仍然存在。但它不再是单一函数。Helix billing 子系统五年间不断膨胀；函数内部三个不同关注点分歧到足以产生摩擦。2031 年的形状：

    # core/refund/validator.py
    class RefundValidator:
        def validate(self, order: Order, request: RefundRequest) -> ValidatedRefundRequest: ...
            # NaN 防护、退款状态检查、货币一致性、
            # 租户策略执行（2028 年多租户迁移时添加）。
    
    # core/refund/calculator.py  (pure)
    def compute_refund_amount(order: Order, validated: ValidatedRefundRequest,
                              rules: list[RefundRule]) -> RefundAmount: ...
        # 纯决策：金额 + 按比例 + 规则归因。
        # 用数千生成订单做基于属性的测试。
    
    # core/refund/persister.py
    class RefundPersister:
        def persist(self, order: Order, amount: RefundAmount) -> RefundResult: ...
            # 可序列化事务（2026 事故修复）。
            # 幂等键（2027 重试风暴事故后添加）。
            # 向审计总线发布事件（2029 年添加）。
    

这次拆分在五年内通过三份 ADR 完成，每次提取都有理由：

* **ADR-094（2027）**：提取 `RefundValidator`。理由：租户策略概念到来时，验证逻辑膨胀；把它与计算混在一起使两者都难以单独测试。
* **ADR-121（2028）**：把 `compute_refund_amount` 提取为纯函数。理由：退款数学的基于属性测试不断撞上 orchestrator 的 I/O 依赖；纯函数提取符合第 14 章 FC/IS 形状。
* **ADR-156（2029）**：提取 `RefundPersister`。理由：持久化步骤积累了三个关注点（2026 竞态条件修复、幂等性、审计事件），它们不属于计算。
