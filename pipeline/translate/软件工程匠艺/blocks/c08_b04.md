### 7.4 内存实现

最常见的 fake 形式是内存实现：把数据存在进程内存中的 Repository（或队列、缓存）。2026 年生态有丰富选择：

* **sqlite（内存模式）**：真实 SQL 引擎在内存中运行。大多数读写行为像 Postgres；在并发、advisory lock、全文搜索和一些 SQL 方言细节上不同。用于锻炼 SQL 的测试。
* **redis-memory-server**：进程内 Redis 兼容存储。用于锻炼 Redis 专用操作的测试。
* **fakes3 / minio**：内存或本地磁盘 S3 兼容存储，用于命中对象存储的测试。
* **手写的 InMemoryRepository**：用 dict 存储的 Python 或 TypeScript 类。用于你控制 Repository 接口且内存版足够简单时。

取舍在于*保真度*：更复杂的内存实现（sqlite、内存 Redis）能抓住更多生产 bug，但增加测试设置复杂度。手写 fake 抓的 bug 更少，但更简单。

合理默认：系统测试用 sqlite 或 redis-memory-server 锻炼存储层；单元测试用手写 InMemoryRepository 锻炼业务逻辑。两层各有位置。


### 7.5 Mock 何时伤人

值得识别的具体失效模式：


#### 过度规定的调用结构

测试里 `mock_repo.find.assert_called_with(1)` 和 `mock_repo.save.assert_called_once_with(...)` 把 repository 调用的精确顺序编码进去。改变顺序的重构（例如缓存 customer lookup）会让测试失败，即使结果行为没变。这就是本章开篇小插曲的具体形式。

修复：断言结果（用 fake 或 spy），而不是内部调用结构。


#### 偏离现实的 mock

Mock 规格在写测试时固定。真实依赖之后可能演化：新方法、返回类型改变、新增错误情况。Mock 不会自动更新；它继续按工程师写它时的想象行为。测试通过；生产失败。

修复：可行时用真实或 fake 实现；如果必须用 mock，定期用真实接口验证（有些工具支持契约测试）。


#### 撒谎的 mock

微妙但重要。Mock 对未显式 stub 的方法默认返回 `None`。生产代码调用 `customer_repo.find_by_region(region)` 并收到 `None`，可能把它理解为“该地区无客户”，而事实只是 mock 没给这个调用配 stub。测试通过；生产行为错误。

修复：用*严格* mock（未预期调用即失败），或用有真实默认行为的 fake。


### 7.6 AI 层：引导 LLM 远离过度 mock

2026 年 LLM 写测试时默认选 mock。模式很一致：测试需要 Repository 时 LLM 建 mock；需要下游服务时 LLM 建 mock；其实 stub/fake/spy/mock 都行时 LLM 仍选 mock。为什么？因为训练语料里教程代码占主导，教程用 mock，因为 mock 用五行就能演示；生产环境用 fake 的代码规模上更难找。
