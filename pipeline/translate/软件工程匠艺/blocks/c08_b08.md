**Q3.** 什么时候用 mock 合适？举一个你会有意选择 mock 而非 fake 的例子。

提示

§7.2 列表提到三类。

**答：** Mock 适合：

(a) 依赖不容易 fake。示例：一个内部行为复杂的 Stripe SDK。Mock 函数调用的具体方法（`stripe.Charge.create`）。

(b) 测试专门关注交互协议。示例：验证熔断器在三次连续失败后打开的测试。测试 mock 下游服务，配置它失败三次，然后断言熔断器状态在正确时刻改变。交互（重试几次后熔断器打开）就是被测行为。

(c) 行为就是协议本身，而非结果。示例：一个应该在 5xx 上重试、4xx 上不重试的重试 HTTP 客户端。测试 mock HTTP transport，配置它返回特定状态码，并验证重试行为。

每种情况下，调用结构都是测试的*主题*，而不是实现细节。因此把它编码进断言是合适的。

**Q4.** 一位 Staff 工程师反对你提出的在业务逻辑和 ORM（代码库用 SQLAlchemy）之间加 Repository 层的提案。他的论点：“SQLAlchemy 已经给了你面向对象、类型化的数据库 API。再包一层 Repository 只是多一层间接；正是第 13 章警告的模式税。我们是 3 人团队，代码库只有 6 个月；不需要这个。” 构造你的回应。对这个团队，他什么时候对、什么时候错？

提示

Repository 的价值取决于 (a) 测试痛苦程度，(b) 代码库寿命，(c) 存储迁移可能性，(d) 领域语言清晰度。

**答：** 他部分对、部分错；答案是“取决于他没衡量的维度。”

**他对的地方（暂时不必加）：**

* 3 人团队，6 个月代码库，没有存储迁移计划，业务逻辑只是薄薄的“存这个、取那个”。现在加 Repository 正是 §13.3 说的模式税：投机性灵活性，永远不会被用到。ORM-as-Repository 捷径在这里够用。先省下这工作。

**他错的地方（可能很快就要加）：**

* 如果测试套件已经痛苦（每个 `OrderService` 测试都需要 Docker 里的 Postgres，因为没法轻易替换数据库），这种痛苦会随着测试数量线性复利。Repository 加内存 fake 能让 100 个单元测试在毫秒级跑完而不是秒级；即使小团队，测试投资也会在一个季度内回本。
* 如果业务逻辑开始像 ORM 代码（`session.query(Subscriber).filter(...).filter(...).options(joinedload(...))` 出现在本应是领域逻辑的地方），代码库就把持久化泄漏进了业务逻辑。Repository 的*领域语言*收益与团队规模无关。

**具体测试：** 随机选一个服务层方法。你能用领域语言读懂它的目的（“X 地区的活跃订阅者”），还是需要翻译 ORM 习语？如果需要翻译，Repository 现在就值得。
