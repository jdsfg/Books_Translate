#### 机制

绞杀者无花果每个功能分三个阶段：

  1. **新实现与旧实现并存**：写新代码；旧代码仍激活。请求仍走旧路径。
  2. **重定向**：对已迁移功能的请求走新代码；旧代码不再是活动路径，但保留作为 fallback。
  3. **删除**：新代码稳定一段时间后（数周或数月），旧代码被删除。

对每个功能重复，直到旧系统为空。然后删除空壳。


#### 完整示例

Trellis 把 legacy 报表服务迁移到现代报表服务：

    初始状态：
      所有报表由 LegacyReportingService 提供。

    阶段 1（第 1–2 月）：
      构建 ModernReportingService。先在其中实现两张报表
      （Customer Activity 和 Revenue Summary）。Modern 服务已部署，
      但还没有流量路由到它。

    阶段 2（第 3 月）：
      Customer Activity 和 Revenue Summary 的流量路由到 Modern。
      其他报表仍由 Legacy 提供。

    阶段 3（第 4–6 月）：
      额外报表逐个迁移到 Modern，每次迁移后监控。

    阶段 4（第 7 月）：
      所有报表都由 Modern 提供。Legacy 代码路径已死亡。

    阶段 5（第 8 月）：
      删除 Legacy 代码。迁移完成。

每个阶段，旧系统都是安全网。如果新系统有 bug，团队回滚到旧系统。只有新系统经数周生产验证后，旧系统才删除。


#### 绞杀者无花果与大型重写有何不同

大型重写（第 21 章）构建完整新系统，然后一次性切换。风险：切换时新系统未经验证；切换后旧系统不可恢复；项目承诺数月甚至数年不发布。

绞杀者无花果相反：每个片段很小（一个报表的工作量）；旧系统在每个片段稳定前不会被移除；项目在整个迁移期间持续发布。

绞杀者无花果的成本是*共存开销*：迁移期间两个系统并存且需维护。成本真实但有界；替代方案（大型重写）有不同且通常更大的风险。


### 20.4 Branch by Abstraction

Branch by Abstraction 是 Paul Hammant 提出的另一种迁移模式。与绞杀者无花果的区别在于抽象层的位置。


#### 定义：Branch by Abstraction

Branch by Abstraction 在应用与其实现之间引入抽象层；旧实现满足抽象；新实现在同一抽象后构建；流量逐步路由到新实现；完成后删除旧实现（抽象本身也可能被移除）。

直白地说：抽出接口；旧代码实现它；新代码在同一接口后构建；逐个片段切换实现。
