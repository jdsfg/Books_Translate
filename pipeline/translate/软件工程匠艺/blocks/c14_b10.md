**场景 A**：使用**对 sum type 的模式匹配**。Python 3.10+ 有 `match` 语句；定义 `Shape = Union[Circle, Square, Triangle, Pentagon]`；每个操作是一个 `match shape:` 体的函数。没有 Visitor 类，没有 accept 方法。新增操作就是新增函数；静态分析时类型检查器会标出缺失分支（`mypy --strict` 或运行时 `case _:` 兜底）。Visitor 在这里只是把 1995 年 Java 代码逐字译成 Python——样板无益。

**场景 B**：使用**Visitor 模式**。Java 8 没有 sealed 层次的模式匹配；30 个节点类型让一长串 `if (node instanceof X)` 不可读。Visitor 的双分派是该语言下的地道做法：定义一个 `Visitor` 接口，每个节点类型一个方法；每种分析是一个 `Visitor` 实现。新增分析就是新增一个类；节点类型不用改。Visitor 模式在这里 earning its keep，原因与 1995 年相同：语言没有更好的替代。

**一般规则**：Visitor 的地位取决于语言。在有 sum type 模式匹配的语言里（Python 3.10+、带 discriminated unions 的 TypeScript、Rust enum、Scala/Kotlin sealed classes、现代 C# `switch` 表达式），它基本过时。在没有这些特性的语言里（Java 21 之前、旧 C++、纯 JavaScript），它仍是惯用选择。模式本身是合理的；变化的是周围工具链。优先使用语言的现代特性；只有语言没有现代特性时才退回到 Visitor。

**Q3.** 描述模式税反模式。为什么它在遗留代码库中延续？

提示

延续既有技术原因也有社会原因。

**答：** 模式税是为假设的灵活性而投机应用模式所带来的开销。常见形式：Abstract Factory Factory 层次、只有一个具体子类的抽象基类、只有一个实现的接口、泛化名称的类（`Handler`、`Manager`、`Processor`）。

延续原因：

* **技术**：每个模式税结构都是真实代码，有真实调用方。移除它需要理解所有调用方并重构。机械成本不低。
* **社会**：原作者可能还在团队；重构他们的作品可能像批评。模式税的分散成本（每个读者多年支付）不会归因于当初的决定。
* **复发**：训练于遗留模式的 AI 智能体可能重新引入；从旧教材学模式的工程师可能不把它们视为反模式。

解法是团队共识（CLAUDE.md、代码审查纪律）加上耐心的增量重构（每次一个模式税结构，在测试保护下）。

**Q4.** 本章为何主张“回顾性地应用模式，而不是前瞻性地应用”？

提示

预测灵活性的失败率是多少？

**答：** 前瞻性应用模式预测未来灵活性；预测常常错误。许多预期扩展永远不会来；模式开销提前并持续；预期灵活性的收益可能永远不会来。回顾性应用模式等到第二个具体案例证明灵活性真实存在；模式在有真实第二案例作证据时才引入。
