#### 概念检查

**Q1.** 你的团队处于三个决策阶段，你需要为每个建议合适的产物：

(a) Platform 和 Data 团队在争论未来 5 年是否标准化使用 Kafka 还是 RabbitMQ。六位工程师跨两个团队，各有意见；尚未决定。

(b) Platform 团队上周在一次 60 分钟会议中决定，Q3 前放弃对 legacy XML API 的支持。有些工程师没参加会议，未来几个月会反复问“为什么？”

(c) 一位工程师写了一个 12 行的 shell helper，从支持 ticket 获取客户数据。变量命名清晰。

为每个决定：ADR、RFC、代码注释、还是不需要文档。辩护。

提示

ADR = 带持久推理的已接受决策。RFC = 讨论中的提案。有些决策太小，两者都不需要。

**答：**

(a) **RFC。** 这是仍在讨论中的提案；团队尚未收敛。写 RFC（Context：当前状态、哪里 broken、为什么现在；Proposal：Kafka 或 RabbitMQ；Alternatives：各自的 case）；分发；收集异步评论；结果要么是 (i) 接受、RFC 变成状态为 “Accepted” 的 ADR，要么 (ii) 修改后重新 circulated，要么 (iii) 拒绝并附归档说明。没有 RFC，讨论会消失在聊天 thread 里，18 个月后有人问选择时找不到。

(b) **ADR。** 决策已做出；会议纪要已经蒸发；未来工程师会反复问“为什么放弃 XML 支持？”——一年多次。写 ADR-N（Context：谁在用 XML、流量占比、迁移成本；Decision：Q3 前放弃；Consequences：短期客户痛苦由长期维护节省抵消；Alternatives：保留 + 弃用 + 迁移，各自被拒理由）。ADR 一旦写成不可变；未来问题用链接回答。

(c) **不需要文档。** 一个 12 行、变量命名清晰的 shell helper *就是* 文档。ADR 会是文档的模式税：仪式性分层，没有真实读者收益。如果 helper 不显然，一个代码注释就够了。ADR 用于跨领域、有下游后果的决策，不用于“我写了个小 helper”的判断。

一般规则：当决策是架构性、跨领域、可能被重新质疑时，用 ADR。当决策仍在团队辩论中时，用 RFC。小局部决策用代码注释；琐碎的什么都不写。选择正确产物既避免记录琐事，也避免让重要决策无文档。
