#### 沼泽一：不是文本的巨大文件

你已经看到这个工具做得很好的所有事（共享未改变材料的快照、向你展示“用白话说到底改了什么”、合并两个版本）之所以能工作，是因为底下的东西是**文本。** 文本由行组成，而行可以比较：工具可以看到第 40 行变了，而第 1 行到第 39 行没有变，并且只存下差异。这就是为什么一篇论文的一千个快照组成的相册，不会占用一千倍空间。快照共享所有没有改变的东西。

一段两小时的婚礼视频不是这样工作的。一个包含一万张高分辨率照片的文件夹也不是，一个大型设计文件也不是。这些是**大型二进制文件**，不是由可比较的行组成，而是由巨大的数据块组成；改动一个小东西，就可能重写整个块。工具无法向你展示视频内部“用白话说到底改了什么”，因为那里没有文字；没有可比较的行。它也无法在快照之间便宜地共享未改变的部分，因为在工具看来，这个文件是一个不可分割的整块。给一个不断增长的视频项目做二十个快照，你最终可能会存下接近二十份完整的巨大文件。相册膨胀到无法使用。

所以：你的论文文本，可以。Rosa 的价格表和合同，可以。Maya 指南**里面**的照片，少量、小尺寸：没问题。一个严肃的视频项目、一个庞大的图片库、一文件夹巨大的 raw 设计文件？那就是错误的工具，把它硬塞到那里会产生一个缓慢、臃肿的相册，结果正好和你想要的相反。有专门为大型二进制资产做版本管理的工具；这不是其中之一。假装不是这样，正是人们因为 Git 没能胜任一份它从未声称过的工作而开始讨厌 Git 的方式。（Volume IV 以及之后会讲到，把大型文件**放在** Git 相册旁边、而不是塞进里面的诚实方法。现在，这条规则已经足够：文本和小东西放进相册；巨大二进制文件，不要。）
