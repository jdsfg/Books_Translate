### 15.4 Git 吃力的时候：大文件和错误工具

还有 2 个边缘，快速而诚实地说完，这样你知道工具在哪里结束。

**大型二进制文件。** Git 非常擅长文本：散文、代码、任何由行构成、可以逐字比较的东西。它不擅长大型非文本文件：长视频、巨大的图片文件夹、大型设计文件、原始数据集。它可以存储它们，但每个版本的存储方式多少有些笨拙，而充满沉重二进制文件的历史会变得臃肿缓慢。有专门的附加工具可以处理这些，你的智能体也知道它们；但地图层面的判断很简单：**如果你的项目主要是沉重媒体，单靠 Git 并不是这些文件的天然住所。** 把文本和小东西放进 Git；把巨大视频放到为巨大视频而建的地方，并让项目引用它。当你感觉相册变得迟钝而庞大时，那就是工具在告诉你它正在吃力，而安全请求是：**这个项目有一些非常大的文件；它们适合放进 Git 吗，还是应该住在别处？**

**当 Git 根本就是错误工具时。** 最清楚的例子，就是我们在上一章末尾见过的：**实时、同步的共同编辑**，也就是 2 个人在同一文档里同一时刻打字，并看见彼此的光标移动，这是 Google Docs 及同类工具的工作，不是 Git 的工作。Git 的模型是有意识的快照和经过审阅的改动，而不是实时按键。对于一本书或一份合同，这是优点，因为你**想要**改动是有意识、可审阅的。对于会议中在共享文档里头脑风暴，它就是错误形状。没有哪个工具更好；它们回答的是不同问题。判断力在于注意你实际提出的问题是哪一个。如果答案是“我们想现在就看见彼此打字”，就拿起实时编辑器。如果答案是“我们想要一段持久、可审阅的、有意识改动历史”，你已经知道该用哪个工具。

工具有边界并不丢人。技能在于知道边界在哪里，这样你既不会强迫 Git 做它不擅长的工作，也不会在它是世界上最擅长的工作上放弃它。

### 15.5 练习

这些是判断场景，是本章的核心。每一题都先想一想你实际会做什么，尤其是你会**对你的智能体说什么**，再去读讨论。这里没有需要答对的命令。有的是需要识别的时刻，以及一句需要准备好的话。

#### 概念检查

**Q1.** 用你自己的话说，为什么从今天的版本里删除一个私人细节，不足以把它从项目历史里移除？

提示

回想一下快照到底是什么。今天删除某个东西，会不会向后伸进上周那张照片？

**答案：** 因为历史是一串快照，而每个快照都是项目在**那个时刻**的一张完整照片。今天删除细节，会创建一张新的、干净的照片，但不会改变那些旧照片；旧照片仍然保存着那个细节当时的原样。历史按设计就是会记得；正是这种持久记忆，让你能恢复几周前删掉的工作。你不可能拥有一种既保存你的好工作、又悄悄忘掉你的错误的记忆。所以当前版本可以看起来完全干净，而上周的版本仍然显示一切。如果你真的需要从历史中移除，那是一个单独且更严肃的操作；如果泄露的是秘密，可靠的修复是把它视为已经泄露并更改它，而不是信任那次删除。
