#### 深入思考

**Q1.** “fork”这个词听起来有攻击性，而且偶尔它**确实**会被用于真正的分裂：一群人拿走一份副本，离开去做竞争版本。如果同一个工具既服务于“这里有一个友善的改进”，也服务于“我们要离开去竞争”，那它怎么还能成为本章所说的友善入口？真正区分慷慨 fork 和敌对 fork 的是什么？这种区别存在于工具本身吗？

**讨论：** 区别不在工具里，而这正是全部洞见。fork 在机械上只是一个完整的独立副本；无论这个人是想贡献还是想竞争，它都完全一样。不同的完全是**意图和接下来发生的事**，而这是任何工具都看不见的。慷慨的 fork 存在，是为了让拉取请求成为可能：副本是一张工作台，而当改进被提回时，循环就闭合了。敌对的 fork 则是故意打破这个循环：副本是一场离开，没有任何提案会回家。所以，同一个中立能力同时服务两者，就像一条路既服务来帮忙的邻居，也服务搬走的邻居。友善用法占绝大多数，是一个关于**人**的事实，不是关于 fork 的事实：大多数复制自己欣赏项目的人，是因为想回馈一些东西；而本章的礼仪（小的变更、清楚的为什么、尊重 拒绝）就是让友善解读保持为默认解读的共享文化。更深的教训贯穿整本书：工具是中立的，而中立是一种特性。一个只能被慷慨使用的工具，也会是一个在最糟糕时刻阻止你的工具。判断哪种用法是哪一种，应该由人来做；这也正是它该在的地方，并解释了为什么维护者说 拒绝 的权利、以及贡献者接受 拒绝 时的风度，比任何机制都更重要。开放形态靠礼貌维系，而不是靠机器维系。

#### 对你的 AI 这样说

加入你不断增长的白话请求集合（前面每一章的那些请求仍然适用），本章贡献了一个动作，让你可以改进陌生人的作品，而永远不会让它处于风险之中：

* **“拿走他们项目的一份我自己的副本，这样我可以添加一个小节，而不打扰他们的项目。”**（然后，当这一节准备好时，使用你已经从第 10 章认识的请求：“把它变成一个他们可以 审阅、确认后再进入的拟议变更。”）

这一句话退休掉了“真正的项目是给专家的”这种恐惧。你现在敢改进不属于你的作品（拿走自己的一份完整副本，平静地把它变好，再把它交回去），同时知道你无法伤害原项目，而且所有者仍然可以自由地说 同意 或 拒绝。陌生人的入口，现在也轮到你来走。
