### 10.2 四件事在同一个地方

下面是这位朋友打开她的拉取请求时实际创建的东西。它同时是四件事，而神奇之处在于它们共处一处。

**一个拟议更改。** 她不是在提问，也不是又提交了一条抱怨。她已经**做出**了修正：一个新版本的指南，移除了那家关门的咖啡馆，并建议用另一家仍在营业的店替代。这个提议是具体的。任何人都能准确看到，如果它被接受，指南会变成什么样。

**一个 diff。** 附在提议上的，是指南当前样子和她提议中的样子之间逐行精确的差异说明。不是用含糊的话说“我改了 Alfama 部分”，而是把具体的旧文字和具体的新文字并排放在一起。我们会用整个第 11 章来学习如何平静地阅读它；现在，先把它理解为**收据**，一份精确、可审阅、只说明发生了什么变化的记录。Maya 可以看到 Núria 只动了一个段落，顺手修正了一个零散的拼写错误，并让指南的其他每一页都保持不变。正是这种具体性，让审阅这件事成为可能。

**一场对话。** 拉取请求是一个可以交谈的地方，而且谈话与更改**待在一起**，不在另一个收件箱里。朋友写了一条说明：“我上周二路过那里，现在它变成手机维修店了。我放进了一家我很喜欢的地方——如果有更好的，随时替换。” Maya 可以就在这里回复。她可以就在这里提问，并把问题附在她正在询问的那一行上。等她们讨论完，整个讨论会永远存放在更改旁边，所以一年之后任何人都不仅能看到**改了什么**，还能看到**为什么**改，以及是谁同意的。

**一个决定。** 最后，悬在这一切之上的，是一道单一的门：某个对指南有权限的人必须说“是”。在 Maya 做出决定之前，拟议更改就只是拟议的。朋友的编辑待在自己的空间里，完整而等待着；真正的指南则继续保持原样。只有在 Maya 接受的那一刻，也只有那一刻，更改才会成为指南的一部分。

拟议更改、diff、对话、决定。四件事，一个对象，一个地方。把这四者拆开，你就回到那个痛苦的旧世界：建议在一个地方，编辑在另一个地方，决定默默做出。把它们合在一起，你就得到了一种新的东西。


#### 定义：拉取请求

> **拉取请求** 是对项目提出的拟议更改，它把这个更改会改动什么的精确说明、关于它的对话，以及是否接受它的决定，全都捆在一起并放在同一个地方。它让某个人完成一次更改的全部工作，并把它提交出来供人审阅，同时让项目所有者保留接受或拒绝的唯一权限。在接受发生之前，项目中的任何东西都不会改变。

注意，这个名字稍微有点侧着来理解，而看清原因会有帮助。提出更改的人，实际上是在请求项目所有者把他们拟议的工作 **pull** 进来，也就是伸手过去把它取走。这是一个请求别人来拉取的请求。这个名字描述的是从请求者一侧看到的交接时刻。有些工作坊把同一个对象称为“合并请求”，那是从所有者一侧来描述它：请求把更改合并进来。同一个对象，同一次握手的两个角度。不要让这个名字承担超过这点的重量。
