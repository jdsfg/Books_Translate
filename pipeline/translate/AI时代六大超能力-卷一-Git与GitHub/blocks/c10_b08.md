#### 应用题

**Q1.** 你的朋友在运营一个读书会，并把阅读日程放在一份共享文档里。一位成员注意到下个月的书列错了作者。描述两种处理方式：一种是“旧世界”的方式，另一种是“带有 issue 的工作坊”方式。第二种方式给了你什么，是第一种没有的？

提示

想一想在每种情况下，修正内容**住在哪里**，以及它是否可能丢失。再想想六个月以后。

**答案：**旧世界：那位成员用短信、邮件或群聊里的评论告诉组织者。此时，修正内容住在一个收件箱里，和日程分离；它的命运取决于组织者是否看到它、记得它，并在它被聊天记录冲走之前采取行动。工作坊方式：那位成员在日程本身上打开一个 **issue**，标题是“下个月的书作者列错了”，并在正文里写上正确姓名。现在，修正内容附在工作上，出现在未处理事项列表里，有时间戳，也不可能在聊天滚动中丢失。第二种方式给你的是：备注住在**工作所在的地方**，它有一个状态（在有人修好之前保持未处理），而且它留下记录。六个月后，你可以看到这个问题曾被提出、由谁提出，以及它是如何解决的。Issue 的重点不是形式感。重点是一个问题一旦被提出，就不会悄悄蒸发。

**Q2.** 在本章中，Núria 面对那家关门的咖啡馆时可以有两种回应：(a) 打开一个 issue，或 (b) 提出实际的替换段落。本章只让她做了 (a)。为什么即使可以直接提出修复方案，先打开一个 issue 仍然可能是**好做法**？

提示

谁拥有这份指南？是否要替换那家咖啡馆，以及用哪一家替换，是谁来决定？

**答案：**因为 issue 和修复是两个不同的动作，而把它们分开，是在尊重这个项目属于谁。Issue 说的是“这里有个问题”，并在任何人投入精力解决之前，先邀请一场对话。也许 Maya 已经知道那家咖啡馆关门了；也许她想完全删掉这个条目，而不是替换它；也许她心里有另一家更喜欢的咖啡馆。先打开 issue，可以让项目的所有者在一个具体修复方案摆上桌面之前，先决定**是否**修，以及**如何**修。这就像是在说“这里有个问题，你想怎么处理？”而不是“我已经重写了你的段落，要么接受，要么算了。”在你自己的项目里，你也许会直接跳到修复。可是在别人的项目里，先提出 issue 既实际（你避免把时间浪费在他们不想要的修复上），也礼貌（这是他们的指南；决定权在他们手里）。到了第 12 章和第 13 章，当提出修改的人是陌生人时，这个习惯会重要得多。
