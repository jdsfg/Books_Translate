### 6.3 编织之前：到底会改变什么？

这里就是判断层发挥价值的地方。Theo 准备把一次完整的重组带进主书。这不是一个小改动。在他说“可以”之前，他应该先问我们三个起飞前问题中的第一个，也就是我们在 Chapter 2 介绍过、并且会不断练习直到它变成本能的那个问题：

> **到底会改变什么？**

不是“它能不能用”；他已经知道重新排序之后读起来更好了。这个问题更窄，也更有用：当这个合并完成时，**主指南里具体会有什么不同？** 哪些章节会移动？有没有什么东西被删除，而那并不是他的本意？他周末做实验时，有没有悄悄改过某个自己已经忘掉的东西（一个说明文字、一个标题、一段散落的文字），现在会在没人注意的情况下跟着进入主书？

合并是一个大量改动一次性到来的时刻。这也正是小错误最容易藏起来的时刻，因为周围有太多合理的移动。所以这条纪律很简单，也没有商量余地：**在批准合并之前，你要先要求看看它会带来什么。** 不是之后。是之前。

在这本书的世界里，这就是一个对你的智能体提出的普通语言请求，也是你会建立的最有价值的习惯之一。你不是要求“运行合并”。你先要求：**在你执行之前，给我看看这个合并会把什么带进主版本。** 智能体会用普通话说明：这些章节重新排序了，这一段是新的，这个说明文字改了，没有任何东西被删除。你阅读它，就像阅读合作者提出的编辑摘要。只有在那之后，在你确实看过之后，你才说可以。

Theo 正是这样做的。他先要求查看改动。智能体给他看：如预期一样，街区顺序重排了；有一个他调整过但已经忘记的标题，这没问题；而且很重要的是，没有任何东西被删除。这和他认为自己做过的事一致。**现在** 他批准。合并完成，而且很干净，主指南也重组好了。Maya 信任的那个版本现在带上了 Theo 周末的工作，他们谁也没有丢东西。

这个习惯很小，小到几乎显得太明显，不值得命名。但它正是把冷静使用这些工具的人，和被工具烫伤的人区分开的习惯。被烫伤的人会批准他们没看过的合并，因为工具让这件事很容易，而改动看起来也很日常。地图不允许你跳过查看。**到底会改变什么？** 在说“可以”之前，把这个问题说出来，只花你十秒，却能比任何命令都多地挽救工作。
