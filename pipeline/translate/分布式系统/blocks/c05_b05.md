### 5.10 真实系统使用什么——工作流 3：同步 vs 异步复制追踪

> **工作流 3（输入 → 输出）** ：给定一个有 RPO / RTO / 每次写延迟约束的工作负载，产出匹配的复制配置。输出是按写法定人数成员选择（同步到 N 个副本？异步到所有？半同步到指定法定人数？）及运维后果（故障切换行为、恢复流程）。变体：PostgreSQL `synchronous_commit = remote_apply` 用于单数据中心 RPO=0；MySQL 半同步用于较低成本下的中等持久性；CockroachDB Raft-quorum 用于自动 RPO=0 且多区域容错。训练技能：按操作的 RPO 需求选择复制模式，而非按系统默认。

System | Default replication | Configuration options
---|---|---
PostgreSQL | Async（一个或多个副本） | `synchronous_commit = remote_apply` 实现按写同步
MySQL | Async | `rpl_semi_sync` 插件实现半同步
MongoDB（replica set）| Async to secondaries | `writeConcern: majority` 实现基于法定人数
CockroachDB | Raft-replicated（per-range）| 所有写都是 Raft-quorum（多数同步）
Spanner | Paxos-replicated（per-tablet）| 所有写都是 Paxos-quorum
Cassandra | Leaderless | 可调一致性：ONE、QUORUM、ALL
DynamoDB | Leaderless | 默认最终一致，可按请求强一致
Redis（master-replica）| Async | `WAIT N` 命令实现临时同步写
Aurora | 自定义存储层；写以 4-of-6 存储 quorum 确认 | 读副本最终一致
TiDB / YugabyteDB | Raft-replicated | 所有写都是 Raft-quorum

模式：现代分布式数据库（CockroachDB、Spanner、TiDB、YugabyteDB）让每个写都走 Raft 或 Paxos quorum，于是 read-after-write 窗口坍缩为“本会话已写的都有已知 HLC；本会话读尊重它”。代价是延迟，用来避免客户存款失败。

较老系统（PostgreSQL、MySQL、MongoDB）把同步作为可选项，默认异步。应用代码负责路由或等待。
