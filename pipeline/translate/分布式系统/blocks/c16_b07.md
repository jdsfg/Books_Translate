**答案：** LWW-Register 使用物理时钟（或 HLC）时间戳决定哪个值胜出。若两个副本并发写入，时钟 _更快_ 的副本胜出（无论哪个写逻辑上更晚），系统就会丢失 “逻辑上更晚” 的写。

问题与 Cassandra 的 LWW 冲突解决相同：依赖独立运行时钟的时间戳在偏移下会结构性丢失信息。

替代方案：

(a) **MV-Register（多值寄存器）** ：不选单一赢家，保留所有并发写。应用看到所有存活值（作为 siblings）并决定。不丢数据；冲突解决在应用层。

(b) **用 HLC 代替物理时钟** ：HLC（第3章）可减少但不能消除偏移问题。HLC 尊重 happens-before；因果有序的两写会被正确打时间戳。并发写仍按 HLC 平票规则排序（本质上是并发集合内的 LWW）。

(c) **领域特定 CRDT** ：不用寄存器，而用能表达应用语义的结构（如标签集合用 OR-Set，点赞数用计数器等）。

(d) **线性化寄存器** ：对 LWW 问题不可接受的字段，回退到每字段线性化实现（Cassandra 的 LWT，CockroachDB 的事务）。

选择：对 “最后更新胜出” 语义正确且时钟偏移有界的字段，LWW 可用。对冲突有意义的数据，用 MV 或领域特定 CRDT。对需要拒绝并发写的字段，线性化。

**Q4.** Yuki 的 Glide 编辑器使用 Yjs。为什么 RGA 是该用例的正确 list CRDT，Yjs 做到了早期 list CRDT 没做到什么？

提示

RGA：每个字符有前驱指针；树状。Yjs 针对顺序打字和小 bundle 大小优化。

**答案：** RGA（复制 Growable Array）把列表表示为图：每个字符有唯一 ID 和指向前驱（插入位置后的字符）的指针。列表顺序由该图的确定性遍历决定；并发插入按 ID 顺序解析。

RGA 适合协作文本编辑的原因：

* 插入是本地的（只记录前驱）；无需全局同步。
* 同一位置并发插入被确定性解析（编辑器永远不会看到 “合并冲突”）。
* 结构保持因果性：字符总插入在其前驱之后。

Yjs 的优化：

(a) **项 bundling** ：同一用户顺序输入的字符被捆绑成单个项；常见情况下结构紧凑。
(b) **WebAssembly 性能** ：合并操作用 Rust 编译为 WebAssembly，比纯 JS 快得多。
(c) **小 bundle 大小** ：Yjs ~80 KB，即使在慢网络下也足够小，适合浏览器。
(d) **垃圾回收** ：删除字符的 tombstone 最终在所有副本观察到删除后 GC。
(e) **持久化格式** ：高效的二进制格式存储和传输 CRDT 更新。

早期 list CRDT（Logoot、Treedoc、WOOT）存在问题：标识符增长、合并慢、内存占用大。Yjs 是首个对生产环境浏览器协作编辑来说足够快、足够小的实用 RGA 实现。
