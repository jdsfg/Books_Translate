两阶段提交模式：checkpoint 完成时，Flink 通知所有接收端提交已准备事务。若有接收端提交失败，checkpoint 无效，系统从上一个 checkpoint 重启。

结果：端到端意义上每个事件恰好处理一次。Checkpoint 定义 “事务边界”；一个 checkpoint 内所有内容要么整体提交（来源推进、接收端提交），要么整体回滚。

代价：checkpoint 延迟（事件到达与持久提交之间的时间）就是 checkpoint 间隔（通常 1-30 秒）。对需要更低端到端延迟的工作负载，这是权衡。

没有 Chandy-Lamport 风格快照，精确一次不可能：系统无法捕获重启的一致状态。该协议是状态流处理整个类别的基础。

**Q3.** 一个团队有全球多区域数据库（DynamoDB Global Tables）。他们发现偶尔从一个区域写入的数据在另一个区域看会 “消失”。诊断。

提示

DynamoDB 全局 Tables 跨区域按项做 LWW。不同区域对同一项并发写会导致一个被覆盖。

**答案：** DynamoDB 全局 Tables 跨区域按项使用 last-write-wins（LWW），时间戳由 AWS 时钟服务决定。当两个区域并发写入同一项（在时钟偏移窗口内），一个会胜出，另一个被丢弃。

从一个区域视角，它自己的写成功了（收到本地区域 ack）。当跨区域复制把另一区域的写（时间戳更晚）送来时，本地写被覆盖。该区域的用户看到自己的写 “消失”。

架构修复：

(a) **按区域分区** ：设计 schema，使每个项只被一个区域拥有。其他区域的写路由到拥有区域。没有跨区域并发写，就没有 LWW 冲突。

(b) **基于 CRDT 的字段** ：对多区域可能更新的字段（计数器、标签），使用并发更新能干净合并的数据结构。DynamoDB 原生不支持 CRDT；应用必须自己实现。

(c) **迁移到多主系统 + 无冲突语义** ：CockroachDB 的每表区域亲和多区域，或 Cassandra 上自定义每区域分区。

更深观察：DynamoDB 全局 Tables 对写少或自然按区域分区的工作负载（读重）很好。对多区域积极写同一项的工作负载不合适。系统文档说明了这点，但初始设计常被忽略。

对 Crescent：支付数据按用户归属区域分区，天然避免跨区域写冲突。São Paulo 用户总是写到南美区域；跨区域复制只用于灾备和分析，不是活跃多主写入。
