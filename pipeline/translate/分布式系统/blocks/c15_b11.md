第二个观察：LLM 的选择暴露了架构盲点。正确答案取决于理解工作负载的流量画像、一致性需求和成本权衡。不询问这些就给出答案的 LLM，是在生成一个看似合理但未参与设计问题的答案。诚实的 LLM 会回答：“告诉我吞吐、一致性需求和成本约束，我才会在 CRDT、最终一致或强一致中推荐。”


### 本章总结

最终一致性是许多工作负载（计数器、浏览追踪、配置传播）的正确答案，当强一致成本过高而短暂不一致成本很小时。纪律在于正确分类操作；现代系统支持按操作选择一致性。

五种会话保证（读己写、单调读、writes-follow-reads、单调写、一致的前缀）定义了完整线性化的有用每个会话弱化版本。CockroachDB、MongoDB、YugabyteDB 通过 HLC感知的会话跟踪提供它们。

Chandy-Lamport 分布式快照是在无全局时钟下捕获一致全局状态的基础原语。协议使用每条通道上的 marker 定义快照边界；记录的各进程状态加上在途消息形成一个可能真实发生过的状态。这是 Apache Flink 精确一次语义和类似分布式 checkpointing 系统的基础。

计数器 / 排行榜 / 库存工作负载展示了频谱：计数器（最终一致即可）、排行榜（需要因果一致）、库存（需要线性化）。应用工程师的任务是为每个操作选择正确的一致性。

第16章深入 CRDT：基于状态的 vs op-基于、典型类型（G-Counter、PN-Counter、OR-Set、LWW-Register）、2026 生产现实（Notion 和 Linear 中的 Yjs、Ink & Switch 项目中的 Automerge）。Yuki 的实例是 Glide 协作文档编辑器实现。
