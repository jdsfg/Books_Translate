#### 应用问题

**Q1.** 某团队分布式追踪显示：服务 A（50 ms）→ 服务 B（200 ms）→ 服务 C（40 ms）→ 服务 D（180 ms）。请求总延迟 470 ms。延迟预算 300 ms。诊断应把优化重点放在哪里。

提示

识别关键路径。B 和 D 是最大的贡献者。

**答案：** 关键路径是 A → B → C → D，串行，共 470 ms。

最大贡献者：

* 服务 B：200 ms（占总 42%）
* 服务 D：180 ms（占 38%）
* 服务 A：50 ms（11%）
* 服务 C：40 ms（8%）

优化优先级：

(a) **调查服务 B**：200 ms 是最大的单一跨度。B 在做什么？若是下游数据库查询，能否优化或缓存？若是复杂计算，能否批量、延迟或并行化？

(b) **调查服务 D**：180 ms 是第二大。同样问题。

(c) **考虑并行化**：若 A → B → C → D 当前是串行，能否把其中某些调用并行？例如，若 A 对 B 和 A 对 C 的调用独立，能否并行（总延迟变成 max(B,C) 而非 B + C）？

(d) **质疑是否所有跳转都必要**：4 个服务跳转对单个请求来说很多。能否通过反规范化数据、在上游嵌入逻辑或重构架构来消除某些跳转？

快速收益（单位努力最大杠杆）：

* 若 B 能降到 100 ms：总延迟降到 370 ms。
* 若 D 能降到 100 ms：总延迟降到 390 ms。
* 若两者都降：总延迟降到 290 ms（在预算内）。

并行化：若 A → (B、C 并行) → D，总为 50 + max(200,40) + 180 = 430 ms；只有边际改善。

重构：若 C 的工作能在 B 内完成（消除一跳），总为 50 + 200 + 180 = 430 ms（省 C 的 40 ms）。若 B 和 C 能合并成一个服务，节省的是跳开销，通常 10-20 ms。

更深观察：追踪是优化的输入。没有追踪，团队只能猜测哪里慢；有了追踪，他们知道。

**Q2.** 某团队追踪显示 1% 请求有以错误结束的跨度。调查发现 80% 这些错误来自一个特定下游服务。走一遍从追踪到修复的诊断流程。

提示

按服务分组错误；看错误属性（状态码、错误消息）；找模式（特定时间窗口、特定请求类型）。

**答案：** 诊断流程：

(a) **按服务分组错误**：80% 来自服务 X，是主导集群。聚焦那里。

(b) **检查错误属性**：错误码是什么？500 vs 503 vs 超时？每个暗示不同根因：

* 500：服务 X 逻辑缺陷。
* 503：服务 X 过载。
* 502/504：调用服务与 X 之间网关问题。
* 超时：X 挂起或慢。

(c) **看时间分布**：错误是否集中在特定时间窗口？若是，找相关事件（部署、流量尖峰、基础设施变更）。若不是，问题是持续性的。

(d) **检查请求属性**：失败请求是否针对特定租户、特定端点、特定输入模式？找输入相关性。

(e) **钻取一条失败追踪**：选一条失败追踪，看错误前的跨度。X 当时在做什么？它调用了什么？它调用的是否先失败？
