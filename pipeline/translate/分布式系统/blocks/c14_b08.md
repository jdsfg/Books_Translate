结构差异：

* **存储布局** ：NewSQL 使用行式存储（每行是逻辑单元）。OLAP 使用列式存储（每列是逻辑单元，允许聚合只扫描相关列）。
* **计算架构** ：NewSQL 拥有固定容量（始终在线节点）。OLAP 常是弹性计算（为查询启动工作节点，结束后释放）。
* **一致性** ：NewSQL 提供每个事务的 ACID。OLAP 常提供快照一致（查询看到查询开始时的一致视图，查询期间写入不反映）。
* **成本模型** ：NewSQL 按节点小时付费。OLAP 常按查询付费（或按扫描数据量）。

大多数生产架构两者都用：NewSQL 作为运营存储（记录系统）；OLAP 在衍生数据集（从运营存储 ETL 或 CDC）上做分析查询。

**Q4.** 对 2026 年构建支付处理器的 fintech 初创公司，你会推荐哪些数据系统？为每个给出理由。

提示

运营存储 + 账本 + 分析。对每种应用诊断方法。

**答案：** 三系统架构：

(a) **运营存储**：CockroachDB。理由：Postgres 兼容（团队熟悉）；多区域以支持全球服务；可串行化事务保证支付完整性；可跑在任何云上。曾考虑替代：Spanner（因 GCP 锁定被否）；Aurora DSQL（若仅限 AWS 可接受，但生产记录较新）；单区域 Postgres（因缺乏多区域灾备被否）。

(b) **账本**：TigerBeetle。理由：金融级正确性；极高吞吐；显式错误状态让审计和对账容易。账本与运营存储通过应用耦合：处理支付时，运营存储记录元数据，账本记录资金变动；两者必须提交（跨两系统的 saga 模式）。

(c) **分析**：Snowflake。理由：serverless 计算（分析工作负载突发）；强并发支持多团队（BI、财务、合规、ML）；时间旅行便于审计。数据通过 CDC 每晚从 CockroachDB 和 TigerBeetle 复制。

可选补充：

(d) **缓存**：Redis 集群用于热读路径（账户余额查询、幂等键检查）。多区域，各区域缓存。

(e) **队列**：Kafka 用于跨服务事件分发（通知、下游流水线）。

(f) **搜索**：Elasticsearch / OpenSearch 用于交易搜索（合规、客户支持、欺诈调查）。

架构分层：热路径（Redis + CockroachDB + TigerBeetle）处理每笔事务；温路径（Kafka + 下游服务）异步处理；冷路径（Snowflake）用于分析。每层都有适合其访问模式的正确系统。
