正确的 LLM 回应：“告诉我你的部署：Kubernetes？VM？混合？云？本地？你们团队目前用什么做编排？我可以根据匹配推荐 Kubernetes Services、Consul、AWS Cloud Map、etcd 或其他选项。”


### 本章总结

服务发现是 “服务 X 的哪些实例现在健康” 的注册表。2026 年标准解是 etcd、Consul 和基于 DNS 的发现（AWS Cloud Map 等云厂商服务）。etcd 主导云原生细分市场；Consul 处理 VM 和多 DC 部署；DNS 对稳定服务足够。

etcd 在新系统中基本替代 ZooKeeper，因为 Kubernetes 采用、Raft 与 ZAB 共识选择、gRPC API 和更好的云原生工具。ZooKeeper 仍在生产中使用（现有 Kafka、Hadoop 等），但缓慢衰退。

Config-as-data with watch streams 把服务发现推广到动态配置：feature flags、流量规则、限速、secret。模式（存在 etcd/Consul 中，watch 变更，动态重新配置）是 2026 年运行时配置的默认，不应要求服务重启。

服务网格（Istio、Linkerd）把服务发现与 mTLS、流量策略、可观测性打包。它适合多区域/多协议/复杂流量需求的团队；没有这些需求的团队则是过度工程。

Crescent 的发现使用四个分层系统：Kubernetes Services 用于区域内、etcd 用于领导者选举锁、Consul 用于跨区域网格、AWS Cloud Map 用于外部 API。每个处理自己的领域；跨领域交互明确。

第20章开始第七部分：运营分布式系统。分布式追踪与调试：因果保持、分区下采样、跨共识边界的 trace context。本章将该主题与可观测性工具（Series IV Vol 3）范围隔离，聚焦追踪支持的分布式系统推理。
