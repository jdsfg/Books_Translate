_vLLM_：

* 核心创新：PagedAttention（KV 缓存内存管理）。
* 优势：通用，多种工作负载下高吞吐。
* 最适合：任意服务、无特定前缀复用模式。

_SGLang_：

* 核心创新：RadixAttention（基于前缀的 KV 缓存复用）。
* 优势：对共享前缀工作负载节省巨大。
* 最适合：具有长共享系统提示、结构化输出、函数调用的工作负载。

各适合何时：

* **vLLM**：任意用户聊天机器人；混合工作负载 API；希望最广泛生产支持的团队。
* **SGLang**：客服机器人（系统提示跨百万请求重复）、代理框架（代理 scaffold 共享）、结构化输出应用（函数调用、JSON 生成）。

对 Tobias 的 Continuum 集群：答案取决于每客户工作负载。一些客户是任意聊天工作负载（vLLM 合适）；一些是重结构化输出工作负载（SGLang 合适）。Continuum 同时运行两者，按客户把工作负载路由到合适引擎。

决策很少是排他的 “vLLM 对 SGLang”；现代推理集群常同时运行两者，负载均衡器按工作负载把请求路由到最适合的引擎。

**Q4.** 什么是连续批处理？它如何提高 GPU 利用率？

提示

GPU 并行处理多个请求；请求持续加入和离开批次；批次间无空闲。

**答案：** 连续批处理：推理服务器保持一个活跃请求批次。GPU 每步为每个请求处理一个 token。请求完成（生成 EOS 或 hit length 限制）后离开批次；等待请求加入。批次持续补充；GPU 始终并行处理多个请求。

如何提高利用率：

(a) **批次间无空闲**。经典（static）批处理等 N 个请求，一起处理，等全部完成。GPU 在批次之间空闲（等待新请求）且在批次内空闲（等待慢请求完成）。

(b) **每个 token 吞吐优化**。每个 GPU 步为每个请求处理一个 token。批次大小 256、每步 50 ms，系统每秒生成 256 tokens / 50 ms = 5120 tokens。

(c) **可变请求长度优雅处理**。短请求（50 token）和长请求（5000 token）可在同一 continuous 批次中运行。短请求 50 步后离开；长请求继续。静态批处理会让短请求等待长请求。

结果：相比朴素服务吞吐提升 2-5 倍。连续批处理现在是生产推理引擎默认（vLLM、SGLang、TGI 等）。

实现复杂度在于动态批次管理：跟踪每个请求状态、处理加入/离开事件、跨批次管理 KV 缓存。复杂度值得吞吐收益。
