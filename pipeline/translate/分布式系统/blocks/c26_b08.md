#### 应用问题

**Q1.** Tobias 的集群现已分离且分布式 speculative。一位新客户 workload 有 5000-token system prompt。走一遍适用的路由优化。

提示

KV-cache-aware 路由处理 system prompt；针对该客户前缀。

**答案：** 该客户工作负载：每个请求以相同 5000-token system prompt 开头；每请求 prompt 短（可能 50 token）；输出中等（200-500 token）。

路由优化：

(a) **Prefix-aware 路由（KV cache locality）**：负载均衡器识别 5000-token system prompt。第一个请求后，该前缀缓存在某节点。该客户后续请求被路由到同一节点（或有缓存的节点）。

收益：5000-token prefill 只付一次（第一个请求）。后续请求跳过前缀 prefill；只 prefill 每请求 prompt（50 token）。Prefill 成本每请求降低约 100 倍。

(b) **缓存层复制**：若该客户流量高（如 100 rps），单节点缓存无法服务所有。缓存层（Mooncake/LMCache，第25章）保存前缀；多个 decode 节点从缓存读取。

(c) **长度预测路由**：中等输出请求（200-500 token）去能支持约 10 秒 decode 的节点。避免放在应快速释放的 burst 节点。

(d) **Speculative decoding**：中等输出 decode 受益于 speculative decoding。2 倍吞吐提升下，每请求 decode 时间从约 10 秒降到约 5 秒。

(e) **客户 SLA 调度**：该客户是 tier-2（中优先级）。Weighted fair scheduling 确保其请求被处理但不饿死 tier-1 客户。

综合：该客户每请求成本降低约 5 倍（前缀复用），延迟显著改善。Continuum 能给出有竞争力的 per-request 定价；客户对延迟满意。

对 Tobias：这正是这些优化针对的场景。客户 onboarding 从第一天起就盈利；优化让 Continuum 能与 Anyscale、Together 等竞争。

**Q2.** 某团队推理集群尾部延迟高（p50=2 秒，p99=30 秒）。诊断并提出修复。

提示

尾部延迟来自长请求阻塞、无长度预测路由、长请求 GPU 竞争、speculative decoding 有帮助。

**答案：** 诊断：p99/p50 比 15:1 表明严重尾部延迟。可能原因：

(a) **长输出请求阻塞短请求**：单个 5000-token 输出请求阻塞 GPU decode 容量。其他请求的尾部 token 等待。Continuous batching 有帮助但不能完全消除。

(b) **Prompt 长度可变**：50000-token prefill 需 10 秒以上；同节点其他请求等待它完成。Disaggregation（分离 prefill 节点）修复此问题。

(c) **GPU 竞争**：若多请求竞争同节点 GPU 内存带宽，最慢者拖累尾部。

(d) **网络抖动或瞬态故障**：需要重试的请求更慢；若重试无预算，尾部可延长。

修复：

(a) **Disaggregated prefill/decode**（第25章）：若未就位，解决 prefill 阻塞 decode 问题。长 prefill 请求隔离在 prefill 节点；decode 不受影响。
