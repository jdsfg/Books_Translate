#### 三层审查架构

Crescent 团队对 AI 生成分布式代码使用三层审查：

**第一层 —— 自动 AI 审查（秒级，每次 push 运行）**：

* 使用 Greptile 或 CodeRabbit 类服务做 pre-PR 检查。
* 检查清单的语法项：timeout、retry-budget 注解、idempotency-键参数使用、排序原语使用。
* 输出：diff 上的自动批注列表；约 80% 准确；约 20% 是 false positive，作者用一行理由 dismiss。

**第二层 —— 人类按清单审查（分钟级，每个分布式 PR）**：

* 受过六个谎言训练的人类审查者打开 PR。
* AI 批注已在 diff 中；人类阅读并决定哪些要处理。
* 人类应用 AI 无法做的上下文判断：哪把锁用于正确性、哪个不变量必须成立、哪个设计选择正确。
* 人类用显式短语 “checklist reviewed” 签批。

**第三层 —— 混沌验证（小时级，发布前运行）**：

* 任何新分布式特性发布前，混沌演练日（第23章）演练该特性声称的防御。
* 演练日验证防御 _有效_，而非仅存在于代码中。
* 这是静态审查的经验补充。
* 成熟度映射：第三层对应第23章 §23.7 的混沌工程成熟度 Level 2-3（预定的演练日和持续自动混沌）。良好运行第三层的团队至少处于 Level 2；达到 Level 3 意味着混沌节奏是持续而非仅在发布前。Level 4（混沌发现作为设计输入）是愿景：AI 审查 → 人类审查 → 混沌验证循环闭合；演练日发现反馈为 AI 审查者的新模式，以便在未来 PR 中标记。

第三层纪律具体：演练日必须注入 AI + 人类审查声称要防御的具体故障模式。若人类审查者写 “circuit breaker 防止下游变慢”，演练日必须包含下游变慢场景。若审查者写 “saga 补偿处理第 4 步失败”，演练日必须在第 4 步中点 crash worker。审查的主张成为演练日的测试计划。

这是与第23章运维紧密连接的地方：审查记录一份声明防御列表；演练日是 falsify（或确认）每个声明的实验。审查者声称但演练日未演练的防御不是已验证防御；只是愿景。在 Crescent 流程中，每个新分布式代码 PR 附带 “演练日 test plan” 附录，逐条列出声明的防御；下一次月度演练日包含这些场景。

具体例子：Olamide 团队合并了一个为新的 partner-onboarding 工作流添加 saga 的 PR。人类审查者评论说：“已验证——步骤 2-5 的 saga 补偿已定义；orchestrator 状态经 Raft 复制；步骤 4（外部 partner API）有 0.1 重试预算和 50% 失败率熔断器。” 下一次演练日计划：(a) 在步骤 3 中点 crash orchestrator，验证新 orchestrator 正确恢复；(b) 让 partner API 返回 50% 错误，验证熔断器打开；(c) 在第 4 步重试期间注入网络分区，验证预算限制放大。每个场景 1:1 映射审查声明。
