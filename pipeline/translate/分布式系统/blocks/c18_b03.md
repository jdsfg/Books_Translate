#### Martin Kleppmann 的批评

2016 年，Martin Kleppmann 发表《How to do distributed locking》，批评 Redlock 并解释它为何没有提供表面上的安全性质。该文是分布式锁的奠基性读物。

核心问题：分布式锁有 _两个_ 常被混淆的目的。

(a) **效率**：同一时间只有一个客户端做昂贵工作。若两个同时做，工作重复但无损害。示例：job queue 中每个任务应由一个 worker 处理。

(b) **正确性**：同一时间只有一个客户端修改受保护资源。若两个同时做，资源损坏。示例：支付提交，两个并发提交导致重复扣款。

Redlock 对效率场景提供合理保证。对正确性场景则不提供保证，原因有二：

(a) **进程暂停**。客户端获得锁后经历长时间 stop-the-world 暂停（垃圾回收、虚拟机暂停）。锁 TTL 过期。另一个客户端获得锁。原客户端恢复，未意识到锁已过期，继续修改资源。

(b) **时钟漂移**。Redlock 的安全分析假设时钟大致同步。若客户端时钟偏快，其锁 TTL 从 Redis 侧看更早过期。两个客户端可能同时认为自己持有锁。

修复方案：_fencing token_。


#### Fencing tokens

Fencing token 是由锁服务分配的单调递增计数器。每次获得锁得到一个最新 token（比之前任何已发 token 高）。该 token 伴随对受保护资源的每个操作。

受保护资源（存储系统、API 端点）跟踪已接受的最高 token。任何带更低 token 的操作被拒绝。

如何修复 Redlock 的失败模式：

(a) 进程暂停：客户端 A 用 token 100 获得锁；暂停 60 秒（TTL 过期）；客户端 B 用 token 101 获得锁（锁服务单调递增）。A 恢复后发送 “token 100 写”，存储拒绝（101 > 100）。锁服务视角已 “释放锁”；存储视角一致。

(b) 时钟漂移：token 逻辑不涉及时钟。锁服务计数器是权威。即使客户端对时间看法 wildly 不同，资源的 “最高已见 token” 提供正确排序。

代价：受保护资源必须实现 fencing-token 逻辑。并非所有系统原生支持；例如 Redis 本身不支持每键 fencing token。应用必须在其上叠加。


#### 常见误解

常见误读：“Redlock 错了；不要用。” 这过于绝对。Redlock 对 _正确性用例_ 是错的；对 _效率用例_ 可以。区别很重要：

* Job queue：用 Redlock（或任何 best-effort 锁）。最坏情况：一个任务被处理两次，浪费但不灾难。
* Payment commit：用 fencing token。不用的话最坏情况：重复扣款，灾难。

正确的分布式锁库用 Raft（或等价共识）管理锁状态，并在受保护资源上执行 fencing token。etcd 的锁原语、Consul 的基于 session 的锁、ZooKeeper 的 sequence-node 锁都提供这种结构。
