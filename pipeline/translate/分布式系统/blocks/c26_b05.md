#### 概念检测

**Q1.** 为什么 LLM 请求路由比 Web 请求路由更重要？

提示

LLM 请求耗时秒级 vs 毫秒级；路由决策后果更大。

**答案：** LLM 请求通常耗时 1-30 秒（取决于提示长度和输出长度）；Web 请求通常 10-50 ms。错误路由决策的成本相应大得多。

具体 LLM 路由机会：

(a) **KV 缓存局部性**：若某节点已缓存提示前缀，路由到该节点节省预填充成本。路由别处浪费缓存。每次请求可节省数百毫秒。

(b) **长度预测**：长输出请求应去有持续解码容量的节点。把长请求集中到少数节点可防止其他节点尾部延迟放大。

(c) **模型可用性**：集群服务多个模型；路由必须考虑哪些节点加载了哪些模型。把模型 A 请求路由到只服务模型 B 的节点需要模型 swap（慢）或拒绝。

(d) **尾部延迟**：LLM 尾部延迟比 Web 宽得多。错误路由决策可导致用户等待 30 秒尾部；Web 等价是 100 ms 延迟。影响数量级不同。

现代推理平台（Anyscale、Together、Fireworks）已构建显式考虑这些因素的路由优化器。朴素轮询或 least-loaded 路由遗留显著性能。

对 Continuum 集群：从朴素路由切换到 KV缓存感知加长度预测路由，吞吐提升约 25%，p99 延迟降低约 30%。改动是算法级（无硬件改动）；收益巨大。

**Q2.** 描述投机解码。它如何加速生成？

提示

小草稿模型提出 K 个 token；大验证模型检查；接受前缀输出；每 “验证步” K 个 token。

**答案：** 投机解码使用两个模型：小 “草稿” 模型和大 “验证” 模型。

每解码步流程：

(a) 草稿模型生成 K 个候选 token（通常 K=4-8）。草稿很快：小模型毫秒级。

(b) 验证模型并行处理 K 个候选（一个验证步一起处理 K 个 token）。这与正常解码步成本大致相同。

(c) 验证模型检查 K 个候选中与其自身预测匹配的前缀。匹配前缀被接受；第一个不匹配被替换为验证模型的选择。

(d) 被接受前缀（1 到 K 个 token）输出。解码前进。

为何加速生成：

* 正常解码：产生 K 个 token 需要 K 步；每步都是完整验证模型前向传播。
* 投机解码：1 个草稿步（快）+ 1 个验证步（并行处理 K）产生（接受率 × K）个 token。

若接受率 80%，验证模型每验证步产出约 0.8 × K = 6.4 个 token，而非 1 个。在验证模型层面吞吐约 5-6 倍。净吞吐提升：2-3 倍（扣除草稿模型成本后）。

接受率取决于草稿模型近似验证模型的程度。精选草稿模型（同架构小版本、从验证模型蒸馏）可达 70-90% 接受率。
