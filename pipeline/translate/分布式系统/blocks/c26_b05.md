#### 概念检测

**Q1.** 为什么 LLM 请求路由比 Web 请求路由更重要？

提示

LLM 请求耗时秒级 vs 毫秒级；路由决策后果更大。

**答案：** LLM 请求通常耗时 1-30 秒（取决于 prompt 长度和输出长度）；Web 请求通常 10-50 ms。错误路由决策的成本相应大得多。

具体 LLM 路由机会：

(a) **KV cache locality**：若某节点已缓存 prompt 前缀，路由到该节点节省 prefill 成本。路由别处浪费缓存。每次请求可节省数百毫秒。

(b) **长度预测**：长输出请求应去有持续 decode 容量的节点。把长请求集中到少数节点可防止其他节点尾部延迟放大。

(c) **模型可用性**：集群服务多个模型；路由必须考虑哪些节点加载了哪些模型。把 model A 请求路由到只服务 model B 的节点需要 model swap（慢）或拒绝。

(d) **尾部延迟**：LLM 尾部延迟比 Web 宽得多。错误路由决策可导致用户等待 30 秒尾部；Web 等价是 100 ms 延迟。影响数量级不同。

现代推理平台（Anyscale、Together、Fireworks）已构建显式考虑这些因素的路由优化器。朴素 round-robin 或 least-loaded 路由遗留显著性能。

对 Continuum 集群：从朴素路由切换到 KV-cache-aware 加长度预测路由，吞吐提升约 25%，p99 延迟降低约 30%。改动是算法级（无硬件改动）；收益巨大。

**Q2.** 描述 speculative decoding。它如何加速生成？

提示

小 draft model 提出 K 个 token；大 verify model 检查；接受前缀输出；每 “verify 步” K 个 token。

**答案：** Speculative decoding 使用两个模型：小 “draft” 模型和大 “verify” 模型。

每 decode 步流程：

(a) Draft model 生成 K 个候选 token（通常 K=4-8）。Draft 很快：小模型毫秒级。

(b) Verify model 并行处理 K 个候选（一个 verify 步一起处理 K 个 token）。这与正常 decode 步成本大致相同。

(c) Verify model 检查 K 个候选中与其自身预测匹配的前缀。匹配前缀被接受；第一个不匹配被替换为 verify model 的选择。

(d) 被接受前缀（1 到 K 个 token）输出。解码前进。

为何加速生成：

* 正常 decode：产生 K 个 token 需要 K 步；每步都是完整 verify model 前向传播。
* Speculative decode：1 个 draft 步（快）+ 1 个 verify 步（并行处理 K）产生（接受率 × K）个 token。

若接受率 80%，verify model 每 verify 步产出约 0.8 × K = 6.4 个 token，而非 1 个。在 verify model 层面吞吐约 5-6 倍。净吞吐提升：2-3 倍（扣除 draft model 成本后）。

接受率取决于 draft model 近似 verify model 的程度。精选 draft model（同架构小版本、从 verify model 蒸馏）可达 70-90% 接受率。
