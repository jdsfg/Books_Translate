这 25 行代码中的六个谎言：

  1. **谎言 1（RPC 语义）**：`bank_service.transfer(payment)` 没有幂等键。若超时重试，银行可能转账两次。

  2. **谎言 2（网络可靠）**：任何网络调用（银行、数据库、通知、ledger）都没有超时。一个慢调用挂起整个函数。

  3. **谎言 3（时钟）**：`ledger_service.record(payment.id, time.time())` 使用本机时钟时间戳。跨区域 ledger 排序依赖机器时钟。

  4. **谎言 4（锁）**：基于 Redis 的锁没有围栏 token。在 GC 暂停或分区下，两个协调器可能同时持有锁；两者都能处理同一笔支付。

  5. **谎言 5（部分故障）**：四个顺序调用（银行、数据库、通知、ledger）没有回滚。若银行成功后数据库失败，用户已在银行扣款但 DB 未扣；后续重试会重复扣款。

  6. **谎言 6（CAP 简单）**：注释 “CockroachDB is CP for 一致性” 暗示读是线性化的；没有显式 `WITH (LINEARIZABLE)` 或类似，读可能来自有旧数据的跟随者。

Olamide 的审查反馈：“拒绝。这段代码包含线程 C 全部六个谎言。具体：bank_service.transfer 缺少幂等键（谎言 1）；任何网络调用都没有超时（谎言 2）；ledger 用 time.time() 排序（谎言 3）；Redlock 无围栏 token（谎言 4）；四步操作没有事务/saga（谎言 5）；在误导性 CP 注释下读一致性模糊（谎言 6）。请用团队设计文档的纪律重新设计；不要提交未应用检查清单的 AI 生成分布式代码。”

30 行审查可行，因为每个谎言都可凭检查识别。受过六个谎言训练的审查者几分钟内捕获；未受训练的审查者会批准 PR，然后在生产中发现缺陷。

**Q2.** 一个团队正在推广 AI 辅助代码生成。他们想保持分布式代码质量。提出一个政策。

提示

政策组成：培训、清单审查、分布式代码配对审查、混沌测试、监控。

**答案：** 政策：

(a) **培训**：每个审查分布式代码的工程师必须完成六个谎言课程。课程覆盖模式、故障模式和修复。时长：8-16 小时。

(b) **清单审查**：每个触及分布式代码（任何含网络调用、复制、共识、排序的代码）的 PR 必须按 10 项清单审查。审查者在 PR 中记录清单结果。

(c) **AI 辅助 PR 配对审查**：被标记为 “AI 辅助” 的 PR 需要两名工程师审查，至少一名是资深分布式系统工程师。配对 Explicitly 走一遍六个谎言。

(d) **测试要求**：分布式代码必须包含混沌测试（第23章），演练清单处理的故障模式。没有混沌测试的分布式代码 PR 被拒绝。

(e) **监控要求**：每个分布式操作必须可观测。没有指标、日志、追踪的操作 PR 被拒绝。

(f) **周期性审计**：高级工程师每季度审计已合并分布式代码 PR 样本。发现与团队共享；模式级问题导致额外培训。

(g) **发布前缺陷清理**：任何新分布式特性发布前进行混沌演练日（第23章）。演练日演练该特性声称的防御。

(h) **事后复盘**：任何涉及分布式代码的事故，事后复盘识别六个谎言中哪些在起作用。修复纳入适当防御；团队培训更新。

(i) **AI 辅助预算**：分布式代码允许但限制 AI 辅助。团队 “AI 辅助代码” 合并提交比例 capped（如 30%）。超过上限，团队被迫回到人工编写代码。

(j) **文档**：团队维护一份活的谎言、清单和实例文档。新员工必读。

该政策对分布式代码较重，因为错误分布式代码的成本高（数据污染、中断、客户影响）。对非分布式代码（UI、简单 CRUD 等），较轻政策即可。

对 Crescent：Olamide 在第1章原始重复扣款事故后起草了类似政策。三年后，团队已内化纪律；AI 辅助 PR 按清单审查；混沌测试是标准；生产中新分布式代码缺陷罕见。
