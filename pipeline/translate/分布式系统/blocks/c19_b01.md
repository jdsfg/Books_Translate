Olamide 的微服务舰队跨三个区域运行 47 个服务。每个服务有 3-12 个实例。实例来来去去（部署、自动扩缩、故障）。每天都反复出现的问题：服务 A 如何知道服务 B 的实例在哪里？

这就是服务发现问题。2026 年的答案是 etcd、Consul 或云厂商 DNS。本章讲授发现问题、标准解，以及更广泛的 “config as data with watch streams” 模式。


### 19.1 发现问题

服务网格有若干实例。实例：

* 启动并变为可用。
* 监听特定端口。
* 有时崩溃或被编排器 kill。
* 在节点间迁移（容器移动）。
* 基于负载上下扩。

客户端服务需要调用目标服务的任意健康实例。客户端不控制目标部署；它必须动态发现实例。

发现流程：

  1. 每个实例启动时向发现服务注册自己。
  2. 实例周期性 heartbeat 以确认健康。
  3. 发现服务跟踪健康实例集合。
  4. 客户端查询发现服务找到实例。
  5. 实例失败（无 heartbeat）时从集合移除。

发现服务本身是分布式系统；它有自己的共识、复制和失败模式。2026 年选择：etcd、Consul 或基于 DNS 的发现（云厂商服务发现）。


### 19.2 etcd

etcd 是 Kubernetes 控制平面使用的开源分布式键值存储。它是服务发现级别系统的现代参考设计。

关键性质：

* 基于 Raft（第9章）实现共识。
* 键值 API 提供线性化读写。
* Watch streams：客户端可订阅 key 变更并接收通知。
* Leases：key 可设 TTL；不续期则自动过期。
* Transactions：多键原子操作。

服务发现用法：

* 每个服务实例写入一个 key（如 `/services/payment/instance-uuid`），包含地址和元数据。
* key 带 lease（如 30 秒）；实例每 10 秒续期。
* 若实例未续期（崩溃、分区），key 过期并被删除。
* 客户端 watch `/services/payment/` 前缀；实例变更时收到通知。

模式很干净：发现服务无需知道具体服务类型；它提供通用键值存储加 lease 与 watch 原语。应用使用这些原语。
