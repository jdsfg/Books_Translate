教训泛化：2026 年，对横切关注点（tracing、metrics、logging、configuration）的正确答案通常是 “用开放标准”（OpenTelemetry、Prometheus、structured logging、基于环境的 config）。Vendor lock-in 是真实且可避免的成本；忽略这点的 LLM 生成代码会让团队失去迁移能力。


### 本章总结

分布式追踪是请求在微服务系统中路径的取证记录。Trace 是跨度树；每个跨度代表一个工作单元；树通过 trace 和 parent-跨度 ID 组装。

三个分布式系统特有关注点：因果保持（跨服务边界传播上下文）、分区下采样（基于头部的 vs 基于尾部的）、跨共识边界的追踪上下文（Raft、Kafka 等）。

OpenTelemetry 是 2026 年事实标准：每种主流语言都有 vendor-neutral API、常见库自动仪器、可导出到任意后端。采用 OpenTelemetry 避免 vendor lock-in 并提供生态契合。

Traces 是强大的调试工具但不是唯一工具。Traces 展示跨服务发生了什么；profiling 展示服务内部发生了什么；metrics 展示资源和速率行为；logs 展示 per-event 叙事。成熟运维团队会关联这四者。

取证 trace（支付 trace、安全事件 trace、客户投诉 trace）是特殊的：对特定操作类型 100% 采样、保存数年、按客户或交易 ID 索引。它们是系统永久记录的一部分，不只是可观测性 artifact。
