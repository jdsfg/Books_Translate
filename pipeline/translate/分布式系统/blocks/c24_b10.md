#### 深入思考

**Q1.** 辩护或反驳：“分布式 LLM 推理只是把 LLM 作为负载的分布式系统。通用分布式系统模式适用；不需要新理论。”

**讨论：** 辩护：分布式系统理论（共识、复制、分片、负载均衡）适用于推理。KV 缓存 sharding 就是分片；推理节点间负载均衡就是负载均衡；故障转移就是故障转移。通用模式足够。

反驳：推理有结构属性（每个 token 延迟预算、两阶段计算、GPU 作为单元、KV 缓存作为状态），通用分布式系统不会为之优化。专用协议（PagedAttention、RadixAttention、分离式预填充/解码）是新贡献；它们并非明显派生自通用分布式系统理论。

综合：分布式 LLM 推理是面向 LLM 负载的分布式系统 _专门化_。通用模式适用高层次；推理专用优化适用低层次。2026 年推理工程师需要两者：通用分布式系统知识加推理专用技术。

第二个考虑：推理领域快速演进。2025-2026 突破（disaggregation、KV 缓存 sharding、投机解码 as 分布式的协议）是近期；2027-2030 还会有进展。把推理当作 “只是分布式系统” 的工程师会错过领域实际进展。把它当作子学科（有自己的会议、库、最佳实践）才是正确框架。

**Q2.** 一个 LLM 被要求 “为我们的 Llama 3 70B 搭建推理集群”。它产出使用基础 Hugging Face TextGenerationInference（TGI）部署的代码。指出 LLM 遗漏什么，2026 年生产部署包含什么。

**讨论：** LLM 的基础 TGI 部署是起点，但遗漏许多 2026 生产特性：

(a) **PagedAttention 引擎**：vLLM（或 SGLang 适合工作负载）是 2026 默认。TGI 合理，但 vLLM 对大多数工作负载吞吐更好。

(b) **连续批处理**：应启用（现代引擎有；LLM 应验证已开启）。

(c) **多 GPU 张量并行**：Llama 3 70B 需要多张 GPU 放权重；部署必须跨 GPU shard 模型（tensor parallelism）。TGI 支持；LLM 应配置。

(d) **生产可观测性**：GPU 利用率指标、KV 缓存利用率、请求队列深度、每个请求延迟。LLM 应提供完整可观测性方案。

(e) **自动扩缩**：随负载变化，集群应扩缩（Kubernetes HPA、自定义控制器）。LLM 应提供自动扩缩配置。

(f) **多租户隔离**：若集群服务多客户，需要隔离（限速、队列优先级、每客户模型分片）。

(g) **成本监控**：每客户 GPU-hour、每工作负载。真实生产部署会针对成本做仪器。

(h) **故障处理**：GPU 故障、节点故障、模型加载故障。部署必须优雅处理每种。

正确答案：“基础部署用 TGI 或 vLLM 加张量并行。2026 生产还要包含 [以上列表]。以下是更完整配置……”

更深观察：“搭建推理集群” 答案空间很广。最小答案（基础部署）适合原型；完整答案（生产级）需要理解工作负载、运维要求和成本约束。给出最小答案的 LLM 产出的是原型级代码，对原型合适但对生产不足。

对 Continuum 部署，上述每个缺失特性都很重要。遵循 LLM 最小答案的团队会构建脆弱、不可观测、昂贵的集群。正确路径是逐步成熟：先用最小答案做原型，再随工作负载需求添加生产特性。
