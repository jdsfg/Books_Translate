(e) **重配置。** 增减节点需要协议层谨慎协调。LLM 生成的代码通常根本不实现重配置，或以允许 split-brain 的天真方式实现。

(f) **网络 framing。** Paxos 消息必须可靠地匹配到正确的 proposer/ballot/acceptor。LLM 代码常用简单 HTTP 无幂等，因此重试消息可能被处理两次，污染 acceptor 状态。

更深观察：Paxos 是 LLM 生成代码的最坏情况类别。Safety 性质在任何单次测试运行中不可见；它们需要对抗性调度（在特定时刻故障）才能揭示。一个只被训练过 Paxos 描述但未被训练过 Paxos 实现的 LLM 会产出看起来正确但静默不安全的代码。这是第27章核心教训：分布式代码需要 LLM 目前做得不好的推理。


### 本章总结

Paxos 是 Lamport 1989 年提出的经典共识协议。单法令 Paxos 通过两阶段（prepare、accept）加法定人数相交就一个值达成一致。Safety 性质由 accept 规则保留：任何 proposer 的 accept 必须提议第一阶段响应中最高已接受的值；这保证一旦值被选定，所有后续 ballot 都会提议它。

Multi-Paxos 通过选举稳定 leader 并把第一阶段摊销到多个决定，把单法令扩展为值序列。稳态下每决定成本是一次往返。

Paxos 以难实现著称：持久化纪律、ballot 唯一性、法定人数 off-by-one、重配置、快照。Spanner 和 Megastore 是经典生产实现。附录 A 的阅读列表包括原始 1998 年论文、2001 年 “Paxos Made Simple” 改写，以及 Lampson 的 “How to Build a Highly Available System Using Consensus” 以获取运维视角。

第9章讲 Raft，Ongaro 和 Ousterhout 2014 年为比 Paxos 更易理解而设计。Raft 使用相同骨架（法定人数 + leader + 持久状态），但教学、实现和运维推理都更容易。它是 2026 年新系统的首选共识协议。
