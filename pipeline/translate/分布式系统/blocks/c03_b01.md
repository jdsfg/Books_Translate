一个 LLM 被要求写一个聊天消息排序函数，产出：


    def display_in_order(messages):
        return sorted(messages, key=lambda m: m.timestamp)


> 说明性伪代码；bug 是结构性（用错原语），而非语法性。

这个函数很短。看起来对。但在生产中，它会偶尔把一条回复显示在它回复的消息之前。本章解释原因以及可行的替代方案。

残酷的事实：分布式系统中没有全局的“现在”。当两台机器上发生两个事件，你想知道哪个先发生时，每个事件上的时间戳讲述的故事可能与事实不符。这个故事来自时钟，而时钟以一种特定的、结构化的方式对你撒谎——如果你理解它，就能防御。


### 3.1 NTP 及其不足

NTP（Network Time Protocol）是让机器时钟大致同步的机制。NTP 通过查询少量时间服务器、测量往返延迟，并让本地时钟缓缓向共识靠近来工作。

在健康 LAN 且附近有 Stratum-2 NTP 服务器时，机器同步到几毫秒以内。在广域网或嘈杂链路上，上界接近几十毫秒。在 NTP 守护进程静默失败的机器上（守护进程未运行、配置错误、上游服务器不可达），本地时钟以硬件速率漂移，典型服务器每天漂移数秒量级。

含义微妙。NTP 给你的是有界 _预期_ 漂移；除非你主动测量并反应，否则它不会给你有界 _保证_ 漂移。一台 NTP 配置错误一周的服务器可能与 peer 偏差数秒，却仍然像健康节点一样服务请求。

还有两个锋利的棱角：

* **NTP 可以回退时间。** 当检测到较大漂移时，NTP 可以一次性把时钟回退数百毫秒。用 `t2 - t1` 测量跨步前后的持续时间的代码会得到负值。
* **闰秒。** UTC 每隔几年插入一秒闰秒。不同系统处理方式不同（smear、step、repeat）。Cloudflare 2017 年闰秒事故是经典案例；其 DNS 服务出现负持续时间并传播到排序比较，导致数据结构破坏。

现代分布式系统的纪律实践是：假设时钟偏移可能达到已知上界（生产系统通常配置为 250 ms 或 500 ms），监控 NTP 健康，并且绝不对来自不同机器的事件写 `wall_clock_a < wall_clock_b` 来做排序。


#### 单调时钟

测量单台机器上的持续时间，应使用独立的 _单调_ 时钟。单调时钟永远不会回退（不被 NTP 调整），也不会跳跃前进。它们不与 wall-clock 时间绑定；其值只有在作差时才有意义。大多数现代语言同时暴露两者：Python 中 `time.time()` 是 wall，`time.monotonic()` 是单调；Go 中 `time.Now()` 内部同时携带两者。

规则：任何测量“X 花了多久”的代码都应使用单调时间。任何记录“X 何时发生”的代码必须使用 wall 时间，但要认识其局限。
