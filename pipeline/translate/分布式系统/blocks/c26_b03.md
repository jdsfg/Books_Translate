### 26.4 投机解码

另一类优化：投机解码通过小 “草稿模型” 预测 token、大 “验证模型” 确认，来加速解码阶段。

机制：

(a) 对每个解码步，草稿模型生成 K 个候选 token（通常 K=4-8）。草稿很快：草稿模型小（1-7B 参数），毫秒级。

(b) 验证模型（大模型，70B+）并行处理所有 K 个候选。这是一个 “验证步”，一次处理 K 个候选 token。

(c) 验证模型检查 K 个候选中与前缀匹配的部分。匹配前缀被接受；第一个不匹配被替换为验证模型偏好的 token。

(d) 被接受的 token（1-K 个）输出。解码前进相应数量。

为何更快：验证模型处理 K 个候选的时间与一次正常解码步大致相同（因为 K 个 token 并行处理远快于顺序 K 步）。若接受率高（如 80% 草稿 token 被接受），验证模型每步产出约 0.8K 个 token 而非 1 个。

吞吐提升：典型工作负载 2-3 倍。成本：草稿模型增加 GPU 使用；验证模型每步成本略高（处理 K 个 token 而非 1 个）。


### 26.5 投机解码作为分布式协议

标准实现把草稿和验证放在同一张 GPU。现代变体把它们分到不同机器：

(a) **草稿在专用节点**：一小模型节点池并行为多个请求运行草稿。

(b) **验证在大模型节点**：大模型节点只做验证（比完整解码便宜）。

(c) **草稿与验证间的网络协议**：草稿节点发送 K 个候选 token 给验证节点；验证节点确认或修正；修正流回。

分布式收益：

(a) 草稿模型节点可用更便宜硬件（小 GPU，某些情况下甚至 CPU 用于微小草稿模型）。

(b) 更好资源利用率：小模型节点并行服务多个请求的草稿；大模型节点以更高吞吐处理验证。

(c) 独立扩缩：根据工作负载扩缩草稿和验证容量。

成本：

(a) 每 token 网络延迟：草稿与验证节点间 round-trip 0.5-2 ms。增加每个 token 延迟。

(b) 网络带宽：不大（每请求每步几个 token），但真实存在。

(c) 同步复杂度：草稿与验证必须保持对齐；mid-request 迁移非平凡。

2026 年，分布式投机解码处于早期生产部署。已发布案例（Together 的栈、一些自定义实现）显示相比 co-located 投机解码 1.5-2.5 倍吞吐，代价是额外网络跳数增加首 token 延迟。
