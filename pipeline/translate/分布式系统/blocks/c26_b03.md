### 26.4 Speculative Decoding

另一类优化：speculative decoding 通过小 “草稿模型” 预测 token、大 “verify 模型” 确认，来加速 decode 阶段。

机制：

(a) 对每个 decode 步，草稿模型生成 K 个候选 token（通常 K=4-8）。Draft 很快：草稿模型小（1-7B 参数），毫秒级。

(b) Verify 模型（大模型，70B+）并行处理所有 K 个候选。这是一个 “verify 步”，一次处理 K 个候选 token。

(c) Verify 模型检查 K 个候选中与前缀匹配的部分。匹配前缀被接受；第一个不匹配被替换为 verify 模型偏好的 token。

(d) 被接受的 token（1-K 个）输出。解码前进相应数量。

为何更快：verify 模型处理 K 个候选的时间与一次正常 decode 步大致相同（因为 K 个 token 并行处理远快于顺序 K 步）。若接受率高（如 80% draft token 被接受），verify 模型每步产出约 0.8K 个 token 而非 1 个。

吞吐提升：典型工作负载 2-3 倍。成本：草稿模型增加 GPU 使用；verify 模型每步成本略高（处理 K 个 token 而非 1 个）。


### 26.5 Speculative Decoding 作为分布式协议

标准实现把 draft 和 verify 放在同一张 GPU。现代变体把它们分到不同机器：

(a) **Draft 在专用节点**：一小模型节点池并行为多个请求运行 draft。

(b) **Verify 在大模型节点**：大模型节点只做 verification（比完整 decode 便宜）。

(c) **Draft 与 verify 间的网络协议**：draft 节点发送 K 个候选 token 给 verify 节点；verify 节点确认或修正；修正流回。

分布式收益：

(a) 草稿模型节点可用更便宜硬件（小 GPU，某些情况下甚至 CPU 用于 tiny 草稿模型）。

(b) 更好资源利用率：小模型节点并行服务多个请求的 draft；大模型节点以更高吞吐处理 verification。

(c) 独立扩缩：根据工作负载扩缩 draft 和 verify 容量。

成本：

(a) 每 token 网络延迟：draft 与 verify 节点间 round-trip 0.5-2 ms。增加 per-token 延迟。

(b) 网络带宽：不大（每请求每步几个 token），但真实存在。

(c) 同步复杂度：draft 与 verify 必须保持对齐；mid-request 迁移非平凡。

2026 年，分布式 speculative decoding 处于早期生产部署。已发布案例（Together 的栈、一些自定义实现）显示相比 co-located speculative decoding 1.5-2.5 倍吞吐，代价是额外网络跳数增加首 token 延迟。
