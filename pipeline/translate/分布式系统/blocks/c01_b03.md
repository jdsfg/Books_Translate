#### 为什么部分失败是正确的默认心智模式

在单机程序中，程序在一秒窗口内经历硬件故障的概率大致等于一台机器故障的概率，这很小。也许十亿秒一次，取决于硬件。

在一万台机器组成的系统中，任意一秒内有 _某台_ 机器发生故障的概率接近 1。在 Google 规模下，问题不是“有没有什么东西坏了？”，而是“过去一小时里什么坏了？损害被控制住了吗？”

这是分布式系统工程师内化的运维现实。不是悲观，是算术。如果你为“什么都不失败”做设计，那你就是在为一个在规模化后不存在的世界做设计。


### 1.3 工程师的提问

这本书教你一个心智动作。当你审视任何分布式系统时，问三个问题：

  1. **这个系统在时间上说谎了吗？** 它是否假设 `time.Now()` 能给事件排序？它是否假设跨机器的时间戳可比较？它是否假设会话在明确定义的时刻开始和结束？
  2. **这个系统在身份上说谎了吗？** 它是否假设某个节点是“领导者”，却没有协议能证明这一点？它是否假设锁是唯一的，却没有围栏 token？它是否假设它正在对话的节点就是它所认为的那个节点？
  3. **这个系统在失败上说谎了吗？** 它是否只有理想路径和错误路径，且错误路径是不常见的情况？它是否把重试视为幂等，却没有证明？它是否有任何代码路径假设“这不会发生”？

如果你能回答这三个问题，你就能推理它的失败模式。如果你回答不了，那你还不理解这个系统，无论你对它的 API 有多熟悉。

本书的四位主角会在不同系统、不同领域反复执行这个循环。Olamide 运行它处理你刚刚遇到的多区域支付平台。Yuki Watanabe 运行它处理 Glide 的协作文档编辑器。Tobias Schwartz 运行它处理 Continuum 推理的 LLM 推理集群。Anya Reddy 运行它处理 Stratus DB 的数据库引擎。系统不同，心智动作相同。
