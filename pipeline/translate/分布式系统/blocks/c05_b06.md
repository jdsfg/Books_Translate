#### 概念检测

**Q1.** 一个团队用异步复制从主库到一个 follower 做灾难恢复。主库在写传播前死亡。走查团队会看到什么以及恢复如何进行。

提示

写丢失。选项取决于如何检测丢失以及 RPO 是什么。

**答案：** 团队会观察到：

(a) 发起写的应用收到成功响应，因为异步复制在传播前 ack。(b) 被提升的 follower 没有该写。(c) 任何观察过该写的客户端（read-your-writes 或下游影响）现在看到的状态与它以为的不一致。

恢复选项：

* 若主库磁盘可恢复，把其日志中上次复制点之后的部分回放给新主库。这是 point-in-time-recovery 工具的做法；要求主库 WAL 完整。
* 若磁盘丢失，上次复制检查点到故障之间的写入永久丢失。团队必须调和下游影响（退款、重试、通知客户）。
* 团队的 _Recovery Point Objective_（RPO）是允许的最大数据丢失时间。异步复制 RPO = 复制延迟，可能是数秒到数分钟。同步复制 RPO = 0。

纪律：按 RPO 需求选择复制模式。支付数据 RPO = 0（用同步或半同步）。分析数据 RPO = 数分钟可接受（异步加更便宜硬件）。

**Q2.** 为法定人数系统定义 $W + R > N$ 规则。为什么它给相交却不给线性一致性？

提示

相交：任意读与任意已提交写在至少一个副本上重叠。线性一致性要求更多：实时顺序和并发期间无异常。

**答案：** $W + R > N$：若写必须被至少 W 个 N 副本 ack，读必须被至少 R 个 N 副本响应，则任意读集合与任意写集合至少共享一个副本。读因此“看到”写（因为至少一个响应读的副本也 ack 了写）。

为什么不是线性一致性：

(a) **进行中的写被读** ：写还在进行（写者已联系部分副本但未满 W）时，命中已联系副本的读看到它，未命中的读看不到。不同并发读者看到不同状态。线性一致性要求所有读者按实时顺序要么都看见写要么都不见。

(b) **Sloppy quorum** ：主副本不可达时，Dynamo hinted handoff 把写发到非主副本。下一次读可能去主副本（从未收到写）而非持有 hint 的副本。相交被破坏。

(c) **并发冲突写** ：两个写者在不同但相交集合上各自满足 W。读看到两个写；冲突解决策略决定哪个“赢”。线性一致性没有这种歧义：只有一条规范顺序。

这个规则给出一个有用的较弱性质（若无并发活动，读会观察到最近完全提交的写），但不是完整线性一致性。混淆它们会让真实工程师损失真实数据。

**Q3.** 基于 leader 与无 leader 复制有何区别？各举一个生产系统。

提示

Leader-based：一个节点排序写（PostgreSQL、MongoDB、CockroachDB）。Leaderless：任意节点接受写（Cassandra、DynamoDB）。

**答案：** Leader-based：一个节点（每分片或每 range）是 leader。该分片所有写发往 leader，leader 排序后传播给 follower。故障切换需要选出新 leader，耗时数秒。示例：PostgreSQL、MongoDB replica sets、CockroachDB（per-range）、Spanner（per-tablet）。

Leaderless：任意节点接受写；系统依赖冲突解决（LWW、sibling、CRDT）收敛并发写。无需故障切换，因为没有指定 leader 可失去。示例：Cassandra、DynamoDB、Riak。

权衡：leader-based 让每分片写排序 trivial（leader 排序），代价是故障切换不可用窗口。leaderless 让故障透明，代价是更复杂的冲突解决和更弱的每键排序。现代系统模糊界限：Spanner 每 tablet leader-based 但 leader 切换开销低；Cassandra 用轻量事务处理需要 leader 类语义的操作。
