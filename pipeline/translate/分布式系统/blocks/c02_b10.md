#### 应用问题

**Q1.** 你正在评估一个文档称其为“AP”的系统。更仔细读文档，找出系统实际执行的三个线性化操作（即对这些操作它并非“AP”）。然后指出延迟成本。

提示

大多数“AP”系统都有一条需要强一致性的元数据路径：领导者选举、集群成员、配置。例如，DynamoDB 有条件写入。

**答案：** 大多数“AP”系统仅对数据平面是 AP；它们的控制平面需要强一致性才能正常工作。以 DynamoDB 为例的工作示例：

(a) 通过 `ConditionExpression` 的条件写入在分区层是线性化的。成本：每次写入延迟包含一次同步法定人数检查，高于默认最终一致 put。

(b) 通过 `ConsistentRead=true` 的强一致读是线性化的。成本：比最终一致读延迟更高（DynamoDB 文档约 2 倍），并消耗更多容量单位。

(c) 流元数据（集群拓扑、分片分配）由用户不可见的强一致控制平面管理。用户不直接为此付延迟，但控制平面变更期间的运营可能短暂不可用。

对 Cassandra：使用 `IF NOT EXISTS` 或 `IF` 子句的轻量事务（LWT）通过 Paxos 实现线性化。成本：远高于非 LWT 写入（常 4 到 10 倍），因为每次写入都发生 Paxos 往返。

对 Riak：启用后的强一致 bucket 是线性化的。成本：每次操作支付一次协调往返；吞吐比最终一致 bucket 低一个数量级。

教训：每个“AP”系统都有一个 CP 角落。知道哪些操作落在哪个角落，比系统级标签更有用。

**Q2.** 你的同事声称“我们用 CockroachDB，所以线性化是免费的。”指出 CockroachDB 中默认 _不是_ 线性化的三种操作或配置，并解释何时重要。

提示

CockroachDB 有 `AS OF SYSTEM TIME`、跟随者读，旧版本的默认 `SNAPSHOT` 隔离级别比可串行化的弱。每个都有一个非线性化角落。

**答案：**

(a) `AS OF SYSTEM TIME` 读是有界过期读，来自任意副本。它们不是线性化的；显式返回过去一致快照的数据。它们很快（无需领导者跳），对分析有用。误用：在需要最新状态的事务中用它做库存检查或余额读。

(b) 通过 `AS OF SYSTEM TIME follower_read_timestamp()` 的跟随者读从最近副本做有界过期读。与上述权衡相同。适用于全球低延迟读取缓慢变化的数据。

(c) 事务优先级与 `CONCURRENTLY` 操作交互，如果误读隔离保证，可能在不同会话的语句间产生微妙的非线性化行为。CockroachDB 默认可串行化的隔离，这是 SQL 隔离级别中最强的，但可串行化的不等于跨会话的线性化；可串行化的将事务排序为某种有效顺序，而线性化要求排序与真实时间一致。对许多工作负载差异不重要；对“会话 B 的读在会话 A 的写返回给 A 之后开始”的期望，差异可能重要。
