更深观察：“实现分布式锁” 这类请求在回答前需要多个澄清问题。没问就产出单一产物（Redlock 代码）的 LLM 是在对训练数据做模式匹配，而非工程。正确回应是：“告诉我：这把锁保护什么？两个客户端同时持有它的失败模式是什么？进程可能暂停多久？”

Crescent 修复组合 etcd + fencing token，因为 Olamide 团队问了这些问题。LLM 没问，且 LLM 生成的代码会重新引入重复扣款 bug。


### 本章总结

分布式缓存（Redis Cluster 作为典型）用 gossip 维护成员关系，可调失效模式（cache-aside、write-through、TTL、event-driven）。缓存失效出了名的难；常见陷阱（惊群、缓存踩踏、失效竞争、把缓存当 truth source）在各系统中反复出现。

分布式锁有两个目的：效率（避免重复工作）和正确性（资源只有一个写入者）。Redlock 式缓存锁对效率可接受；对正确性，在进程暂停和时钟漂移下失败。正确原语是共识支持的锁服务（etcd、Consul、ZooKeeper）加受保护资源上强制执行的 fencing token。

第1章 Crescent 修复结合基于 Raft 的协调者选举与银行端点的 fencing token。即使两个协调者短暂认为自己在位，只有 token 更高者能提交。重复扣款不可能复发。

缓存作为锁是正确性用例的反模式。用共识支持的锁；在资源处用 fencing token。代价小；正确性收益大。

第19章讲服务发现与配置：etcd 作为现代默认（替代 ZooKeeper）、Consul、基于 DNS 的发现，以及 config-as-data + watch stream 模式。这些是让其余分布式基础设施运行的元系统。
