#### 深入思考

**Q1.** 辩护或反驳：“2026 年 FLP 只是历史好奇心；现代系统都已处理它，工程师无需了解。”

**讨论：** “历史好奇心”观点：每个生产共识协议都假设部分同步。工程师只需选个协议，不必想 FLP。协议自会处理。

反驳：理解 FLP 对理解共识集群为何如此行为至关重要。Raft 在分区期间无法选出领导者时，就是 FLP 在起作用：在持续恶劣条件下，协议优先安全性而非活性。不懂 FLP 的运维会视为“数据库坏了”，并可能采取破坏安全性的反生产措施（强制领导者、禁用 Raft）。

现代协议通过明确选择（始终安全的，活性有条件）来 _处理_ FLP。部署、运维、调试协议的工程师需要理解做了什么选择。FLP 就是解释该选择的框架。

第二个考虑：2026 年仍在设计新共识协议（Narwhal-Bullshark、Mysticeti、HotStuff 变体）。每种都做出与 FLP 相关的明确选择。工程师在它们之间选择需要比较的词汇。

综合：FLP 是基础，不是好奇心。应用工程师需要知道不可能性说了什么、逃生舱是什么。证明本身主要对协议设计者重要；其含义（安全性 vs 活性；部分同步；故障检测）对每个人都重要。

**Q2.** 一个 LLM 被问“为什么我们不能对所有东西都用两阶段提交？”它给出关于锁争用的回答。指出 LLM 关于协调者故障下 2PC 阻塞性质的遗漏。

**讨论：** 2PC 有一个臭名昭著的阻塞失败模式：若协调者在发送 PREPARE 后、发送 COMMIT 或 ABORT 前崩溃，参与者就卡住。它们已投票（并持有锁），无法自行决定（不知道其他参与者投票），也不能中止（协调者可能在崩溃前已提交）。

这种阻塞不只是“锁争用”。它是更深层的结构性问题：2PC 把共识归约到单一协调者，协调者成为活性的单点故障。参与者在协调者恢复前被阻塞，而协调者可能永不恢复。

3PC 被提出修复，但 3PC 在网络分区下也失败；它只在生产网络不满足的特定故障模型下才非阻塞。

真正修复是 _复制协调者_ ：协调者状态本身通过共识（Raft 或 Paxos）复制，因此任何协调者状态都可从共识日志恢复。这就是 Spanner / CockroachDB / Percolator 模式（第13章）。

只回答“锁争用”而不提阻塞失败模式的 LLM 错过了 2PC 不能作为通用共识原语的核心原因。锁争用是另一个（真实但较不根本）问题。
