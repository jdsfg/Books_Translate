第二个观察：LLM 对强一致的偏好反映了训练偏差。LLM 训练数据中大多数 “实现 X” 请求可能隐含答案是 “用数据库”，即使更专门的原语（CRDT、队列、缓存）才是正确的。LLM 在安全默认；工程师应质疑该默认是否适合工作负载。

正确的工程反射：当被要求 “实现计数器” 时，先问吞吐。若吞吐高，答案不是数据库事务。


### 本章总结

一致性格在 Linearizable 和 Eventual 之间有许多有用的中间点。Causal consistency 保持因果顺序；strong-eventual（基于 CRDT）提供确定性收敛。两者都比线性化便宜；两者都比纯最终更强。

计数器 / 排行榜 / 库存工作负载最终定型：计数器是最终一致（第15章）；排行榜是因果一致（本章）；库存是线性化（第13章）。每个都是其需求的正确一致性；选错级别要么导致正确性违规，要么浪费资源。

生产系统提供 per-operation 一致性选择：Spanner（线性化 + 过期读）、DynamoDB（最终 + 条件写）、Cassandra（可调级别 + LWT）。应用工程师的任务是为每次操作正确选择。

混合架构组合系统：Crescent 用 CockroachDB（线性化）+ 自定义计数器服务（最终）+ Snowflake（分析）。Glide 用 Yjs（CRDT/强最终）+ Cloudflare Durable Objects（per-object 线性化）做文档元数据。“每个工作负载的正确系统” 是 2026 年复杂系统的默认架构模式。

第18章开启第六部分：协调原语。分布式缓存（Redis Cluster gossip；失效模式）和分布式锁（Redlock 辩论；fencing token 作为正确原语）。Crescent 支付系统使用 fencing token 保证协调者唯一性；本章解释这是防御 “身份谎言” 的正确手段。
