#### 深入思考

**Q1.** 辩护或反驳：“2026 年 Paxos 已过时。Raft 同样好、更简单，每个新系统都应该用它。”

**讨论：** 辩护：Raft 由 Ongaro 和 Ousterhout 明确设计为比 Paxos 更易理解，同时提供相同安全性保证。大多数新分布式系统（etcd、Consul、TiKV、CockroachDB、SpiceDB）用 Raft。Diego Ongaro 的博士论文 “Designing for Understandability” 直接针对 Paxos 的复杂性。对新团队来说，Raft 是正确默认。

反驳：Paxos 有 Raft 没有的属性，视变体而定。EPaxos 无领导者；对低竞争工作负载，其吞吐高于 Raft 的领导者瓶颈设计。Flexible Paxos 允许运维调节法定人数大小，Raft 不行。Google 的 Chubby 和 Spanner 基于 Paxos，有数十年生产伤痕沉淀。

综合：对 2026 年新通用系统，Raft 是正确选择。实现成本更低；运维人体工学更好。对专门系统（极低竞争、极高吞吐、异常故障模型），Paxos 变体可能仍值得实现复杂度。“Paxos vs Raft” 辩论对常见情况已基本倒向 Raft，Paxos 在少数真正有其优势的领域存活。

第二个考虑：ZooKeeper 的 ZAB（原子广播）是 Paxos 变体，大量生产基础设施依赖 ZooKeeper。因此即使系统不标榜“用 Paxos”，Paxos 家族在运维上仍然活跃。协议家族的存在比简单名字匹配更广泛。

**Q2.** 一个 LLM 被要求用 Python 实现 Paxos，产出 200 行代码。在不运行的情况下，指出任何 LLM 生成的 Paxos 实现中可能存在的三类缺陷。

**讨论：**

(a) **持久化遗漏。** 接受者状态（$b_{max}$、`accepted_ballot`、`accepted_value`）必须在回复准备或接受消息 _之前_ 持久化。LLM 生成的代码常用内存状态，无 fsync、无 WAL、无恢复。崩溃后接受者 “忘记”先前承诺并可接受冲突值，违反安全性。单进程测试无法发现。

(b) **投票唯一性。** 投票编号必须在所有提议者间唯一且每个提议者单调递增。LLM 代码常用简单计数器而不带提议者-ID 消歧，于是两个提议者可能使用相同投票，破坏“最高已接受投票”决胜规则。

(c) **法定人数差一。** N 个节点的多数是 $\lceil (N+1)/2 \rceil$。$N=4$ 时多数是 3；$N=5$ 时多数也是 3。LLM 代码常硬编码错误值，与偶数节点一起使用时破坏法定人数相交。

还有三条（任一条都会造成静默安全性违反）：

(d) **第二阶段值选择。** 接受规则（提议者必须提议第一阶段响应中最高已接受投票的值）是核心安全性不变式。LLM 代码常无条件使用自己的值，提议者崩溃 mid-protocol 时立即违反安全性。
