### 19.6 服务网格：现代层

2026 年，服务发现通常是更广泛服务网格实现的一部分。服务网格提供：

(a) **服务发现**：实例注册表；动态路由。

(b) **mTLS**：服务间加密与认证。

(c) **流量策略**：金丝雀发布、蓝绿、A/B 测试。

(d) **可观测性**：每个请求追踪、延迟指标、错误率。

(e) **弹性**：熔断、重试预算、超时策略。

2026 年两大主导服务网格：Istio（基于 envoy；Kubernetes 原生）和 Linkerd（更轻量）。两者都用 etcd/Kubernetes 做发现，用 envoy 做数据面。

服务网格采用已趋于平稳；许多团队发现运维开销大于收益。服务图简单（10 个服务、单区域）的团队，服务网格过度。服务图复杂（50+ 服务、多区域、多协议）的团队，服务网格至关重要。


### 19.7 Crescent 的发现架构

Olamide 的 Crescent 使用：

* **Kubernetes 原生服务发现** 用于区域内服务间流量。每个服务是 Kubernetes 服务对象；客户端解析 `payment.crescent.svc.cluster.local`；kube-proxy 负载均衡到健康 pod。

* **直接使用 etcd** 做领导者选举锁服务（第18章）。Raft 支撑的 etcd 集群提供带 revision 号围栏 token 的线性化锁获取。

* **Consul 做跨区域服务网格**：EU-West 的服务通过 Consul 多 DC 支持找到 US-East 的服务。Consul 处理跨区域的 DNS 解析与路由。

* **AWS Cloud Map 做外部 API 网关**：面向客户的 API 端点通过路由 53 + Cloud Map 暴露；全球客户解析到最近的区域负载均衡。

这四个系统分层。每个处理自己的领域；跨领域交互通过明确定义的 API。这比 “全用 etcd” 更复杂，但匹配部署拓扑（Kubernetes + AWS + 跨区域），并让每个系统做其最擅长的。
