### 25.5 工作流 12：Continuum 的分离式部署

Tobias 的 80% 利用率目标计划：

**架构**：

* 30 个 prefill 节点（每个 4x H100 = 120 张 H100）。针对计算优化。
* 30 个 decode 节点（每个 8x H200 = 240 张 H200）。针对内存带宽和容量优化。
* 10 个 cache 节点（Mooncake 风格缓存层；高带宽存储，RDMA 连接 serving）。
* 高带宽互联：每个 rack 内 800 Gbit/s InfiniBand，rack 间 400 Gbit/s。

**请求流**：

  1. 请求到达负载均衡器。
  2. 负载均衡器基于可用性把请求分配到 prefill 节点和 decode 节点。
  3. Prefill 节点处理 prompt；产生 KV cache。
  4. KV cache 从 prefill 传输到 decode（若可能复用则存入缓存层）。
  5. Decode 节点生成输出 token；每 token 从缓存层读取 KV cache。
  6. 输出流回客户端。

**运维特征**：

* Prefill 延迟：典型 prompt（1000-5000 token）约 50-200 ms。
* Decode 延迟：每 token 约 30 ms（受 decode GPU 内存带宽限制）。
* KV cache 传输：典型 KV cache（5-10 GB 经 RDMA）约 50 ms。
* 首 token 延迟：约 100-300 ms（prefill + 传输 + 首 token 生成）。
* 后续每 token 延迟：约 30 ms。

**成本影响**：

* GPU 利用率从 60% 提升到约 85%。
* 有效集群容量提升约 40%（利用率收益加每 GPU 效率提升）。
* 每个请求成本下降约 30%。
* 年度节省：此前 1400 万美元年运行费中节省 400-500 万美元。

**运维关注点**：

* KV cache 传输是新瓶颈；带宽配置必须跟上。
* 故障模式：prefill 节点崩溃会让 in-flight 请求的 KV cache 搁浅；需要恢复逻辑。
* 负载均衡更复杂；分配必须同时考虑两个阶段。
* 可观测性：trace 必须跟随请求从 prefill 到 decode 到输出。

**实现时间线**：架构改动 6 个月。团队构建分离层；在小 pilot 集群测试；全集群 rollout。最终达到 80% 目标。

更深教训：2026 年推理成本优化是架构机会。这些模式是 2023-2024 年研究论文在 2025-2026 年成熟为生产设计。投资架构的团队会看到可观回报。
