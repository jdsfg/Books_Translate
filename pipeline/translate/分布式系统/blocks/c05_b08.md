#### 应用问题

**Q1.** Olamide 的团队正在决定 Crescent 支付系统用 Postgres + 读副本（异步）还是 CockroachDB。列出他们应先用 PACELC 框架（第2章）和本章复制权衡回答的五个问题。

提示

RPO、RTO、read-after-write 需求、多区域需求、团队运维成熟度。

**答案：**

(a) **RPO 是多少？** 异步 Postgres 复制 RPO = 复制延迟（正常负载通常亚秒，压力大时数分钟）。CockroachDB 的 Raft 复制对已提交写 RPO = 0。支付数据通常 RPO = 0 是硬性要求。

(b) **RTO 是多少？** Postgres 故障切换（用 Patroni 等）通常 30 秒到数分钟；CockroachDB 自动每范围领导者转移只需数秒。如果支付处理的用户可见中断不可接受，差别重要。

(c) **应用需要什么 read-after-write 保证？** 若仪表盘必须立即反映存款，两个系统都能提供（Postgres 走主库读；CockroachDB 用 HLC-aware 读），但应用纪律不同。

(d) **部署是否多区域？** Postgres 可用逻辑复制做多区域，但失败模式复杂；CockroachDB 从一开始就按多区域设计，具有一致延迟模型。若 Crescent 运营三区域，CockroachDB 运维更干净。

(e) **团队运维成熟度如何？** 跑了十年 Postgres 的团队对备份、恢复、复制监控、切换有肌肉记忆；CockroachDB 较新，团队需要学习其细节。把熟悉系统用错的代价通常低于把不熟悉系统用错的代价。

第六个值得问：成本？自托管 Postgres 比 CockroachDB 许可证和基础设施开销低。对规模化支付系统，运维收益通常 justify；对小初创公司，成本可能不 justify。

**Q2.** 一个团队运行 Cassandra，$N = 3, W = 2, R = 2$。他们观察到偶发读异常：用户更新资料后立即读取，看到旧值。用法定人数系统诊断并提出两种修复。

提示

$W = 2$ 表示写命中 3 中 2 个节点。$R = 2$ 表示读命中 3 中 2 个节点。相交保证至少一个共同节点，但读可能在该共同节点完全应用写之前就读到它。

**答案：** 诊断：$N = 3, W = 2, R = 2$ 相交保证写者集合与读者集合至少有一个共同节点。但：

(a) 写可能在 2 个节点 ack 后就被确认，即使第三个尚未应用。若读者的 2 个节点是第三个（不在写者集合）和写者集合中一个离线的节点，读可能看不到写。

(b) Cassandra 的 “法定人数” 协调者 opportunistically 选择节点。读协调者可能选择与写协调者不同的节点集合。即使两个法定人数都有效，具体重叠可能不包括持有最新值的节点，如果写者法定人数只是部分传播。
