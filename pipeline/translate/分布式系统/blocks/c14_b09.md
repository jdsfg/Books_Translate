#### 应用问题

**Q1.** 一个团队在 AWS 上运行 PostgreSQL，数据库已增长到 10 TB。单 Aurora Postgres 实例峰值 CPU 60%，延迟在下降。他们需要决定：手动分片、迁移到 Aurora DSQL，还是迁移到 CockroachDB。走一遍权衡。

提示

手动分片：工作量最大、控制最大。Aurora DSQL：托管、AWS 原生、较新。CockroachDB：托管或自托管、多云、成熟。

**答案：**

_选项 1：手动分片_。把 10 TB 跨 N 个 Postgres 实例在应用层拆分。优点：完整 Postgres 兼容、细粒度控制。缺点：大量应用改动（分片感知查询、跨分片连接变成应用层）、跨分片事务需要应用层 saga 或 2PC、运维复杂度倍增。

_选项 2：Aurora DSQL_。迁移到 AWS 托管 NewSQL。优点：serverless 计费（无空闲容量）、兼容 Postgres（大部分）、多区域可用、AWS 原生集成。缺点：AWS 锁定加深、较新且生产记录较少、每租户 Firecracker 开销可能意外。

_选项 3：CockroachDB_。迁移到 CockroachDB Serverless 或自托管。优点：多云、成熟、Postgres 兼容、强可串行化事务。缺点：与现有 Aurora 分开运维、付费产品（企业功能需 license）。

推荐因素：

* 若团队可预见未来仍 commitment AWS 且看重托管运维：Aurora DSQL。
* 若团队看重多云可选性或 AWS commitment 不确定：CockroachDB。
* 若团队增长已放缓且希望最小架构改动：继续用 Aurora Postgres 并纵向扩展；推迟决策。

10 TB / 60% CPU 尚未临界（还可进一步纵向扩展）。关键问题是未来 12-24 个月是否一定需要多区域或进一步扩展。若是，现在就选 CockroachDB 或 DSQL 并增量迁移；若否，推迟。

许多团队在这种情况下选择 “纵向扩展 + 读副本” 作为下一步，只在被迫时才迁移到 NewSQL（12-24 个月后）。这在运维上理性；只有当收益明确时才应支付迁移成本。

**Q2.** 一个团队正在构建全球 SaaS 分析产品。客户通过产品 UI 查询自己的数据；查询可以是即席 SQL。团队在 Snowflake（托管）和数据湖上自托管 Trino 之间选择。比较。

提示

Snowflake：托管、成本可预测、控制少。Trino：自托管、更多控制、需要运维专长。

**答案：**

_Snowflake_ ：

* 优点：零运维负担；按查询和存储付费；并发极强（每个 warehouse 独立）；自动优化；定价透明。
* 缺点：厂商锁定（历史上专有格式，Iceberg 集成正在出现）；写得差的查询成本可能意外；无法细粒度调优。

_自托管 Trino_ ：

* 优点：开源；成本由团队控制；完全调优控制；跨多源联邦查询；无锁定。
* 缺点：重大运维负担（计算集群管理、查询优化、缓存）；需要 JVM 调优、Trino 内部知识；成本包含运维团队。
