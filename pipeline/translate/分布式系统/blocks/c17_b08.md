(b) **降低复制滞后**：为 secondary 调优以降低滞后（更多内存、更快网络、更多并行应用线程）。缩小等待窗口但不消除。

(c) **缩短超时并回退**：配置更短的等待超时；超时后回退到 “非因果” 读（从任意副本读而不等待）。这以牺牲因果正确性换取可用性；应用代码必须处理轻微过期读。

(d) **切换到具有 HLC-aware 多区域语义的系统**：CockroachDB 的 follower reads 或 YugabyteDB 的类似特性；读可从更近副本做有界过期，无需因果会话等待。

对 MongoDB，(a) 和 (b) 是常见模式。因果会话对许多工作负载是正确模型，但会以更严格读不暴露的方式揭示底层复制滞后。

**Q3.** 一个团队在购物车工作负载中选择 Riak（sibling-value 冲突解决）与 Cassandra（LWW）。分析。

提示

购物车：不同设备并发更新；合并物品有意义（并集）。Sibling values 让应用合并；LWW 会丢失物品。

**答案：** 购物车特性：

* 用户可从多个设备（手机、笔记本）并发添加商品。
* “手机上添加的物品” 和 “笔记本上添加的物品” 的合并应是并集。
* “移除商品” 可能与 “添加商品” 竞争；正确语义取决于用户意图。

_Cassandra LWW_ ：当购物车两个并发写冲突（来自不同设备）时，时间戳更高的写胜出。另一个被丢弃。

失败：用户在手机添加商品 X，笔记本并发添加商品 Y。两者是独立操作，但 Cassandra 把它们视为同一购物车键的冲突写。一个胜出；另一个丢失。用户发现只添加了一件商品。

Cassandra 中的修复是把每个物品作为单独一行存储（键 = (user_id, item_id)），这样添加不冲突。可行但需要 schema 设计纪律。“清空购物车” 或 “设置数量” 等操作若仍用单个购物车状态行仍会冲突。

_Riak with sibling values_ ：两个写冲突时，两个值都作为 sibling 保留。应用看到 `[{cart: [X]}, {cart: [Y]}]` 并决定。标准购物车合并是 “物品并集”，由应用实现（Riak 不自动合并）。

Riak 的方法干净地处理购物车工作负载：并发添加作为 sibling 保留；应用的合并函数取并集。

_Riak 的 CRDT bucket types_（较新的 Riak 特性）：购物车可建模为 OR-Set CRDT。Riak 自动处理合并；无需应用逻辑合并 sibling。这是现代路径：对需要的数据类型使用 CRDT，sibling values 用于应用控制的合并。

推荐：对购物车用 Riak 的 CRDT bucket types。OR-Set 语义匹配购物车的 “物品并集” 行为。并发添加保留；并发移除被 tombstone；最终购物车是确定性合并。

若团队现有系统是 Cassandra：重新设计 schema（每物品一行，而非每购物车一行），并对 “清空购物车” 操作使用 LWT。比 Riak CRDT 方法复杂但可行。
