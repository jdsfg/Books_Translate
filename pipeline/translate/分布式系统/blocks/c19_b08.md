**Q2.** 一个团队有 47 个微服务使用 Consul 做发现。他们注意到 Consul 集群故障转移（3 副本 Consul，一个节点故障）期间，服务间流量中断 30 秒。诊断并给出修复方案。

提示

Consul 基于 gossip 的健康检查；故障转移行为；客户端缓存 last-known-good 注册表。

**答案：** 诊断：Consul 故障转移期间，集群重新选举 Raft 领导者。选举期间新写被阻塞（通常 5-15 秒）。此窗口查询 Consul 的客户端可能收到过期或错误响应。

若客户端配置为 “fail open”（Consul 不可用时使用 last-known 服务注册表），影响很小。若配置为 “fail closed”（Consul 不可达时返回错误），每次服务调用在选举窗口内失败。

修复：

(a) **配置客户端使用 stale 读**：Consul 支持从任意副本 stale 读（`?stale=true`）；领导者不可达时客户端回退到 stale 读。权衡：故障转移期间数据略过期；对服务发现可接受。

(b) **客户端缓存带宽限期**：客户端本地缓存发现的服务注册表一段宽限期（如 60 秒）。Consul 故障转移期间，客户端使用缓存注册表。风险：故障转移期间死亡的实例可能仍被返回给调用者；应用看到连接拒绝错误并回退到其他实例。

(c) **提高 Consul 冗余**：运行 5 节点 Consul 集群而非 3 节点；更大集群对故障容忍更高，重选更快。

(d) **使用带 sidecar 缓存的服务网格**：Istio/Linkerd sidecar 本地缓存服务注册表；客户端到 sidecar 的查找是本地的，不受 Consul 中断影响。sidecar 异步从 Consul 刷新。

(e) **迁移到集群内发现（Kubernetes service）**：Kubernetes 用 etcd 作为后端；每个节点的 kube-proxy 缓存 service 定义；Kubernetes API 中断影响新 service 定义，但不影响已有。对 Kubernetes 内服务，这通常比 Consul 更弹性。

推荐：短期缓解用 (a) + (b)；长期架构改进用 (d) 或 (e)。30 秒故障转移导致的中断是运维痛点；实质降低它会明显改善用户体验。
