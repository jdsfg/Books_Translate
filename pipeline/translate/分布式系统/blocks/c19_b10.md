#### 深入思考

**Q1.** 辩护或反驳：“2026 年服务网格对大多数团队过度工程。普通 Kubernetes 服务发现对 90% 的微服务部署足够。”

**讨论：** 辩护：Kubernetes 服务发现（通过内置服务对象、kube-proxy、DNS）快速、可靠、运维简单。对纯 Kubernetes 部署、几十个服务以内，它无需 Istio 或 Linkerd 的运维开销就能处理发现。网格增加 CPU、内存、延迟和巨大运维面。

反驳：服务网格对多集群、多区域或非 Kubernetes 部署增加真正价值。mTLS、流量策略和可观测性功能替代了团队否则需要自建的工做。有这类需求的团队中，服务网格比替代方案更便宜。

综合：服务网格适合需求与其能力匹配的团队（多区域、多协议、复杂流量策略）。对没有这些需求的团队是过度工程。错误是 “因为大家都在做” 就采用服务网格而不评估是否匹配。

2026 现实：服务网格采用在 2022-2023 年左右达到顶峰；许多团队随后因运维开销弃用服务网格，转向更简单的替代。趋势是 “需要时才用服务网格，不要因为 FOMO”。Istio 的复杂性尤其驱使团队转向更轻量的替代（Linkerd）或完全不用网格。

第二个考虑：服务网格价值很大程度上取决于数据面技术。Istio 的数据面 Envoy 很重；基于 eBPF 的替代（Cilium）更轻。随着 eBPF 网格成熟，服务网格运维成本下降，成本收益计算会改变。

**Q2.** 一个 LLM 被要求 “为我们的微服务舰队实现服务发现”。它产出使用 Kubernetes 服务的代码。该团队在 EC2 上运行（非 Kubernetes）。指出 LLM 的失败和正确模式。

**讨论：** LLM 的失败：它产出的是它最熟悉部署（Kubernetes）的答案，而没有问实际部署目标。EC2（或基于 VM）部署无法使用 Kubernetes 服务；需要不同机制。

EC2 的正确模式：

(a) **Consul**：HashiCorp 的 Consul 为 VM 和混合部署设计。EC2 实例启动时通过 Consul 代理注册；客户端通过 DNS 或 HTTP API 解析。

(b) **AWS Cloud Map**：AWS 托管服务发现。实例通过 API 注册，或与 ECS/Fargate 自动注册；客户端通过 DNS 解析。

(c) **直接使用 etcd**：在 EC2 上部署 etcd 集群；服务通过 etcd API 注册和发现。比 Consul 或 Cloud Map 工作量更大，但可控。

(d) **Eureka（Netflix OSS）**：较老的 Java 中心化服务发现。Netflix 使用；2026 年较不常见，但某些遗留系统仍在用。

对 2026 年的新 EC2 部署：Consul 或 Cloud Map。选择取决于团队偏好（Consul：HashiCorp 生态、多云；Cloud Map：AWS 原生、更简单）。

更深观察：LLM 没问部署目标。“实现服务发现” 这类请求需要上下文。未问就产出 Kubernetes 服务的 LLM 是把流行模式套到不适用的上下文。
