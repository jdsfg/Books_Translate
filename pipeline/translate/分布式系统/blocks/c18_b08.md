#### 应用问题

**Q1.** 一个团队实现任务队列，每个任务应被恰好一个工作节点处理。他们考虑 (a) Redlock，(b) 带围栏 token 的 etcd 锁，(c) 数据库行级锁。比较。

提示

任务队列可以是纯效率（若任务幂等）。每种锁方法有不同成本/安全权衡。

**答案：**

(a) **Redlock** ：简单、快、除 Redis 外无需额外基础设施。若任务幂等（偶尔双处理浪费但无害）可接受。若任务有非幂等副作用（发邮件、扣款、发货）则不可接受。

(b) **带围栏 token 的 etcd 锁** ：对效率和正确性用例都正确。增加 etcd 依赖（若团队没跑 etcd）。锁具有线性化语义；围栏 token 防止过期持有者问题。每次获取较慢（etcd 写是多数复制）。

(c) **数据库行级锁** ：数据库中的一行表示 “正在处理任务 X”。工作节点用 `SELECT ... FOR UPDATE` 获取锁；行的存在阻止其他工作节点申领。完成后工作节点更新行（如状态 = "完成"）。对已有 Postgres 的应用，运维干净：无额外基础设施。

推荐：

* 幂等任务（大多数 ETL 流水线、周期任务）：Redlock 即可。最简单最快。
* 非幂等任务：若已有数据库，选 (c)；若无，选 (b)。两者都提供正确性。
* 高吞吐任务队列（每秒数千任务）：专用系统（Kafka with 消费者 groups、Cloud Pub/Sub）原生处理投递语义，避免每个任务锁模式。

更深观察：”每个任务锁“ 往往是错误架构。专用任务队列（内置至少一次或恰好一次语义）原生去重。锁模式通常是 “自己造轮子”；现代系统通常可围绕专用队列基础设施设计。

**Q2.** Anya 正在为 Stratus DB 领导者选举服务实现围栏 token。描述存储层如何强制执行 token 顺序。

提示

每次范围写入包含领导者 token。范围的 Raft 状态跟踪最高 token。低 token 被拒绝。

**答案：** Stratus DB 的领导者选举使用带围栏 token 的 etcd 锁。实现：

(a) 集群的领导者角色（对给定范围或集群范围协调）通过 etcd 锁获取。每次获取分配一个围栏 token（来自 etcd revision 号的单调递增计数器）。

(b) 领导者的后续操作（发起范围拆分、再平衡决策、配置变更）携带该 token。

(c) 范围的 Raft 状态存储已接受的最高 token。Raft 领导者的提交机制检查：该操作 token >= 已接受最高 token？若是，接受；否则拒绝。

(d) 拒绝：操作失败并返回 `STALE_LEADER`。提议客户端知道自己失去领导权并下台。

实现细节：token 比较发生在 Raft AppendEntries 阶段，而非仅在 API 层。这确保即使过期领导者的 RPC 到达 Raft group，条目在共识层也被拒绝；应用逻辑永远看不到它们。
