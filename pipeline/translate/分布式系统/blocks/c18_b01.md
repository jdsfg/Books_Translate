    def acquire_lock():
        return redis.set("leader_lock", node_id, nx=True, ex=30)


> 说明性伪代码；bug 在于原语选择（无 fencing token 的超时锁），而非语法。

这就是 Redlock 模式。代码很短。生产环境中，它偶尔会允许两个领导者同时行动。原因是分布式系统中最深刻的论证之一：Martin Kleppmann 对 Redlock 的分析以及 _fencing token_ 的作用。

本章讲授两个相关原语：分布式缓存（具体是 Redis Cluster gossip 与缓存失效模式）和分布式锁（具体是为什么朴素锁会失败、正确原语长什么样）。第1章 Crescent 支付系统 “身份谎言” 的修复使用了 fencing token；本章解释原因。


### 18.1 分布式缓存

缓存是一种性能模式：把昂贵操作结果存在快速查找存储中，后续请求避免重复计算。分布式缓存把这一模式扩展到多个缓存实例，被多个服务访问。

2026 年典型系统是 Redis Cluster（及其商业变体：Redis Enterprise、Amazon ElastiCache for Redis、Redis Labs）。下面讨论聚焦 Redis Cluster。


#### Redis Cluster gossip

Redis Cluster 是分片、复制的键值存储。键被映射到 16,384 个 hash slot 之一；每个 slot 属于一个 master，可有可选副本。

集群成员关系通过 gossip 维护：每个节点周期性向随机选择的其他节点子集发送 PING；PING 携带发送者对集群的视图。接收者基于 PING 更新自己的视图。随时间推移，集群对自身的视图收敛。

gossip 不是共识；分区下，集群两半可能有不一致视图。Redis Cluster 要求大多数 master 节点同意配置变更（slot 重分配、主从切换）来处理。分区期间的少数派写失败并返回 `CLUSTERDOWN`。


#### 缓存失效模式

Phil Karlton 的名言：“计算机科学中只有两件难事：缓存失效和命名。” 缓存失效模式：

(a) **Cache-aside**：应用先查缓存；未命中则从 truth source 读取并回填缓存。写时使缓存失效。

(b) **Write-through**：写穿过缓存（缓存同步写入 truth source）。缓存与 source 始终一致。

(c) **Write-back（write-behind）**：写先写缓存；缓存异步写回 source。source 可能暂时过期。

(d) **TTL-based**：缓存条目在指定时间后过期。隐式失效；TTL 后的下一次读会取最新。

(e) **Event-driven invalidation**：source 发布 “该 key 变了” 事件；缓存订阅并失效。

选择取决于工作负载：

* 读多写少：cache-aside + 长 TTL。
* 读多写多：cache-aside + 短 TTL 或 event-driven invalidation。
* 写多：write-through（保持一致）或 write-back（牺牲持久性换速度）。
