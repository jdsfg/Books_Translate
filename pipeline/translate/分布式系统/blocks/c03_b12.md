实际建议：HLC 几乎肯定足以满足应用的真实需求。团队应该问自己需要的是 _并发检测_ （需要类向量结构）还是只有 _一致排序_ （HLC 已提供）。大多数分布式应用代码只需要后者。

**Q3.** Spanner 的 commit-wait 是 7 ms。CockroachDB 的 HLC 带偏移上界默认 500 ms。为什么 CockroachDB 的数字大了 70 倍，在实践中意味着什么？

提示

7 ms 是 Spanner 在有 GPS 原子钟基础设施下观测到的 _实际_ 不确定度。500 ms 是 CockroachDB 在没有专用硬件时 _假设_ 的最大偏移上界。两者付出代价方式不同：Spanner 每次提交都等待；CockroachDB 只在读观察到写入落在偏移窗口内时才重启事务。

**答案：** Spanner 的 7 ms 是在其 GPS 加原子钟设置下 TrueTime 的经验不确定度。Spanner 通过每次提交 _等待_ 来支付这 7 ms。等待是每次事务真实增加的延迟。补偿收益是线性化时间戳无需任何重试或重启即可分配。

CockroachDB 的 500 ms 是它假设节点间 _最大时钟偏移_ 的配置参数。这个数字不是作为等待支付的。相反，CockroachDB 的做法是：事务启动时获取时间戳 t_s。如果读时观察到已提交写入的时间戳 t_w 满足 t_s < t_w < t_s + \文本{max\_skew}，系统无法判断该写入在物理时钟时间中是否发生在事务开始之前，于是 _重启_ 事务，用新时间戳推到观察到的写入之后。这就是“uncertainty restart”路径。

实际含义：

* Spanner 的成本是每个事务恒定的。CockroachDB 的成本只在与其他节点近期写入冲突时支付。低竞争工作负载下，CockroachDB 不付任何代价。
* Spanner 每次提交都付。CockroachDB 由部分事务（命中不确定性窗口的）付，其他不付。
* 在 CockroachDB 中，对最近写入键有高竞争的工作负载可能遭受大量 uncertainty restarts。500 ms 上界是最坏情况；收紧它（通过严格 NTP 纪律）会成比例减少重启。
* Spanner 跨区域部署仍可用同样的 7 ms；CockroachDB 跨区域也能通过良好 NTP 收紧偏移上界，但没有 GPS 硬件无法匹敌 Spanner。

2026 年的选择：如果你能负担 GPS 基础设施或使用云 TrueTime 等价物，Spanner 风格运维更干净。如果不能，CockroachDB 风格 HLC 加偏移上界是实际默认； aggressively 调优 NTP 和偏移上界。
