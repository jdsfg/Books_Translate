### 18.3 Crescent 的修复

回顾第1章：Crescent 重复扣款是因为两个协调者都认为自己正在处理 Adaeze 的交易。修复涉及围栏 token。

架构：

(a) 协调者角色由 Raft 复制的锁服务管理。每次获得协调者角色时分配一个围栏 token。

(b) 银行支付端点存储已接受的最高 token。任何带更低 token 的提交被拒绝。

(c) 若两个协调者短暂都认为自己持有角色（故障转移、分区愈合等期间），只有 token 更高的能行动。

有了这套机制，原始 Crescent 失败不会复发。即使两个协调者同时存活并尝试提交，银行的围栏 token 检查保证至多一个成功。

围栏 token 机制可视化：

        L-->>C2: granted, token=101
        C2->>银行: 提交 (token=101)
        Bank->>银行: 101 >= highest (100); 接受
        Bank-->>C2: ok
        Note over C1: resumed 之后暂停
        C1->>银行: 提交 (token=100, 陈旧的)
        Bank->>银行: 100 < highest (101); 拒绝
        Bank-->>C1: STALE_TOKEN


即使 C1 醒来仍以为自己持有锁（经典的基于超时锁失败模式），银行的单调 token 检查拒绝其提交。两个协调者可以短暂共存；只有一个能修改受保护资源。

（Raft 复制的锁服务）+（受保护资源上的围栏 token）的组合是正确生产模式。朴素 Redlock 是错误模式；正确模式更复杂，但复杂性必要。
