#### 应用问题

**Q1.** 一个团队在三个数据中心运行 Cassandra，每秒 100,000 次写入，偶尔发现“last write wins” tombstone 复活了一条已删除记录。用时钟偏移问题诊断，并推荐修复。

提示

Cassandra 的 LWW 依赖每次写入的 wall-clock 时间戳。如果删除被盖戳早于后续写入的时间戳，会发生什么？

**答案：** Cassandra 的默认冲突解决是 last-write-wins（LWW），基于协调者节点分配的 wall-clock 时间戳。如果删除由时钟落后的协调者处理，它被盖戳早于另一个时钟超前的协调者上的后续写入。当删除和写入到达副本时，副本看到 write-timestamp > delete-timestamp，于是保留写入，实际上复活了记录。

这就是经典的 Cassandra “复活删除”失败模式，在 Jepsen 分析中有详尽记录。修复方案：

* 确保严格 NTP 纪律；当 NTP 漂移超过小上界（10 到 50 ms）时告警。这只会让失败更罕见，不能消除它。
* 只有当你有可靠单调来源时才使用 `USING TIMESTAMP` 的服务端时间戳。
* 对复活不可接受的数据，使用带 `IF` 子句的轻量事务（LWT）；LWT 使用 Paxos，提供线性化语义。代价：每次操作延迟增加一个数量级。
* 迁移到基于 HLC 的 MVCC 系统（CockroachDB、YugabyteDB），其冲突解决不依赖 wall clock。

对这个具体工作负载（三数据中心每秒 100k 写入），每次写入用 LWT 可能太贵；实际答案是要么严格 NTP 纪律加监控症状，要么迁移到写入路径不依赖 wall clock 正确性的系统。

**Q2.** 一位新工程师为 10,000 节点微服务系统实现向量时钟。向量增长到每个消息 10,000 个条目，带宽成本不可接受。提出两种替代方案并讨论权衡。

提示

HLC 恒定扩展。dotted version vectors 压缩稀疏向量。若跨租户交互罕见，每会话或每租户向量有效。

**答案：** 两种替代方案：

(a) HLC。用 HLC 替换向量时钟。每条消息携带一个 (l, c) 对，而非 10,000 项向量。权衡：HLC 尊重 happens-before 但无法检测并发。如果应用需要并发检测（CRDT 合并、冲突解决），单用 HLC 不够，还需要每键版本向量或类似机制。

(b) 每租户或每会话向量。如果跨微服务交互按租户聚类（每个请求属于一个租户，租户数据互不交互），则每个租户维护一个向量。向量大小是触及某租户数据的服务数，通常几十而非 10,000。权衡：协议层需要“租户”或“会话”概念，对真正跨租户的操作会失效。

第三条路，dotted version vectors（DVV），适合存储数据而非每条消息的逻辑时钟。DVV 压缩稀疏向量（大多数条目不活跃），Riak 使用过。对活跃消息系统，DVV 没有直接帮助，因为每个活跃服务都会贡献。
