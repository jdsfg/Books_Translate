二阶收益：如果请求已经在传播 trace context（用于分布式追踪，第20章），它们已经携带了足以跨服务正确排序日志事件的信息。用 wall clock 的日志系统把这些取证证据白白浪费掉。


### 本章总结

分布式系统讲的第一个谎言是时间。NTP 只给有界 _预期_ 漂移，不给有界 _保证_ 漂移。wall-clock 时间戳是事件偏序的有损代理。用跨机器时间戳比较来决定“哪个先发生”的代码是在对一个虚构概念做推理。

Lamport 的 happens-before 是正确的原语。Lamport 时间戳为每个事件分配一个整数，尊重 happens-before 但不能检测并发。向量时钟为每个进程每个事件分配一个整数，能检测并发，但扩展性差。混合逻辑时钟（HLC）结合 wall-clock 风格与逻辑计数器排序，保持恒定大小，是 CockroachDB、YugabyteDB、MongoDB 等 2026 系统的现代默认。

TrueTime 走硬件路线：每个数据中心 GPS 加原子钟，向应用暴露 `[earliest, latest]` 不确定性区间。Spanner 用 TrueTime 支付 7 ms commit-wait，换取线性化全局时间戳。AWS 的 clock-bound API 正在让 TrueTime 类原语在云厂商上可用。HLC 加已知偏移上界是该领域其余团队的实用替代。

本章开头的聊天消息排序函数有三个修复（HLC、向量时钟、CRDT），按严谨性递增。任一都正确；原版 `sorted(messages, key=lambda m: m.timestamp)` 错误。

第1章提到 Crescent 多区域支付系统用 HLC、fencing token 和 Raft 修复。现在你知道 HLC 的含义及为何它是正确原语。Fencing token 在第18章；Raft 在第9章；Spanner / CockroachDB / Calvin / TrueTime 在事务上下文中的完整比较在第13章。

第4章迈出下一步：既然我们能在机器间排序事件，就需要把事件 _可靠广播_ 给其他机器。可靠广播、原子广播、因果广播是共识赖以建立的原语。它们是“我有时间戳”与“所有人都认同该顺序”之间的层。
