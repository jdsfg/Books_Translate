LLM 请求路由与 Web 请求路由根本不同。Web 请求耗时 10-50 ms；路由到错误服务器的最坏成本是延迟翻倍。LLM 请求耗时 1-30 秒；路由到错误服务器的最坏成本是用户看到 30 秒转圈等待。

本章讲 2024-2026 年出现的两个技术，处理 LLM 专用路由问题：KV-cache-aware load balancing（把请求路由到有相关 cache 的服务器；重大效率收益）和 speculative decoding（用小 draft model 加速生成；可作为跨机分布式协议实现）。

### 26.1 LLM 请求路由问题

典型设置：N 个节点的推理集群，每个运行多个模型实例。请求到达负载均衡器；负载均衡器决定哪个节点处理每个请求。

朴素负载均衡（round-robin、least-loaded）错过 LLM 推理特有的关键机会：

(a) **KV cache locality**：若请求 prompt 的前缀已在某节点缓存，路由到该节点可节省缓存部分的 prefill 成本。路由别处则浪费缓存。

(b) **长度预测**：请求的预期输出长度影响正确路由。长输出请求应去能持续 decode 的节点；短输出请求可去任何地方。

(c) **模型可用性**：许多集群服务多个模型。路由必须考虑哪些节点加载了哪些模型。

(d) **尾部延迟**：LLM 推理的尾部延迟比 Web 请求宽得多（p99 30 秒正常）。差的路由决策对用户可见。

机会：考虑这些属性的路由决策可带来显著效率提升。Anyscale、Together、Fireworks 都发布过相关内容。
