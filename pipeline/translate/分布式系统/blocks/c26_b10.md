#### 深入思考

**Q1.** 辩护或反驳：“2026 年 LLM 推理已足够成熟，进一步优化只是增量。大的收益已过去。”

**讨论：** 辩护：主要架构收益（PagedAttention、RadixAttention、disaggregation、speculative decoding）已部署。剩余优化是增量：调优、硬件刷新、小型协议改进。2022-2024 年 5-10 倍收益不会再来。

反驳：领域仍快速演进。新技术不断涌现：更好的 speculative decoding（multi-token speculation、EAGLE、Medusa）、MoE 专用优化（expert routing、expert parallelism）、更激进量化（NF4、FP4 serving）、专用硬件（NVIDIA B100、B200 大幅提升）。每项单独是较小收益，但复合后，到 2028 年成本效率可再提升 2-3 倍。

综合：容易的收益已过；领域处于持续增量改进模式。保持前沿的团队继续捕获收益；“设好就忘” 的团队会落后。保持最新的累积收益是真实的，即使每步很小。

第二个考虑：硬件演进是主导杠杆。H100→H200→B100→B200 三代带来 2-3 倍每美元计算。软件优化与硬件复合；两者都保持最新才是正确策略。

2026 现实：大推理平台（Anyscale、Together、Fireworks、AWS Bedrock、Azure OpenAI）在推理成本上竞争。竞争推动持续优化。Continuum 的优化冲刺不是可选；它是保持竞争力所必需。

**Q2.** 一个 LLM 被要求 “为我们集群实现 KV-cache-aware 路由”。它产出一个带哈希检查的基本 least-loaded 均衡器。指出遗漏什么。

**讨论：** LLM 的基本方法：哈希 prompt，检查是否有节点缓存该哈希，若有则路由过去。

遗漏什么：

(a) **前缀匹配，而非精确匹配**。LLM 的哈希检查只匹配完全相同 prompt。真实工作负载的 prompt 共享 _前缀_（system prompt + 不同用户消息）。需要 radix tree 或类似前缀索引。

(b) **缓存新鲜度跟踪**。KV cache 会过期（内存压力、TTL）。路由器必须知道哪些缓存仍然有效；路由到缓存已被 evict 的节点无收益。

(c) **负载感知**。即使某节点有缓存，它可能已超载。路由器必须平衡缓存局部性与当前负载。

(d) **缓存层集成**（对使用 Mooncake/LMCache 的集群，第25章）：缓存层是共享的；任何节点可读。路由器应考虑这点：基于哪个 decode 节点有容量来路由，然后该节点从缓存层读取。

(e) **客户亲和性**：对 workload 可预测的客户（相同 system prompt），把客户流量 pin 到特定节点以最大化缓存复用。

(f) **冷启动 fallback**：若没有节点有缓存，路由器回退到默认负载均衡（least-loaded、round-robin 等）。

(g) **指标和可观测性**：缓存命中率、每请求节省、per-customer 缓存效率。
