#### 概念检测

**Q1.** 用你自己的话陈述每个分布式系统都会说的三个谎言。对每个谎言，给出一个具体代码示例，说明该代码假设谎言为真。

提示

三个谎言是时间、身份和失败。寻找代码模式：跨机器比较时间戳、假设锁持有者是唯一的、假设 RPC 要么成功要么明显失败。

**答案：** 三个谎言是时间、身份和失败。

_时间_ ：假设机器时钟可比较的代码。示例：`if user_event.timestamp < server_event.timestamp: process_in_order()`。这比较了客户端机器时间戳和服务器机器时间戳，没有考虑时钟偏移。NTP 在好日子里能让机器保持在毫秒级以内；坏日子或防火墙后，它们可能漂移数秒甚至更多。这种比较可能产生错误顺序，代码会静默按错误顺序处理事件。

_身份_ ：假设某个进程独一无二地是“领导者”，却没有协议证明这一点的代码。示例：`if redis.set("leader_lock", node_id, nx=True, ex=30): become_leader()`。这是 Redlock 模式（第18章）。它假设持有锁 30 秒就意味着没有其他节点持有它。在网络分区或 GC 暂停下，两个节点可能都相信自己持有锁，两者都会作为领导者行动。

_失败_ ：只有 happy path、把失败当作异常的代码。示例：`result = remote_service.call(); update_local_state(result)`。`remote_service.call()` 可能在远端成功而响应丢失，可能明显失败，可能挂起未知时长，或者如果网络或传输层重试它，可能被送达两次。把成功视为默认、把可见失败视为例外，忽略了最大的一类：部分可见性。

**Q2.** Crescent 事件涉及在不稳定移动连接上的一次单一重试。对每个谎言分别走一遍，什么本可以预防它？为什么单一修复不够？

提示

每个谎言需要不同纪律。幂等 token 解决一个。fencing token 带来的协调者唯一性解决另一个。时钟偏移有界的时间戳解决第三个。

**答案：** 对于失败谎言，请求上的幂等 token 会让第二个协调者的重试被识别为“我已经处理过这个事务 ID”并拒绝——第二次提交变成 no-op 而不是重复扣款。银行的幂等性检查本应做到这一点，但窗口太短；第二个请求刚好落在窗口外。

对于时间谎言，使用混合逻辑时钟（HLC）时间戳（第3章）而非 wall-clock 时间戳，会让两个协调者得到相同的可比较顺序。任一协调者都会看到另一方的提交在 HLC 时间中先发生，即使两者都在 NTP 时钟的 5 ms 窗口内完成。

对于身份谎言，协调者角色上的 fencing token（第18章）会让银行拒绝第二次提交，因为第二个协调者的 token 会低于第一个。即使两者都相信自己是活跃协调者，银行也会根据单调 token 顺序知道该信任哪一个。
