* **团队规模**：小团队 → NIM（现成企业）；有平台工程师的大团队 → vLLM（自建企业特性）。
* **合规紧迫性**：3 个月内 SOC 2 审计 → NIM（更快）；12 个月 timeline → 两者都可。
* **定制化需求**：重度定制 → vLLM（完全控制）；标准服务 → NIM（集成优于灵活）。
* **成本敏感度**：非常敏感成本 → vLLM 加自定义集成；CapEx 灵活 → NIM。

对 Continuum（重度基础设施用户，有平台团队）：vLLM 加自定义企业特性合理。对大多数 enterprise IT 商店：NIM 是正确答案。

**Q3.** 某团队推理集群出现双峰延迟：短请求快，长请求阻塞短请求。诊断并提出修复。

提示

队头阻塞。连续批处理有帮助；优先队列帮助更大；分离预填充/解码是架构修复。

**答案：** 双峰延迟是队头阻塞。长请求占用资源（GPU 内存、每步计算时间）；短请求在其后等待。

修复，按影响排序：

(a) **连续批处理**（若尚未）：短请求可与长请求同批次。每步并行处理所有请求；短请求生成完自己的 token 即完成，不受长请求影响。这消除大部分队头阻塞。

(b) **优先队列**：短请求和长请求分别走不同队列。短请求批次快速处理；长请求批次按自己节奏处理。权衡：更难最优共享 GPU 资源。

(c) **分离预填充和解码（第25章）**：长请求问题常在于预填充（处理 10000-token 提示需要数秒）。若预填充与解码在不同节点，短请求的解码不会被长请求的预填充阻塞。

(d) **限制最大请求大小**：把提示限制为 N token（足够小以不阻塞其他请求）。拒绝更大提示并返回结构化错误；调用者必须分块或使用不同端点。

(e) **Speculative decoding（第26章）**：对长生成，投机解码可提速解码 2-3 倍；长请求完成更快，缩短短请求等待时间。

对 Continuum：连续批处理可能已经就位（现代引擎都有）。下一步影响最大的是分离式预填充/解码（第25章）。架构改动大，但收益（消除双峰延迟）是用户可见的改善。
