#### 应用问题

**Q1.** 一个团队的电商应用用 Cassandra + LWW 维护用户资料。他们开始收到用户资料编辑被静默覆盖的报告。诊断并给出修复建议。

提示

写节点间时钟偏移可导致 “逻辑上更晚” 的写输掉。检查 NTP 纪律并考虑每个字段处理。

**答案：** 诊断：Cassandra 协调节点间时钟偏移。当用户从设备 A 编辑资料（通过协调器 A），紧接着又从设备 B 再次编辑（通过协调器 B），若 A 时钟快于 B，A 的较早写会按 LWW 胜出，即使 B 的编辑逻辑上更晚。

用户看到：“我编辑了，但编辑没生效。” 从用户视角应用坏了。

修复：

(a) **严格 NTP 纪律** ：确保所有 Cassandra 节点保持小范围漂移（10-50 ms）。这减少但不能消除缺陷；残差概率小但非零。

(b) **服务端时间戳 + 每个资料指定单一协调器** ：通过 `user_id` 的一致哈希把某用户所有写路由到同一协调器。单一协调器时钟能正确排序该用户的写。Cassandra 通过 session-level 路由支持。

(c) **轻量事务（LWT）** ：资料更新使用 `UPDATE ... IF` 子句。LWT 用 Paxos 提供每个行线性化语义。代价：每次写延迟 4-10 倍。对资料编辑（不频繁操作）可接受。

(d) **每个字段 CRDT** ：对合并语义明确的字段（如 “tags” 字段可用 CRDT 集合；“last_updated” 可用带 HLC 的 LWW），使用 CRDT 语义。对简单 LWW 字段（名称、邮箱），LWT 路径处理。

(e) **迁移到 CRDT 感知系统或 NewSQL** ：对新开发，选择默认提供正确一致性模型的系统。CockroachDB（可串行化）以更高写成本消除此类缺陷。

建议：短期部署 (a) + (c)。长期若工作负载增长或用户投诉持续，评估 (e)。

**Q2.** 一个团队为流分析流水线构建 Apache Flink，需要端到端 “精确一次” 保证（从 Kafka 来源到 Postgres 接收端）。Chandy-Lamport 风格的 checkpointing 如何使之可能？

提示

Checkpoint 捕获一致状态；故障时从上一个 checkpoint 重启。接收端必须幂等或两阶段提交。

**答案：** Flink 的精确一次依赖三个组件：

(a) **来源重放** ：Kafka 允许从已知 offset 重放消息。Checkpoint 记录每个来源已读的 offset；重启后来源从该 offset 恢复。

(b) **Checkpointed 操作者状态** ：Flink 的 checkpoint 协议（Chandy-Lamport 变体）记录数据流中每个算子状态。重启后每个算子从 checkpoint 恢复状态。

(c) **Transactional 接收端** ：接收端（此处 Postgres）必须参与 checkpoint。两种策略：

* **幂等写** ：接收端记录每个唯一事件 ID 并忽略重复。本质上接收端可安全重处理。
* **两阶段提交接收端** ：checkpoint barrier 到达时接收端在 Postgres 事务中准备写；Flink 确认 checkpoint 完成后提交。
