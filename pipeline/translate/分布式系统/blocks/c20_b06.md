_基于尾部的 sampling_ ：跨度被缓冲到 trace 完成（或超时）。基于 trace 整体属性做决策（例如 “保留所有含错误的 trace；成功 trace 采样 1%”）。只有被选中的 trace 被导出到存储。

优点：可保留所有错误 trace；可保留所有慢 trace；可基于结果选择。缺点：需要缓冲基础设施（通常几分钟的 trace 数据）；更复杂；数据可查询的延迟高于基于头部的。

何时适用：

* **基于头部的**：简单部署；统一采样率；对延迟敏感的基础设施。绝大多数 OpenTelemetry 部署从基于头部的开始。

* **基于尾部的**：聚焦错误和异常值的部署；大舰队中统一 1% 采样会漏掉太多错误；有基础设施支持大规模缓冲和决策的团队。

实践中，许多大规模系统两者都用：基于头部的处理主体；基于尾部的在之上捕获错误/异常值。混合最大化覆盖同时控制成本。

**Q4.** 为什么追踪上下文必须跨越共识边界持久（例如跨越 Raft apply）？

提示

请求流过共识；共识 apply 侧因果上是下游。没有上下文，trace 断裂。

**答案：** 流过共识协议（CockroachDB 事务、Kafka publish-with-confirm、Raft 复制状态变更）的请求，其工作在共识 apply 侧发生：当共识日志条目被应用到状态机时，下游效果产生（写磁盘、发送通知等）。

这些下游效果因果上是原始请求的一部分。若追踪上下文没有通过共识日志传播，apply 侧的工作看起来是独立的 trace，与发起请求断开。

对调试：若请求因在 apply 侧出问题而失败（如状态机拒绝条目），没有链接 apply 与原始请求的追踪上下文，无法诊断。

对取证：支付系统中，原始支付请求与 apply 侧放款必须链接在 trace 中。没有链接，审计链不完整。

实现：追踪上下文包含在共识日志条目的元数据中。apply 代码运行时提取上下文，并为它创建的任何跨度使用。现代 Raft 库（etcd 的 Raft、raft-rs）直接支持；旧库可能不支持。

更深观察：trace 价值随分布式系统复杂度增加而增加。对简单两服务架构，trace 有用但非必需。对内含共识的 50 服务 mesh，trace 是主要调试工具；缺失上下文传播是严重的运维缺口。
