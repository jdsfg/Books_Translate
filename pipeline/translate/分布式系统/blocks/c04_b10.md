现在假设 P1 只发给了 P2 就崩溃，然后 P2 在重广播前也崩溃。P3 和 P4 就收不到 m。可靠广播在此失败。一致可靠广播会通过要求 P2 等到收到多数进程的 ack 后才“向上交付”来防止；按此规则，P2 的本地交付不会发生，于是“要么全要么无”的一致性得以维持。

**Q3.** 因果广播用向量时钟实现。对 1000 节点系统，向量是每条消息 1000 项。指出两种让大 N 可实践的策略。

提示

压缩稀疏向量。按更小组划分，向量大小受组规模限制。

**答案：** 两种策略：

(a) **Dotted version vectors（DVV）** 或稀疏向量。若大多数条目为零（大多数进程最近未贡献消息），只存非零条目。Riak 使用过类似技术。成本是检测条目何时可丢弃（该进程“跟上”到足以让其条目隐含）的记账。当贡献呈突发且按进程聚类时效果良好。

(b) **分层 / 分组因果广播** 。把进程分组（例如按区域或租户）。每条消息携带每个group 向量（组大小条目）加一个每区域摘要。跨组因果以较粗粒度跟踪。可扩展 gossip 系统就是这样做的；代价是跨组因果近似而非精确。

第三种选择：对某些应用用 _causal+ consistency_ 加每键版本向量替代因果广播。每个键有一个 contributors 向量；向量随键的写作者数增长，而非系统大小。这是 CRDT 模式；广播层退化为“可靠”，因果性由数据类型承载。Yjs 和 Automerge（第16章）使用这种方法。

对大多数 2026 系统，正确的问题是：应用是否真的需要 _所有_ 消息的因果广播，还是因果可以限定在每个实体或每个房间操作？前者很少成立；后者通常够用。
