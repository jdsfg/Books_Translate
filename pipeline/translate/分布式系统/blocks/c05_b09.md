(c) 读修复异步运行。读可能返回旧值（因为它联系节点时的多数），并触发后台修复，使后续读正确，但本次读无济于事。

修复方案：

(a) **对资料更新使用轻量事务（LWT）。** `UPDATE ... IF` 子句强制 Paxos 轮，是线性化的。代价：受影响操作延迟 4-10 倍。

(b) **用 HLC 做客户端 LSN 跟踪** ：跟踪写的时间戳；同一会话的后续读拒绝返回早于写时间戳的数据。Cassandra 原生不支持；应用层封装可实现。或切换到原生支持的 CockroachDB/YugabyteDB。

(c) **把 read-your-writes 流量路由到主副本** ：若应用知道某键的“主”节点（Cassandra 有自然副本顺序；顺序中第一个常是写协调者），在写之后的一段时间内把读发到那里。Cassandra 的 “PER_REPLICA_DC” 或类似协调者感知模式能做到。

通用教训：quorum 读/写规则给的是相交，不是线性一致性。需要 read-your-writes 的应用必须显式实现它。

**Q3.** 为一个客户端跟踪 HLC 的系统写 read-your-writes 伪代码。走查当客户端从落后的 follower 读时会发生什么。

提示

客户端跟踪 max-HLC-observed。读请求带“最小所需 HLC”。服务器要么等待，要么返回该 HLC 的数据，要么拒绝。

**答案：**


    class Session:
        def __init__(self):
            self.max_hlc = (0, 0)

        def write(self, key, value):
            result = db.write(key, value)
            # 服务器返回写提交时的 HLC。
            self.max_hlc = max(self.max_hlc, result.hlc)
            return result

        def read(self, key):
            # 请求数据的最小 HLC 为 self.max_hlc。
            result = db.read(key, min_hlc=self.max_hlc)
            # 服务器返回数据及读取时的 HLC。
            self.max_hlc = max(self.max_hlc, result.hlc)
            return result.value

    # 服务器端读处理器：
    def handle_read(key, min_hlc):
        while server.local_hlc < min_hlc:
            # 等待复制追上，或超时后拒绝。
            sleep(1ms)
            if elapsed > timeout:
                raise StaleReplicaError
        return read_local(key, at_hlc=server.local_hlc)


当客户端从落后的 follower 读时：该 follower 的 `local_hlc` 小于 `min_hlc`。处理器要么等待（直到复制把它带到最新）要么拒绝（返回 “stale replica” 错误）。拒绝后客户端要么重试不同副本，要么重试主库。

CockroachDB 和 YugabyteDB 使用这种模式的变体。HLC 作为 SQL 连接会话状态的一部分自动传播；应用无需显式跟踪。

代价：慢读路径上的等待或拒绝延迟。收益：任何会话的 read-your-writes 自动生效，无需 per-application 路由逻辑。
