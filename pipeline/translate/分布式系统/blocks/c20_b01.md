一位用户报告：“我点击提交后收到 500 错误。”该请求跨越两个区域接触了 14 个服务；在这 14 跳中的某处出了问题。找出原因就是分布式追踪问题。

本章讨论追踪的分布式系统特定方面：因果保持、分区下采样、跨共识边界的 trace context。本章范围受限：深入的 OpenTelemetry pipeline 细节属于 Series IV Vol 3（可观测性）。本章聚焦追踪所支持的分布式系统推理。


### 20.1 为什么需要分布式追踪

单体应用中，stack trace 告诉你发生了什么：哪个函数调用了哪个，错误在哪里。分布式系统中，等价物是 _trace_：请求跨服务的因果链。

分布式 trace 由 _spans_ 组成。每个 span 代表一个工作单元（接收到的请求、被调用的函数、下游 RPC）。Spans 有父子关系，形成一棵树（或 DAG）。根 span 是初始请求；子 span 是父请求触发的下游工作。

每个框是一个 span；箭头是 parent → child 关系。根的子节点是 _串行_ 阶段（非并行）；它们时长相加约等于根总时长（65 + 22 + 80 + 95 + 30 + 73 ≈ 365 ms p50）。DB transaction 的四个子节点在事务内部也是串行的；总和（93 ms）接近 DB span 总时长（95 ms），2 ms 差异反映事务协调开销。该图让工程师立即看出哪个 span 主导延迟（本例中是跨区域 DB transaction 和 fraud check）。

每个 span 携带：

* Trace ID（每个请求唯一；整个 trace 所有 span 共享）。
* Span ID（每个 span 唯一）。
* Parent span ID（根为 null）。
* 时间戳和时长。
* 服务名和操作名。
* 状态（成功、错误、代码）。
* Attributes（自定义键值对）。
* Events（span 内的时间戳日志条目）。

一个典型请求可能产生 50-500 个 spans，取决于服务深度。存储所有 trace 在大规模下不现实；采样决定保留哪些 trace。
