#### 概念检测

**Q1.** 描述 2PC 的两个阶段。协议的经典失败模式是什么？

提示

阶段 1：prepare；投 yes/no。阶段 2：commit 或 abort。失败：协调者在阶段 1 后崩溃。

**答案：**

阶段 1（Prepare）：协调者向所有参与者发送 PREPARE。每个参与者验证、将操作持久化为 prepared 状态，并投 YES（就绪）或 NO（必须中止）。

阶段 2（Commit 或 Abort）：若全部投 YES，协调者发送 COMMIT；参与者 finalize。若任一投 NO（或超时），协调者发送 ABORT；参与者丢弃。

经典失败：协调者在发送 PREPARE 后、尚未发送 COMMIT/ABORT 前崩溃。参与者已投 YES 并持锁；无法自行决定（协调者可能在崩溃前已提交）；无限期等待协调者。

现代修复：通过共识（Raft、Paxos）复制协调者状态。协调者不再是活性单点；任何节点可接管并查询复制状态。Spanner、CockroachDB、FoundationDB 都用此模式。

**Q2.** 什么是 Google Percolator？它如何避免需要中心协调者？

提示

Percolator 用事务中的 “primary key” 作为原子提交点。恢复由读者而非协调者执行。

**答案：** Percolator 是 Google 的分布式事务协议，构建于 Bigtable 之上，用于网页索引流水线。它通过两阶段（Prewrite + Commit）在键值存储上实现快照隔离事务，无中心协调者。

如何避免协调者：事务指定其中一个键为 _primary_。原子提交点是 primary 行上的单次变更（在时间戳处提交 value 并清除锁）。Secondary 键的锁指向 primary；任何遇到 secondary 锁的读者沿指针到 primary 了解事务结果。

若客户端在协议中途崩溃，由读者恢复：任何后续 reader 遇到陈旧锁时检查 primary 状态。若 primary 已提交，secondary 锁代表已提交写；否则可丢弃。清理由读者摊销；无需单独恢复进程。

用于：TiDB（Percolator 派生），以及概念上大多数 KV 快照隔离设计。
