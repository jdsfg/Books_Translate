### 16.3 List CRDT：协作文辑的核心

List（文档正文）是最复杂的常见 CRDT。挑战：两个副本独立在不同位置插入字符；合并必须产生一致的全序。


#### Logoot / Treedoc / WOOT

早期 list CRDT（2000 年代中期）。每个字符被分配一个 _position identifier_，位于相邻字符之间。Position identifiers 长度任意（通常是整数数组）；A 和 B 之间（id 1.2 与 1.5）插入的新字符获得 id 1.3 或 1.4。1.3 与 1.4 之间再插入则取 1.35；递归继续。

Position identifier 给字符排序；list 就是排序序列。插入是本地的；合并做 pair 并集。

局限：对抗性编辑下 position identifiers 可能变长（交替插入可使 id 长度翻倍）。删除字符的垃圾回收微妙。


#### RGA（Replicated Growable Array）

另一种方法：每个字符带一个 ID（通常是 (timestamp, replica)）和一个指向其 “前驱”（插入位置后的字符）的指针。列表通过拓扑排序重建。

同一位置的并发插入按 ID 顺序（或副本顺序作为平票）解析。结构类似树；线性化是树遍历。


#### Yjs 的实现

Yjs（Kevin Jahns 约 2014 年启动）使用 RGA 的优化变体。每个字符由一个小结构体表示（约 8 字节），包含其时钟、client ID 和指向前驱的指针。该结构对常见情况高度优化（顺序打字产生字符链，每个指向前一个）。

Yjs 在 Notion、Linear 等众多系统生产中运行。库很小（~80 KB），用 TypeScript / WebAssembly 实现。


#### Automerge 的实现

Automerge（Martin Kleppmann、Adam Wiggins 等）使用类似的 RGA-like 方法，但优化不同。Automerge 注重 git-like 的文档历史；数据结构包含完整变更历史，支持时间旅行和丰富的合并 UI。

Automerge 2.x（2023 年发布）是重大重写，将性能提升到生产可接受水平。早期版本在大规模下有内存问题；2.x 使用 Rust + WebAssembly，效率更高。

2026 年 Yjs 与 Automerge 的选择：

* Yjs：bundle 更小、高频编辑更快、功能较少（无内置历史 UI）。
* Automerge：更丰富的历史模型、稍重、更 “git-like” 语义。

对 Glide 协作文档编辑器，Yuki 选择 Yjs，因为 bundle size 重要（Glide 在浏览器运行，包括慢网络），且其文档模型比 Automerge 完整历史图更简单。
