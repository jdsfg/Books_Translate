#### 做得对的地方

(a) 协议在线：客户无停机体验。

(b) 整个过程中集群事务一致性保持（Raft 处理 per-range 领导权转移；强一致性不中断）。

(c) 协议可逆：若中间检测到问题，可暂停并回滚飞行中状态。

(d) 协议可并行：多个 range 同时移动，受网络和磁盘吞吐限制。


#### 可能出错的地方

(a) **Range 大小估算错误** ：若系统对 range 大小的元数据过期，重平衡计划可能移动过多或过少数据。修复是定期重新估算，集群每小时执行。

(b) **流式期间复制滞后** ：若网络饱和，目标节点通过 Raft log replay 追赶耗时超过预期。修复是在移动期间节流其他流量。

(c) **移动期间节点故障** ：源或目标节点故障需要重新规划移动。集群的 Raft group 继续服务（per-range 多数不受影响），因此用户可见影响只是短暂降级。

纪律是运维层面的：runbook 是多年移动略出问题的经验结晶。Anya 的 runbook 有 47 项检查清单；她逐项勾选。


### 12.6 B+ Tree 作为替代

LSM-tree 主导现代分布式数据库存储底层，但 B+ tree（只在叶节点存数据的 B-tree 变体）并未过时。B+ tree 仍占优之处：

* **Postgres** ：默认 B+ tree 索引。成熟、理解充分。
* **MySQL InnoDB** ：B+ tree。
* **SQL Server、Oracle** ：B+ tree 主存储。

B+ tree 优势：

* 可预测读延迟（一条 root-to-leaf 路径；深度有界）。
* 低空间放大。
* 成熟运维工具（数十年优化）。

B+ tree 劣势：

* 随机写成本（每次更新可能修改不同页）。
* 页级锁（或 MVCC 开销）。

现代结论：对读主导、写率较低的 OLTP 工作负载，单节点数据库中的 B+ tree 仍然优秀。对高写吞吐、尤其是分布式场景，LSM 是正确底层。
