(a) 发起者记录自身状态并向每条出通道发送 _marker_。发起者开始在每条入通道上记录收到的所有消息。

(b) 其他每个进程首次收到 marker 时，记录自身状态，将收到 marker 的通道标记为 “快照期间为空”，向每条出通道发送 marker，并开始在每条其他入通道上记录消息。

(c) 当进程在已开始记录的通道上收到 marker 时，停止在该通道记录；已记录的消息就是在途集合。

记录的状态代表什么：系统的 _一致全局状态_。各进程状态加上各通道在途消息合在一起，形成某个时刻可能真实发生过的状态。

“可能真实发生” 是关键：存在某个合法事件序列，使得记录状态就是系统在该时刻的状态。协议并不命名该时刻具体何时（实际上它可能不对应任何单一物理时钟时刻），但快照是系统的一个 _合法_ 状态。

这是分布式 checkpointing 的基础结果。Apache Flink 的精确一次语义建立于 Chandy-Lamport（或其变体）；Spark、MapReduce 等批处理系统使用相关思想。

**Q4.** 什么是 “最后写入 wins”（LWW）冲突解决，它的失败模式是什么？

提示

LWW：时间戳最高的写胜出。失败：时钟偏移可导致 “逻辑上更晚” 的写输掉。

**答案：** LWW：当同一键的两个写冲突（并发，由未看到对方的副本发起）时，时间戳更高的写胜出。另一个被丢弃。

失败模式：时间戳依赖机器时钟（第3章），而机器时钟可能漂移。若 “逻辑上更晚” 的写被标上更早时间戳（因其写入节点时钟慢），LWW 会丢弃逻辑上更晚的写，而选择逻辑上更早的写。

Cassandra 的 “tombstone resurrection” 缺陷（第5章）是经典示例：由于时钟偏移，删除的时间戳早于后续写；后续写 “胜出” 并复活了已删记录。

抵御 LWW 失败模式：

* 严格 NTP 纪律；漂移超过小阈值时告警。
* 使用服务端时间戳（由协调者在数据库分配时间戳）而非客户端。
* 对正确性关键数据，使用轻量事务（Cassandra LWT）或迁移到基于 HLC 的 MVCC（CockroachDB）。

更深层问题：LWW 在结构上是会丢失信息的。按设计，冲突写会丢失信息（被丢弃的写消失）。对 “丢失” 可接受的数据（如资料字段最后更新），LWW 没问题。对 “丢失” 不可接受的数据（如交易日志），LWW 错误；应用需要 sibling 值或 CRDT。
