### 27.4 谎言 3：机器时钟说真话

LLM 生成代码：


    def merge_events(events_from_replicas):
        return sorted(events_from_replicas, key=lambda e: e.timestamp)


谎言：时间戳跨机器可比较。代码用时间戳排序事件，不考虑时钟偏移或因果性。

现实：跨机器时钟最好情况下可能差数十毫秒，最坏情况差数秒。时间戳非常接近的事件无法可靠用 wall clock 排序。应由因果性排序的事件（回复发生在其父事件之后）可能被时钟偏移颠倒。

修复：用 happens-before、HLC 或 vector clock（第3章）排序。


    def merge_events(events_from_replicas):
        # 按 HLC 排序（假设事件带有正确 happens-before 传播的 HLC 时间戳）
        return sorted(events_from_replicas, key=lambda e: (e.hlc.l, e.hlc.c, e.replica_id))


LLM 产出 wall-clock 版本因为它是最简单的排序表达式。HLC 版本需要理解时间的谎言。


### 27.5 谎言 4：朴素分布式锁有效

LLM 生成代码：


    def process_unique_action(action_id):
        if redis.set(f"action_lock:{action_id}", "1", nx=True, ex=30):
            do_critical_work(action_id)
            redis.delete(f"action_lock:{action_id}")


谎言：持有 Redis key 意味着唯一性。代码用 Redlock 风格锁保护正确性关键操作。

现实：没有 fencing token 的 Redlock 在进程暂停、时钟漂移和 Redis failover 下失败。两个客户端可能都相信自己持有锁；两者都调用 `do_critical_work`；关键工作被污染。

修复：用 consensus-backed 锁（etcd、Consul）并在被保护资源上加 fencing token。


    def process_unique_action(action_id):
        token = etcd_lock.acquire(f"action:{action_id}", ttl=30)
        try:
            do_critical_work(action_id, fencing_token=token)
        finally:
            etcd_lock.release(token)

    def do_critical_work(action_id, fencing_token):
        # 存储层拒绝 stale token 的写
        db.atomic_write(action_id, ..., max_token=fencing_token)


LLM 产出 Redis 版本是因为 Redlock 风格代码在训练语料中（尤其旧博客）。修复需要理解第18章教训（Kleppmann 对 Redlock 的批评）。
