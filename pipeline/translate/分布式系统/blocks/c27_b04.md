### 27.6 谎言 5：部分故障罕见

LLM 生成代码：


    def update_user_across_systems(user):
        primary_db.update(user)
        cache.update(user)
        notification_service.notify(user.id, 'updated')


谎言：三个调用一起成功。代码只有 happy path；部分故障是隐含的。

现实：调用相互独立；任何都可能失败。`primary_db.update()` 成功但 `cache.update()` 之前，缓存已过期。两者都成功但 `notification_service.notify()` 之前，通知未发出。系统处于不一致状态。

修复：识别哪些调用对一致性关键，并用 saga 模式（第13章）或 transactional outbox。


    def update_user_across_systems(user):
        # 关键：DB 更新。失败即中止。
        primary_db.update(user)

        # 尽力：缓存和通知。用 outbox 模式。
        outbox.enqueue(InvalidateCache(user.id))
        outbox.enqueue(NotifyUser(user.id, 'updated'))

    # 异步 worker 处理 outbox；失败时重试。


LLM 产出朴素版本是因为训练数据显示 “做 A；做 B；做 C” 是常见模式。“若 A 成功但 B 失败会怎样？” 的纪律是 LLM 不会自然进行的工程思考。


### 27.7 谎言 6：CAP 分类简单

LLM 生成代码：


    # 注释：我们用 CockroachDB，它是 CP，所以是一致的。
    def get_account_balance(account_id):
        return db.query("SELECT balance FROM accounts WHERE id = %s", account_id)


谎言：“CP” 意味着 “完全一致”。代码注释显示 LLM 在应用口号级 CAP，不理解 per-operation 行为。

现实：CockroachDB 默认读写事务是可串行化（serializable）；读可以在领导者（per-operation linearizable）或跟随者（bounded-staleness）。这段代码中的查询，没有显式配置，可能线性化也可能不是，取决于连接设置。带 `AS OF SYSTEM TIME` 或通过跟随者-read 设置的读可能返回旧数据。

修复：每个操作显式一致性选择。


    def get_account_balance_authoritative(account_id):
        # 线性化读；显式强制 leader replica
        with db.transaction() as tx:
            return tx.query("SELECT balance FROM accounts WHERE id = %s", account_id)

    def get_account_balance_cached(account_id):
        # 展示用途有界旧数据可接受
        return db.query("SELECT balance FROM accounts WHERE id = %s AS OF SYSTEM TIME '-10s'", account_id)


LLM 产出第一版加误导注释是因为口号级 CAP 陈述在训练数据中过度代表。修复需要理解 PACELC（第2章）和具体数据库的 per-operation 语义。
