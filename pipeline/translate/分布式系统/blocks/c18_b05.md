### 18.4 缓存作为锁的反模式

一个特定反模式：没有 fencing token 时把缓存当分布式锁。


    # WRONG
    if cache.set("user_processing_lock_42", "1", nx=True, ex=10):
        process_user(42)
        cache.delete("user_processing_lock_42")


这种模式因简单而诱人。失败原因除了 Redlock（进程暂停、时钟漂移、缓存故障）还有缓存特有原因：

(a) **缓存故障转移**：Redis Sentinel 提升副本；新 master 可能尚未复制锁 key；另一个客户端获得锁；两个持有者。

(b) **缓存内存驱逐**：内存压力下 Redis 驱逐 key；锁 key 被驱逐；另一个客户端获得锁；两个持有者。

(c) **缓存崩溃**：Redis 崩溃；锁 key 在重启后丢失（RDB 或 AOF 可能没持久化最近变更）；另一个客户端获得锁；两个持有者。

修复：对需要正确性的锁不要用缓存。用 etcd、Consul 或 ZooKeeper 做锁；在受保护资源上执行 fencing token。性能代价小（锁获取罕见）；正确性收益大。

对纯效率锁（job queue 去重、幂等提示），基于缓存的锁可以。纪律在于知道自己属于哪种情况。
