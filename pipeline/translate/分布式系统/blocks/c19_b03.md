### 19.4 基于 DNS 的发现

最简单的发现机制，常被忽视。服务在 DNS 中注册地址；客户端通过 DNS 查询找实例。

性质：

* **通用**：每种语言和运行时都支持 DNS 解析。
* **可缓存**：DNS 响应被缓存；发现服务负载低。
* **简单**：无需专用客户端库；标准 DNS API。

局限：

* **TTL 粒度**：DNS TTL 通常 30-300 秒；更新传播慢。失败实例可能在 TTL 过期前仍被返回给客户端。
* **无 watch 原语**：客户端在 TTL 边界轮询 DNS；无推送通知。
* **元数据有限**：DNS 记录只带 IP 和端口；更丰富元数据需要 SRV 或 TXT 记录，并非所有客户端库都能优雅处理。

用例：

* **云厂商服务发现**：AWS Cloud Map、GCP Cloud DNS、Azure DNS 提供托管的 DNS 后端发现。适合成员变化少的服务。

* **Kubernetes headless 服务** ：“headless” Kubernetes 服务没有集群 IP；客户端解析服务名得到所有 pod IP。Kubernetes DNS 插件透明处理。

对成员稳定的服务（数据库、有状态服务），DNS 通常足够。对成员快速变化的服务（自动扩缩无状态服务），基于 watch 的发现（etcd、Consul）响应更快。


### 19.5 配置即数据 with Watch 流

一个超越服务发现的更广泛模式：把配置作为数据存在协调服务中，客户端 watch 变更。

模式：

(a) 配置以键形式存在 etcd/Consul/ZooKeeper（或支持 watch 的配置数据库）中。

(b) 消费配置的服务启动时 watch 相关键。

(c) 配置变更时 watch 触发；服务接收新配置并重新配置（无需重启）。

(d) 对需要跨服务一致性的配置，配置存储使用共识。

示例：

* **功能开关**：跨所有服务切换功能，无需重新部署。
* **限速**：根据负载动态调整限速。
* **路由规则**：流量路由策略（金丝雀发布、A/B 测试）。
* **密钥 rotation**：不重启服务即可分发轮换后的密钥。


#### 常见陷阱

(a) **Watch storms**：若很多服务 watch 很多键，一次配置变更可同时触发数千 watch 事件，压垮发现服务。

(b) **重配置竞争**：若服务正在执行操作时配置变更，在操作中途应用新配置会导致不一致。解决：在明确边界（请求之间）应用配置变更。

(c) **不一致读**：并非所有配置存储都提供线性化读。一个服务读到 `feature_flag_X = true`，另一个读到 `false`，可能产生意外用户体验。解决：对影响用户可见行为的配置使用线性化读。

(d) **配置漂移**：未能应用配置变更的服务（因缺陷、网络故障）静默漂移出同步。解决：每个服务显式 ack，监控过期。
