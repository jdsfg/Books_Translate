可辩护的精确答案：“MongoDB 在副本集中可用 `writeConcern: majority, readConcern: linearizable` 配置成按操作线性化。默认配置是最终一致（writeConcern 1，从 secondary 读）。跨分片事务提供快照隔离。团队必须为每次操作有意识地选择适合的一致性级别；系统默认不是最强级别。”

这是正确答案的形状：精确说明配置、操作、保证。说“MongoDB 一致”毫无意义；说“MongoDB 用此配置可线性化”可执行。

**Q3.** 一家初创公司在 Cassandra 和 ScyllaDB 之间为分析工作负载选择。对两者应用诊断方法，然后综合建议。

提示

ScyllaDB 与 Cassandra 兼容但用 C++ 编写，采用每核心一个分片。协议家族相同，实现不同；比较性能、运维特征。

**答案：** 两者诊断画像相同（共享协议）：

问题 | 答案（两者）
---|---
Replication 协议 | 无领导者；按请求可调一致性
故障恢复 | 基于 gossip；超时后排除节点
一致性模型 | 可调：默认最终，LWT 线性化
Partition 行为 | 可调；低一致性 AP，法定人数 CP
PACELC | 可调；低一致性 PA/EL，法定人数 PC/EC

差异在实现：

方面 | Cassandra | ScyllaDB
---|---|----
实现 | Java（JVM） | C++（每核心一个分片）
内存个人资料 | 受堆限制（GC 停顿） | 无堆（无 GC 停顿）
每个节点throughput | ~50,000 操作/秒 | ~500,000 操作/秒
运维的复杂度 | 高（compaction 调优、GC 调优） | 中等（架构已处理大部分）
生态系统 | 更大（项目更老） | 成长中；Cassandra 兼容 API
成本 | 开源；众多云托管服务 | 开源 + ScyllaDB Cloud

对分析工作负载（通常高吞吐、可容忍最终一致）的综合：

若 (a) 每节点吞吐重要（希望更少但更强大的节点）、(b) GC 停顿是问题（延迟敏感分析）、(c) 运维团队熟悉 C++ 栈调试，选 ScyllaDB。若 (a) 团队已深度熟悉 Cassandra、(b) 更广泛的生态重要（现有 Cassandra感知的工具）、(c) 每节点吞吐不是瓶颈，选 Cassandra。

对没有历史包袱的新创公司，2026 年新分析工作负载的默认很可能是 ScyllaDB。10 倍每节点吞吐优势意味着更少节点、更简单拓扑、更低成本。诊断方法显示（两系统逻辑画像相同）切换实现不会丢失任何东西。
