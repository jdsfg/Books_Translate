可辩护的精确答案：“MongoDB 在副本集中可用 `writeConcern: majority, readConcern: linearizable` 配置成按操作线性化。默认配置是最终一致（writeConcern 1，从 secondary 读）。跨分片事务提供快照隔离。团队必须为每次操作有意识地选择适合的一致性级别；系统默认不是最强级别。”

这是正确答案的形状：精确说明配置、操作、保证。说“MongoDB 一致”毫无意义；说“MongoDB 用此配置可线性化”可执行。

**Q3.** 一家初创公司在 Cassandra 和 ScyllaDB 之间为分析工作负载选择。对两者应用诊断方法，然后综合建议。

提示

ScyllaDB 与 Cassandra 兼容但用 C++ 编写，采用 shard-per-core。协议家族相同，实现不同；比较性能、运维特征。

**答案：** 两者诊断画像相同（共享协议）：

Question | Answer（两者）
---|---
Replication protocol | 无 leader；按请求可调一致性
Failure-recovery | 基于 gossip；超时后排除节点
Consistency model | 可调：默认最终，LWT 线性化
Partition behavior | 可调；低一致性 AP，quorum CP
PACELC | 可调；低一致性 PA/EL，quorum PC/EC

差异在实现：

Aspect | Cassandra | ScyllaDB
---|---|----
Implementation | Java（JVM） | C++（shard-per-core）
Memory profile | 受堆限制（GC 停顿） | 无堆（无 GC 停顿）
Per-node throughput | ~50,000 ops/sec | ~500,000 ops/sec
Operational complexity | 高（compaction 调优、GC 调优） | 中等（架构已处理大部分）
Ecosystem | 更大（项目更老） | 成长中；Cassandra 兼容 API
Cost | 开源；众多云托管 offering | 开源 + ScyllaDB Cloud

对分析工作负载（通常高吞吐、可容忍最终一致）的综合：

若 (a) 每节点吞吐重要（希望更少但更强大的节点）、(b) GC 停顿是问题（延迟敏感分析）、(c) 运维团队熟悉 C++ 栈调试，选 ScyllaDB。若 (a) 团队已深度熟悉 Cassandra、(b) 更广泛的生态重要（现有 Cassandra-aware 工具）、(c) 每节点吞吐不是瓶颈，选 Cassandra。

对没有历史包袱的新创公司，2026 年新分析工作负载的默认很可能是 ScyllaDB。10 倍每节点吞吐优势意味着更少节点、更简单拓扑、更低成本。诊断方法显示（两系统逻辑画像相同）切换实现不会丢失任何东西。
