对 Crescent：Olamide 事故后三年建立了以上每项。团队分布式代码质量显著改善；涉及六个谎言的新事故罕见。投资（审查时间、混沌测试、培训）巨大；事故成本更高。


### 本章总结

线程 C 的 LLM 关于分布式系统的六个谎言：(1) RPC 有 TCP 式语义；(2) 网络可靠；(3) 机器时钟说真话；(4) 朴素分布式锁有效；(5) 部分故障罕见；(6) CAP 分类简单。每个都是 LLM 生成分布式代码的默认模式。

LLM 生成分布式代码默认嵌入谎言。缺陷沉默（不抛异常），单元测试不可见，只在生产故障场景下可见。成本高：重复扣款、丢失写、脑裂、级联故障。

审查清单（10 项）：幂等性、超时、带预算重试、熔断器、排序原语（HLC 而非物理时钟）、由共识支持的锁加围栏 token、部分故障处理（saga/outbox）、显式一致性选择、追踪上下文传播、可观测性。每份分布式代码 PR 按清单审查，捕获高频失败。

为什么 LLM 结构性地不擅长分布式代码：训练数据偏差（简单模式过度代表）；模式匹配而非推理；不变量在代码中不可见；测试抓不到缺陷；缺陷沉默。

2026 含义：AI 辅助代码生成对很多事有用；对分布式代码，需要人类用清单审查。LLM 是生产力工具；不是分布式系统思考的替代品。使用 AI 辅助的团队必须投资审查纪律；没有纪律的团队产出的分布式代码每月都会重现第1章的重复扣款失败。

AI 辅助审查（§27.10）处理约 60% 检查清单——语法和习惯模式。人类分布式系统判断处理剩余 40%——上下文适配、业务不变量、架构选择、新模式。三层架构（AI 审查→人类按清单审查→发布前混沌验证）是 2026 生产纪律；跳过任何一层都会产生可预测缺口。对 AI 审查 PR 橡皮图章是被点名的反模式。
