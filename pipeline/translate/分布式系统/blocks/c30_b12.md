#### F.6 — 常见反模式：何时不该伸手选显而易见的选择

上述决策树偏向 “选什么”。同样重要的是何时 _不_ 选诱人的系统。以下是 Olamide 团队在新晋工程师身上看到的最常见 2026 反模式：

**刚遇到扩展 pain 就不要伸手选 NewSQL。** 一个团队 PostgreSQL 在 50k QPS 出现 p99 延迟问题，通常不需要 CockroachDB；它需要的是读副本、更好的索引、连接池和 Redis 缓存。迁移到 NewSQL 的成本真实（运维学习曲线、每次写入延迟增加、license 成本）；迁移应被 _结构性_ 需求触发（多区域需求、超出单节点硬件的横向写入扩展、监管数据驻留），而非第一次 p99 尖峰。

**单区域 Postgres + 读副本足够时不要伸手选 Spanner。** Spanner 是最干净的多区域系统，但它的 commit-wait 延迟每次写入都要支付。对单区域工作负载，Postgres 生态成熟度和每次写入延迟通常更好。只有真正需要其能力时才支付 Spanner 成本。

**团队需要 SQL 灵活性时不要伸手选 DynamoDB。** DynamoDB 的可预测按请求成本和低延迟是真实好处，但代价是严格的数据建模纪律（PK 设计、GSI 设计、无连接）。习惯 “丢一个查询过去” SQL 灵活性的团队会与 DynamoDB 持续斗争。只有当数据模型真正匹配其访问模式时才选 DynamoDB。

**3 节点集群就能搞定时不要伸手选 Cassandra。** Cassandra 的运维故事（tombstone、compaction、逐节点维护）是真实的工程工作。对能被 3 个任意节点服务的工作负载，Cassandra 的运维税不划算。Cassandra 在 100+ 节点集群中才值得，此时其横向扩展是必需的。

**10 个服务不需要时不要伸手选服务网格。** Istio/Linkerd 增加运维复杂度。对小型服务图，Kubernetes 原生服务发现足够。只有在多区域、多协议、复杂流量需求真实存在时才采用服务网格。

**崩溃故障共识足够时不要伸手选 BFT。** BFT 需要 3 倍副本和运维成本。对操作者可信、节点相当安全的团队，崩溃故障共识（Raft）是正确选择。BFT 属于特定高风险垂直领域（区块链、跨组织金融结算、国防），而非主流。

**按用户地理分区数据足够时不要伸手选 Spanner 风格全局线性化。** 大多数以用户为中心的工作负载（聊天、社交、生产力）可通过将每个用户数据放置在一个区域来服务。全局线性化是最昂贵的一致性级别；只有当工作负载真正需要所有用户的全局排序时才支付它。

统一模式：**系统的成本每天都在支付；收益可能只在罕见场合才需要。** 选择每天成本匹配工作负载每天需求的系统，并接受罕见场合（跨区域分区、热键竞争等）可能支付额外成本。
