#### 关注点 1：因果保持

追踪上下文（trace ID、parent 跨度 ID、采样决策）必须从每个父跨度传播到每个子跨度，跨服务边界。

标准传播：HTTP headers（W3C 标准的 `traceparent`、`tracestate`）或 gRPC metadata。服务接收请求时从 headers 提取追踪上下文；它创建的跨度使用该上下文。

陷阱：

* **异步边界上下文丢失**：服务把工作交给后台队列但未传播追踪上下文，会产生 “断裂” trace（下游工作无父节点）。修复：通过队列传播追踪上下文（Kafka headers、SQS message attributes）。

* **协议转换时上下文丢失**：服务从 HTTP 转换到自定义二进制协议可能丢失追踪上下文。修复：在协议边界显式传播逻辑。

* **重试时上下文损坏**：同一操作重试应产生独立跨度（trace 中显示重试），而不是与原跨度合并。修复：每次重试创建新的子跨度。


#### 关注点 2：分区下采样

Traces 通常被采样（只有 1% 或更少的请求被详细追踪），因为存储每条 trace 很贵。

采样决策通常在根跨度做出：若根跨度被采样，则所有子跨度也被采样（trace 完整）。这是 “基于头部的” 采样。

分区下，采样决策传播可能丢失。部分跨度被采样，其余没有；trace 不完整。修复：采样决策冗余编码（在追踪上下文加每跨度 attribute 中）。

基于尾部的 sampling（trace 完成后再决策）更复杂但更强：跨度必须被缓冲到 trace 完成，然后 retroactively 应用决策。这需要更多基础设施，但允许基于结果采样（“保留所有错误 trace；成功 trace 采样 1%”）。


#### 关注点 3：跨共识边界的追踪上下文

当操作流过共识协议（Raft、Paxos）时，追踪上下文必须持久通过共识轮次。否则共识 apply 侧与发起请求无关联。

在 Raft 中，追踪上下文可存在日志条目元数据中。跟随者 apply 条目时，apply 代码使用存储的上下文。这要求应用的 Raft 库支持上下文传播；并非所有都支持。

对共识日志是不可变历史（Kafka、区块链）的系统，追踪上下文是事件数据的一部分。后续处理器使用嵌入的上下文。

更深观察：分布式追踪是事件所发生事情的取证记录。对历史记录重要的系统（审计、合规、调试数月前问题），追踪上下文是系统永久状态的一部分，不只是可观测性 artifact。
