#### E.5 — GitHub MySQL 24 小时降级，2018-10-21

* **触发**：GitHub 两个主数据中心之间 43 秒网络分区导致 MySQL Orchestrator failover 自动化在东海岸设施选出新主库，而西海岸原主库仍活着。
* **放大**：分区愈合后，系统有两个主库且数据分歧。恢复需要手动协调分歧写入（在协调数据期间整个集群只读）。
* **时间线**：24 小时服务降级；完全恢复约 24 小时。
* **恢复**：大量手动数据协调，部分提交永久丢失。
* **章节映射防御**：
    * Ch.18（分布式锁，fencing token）：failover 自动化缺少 fencing token；新主库不应能在旧主库仍自认为主库时写入。
    * Ch.7（共识，防止 split-brain）：基于共识的 leader 选举可防止双主状态。
    * Ch.5（复制，主库 failover 纪律）：无 fencing 的 failover 模式正是第5章警告的。


#### E.6 — Google Cloud BigQuery 存储故障，2023-08-08

* **触发**：BigQuery 存储写入 API 的 bug 导致存储层开始拒绝特定表类的写入。
* **放大**：客户端应用重试；重试放大拒绝率；拒绝指标越过告警阈值，触发自动区域 failover，但 failover 不包含 bug 修复。
* **时间线**：受影响工作负载的 BigQuery 写入部分中断 4 小时。
* **恢复**：部署 bug 修复；手动重置区域 failover 状态。
* **章节映射防御**：
    * Ch.21（级联故障，重试风暴）：客户端层重试预算可限制放大。
    * Ch.22（灰色故障）："拒绝率飙升触发 failover" 循环是经典亚稳态模式；更好的 failover 纪律（跨区域 failover 需人工介入）有帮助。
    * Ch.27（审查清单）：bug 修复应被审查 "跨区域回滚时会发生什么"；未覆盖到 failover-without-the-fix 场景。


#### E.7 — Fastly 全球 CDN 故障，2021-06-08

* **触发**：客户推送了一个有效配置，触发了 Fastly 基于 Varnish 的 CDN 平台中此前未知的软件 bug。该 bug 导致配置解析器在特定输入模式上崩溃。
* **放大**：坏配置被分发到全球所有 Fastly CDN 节点；每个节点崩溃；整个 CDN 同时离线。
* **时间线**：全球中断约 1 小时；主要网站（Reddit、Stack Overflow、Amazon、BBC）受影响。
* **恢复**：客户回滚配置；Fastly 节点恢复。
* **章节映射防御**：
    * Ch.19（config-as-data，watch streams）：配置 rollout 需要分阶段（canary region）；全局原子 rollout 是反模式。
    * Ch.23（混沌工程）："配置触发所有节点解析器崩溃" 应作为 game-day 场景。
    * Ch.21（级联故障）：同时全球崩溃是无阶段 rollout 的最坏情况。
