(f) **磁盘满**：节点活着但无法写入。专门故障。

(g) **内存压力 / GC 暂停**：节点活着但慢。专门故障。

(h) **配置变更**：部署、schema 变更、feature flag。本身不是故障，但与系统交互的运营事件。

Chaos Monkey 测试一个切片（“实例故障” 切片）。完整混沌工程学科测试其他切片。进阶：Chaos Monkey 用于基本实例故障韧性；Chaos Mesh、Toxiproxy 等专业混沌工具用于其他故障模式；game day 用于协调场景。

运行 Chaos Monkey 两年没有重大中断的团队只建立了一个韧性切片。他们应扩展：增加网络分区混沌、慢节点混沌、为区域故障运行 game day。每次扩展都会发现新问题。

更深观察：混沌工程不是 “完成” 的状态。它是随系统成长的持续实践。随着系统增加功能、集成新依赖、扩展到新区域，混沌面也在增长。成熟混沌工程实践把它视为持续投资，而非一次性里程碑。

**Q3.** 某团队 game day 发现一个真实 bug（导致数据损坏的竞态条件）。他们现在争论：继续计划的后续 game day，还是先暂停修复 bug。分析。

提示

继续 game day 与暂停修复。Bug 真实；继续可能发现更多问题；先修复确保下一次 game day 测试正确的东西。

**答案：** 两种选择都有道理；正确答案取决于 bug 严重程度和团队带宽。

_继续 game day_ ：

* 优点：每次 game day 都揭示更多问题；团队建立行动项清单并按优先级修复。
* 缺点：已知 bug 仍在生产环境；间隙期间有客户影响风险。

_暂停并修复_ ：

* 优点：已知 bug 快速修复；后续 game day 测试已移除 bug 的系统（更有用数据）。
* 缺点：game day 计划推迟；其他问题可能更久未被发现。

推荐因素：

(a) **Bug 严重程度**：若是数据损坏（如示例），属于高严重。立即暂停修复；不要继续可能让更多客户暴露于损坏的 game day。

(b) **修复复杂度**：若修复小（几小时），暂停并修复；恢复 game day。若修复大（几周），不要阻塞所有 game day；继续不触发该 bug 的限定范围 game day。

(c) **生产影响**：bug 是否已影响客户？若是，修复紧迫性最高。若只在特定条件下触发，更灵活。

(d) **团队带宽**：小团队带宽有限必须优先；暂停一件事做另一件事。大团队可并行推进。

对 Olamide 的假设场景（故障转移下重复扣款）：bug 严重高（客户可见数据损坏）；修复复杂度可能中等（单团队几天可解决）。推荐：暂停大型 game day；可继续小范围 targeted 实验验证修复；修复验证后恢复常规 game day 计划。
