凌晨 2:17，on-call 告警响起：“面向客户的错误率飙升到 14%。” Olamide 打开监控面板。每个节点都是绿色。CPU 正常。内存正常。健康检查都返回 200 OK。面板是绿的；客户却遇到错误。

二十分钟后她找到问题：一个节点的磁盘静默降级。原本 1 ms 的读取现在要花 100 ms。健康检查是廉价的仅 RAM 端点——从不触碰磁盘，所以它在 1 毫秒内返回 200。负载均衡器信任 200，继续把流量路由到慢节点，客户看到挂起。

这是灰色故障（gray failure）模式。节点按健康检查定义 “活着”，但按应用定义 “死了”。灰色故障及其表亲亚稳态故障（metastable 故障，2021 年的形式化框架）是最难检测和恢复的生产故障模式。本章讲两者。

愚弄 Olamide 监控的失败，部分源于 LLM 对健康检查的默认建议：


    @app.route('/healthz')
    def 健康():
        return 'OK', 200


> 说明性伪代码；缺陷在于检查 _没有_ 锻炼的内容（真正的 I/O 路径），而非语法。

该检查快速、廉价，但对捕获灰色故障是错的。即使节点以 30 秒延迟服务真实请求，它仍返回 200。


### 22.1 灰色故障

经典定义：一个进程响应其监控（通过健康检查），但从应用视角看实际上是坏的。“监控说活着” 与 “用户看到坏了” 之间的缺口就是灰色故障窗口。

示例：

(a) **慢节点**。节点磁盘降级；原本 1 ms 的读取现在 100 ms。健康检查是廉价的仅 RAM 端点；快速返回 200。应用请求触及磁盘时变慢；用户体验挂起。负载均衡器继续路由流量到慢节点。

(b) **内存压力**。节点内存 90%；GC 暂停越来越长。健康检查在 GC 之间完成；返回 200。应用请求在 GC 触发时暂停；延迟是双峰的（快或 30 秒）。

(c) **过期状态**。节点本地缓存损坏；返回错误答案但不报错。健康检查检测不到错误答案；节点 “活着”。

(d) **网络黑洞**。节点能接收入站流量但无法发出出站流量（防火墙配置错误、网卡问题）。健康检查（从监控接收，返回值未严格验证）通过；需要下游调用的应用请求挂起。

(e) **嘈杂邻居导致的 CPU 竞争**。共享环境（云、Kubernetes）中的节点与另一租户争夺 CPU；延迟剧烈波动。健康检查在嘈杂邻居发威前完成；通过。

模式：故障真实存在（用户看到问题）但未被检测（监控是绿的）。运维在客户报告到达之前是盲目的。
