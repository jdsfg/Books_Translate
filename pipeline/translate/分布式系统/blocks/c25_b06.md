对 Continuum 部署，缓存层是实现超长上下文和前缀复用的基础。对其工作负载需求，架构复杂度值得。

**Q3.** 为什么分离式架构的阈值大约是 50+ 节点？

提示

分离的运维开销（不同节点类型、传输逻辑、集群复杂度）；对小集群，收益不占优。

**答案：** 分离有运维成本：

(a) **两种节点类型**：预填充节点和解码节点。分离 Kubernetes 节点 pools；分离扩展策略；分离供应 and 退役逻辑。

(b) **KV 缓存传输逻辑**：把 KV 缓存从预填充传输到解码的代码；处理传输期间故障；与路由层协调。

(c) **更复杂的负载均衡**：请求必须基于可用性分配到 (预填充, 解码) 对；分配可能需要重新平衡。

(d) **可观测性复杂度**：追踪必须跨阶段跟踪请求；指标必须区分预填充和解码工作。

(e) **故障模式**：预填充中途失败；解码生成期间失败；缓存传输失败。每种都需处理。

对小集群（5-10 节点），运维开销占主导。效率收益（更好利用率）只转化为几个百分点的成本节省，但运维复杂度增加工程时间和风险。

对大集群（50+ 节点），效率收益可观：

* 1M+ USD/月成本下 40% 容量提升即每月 40 万美元节省。
* 运维复杂度在更多节点上摊销。
* 团队规模足以 justify 专门平台工程师做分离逻辑。

阈值与工作负载相关：50 节点但统一的短提示工作负载的集群可能不受益（预填充成本相对解码小）。30 节点但重长提示工作负载的集群可能受益（预填充成本是瓶颈）。

Tobias 的 Continuum 集群（50 节点，混合工作负载）处于阈值。6 个月分离投资值得；更小集群可能不值得。

**Q4.** 一个请求流过分离式架构。列出延迟组件和近似值。

提示

预填充、KV 缓存传输、解码每个 token。各自贡献首 token 和每个 token 延迟。

**答案：** 典型请求（1000-token 提示，200-token 输出）的延迟组件：

(a) **网络入口**：约 5 ms（负载均衡器到推理节点）。

(b) **预填充**：1000-token 提示在计算优化 GPU 上约 100 ms。

(c) **KV 缓存传输**：5 GB KV 缓存经 400 Gbit/s RDMA 约 50 ms。

(d) **首 token 生成**：解码节点上约 30 ms（一个解码步）。

(e) **首 token 总计**：约 185 ms（网络 + 预填充 + 传输 + 首解码）。

(f) **后续每 token**：约 30 ms。

(g) **200 输出 token 总计**：约 185 ms（首 token）+ 199 × 30 ms（其余）= 约 6.2 秒。

对 co-located（未分离）架构，首 token 延迟可能约 150 ms（预填充 + 首解码，无传输），但每个 token 延迟类似。分离版为首 token 多付约 50 ms（传输）；吞吐收益来自集群整体更好的每 GPU 利用率。
