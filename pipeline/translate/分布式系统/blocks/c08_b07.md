(b) 领导者上任伊始对所有未来槽跑一次第一阶段（“为槽 [current_slot, \infty) prepare” 模式）。

(c) 对每个要提交的新值，领导者只跑第二阶段（ACCEPT）。承诺过领导者投票的接受者会接受。

每决定成本是一次往返（ACCEPT + ACCEPTED），而非两次（PREPARE + PROMISE + ACCEPT + ACCEPTED）。对服务多个决定的稳定领导者，摊销效果显著。

若领导不稳定（频繁重选），每次重选都要跑第一阶段。实用 Multi-Paxos 系统追求领导稳定数分钟到数小时。

**Q4.** 为什么 Paxos 以难正确实现著称？说出三个运维关注点。

提示

持久状态、重配置、快照、fsync 纪律、Multi-Paxos 优化。

**答案：** Paxos 难实现有多个运维原因：

(a) **持久状态纪律** ：接受者必须在回复 prepare 或 accept 消息 _之前_ 把 $b_{max}$、`accepted_ballot`、`accepted_value` 持久化到可靠存储。若接受者丢失该状态（磁盘故障、漏 fsync、文件系统损坏），它会“忘记”先前 promise 并接受冲突值，违反安全性。

(b) **重配置** ：改变接受者集合（增删节点）不能随意，因为两个不同配置可能各自形成无重叠的“多数”。标准解是 “joint consensus” 或 “alpha-paxos” 模式，但正确实现微妙。

(c) **快照与日志截断** ：Paxos 日志无限增长；生产系统必须给状态机快照并截断日志。快照必须与该点日志状态一致；截断太激进会让恢复中的副本没有足够日志追赶。

还有三条（任一条都曾引发生产故障）：

(d) **稳定领导维护** ：Multi-Paxos 依赖稳定领导；若网络不稳定导致领导频繁更替，每次更替都花第一阶段往返并可能暂停集群。

(e) **读一致性** ：提供线性化读要么需要一轮共识（慢），要么需要基于 lease 的捷径（快但 lease 实现微妙）。

(f) **故障期间成员变更** ：分区期间移除故障节点危险；分区愈合后“被移除”节点可能 resurfacing，导致配置不一致。

累积效应：Paxos 实现通常是数千行谨慎代码。上述任何 bug 都可能导致数月后才显现的静默安全性违反。“正确 Paxos 实现很少”并非夸张。
