#### 概念检测

**Q1.** 描述 Redlock 模式。根据 Kleppmann 的批评，它为什么不提供正确性？

提示

Redlock：让多数 Redis master 设置锁 key。失败：进程暂停、时钟漂移。修复：fencing token。

**答案：** Redlock：客户端通过在 N 个 Redis master（通常 5 个）上设置唯一值作为 key 来获取锁。若多数（3/5）在超时内成功，则获得锁。锁有 TTL；客户端通过删除 key 释放（需验证 value 与 nonce 匹配）。

Kleppmann 的批评：Redlock 不提供正确性，因为：

(a) _进程暂停_ ：客户端获得锁后暂停（GC、VM 暂停）。从 Redis 看 TTL 过期。另一个客户端获得锁。原客户端恢复，以为自己仍持有锁，并操作受保护资源。两个写入者同时行动。

(b) _时钟漂移_ ：锁的 TTL 基于 Redis 时钟；客户端对时间的看法可能不同。两者对锁是否仍有效可能意见不一。

两者都是基于超时协议的知名问题，也适用于许多朴素分布式锁方案，不只是 Redlock。

修复是 fencing token：锁服务在每次获取时颁发单调递增 token。受保护资源跟踪已接受的最高 token；任何更低 token 的操作被拒绝。即使两个客户端都以为自己持有锁，只有 token 更高者能行动。

Redlock vs fencing token 的争论是分布式锁正确性的经典读物。Kleppmann 的博客文章是必读。

**Q2.** 什么是 fencing token，它如何修复分布式锁正确性问题？

提示

单调递增计数器；存储拒绝更低 token；即使两个客户端持有 “锁”，只有更高 token 能行动。

**答案：** Fencing token 是锁服务在每次锁获取时分配的单调递增计数器。每次获取获得一个比之前任何已发 token 严格更高的新 token。

该 token 伴随受保护资源的每个操作。资源跟踪已接受的最高 token；更低 token 的操作被拒绝。

如何修复正确性问题：

* 若客户端 A 用 token 100 持有锁并暂停（TTL 过期），客户端 B 用 token 101 获得锁。A 随后到达资源的 token 100 操作被拒绝（资源已见过 101）。A 的过期锁状态无法伤害系统。

* 时钟漂移不影响 token：锁服务的计数器是权威，而非任何客户端时钟。

* 分区愈合：若网络分区，两个客户端各自获得它们认为的锁（若锁服务用共识则不可能，但对朴素设置可以想象），token 不同。资源只接受更高 token。

Fencing token 把安全责任从 “锁服务保证唯一性” 转移到 “受保护资源强制执行排序”。结构上更健壮：即使锁服务有 bug（对同一把锁发了两个 token），资源的单调检查也能捕获。

代价：受保护资源必须实现 token 跟踪。许多存储系统（数据库、消息队列）原生不支持 fencing token；应用或中间件必须叠加。对正确性关键用例，这是必要工作。

**Q3.** 基于缓存的 Redlock 式锁何时可接受，何时不可？

提示

效率用例可接受（重复只是浪费但不灾难）。正确性用例不可接受（重复是灾难）。
