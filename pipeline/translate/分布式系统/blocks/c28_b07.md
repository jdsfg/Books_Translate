### 28.5 四位主角的视角

每位主角都有贡献和收获：

**Olamide（SRE 主管）**：“架构健壮，因为我们提前支付了分布式系统正确性的成本。三年前，我们交付的系统内置了六个谎言；我们用事故为之买单。对混沌工程、可观测性和诊断方法纪律的投资，造就了一个 ‘刚刚好使’ 的系统。”

**Anya（Stratus DB 主管）**：“带 fencing token 的 Raft 复制协调器是系统安全的核心。集成到 Crescent 技术栈很直接，因为 Stratus DB 从一开始就用这些模式设计。诊断方法（第11章）是我们向 Crescent 团队推销集成的方式；他们对 Stratus 运行了该方法，验证了其 profile 匹配需求。”

**Yuki（从 Glide 借调）**：“商户入驻合同编辑器使用 Yjs。协作编辑 ‘刚好工作’，因为 CRDT 确定性地处理冲突。与 Crescent 的认证和审计追踪系统集成是难点；编辑器本身很容易。”

**Tobias（从 Continuum 借调）**：“欺诈检测推理是 sub-100-ms p99（p50 80 ms；与 §28.2 记录一致），得益于分离式架构和 KV-cache-aware 路由。集成只是一个简单 HTTP endpoint；Crescent 的 API 服务调用我们的 endpoint；我们返回分数。复杂度在我们这边；Crescent 这边微不足道。”

四个视角说明 2026 现实：复杂分布式系统由组合组件构建，每个组件来自拥有深厚专长的团队。本书纪律在每个层级都适用：组件内部（CockroachDB 用 Raft、TigerBeetle 用 VSR）；跨组件（通过 HTTP、Kafka、trace propagation 一致集成）；架构层级（每个工作负载做 PACELC 分析、混沌工程做端到端验证）。
