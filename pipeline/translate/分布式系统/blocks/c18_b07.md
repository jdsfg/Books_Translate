**答案：** 缓存锁（Redlock 或类似）在以下情况可接受：

(a) 锁用于 _效率_ ：只有一个工作节点应同时做昂贵工作。若偶尔两个工作节点都做（因锁失败），重复工作浪费但无害。

示例：任务队列去重、周期批处理任务调度、昂贵计算记忆化。

(b) 下游影响是幂等的：即使两个工作节点都执行，效果与一个相同。示例：工作节点写入带幂等键的数据库 “user_id seen”。

缓存锁在以下情况 _不可接受_ ：

(a) 锁用于 _正确性_ ：只有一个客户端应同时修改资源。若两个都做，资源损坏。

示例：支付提交、库存扣减、唯一名申领、做出不可撤销决策的领导者选举。

(b) 下游影响不是幂等的：每个动作都有真实世界效果（扣款、发邮件、发货）。重复动作造成真实世界的重复后果。

纪律：选择锁前先分类用例。正确性用例使用基于共识的锁（etcd、Consul、ZooKeeper）加围栏 token。效率用例可用缓存锁。

Crescent 支付协调者角色是正确性用例；修复使用围栏 token。Glide 处理用户上传的任务队列是效率用例；缓存锁即可。

**Q4.** 为什么 Crescent 修复同时组合 Raft 锁服务和围栏 token？而不是只用其一？

提示

Raft 提供安全锁获取；token 在资源处强制执行每次操作安全。

**答案：** 组合提供两层安全：

(a) **Raft 锁服务** ：保证锁获取本身是安全的。Raft 共识保证集群在任何时刻都就谁持有锁达成一致。没有它，朴素锁方案可能在分区或故障转移期间把同一把锁发给两个客户端。

(b) **受保护资源上的围栏 token** ：保证资源上的操作按 token 排序。即使锁服务出错（或锁持有者在别人获得锁后暂停恢复），资源强制执行单调 token 顺序。

两层覆盖不同失败模式：

* 只有 Raft：提供安全获取，但不防御客户端进程暂停。从 Raft 视角持有 “有效” token 的暂停客户端仍可在另一个客户端获得锁后操作资源。
* 只有围栏 token：提供操作级排序，但不提供 “当前持有者” 概念。没有锁服务，每个操作都要求资源与所有潜在持有者协商。

组合是正确生产模式。实践中：etcd 或 Consul 提供锁服务（基于 Raft）；应用在存储层实现围栏 token 检查（或依赖支持它的存储系统，如带版本列检查的数据库）。
