#### 同步

两种同步模式共存：

(a) **通过 WebSocket 实时同步** ：用户 actively 编辑时，其 update 被发送到服务器（带 Durable Objects 的 Cloudflare Worker）并广播给其他连接客户端。每次编辑延迟亚秒级。

(b) **重连时追赶** ：客户端离线后重连，与服务器交换 _state vectors_（“我有哪些 update” 的压缩表示），并接收缺失 update。

Cloudflare Worker 持有文档权威副本。它应用进入的 update 并广播给所有连接客户端。重连时，它计算客户端与服务器状态差并只发送所需内容。


#### 持久化

权威文档以 update 序列形式存在 Durable Object 存储中。定期地（约每小时），update 被 _compacted_ 成快照：文档被序列化，历史 update 被丢弃。

快照是 CRDT 历史的 “垃圾回收”。没有它，存储会无界增长。有了它，旧编辑被合并进快照，任何重连恢复都使用快照加后续 update。


#### 冲突解决

Yjs 自动处理所有冲突。若两个用户并发在同一位置插入字符，Yjs 按 client ID 和时钟确定性排序。若一个用户删除段落时另一个将其加粗，粗体属性保留在幸存字符上（未被删除的字符）；被删除的字符消失。

结果在运维上令人惊叹：用户独立编辑，有时离线数小时，合并却正确且无需弹窗。Glide 生产两年没有出现 “合并冲突对话框”。


#### 失败模式

系统不是魔法。失败模式：

(a) **并发相同动作** ：两个用户同时按 “删除文档”。CRDT 不帮忙；应用需要显式唯一动作语义，通常在服务器以轻量事务实现（Durable Object 接受第一次删除，拒绝后续）。

(b) **Schema migration** ：文档 schema 变更时（如新增字段类型），旧客户端的飞行中 edit 可能解析不正确。Yjs 的版本处理覆盖很多情况；应用以向后兼容层处理其余。

(c) **存储大小** ：重历史文档（编辑数月的文档）会累积状态。定期 compaction 必不可少；否则存储无界增长。

(d) **大量并发用户性能** ：单个文档超过约 100 个并发编辑者时，广播流量成为瓶颈。Glide 的方案是分片文档（1000 用户的文档被分成 per-section 子文档）。
