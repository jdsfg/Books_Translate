#### 概念检测

**Q1.** 描述服务发现问题及发现服务的作用。

提示

服务实例众多且来去；客户端需找健康实例。发现服务维护注册表。

**答案：** 服务发现：在微服务架构中，服务有多个实例，不断启动和停止（自动扩缩、部署、故障）。想调用目标服务的客户端服务必须动态发现哪些实例当前健康可达。

发现服务维护注册表：

(a) 每个服务实例启动时注册自己（地址、端口、元数据）。(b) 实例周期性 heartbeat 确认存活。(c) 其他服务查询注册表找目标服务实例。(d) 实例未 heartbeat（崩溃、分区）时从注册表移除。

现代发现服务：etcd、Consul、ZooKeeper、云厂商基于 DNS 的服务、Kubernetes API server。

发现服务本身是分布式系统。它需要共识（让所有客户端看到同一注册表）、高可用（不让服务间调用失败）和低延迟（不让调用被注册表查找延迟）。

**Q2.** 比较 etcd 与 ZooKeeper。为什么 etcd 在新系统中基本替代了 ZooKeeper？

提示

etcd：Raft、gRPC、Kubernetes 采用。ZooKeeper：老 API、ZAB 共识、较小的现代生态。

**答案：** etcd 和 ZooKeeper 都是分布式协调服务，具有相似原语（键值存储、watch、lease/ephemeral node）。

差异：

| Aspect | etcd | ZooKeeper |
|---|---|---|
| Consensus | Raft | ZAB（Paxos 变体） |
| API | 基于 gRPC，现代 | 较老的自定义协议 |
| Key model | 平铺 key + 前缀 watch | 层级 zNodes |
| Ecosystem | Kubernetes 原生使用 | Hadoop 生态（Kafka、HBase 历史） |
| Operational tooling | etcdctl；云原生 | zkCli.sh；较老模式 |
| Performance | 针对现代硬件优化 | 成熟但较老优化 |

etcd 替代 ZooKeeper 的原因：

(a) **Kubernetes 采用**：Kubernetes 选择 etcd；Kubernetes 的引力把 etcd 带到云原生基础设施的主导地位。

(b) **更好的运维模型**：Raft 比 ZAB 更易理解；etcd 的运维工具更精致。

(c) **gRPC 和云原生契合**：etcd 与现代云原生工具（Prometheus 指标、Helm charts、Kubernetes operators）集成良好。

(d) **Kafka 的 KRaft 迁移**：Kafka 作为 ZooKeeper 最大的单一用户，迁移到 KRaft（自己的 Raft 实现）。Raft 趋势广泛。

ZooKeeper 仍在生产中使用（KRaft 前的现有 Kafka 集群、HBase、一些旧 Apache 项目），但新系统通常从 etcd 开始。ZooKeeper 生态逐渐萎缩；etcd 生态逐渐增长。

**Q3.** 什么是 “config as data with watch streams”？举一个用例。

提示

配置作为数据存在协调服务中；客户端 watch 变更并动态重新配置。

**答案：** Config-as-data with watch streams：一种模式，配置作为数据存在协调服务（etcd、Consul）中，配置消费者 _watch_ 相关 key 的变更。配置变更时，消费者收到通知并动态重新配置自己。
