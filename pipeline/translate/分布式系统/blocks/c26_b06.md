投机解码现在已是生产推理引擎标准（vLLM 支持；SGLang 支持；有专门库）。2-3 倍吞吐本质上是免费（附加成本是运行草稿模型，很小）。

**Q3.** 何时把投机解码分布到多机有意义？

提示

当草稿模型可放在更便宜硬件；当验证模型被多请求共享。

**答案：** 在以下情况把投机解码分布到多机有意义：

(a) **草稿模型可放在更便宜硬件**。1B 参数草稿可放在小 GPU（甚至 CPU）。把草稿放在便宜硬件上，让昂贵大模型 GPU 做验证。

(b) **验证模型被多请求共享**。验证模型的 GPU 可并行处理多请求的验证（每请求一个验证步）。昂贵资源被摊销。

(c) **集群足够大以支持角色分离**。与 disaggregation（第25章）类似，分布式投机解码增加运维复杂度；大规模才划算。

(d) **草稿与验证间网络延迟有界**。每个 token round-trip 0.5-2 ms 可容忍；50+ ms round-trip 会抵消加速。

具体例子：100 张大模型 GPU + 20 张小模型 GPU 的集群。小模型 GPU 为所有请求做草稿；大模型 GPU 做验证。小 GPU 更便宜；大 GPU 利用率更高（始终处理验证）。

何时 co-located 投机解码更合适：

* 小集群，分布式运维开销占主导。
* 网络延迟会把首 token 延迟推到不可接受阈值的工作负载。
* 没有工程能力维护分布式协议的团队。

对 Continuum：他们规模下分布式投机解码合理。已发布的 Anyscale、Together、Fireworks 部署确认：在规模上，分布式获胜。

**Q4.** 什么是多租户推理集群的加权公平调度？

提示

每客户有权重；调度器按比例分配 GPU 时间；防止饥饿。

**答案：** 加权公平调度：每客户（或租户）有权重；调度器按权重比例在客户间分配 GPU 时间。

示例：三客户权重 5、3、2（共 10）。调度器目标让 GPU 花 50% 时间处理客户 1 的请求，30% 处理客户 2，20% 处理客户 3。

如何防止饥饿：即使客户 1 有很多请求排队，调度器也确保客户 2 和 3 得到 GPU 时间。没有客户被另一个客户的突发饿死。

实现模式：

(a) **令牌桶**：每客户有一个按权重速率累积 token 的桶。请求消耗 token；调度器从 token 最多的客户中挑选。

(b) **差额轮询**：每客户轮流处理；每轮每客户最多获得 N 单位 GPU 时间（N 与权重成正比）；超额工作等下一轮。

(c) **Hierarchical 调度**：客户可分组（如按层级）；调度器分层（层级内公平；层级间有优先级）。
