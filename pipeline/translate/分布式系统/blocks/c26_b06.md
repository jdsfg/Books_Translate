Speculative decoding 现在已是生产推理引擎标准（vLLM 支持；SGLang 支持；有专门库）。2-3 倍吞吐本质上是免费（附加成本是运行草稿模型，很小）。

**Q3.** 何时把 speculative decoding 分布到多机有意义？

提示

当草稿模型可放在更便宜硬件；当 verify 模型被多请求共享。

**答案：** 在以下情况把 speculative decoding 分布到多机有意义：

(a) **草稿模型可放在更便宜硬件**。1B 参数 draft 可放在小 GPU（甚至 CPU）。把 draft 放在便宜硬件上，让昂贵大模型 GPU 做 verification。

(b) **Verify 模型被多请求共享**。Verify 模型的 GPU 可并行处理多请求的 verification（每请求一个 verify 步）。昂贵资源被摊销。

(c) **集群足够大以支持角色分离**。与 disaggregation（第25章）类似，分布式 speculative decoding 增加运维复杂度；大规模才划算。

(d) **Draft 与 verify 间网络延迟有界**。Per-token round-trip 0.5-2 ms 可容忍；50+ ms round-trip 会抵消加速。

具体例子：100 张大模型 GPU + 20 张小模型 GPU 的集群。小模型 GPU 为所有请求做 draft；大模型 GPU 做 verification。小 GPU 更便宜；大 GPU 利用率更高（始终处理 verification）。

何时 co-located speculative decoding 更合适：

* 小集群，分布式运维开销占主导。
* 网络延迟会把首 token 延迟推到不可接受阈值的工作负载。
* 没有工程能力维护分布式协议的团队。

对 Continuum：他们规模下分布式 speculative decoding 合理。已发布的 Anyscale、Together、Fireworks 部署确认：在规模上，分布式获胜。

**Q4.** 什么是多租户推理集群的 weighted fair scheduling？

提示

每客户有权重；调度器按比例分配 GPU 时间；防止饥饿。

**答案：** Weighted fair scheduling：每客户（或租户）有权重；调度器按权重比例在客户间分配 GPU 时间。

示例：三客户权重 5、3、2（共 10）。调度器目标让 GPU 花 50% 时间处理客户 1 的请求，30% 处理客户 2，20% 处理客户 3。

如何防止饥饿：即使客户 1 有很多请求排队，调度器也确保客户 2 和 3 得到 GPU 时间。没有客户被另一个客户的突发饿死。

实现模式：

(a) **Token bucket**：每客户有一个按权重速率累积 token 的桶。请求消耗 token；调度器从 token 最多的客户中挑选。

(b) **Deficit round-robin**：每客户轮流处理；每轮每客户最多获得 N 单位 GPU 时间（N 与权重成正比）；超额工作等下一轮。

(c) **Hierarchical scheduling**：客户可分组（如按 tier）；调度器分层（tier 内公平；tier 间有优先级）。
