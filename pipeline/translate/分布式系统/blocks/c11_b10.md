#### 深入思考

**Q1.** 辩护或反驳：“诊断方法不完整，因为它没包含成本、生态和运维经验。这些因素常常主导技术评估。”

**讨论：** 辩护（该说法正确）：现实数据库采用中，成本、生态和运维经验通常是最重要因素。诊断方法给出技术阅读，但不给商业阅读。一个团队只选技术上最好的系统而不考虑成本或运维成熟度，往往会后悔。

反驳（方法足够）：诊断方法有意限定在技术评估。把成本、生态、运维经验也作为“问题”加入，会让方法变长且跨系统适用性降低。正确模型是：用诊断方法产出技术阅读，再把商业考虑叠加上去。

综合：书中呈现的方法是评估的 _技术_ 部分。完整评估还包括 (i) 成本（云账单、许可证、基础设施）、(ii) 生态（现有工具、招聘池、第三方支持）、(iii) 运维经验（团队既有知识、该技术的事故历史）、(iv) 战略考虑（厂商锁定、退出选项）。这些因素组织特定，需由评估团队自行添加。

Crescent 决策示例展示了两层：技术方法把选择缩到 Spanner vs CockroachDB；商业层（不锁 GCP、团队已有 Postgres 兼容技能）做出最终决定。两层都必要；单独都不充分。

**Q2.** 一个 LLM 被问“哪个数据库最好？”且没有更多上下文。它给出答案。为什么这个答案几乎肯定错，LLM 应该先问什么？

**讨论：** “最好”没有上下文无意义。LLM 被问时不知道：

* 工作负载的一致性需求（线性化、最终、介于两者之间）。
* 每次操作延迟预算。
* 部署范围（单区域、多区域、跨云）。
* 成本预算。
* 团队现有专长。
* 集成约束（必须与哪些其他系统协作）。
* 监管约束（GDPR、数据驻留、审计）。
* 规模（TB 或 PB；每秒行数）。

没有任何这些信息，LLM 只是在按训练数据平均产出观点，这过度代表流行系统（PostgreSQL、MongoDB、DynamoDB），低估特定上下文下应选的专业系统。

LLM 应该问：“工作负载需要什么？约束是什么？你想优化什么？”任何人类数据库顾问也会问同样问题。

更深观察：“最好数据库”这种问题没有上下文就没答案，而 LLM 若自信回答，正说明它不理解问题。更诚实的 LLM 会拒绝回答直到获得上下文，或产出“如果…那么…”答案，把工作负载特征映射到数据库选择。

诊断方法是桥梁：一旦 LLM（或人）知道工作负载，方法就把候选范围缩小到几个。然后领域专长（或进一步问题）在它们之间选择。
