### 23.3 Nora Jones 的组织实践

Nora Jones（与 Casey Rosenthal 合著《Chaos Engineering: System Resiliency in Practice》）是混沌工程组织方面的权威声音。

关键实践：

(a) **心理安全**。演练日必须让团队能无责地识别问题。若失败暴露运维缺口，讨论应是 “我们如何修复系统” 而非 “谁负责”。没有心理安全，团队会隐藏问题而非暴露。

(b) **无责复盘**。赛后讨论聚焦系统性原因（防御缺失、runbook 错误）而非个人错误。责备产生防御行为；系统改进需要诚实分析。

(c) **多元参与**。演练日不仅应包括 on-call 工程师，还应包括产品经理、客服代表、业务利益相关者。每个角色对 “系统崩溃意味着什么” 有不同视角。

(d) **记录学习**。每次演练日都产生书面产物：测试了什么、发生了什么、学到了什么、提交了哪些行动项。随着时间，这些产物形成系统故障模式的机构记忆。

(e) **固定节奏**。演练日不是一次性事件。每月或每季度节奏保持肌肉锻炼；新成员通过参与学习。

组织实践才是区分 “我们用 Chaos Monkey” 与 “我们有混沌工程学科” 的关键。工具容易；文化难。


### 23.4 工具

现代混沌工程工具：

(a) **Chaos Mesh**：Kubernetes 原生混沌工程。注入 pod 故障、网络故障、磁盘故障、时间偏移。广泛采用。

(b) **Litmus**：另一个 Kubernetes 混沌框架。云原生；基于 Helm 部署；可扩展。

(c) **Gremlin**：商业混沌工程平台。易用；面向企业团队。

(d) **AWS Fault Injection Simulator**：AWS 原生；注入 EC2 故障、RDS 故障、网络故障。适合 AWS 重度团队。

(e) **Toxiproxy**：TCP 层故障注入。慢连接、丢包、模拟下游变慢。与应用无关。

选择取决于部署：Kubernetes 原生部署用 Chaos Mesh 或 Litmus；AWS 原生部署用 FIS；需要商业支持用 Gremlin；跨平台团队用 Toxiproxy。
