#### 常见陷阱

(a) **缓存过期时的惊群（thundering herd）** ：多个读者在 key 过期时同时请求；全部未命中并涌向 source。缓解：概率性提前刷新；刷新期间 per-key 锁。

(b) **事故期间的缓存踩踏** ：truth source 变慢或宕机；所有缓存过期，所有读者击中慢 source，使其更慢。缓解：异常时提供过期数据（serve stale-on-error）。

(c) **失效竞争的过期数据** ：缓存被失效，但 truth source 写尚未提交；在失效与提交之间的一次读会用旧值刷新缓存。缓解：提交后再失效，失败时重试。

(d) **把缓存当作 truth source** ：开发者开始把缓存用于正确性；缓存无形中成为记录系统。缓存故障（Redis 崩溃、内存驱逐）后数据丢失。缓解：纪律；把缓存当缓存，而不是存储。

Crescent 系统在热读路径（账户余额查询、幂等键检查）使用 Redis Cluster。每个缓存条目有短 TTL（60 秒）；未命中时查询 truth source（CockroachDB）。事件驱动失效在每次提交时发布 “账户已变” 事件；缓存主动失效。


### 18.2 分布式锁

锁协调跨进程对共享资源的访问。朴素形式：在共享存储中放一个 key；key 持有者是锁拥有者。


#### Redlock 模式

Salvatore Sanfilippo（Redis 作者）提出 Redlock 作为分布式锁算法：

(a) 客户端选一个唯一值（随机 nonce）。(b) 客户端尝试在 N 个独立 Redis master（通常 5 个）上设置锁 key。(c) 若多数（3/5）在超时内成功，则获得锁。(d) 客户端持有锁一段时间 TTL；可通过删除 key 释放（需验证 value 与 nonce 匹配）。

意图：容忍少数 Redis master 故障；在集群上提供互斥。
