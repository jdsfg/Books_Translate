#### 应用问题

**Q1.** 一个团队设计全球聊天应用。任何区域的用户应在 500 ms 内看到来自任何区域的消息。团队在 (a) 中央 US-East 数据库供所有区域读，(b) 每区域数据库 + 异步跨区域复制，(c) 全局复制数据库（Spanner）之间选择。针对延迟需求评估各选项。

提示

计算每个选项最坏情况的跨区域往返。500 ms 是阈值；每个选项最坏情况交付多少？

**答案：**

(a) **中央 US-East DB。** 东京用户写；消息必须到达 US-East（单程 ~100 ms），持久化（~10 ms），然后东京用户可读（再 ~100 ms）。东京会话写后读往返约 210 ms；东京到悉尼的跨区域读也类似。500 ms 预算对多数路径够用，但用户体验不对称（东京用户所有操作都跨太平洋，感觉 lag）。

(b) **每区域 DB + 异步复制。** 东京用户写到东京 DB（本地、快）。写通过异步复制传播到其他区域（通常 <5 秒，常亚秒）。伦敦用户读同一聊天会在数秒内看到消息。写路径满足延迟预算；读路径有“最终”延迟，可接受与否取决于产品。聊天里“消息数秒内跨区送达”通常可接受；用户把这叫消息传递延迟，符合对消息的心理模型。

(c) **全局复制（Spanner）。** 每个聊天室数据驻留在某个区域并全球复制。写付 Spanner commit-wait（~7 ms）加 quorum 往返；跨大陆 quorum 约 200 ms 提交。读可用 follower 区域做有界过期读。500 ms 预算满足；成本是 Spanner 基础设施开销。

推荐：大多数聊天应用选 (b)。异步复制延迟对用户不可见（用户把数秒内跨区送达当作消息传递延迟，这是他们的心理模型）。Spanner 过度；中央 DB 让用户体验不对称。

这正是 Slack 的模式：per-region channels，跨区复制做 federation。

**Q2.** 一个团队为 Raft 复制数据库选三个区域，希望最小化最坏情况 Raft quorum 延迟。给定上述光速下限，提出一个三区域选择并论证。

提示

Raft quorum 是多数；你希望中位数成对往返低。地理聚类有帮助。

**答案：** 三个副本的 Raft：quorum 是任意 2 of 3。leader 自己算一个 ack；条目在 _最快_ follower 响应后提交。因此 US-East 发起的写，提交延迟是到其他两个区域中较快者的往返。系统级最坏情况是所有可能发起区域中这个延迟的最大值。

聚类三区域：US-East、US-Central、US-West。成对往返：East-Central ~30 ms，East-West ~80 ms，Central-West ~50 ms。

* US-East 发起：最快 follower = US-Central，30 ms。
* US-Central 发起：最快 follower = US-East，30 ms。
* US-West 发起：最快 follower = US-Central，50 ms。
