#### F.3 — 读重全球内容分发

**输入**：读主导工作负载；面向用户；延迟敏感；大多数读可接受最终一致。

**决策**：DynamoDB Global Tables 或 Cassandra/ScyllaDB + CDN。

* **Operational 存储**：DynamoDB Global Tables（AWS 原生、托管）或 Cassandra/ScyllaDB（开源、多云）。
* **CDN**：Cloudflare 或 Fastly 用于静态内容路径。
* **缓存**：区域 Redis 或 Memcached 用于热读。
* **一致性策略**：per-operation 选择；内容读用最终一致，唯一声明操作（用户名保留等）用条件写入。
* **为何这个组合**：读规模占主导；最终一致可接受；对仅 AWS 部署，可接受厂商锁定（DynamoDB）。
* **替代**：更高成本下 Spanner 提供更强一致性；Cassandra 用 LWT 可选线性化。


#### F.4 — 高吞吐流处理 / 事件处理

**输入**：100K-1M 事件/秒；分区内有序处理；端到端 exactly-once；分钟到小时级延迟预算。

**决策**：Kafka + Apache Flink + Postgres 或 CockroachDB sink。

* **Event broker**：Kafka（或更轻量的 NATS JetStream）。
* **Stream processor**：Apache Flink（通过 Chandy-Lamport 快照实现 exactly-once，第15章）或 Spark Structured Streaming。
* **Sink**：PostgreSQL 或 CockroachDB，幂等写入；事务 sink 与 Flink checkpoint 协调。
* **Schema 管理**：Confluent Schema Registry 或等价物。
* **为何这个组合**：Kafka 的 per-partition 排序是正确原语；Flink 的 exactly-once 成熟；sink 选择取决于下游需求。
* **替代**：Pulsar 替代 Kafka；Materialize 用于物化视图式流 SQL；Beam 用于跨 runner 可移植性。


#### F.5 — 大规模分布式 LLM 推理（月推理预算 10 万美元以上）

**输入**：每日 10 亿+ token；多模型；延迟敏感的交互路径 + 批处理路径；成本优化是强制的。

**决策**：vLLM/SGLang + 分离式 prefill/decode + KV-cache-aware 路由。

* **推理引擎**：vLLM（通用）或 SGLang（前缀重工作负载）；企业部署两者都通过 NVIDIA NIM。
* **架构**：集群超过约 50 节点后做 prefill/decode 分离（第25章）；KV cache 层（Mooncake / LMCache）用于前缀复用。
* **路由**：KV-cache-aware 负载均衡（第26章）加长度预测路由。
* **投机解码**：按模型为长输出工作负载启用。
* **监控**：每客户 GPU 秒成本；每阶段利用率。
* **为何这个组合**：2025-2026 架构突破（分离、KV cache 层、投机解码）复合产生显著成本节省。
* **替代**：企业团队用 NVIDIA NIM；若团队想避免运维复杂度，可用 Anyscale / Together / Fireworks 等托管替代。
