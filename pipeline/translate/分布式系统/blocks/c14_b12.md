#### 深入思考

**Q1.** 辩护或反驳：“2026 年所有新应用都应使用 NewSQL 数据库（CockroachDB 或等价）而非单节点 Postgres。成本差异小，而多区域收益大。”

**讨论：** 辩护：NewSQL 数据库提供多区域灾备、水平扩展，以及无需手动分片 Postgres 的 SQL/Postgres 体验。对架构收益来说，成本溢价小（1.5-2 倍）。

反驳：大多数应用永远不需要多区域。成本溢价真实（运维复杂度、企业功能 license、每操作更高延迟）。单节点 Postgres 加热备以更低成本和复杂度服务巨大工作负载。“过早优化” 论点适用：当你有这个问题时再解决多区域。

综合：对有明确多区域需求的绿地应用（全球 SaaS、金融系统），从第一天就用 NewSQL 是正确的。对没有明确多区域需求（单国 SaaS、内部工具、大多数初创公司），Postgres 是正确的起点；需求出现时再迁移到 NewSQL。

2026 年现实：从 Postgres 到 CockroachDB 的迁移路径已非常成熟。“先 Postgres；多区域成为硬需求时再迁移到 CockroachDB” 的模式在运维上可靠。直接上 NewSQL 会增加前期成本，而收益可能永远不会兑现。

第二个考虑：serverless 选项（Neon、Aurora DSQL）正在模糊界线。Neon 让你无需运维 Postgres；Aurora DSQL 让你无需运维 NewSQL。两者都以不同的扩展特性提供 “托管简单性”。选择取决于具体工作负载的扩展轴。

**Q2.** 一个 LLM 被要求为 “现代 Web 应用” 推荐数据库，它推荐了 MongoDB。为什么这个答案在没有更多上下文时是错误的，LLM 应该先问什么？

**讨论：** MongoDB 对某些工作负载合理，但对许多其他工作负载不合适。“现代 Web 应用” 这个框架没有具体内容；正确数据库取决于：

* 应用做什么操作（文档 CRUD？复杂查询？Join？）。
* 一致性需求（金融事务需要 ACID；社交信息流读可容忍最终一致）。
* 规模（10 用户还是 1000 万？）。
* 团队专长（熟悉 MongoDB？Postgres？两者？）。
* 部署目标（单区域？多区域？特定云？）。

MongoDB 的优势（灵活文档 schema、水平扩展、文档形态数据的良好开发者体验）与某些工作负载匹配。其劣势（默认一致性较弱、大规模下 schema-on-read 陷阱、生态比 Postgres 有限）使其对许多其他工作负载错误。

更诚实的 LLM 应该问：

* 应用实际做什么？
* 数据形态是什么（关系、文档、图、时序）？
* 规模多大？
* 团队专长如何？
* 部署目标是什么？

没有这些，“推荐 MongoDB” 只说明 LLM 在从训练数据中给出流行答案（MongoDB 是 2010 年代流行的 NoSQL，训练数据中占比高），而非基于工作负载推理。
