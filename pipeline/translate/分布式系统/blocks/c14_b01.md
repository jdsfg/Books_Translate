2026 年，“我们应该用 Postgres 还是 NewSQL 数据库？”是新系统最常见的架构问题之一。答案取决于工作负载、部署范围和团队。本章讲授全景：NewSQL 竞争者（Spanner、CockroachDB、TiDB、YugabyteDB、Aurora DSQL、Neon、TigerBeetle）和处理分析工作负载的分布式查询处理器（Trino/Presto、Snowflake、BigQuery 的 Dremel）。

### 14.1 “NewSQL” 含义

“NewSQL” 一词约 2011 年出现，描述一类在水平扩展同时保留 SQL 和 ACID 事务的分布式数据库。原始定义将 NewSQL 与以下两类对比：

* **传统 SQL** ：PostgreSQL、MySQL、Oracle。ACID，单节点或主从复制，纵向扩展。
* **NoSQL** ：Cassandra、DynamoDB、MongoDB。水平扩展，但历史上放弃 ACID 或使用非 SQL API。

NewSQL 系统目标是 “两全其美”：水平扩展 + 强事务保证 + SQL。

2026 年，NewSQL 类别已成熟。主要竞争者：

* **Google Spanner** ：开创者；仅限 GCP。
* **CockroachDB** ：开源 NewSQL；可跑在任何云上。
* **TiDB** ：另一开源 NewSQL；兼容 MySQL。
* **YugabyteDB** ：开源 NewSQL；兼容 Postgres。
* **AWS Aurora DSQL**（2024 GA）：AWS 上托管的 serverless NewSQL。
* **Neon** ：serverless Postgres，存储与计算分离。
* **TigerBeetle** ：金融级账本，采用确定性模拟测试和 TigerStyle 规范（固定大小消息、显式状态机枚举）。

该类别已成熟到问题不再是 “是否用 NewSQL？”，而是 “用哪个 NewSQL？”。


### 14.2 Spanner

参考实现。Google Spanner 自 2012 年在生产运行，2017 年左右作为 Cloud Spanner 对外提供。

关键属性：

* 每 tablet 使用 Paxos 复制。
* TrueTime 用于线性化全局时间戳。
* 支持跨多行、多 tablet 事务的 SQL。
* 区域或多区域部署配置。
* 在线 schema 变更。

优势：

* 最成熟的多区域事务数据库；在 Google 规模下久经考验。
* 基于 TrueTime 的时间戳避免不确定性重启。
* 单一全球实例可跨多区域（或仅区域）。

劣势：

* 仅限 GCP。不能部署在 AWS 或 Azure。
* 昂贵（按节点小时 + 存储和 IO 计费）。
* 相比完整 Postgres，某些 SQL 功能（子查询等）曾有限制，虽已逐步改善。

Spanner 适合：能 justify 成本和 GCP 承诺的全球规模工作负载。生产示例：Google 自身基础设施（Ads、Cloud、Workspace）、Spotify、部分大型金融客户。
