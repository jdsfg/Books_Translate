#### 应用问题

**Q1.** 你正在阅读一个支付服务 double-charge 客户的堆栈 trace。trace 显示两个 POST `/charge` 请求，带有相同幂等键，相隔 47 ms 到达支付服务的两个不同副本。两者都成功了。走一遍三个谎言，指出系统未能防御的是哪一个。

提示

幂等键是系统针对失败谎言的防御（它让重试安全）。既然防御失效，问题出在哪？

**答案：** 系统试图用幂等键防御失败谎言。该防御依赖单一真相来源，能识别“我已经处理过这个键”。如果两个副本共享一个强一致性的已见幂等键存储（例如带有唯一约束的 Spanner 或 CockroachDB 表），第二个请求会违反约束，重复扣款被阻止。

如果两个副本各自查询本地缓存或尚未复制第一条请求条目的每区域存储，那么谁都没看到对方的先前提交。系统在存储层失败了身份谎言：系统相信存在一个“幂等记录存储”，但现实中存在两个短暂不一致的视图。

修复是让幂等检查走强一致路径（第13章的 Percolator 式事务，或第9章的 Raft 复制提交日志）。更便宜但错误的修复是延长幂等窗口，这只能争取时间，下一次接近同时的重试仍会撞上同一个缺口。

**Q2.** 你加入一个团队，正在为一个配置服务构建领导者选举协议。一位资深工程师说：“我们用 Redis `SET NX EX 30` 选主。领导者每 10 秒刷新一次键。如果领导者挂掉，键过期，别人接管。”指出该设计未处理的三种失败模式。需要时可参考第18章。

提示

该模式是 Redlock。Jepsen / Kleppmann 辩论至少指出三种失败模式。想想 GC 暂停、到 Redis 的网络分区、以及旧领导者醒来时会发生什么。

**答案：** 第一，领导者上的长 GC 暂停（或 VM 暂停，或任何 stop-the-world 事件）可能导致它没来得及刷新锁。锁过期；新领导者上任；然后原领导者醒来，因为从未抛出异常，继续以为自己持有锁。两个领导者同时活跃。

第二，领导者与 Redis 之间的网络分区也会导致相同情况。领导者无法刷新，锁过期，另一网络路径上的新领导者被选出，分区恢复后，原领导者从自己的视角仍作为领导者行动。

第三，即使锁确实被唯一持有，也没有 fencing token。一条旧领导者在锁过期前发出、但尚未送达下游系统的动作，在新领导者发出自己的动作后到达下游。下游系统无法区分“由当前领导者发出”和“由过期领导者发出”，于是两者都处理。
