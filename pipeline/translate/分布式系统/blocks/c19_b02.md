#### etcd 为何替代 ZooKeeper

Apache ZooKeeper 是首个生产分布式协调系统（2000 年代末起源于 Yahoo；用于 Hadoop、Kafka、Cassandra 等）。ZooKeeper 提供类似原语：层级键（zNodes）、watches、ephemeral 节点（与会话生命周期绑定）。

etcd 在新系统中已基本替代 ZooKeeper，因为：

(a) **更好的运维模型**：etcd 使用 Raft（更易理解；工具更好），而 ZooKeeper 的 ZAB（Paxos 变体）更复杂。

(b) **gRPC API**：etcd 的 API 基于 gRPC；现代；与云原生生态契合。ZooKeeper 的 API 较老、不够精致。

(c) **Kubernetes 采用**：Kubernetes 选择 etcd；Kubernetes 的引力把 etcd 推向主导地位。

(d) **更好的集群管理**：etcd 的 `etcdctl` 和基于操作者的管理比 ZooKeeper 的 CLI 和运维故事更友好。

ZooKeeper 仍在生产中使用（Kafka 旧元数据层、HDFS、较老的 Cassandra 集群）。新系统通常从 etcd 开始。Kafka 从 ZooKeeper 迁移到 KRaft（Kafka Raft）是近期大趋势的例子。


### 19.3 Consul

HashiCorp 的 Consul 是另一个流行的服务发现系统。与 etcd 的关键差异：

(a) **原生多 DC**：Consul 内置数据中心感知；跨 DC 服务发现是一等特性。

(b) **服务网格**：Consul 包含服务网格功能（服务间 mTLS、流量策略、intentions）。

(c) **基于 DNS 的发现接口**：服务可通过 DNS 查询发现（如 `payment.service.consul`），无需客户端库即可与任何语言配合。

(d) **内置健康检查**：Consul 轮询服务实例以验证健康（不依赖实例侧心跳）。

(e) **多租户**：Consul 企业版支持命名空间。

Consul 在异构环境（混合云、本地、基于 VM 的部署）中流行，这些场景下仅 Kubernetes 发现不够。对纯 Kubernetes 部署，通过 Kubernetes API 使用 etcd 通常更简单。
