更深观察：LLM 的设计是每个团队都会先尝试的朴素方法。CRDT 在结构上解决以上所有问题；重新发明它们不必要且错误。正确的 LLM 回答应该是 “用 Yjs 或 Automerge；不要从零实现协作编辑。” LLM 产出朴素代码说明它没学到这一课，或它在不考虑需求的情况下生成最简代码。

对协作文辑来说，答案是 “用库”。这是一个 DIY 成本远高于库成本的领域。


### 本章总结

CRDT（无冲突复制数据类型）是为并发更新下确定性合并而设计的数据结构。基于状态的 CRDT（CvRDT）合并完整状态；基于操作的 CRDT（CmRDT）广播操作。两者表达能力等价；选择是运维性的。

典型 CRDT：G-Counter（只增计数器）、PN-Counter（支持递减的计数器）、LWW-Register（最后写胜出）、MV-Register（多值）、OR-Set（观察删除集合）、list CRDT（Yjs 使用 RGA 衍生；Automerge 使用带完整历史的类似结构）。

Yuki 的 Glide 协作编辑器在 Cloudflare Workers + Durable Objects 上使用 Yjs。文档是 Y.Doc；通过 WebSocket 实时同步；awareness 协议处理光标；定期 compaction 为快照。冲突解决自动；无合并对话框。

本地优先软件——Kleppmann 等人在 2019 年论文中命名这场运动——是 CRDT 使能的设计理念：离线工作、无缝同步、用户拥有数据。Linear、Notion、Glide、Logseq、Skiff 是示例。

2026 年新协作编辑器设计默认用 CRDT。现有基于 OT 的系统（Google Docs、Microsoft Word Online）继续使用 OT。迁移成本高；就地升级不太可能。

第17章结束第五部分：混合方案。因果一致（COPS/Eiger 家族）、强最终（CRDT 作为原型），以及把它们放在线性化和最终一致之间的一致性格。Yuki 的 Glide 系统同时使用了这三者的元素。
