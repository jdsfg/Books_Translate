#### 深入思考

**Q1.** 辩护或反驳：“2026 年，所有严肃的分布式数据库都应该用 HLC；TrueTime 在 Google 之外已经过时。”用至少两个生产系统的证据。

**讨论：** 辩护：HLC 在没有 GPS 基础设施的情况下实现了 TrueTime 的大部分价值。CockroachDB、YugabyteDB、TiDB、MongoDB 都选择 HLC 并已规模化生产。经验证据表明 HLC 已足够好。

反驳：TrueTime 给 Spanner 两条 HLC 做不到的东西。第一，整个系统的 _外部一致性_ 无需基于偏移的重启。第二，全局时间戳排序在任何分区下都能存活而不重启。对重启不可接受的工作负载（热键高竞争写入），TrueTime 的 commit-wait 比分摊到每次重启的成本更划算。

综合：HLC 加严格 NTP 对大多数团队是正确默认。TrueTime 对能负担 GPS 基础设施且工作负载中重启成本超过 commit-wait 成本的团队是正确答案。AWS 的时钟-bound API（Amazon Time Sync Service）首次在 Google 之外提供 TrueTime 风格能力，我们可能会看到高利害工作负载缓慢迁移到云厂商的 TrueTime-like 模型。

第二个考虑：HLC 的“最大时钟偏移”上界是一个配置参数。如果实际偏移超过该上界，数据库会静默产生非线性化结果。TrueTime 的 `[earliest, latest]` API 迫使系统对不确定性变宽作出反应（commit-wait 自动增长）。HLC 的失败模式不那么可见，从运维纪律角度看可能更糟。

**Q2.** 一个 LLM 生成的日志系统用 `time.time()` 给每条日志行盖戳，然后合并 100 台服务器的日志并排序。指出该设计的三种具体失败模式，并提出一种不需要所有服务器统一时钟的修复。

**讨论：** 三种失败模式：

(a) **反向因果** ：请求从服务器 A 流向服务器 B。A 的“收到请求”日志行时间戳为 t_a；B 的“开始处理”行时间戳为 t_b。如果 A 的时钟比 B 快 50 ms，合并日志显示 B 在 A 收到之前就开始处理。取证追踪被破坏。

(b) **同毫秒物理时钟碰撞** ：多台服务器每秒写数千行日志，可能产生相同毫秒分辨率的时间戳。按时间戳排序会在每毫秒内任意排序，破坏每台服务器的本地顺序。

(c) **时钟跳跃** ：单台服务器的 NTP 调整可以一次性让时钟回退数百毫秒。跳跃后它的日志行出现在跳跃前紧接写入的行的“前面”，再次破坏本地顺序。

无需同步时钟的修复：用 HLC 加每服务器单调序列号给每条日志行盖戳。HLC 在服务器交换消息时尊重 happens-before（例如，携带 HLC 的请求 ID）。单调序列号保留每台服务器本地顺序。按 HLC 排序显示合并日志，平手用服务器 ID + 序列号打破。

这就是现代可观测性栈（OpenTelemetry，配合正确的追踪上下文传播）实际做的事情。跨服务传播的追踪上下文携带 HLC 等价信息的机制，追踪 ID + 跨度 ID + 序列号提供本地顺序的平手打破。
