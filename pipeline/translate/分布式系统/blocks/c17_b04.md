#### 概念检测

**Q1.** 定义因果一致性。它与线性化和最终一致有何不同？

提示

因果：因果相关操作按因果顺序；并发操作可任意。线性化：实时顺序。最终：收敛过程中无顺序保证。

**答案：** 因果一致性：若操作 A happens-before 操作 B（Lamport 意义），则每个进程先看到 A 再看到 B。并发操作（无 happens-before 关系）可任意顺序；不同副本可看到不同顺序。

与线性化相比：线性化额外要求操作按实时顺序排列（若 A 在 B 开始前完成，则 A 排在 B 前）。因果不需要；两个并发操作可在不同副本以不同顺序出现。

与最终一致相比：最终只承诺无新更新时副本收敛到同一状态；对收敛过程中的顺序无保证。因果保证因果相关操作顺序始终被保持。

实践上：

* 线性化：每次操作付共识往返；最强保证；最贵。
* 因果：付依赖跟踪开销；中等成本；因果重要但实时顺序不重要时适用。
* 最终：每次操作几乎不付；最弱保证；最便宜。

**Q2.** 为什么排行榜工作负载的正确选择是因果一致？

提示

排行榜：B 在看到 A 后提交的分数应排在 A 后；并发提交可任意顺序。

**答案：** 排行榜工作负载：

* 玩家 A 提交分数。其他玩家看到（出现在排行榜上）。
* 玩家 B 看到 A 的分数，然后提交自己分数（也许更高以竞争）。
* 所有观众最终应在排行榜上看到 A 在 B 前（或至少系统不能显示 B 的提交仿佛先于 A）。

因果关系：B 的提交 happens-after B 看到 A 的分数；因此 B 的提交 happens-after A 的提交。因果一致保持这一点：所有副本都显示 A 在 B 前。

对两个并发提交（玩家 C 和 D 同时提交且互未看到），因果一致允许任何顺序——不同观众可能看到 C 在 D 前或 D 在 C 前。这没问题；没有因果期望被违反。

为何不更强：

* 线性化会要求全局顺序；吞吐在共识处瓶颈；每次提交延迟更高。成本不合理，因为没人关心毫秒级并发提交的精确顺序。

为何不更弱：

* 最终一致允许 “我看到 A 的分数，然后刷新排行榜却没有它” 的失败。B 提交分数后刷新，可能读到没有 B 的副本。读己写是因果一致的特例。

排行榜位于频谱中间。因果是正确模型。

**Q3.** 强最终与纯最终一致有何不同？

提示

强最终：给定相同操作集合，收敛是确定性的。纯最终：取决于冲突解决策略。
