#### 应用问题

**Q1.** 一个团队用消息代理实现微服务舰队的事件分发，该代理提供至少一次交付和主题内有序。这给他们哪一层广播？应用代码还需要哪些纪律？

提示

代理在主题分区内提供的是原子广播。跨主题或分区需要应用自己强制。至少一次意味着消费者可能看到重复。

**答案：** 代理在主题分区内提供原子广播（per-topic ordering）。跨主题或分区只提供应用强制出的性质。至少一次交付意味着重试情况下每个消费者可能多次收到同一条消息。

应用需要纪律：

(a) 每个消息处理函数必须具备 **幂等性** 。收到同一条消息两次应产生与收到一次相同的最终状态。通常通过每条消息带幂等键，在处理前检查数据库实现。

(b) 若应用需要跨主题顺序，则要自己保证。代理只在一个分区内保证顺序；同一主题不同分区间的事件无序。应用必须将相关事件放在同一分区（分区键 = 实体 ID），或接受跨分区顺序未定义。

(c) **消费者重平衡语义** 。若消费者重平衡（例如部署期间），一条在途消息可能被另一个消费者重新处理。幂等性处理此情况；缺乏幂等性会导致双重处理。

第1章的 Crescent 支付系统正是这种模式：Kafka 提供每个partition 排序，应用必须按分区键（通常是事务 ID）幂等。重复扣款缺陷是因为幂等检查没有强一致。

**Q2.** 用 flooding 写可靠广播的伪代码。走查一个 4 节点示例，其中一个接收者收到消息后、重广播前崩溃。消息还能到达其余正确接收者吗？

提示

flooding 下，发送者发给所有对等节点。只要崩溃节点之外至少有一个对等节点收到并重广播，消息就会到达全部。

**答案：** 伪代码：


    已投递 = set()

    def 广播(msg):
        flood(msg, sender=self)

    def flood(msg, sender):
        if msg in 已投递:
            return
        delivered.add(msg)
        upper_layer.deliver(msg)
        for 对等节点 in all_processes:
            if 对等节点 != sender and 对等节点 != self:
                发送(对等节点, msg, sender=self)

    def on_receive(msg, sender):
        flood(msg, sender)


四节点示例：P1、P2、P3、P4。P1 广播 m。

* P1 将 m 发给 P2、P3、P4。
* P2 收到 m，加入已投递，发给 P3、P4（跳过 P1）。
* P3 收到 m（假设先从 P1），加入已投递，发给 P2、P4。
* P4 收到 m，依此类推。

现在假设 P2 收到 m 后在重广播前崩溃。P3 和 P4 仍直接从 P1 收到 m，并且它们会互相重广播（因已有，所以空操作）。所有正确接收者（P3、P4）都已交付。一致性满足。
