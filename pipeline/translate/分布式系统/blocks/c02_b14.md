一个不回答这些问题就给出答案的模型，充其量是幸运。单区域 Shopify 风格商店的正确答案可能是 PostgreSQL + 读副本；Stripe 风格全球支付系统的正确答案可能是 Spanner 或 TigerBeetle。正确的推理路径要经过这些问题。没有推理路径的答案是一个团队无法辩护、无法扩展、在工作负载变化时无法调试的价值。

更深观察：分布式系统决策不是那种可以外包推理的决策。推理 _就是_ 决策。一个碰巧正确的 LLM 生成答案不会给团队带来任何理解，无法评估未来变更，也无法在假设变化时为自己辩护。


### 本章总结

Deutsch 的八大谬误命名了产生大多数分布式系统 bug 的单机直觉。谬误不是要记住的 checklist；它们是审计每段分布式代码时应检查的假设类别。第21章会作为级联失败重新审视网络可靠性的谬误；第18章会作为锁与协调 bug 重新审视安全和“只有一个管理员”的谬误。

精确陈述的 CAP 说，在网络分区下，你不能同时拥有线性化和可用性。口号版本（“选两个”）有误导性，因为分区容错性不是可选项。CAP 的“一致性”是线性化，比该词的宽松数据库意义强得多。

PACELC 扩展了 CAP 忽略的情况：没有分区时。PACELC 命名了正常运营中延迟与一致性之间的权衡，这就是应用每天付出的代价。系统的 PACELC 画像比它的 CAP 标签更实用。

§2.4 的计数器-排行榜-库存工作负载会在全书反复出现。它们代表一致性光谱上的点：计数器（最终一致即可）、排行榜（需要因果）、库存（需要线性化）。知道哪个工作负载需要哪种一致性，是比知道哪个数据库是“CP”或“AP”更有用的技能。

第3章抓住第一个谎言——时间——展开 Lamport、向量、HLC、TrueTime 等协议，让你能够在机器间推理顺序而不撒谎。本章提到的 Spanner commit-wait 延迟将在第3章完整解释；CockroachDB 基于 HLC 的 MVCC 将在第13章完整解释。
