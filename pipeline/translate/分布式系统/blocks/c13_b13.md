**Q3.** 比较 Calvin 的确定性排序与 CockroachDB 的乐观并发控制。

提示

Calvin：先排序再执行；无因锁冲突导致的中止。CockroachDB：先执行，冲突时重试。

**答案：**

_Calvin_ ：sequencer 在执行前全局排序所有事务。每个分片按约定顺序执行事务。无冲突（顺序预先决定）。无因锁冲突导致的中止。

优点：无重试成本；确定性、可预测延迟；高争用下无 abort storm。

缺点：sequencer 是全局同步点；每笔事务付 sequencer 往返；sequencer 是跨区域瓶颈。

_CockroachDB（乐观快照隔离 + 可串行化）_ ：每个事务启动并执行；提交时检测冲突。若检测到冲突，事务重启。

优点：无全局 sequencer；事务独立推进；低争用下吞吐很高。

缺点：争用导致重启；病态争用下产生 abort storm；高争用下延迟不可预测。

权衡：Calvin 赢在高争用工作负载（计数器递增、热行更新）；CockroachDB 赢在低争用工作负载（大多数 OLTP）。2026 年分布式数据库市场由乐观方法主导，因为真实工作负载大多低争用；Calvin 在专业应用（FaunaDB）中存活，那里确定性语义重要。

**Q4.** 什么是 TrueTime，Spanner 如何用它提供线性化全局时间戳？

提示

TrueTime：每个 DC 的 GPS + 原子钟；返回不确定性区间。Spanner 在提交前等待不确定性消失。

**答案：** TrueTime 是 Google 的硬件辅助时间服务。每个数据中心有 GPS 接收器和原子钟；软件监控并报告时钟不确定性。`TT.now()` 返回区间 `[earliest, latest]`，真实物理时钟时间 provably 位于该区间内。典型不确定性：1-7 毫秒。

Spanner 通过 _commit-wait_ 协议用 TrueTime 实现线性化提交时间戳：

  1. 事务选 `commit_timestamp = TT.now().latest`。
  2. 事务等待直到 `TT.now().earliest > commit_timestamp`。通常约 ~7 ms。
  3. 等待后，真实物理时钟时间 provably 已过 commit_timestamp。
  4. 提交释放；锁释放。

等待确保任何后续事务（系统任何地方）以大于 commit_timestamp 的时间戳读时，其真实时间都在本事务提交之后。结果是全局线性化：跨越全球所有 Spanner 实例，时间戳形成与实时一致的全序。

7 ms commit-wait 在每次写上支付。成本是 TrueTime-基于线性化的代价，无需为时间戳做协调者往返。
