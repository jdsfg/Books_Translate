(d) **协议消息幂等性**。网络重试可能使 PREPARE 或 COMMIT 到达两次。参与者必须幂等处理。LLM 代码通常不会。

(e) **参与者崩溃后的恢复**。参与者在投 YES 后、收到 COMMIT 前崩溃，恢复时必须记住其投票并一致行动。这需要已准备状态的持久化存储。LLM 代码常用内存状态，崩溃后丢失投票。

(f) **超时纪律**。协调者必须对不响应的参与者超时，并决定是否中止整个事务。LLM 代码通常完全没有超时或使用不当值。

更深观察：跨服务 2PC 在 2026 年微服务架构中很少是正确模式。LLM 为 “跨微服务事务” 生成 2PC 而未问及 saga、最终一致或异步补偿，说明它跳过了架构问题。正确答案通常是 saga；LLM 生成 2PC 反映的是旧教科书里突出的内容，而非当前最佳实践。


### 本章总结

分布式事务是跨分片、跨区域原子性问题。四种经典方法：2PC（经典，存在协调者故障时阻塞的弱点）、Percolator（带 primary-键原子提交的快照隔离，无中心协调者）、Calvin（通过 sequencer 的确定性排序，无中止）、TrueTime/Spanner（硬件辅助时间戳 + commit-wait）。

现代 2PC 模式（Spanner、CockroachDB、FoundationDB 使用）通过共识复制协调者状态，消除经典阻塞。阻塞版 2PC 已基本过时。

CockroachDB 和 TiDB 使用 HLC 加可配置时钟偏移上界作为实用的 TrueTime 替代。成本可变（争用时重启）而非恒定（每次写 commit-wait）。AWS 的时间 Sync 时钟-bound API 正把 TrueTime-like 能力带出 Google。

Olamide 的跨区域支付事务在 CockroachDB 中约 120 ms 原子提交到三个区域，可串行化的隔离且完整 ACID 保证。协议成熟；运维调优（局部性、分片、重启预算）决定生产性能。

Saga 模式（跨服务补偿动作，§13.6.5）是跨微服务 “事务” 的正确模式；2PC 是分布式数据库内跨分片的正确模式。编排 vs 舞蹈化 saga；正确性义务（独立可提交、幂等、可补偿、补偿幂等）；saga-vs-2PC 决策矩阵；Crescent 的混合使用都在 §13.6.5 展开。两种模式在现代应用中共存。

第14章结束第四部分：NewSQL 全景。Spanner、CockroachDB、TiDB、YugabyteDB、Aurora DSQL、Neon、TigerBeetle，以及分布式查询处理器（Trino/Presto、Snowflake、BigQuery）。本章讲授如何用第11章的诊断方法加上第13章的事务协议视角来映射工作负载到系统。
