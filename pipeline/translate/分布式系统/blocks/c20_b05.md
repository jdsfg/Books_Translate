#### 概念检测

**Q1.** 什么是分布式 trace？每个跨度携带哪些信息？

提示

Trace 是跨度树。每个跨度携带 trace ID、跨度 ID、parent 跨度 ID、时间戳、状态、attributes。

**答案：** 分布式 trace 是单个分布式请求的因果记录：请求触发的跨服务工作链。它结构化为跨度的树（或 DAG）；每个跨度代表一个工作单元。

每个跨度携带：

* **Trace ID**：该 trace 内所有跨度共享；全局标识 trace。
* **跨度 ID**：该跨度唯一。
* **Parent 跨度 ID**：标识该跨度的父节点；根跨度为 null。
* **Service name 和 operation name**：哪个服务、哪个操作。
* **Start time 和 duration**：跨度何时开始、持续多久。
* **Status**：成功、错误，可带错误码。
* **Attributes**：自定义键值对（HTTP 状态、数据库查询、应用自定义元数据）。
* **Events**：跨度内的时间戳日志条目（状态变化、错误、里程碑）。

单个 trace 的所有跨度通过 trace 和 parent-跨度 ID 组装，形成可视化显示的树结构。

**Q2.** 为什么跨服务边界传播追踪上下文至关重要？

提示

没有传播，子跨度无法链接到父跨度；trace 会碎片化。

**答案：** 追踪上下文（trace ID、parent 跨度 ID、采样决策）是父跨度和子跨度之间的链接。没有传播：

* 接收请求的服务不知道请求属于哪个 trace。它创建新的 trace ID；工作看起来与原始请求是分开的 trace。
* 父子关系丢失；trace 树碎片化。
* 采样决策不传播；子跨度可能未被采样而父跨度被采样（或相反），导致不完整 trace。

结果：不是一条展示完整因果链（原始请求和所有下游工作）的 trace，而是许多断开的片段。调试变得不可能，因为你无法跟随请求路径。

传播通常通过 HTTP headers（W3C 标准的 `traceparent`）或消息队列元数据（Kafka headers、AWS SQS attributes）。OpenTelemetry 库对常见框架自动处理；自定义协议需要显式传播逻辑。

纪律：每次跨服务交互都必须传播追踪上下文。异步交接（队列、定时任务）需要通过异步机制显式传播上下文。没有这种纪律，分布式追踪产生碎片化的 trace，误导性大于帮助。

**Q3.** 什么是基于头部的采样与基于尾部的采样？各自何时适用？

提示

基于头部的：在根处决策；传播决策。基于尾部的：缓冲跨度，trace 完成后决策。

**答案：** _基于头部的 sampling_ ：采样决策在 trace 起点（根跨度）做出。决策（是否采样）通过追踪上下文传播给所有子跨度。要么 trace 所有跨度都被采样，要么都没有。
