### 13.7 工作流 8：Olamide 的跨区域支付事务

Olamide 从 Adaeze 到商家 Femi 的支付：


    -- 金额以 BRL（巴西雷亚尔）计；到 Femi NGN 计价账户的跨币种结算
    -- 由银行端 FX 层处理（此处范围外——本事务在 Crescent 内部 BRL 账本
    -- 全程运行，FX 作为单独分录入账）。
    BEGIN TRANSACTION;
      -- 检查 Adaeze 余额充足
      SELECT balance FROM accounts WHERE account_id = 'adaeze';
      -- 扣 Adaeze 款项（1200 BRL ≈ 240 USD；是一笔 substantial 交易，不是
      -- 第1章的 6-BRL 数据包）
      UPDATE accounts SET balance = balance - 1200 WHERE account_id = 'adaeze';
      -- 给 Femi 入账（不同分片、不同区域：Femi 在 Lagos，
      -- 被划分到 EU-West）
      UPDATE accounts SET balance = balance + 1200 WHERE account_id = 'femi';
      -- 更新 Femi 的日汇总
      UPDATE merchant_day_rollup SET total = total + 1200 WHERE merchant_id = 'femi' AND day = '2026-05-19';
    COMMIT;


在 CockroachDB 下：

  1. 事务以来自发起节点的 HLC 时间戳开始。Crescent 运营三个区域——US-East、EU-West、US-West——因此 São Paulo 客户的会话落在 geo-DNS 路由选定的区域。按第6章 §6.1 方法（光纤中光速下限约 200,000 km/s，真实 RTT 的 2-3× 路由开销乘数）：São Paulo → US-East（经南美沿海电缆约 8,500 km）p99 RTT 约 110 ms；São Paulo → EU-West（经大西洋约 9,500 km）约 190 ms；São Paulo → US-West（经美国大陆路由约 11,000 km）约 200 ms。US-East 对 Adaeze 最优。
  2. `SELECT` 从 Adaeze 分片 Raft leader 读取余额。Adaeze 账户行被 geo-partition 到 US-East（服务南美的区域），因此读留在区域内。
  3. 对 Adaeze 余额的 `UPDATE` 在她的分片（US-East）上获取 write intent。
  4. 对 Femi 余额的 `UPDATE` 在他的分片上获取 write intent。Femi 是 Lagos 商家；他的数据被划分到 EU-West（服务非洲和欧洲的区域）。这次 `UPDATE` 是跨区域跳转。
  5. 对日汇总的 `UPDATE` 在该分片上获取 write intent。
  6. `COMMIT`：事务协调者（本身通过 Raft 复制）在选定的 commit_timestamp 标记事务提交。intents 变成提交值。

跨区域延迟：每个 Raft commit 都涉及受影响分片在跨区域法定人数中的往返。对 Crescent 的 3 区域部署（US-East / EU-West / US-West），per-shard 提交最坏情况约 90 ms（第6章 AP Q2）。事务必须在所有三个分片提交后才会返回给应用；总提交延迟受最慢分片加上跨分片事务协调开销限制（跨区域事务通常 100-150 ms 端到端）。

若两笔事务竞用同一账户（罕见但可能），一笔获胜；另一笔拿到 serializable error 并重试。CockroachDB 的 serializable 隔离保证正确性；应用代码必须准备好重试（标准模式是带指数退避的重试循环，最多 N 次）。
