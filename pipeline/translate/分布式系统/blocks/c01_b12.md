修复方案是 fencing token，第18章会覆盖：每次获取锁都会增加一个单调计数器，每个下游动作都携带该 token。下游拒绝任何低于它所见过最高 token 的 token 的动作。即使两个节点短暂相信自己持有锁，也只有 token 更高的那个能说服下游行动。

**Q3.** 一个微服务架构有 14 个服务，单个请求通常触及其中 5 到 8 个。其中一个服务间歇性变慢（它能工作，但返回需要 5 到 8 秒，而不是预期的 50 ms）。这可能给系统其余部分带来哪些分布式失败？至少指出三种。

提示

慢服务会导致背压（back-pressure）、超时和重试风暴（第21章）。它们还会通过健康检查，却实际上已经坏了（第22章——灰色故障）。

**答案：** 第一，慢服务的调用者超时、重试，并助长重试风暴。如果每个上游服务重试三次，每次 5 秒超时，且每次重试都会给慢服务排一条新请求，慢服务的队列深度会无限增长，直到整个上游崩溃。这是第21章级联失败的动态。

第二，慢服务可能通过它自己的健康检查，却实际上不可用。它的健康检查在几毫秒内返回 200 OK，因为健康检查是廉价端点，不触及慢代码路径。负载均衡器继续向它路由请求。这是第22章的灰色故障模式，正是监控最糟的情况：系统报告“健康”，用户却报告“坏了”。

第三，通过同步调用依赖慢服务的下游服务继承了它的延迟。本应 200 ms 完成的请求因为链中一跳变慢而耗时 8 秒。资源池（数据库连接、线程池、请求槽）填满等待慢服务的请求。最终下游服务耗尽池子，开始拒绝与慢依赖无关的请求。这是级联失败的跨服务传染。

**Q4.** 挑选你最近使用过的任一分布式系统（数据库、缓存、队列、键值存储）。在不读文档的情况下，写下你认为该系统对时间、身份和失败做出什么承诺。然后查看它的文档，指出你持有的一个错误假设。

提示

这是本书其余部分将训练你掌握的练习。重点是注意你的假设与系统承诺之间的差距。

**答案：** 这里的纪律比任何具体答案都重要。一个工作示例：Postgres 读者若假设“如果我先 `SELECT now()`，再 `INSERT INTO log (created_at) VALUES (now())`，插入行的 timestamp 会与 SELECT 一致”，会惊讶地发现 Postgres 中的 `now()` 返回的是 _事务开始时间_ ，而非调用时刻的 wall-clock 时间。同一事务中的两条语句看到同一个 `now()`。这是文档里写明的，但违背朴素的单机直觉。
