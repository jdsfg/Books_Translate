示例：功能开关。配置存储保存如 `feature_flags/new_checkout_flow = true` 的键。所有尊重功能开关的服务 watch `feature_flags/` 前缀。当运维更新开关（`etcdctl put feature_flags/new_checkout_flow false`），每个服务收到 watch 事件并在毫秒级禁用该功能。

没有 watch 模式，替代是轮询（每个服务每 N 秒查询配置）或变更后重启（服务必须重启才能取新配置）。两者都有缺点：轮询增加负载和延迟；重启导致短暂不可用。

Watch 模式是动态配置的现代默认。它行之有效是因为：

* 更新传播快（无轮询延迟）。
* 配置存储负载低（客户端只接收变更，而非全量重读）。
* 运维变更即时生效；无需重启。

其他示例用例：流量路由规则（金丝雀发布）、限速（动态调整）、密钥 rotation（无需服务重启）、监控阈值（无需代码部署即可调整告警）。

**Q4.** 为什么基于 DNS 的服务发现对 Stateful 服务常足够，但对无状态自动扩缩服务不足？

提示

DNS TTL 30-300 秒；有状态服务变化少；无状态服务变化快。基于 watch 的发现响应更快。

**答案：** DNS 记录有 TTL，生产中通常 30-300 秒。客户端缓存 DNS 响应；更新在 TTL 边界传播。

对有状态服务（数据库、消息队列、缓存）：实例寿命长。故障转移很少（可能一月一次）。60 秒 TTL 意味着缓存 DNS 的客户端最多 60 秒 failover 延迟；对大多数工作负载可接受。

对无状态自动扩缩服务：实例快速增减。负载增加后数秒内出现新实例；负载降低后数秒内旧实例被终止。60 秒 DNS TTL 意味着客户端在最多 60 秒内仍路由到已终止实例；失败请求、重试风暴、用户可见错误。

基于 watch 的发现（etcd、Consul）：

* 更新在数百毫秒内传播。
* 客户端收到推送通知；无轮询延迟。
* 失败实例在数秒内从注册表移除（心跳超时）。

对快速变化的服务拓扑，watch 式发现足够快，能跟得上。DNS 太粗。

实践中，许多生产系统两者都用：DNS 用于稳定服务（数据库、缓存），watch 式用于自动扩缩服务。组合匹配部署特征。
