对 Stratus 的具体架构，token 存储在 Raft 条目本身（作为条目元数据）。跟随者在 apply 时验证 token；过期 token 的条目是 no-op。

这种模式在分布式系统文献中有时称为 “epoch number”，提供运维安全。即使在复杂故障转移期间（集群重选领导者；旧领导者在网络抖动后重新加入并尝试发命令），token 排序保证只有一位领导者的命令被接受。

代价：每条命令携带 token（几个字节）；每个条目 apply 时检查 token（很快）。代价可忽略；安全收益巨大。

**Q3.** 团队缓存层（Redis Cluster）出现热门键过期时的 “thundering herd”：流行缓存条目过期时，数百读者同时击中数据库。提出三种缓解策略。

提示

概率性提前刷新、刷新期间每键锁、请求合并、异常时提供过期数据。

**答案：** 三种缓解策略：

(a) **概率性提前刷新**：每个缓存读者读取接近过期的条目时，以一定概率提前刷新缓存。概率随过期临近增加。到期时，缓存已被某个读者刷新；后续读者看到新条目。Vattani 等人的模式显著减少踩踏。

(b) **每键刷新锁**：缓存未命中时，读者获取该键的短期锁。其他并发读者阻塞在锁上；只有一个去数据库取；完成后回填缓存并释放锁。其他读者解除阻塞后从缓存读取。

(c) **请求合并**：在应用层（或缓存客户端库），同一键的并发请求去重。只有一条真实 cache-miss 请求去数据库；其他等待结果。

(d) **异常时提供过期数据**：缓存过期且数据库慢或宕机时，提供过期值而非失败。这破坏缓存新鲜度契约但保持可用性。

(e) **后台刷新**：后台任务在热门缓存条目过期前刷新它们。缓存始终温热；缓存未命中只发生在冷键（不会发生踩踏）。

对高流量系统，常见组合 (a) + (b)：概率性提前刷新处理常见情况；每键锁处理最坏情况。(d) 处理数据库中断情况。

更深观察：惊群是缓存被要求做太多的征兆。若单个缓存键热到过期会引发踩踏，底层数据可能应放在更快 source（应用内存、Hazelcast 等分布式内存、CDN）。缓存是一层工具；组合工具通常能更好处理最坏工作负载。
