### 附录 F — 生产决策树

针对五种常见工作负载模式，本附录提供端到端 “从需求到架构” 的走查。每条路径都应用第11章诊断方法、第14章系统矩阵和相关防御。


#### F.1 — 中等规模单区域 OLTP（10K-100K QPS）

**输入**：读多写少；需要事务一致性；单国家部署；p99 延迟低于 100ms。

**决策**：PostgreSQL 加读副本 + Redis 缓存。

* **运维的存储**：PostgreSQL 16，带一或两个热备读副本（同步到一个，异步到另一个）。
* **缓存**：Redis 集群用于热读路径（TTL 60s；写入时事件驱动失效）。
* **复制**：同步到一个 standby，异步到另一个。RPO = 0 对同步副本；RPO 为秒级对异步副本。
* **为何不选 NewSQL**：在中等单区域规模，PostgreSQL 的运维成熟度和生态系统胜过横向扩展的边际收益。直到真正需要多区域再迁移 NewSQL。
* **替代**：若团队偏好 MySQL 生态，可用类似复制的 MySQL；AWS 上 Aurora PostgreSQL 用于托管简单，但每 IOPS 计费更高。


#### F.2 — 面向全球用户的多区域 OLTP

**输入**：全球用户；部分操作需跨区域一致性（支付、库存）；p99 延迟低于 500ms；跨大洲灾难恢复。

**决策**：CockroachDB 或 Spanner；财务账本用 TigerBeetle 补充。

* **运维的存储**：CockroachDB（任意云）或 Spanner（仅限 GCP）。按云承诺选择。
* **账本**（如适用）：TigerBeetle 用于复式记账；在运维的存储中引用 TigerBeetle 转账 ID。
* **区域放置**：选择 3 个区域，使最坏情况 Raft 法定人数约 90ms（第6章 AP Q2 方法）。典型：US-East + EU-West + US-West（或类似）。
* **缓存**：区域 Redis 集群用于热读；全局表做跨区域复制。
* **为何这个组合**：CockroachDB 的每表区域亲和性匹配地理分区数据；TigerBeetle 的专用正确性模型是财务完整性的正确工具。
* **替代**：若需 MySQL 兼容选 TiDB；若需更接近 Postgres 兼容选 YugabyteDB；AWS 原生 serverless 选 Aurora DSQL。
