让 LLM 写一个分布式库存服务，它会产出 200 行看起来干净的 Python。代码旁的说明写道：“我们使用强一致性数据库（CockroachDB），以确保任何商品都不会超卖。这让我们按 CAP 看是 CP 系统。”代码可信，注释也可信。两者都错了，而“可信”与“正确”之间的差距正是本章的主题。（与本书每次 LLM 冷启动代码引用一样，这里的缺陷是结构性的——一个口号级别的 CAP 论断掩盖了每个操作层面的问题——而非语法性的。）

模型选择 CP，是因为网上关于 CockroachDB 的论调说 CockroachDB 是 CP。模型没有说明 CockroachDB 默认隔离级别是可串行化的，没有说明它的提交延迟取决于数据在单区域还是多区域，没有说明“CAP 里的一致性”指的是线性一致性（linearizability）——这比“事务性”强得多——也没有说明应用看到的延迟更多与 PACELC 有关（无分区时的 C 与 L 权衡），而非分区时的 C 或 A 选择。

本章教你区分“知道标签”（CP、AP、最终一致性、强一致性）和“推理它们的实际代价”。我们从 Deutsch 的八大谬误开始，因为它们命名了每个错误分布式直觉所依赖的假设。然后精确陈述 CAP（不是口号），再讲 PACELC——它把 CAP 忽略的无分区情况也纳入进来。


### 2.1 Deutsch 的分布式计算八大谬误

20 世纪 90 年代初，Sun Microsystems 的 Peter Deutsch 写下了新手进入分布式计算时常犯的错误假设清单。后来 James Gosling 补充了第八条。这份清单经得起时间考验，因为它们不是关于具体技术的谬误；它们关乎单机直觉与分布式现实之间的差距。

八大谬误：

  1. **网络是可靠的。**
  2. **延迟为零。**
  3. **带宽无限。**
  4. **网络是安全的。**
  5. **拓扑不会变。**
  6. **只有一个管理员。**
  7. **传输成本为零。**
  8. **网络是同构的。**

每条谬误对应一类缺陷。我们快速过一遍，因为本书后续章节会深入展开其中大部分。


#### 网络是可靠的

数据包会丢。TCP 会重传，但 TCP 本身在多次重试后也可能放弃并报告连接断开。HTTP 构建在 TCP 之上，继承了这一点。当你的代码调用 `http.post(url)` 并收到超时时，你不知道请求是否已被处理；你只知道你没收到响应。

仅此一条谬误就是第1章第三个谎言（失败谎言）的根源。所有假设“RPC 有 TCP 语义”的代码模式都从这里开始。我们将在第21章再次回到网络，它的不可靠会引发级联故障；在第18章回到它，它会破坏朴素的分布式锁。
