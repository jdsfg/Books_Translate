(f) **检查失败请求的日志**：trace 展示时间线；日志展示服务当时的想法。按 trace ID 关联。

(g) **检查 service X 的指标**：失败时的错误率、延迟、资源使用。X 是否 CPU 受限？内存受限？其下游是否慢？

(h) **在测试环境复现**：用已知的坏输入模式复现失败。迭代修复。

诊断流程的技巧是知道每一步该看什么。Trace 是起点；诊断流程结合 traces、logs、metrics 和复现。常见模式：1% 中的 80%（即所有请求的 0.8%）足够高，表明真实 bug，但低到随机抽查可能发现不了。Tracing  surfaced 这些客户支持量尚未检测到的长尾问题。

**Q3.** 某团队已 rollout OpenTelemetry。Trace 工作正常，但他们发现 Kafka 消费服务的 trace 没有与生产服务的 trace 连接。诊断。

提示

追踪上下文默认不会通过 Kafka 消息传播。

**答案：** 默认 Kafka 客户端不传播追踪上下文。当 service A 生产消息、service B 消费时，B 没有追踪上下文把它的工作链接回 A。

修复：在 Kafka message headers 中显式传播追踪上下文。生产端：


    from opentelemetry.propagate import inject

    headers = {}
    inject(headers)
    producer.send(topic, value=message, headers=headers)


`inject` 函数按 W3C 标准将当前追踪上下文作为 `traceparent` 和（可选）`tracestate` headers 插入。消费端：


    from opentelemetry.propagate import extract

    headers = {k: v for k, v in record.headers}
    context = extract(headers)
    with tracer.start_as_current_span("consume", context=context):
        process(record)


`extract` 读取 headers 并创建链接到生产者跨度的上下文。消费端跨度成为生产者 send 跨度的子跨度；trace 树跨越 Kafka 边界。

OpenTelemetry 有许多 Kafka 客户端自动仪器库（`opentelemetry-instrumentation-kafka-python`、`opentelemetry-instrumentation-confluent-kafka`）可自动处理传播。若团队使用这些，传播透明。若使用未自动仪器的原始 Kafka 客户端，需要如上手动传播。

该模式可泛化：任何异步边界（队列、定时任务、webhooks、event buses）都需要显式传播。OpenTelemetry 提供 `inject`/`extract` 原语；应用代码使用它们。

Kafka 传播修复后，团队将看到从 API gateway → producer service → Kafka → consumer service → 下游服务的完整 trace。端到端可见性是分布式追踪的全部意义。
