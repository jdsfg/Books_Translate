(f) **检查失败请求的日志**：追踪展示时间线；日志展示服务当时的想法。按追踪 ID 关联。

(g) **检查服务 X 的指标**：失败时的错误率、延迟、资源使用。X 是否 CPU 受限？内存受限？其下游是否慢？

(h) **在测试环境复现**：用已知的坏输入模式复现失败。迭代修复。

诊断流程的技巧是知道每一步该看什么。追踪是起点；诊断流程结合追踪、日志、指标和复现。常见模式：1% 中的 80%（即所有请求的 0.8%）足够高，表明真实缺陷，但低到随机抽查可能发现不了。追踪  surfaced 这些客户支持量尚未检测到的长尾问题。

**Q3.** 某团队已 rollout OpenTelemetry。追踪工作正常，但他们发现 Kafka 消费服务的追踪没有与生产服务的追踪连接。诊断。

提示

追踪上下文默认不会通过 Kafka 消息传播。

**答案：** 默认 Kafka 客户端不传播追踪上下文。当服务 A 生产消息、服务 B 消费时，B 没有追踪上下文把它的工作链接回 A。

修复：在 Kafka 消息头部中显式传播追踪上下文。生产端：


    from opentelemetry.propagate import inject

    头部 = {}
    inject(头部)
    producer.send(主题, 值=消息, 头部=头部)


`inject` 函数按 W3C 标准将当前追踪上下文作为 `traceparent` 和（可选）`tracestate` 头部插入。消费端：


    from opentelemetry.propagate import extract

    头部 = {k: v for k, v in record.headers}
    上下文 = extract(头部)
    with tracer.start_as_current_span("消费", 上下文=上下文):
        进程(记录)


`extract` 读取头部并创建链接到生产者跨度的上下文。消费端跨度成为生产者发送跨度的子跨度；追踪树跨越 Kafka 边界。

OpenTelemetry 有许多 Kafka 客户端自动仪器库（`opentelemetry-instrumentation-kafka-python`、`opentelemetry-instrumentation-confluent-kafka`）可自动处理传播。若团队使用这些，传播透明。若使用未自动仪器的原始 Kafka 客户端，需要如上手动传播。

该模式可泛化：任何异步边界（队列、定时任务、webhooks、事件 buses）都需要显式传播。OpenTelemetry 提供 `inject`/`extract` 原语；应用代码使用它们。

Kafka 传播修复后，团队将看到从 API 网关→生产者服务 → Kafka → 消费者服务→下游服务的完整追踪。端到端可见性是分布式追踪的全部意义。
