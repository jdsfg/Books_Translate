#### 为何有效

Marker 是同步令牌。Marker 之后，快照前发送的消息不可能到达（因为 FIFO 顺序保证任何在 marker 前发送的消息都会在 marker 前到达）。Marker 之前，快照后发送的消息不可能到达（因为 marker 在发送之后到达）。

记录的状态（各进程状态 + 各通道在途消息）是一个一致快照：它可能在某个真实时刻就是系统状态，尽管没有命名某个具体时刻。


#### 2026 年重要性

Chandy-Lamport 是分布式 checkpointing 系统的基础：

* **Apache Flink 的 checkpointing** ：Chandy-Lamport 的变体，用于流计算。定期地，一个 marker（在 Flink 中叫 “checkpoint barrier”）流过数据流图。每个算子在 barrier 经过时记录状态；合在一起，这些状态是一个一致快照。Flink 的 exactly-once 语义建立于此。

* **某些实现的分布式事务** ：特定时间戳处系统的 “快照” 概念上是一个 Chandy-Lamport 快照，尽管大多数生产系统使用基于时间戳的 MVCC。

* **可重启分布式计算** ：Spark RDD lineage、MapReduce 的 checkpointing、各种 ML 训练系统使用基于快照的重启。

该协议已有 40 多年历史，仍是思考一致分布式状态的标准方式。任何从事流处理的人都应了解；任何评估 Flink 风格系统的人都应知道它提供什么保证以及如何实现。


### 15.5 生产中的最终一致性


#### DynamoDB

默认读最终一致：读返回最近成功复制的值，但复制滞后可能意味着稍旧的值。区域内滞后通常亚秒。

对需要 read-your-writes 的操作，客户端可请求 `ConsistentRead=true`，对领导者做同步读。代价：通常是最终读延迟的 2 倍，并消耗更多 capacity unit。

跨区域（Global Tables）时，DynamoDB 使用异步多主复制。冲突解决按 item 做 last-write-wins。应用必须处理自己写入一个区域后被另一区域并发写覆盖的情况（罕见但可能）。


#### Cassandra

按操作可调。Consistency level ONE：一个副本响应即可；非常快；最终。Consistency level 法定人数：多数响应；per-operation 线性化（关于 sloppy 法定人数有注意事项）。Consistency level ALL：所有副本；只对特定一致性证明有用。

应用纪律：按需求为每次操作选择一致性级别。许多 Cassandra 生产故障可追溯为使用错误的一致性级别（例如，需要 read-your-writes 时却用 ONE 读）。


#### Redis 复制

主从复制异步。从副本读可能过期。Master 上 ack 的写尚未在副本上；故障切换可能丢失近期写。

对需要更强保证的应用，Redis 提供 `WAIT N` 命令，阻塞直到 N 个副本 ack。这是 per-write 选择加入，非全局模式。
