#### 实践实现

标准实现使用 per-session HLC（第3章）跟踪。客户端记录观察到的最大 HLC；后续操作要求服务器至少赶上该 HLC。服务器要么等待、返回该 HLC 的数据，要么以 “换副本重试” 拒绝。

CockroachDB、MongoDB、YugabyteDB 都实现了变体。Cassandra 和 DynamoDB 历史上不自动提供会话保证；应用代码必须通过 “本会话路由到主库” 模式自行处理。


### 15.3 冲突解决策略

当两个并发写冲突（两个副本接受同一键的不同值）时，系统必须解决。三种策略：

(a) **Last write wins（LWW）** ：时间戳最高的写胜出。简单，但受第3章时钟偏移问题影响。Cassandra 默认。

(b) **Sibling values** ：系统保留所有冲突值；应用看到它们并选择（或合并）。Riak 的做法。需要应用逻辑，但从不静默丢失数据。

(c) **CRDT** ：数据类型被设计成冲突有确定性合并函数。系统自动应用合并；无需应用逻辑。第16章深入讲解。

正确策略取决于工作负载：

* 应用有明确 “赢家” 语义的数据：LWW。
* 应用能推理所有候选的数据：sibling values。
* 具有数学结构的数据（计数器、集合、寄存器）：CRDT。

LWW 是最常见默认因为它最简单。代价是时钟偏移问题：一个逻辑上更晚的写可能因写节点时钟慢而输掉。


### 15.4 Chandy-Lamport 分布式快照

一个基础原语：如何在系统仍在运行时拍下一致快照？

Chandy 和 Lamport 1985 年论文引入了一个协议，无需全局时钟即可产生代表一致全局状态的快照。


#### 场景

一组进程通过 FIFO 通道通信（每条通道消息按发送顺序投递）。系统状态是各进程状态加上每条通道上正在传输的消息。

_一致全局状态_ 是指一个可能真实发生过的状态：对任何在途消息，它必须已被发送（发送者状态反映发送）但尚未被接收（接收者状态未反映接收）。

挑战：如何在不冻结系统的情况下捕获这种状态？


#### 协议

一个指定发起者决定拍快照。发起者：

(a) 记录自身状态。(b) 向每条出通道发送一个 _marker_。(c) 开始记录每条入通道上收到的所有消息（直到该通道的 marker 到达）。

其他每个进程首次收到 marker 时：

(a) 记录自身状态。(b) 记录收到 marker 的通道为 “快照期间为空”（该通道消息不属于快照）。(c) 向每条出通道发送 marker。(d) 开始在每条 _其他_ 入通道上记录消息，直到各通道都收到 marker。

当进程在已经开始记录的通道上收到 marker 时，停止在该通道上记录；已记录的消息就是该通道的在途集合。
