#### 执行代价

窗口函数至少对每个不同的 `PARTITION BY + ORDER BY` 规范做一次排序。引擎按分区键分组、在每个分区内排序、再扫 frame。如果有三个窗口函数使用相同的 `OVER` 子句，引擎只排序一次并复用。不同的 OVER 子句意味着多次排序——要留意计划。


### 8.8 EXPLAIN —— 读懂引擎实际做了什么

每个 DBMS 都提供 `EXPLAIN` 或 `EXPLAIN ANALYZE` 命令来显示计划。计划是一棵算子树——第 7 章逻辑表达式的物理版本。

“GPA 高于院系平均”查询在 PostgreSQL 中的输出（`Hash Join` 即哈希连接，`Hash` / `HashAggregate` 都基于哈希）：

    Hash Join  (cost=25.00..500.00 rows=800 width=40)
      Hash Cond: (s.dept_id = d.dept_id)
      Join Filter: (s.gpa > d.avg_gpa)
      ->  Seq Scan on Students s
      ->  Hash
            ->  HashAggregate
                  Group Key: dept_id
                  ->  Seq Scan on Students

从下往上读。内部 `Seq Scan` 喂给 `HashAggregate` 计算院系平均。结果被 hash。外部 `Seq Scan` 探测 hash 并应用过滤 `s.gpa > d.avg_gpa`。优化器自动完成了子查询去相关。

`EXPLAIN ANALYZE` 还会实际运行查询并显示真实行数和时间。它是工作中数据库工程师最有价值的单一命令。

我们还没讲索引或代价模型——那是第 10 和第 12 章。这里的重点是文化：不懂计划就读 SQL 是 folklore。本章每个高级构造都对应一个计划。要学看。


#### 常见误解

“EXPLAIN 会运行查询。” 不会——除非你加 `ANALYZE`。普通 `EXPLAIN` 只显示估计计划。`EXPLAIN ANALYZE` 才真正执行并测量。生产环境中这很关键：不小心在 `EXPLAIN UPDATE` 上加 `ANALYZE` 会真的执行更新。


### 8.9 把各部分拼在一起——一个真实查询

注册主任问：“给出每个院系 GPA 前三的学生，但只保留至少 20 名学生的院系，并附上每个学生最近一门课的成绩。”

    WITH dept_large AS (
      SELECT dept_id FROM Students GROUP BY dept_id HAVING COUNT(*) >= 20
    ),
    ranked AS (
      SELECT s.id, s.name, s.dept_id, s.gpa,
             RANK() OVER (PARTITION BY s.dept_id ORDER BY s.gpa DESC) AS r
      FROM Students s
      WHERE s.dept_id IN (SELECT dept_id FROM dept_large)
    ),
    latest_grade AS (
      SELECT e.student_id, e.grade
      FROM (
        SELECT student_id, grade,
               ROW_NUMBER() OVER (PARTITION BY student_id ORDER BY term DESC) AS rn
        FROM Enrollments
      ) x WHERE rn = 1
    )
    SELECT r.name, r.dept_id, r.gpa, g.grade AS latest_grade
    FROM ranked r LEFT JOIN latest_grade g ON r.id = g.student_id
    WHERE r.r <= 3
    ORDER BY r.dept_id, r.gpa DESC;

本章每个构造都齐了：CTE、用于“每组取一行”的嵌套窗口函数、IN 里的子查询、LEFT JOIN 以保留没有成绩的学生。查询虽长，但阅读线性——关键是，单个 EXPLAIN 就能看到引擎的完整计划。
