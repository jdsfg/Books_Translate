(c) 不会，它不改变*最坏情况*。最坏情况是查询第一次运行时什么都没被缓存——我们仍然要从磁盘读最多 629 页。缓冲池帮助的是*后续*查询：如果 Courses 表小到可以完全留在缓冲池中（4 页 trivial），那么第二次及以后的课程标题查找就几乎免费。这也是缓冲池管理（第 9 章）和索引（第 10 章）都必不可少的第一条提示——一个帮助重复查询，另一个帮助第一次查询。

**Q3.** 团队里一位初级工程师说：“我们用 JSON 文件代替数据库吧。JSON 有 Schema，容易读，还不用安装任何东西。” 这个方案放弃了四项 DBMS 承诺中的哪些？又保留了哪些（如果有）？在什么狭窄场景下 JSON 文件真的够用？

提示

独立地处理每一项承诺。哪些 JSON 免费给你？哪些必须自己拙劣地重建？

**答案：**

* **查询语言：** 放弃。每个问题都要写 Python 或 jq 一次性脚本。
* **并发控制：** 放弃。文件锁是你唯一手段，而且要么全锁要么不锁。
* **崩溃恢复：** 放弃。保存时崩溃会得到截断或半写的 JSON 文件，甚至可能无法解析。
* **完整性保证：** 部分保留。JSON 可以有结构 Schema（必填字段、类型，通过 JSON Schema），但它没有文件之间的引用完整性概念。

**JSON 够用的场景：** 单用户、 mostly-read、数据量小、没有并发、没有崩溃安全要求。例如：配置文件、随应用发布的静态数据集、个人 200 条书签列表。一旦工作负载出现*任一*（多写者、需要掉电 survive、大数据量下亚秒查询、强制引用）之一，JSON 就不够了。
