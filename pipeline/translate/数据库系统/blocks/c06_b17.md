#### 深入思考

**Q1.** ER 模型表达结构关系，但不说数据将如何被查询。查询模式应该影响 ER 建模吗？还是 ER 应纯粹是结构，性能考虑只在 Schema/索引阶段应用？

**讨论：** 纯理论说：ER 是结构，性能是另一回事。这个论点很干净——如果让性能渗入 ER，我们会混淆两个问题，模型就会和实现耦合。

但纯理论有时会产出生动痛苦的 Schema。例子：一个严格从 ER 推导出的电商 Schema 可能有 `ProductImages` 表存图片 URL，由 `Products` 引用。结构上正确。但每次在分类页列出 20 个产品时，为了取主图就要多 20 次连接。务实的做法会把主图 URL 折叠进 `Products.primary_image_url` 作为反规范化便利列，在变更主图时由触发器或应用更新。不纯，但快得多。

中间道路：**先纯粹地 ER 建模，然后在真实工作负载下评估 Schema，只在证据要求时才反规范化。** 这给你一个干净的基线，可以向新工程师解释（“我们从这里开始，因为它结构上正确；我们在这里偏离，因为这条查询是已知热路径，而反规范化由 <trigger / 应用代码 / 夜间重建> 维护”）。偏离是被记录和可解释的，不是意外。

更深的原理：抽象和性能之间存在张力，好的设计先选抽象，再在必不得已处为性能付费。直接跳到性能优化 Schema 而没有抽象，往往会产生没人完全理解的系统。

**Q2.** Codd 1970 年发表关系模型；Chen 1976 年发表 ER 模型。为什么我们仍把 ER 建模作为独立步骤教授，而不是直接教授关系建模？

**讨论：** 两个原因，都很实用。

第一：关系模型对初始设计讨论来说_太低级_。当你草图“我们有学生、课程、选课”时，你不会想争论选课该有复合主键还是代理 id。你想先对_形状_达成一致。ER 建模给了这个形状一套词汇——实体、关系、基数——位于 DDL 决策之上。

第二：ER 建模产出图，而图是沟通工具。你可以在会议上指着 ER 图说“我们把这个建模成 M:N 关系，带这两个属性”，房间里每个人都懂。而关于关系 Schema 的等价对话是“我们有 X、Y、Z 三张表，Z 有这两个外键”——需要更多上下文，也无法一样干净地传达基数。

实际后果：即使是写了 20 年 SQL 的工程师，在非平凡 Schema 之前仍会画 ER 图（或某种非正式等价物）。ER 模型是一种思考工具，超越了“我直接写表”的职业阶段。
