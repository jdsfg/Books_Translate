第 4 章教会我们在已有 Schema 上写 SQL 的机制。但 Schema 从哪里来？我们一直表现得好像 `Students`、`Courses`、`Instructors`、`Enrollments` 的分解很明显。其实并非如此——有人设计了它，很可能是在写任何 DDL 之前就经过思考的。

本章就是退后那一步：在你键入 `CREATE TABLE` 之前，如何设计 Schema？在主流关系型传统中，答案是**实体-关系建模（Entity-Relationship, ER modeling）**。ER 建模是一种思考和画图方式，把“我的领域里有哪几类东西，它们如何关联？”和“我应该创建哪些表？”分离开。第一个问题是领域建模问题，第二个是 Schema 映射问题。把它们混在一起是坏 Schema 设计的经典来源。

叙事 A 以新角色重新登场。在第 2、3 章我们*逆向工程*了选课系统——我们有 CSV，观察到异常，重建了表。本章我们将*正向工程*它：从注册员用自然语言描述出发，产出 ER 模型，再机械地导出关系 Schema。如果一切顺利，我们应该得到与第 3 章 Schema 非常接近的结果。目标是看到过程，而不只是结果。


### 5.1 为什么先建模？

假设你拿到这样的描述：“为大学注册办公室建一个系统。跟踪学生、他们的选课、课程、教师、院系、先修课和转学分。”

如果你直接跳到 DDL，20 分钟内你会创建八张表——然后中途发现其中三张尴尬重叠，一张表的字段应该拆到另一张表里，还漏掉了一种关系。你会撤回重做。多次。大多数坏 Schema 就是这样来的：Schema 增量累积，没有设计阶段，最终反映的是开发者碰巧想起东西的顺序。

ER 建模介入在 DDL 之前。你识别*实体*（领域中的“事物”）、它们之间的*关系*、以及每个实体的*属性*。你决定基数（“一个学生可以选多门课；一门课可以有多个学生”）。你决定什么有独立存在，什么没有。然后——只有然后——你才按一组标准规则机械地把 ER 模型映射成表。

对小 Schema 来说这听起来流程很重。实践中，一个小系统的 ER 建模可能只需白板 15 分钟，却能省下后续几天重构。对大系统（例如第 23 章的综合设计评审场景），ER 建模决定你能否把 Schema 交给其他团队，还是不得不一直为它辩护。
