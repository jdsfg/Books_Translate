**答案：** **(a) 候选键。** `order_id` 和 `item_id` 不出现在任何 FD 右侧，所以它们必须在每个候选键中。\{order\_id, item\_id\}^+：由第一条 FD 加入 customer\_\*、ship\_to\_address、order\_date；由第二条加入 item\_name、item\_price；由第四条加入 quantity。闭包为全部属性。\{order\_id, item\_id\} 是唯一候选键。

**(b) BCNF 分解。**

    Customers(customer_email, customer_name)           -- 来自 customer_email -> customer_name
    Orders(order_id, customer_email, ship_to_address, order_date)
                                                      -- ship_to_address 更宜视为每订单，而非每客户
    Items(item_id, item_name, item_price)
    OrderItems(order_id, item_id, quantity)

四张表都满足 BCNF（每张表内的每个非平凡 FD 的左侧都是超键）。

**(c) `price_snapshot` 与设计决策。** 如果我们给 `OrderItems` 增加 `price_snapshot` 列，它就复制了下单时的 `Items.item_price`。在合并视图中，FD `item_id \rightarrow item_price` 不再成立（同一 item 的不同行可能有不同的 price_snapshot）。

这是规范化违反吗？严格说是——`price_snapshot` 若维护价格历史，可由 (item_id, order_date) 推出，因此可以抽出去。但务实的答案是：**历史价格在语义上独立于当前价格。** 一旦订单生成，其商品价格不应改变，即使商品当前价格后来变了。把 `price_snapshot` 视为 OrderItem 的一个独立属性（每个订单项的价格事实）不是冗余错误——而是 capture 不可变历史状态的有意建模选择。

更严格的替代方案是维护 `PriceHistory(item_id, effective_from, price)` 表，并始终按 (item_id, order_date) 查找历史价格。这在规范化角度更优雅，但操作上更慢、更复杂。大多数真实电商系统选择 `price_snapshot` 作为务实折中。

这是第 6.8 节案例 1“作为历史状态捕获的反规范化”的干净例子。

**Q3.** 求 F = \{AB \rightarrow C, A \rightarrow D, D \rightarrow C, AB \rightarrow D\} 的最小覆盖。

提示

步骤 1：右侧单属性。步骤 2：剪枝左侧冗余。步骤 3：移除冗余 FD。使用属性闭包。

**答案：**

**步骤 1。** FD 的右侧已经是单属性。F_1 = \{AB \rightarrow C, A \rightarrow D, D \rightarrow C, AB \rightarrow D\}。

**步骤 2。** 剪枝左侧冗余属性。

* AB \rightarrow C：能否去掉 B？在 F_1 中计算 \{A\}^+：\{A\} → A \rightarrow D → \{A, D\} → D \rightarrow C → \{A, C, D\}。包含 C。所以 A \rightarrow C 被蕴含；从左侧去掉 B。把 AB \rightarrow C 替换为 A \rightarrow C。
* AB \rightarrow D：能否去掉 B？\{A\}^+ 同上，包含 D。所以 A \rightarrow D 被蕴含；从左侧去掉 B。把 AB \rightarrow D 替换为 A \rightarrow D（已存在）。

步骤 2 后：F_2 = \{A \rightarrow C, A \rightarrow D, D \rightarrow C\}（去重后 A \rightarrow D 只保留一个）。
