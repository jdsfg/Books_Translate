#### 权衡：CTE 物化

不同数据库对 CTE 处理不同。PostgreSQL 12 之前*总是*把 CTE 物化——先运行，把结果写入临时结构，外部查询再读回来。这堵“栅栏”会阻止优化器把谓词下推到 CTE 内部，导致一个看起来清爽的 CTE 往往比 inline 子查询慢。12 版改了默认行为：非递归 CTE 默认被内联，除非你显式写 `WITH x AS MATERIALIZED (...)`。MySQL 8 和 SQL Server 默认也内联。要清楚你的引擎版本。


#### 常见误解

“CTE 总是比子查询快。” 有时它们因为物化栅栏而更慢；有时一样快。用 CTE 是为了清晰和递归；其余事情信任优化器，性能关键时用 EXPLAIN 验证。


### 8.6 视图

**视图（view）**是一条命名的 SELECT 语句，表现得像表。

    CREATE VIEW active_students AS
    SELECT s.id, s.name, s.dept_id, s.year
    FROM Students s
    WHERE s.status = 'active';

    SELECT * FROM active_students WHERE dept_id = 3;

引擎不存储视图的结果。当你查询视图时，引擎把视图定义代入你的查询，然后优化合并后的语句。这种代入称为**视图展开（view expansion）**或**内联（inlining）**。


#### 视图的用途

  1. **抽象。** 一个跨六张表的复杂连接可以打包成 `enrollment_summary`。应用代码读一个视图即可。
  2. **访问控制。** 授予用户对 `active_students` 的 SELECT 权限，而不授予整张 `Students` 表的 SELECT。视图过滤掉用户不该看的列和行。
  3. **Schema 演进。** 要重命名列？加一个把旧名映射到新列的视图。迁移期间客户端继续工作。


#### 性能隐患

视图看起来像表，但不是表。查询

    SELECT * FROM active_students a JOIN Enrollments e ON a.id = e.student_id
    WHERE a.year = 4;

会展开成带有 `Students s WHERE s.status='active'`、与 Enrollments 连接、再按 year 过滤的查询。规划器随后决定下推 `year = 4` 到扫描、是否对 `status` 用索引等。写得好的视图对规划器透明。但带非平凡 DISTINCT、GROUP BY 或窗口函数的视图会构成优化障碍——规划器无法把谓词推过聚合。


#### 定义：可更新视图

如果针对视图的 UPDATE/INSERT/DELETE 能无歧义地翻译为对底层表的操作，该视图就是**可更新的**。标准可更新视图必须：

* 只引用一张基表；
* 不含 DISTINCT、GROUP BY、HAVING、UNION、聚合或窗口函数；
* SELECT 列表包含基表主键；
* INSERT 路径中不使用派生列。

跨连接的视图通常**不可更新**——引擎不知道该写哪张基表。可更新视图在适用时方便，在不适用时则是坑。


#### 物化视图

**物化视图（materialized view）**把视图结果作为真实表存储。当底层数据变化时，需要刷新。

    CREATE MATERIALIZED VIEW dept_stats AS
    SELECT dept_id, COUNT(*) AS n_students, AVG(gpa) AS avg_gpa
    FROM Students GROUP BY dept_id;

    REFRESH MATERIALIZED VIEW dept_stats;
