第 2 章留下了一片废墟——三种异常、悬空引用、一个轻微使用下就会自我腐蚀的文件系统数据层。本章要介绍一个在 1970 年代悄然取代废墟、并在 2026 年仍支撑每个主流数据库的思想：**关系模型（relational model）**。

关系模型的洞见几乎带有哲学意味。不要问“我如何存储数据？”（这会产生文件、结构、指针、索引），而要问“我的数据的*形状*是什么，独立于存储？” 答案是：元组的集合，每个元组是一个扁平的值集合，每个值来自一个已知的域。仅此而已。关系模型说，数据*就是*一组组元组的集合，其余一切——页、B 树、缓冲池——都只是存储引擎的问题。

正是这种抽象使数据库成为一门学科，而不是一袋子技巧。第 2 章 CSV 文件饱受折磨的三种异常，在正确设计的关系 Schema 下会在结构上*不可能*发生。这是我们在本章要精确阐述、并在第 6 章形式化证明的主张。


### 3.1 关系：核心概念

在数学意义上，**关系（relation）**是一个集合。具体来说，是一组**元组（tuple）**，其中每个元组具有相同结构——相同属性、相同数量的值、来自相同的域。

对于第 2 章的大学选课系统，`Students` 关系可以写成：

    Students(id INTEGER, name VARCHAR, email VARCHAR)

该关系的一个具体实例可能是集合：

    { (1001, "Alice Wong",   "alice.wong@uni.edu"),
      (1002, "Bob Khan",     "bob.khan@uni.edu"),
      (1003, "Carlos Silva", "carlos.silva@uni.edu") }

注意“关系是集合”带来的三个后果：

  1. **无序。** 上面三个元组可以按任意顺序列出——关系不变。如果你写 SQL 时依赖行顺序（“给我第一个学生”），你就误解了模型。（要顺序，你需要显式请求：`ORDER BY`。）
  2. **无重复。** 严格地说，关系不能包含两个完全相同的元组。在 SQL 中——它是一种袋（bag）模型而非严格集合模型——重复是可能的，但候选键和唯一性约束正是为了让你在需要时强制集合语义。
  3. **每个元组属性相同。** 不存在逐行变化的“行级 Schema”。这是一条原则性决策——它限制了灵活性，却使类型检查查询到索引结构的一切成为可能。

> ### 定义：关系

**关系（relation）**是元组的集合，所有元组共享同一 Schema——即具有相同属性，且属性值来自相同域。关系的 Schema 是属性名与其域的配对；关系实例是某时刻存在的具体元组集合。

通俗地说，关系是一张表，行无序、重复无意义，每一行都有相同类型、相同数量的列。中文常称“表”，数学术语是“关系”。我们会交替使用这两个词，但当需要精确时，“关系”强调我们关心抽象集合，而非存储布局。
