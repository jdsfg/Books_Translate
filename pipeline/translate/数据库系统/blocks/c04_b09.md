#### 引用完整性（输入错误）

第 2 章：`1099,Alice Wong,109,...` 可以被写进 CSV 而没有任何抱怨。

关系型 Schema：`Enrollments.student_id` 和 `Enrollments.course_id` 上的外键会在插入时捕获这个 typo：

    INSERT INTO Enrollments (student_id, course_id) VALUES (1099, 109);
    -- ERROR: insert or update on table "Enrollments" violates
    -- foreign key constraint — Key (student_id)=(1099) is not
    -- present in table "Students".

坏行永远不会落盘。操作员看到错误后可以用正确的 ID 重试。

第 2 章的四种失败，第 3 章的四种结构性修复。这就是关系模型为何是一场革命。


### 3.8 作为教学工具的关系模型

全书其余部分，我们有时说“关系模型”，有时说“SQL”。它们不是一回事：

* **关系模型**（Codd, 1970）是数学抽象：元组的集合，由关系代数（第 7 章）操作。它干净且正交。
* **SQL**（商业产物，约 1974 年至今）是实现最终收敛到的语言。它并非纯粹关系型——它允许重复（袋语义）、有三值逻辑的 NULL、有过程化特性——但它是每个主流关系型 DBMS 使用的接口。

为何有分歧？三个原因：

  1. 重复在许多常见操作中更容易产生和推理。严格的集合语义需要引擎做额外工作。
  2. 三值逻辑是对现实世界数据有洞这一事实的让步。
  3. SQL 在商业压力下演化，积累了原始关系模型未曾预料的特性（窗口函数、递归查询、JSON 支持）。

接下来的三章（第 3、4、7 章），我们在有助于推理时倚仗干净的数学抽象，在需要展示真实代码时倚仗 SQL。到第 8 章，SQL 和关系模型会进一步分道扬镳（窗口函数并非纯关系型），我们会明确说明。
