**讨论：** 这是任何长期存活系统的核心挑战。三种常见策略：

  1. **迭代式 ER 建模。** 你今天对已知领域 ER 建模，然后随着领域显现再修订模型。Schema 同步迁移。这是标准做法——每个生产 Schema 都这样演化。

  2. **可扩展属性列（EAV，实体-属性-值）。** 一张表保存 `(entity_id, attribute_name, value)` 行。每行是一个实体的一个属性，你可以通过增加新行来添加新属性，而无需改 Schema。这以模式刚性换取可查询性（EAV 查询难以优化，且常常丢失类型安全）。用于病历、CRM 定制等“每个客户有不同自定义字段”是业务现实的场景。

  3. **文档或无模式存储（第 20 章）。** 把实体存为 JSON 文档；每个文档有自己的形状。这以模式刚性换取更大的灵活性。适合真正异构的数据；对大多数操作型系统则错误，因为 Schema 能给你完整性。

正确答案取决于_预期变化多大_以及_即席查询频率_。每季度变化一次的 Schema（电商）→ 迭代 ER 建模加迁移纪律。每个客户属性都不同的 Schema（医疗 EHR）→ EAV 或混合。数据真正是文档形状的系统（用户生成的富内容、多变的网络爬取数据）→ 文档存储。

ER 建模对开放式领域并非错误方法——只是*不完整*。你仍需要 ER 模型（对应稳定核心）加扩展机制（对应可变部分）。这种混合正是大多数成熟系统收敛的方案，第 22 章会作为多语言持久化问题再次讨论。


### 本章总结

本章讲授了 ER 建模——在写 DDL 之前设计 Schema 的纪律。我们识别了**实体**（有独立存在和属性的事物）、**关系**（实体之间的关联，以度、基数、参与度刻画）、以及**属性类型**（简单、复合、多值、派生、键）。我们走过五条**ER 到关系映射规则**，并用它们正向工程了叙事 A 的大学注册系统 Schema，最终得到与第 3 章逆向工程基本相同的 Schema。

核心洞见：ER 建模把*形状*与*实现*分离。形状是你在设计会议上争论的东西——存在哪些事物、如何连接、哪些是强制的。实现细节（代理键 vs 自然键、索引选择、反规范化）在下一层，由工作负载决定。把两者混淆会产生坏 Schema，因为 DDL 级决策会泄漏进抽象层。

我们还遇到了“属性成长为实体”这一重构——现实世界最常见的 Schema 演化之一，最初建模为属性的东西积累了足够多的自身属性，值得升级为表。

展望：第 6 章对我们得到的 Schema 提出一个更尖锐的问题：它_够好吗_？是否还潜藏会导致异常的依赖？**规范化理论**（函数依赖、最小覆盖、3NF、BCNF）给我们形式化答案，并将让我们能够*证明*——而不只是争论——叙事 A 的第 3 章 Schema 在结构上是安全的。
