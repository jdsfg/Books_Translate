### 1.2 存储层次（以及它为何决定一切）

如果不理解数据“住在哪里”，就无法合理地讨论数据库为什么被设计成现在这样。本书中你会看到的每一个设计决策——B 树为何是这种形状、为什么查询计划器按 I/O 次数而不是 CPU 指令数来计代价、为什么恢复算法要那样写——都源于一个物理现实：**存储是一个层次结构**，每一层都比上一层慢得多、大得多。

以下是 2026 年典型服务器上现代存储层次的大致参数。具体数字每年都在变；**比例关系**不会变。

| 层级 | 典型容量 | 访问时间 | 相对成本 | 易失？ |
|---|---|---|---|---|
| CPU 寄存器 | < 1 KB | ~0.3 ns | 每字节无限高 | 是 |
| L1 缓存 | ~64 KB | ~1 ns | 非常高 | 是 |
| L2 缓存 | ~1 MB | ~3 ns | 高 | 是 |
| L3 缓存 | ~32 MB | ~10 ns | 高 | 是 |
| DRAM（内存） | ~64–512 GB | ~100 ns | 中等 | 是 |
| SSD（NVMe） | ~1–4 TB | ~10–100 µs | 低 | 否 |
| HDD（机械硬盘） | ~4–20 TB | ~5–15 ms | 非常低 | 否 |
| 磁带 / 冷存 | 无限 | 秒级+ | 最低 | 否 |

关注两个比例。寄存器到 DRAM 约为 300 倍。DRAM 到 SSD 约为 1000 倍。DRAM 到 HDD 约为 100,000 倍。在 HDD 返回一个页的时间里，CPU 可以执行大约 **3000 万** 次寄存器操作（\frac{10\,\text{ms}}{0.3\,\text{ns}} \approx 3.3 \times 10^7；§1.6 习题 2 会具体算出这个数值）。在 SSD 上比例更小，但仍然有六个数量级——每次页读取大约对应 10 万–20 万次 CPU 操作。

这告诉我们三件塑造后续每一章的事：

  1. **数据库比内存大。** 大多数有用的数据库无法全部装进 DRAM。我们必须假设数据驻留在 SSD 或 HDD 上，并以块为单位调入内存。这些块称为**页（page）**——一个从第 9 章开始会频繁使用的概念。

  2. **I/O 才是需要关注的代价。** 分析查询代价时，我们数 I/O 次数，而不是 CPU 指令数。原因就在上面的比例。一个执行 1 亿次 CPU 操作但只读 1 个页的连接算法，轻松打败一个执行 100 万次 CPU 操作却要读 100 个页的算法。

  3. **易失性是一个生死攸关的区分。** SSD 以上所有层级都是**易失的**——断电后数据消失。数据库承诺“记住”的任何东西（ACID 中的 D）必须在做出承诺之前到达非易失存储。这就是崩溃恢复成为 DBMS 四大核心职责之一的原因。


#### 常见误解

新手工程师常想：“SSD 已经很快了，所以磁盘和内存的差距不再重要。” 这种想法在两个意义上是错的。第一，DRAM 到 SSD 的差距仍然是约 1000 倍，这非常巨大——一条查询如果多读 1000 次 SSD，人会明显感觉到慢。第二，SSD 有*不同*的性能特征（随机读很快、随机写会磨损单元、顺序写比随机写快得多），这就是为什么写优化引擎如 LSM 树会专门优化顺序写。认为“磁盘不再重要”会直接导致查询比必要情况慢 100 倍。
