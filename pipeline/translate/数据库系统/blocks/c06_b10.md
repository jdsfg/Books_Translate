现在同一副本不能同时有两笔 `return_date IS NULL` 的借阅。
* 另一种设计是使用单独的 `ActiveLoans` 表保存仅未关闭的借阅，再用 `LoanHistory` 表保存已关闭的历史记录。两种方法都可行；第一种更简单，第二种在庞大的借阅历史上查询“所有在借记录”时更快。

注意，权衡主题（第 1 章）正在显现：“用部分唯一索引在 SQL 中强制约束” vs “拆成两张表”有不同的性能和运维特征。ER 建模本身不强制选择——那是在 ER 模型稳定后做出的 Schema 级权衡。


#### 常见误解

新手工程师常以为“ER 模型会给你唯一正确的 Schema”。并不会。ER 模型捕捉的是领域的*形状*，但最终 Schema 还涉及更多选择：代理键 vs 自然键、合并还是拆分几张小表、如何处理历史数据、如何表达 ER 图轻描淡写掠过的约束。ER 模型是 Schema 设计的*输入*，不是*输出*。两个不同工程师拿到同一张 ER 图可能产生略有不同的 Schema，对不同的工作负载都可能正确。


### 5.7 属性何时应升级为实体

ER 建模中最常见的重构之一：发现你最初建模为属性的东西其实应该是独立实体。

症状：该属性开始增长。先有 name，再有 name + description，再加 display order。其他实体想引用它。同样的值在许多行中重复出现。

例子：在我们的大学模型中，`Course.credits` 只是一个整数。但假设有人说：“实际上，不同院系对学分的度量不同——艺术学院按学期学时，工程学院按季度学时，研究生课程使用不同尺度。” 突然之间，credits 不再是简单整数，而必须在上下文中解释。

此时 `credits` 很可能应该变成引用一个 `CreditSystem` 实体：

    CreditSystems (id, department, unit_name, scale_factor)
    Courses (id, title, credit_value, credit_system_id REFERENCES CreditSystems(id), ...)

症状是：“我的属性开始有了自己的属性。” 这就是把它提升为实体的时刻。实践中，过早做会增加不必要的复杂度；过晚做会迫使后续迁移。需要判断。

另一个例子：电商系统中，`order.shipping_address` 开始时是字符串。然后你发现客户有多个地址。然后你想对照邮政数据库验证。然后你想跟踪每个地址的配送状态。发货地址（shipping address）已经变成了实体（`Addresses`），订单引用它。

这种“属性成长为实体”的模式是最常见的数据库重构故事之一，尤其是系统起初简单、多年演化的场景。
