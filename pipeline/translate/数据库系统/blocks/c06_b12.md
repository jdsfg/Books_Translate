#### 概念检查

**Q1.** 对下列每一项，归类为实体、属性或关系，并用一句话说明理由：(a) 社交媒体应用中的 “User”。(b) 社交媒体帖子上的 “Like”。(c) 用户的 “Location”。(d) 两个用户之间的 “Friendship”。(e) 照片的 “Tag”。

提示

问：它有独立存在和自己的属性吗？它连接两个东西吗？

**答案：** (a) **实体。** 有身份（user_id）、独立属性（name, email, bio）、独立生命周期。(b) **实体**（带关系色彩）。Like 有属性：timestamp，可能有反应类型。它_关联_一个 User 和一个 Post，因此是典型的 M:N 关系——在 SQL 中变成连接表。你也可以把它建模为带属性的关系；两者都合理。(c) **属性**（大多数情况下）。除非位置被历史跟踪（用户搬家，旧位置保留）或有自己的属性（时区、邮编有效性），否则它是 User 的属性。若位置有自己的属性或历史，它就变成实体。(d) **关系。** 连接两个 User；最简单形式是 M:N（一元，因为两端都是 User）。常带属性：friendship_since、status（pending、accepted、blocked），这又把它推向“本身是实体的连接表”。(e) **灰色地带。** 如果 Tag 只是字符串（“#vacation”），它是照片的属性。如果 Tag 有属性（创建者、使用次数、翻译），它们就是实体，通过 M:N 连接表（PhotoTags）引用。

规律：“灰色地带”在 ER 建模中很常见。问题不是“它到底是什么”，而是“我的系统需要记住并改变关于它的哪些东西？”如果答案随时间增长，你最初建模为属性的东西就会变成实体。

**Q2.** Schema 中存在一个 1:1 关系。什么时候应该把两个实体合并成一张表，什么时候应保持分开？

**答案：** **合并**当：

* 两个实体总是一起出现（相同生命周期——一起创建、一起删除）。
* 没有其他实体分别引用它们。
* 查询通常需要两者的数据。

**保持分开**当：

* 一侧可选。`User` 始终存在；`PremiumSubscription` 只存在于部分用户。此处 1:1 让你能避免给所有免费用户的 premium-only 列填 NULL。
* 数据访问模式不同。如果一侧的读取频率是另一侧的 1000 倍，分开能减少热表的页大小、改善缓存行为。
* 数据敏感度不同。`User` 有公开字段；`UserSSN` 高敏感且受访问控制。分开更安全。
* 历史/版本化不同。一侧经常变化，另一侧几乎不变。

实践中大多数 1:1 关系因上述原因之一属于“保持分开”，所以真正可合并的 1:1 很少见。
