#### BCNF 与 3NF 何时不同？

大多数实际中满足 3NF 的 Schema 也满足 BCNF。差异出现在 Schema 有**重叠候选键**，并且存在一个 FD，其右侧是主属性但左侧不是完整候选键。

经典例子：

    R(city, street, zip)

> **领域提示——读例子前先看。** 以下分析假设美国 5 位 ZIP 编码，其中每个 ZIP 恰好对应一个城市。这个 FD（`zip \rightarrow city`）**对英国邮编、德国 PLZ、加拿大邮政编码及大多数其他国家邮政系统不成立**，因为单个编码可能跨越多个地区或市镇。函数依赖是_领域特定断言_，不是逻辑真理。在把规范化应用于真实数据前，请验证你用的 FD 在你的地区、组织和时间段确实成立。ZIP 例子在教科书中流行正是因为它干净且美国中心；它误导过很多国际学生设计出坏的 Schema。

假设——**在“每个 zip 恰好对应一个城市”的邮政系统（如美国 ZIP）前提下**：

* \{city, street\} \rightarrow \{zip\}（每个地址有唯一 zip）
* \{zip\} \rightarrow \{city\}（每个 zip 只属于一个城市）

候选键：\{city, street\} 和 \{zip, street\}（两者都能决定所有属性）。

FD zip \rightarrow city：左侧 `zip` 不是超键（单独 zip 不能决定 street）。右侧 `city` 是主属性（它是第一个候选键的一部分）。因此该 FD 满足 3NF（条件 2），但违反 BCNF（BCNF 要求左侧是超键）。

这是“真实”的违反吗？它仍然导致冗余：同一 zip 的每一行都要重复相同城市。改变一个 zip 的城市归属就要更新所有行。

BCNF 分解：

    ZipCity(zip, city)
    StreetZip(street, zip)

但这样我们丢失了原始 FD \{city, street\} \rightarrow \{zip\}——在分解后的任何单张表中都无法强制执行。这就是权衡：BCNF 分解有时会丢失 FD，意味着该分解_不保持依赖_，尽管它是_无损连接_的。


#### 3NF vs BCNF：务实选择

* **3NF** 总能实现且不丢失任何 FD（存在保证算法）。
* **BCNF** 总能以无损连接方式实现，但可能需要丢失 FD。

实践共识：

* 能做到就追求 BCNF。
* 当 BCNF 会丢失有意义的约束时，退而接受 3NF。
* 无论哪种情况，通过 ER 建模构建的大多数操作型 Schema 自然地落在 BCNF，所以实践中这个区别很少咬人。
