**Q3.** 一位资深工程师说：“总是写能利用查询优化器的 SQL——你不需要理解查询如何执行。”一位初级工程师回答：“但如果我不理解执行过程，怎么知道优化器什么时候会坑我？”谁对，各自观点抓住了什么？

**讨论：** 两者都对，部分对。

资深工程师的观点_多半_正确：成熟数据库（PostgreSQL、MySQL、SQL Server、Oracle）的优化器确实很复杂——它把大多数查询处理得足够好，以至于手工调优往往适得其反。把职业生涯花在手写执行计划上是浪费；优化器做得更好，而且数据量变化时它能自动调整。过早执行查询优化确实是真正的反模式。

初级工程师的观点针对那_困难_的 5% 查询。当查询慢时，优化器已经选了一个计划。要修复它，你需要理解 (a) 它选了什么计划（`EXPLAIN ANALYZE`），(b) 为什么计划不好（缺索引？统计信息陈旧？连接顺序错误？），以及 (c) 如何把它推向更好的计划（加索引、用等价形式重写查询、更新统计信息、加 hint）。

结论是：**声明式写 SQL，但学会读执行计划。** 日常工作中你把数据库当黑盒（“告诉它你想要什么”）。出问题时就打开盒子诊断。技能在于知道什么时候看——通常不用；偶尔必须。

这正是第 11、12 章的中心哲学：优化器既强大又不完美，真正的工程师需要理解它的两面。


### 本章总结

本章把第 3 章的关系模型变成了一门工作语言。**DDL** 定义 Schema，**DML** 操作数据，`SELECT` 的逻辑求值顺序（FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT）决定正确性，无论引擎实际如何执行。

**连接**沿外键进行；五种类型（INNER、LEFT/RIGHT/FULL OUTER、CROSS）控制不匹配行如何处理。最常见 bug 是把右侧表的过滤条件放在 `WHERE` 而不是 `ON` 中，从而把 LEFT JOIN 悄悄降级为 INNER JOIN。**`GROUP BY / HAVING`** 是聚合机制：每个非聚合 `SELECT` 列必须出现在 `GROUP BY` 中，`HAVING` 过滤分组而 `WHERE` 过滤行。**NULL** 贯穿每条查询——用 `IS NULL` 和 `COALESCE` 显式处理它，因为 `=` 和 `!=` 会悄悄丢掉 null 行。

我们预览了**事务**（第 13 章）和**索引**（第 10 章），足以让全书后续 SQL 例子都能看懂。叙事 A 里程碑：“Alice 选了哪些课？”现在变成一条 SQL 语句，而不是每个问题都写一个 Python 脚本。叙事 B 伏笔：同样的连接很快会变成一条“20 分钟查询”，其代价由第 10–12 章解释。
