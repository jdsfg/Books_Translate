### 6.9 3NF 合成算法（可选深入）

为完整起见，这里给出从一组 FD 产生 3NF 分解的标准算法。当你需要严格地从给定约束设计 Schema 时，它很有用。

**输入：** 关系 R，属性集 U，FD 集合 F。

**输出：** 一组关系，每个满足 3NF，且分解是无损连接和依赖保持的。

    1. 计算 F 的最小覆盖 F_c。
    2. 对 F_c 中每个 FD X -> A：
         如果 X 还没有产生关系，创建关系 R_X，模式为 X \cup A；
         否则把 A 合并进已有的 R_X 关系。
    3. 如果目前创建的关系中没有一个包含 R 的候选键，
       则再创建一个关系，恰好包含 R 的一个候选键的属性。
    4. 消除任何属性集是另一个关系属性集子集的关系。

结果是一组关系，每个满足 3NF，并保证依赖保持和无损连接。

对于 BCNF，不存在能保证依赖保持的通用合成算法——你只能迭代分解，并接受某些 FD 可能不再能在单张关系内强制执行。大多数生产 Schema 在需要做选择时，会选择 3NF 或更好。


### 权衡总结

* **更高范式以查询便利性换取更新安全。** 完全分解的 Schema 没有更新异常，但任何非平凡报表都需要连接。报表消耗 CPU；异常导致数据丢失。对事务型系统来说，这个权衡几乎总是不划界。

* **BCNF 以依赖保持换取更强的异常保证。** BCNF 消除了每个非平凡 FD 导致的冗余，但某些 FD 可能跨越分解后的表，需要 CHECK 或触发器来强制。3NF 以允许一小类冗余为代价，把所有 FD 保留在单表内。

* **3NF 合成算法以局部优化换取无损、依赖保持的保证。** 它能从任意 FD 集合机械地产生正确的分解——它得出的 Schema 可能不是人类会设计的，但可证明是正确的。

* **反规范化以异常免疫换取读速度或历史准确性。** 快照列（`item_price_snapshot`）、计数器（`like_count`）或物化闭包都是故意重复数据。在更新不传播或由机械机制维护时可接受；作为随意的“省一次连接”优化则危险。

* **函数依赖推理以手工检查换取算法化的闭包计算。** 计算 X^+ 和检查最小覆盖是机械工作；凭目测判断 Schema 是否满足 BCNF 则不是。一旦 FD 正确，下游一切——键发现、规范化、分解——都是确定性计算。

* **把规范化作为默认，以短期性能直觉换取长期正确性。** 从 3NF/BCNF 开始，只在实测工作负载需要时才反规范化，几乎总是优于从反规范化开始——你避免的异常永远不会变成事故，而现代引擎连接规范化表的速度通常比人们预期快。
