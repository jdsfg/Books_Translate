### 7.5 集合 vs Bag 问题

纯关系代数处理_集合_。SQL 处理_bag_——允许重复行。这在哪里重要？

考虑 \pi_{\text{credits}}(\text{Courses})：严格关系代数中，如果三门课都是 4 学分，结果返回 `\{4\}`（一行）；而 SQL 的 `SELECT credits FROM Courses` 返回 `[4, 4, 4]`（三行）。

真实优化器有两种做法：

  1. **按集合语义工作，要求显式 DISTINCT 才去重。** 哲学上纯粹但令人沮丧——大多数 SQL 查询默默依赖重复计数（例如对 `SUM`、`AVG` 这类聚合，重复就是信息）。

  2. **按 bag 语义（多重集）工作，把代数做少量扩展。** 真实优化器就是这样做的。算子规则大多可以推广：\sigma 与 \times 在 bag 上行为相同；\pi 在 bag 上*不*消除重复；并/交/差有两个变体（`UNION ALL` / `UNION` 等）。

本书其余部分把关系代数当作集合语义处理，以便推理清晰，但会在 SQL bag 语义偏离时做标注。最常偏离的地方：

* 投影（\pi 去重，`SELECT` 默认不去）。
* 并（\cup 去重；`UNION ALL` 不去；`UNION` 去）。
* 聚合（聚合天然在 bag 上操作）。


#### 常见误解

有些工程师认为“SQL 就是加糖的关系代数”。它几乎如此，但 bag 语义和三值逻辑（NULL）让 SQL 与纯关系代数有一步距离。优化器仍然按代数思考——但它思考的是一种稍经扩展的“多重集关系代数”，而大多数教科书会把它简化为纯代数。真实查询优化的学术论文会仔细区分；本书为清晰起见大多用纯代数，并在 bag 语义注意点重要的地方特别指出。
