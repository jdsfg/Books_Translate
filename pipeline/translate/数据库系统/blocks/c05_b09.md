### 权衡总结

* **DDL 的刚性以模式灵活性换取机器检查的结构。** 声明一列为 `INTEGER NOT NULL` 意味着未来程序不能插入 `"n/a"`；也意味着新增必需属性是迁移，而不是字典更新。严格的类型正是行在多年后仍保持正常的原因。
* **声明式 SQL 以细粒度控制权换取优化器自由。** 你描述*什么*，而不是*如何*；引擎选择扫描顺序、连接算法、索引使用。你失去手动微调每个计划的能力，换来计划随统计信息和硬件变化而改进、无需改代码。
* **每个索引以写吞吐量换取读速度。** 每个 `INSERT`、`UPDATE`、`DELETE` 都必须维护表上的每个索引。外键上的精明索引在读上值得付出；一个很少被查询列上的臆测索引会默默拖累每次写入。
* **事务范围（BEGIN/COMMIT 边界）以并发换取原子性。** 短事务持有锁更少，但可能把逻辑操作拆成多次提交；长事务保证全有或全无，但会饿死其他写入者。原子单元必须尽可能小，但不能小于正确性要求。
* **`DISTINCT` 和 `GROUP BY` 以 CPU 工作（通常是排序或哈希）换取无重复输出。** 当重复是真实信号时（用于 `AVG`、`COUNT`），保留它们；当重复来自连接的意外产物时，`DISTINCT` 是正确的修复——但要意识到你刚刚为排序买了单。
* **外连接以计划简单性换取保留 NULL 的输出。** `LEFT JOIN ... WHERE x IS NULL` 是表达“没有匹配的行”的方式，但也意味着后续对右侧列的每个谓词都必须注意 NULL。许多微妙 bug 就藏在这个转换里。
