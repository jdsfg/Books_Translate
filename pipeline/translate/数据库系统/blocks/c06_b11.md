### 5.8 叙事 A，再回顾

我们以“正向工程叙事 A”的承诺开启本章。我们做了：

  1. 用英文读注册员描述。
  2. 识别实体：Student、Instructor、Course。判定 Enrollment 是带属性的关系（或等价地，Student 和 Course 两者的弱实体）。
  3. 识别关系：Teaches（1:N）、Enrolls（M:N）。
  4. 应用五条映射规则。
  5. 在步骤 5 只做机械工作，就得到了第 3 章的 Schema。

这个练习的重点不是“即使简单 Schema 你也应该永远 ER 建模”（对这种规模，大多数工程师可以跳过正式步骤）。重点是**当 Schema 变难时，这就是流程。** 一个医院电子病历系统的 30 个实体 Schema，不会凭空从白板会议里冒出来；必须有人系统地走完实体、关系、基数、映射规则。当两个团队必须共享 Schema 时，ER 图就是契约——一种对形状的共同理解，比任何具体 DDL 都长寿。


### 权衡总结

* **ER 建模以提前投入时间换取 Schema 清晰。** 五张表的小 Schema 通常可以直接写 DDL；30 个实体的大系统，ER 图是暴露缺失关系和错误基数的唯一方式，趁它们还没被烤进表里。
* **代理键以人类可读性换取稳定性。** 数字 `id` 保护每个外键不受“自然键（email、ISBN、SSN）变化或最终不唯一”带来的波动。代价是多了一列对读数据的人来说无意义的列。
* **自然键以稳定性换取内置唯一性和自然连接。** 以 `(isbn)` 为主键的 Schema 不需要额外 `id` 列，连接读起来自然；但一旦 ISBN 格式变化——或发现两个版本共享同一 ISBN——你的键就变成迁移工程。
* **弱实体以独立身份换取所有权语义。** 把 `Enrollment` 建模为 (`Student`, `Course`) 的弱实体意味着“没有父实体，这一行就不能存在”，并让 `ON DELETE CASCADE` 自动正确。代价是你无法再谈论一个比学生更长寿的选课。
* **把带属性的关系建模为实体以图 simplicity 换取 M:N 灵活性。** 一旦 `Enrolls` 带有 `grade`，它就必须变成一张表；把它当纯连接会丢失属性。任何基数高于 1:1 且自身带数据的关系都会变成实体。
* **ER 到关系映射规则以机械刚性换取可重复性。** 遵循五条规则，每次得到相同 Schema，这正是两个人需要从同一张图产出兼容 DDL 时想要的——代价是规则看不见工作负载相关的调优。
