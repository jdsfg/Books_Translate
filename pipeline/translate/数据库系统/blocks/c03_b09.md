#### 概念检查

**Q1.** 用一句话分别定义更新异常、删除异常和插入异常。你的定义应该说明三者共同之处。

提示

找出三者背后唯一共同的结构性原因。

**答案：**

* **更新异常：** 同一事实被存储在许多行中，改变其中一些行却漏掉其他行，产生矛盾数据。
* **删除异常：** 删除一个事实（一条选课）时，因为另一个逻辑独立的事实（教师）与它共存一行，无意中擦除了后者。
* **插入异常：** 不发明 NULL 或 phantom 相关行就无法记录新事实，因为 Schema 强制无关事实住在一起。

共同原因：_由把无关事实塞进同一行的冗余 Schema 驱动的数据冗余。_ 三种异常是同一种底层疾病的症状；消除冗余一次性治愈全部。

**Q2.** 以下哪几项基于 CSV 的“数据库”自身无法提供？标记为“提供/不提供”，并给出一行理由。

(a) Schema 级类型检查（例如 “`credits` 必须是整数”）。(b) 防止主键重复。(c) 多行原子更新。(d) 人类可读性。(e) 引用完整性（外键强制）。(f) 跨平台可移植性。

**答案：** (a) **不提供。** CSV 是文本。在 `credits` 列存 “not a number” 不会报错，直到某处尝试解释它。(b) **不提供。** 没有任何东西强制 `id` 列唯一——可以有两个 `id = 1001` 的学生，文件系统也很高兴。(c) **不提供。** 没有事务概念；任何多行操作都是可被中断的独立写入序列。(d) **提供。** CSV 是纯文本，任何编辑器都能打开。(e) **不提供。** 没有外键概念；`enrollments.csv` 可以引用不存在的 `student_id` 而无人察觉。(f) **提供。** CSV 是最可移植的数据格式之一。

CSV 几乎用所有正确性保证换取了最大的简单性和可移植性。这种权衡偶尔是正确的——静态数据导出、归档、人类可编辑配置——但不适合操作型数据。

**Q3.** 注册员在 `courses.csv` 的每门课程行上保留一个 instructor-email 字段。某教师教三门课，她更改了邮箱。必须更新多少行？这是什么异常？结构上如何修复？

**答案：** 必须更新三行，每门课一行。这是**更新异常**：同一事实（教师邮箱）跨多行冗余存储。结构修复是引入第四张表 `instructors(id, name, email)`，并把 `courses.csv` 改为引用 `instructor_id` 而不是嵌入教师姓名和邮箱。现在邮箱只存在于一行，编辑它只需改一行。（第 3 章会介绍外键；第 6 章会形式化地证明为何这种安排能消除异常。）
