#### 概念检查

**Q1.** 对于属性为 `(id, name, email, birthdate)` 的 `Students` 关系，列出：(a) 两个不是候选键的超键；(b) 两个候选键；(c) 说明你会选哪个候选键作为主键，为什么。

假设每个学生的 email 唯一，且没有两个学生 id 相同。

提示

候选键是最小超键。如果一个超键有真子集也是超键，那它就不是最小的。

**答案：** (a) `{id, name}` 和 `{email, birthdate}` 都是超键但不是候选键。第一个是超键，因为 `{id}` 单独就是超键，加 `name` 保持唯一性但不最小。第二个是超键，因为 `{email}` 单独就是超键。

(b) `{id}` 和 `{email}`。两者都能唯一标识，且都不包含能唯一标识的真子集。

(c) 用 `{id}` 作为主键。`id` 是整数代理键：稳定、不会变更、索引廉价、从其他表引用也廉价（4 字节整数比 50 字节邮箱字符串便宜）。`email` 设为 `UNIQUE NOT NULL`，保留唯一性而不需要把这个重、受用户控制的值作为规范行标识符。

**Q2.** 考虑主键为 `(student_id, course_id)` 的 `Enrollments` 关系。假设一名学生两次选同一门课（例如挂科重修），当前主键支持吗？

**答案：** 不支持。复合主键 `(student_id, course_id)` 强制每个（学生，课程）对最多出现一次。学生 1001 第二次尝试课程 101 会违反主键约束。

修复：把主键扩展为包含 `semester` 或 `term_id` 属性：`PRIMARY KEY (student_id, course_id, term_id)`。这样同一学生可以在不同学期选同一门课。Schema 现在建模的是“学生 X 在学期 Z 选了课程 Y 的选课”，而不是简单的“学生 X 选过或正在选课程 Y”。这个选择反映了业务规则真正想要什么。

**Q3.** 为什么 SQL 要单独设置 `IS NULL` 结构，而不让我们写 `x = NULL`？如果 `= NULL` 在 x 为 null 时返回 `TRUE` 会怎样？

**答案：** 因为 NULL 表示“未知”，不是“值为 null”。如果 `NULL = NULL` 返回 `TRUE`，我们就会断言“两个未知肯定相等”——这与“未知”的含义相反。两个 `grade` 为 null 的行实际上可能在知道后是不同的成绩；我们只是还不知道。因此涉及 NULL 的比较必须返回“未知”（SQL 的第三个布尔值），而 `IS NULL` 专门用来显式测试“无值”状态，与真实值的相等比较分开。这就是三值逻辑的本质。

如果 `= NULL` 返回 `TRUE`，那么当 `target_grade` 碰巧为 null 时，`WHERE grade = target_grade` 会悄悄匹配 grade 未知的行——产生与实际数据无关的 phantom 匹配。
