### 6.5 范式：1NF、2NF、3NF、BCNF

范式是对 Schema 逐步收紧的条件。越高的范式越能排除更多异常类，因为它要求 Schema 避免某些结构模式。

> ### 定义：第一范式（1NF）

关系满足**1NF**当且仅当每个属性值都是原子的——没有数组、没有重复组、没有把嵌套关系作为列值。每个单元格保存一个不可分割的单一值。

通俗地说，1NF 就是“只用扁平表”。一列不能保存 `['a', 'b', 'c']` 或 `{name: 'Alice', age: 20}`。如果你需要多个值，就需要另一行或另一张表。

1NF 是每个关系型 Schema 的基线。关系模型假设它。ER 映射规则 2（多值属性变成自己的表）就是操作上的治疗。

微妙点：SQL 数据库支持 ARRAY 和 JSON 列类型，从技术上违反 1NF。这是对_不透明_数据（你把数组当 blob 存，从不在里面查询）的务实让步；但当数组内部有意义时，它会破坏关系推理。

> ### 定义：第二范式（2NF）

关系满足**2NF**当且仅当它满足 1NF，并且每个非键属性都完全函数依赖于整个主键（而不只是主键的一部分）。

通俗地说，2NF 排除**部分依赖**——非键属性只依赖于复合主键的一部分。

2NF 只在主键是复合键时才重要。如果主键是单属性，2NF 自动满足（没有“部分”可依赖）。


#### 2NF 违反示例

考虑：

    BadEnrollments(student_id, course_id, student_name, course_title, grade)
    Primary key: (student_id, course_id)

FD：

* \{student\_id\} \rightarrow \{student\_name\} —— 部分依赖（只依赖 PK 的一部分）
* \{course\_id\} \rightarrow \{course\_title\} —— 部分依赖
* \{student\_id, course\_id\} \rightarrow \{grade\} —— 完全依赖（依赖整个 PK）

`student_name` 完全由 `student_id` 决定，不需要 `course_id`。这就是部分依赖，也是冗余的根源——Alice 的名字出现在她的每一条选课记录中。

**修复（分解）：**

    Students(student_id, student_name)  -- student_name 完全依赖于 student_id
    Courses(course_id, course_title)    -- course_title 完全依赖于 course_id
    Enrollments(student_id, course_id, grade)  -- grade 完全依赖于该组合

分解后，每张表都满足 2NF：每个非键属性都完全依赖于整个主键。

> ### 定义：第三范式（3NF）

关系满足**3NF**当且仅当它满足 2NF，并且不存在非键属性对键的**传递依赖**。形式化地说：对关系中每个非平凡 FD X \rightarrow A，要么：

  1. X 是超键，或者
  2. A 属于某个候选键的一部分（即 A 是**主属性**）。

通俗地说，3NF 排除“非键属性决定另一个非键属性”的传递依赖模式。
