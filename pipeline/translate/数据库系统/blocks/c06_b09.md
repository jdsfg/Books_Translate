### 5.6 更难的例子：图书馆

为了展示 ER 建模处理更复杂场景的能力，我们快速做一个图书馆系统的前向演练。领域描述：

> “图书馆有图书。每本书有标题、作者、ISBN。图书馆拥有每本图书的多个物理副本；每个副本有唯一条码和书架位置。图书馆会员借走副本。每笔借阅有到期日；副本归还时，借阅记录归还日期。一名会员可同时有多笔借阅；一个副本一次最多借给一名会员（尽管其借阅历史有多条记录）。”

**实体：**

* Book (ISBN*, title, author) — 概念上，每种书一本。
* Copy (barcode*, location) — 物理上，每本书有多个副本。
* Member (id*, name, email)
* Loan — 有自己的属性（due_date, return_date）。实体。

**关系：**

* _Book has Copy_ — 1:N，Copy 侧全参与（每个副本都属于一本书）。
* _Member borrows Loan_ — Member 到 Loan 的 1:N（一名会员有多笔借阅；每笔借阅属于一名会员）。
* _Copy is lent via Loan_ — Copy 到 Loan 的 1:N（一个副本有很多历史借阅；每笔借阅涉及一个副本）。

**弱实体考虑：两种情况，两种答案。**

* **情况 1：条码全局唯一**（现代图书馆常见，条码来自共享池或编码 ISBN）。Copy 的身份独立——`barcode` 单独就能定位一个副本。Copy 是带 `barcode` 作为主键、`isbn` 作为外键的**强实体**。下面我们将使用这个模型。
* **情况 2：条码只在同一本书内唯一**（旧系统，每本书独立条码，例如“书 47 副本 3”）。Copy 是 Book 的**弱实体**。其主键是 `(isbn, barcode)`，删除 Book 会级联删除其 Copies。

这个区分不是风格问题——它决定查询 `SELECT * FROM Copies WHERE barcode = '100000017'` 是返回一行（情况 1）还是需要用 ISBN 限定（情况 2）。选择与你条码系统物理现实相符的模型。

**推导 Schema（规则 1–5）：**

    Books   (isbn VARCHAR PRIMARY KEY, title VARCHAR, author VARCHAR)
    Copies  (barcode VARCHAR PRIMARY KEY, isbn REFERENCES Books(isbn), location VARCHAR)
    Members (id INTEGER PRIMARY KEY, name VARCHAR, email VARCHAR UNIQUE)
    Loans   (
      id         INTEGER PRIMARY KEY,
      member_id  REFERENCES Members(id),
      barcode    REFERENCES Copies(barcode),
      due_date   DATE,
      return_date DATE,  -- 归还前为 NULL
      INDEX (member_id),
      INDEX (barcode, return_date)  -- 查找某副本当前借阅
    )

设计说明：

* 我们在 `Members` 和 `Loans` 上使用整数代理主键，`Books` 用 ISBN（ISBN 已经是稳定的全局唯一自然键），`Copies` 用条码（也是稳定的自然键）。
* “一个副本同一时刻最多有一笔活跃借阅”约束更难表达——它是对数据在时间上的条件。我们无法简单地用唯一性约束表达（因为同一副本的历史重复借阅是正常的）。现代 PostgreSQL 支持部分唯一索引来处理这种情况：

        CREATE UNIQUE INDEX ON Loans(barcode) WHERE return_date IS NULL;
