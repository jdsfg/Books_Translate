#### 深入思考

**Q1.** 为什么 SQL 的 `ORDER BY` 子句在 `SELECT` 之后求值，而 `GROUP BY` 在之前？如果顺序互换，会出什么错？

**讨论：** `GROUP BY` 必须对源数据操作——它在汇总之前把行分区。如果 `GROUP BY` 在 `SELECT` 之后运行，`SELECT` 已经用聚合把行折叠或重塑成不再保留分组键的形式，你无法按一个已经不存在的聚合键分组。

`ORDER BY` 则相反，它关乎展示——对*输出*排序。说“先计算输出行，再按计算值排序”完全合理。这就是为什么 `ORDER BY` 可以使用 `SELECT` 列表别名（`ORDER BY avg_gpa DESC`），而 `WHERE` 和 `GROUP BY` 不能——它们运行在别名产生之前。

如果顺序互换，会得到荒唐的失败。`ORDER BY avg_gpa DESC` 在 `SELECT AVG(grade) AS avg_gpa` 之前运行，会因为 `avg_gpa` 尚未计算而失败。SQL 的逻辑求值顺序是一个精心设计的数据流水线，每个阶段只能引用它之前的阶段。

这也是为什么 `WHERE` 不能引用聚合而 `HAVING` 可以：`WHERE` 在聚合前运行，所以聚合还不存在；`HAVING` 在聚合后运行，所以它们存在。这个限制不是任意的——它是流水线形状的直接结果。

**Q2.** 考虑“找出没有选课的学生”。SQL 至少有三种写法。列出它们，并讨论哪个可能性能最好，为什么。

**讨论：** 三种常见形式：

  1. **LEFT JOIN 并检查 NULL：**

         SELECT s.id, s.name FROM Students s
         LEFT JOIN Enrollments e ON s.id = e.student_id
         WHERE e.student_id IS NULL;

  2. **NOT IN：**

         SELECT id, name FROM Students
         WHERE id NOT IN (SELECT student_id FROM Enrollments);

  3. **NOT EXISTS：**

         SELECT id, name FROM Students s
         WHERE NOT EXISTS (
           SELECT 1 FROM Enrollments e WHERE e.student_id = s.id
         );

三者结果相同（原则上；见下面注意）。哪个最快取决于优化器，但典型行为：

* **LEFT JOIN 反连接（anti-join）** 和 **NOT EXISTS** 通常都会被优化成_反连接_——一种专门返回左侧没有匹配行的连接算法。两者通常并列最佳。
* **NOT IN** 最危险。如果 `Enrollments.student_id` 可能为 NULL，`NOT IN` 会悄悄返回_零行_（因为 `x NOT IN (NULL)` 求值为 `UNKNOWN` 并被过滤）。这是一个微妙的正确性 bug。性能上，`NOT IN` 强制优化器物化内层集合，有时无法使用反连接策略。

推荐默认写法：`NOT EXISTS`。它在 null 下永远正确，通常优化良好，读起来自然（“只有当不存在匹配的 e 时才保留 s”）。
