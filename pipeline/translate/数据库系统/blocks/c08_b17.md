#### 深入思考

**Q1.** 为什么关系代数没有“排序”算子？你能从基本算子中派生出一个吗？代价是什么？

**讨论：** 代数处理的是_集合_（或 bag）元组，集合没有固有顺序。排序操作施加顺序，超出集合论模型——它是关系的*渲染*，而非新关系。因此 SQL 中的 `ORDER BY` 不在纯关系代数之内；它是最后施加的表示层操作。

能用基本算子模拟排序吗？只能通过引入一个序数属性来使用它（例如添加 `rank` 列并通过算术实现）。这不自然，也违背关系模型的目的。

真实查询引擎把排序作为物理算子——实现 SQL `ORDER BY` 的方式之一，或生成排序合并连接输入（第 11 章）。它不是逻辑算子，因为它不改变关系内容，只改变呈现顺序。

深层观点：代数 capture *计算了什么*，不 capture *如何呈现*。排序关乎呈现。这种分离是查询处理反复出现的主题（第 11 章）。

**Q2.** 代数等价规则让优化器能自由重写查询。但某些对集合成立的等价规则对 bag（多重集）失效。至少举一例，并解释为什么优化器必须小心 bag 语义。

**讨论：** 最干净的例子：\pi_L(\pi_M(R)) = \pi_L(R)，当 L \subseteq M。在集合代数中，两边返回相同的元组集合（无重复）。在 bag 代数中，它们仍然可以相同：bag 的 \pi 不去重，所以 \pi_L(R) 保留在 L 上一致的重复；\pi_L(\pi_M(R)) 也保留这些重复。因此这个等价规则在 bag 下其实也成立。

更难的例子：R \cup S（严格） 与 SQL 的 `UNION`。集合代数中，并是幂等的：R \cup R = R。bag 代数中（具体是 SQL 的 `UNION ALL`），R \text{ UNION ALL } R 的元组数是 R 的*两倍*。SQL 默认的 `UNION`（非 `UNION ALL`）会去掉重复，恢复集合语义，但那是另一个算子。

对优化器的启示：重写 `UNION ALL` 时不能随意假设幂等。重写 `UNION` 时可以（因为反正会去掉重复）。另一个例子：\pi_L(R - S) 与 (\pi_L(R)) - (\pi_L(S)) 即使对集合也不等价，因为投影会丢失信息：某个在 R 中的元组，可能在 S 中只在 L 外属性上不同，导致是否被减去变得不确定。优化器在这里必须保留精确信息。

教训：bag 语义与尊重多重集的代数比集合代数更复杂。真实优化器每天都在这种复杂性中工作。

**Q3.** 关系代数可追溯到 1970 年代。为什么没有一种显著更强大的“查询代数”取代它成为主流数据库的内部表示？

**讨论：** 几个原因：

  1. **它的抽象层次恰到好处。** 关系代数足以表达主流应用实际写的查询（过滤、连接、聚合、并）。更具表达力的代数（例如带递归的 Datalog、图遍历代数）要么被 SQL 扩展所涵盖，要么只服务小众领域。
