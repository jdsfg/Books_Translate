#### 朴素执行代价

执行相关子查询的明显方式是每个外部行运行一次。一万名学生就意味着内部查询运行一万次。每次运行都会扫描或索引进 `Students`。这潜在是 O(n^2) —— 在规模上灾难性。

现代优化器常把相关子查询重写为与预聚合子查询的连接：

    SELECT s.id, s.name
    FROM Students s
    JOIN (
      SELECT dept_id, AVG(gpa) AS dept_avg FROM Students GROUP BY dept_id
    ) d ON s.dept_id = d.dept_id
    WHERE s.gpa > d.dept_avg;

这运行在 O(n)：一次计算平均值，一次过滤。PostgreSQL 和 SQL Server 称这种变换为**去相关（decorrelation）**。MySQL 8 加入了它；MySQL 5.7 没有，这就是为什么老论坛帖子说“相关子查询总是慢”。并非如此——除非优化器无法重写它们。


#### 常见误解

“相关子查询总是慢，所以用 JOIN。” 真相更窄：**未被重写**的相关子查询慢。规划器一旦重写，性能与 JOIN 相同。解决之道是读计划，而不是回避语法。


#### 去相关何时失败

优化器无法在几种情况下把相关子查询展平为连接：

**1. 子查询使用 LIMIT 或 OFFSET。**

    SELECT s.id FROM Students s
    WHERE s.id = (
      SELECT e.student_id FROM Enrollments e
      ORDER BY e.enrolled_at DESC
      LIMIT 1
    );

`LIMIT 1` 意味着内部查询依赖返回哪些行，这会随外部行上下文变化。去相关需要预先计算“每个外部行最后注册的学生”，这不是简单 group-by——而是每个分组取 top-N。一些优化器（PostgreSQL 14+）可用 lateral join 处理；旧的不行。

**2. 相关子查询内部有非确定性函数。**

    -- 每个外部行必须得到不同随机阈值；无法一次性预先计算。
    SELECT s.name FROM Students s
    WHERE s.gpa > (
      SELECT AVG(g.score) * (1 + random() * 0.1)   -- ← 子查询里的 random()
      FROM Grades g
      WHERE g.student_id = s.id
    );

子查询里的 `random()` 意味着每次内部运行结果必须不同。规划器若把它去相关成预聚合连接，就会把 `random()` 计算一次（粒度错误），改变每行语义。注意：在*外层* WHERE 子句里使用 `random()`（而非子查询内部）不会阻止去相关——优化器只关心相关子查询内部有什么。

**3. SELECT 中的标量子查询在无匹配时返回 NULL。**

    SELECT s.name, (SELECT MAX(g.score) FROM Grades g WHERE g.student_id = s.id) AS best
    FROM Students s;

现代规划器几乎总能把它去相关为 LEFT JOIN 加聚合。但如果内部查询有多个相关谓词，导致无法形成干净连接条件，一些规划器会退回到逐行求值。始终检查计划。

**诊断规则：** 如果 `EXPLAIN ANALYZE` 显示 `(cost=…) (actual rows=N, loops=M)`，其中 M 等于外部行数，且内部算子是全表扫描，说明去相关没有发生——每个外部行都在完整跑内部查询。手工重写为预聚合连接，然后对比。
