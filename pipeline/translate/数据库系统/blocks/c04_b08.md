### 3.6 NULL 与三值逻辑

关系模型中的 NULL 表示“没有值”——未知、不适用或尚不知道。它不是零，不是空字符串，也不是 false。它是它自己的东西，除非理解规则，否则与它交互会产生意外。

> ### 定义：三值逻辑

SQL 的布尔逻辑有三个值：`TRUE`、`FALSE` 和 `UNKNOWN`。任何涉及 `NULL` 的表达式求值为 `UNKNOWN`。`UNKNOWN` 在布尔运算中按严格规则传播，并在 `WHERE` 子句中被视为“非真”（条件为 `UNKNOWN` 的行被过滤掉）。

真值表：

| P | Q | P AND Q | P OR Q |
|---|---|---|---|
| T | T | T | T |
| T | F | F | T |
| T | U | U | T |
| F | F | F | F |
| F | U | F | U |
| U | U | U | U |

关键后果：

  1. `NULL = NULL` 求值为 `UNKNOWN`，不是 `TRUE`。要判断 null，请用 `IS NULL`，绝不用 `= NULL`。
  2. `grade = 'A'` 当 `grade IS NULL` 时求值为 `UNKNOWN`。查询 `WHERE grade = 'A'` 会排除所有 `NULL` 成绩，这通常是你想要的——但 `WHERE grade != 'A'` *也*会排除所有 `NULL` 成绩，这往往令人意外。
  3. 聚合函数跳过 null。`AVG(grade_points)` 只对非 null 成绩点求平均。`COUNT(*)` 统计包括含 null 列的行；`COUNT(grade)` 统计 grade 非 null 的行。

NULL 是一个务实让步——真实数据不完整，关系模型必须以某种方式处理“我们还不知道 Alice 的成绩”。但你 Schema 中的每个 NULL 都是潜在微妙查询 bug 的来源。能少则少。积极使用 `NOT NULL`。当“尚未知道”的语义可以用哨兵值捕获时，使用 `DEFAULT`（如 `DEFAULT 'pending'`）。


### 3.7 叙事 A：异常烟消云散

让我们把叙事 A——大学选课系统——重新走过第 2 章的三种异常，验证每一种现在在结构上都不可能发生。


#### 更新异常（Park 博士改名）

第 2 章：Park 博士的名字出现 301 次（`courses.csv` 一次，反规范化 `enrollments.csv` 中 300 次）。更新需要改 301 处。

关系型 Schema：Park 博士的名字只存在于 `Instructors` 的一行。

    UPDATE Instructors SET name = 'Dr. Soo-min Park' WHERE id = 42;

只改一行。所有 join 到 `Instructors` 的查询都看到新名字。异常在结构上被消除。


#### 删除异常（Navarro 博士消失）

第 2 章：Bob Khan 在课程 103 的唯一选课行是唯一包含 Navarro 博士信息的行。删除选课记录也悄悄删除了教师。

关系型 Schema：Bob 的选课在 `Enrollments` 中；Navarro 博士在 `Instructors` 中；它们位于不同表。删除 Bob 的选课：

    DELETE FROM Enrollments WHERE student_id = 1002 AND course_id = 103;

只触及 enrollments 表。`Instructors` 不受影响。Navarro 博士仍在。


#### 插入异常（新课无学生）

第 2 章：课程 104 若不发明 NULL `student_id` / `course_id` 值就无法插入反规范化文件。

关系型 Schema：课程与选课相互独立。创建新课 trivial：

    INSERT INTO Courses (id, title, credits, instructor_id)
    VALUES (104, 'Database Internals', 4, 71);

无需选课行。异常在结构上被消除。
