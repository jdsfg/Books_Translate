#### 定义：页

**页**是磁盘存储上连续、固定大小的数据块，通常 4 KB、8 KB 或 16 KB，DBMS 把它视为 I/O 的不可分单位。所有读写都以页粒度进行。

真实系统的页大小：

* PostgreSQL：8 KB（编译时常量，很少改）
* MySQL InnoDB：16 KB（可在 4/8/16/32/64 KB 中调节）
* SQLite：默认 4 KB，最高可配 64 KB
* SQL Server：8 KB（固定）
* Oracle：默认 8 KB，可按表空间调节

为什么不设 1 字节或 1 MB？页越小，每单位数据的元数据和每次页操作越多；页越大，查询只想要一行时却加载太多无关数据。OS 页大小（Linux 上 4 KB）和设备块大小（多数 SSD 上 4 KB）设定了自然下限。经验上，事务型工作负载 8–16 KB 最平衡；分析型仓库常用 64 KB+，因为它们本来就要扫描大片数据。


#### 权衡：页大小

* **小页（4 KB）**：读一行时浪费内存少、热页并发争用小、校验便宜。但每表页数更多意味着更大的索引（B 树内部节点更多）和更多每页开销。
* **大页（32 KB+）**：扫描大表所需页读次数少、索引更紧凑、顺序扫描吞吐更好。但只想要一小行时浪费 I/O，且多个事务命中同一页时争用更大。

OLTP 系统选中小页；OLAP 系统选大页。


#### 页布局 —— 槽页（slotted page）

页不只是原始行数组。行有变长（VARCHAR 列、可空字段），所以 DBMS 使用**槽页（slotted page）**布局。

    ┌─────────────────────────────────────────┐
    │ Page Header: LSN, checksum, free space  │
    │ Slot directory: [s1, s2, s3, ...]       │
    │ ...                                     │
    │ free space (grows downward)             │
    │ ...                                     │
    │ Record N                                │
    │ ...                                     │
    │ Record 2                                │
    │ Record 1 (grows upward from the bottom) │
    └─────────────────────────────────────────┘

**槽目录（slot directory）**在顶部向下增长；记录在底部向上增长。每个槽项保存一个偏移（和长度）指向某条记录。一条行通过 `(page_id, slot_id)` 寻址——这就是**记录标识符（record identifier, RID）**。

槽页布局带来三个特性：

  1. **变长行**无需碎片即可放下——新行填入空闲空间。
  2. **稳定地址**：更新行内容不移动 RID，因为槽间接指向它。
  3. **易于删除**：把槽标记为已删除；稍后由 vacuum 或页重组压缩。

当你看到像 PostgreSQL 的 `ctid = (42, 7)` 这样的标识符，意思就是“第 42 页的第 7 槽”。


#### 常见误解

“更新一列会原地重写该行。” 通常如此——当新值放得下时。当更新后的行不再适合该页的空闲空间，DBMS 可能把它移到另一页，并留下一个**转发指针**（Oracle 的 migrated rows、MySQL 的溢出页、PostgreSQL 的新行版本）。连串转发会让扫描一行的 I/O 成本翻倍。定期表重组或 `VACUUM FULL` 可修复。
