#### `ALTER TABLE` — 演进 Schema

Schema 会随时间变化。注册员决定跟踪选课日期：

    ALTER TABLE Enrollments
      ADD COLUMN enrolled_on DATE;

已有行的 `enrolled_on` 为 `NULL`。要让它以后必填，先回填，再收紧：

    UPDATE Enrollments SET enrolled_on = '2026-01-01'
    WHERE enrolled_on IS NULL;

    ALTER TABLE Enrollments
      ALTER COLUMN enrolled_on SET NOT NULL;

大多数生产 Schema 迁移都是这样的几步精心排序，目的是在不破坏运行应用的情况下演进 Schema。


#### `DROP TABLE` — 最危险的 SQL

    DROP TABLE Enrollments;

立即且不可逆地删除表及其所有数据，无需确认。生产数据库应通过迁移框架、权限或审批流程来保护 `DROP TABLE`——没有备份就无法撤销，而粗心的 `DROP TABLE` 已经断送过许多人的职业生涯。


### 4.2 `INSERT`、`UPDATE`、`DELETE`：写入数据


#### `INSERT`

单行、多行和 `INSERT ... SELECT`：

    INSERT INTO Students (id, name, email)
    VALUES (1001, 'Alice Wong', 'alice.wong@uni.edu');



    INSERT INTO Enrollments (student_id, course_id, grade) VALUES
      (1001, 101, 'A'),
      (1001, 102, 'B+'),
      (1002, 101, 'A-'),
      (1002, 103, 'B'),
      (1003, 102, 'A');



    INSERT INTO ArchivedEnrollments (student_id, course_id, grade)
    SELECT student_id, course_id, grade
    FROM Enrollments
    WHERE course_id IN (
      SELECT id FROM Courses WHERE credits = 0 -- 已取消课程
    );

`INSERT ... SELECT` 是批量数据在表之间移动的典型方式——一条服务端语句，比通过客户端往返传输行更快、更安全。


#### `UPDATE`

    UPDATE Instructors
    SET name = 'Dr. Soo-min Park'
    WHERE id = 42;

任何理智的生产环境中，`WHERE` 子句都是必须的。`UPDATE Enrollments SET grade = 'A';` 会让所有人都得 A——这正是 SQL 被告诉做的事。PostgreSQL 的 `safe-updates` 模式会在客户端层面拒绝无过滤的 `UPDATE`/`DELETE`；请使用它。


#### `DELETE`

    DELETE FROM Enrollments
    WHERE student_id = 1001 AND course_id = 102;

同样注意：没有 `WHERE` 的 `DELETE` 会删除表中每一行。


#### 缺少 `WHERE` 的后果

一个真实的事故模式：工程师想跑 `DELETE FROM Customers WHERE id = 47;`，语句写到一半被分心，在第一个 `;` 处按了回车——整张表被清空。如果会话处于自动提交（默认），没有撤销，只有备份恢复。


#### 常见误解

“`ROLLBACK` 会救我”——只有当你处于显式事务中时才会。大多数 SQL 客户端默认处于自动提交模式，意味着每条语句都是自己的事务，立即提交。要拥有 `ROLLBACK`，必须显式启动事务：`BEGIN;` 在你的危险语句之前。（我们将在第 13 章更深入地讨论事务；现在，实用建议是：总是把危险语句包在 `BEGIN ... COMMIT` 块里。）
