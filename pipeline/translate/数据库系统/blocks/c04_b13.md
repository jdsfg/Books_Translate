#### 应用问题

**Q1.** 重读第 2 章习题 2.10 Q2 的订单例子：

    order_id, customer_name, customer_email, item_id, item_name, item_price, quantity, ship_to_address, order_date

为这些数据设计一个规范化的关系 Schema。包括主键、外键、适当的 `NOT NULL` 以及每个外键合理的引用动作。简要评论设计决策（尤其 `item_price` 和 `ship_to_address`）。

提示

领域中有四种自然实体类型（customers、items、orders、order items）。每种放进自己的关系。

**答案：**

    Customers(
      id       INTEGER PRIMARY KEY,
      name     VARCHAR(100) NOT NULL,
      email    VARCHAR(100) UNIQUE NOT NULL
    )

    Items(
      id       INTEGER PRIMARY KEY,
      name     VARCHAR(200) NOT NULL,
      current_price NUMERIC(10,2) NOT NULL CHECK (current_price >= 0)
    )

    Orders(
      id          INTEGER PRIMARY KEY,
      customer_id INTEGER NOT NULL REFERENCES Customers(id) ON DELETE RESTRICT,
      order_date  DATE    NOT NULL,
      ship_to_address_snapshot VARCHAR(500) NOT NULL  -- 订单时地址快照
    )

    OrderItems(
      order_id      INTEGER NOT NULL REFERENCES Orders(id) ON DELETE CASCADE,
      item_id       INTEGER NOT NULL REFERENCES Items(id)  ON DELETE RESTRICT,
      quantity      INTEGER NOT NULL CHECK (quantity > 0),
      price_snapshot NUMERIC(10,2) NOT NULL,  -- 订单时价格快照
      PRIMARY KEY (order_id, item_id)
    )

**设计说明：**

* **`price_snapshot`** 在 `OrderItems` 中复制了订单时商品的价格。这*看起来*像反规范化，但它是故意的：历史价格是与商品当前价格不同的事实。如果下个月商品价格变了，我们不该修改历史订单总额。这是受控冗余，不是异常来源。
* **`ship_to_address_snapshot`** 在 `Orders` 中同样快照了订单时的发货地址。（也可以把地址建模为带版本的单独表；对大多数工作负载，快照字符串更简单且足够。）
* **`OrderItems.order_id` 上的 ON DELETE CASCADE**：删除订单时删除其明细行是合理的——明细行离开订单没有意义。
* **`OrderItems.item_id` 和 `Orders.customer_id` 上的 ON DELETE RESTRICT**：我们不希望删除商品或客户时悄悄丢失订单历史。如果确实因隐私/合规要删除客户，应用必须显式处理级联，而不能让数据库静默 orphan 一切。

**跨章联系：** 这道习题预习了第 6 章（我们会形式化证明这个 Schema 满足 BCNF）和第 8 章（历史快照是高级 SQL 中时态表和版本模式的一种动机）。
