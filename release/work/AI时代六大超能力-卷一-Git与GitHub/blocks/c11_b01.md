Núria 的消息正放在工作坊里，位置和第 9 章结束时完全一样：一个议题，标题写得很直白，说指南里推荐的那家 Alfama 小咖啡馆，本来适合雨天下午去坐坐，现在已经永久关门了。Maya 读到了，谢过她，然后想：**总得有人来修正这个。** 接着，Núria，这位第 9 章里从来没有碰过一行代码的朋友，做了一件十年前几乎不可想象的事。她自己修好了它，并请求 Maya 允许她把这个修正交过来。

她没有给 Maya 发一段改好的文字。她没有说“把 Alfama 下面第三个项目改成这个”。她向指南提出了一个具体、可审阅的更改，附上精确的编辑，并围绕它开启了一场对话，全都在同一个地方。然后她等待。她等待的时候，真实的指南没有发生任何变化。这个等待正是全部重点，而本章讲的就是让这种等待成为可能的对象。

这个对象叫作 **拉取请求**，我认为它是这个共同创造时代最伟大的社会发明。比任何命令都重要，也比工具本身更重要。让我来配得上这个说法。


### 10.1 拉取请求解决的问题

想象一下，在这个东西出现之前，陌生人过去有两种方式可以改善彼此的工作。

第一种方式是把钥匙交给陌生人。你足够信任某个人，于是让她进入项目；现在她可以在任何时候更改任何东西，而你事后才会知道，如果你真的知道的话。这很快，也很吓人。你只会对已经完全信任的人这么做，这意味着能帮助你的人圈子会一直很小。

第二种方式是把钥匙留在自己手里，把建议从墙那边递过来。朋友给你发邮件：“Alfama 那家咖啡馆关门了。” 现在工作全都落到你身上。你必须在指南里找到那家咖啡馆，弄清她的意思，写出替换内容，并希望自己理解对了她。建议和更改存在于两个不同的地方。她的话在你的收件箱里，实际编辑在你的手里，两者始终没有真正相遇。大多数人的大多数建议都会死在这道缝隙里。对一个小修正来说，摩擦太大，所以修正永远不会发生。

这两种方式都迫使人做出痛苦的选择：要么完全信任，要么完全摩擦。你要么允许陌生人覆盖你的工作，要么自己完成他们建议中的所有劳动。在人们共同创造的绝大部分历史里，这就是仅有的两个选项，也正因为如此，“真该有人修一下那个”才很少变成“有人修好了那个”。

拉取请求化解了这个选择。它允许一个完全陌生的人完成一次修正的**全部**工作：找到位置、写出精确的更改、解释理由，然后把它作为已完成的东西交给你，**而不需要**拿到钥匙。你保留对实际进入项目内容的全部控制。她完成改进所需的所有劳动。没有人必须在信任和摩擦之间选择，因为拉取请求把两个过去总是绑在一起的东西分开了：**完成工作**和**决定接受它**。
