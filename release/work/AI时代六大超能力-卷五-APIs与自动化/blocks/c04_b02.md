### 3.2 找到你在乎的那一个盒子

多数时候，柜台窗口递回来的远比你问的多，技能不在于通读一切。技能在于找到你来要的那一个盒子。

假设 Mara 问助手：「订单 CB-4471 要寄到哪里？」答案就坐在上面那份响应里，但是嵌套的。它不在顶层挨着 `order_id`。它在 `shipping` 盒子里。所以老实路径是：打开订单盒，找到 `shipping` 标签，打开*那个*盒子，读 `city`。Porto。

这正是你会用来核对助手的那种事。它会说「那笔订单以标准方式寄往葡萄牙波尔图」，而你能扫一眼贴签的盒子，确认它没有比如说把买家名字误读成城市。你什么都没写。你在审计一张标签——而你已经会做这件事。

列表也以同样友善的方式工作。当 Mara 要*所有*周末订单时，柜台窗口不会只送一个盒子；它送一列盒子，像一托盘包裹：
    
    
    {
      "orders": [
        { "order_id": "CB-4471", "buyer_name": "Tomas Weerasinghe", "paid": true },
        { "order_id": "CB-4472", "buyer_name": "Aditi Rao", "paid": true },
        { "order_id": "CB-4473", "buyer_name": "Lena Fischer", "paid": false }
      ]
    }
    

标签 `orders` 装着一个列表，列表里每一项都是自己的小盒子。读到这里，Mara 一眼就能看出进了三笔订单，其中 Lena Fischer 的那笔 `paid` 设为 `false`。这一条贴签事实可能是整托盘上最重要的——因为它告诉 Mara 先别发那件货。她是靠读标签找到的，不是靠懂任何技术。


#### 常见误解

*「要用 API，我得学会正确写出 JSON，逗号和括号都放对位置。」*

你不必，而以为自己必须，正是把人留在前门的原因。逗号和括号是真的，也很严格，放错一个确实会坏。但把它们*放对*是助手的活——就像印刷机而不是你把墨弄到正确位置。属于你的是阅读结果，并核对它说的是否该说的。若你把精力花在背每个括号该在哪儿，你就接过了机器的活，却留下自己的活——判断——没做。读盒子。让助手去管逗号。
