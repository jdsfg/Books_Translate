#### 概念检查

**Q1.** 列出五类变化，并分别给出一个例子。

**答案：** (1) **代码变化**——开发者修改了认证处理器以添加限流。(2) **配置变化**——管理员把一个功能开关从 `enabled` 切换到 `disabled`。(3) **数据变化**——一个新用户注册时用户名里带了 emoji，而系统无法处理。(4) **依赖变化**——CI 流水线拉取了某个库的新版本，而这个版本废弃了代码正在使用的方法。(5) **环境变化**——服务器的 SSL 证书过期，导致 HTTPS 连接失败。

**Q2.** 为什么"我们什么都没改"几乎总是错的？不可见变化为什么特别危险？

**答案：** "我们什么都没改"几乎总是错的，因为许多变化会自动发生，或者发生在团队直接意识之外：自动更新的依赖、会轮转的 Docker 标签、到期的证书、云提供商基础设施变化、后台 cron 任务，以及其他团队修改共享服务。这些不可见变化特别危险，因为：(1) 没人知道要调查它们——它们不在任何团队的部署日志或 git 历史里。(2) 它们更难回滚——你不能 `git revert` 一个证书过期或一个 LTS 标签变化。(3) 它们破坏心智模型——当团队真心相信什么都没变时，他们往往会在代码里找缺陷（而代码没变），而不是在环境里找（环境已经变了）。
**Q3.** 为什么 macOS 和 Linux 之间的文件系统大小写敏感性差异，是"本地能跑，服务器坏掉"缺陷的常见来源？

提示

想想当你写 `import Component from './component'`，而文件名是 `Component.js` 时会发生什么。

**答案：** macOS 的文件系统默认大小写不敏感：`./component` 和 `./Component` 指向同一个文件。所以即使文件名是 `Component.js`，`import Component from './component'` 也能工作。Linux 的文件系统大小写敏感：`./component` 和 `./Component` 是不同文件。同一个 import 在 macOS 上可用，在 Linux 上会失败，因为文件 `component.js` 不存在——只有 `Component.js` 存在。这个缺陷很常见，因为：开发者在 macOS 上工作，CI/服务器运行 Linux，而大小写不匹配在开发机器上不可见。修复方法：使用一致的大小写约定（例如，文件名始终小写），并添加能捕获大小写不匹配的 lint 规则。

**Q4.** 版本对比与二分查找调试法（第 5 章）和反向追溯（第 8 章）有什么关系？
**答案：** 版本对比是把反向追溯应用到时间维度——你从"现在坏了"出发，沿时间向后追踪，找出它什么时候坏的。二分查找（特别是 git bisect）是在时间维度上高效搜索的_技术_——你不是检查时间线上的每一个点，而是检查中点并排除一半时间线。合在一起：版本对比告诉你看发生了什么变化，反向追溯给出方向（从故障的现在回到正常的过去），二分查找给出策略（对时间线做二分）。它们是同一种根本方法的互补视角。
