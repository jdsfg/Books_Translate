#### 概念检查

**Q1.** 用你自己的话解释为什么小黄鸭调试法有效。至少引用两个认知机制。

**答案：** 小黄鸭调试法有效，是因为：(1) **语言处理使用不同于默想的认知通路**——说出来或写下来会迫使你把脑中的捷径解压成完整的、逐步的解释，从而暴露你无意识跳过的步骤。(2) **假设浮出水面**——当你向一个“什么都不知道”的人解释时，你被迫明确说出自己的假设（“我假设数据以 JSON 形式传入”），这让原本不可见的假设变得可测试、可质疑。额外机制包括受教者/解释效应（教学会加深理解）以及对连贯性的社交压力（当有人在“听”时，你会更严谨）。

**Q2.** 使用小黄鸭调试法时，你应该先解释什么：bug，还是预期行为？为什么？

**答案：** 先解释**预期行为**——代码应该做什么。这会建立基线：“这个函数应该接收订单列表并返回总收入。” 然后，当你描述实际行为（“但它对周末下的订单返回 0”）时，预期与实际之间的缺口会非常清楚。如果你从 bug 开始（“它在周末返回 0”），你没有足够上下文理解为什么这是错的，你的解释也容易聚焦于症状而不是机制。先讲预期的方法会自然引导你追踪逻辑，并找出现实偏离意图的位置。

**Q3.** 什么时候结对调试比小黄鸭调试法更合适？

提示

想想人类搭档能提供什么，而橡皮鸭不能。

**答案：** 在以下情况下，结对调试更合适：(1) **你缺少领域知识**——bug 位于你不太理解的系统部分，而熟悉该区域的同事能给你指出方向。(2) **你已经试过小黄鸭调试法**，但它没有揭示 bug——你需要的是新鲜视角，而不只是强制表达自己的视角。(3) **bug 需要广度**——它跨越多个系统或代码库，不同团队成员拥有不同部分。(4) **你需要被挑战**——人类搭档可以追问你的解释（“等等，你确定那个 middleware 会在所有路由上运行吗？”），这是橡皮鸭做不到的。

**Q4.** 调试日志如何作为一种小黄鸭调试法发挥作用？

**答案：** 写日志条目提供了和向橡皮鸭解释一样的认知收益：你必须用文字表达问题，按顺序组织思路，并明确说出假设。写下“我怀疑数据库，但实际原因是 API 响应处理器”这一动作，会迫使你承认假设与现实之间的差距。日志还增加了鸭子没有的一个维度：随时间积累。每一个单独条目都是一次小黄鸭练习，而条目集合会揭示模式——反复出现的 bug 类型、反复出现的偏差、反复出现的盲点——这些是任何一次单独解释都看不到的。
