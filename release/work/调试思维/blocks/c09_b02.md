#### 4\. 依赖变化

某个库被更新，某个系统包被打补丁，某个 Docker 基础镜像被刷新，或者你的应用依赖的某个微服务被重新部署。
    
    
    # Compare package versions
    diff package-lock.json.old package-lock.json
    
    # Check if Docker base image changed
    docker image inspect your-image:latest --format '{{.Created}}'
    
    # Check system package versions
    apt list --installed 2>/dev/null | grep relevant-package
    

依赖变化特别棘手，因为它们往往自动发生（运行 `npm update` 的 CI 流水线、拉取 `latest` 的 Docker 镜像、OS 自动更新），而且没人想到要提起它们，因为"我们什么都没改。"


#### 5\. 环境变化
服务器磁盘满了。云提供商发生了局部故障。SSL 证书过期了。DNS 记录被修改了。时钟漂移了。内存或 CPU 限制被调整了。

这些是最难察觉的变化，因为它们不在任何代码 diff 或配置文件中。它们存在于基础设施里。

**需要检查什么：**

* 服务器指标（CPU、内存、磁盘、网络）
* 云提供商状态页面
* SSL 证书过期时间
* DNS 变化
* 服务之间的网络连通性


#### 常见误解

**"我们什么都没改。"** 这几乎从来不是真的。_一定有东西_变了——你只是还不知道是什么。上面的五类变化就是一份检查清单。在断定这个变化真的神秘之前，要逐项系统地检查。在 15 年的专业调试经历中，我从未遇到过"什么都没变"真的成立的情况。变化总是在那里——只是落在了没人查看的类别里。


### 9.3 时间线调查
当一个缺陷突然出现时，重建时间线通常是最快的诊断方法：

  1. **它到底是什么时候坏的？** 不是"今天某个时候"——要找到确切时间。检查监控仪表盘、错误日志、带时间戳的用户报告。

  2. **那个时间发生了什么？** 与以下内容交叉核对：部署日志、CI/CD 流水线运行、cron 任务、数据库迁移、基础设施变更、团队沟通（"我下午 2 点更新了 staging 配置"）。

  3. **谁当时在操作？** 检查 git 提交时间戳、部署审计日志和管理面板访问日志。这不是为了追责——而是为了找到相关变化。

  4. **之前刚刚变了什么？** 原因通常比症状早几分钟到几小时出现。查看第一次失败之前那个时间窗口内所有五类变化。
一个仪表化良好的系统会让这件事很容易。一个仪表化糟糕的系统会让它几乎不可能——这也说明了可观测性（第 10 章）的重要性。
