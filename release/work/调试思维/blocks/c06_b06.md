#### 概念检查

**Q1.** 定义最小可复现示例的三个属性：最小、可复现和完整。为什么每个都重要？

**答案：** (1) **最小** ——只包含 bug 所必需的元素。重要是因为额外元素会隐藏原因并浪费调查时间。(2) **可复现** ——稳定地产生 bug。重要是因为你需要测试你的改动是否修复了 bug，而间歇性复现会让测试不可靠。(3) **完整** ——包含一切必要内容，让别人也能复现。重要是因为如果你在寻求帮助（甚至只是明天丢失上下文后继续调试），缺失部分会阻止复现，并浪费时间重建设置。

**Q2.** 解释用于构建 MRE 的减法方法和加法方法之间的区别。你会在什么时候使用各自方法？

**答案：** **减法**从完整系统开始，移除组件，直到只剩下与 bug 相关的部分。当你有一个正在工作但带 bug 的系统并想把它修剪下来时使用——这是大多数实际调试场景。**加法**从零开始，添加组件，直到 bug 出现。当你怀疑某个特定组件/交互但需要确认时，或者当完整系统太复杂而无法有效减法（依赖太多、耦合太深，无法干净移除）时使用。减法通常对应用级 bug 更快；加法更适合 library/framework bug 或交互 bug。

**Q3.** 为什么构建 MRE 的过程常常会在 MRE 完成之前揭示 bug？

提示

想想在决定保留什么、移除什么时，你执行了哪些心智操作。

**答案：** 构建 MRE 要求你检查每个组件，并决定“这对 bug 必要吗？”这种检查迫使你：(1) 真正阅读并理解你可能一直在略读的代码。(2) 思考每个组件的角色和交互。(3) 持续测试假设（每次移除都是一次测试）。(4) 面对假设——“我以为这个 module 无关，但移除它修复了 bug。”这种对代码的高强度参与自然会浮现根因。它本质上是调试循环（第 2 章）的结构化版本，其中每个减法步骤都是一次假设测试。

**Q4.** 构建 MRE 与二分查找调试法（第 5 章）有什么关系？

**答案：** MRE 构建中的每个移除步骤都是一种二分查找。当你移除一个组件并检查 bug 是否仍然存在时，你是在把系统拆分成“这个组件”和“其他所有东西”，并判断 bug 住在哪一边。减法方法本质上是把二分查找应用到_组件空间_，而不是代码行或提交。主要区别是：二分查找意味着系统性的减半策略，而 MRE 构建常常会先移除最大或最可疑的一块（它不一定正好是一半）。但核心原则——每次测试排除一半可能性——是相同的。
