#### 深入思考

**Q1.** 火星气候轨道器 bug 是单位不匹配——一个系统使用英制，另一个系统使用公制。类似 bug 在日常编程中不断出现：混淆 milliseconds 和 seconds、bytes 和 kilobytes、pixels 和 points、UTC 和 local time。为什么单位不匹配 bug 明明概念上很简单，却仍然持续存在？一个彻底的解决方案会是什么样？

**讨论：** 单位不匹配之所以持续存在，是因为：

**原始类型不携带单位信息。** 在大多数语言中，timestamp 只是一个 integer 或 float。它是 milliseconds since epoch？Seconds？Microseconds？类型 `int64` 不会说明。开发者每次都必须记住（或查看文档）。

**约定各不相同。** JavaScript 的 `Date.now()` 返回 milliseconds。Unix timestamps 是 seconds。Python 的 `time.time()` 返回 float 形式的 seconds。数据库 timestamp 可能是 microseconds。每个生态系统都有自己的约定，跨生态系统工作的开发者会不断进行转换。

**隐式转换是静默的。** 如果你把 seconds 传给一个期望 milliseconds 的函数，数值会以 1000 倍的因子“出错”，但语言会愉快地接受它，因为它是正确的 _类型_（一个数字）。没有错误，没有警告。

**彻底的解决方案：** 编码单位的类型系统。像 `quantities`（Python）、`units-of-measure`（F#）或 Rust 的 newtype pattern 这样的库，会为不同单位创建不同类型。`Milliseconds(5000)` 和 `Seconds(5)` 是不同类型，不能被意外混用。编译器会捕获不匹配。这本质上就是本可以拯救火星气候轨道器的东西：如果导航软件产生 `PoundForceSeconds`，而飞行软件期望 `NewtonSeconds`，类型不匹配就会在编译时被捕获，而不是在九个月飞行之后。

**Q2.** Cloudbleed 是由外部安全研究员发现的，而不是由 Cloudflare 自己的监控发现的。这说明了内部测试和监控有哪些限制？组织应如何检测那些不产生可见症状的 bug？

**讨论：** 内部测试有固有盲点：

**你测试的是你预期的东西。** 内部测试验证系统是否做了它应该做的事。它们很少检查系统 _不应该_ 做的事（比如泄露相邻内存）。Cloudbleed 没有违反任何正向规格——它只是除了预期行为之外，又做了一件意外的事。

**监控寻找的是已知失败模式。** 错误率、崩溃次数、延迟尖峰——这些能捕获已知类别的问题。一种新颖的失败模式（响应中出现不该存在的数据）不在监控手册中，因为没人预料到它。

**内部人员已经习惯了预期。** 构建解析器的团队知道它会转换 HTML。他们可能看到稍长的响应，却没有质疑。外部人员（Google 研究员）看到不属于那里的内容，会立刻标记。
