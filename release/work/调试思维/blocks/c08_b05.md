### 8.5 解开 Ampersand Bug（与号缺陷）之谜

是时候了。让我们解决从第 1 章起一直跟着我们的登录 bug。

**我们知道：**

* 有些用户尽管密码正确也无法登录
* 错误显示 “invalid credentials”
* 数据库中的密码确实正确
* 有些密码可用，有些不可用

**反向追溯：**

**步骤 1 —— 认证比较。** 服务器把提交的密码与存储的 hash 进行比较。它返回 “invalid credentials”，是因为比较失败。所以要么存储的 hash 错了（但我们已经验证它是正确的），要么提交的密码错了。

**步骤 2 —— 服务器收到了什么密码？** 在服务器端记录传入的密码（临时这样做——绝不要在生产环境记录密码）。把它与用户输入的内容比较。

对于密码为 `myp@ss` 的用户：服务器收到 `myp@ss`。正确。认证成功。

对于密码为 `correct&safe` 的用户：服务器收到 `correct`。只有 `&` _之前_的部分。

**步骤 3 —— 为什么密码在 `&` 处被截断？**

**隔离变量：**

用不同密码测试：

* `abcdef` → 可用 ✓
* `abc&def` → 失败（服务器收到 `abc`）
* `abc&` → 失败（服务器收到 `abc`）
* `abc=def` → 可用 ✓
* `abc def` → 可用（服务器收到 `abc def`）✓
* `abc+def` → 可用 ✓

只有 `&` 会导致截断。`&` 在 Web 技术中有什么特殊之处？

**根因：** 密码被作为 URL 参数发送（可能是在 GET 请求中，也可能是在 content type 为 `application/x-www-form-urlencoded` 的 POST body 中），但_没有正确编码_。在 URL 编码中，`&` 是参数分隔符。所以密码 `correct&safe` 会变成两个参数：`password=correct` 和 `safe=`（第二个空参数）。服务器只读取 `password` 参数，也就是 `correct`——被截断后的版本。

**验证（隔离步骤）：** 把密码提交改为发送前对密码使用 `encodeURIComponent()`。密码 `correct&safe` 现在被编码为 `correct%26safe`。服务器把它解码回 `correct&safe`。认证成功。

**反向追溯走过的链条：** 认证失败 → 服务器收到被截断的密码 → 截断发生在 `&` 处 → `&` 在 URL 编码中有特殊含义 → 传输前没有对密码进行 URL 编码。

**变量隔离确认了原因：** 只有 `&` 触发这个 bug，而对密码编码可以修复它。

这个 bug——我们在第 1 章引入，并在第 4、5、6 章从不同角度反复查看的那个——现在已经完整解决。每一章都给了我们一副不同的镜片：

* 第 4 章（错误信息）： “invalid credentials” 告诉我们比较失败
* 第 5 章（二分查找）：我们本可以二分密码的旅程，找到截断发生的位置
* 第 6 章（最小可复现示例）：剥离到最小表单 + 最小服务器，本可以隔离编码问题
* 第 7 章（小黄鸭调试法）：大声解释密码流，本会暴露“它是如何传输的？”这个假设
* 第 8 章（反向追溯 + 隔离）：从症状追踪到原因，然后用受控实验确认

多种技术，一个答案。真实调试就是这样——你选择适合情境的工具，而且经常组合使用多个工具。
