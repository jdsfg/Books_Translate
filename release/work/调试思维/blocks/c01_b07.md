#### 应用题

**Q1.** 你正在开发一个功能，并注意到应用的自动化测试套件在本地通过，但在 CI 服务器上失败。列出至少三类可能解释这种差异的根因。对每一类，描述一个你可以测试的具体假设。

提示

想想你的本地机器和 CI 服务器之间有什么不同：软件版本、数据、时序、环境变量、文件系统……

**答案：**三类原因和可测试假设：

  1. **环境差异：**CI 服务器可能有不同版本的依赖（例如，本地是 Node.js 18，而 CI 上是 Node.js 20）。_假设：_“如果依赖版本是问题所在，那么在两个环境中运行 `node --version` 应该会显示不同版本。”_测试：_检查版本输出。

  2. **时序/顺序问题：**测试可能在 CI 上以不同顺序运行，或者运行得更快/更慢，从而暴露出竞态（race condition）或测试之间的相互依赖。_假设：_“如果测试顺序有影响，那么在 CI 上单独运行失败的测试应该会通过。”_测试：_在 CI 上运行单个失败测试。

  3. **数据/状态差异：**你的本地环境可能残留了上一次运行留下的测试数据，而 CI 是从干净状态开始的。_假设：_“如果陈旧数据是问题所在，那么清空我的本地数据库并运行测试，本地也应该失败。”_测试：_重置本地状态并重新运行。

  4. **文件系统差异：**大小写敏感性（macOS 默认不区分大小写，Linux 区分大小写）、行尾符或文件权限。_假设：_“如果大小写敏感性是问题所在，那么存在一个大小写不匹配的文件导入。”_测试：_搜索大小写不匹配的导入。

**Q2.** 对下面每个场景，判断提出的“修复”是解决了根因，还是只是掩盖了症状：

(a) 用户抱怨搜索功能很慢。团队添加了一个加载指示器，让用户不注意到延迟。

(b) 一个 API 在收到空输入时返回 500 错误。团队添加输入验证，用 400 错误拒绝空输入。

(c) 一份报表显示了不正确的总数。团队添加了一个手动校正因子，按观察到的误差幅度调整总数。

**答案：**

(a) **症状掩盖。**加载指示器并不会让搜索更快——它只是管理用户的感知。搜索仍然很慢。如果延迟进一步增加，连加载指示器也帮不上忙。根因（搜索慢）没有被触及。

(b) **根因修复——部分修复。**输入验证解决了眼前问题（空输入不应该导致 500），返回 400 是正确行为。然而，彻底的修复还会调查空输入_为什么_会导致 500——代码更深处可能存在空指针解引用或未处理的边界情况，也可能被其他异常输入触发。验证是正确的，但 500 可能表明还有一个值得调查的更深层问题。

(c) **症状掩盖——而且很危险。**添加校正因子，字面上就是在不了解为什么错误的情况下调整输出。如果误差幅度发生变化（由于新数据、计算变化、季节性影响），校正因子就会变错，报表又会不准确。更糟的是，报表现在_看起来_正确，所以没人会质疑它。必须找到并修复产生错误总数的根因。
