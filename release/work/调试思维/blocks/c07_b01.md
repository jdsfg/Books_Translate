你盯着一个 bug 已经一个小时了。你试过二分查找，尝试构建一个最小可复现示例，也把错误信息读了三遍。仍然毫无头绪。无奈之下，你走到同事的工位旁。

“嘿，我能跟你讲讲这个 bug 吗？”

“当然。”

“好，是这样的，有个函数接收一个 user 对象，然后返回这个用户的权限。user 对象来自数据库，里面有一个角色列表。每个角色会在一个查找表里映射到一组权限。这个函数遍历这些角色，逐个在——哦。哦。查找表。我用的是旧的查找表。就是我们重组角色结构之前的那个。没事了，我找到了。”

你的同事什么也没说。他们甚至不需要理解这个问题。_解释_这件事本身——按顺序、大声说出每一步，讲给一个什么都不知道的人听——迫使你检查了一个一直被你视为理所当然的假设。那个假设就是 bug。

这就是**小黄鸭调试法**，也是迄今发现的最稳定有效的调试技术之一。


### 7.1 技术本身

这个名字来自《_程序员修炼之道_》中的一个故事：有位程序员在桌上放了一只橡皮鸭，通过向它解释问题来调试。显然，鸭子不会给出任何反馈。这正是重点——你不需要反馈。你需要的是_解释_。


#### 定义：小黄鸭调试法

小黄鸭调试法是一种刻意的调试技术：把问题详细解释给一个人、一个物件，甚至一个空房间听。表达的动作会迫使你组织思路，检查流程中的每一步，并暴露那些你无意识跳过的隐藏假设。

用直白的话说：从最开始，把问题大声讲出来，就像听的人什么都不知道一样。解释本身会揭示 bug。

步骤如下：

  1. **找到你的“小黄鸭”。** 可以是一只橡皮鸭、一只泰迪熊、一位同意只倾听的同事，甚至一把空椅子。听众不需要理解问题——他们只需要存在（或被你假装存在），让你感受到必须连贯解释的社交压力。

  2. **从最开始讲起。** 不要跳过任何东西。“用户点击这个按钮。它触发这个函数。这个函数接收这些参数……”强迫自己把每一步说清楚。

  3. **当你遇到讲不清的地方时，停下来。** 那就是 bug。或者至少，那就是 bug 藏身的区域。如果你发现自己在说“然后它会做……嗯，我不太确定这时它具体做什么”——那就是你需要查看的地方。

  4. **当你的解释与实际行为矛盾时，停下来。** “……所以这个函数应该返回用户的权限，但它返回的是一个空数组……” “应该”和“实际”之间的缺口，就是 bug 的地址。
