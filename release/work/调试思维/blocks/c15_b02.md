#### CPU 分析

CPU 分析会显示哪些函数消耗了最多 CPU 时间。它们通常会生成这样的结果：
    
    
    Function                    Self Time    Total Time    Calls
    processOrder()              12ms         4,523ms       1
      validateItems()           2ms          3,801ms       1
        checkInventory()        3,799ms      3,799ms       1
          calculateTax()            320ms        320ms         1
      formatReceipt()           400ms        400ms         1
    

这样阅读：`processOrder` 总共需要 4,523ms，但其中只有 12ms 花在 `processOrder` 自身。大部分时间（3,799ms = 84%）花在深埋两层的 `checkInventory` 里。如果没有性能分析器，你可能会猜 `calculateTax` 或 `formatReceipt` 很慢（它们听起来计算量很大）。性能分析器证明 `checkInventory` 才是瓶颈。

这就是自动化的二分查找（第 5 章）——性能分析器同时检查每一个“中点”，并准确告诉你时间花在了哪里。


#### 如何做性能分析

每一种主流语言和平台都有性能分析工具：

* **JavaScript/Node.js：** Chrome DevTools Performance 选项卡（前端）、`node --prof` 或 `clinic.js`（后端）
* **Python：** `cProfile`、`py-spy`、`line_profiler`
* **Java：** VisualVM、YourKit、Java Flight Recorder
* **Go：** `pprof`（内置）
* **C/C++：** Valgrind（callgrind）、perf、gprof

基本工作流：

  1. 启动性能分析器
  2. 运行缓慢的操作
  3. 停止性能分析器
  4. 检查结果——按总时间排序，找到热点路径


### 15.3 常见性能反模式

一旦你通过性能分析识别出瓶颈，就需要理解它_为什么_慢。下面是最常见的罪魁祸首：


#### 隐藏的 O(n²)

最常见的性能缺陷：一个看起来无害、但具有平方时间复杂度的算法。
    
    
    # Looks innocent — just checking for duplicates
    def has_duplicates(items):
        for i in range(len(items)):
            for j in range(i + 1, len(items)):
                if items[i] == items[j]:
                    return True
        return False
    

有 100 个元素：约 5,000 次比较（很快）。有 10,000 个元素：约 50,000,000 次比较（很慢）。有 1,000,000 个元素：约 500,000,000,000 次比较（不可用）。

修复方法：使用 set，它提供 O(1) 查找：
    
    
    def has_duplicates(items):
        return len(items) != len(set(items))
    

**诊断模式**：性能会随着数据规模增大而急剧恶化。如果数据翻倍使操作慢了 4x（不是 2x），你很可能遇到了 O(n²)。如果慢了 8x，可能是 O(n³)。
