#### 应用题

**Q1.** 一个用户报告：“我下了订单，收到了确认邮件，但订单没有出现在我的订单历史中。” 系统包括：订单服务（写入订单）、通知服务（发送邮件）和历史服务（显示订单历史，从独立数据库读取）。设计一次系统性调查。你会按什么顺序检查什么？

提示

确认邮件已发送，这意味着订单已经被创建。问题是：为什么历史服务看不到它？

**答案：**

**步骤 1：确认订单存在。** 直接查询订单服务的数据库。如果订单在那里，写入成功。（确认邮件已经证明了这一点，但仍要验证。）

**步骤 2：检查历史服务的数据源。** 历史服务是从订单服务相同的数据库读取，还是从副本/独立存储读取？如果是独立的：订单是否存在于历史服务的数据存储中？

**步骤 3：如果订单在历史服务的存储中缺失：**

* **复制延迟？** 检查订单服务数据库和历史服务数据库之间的延迟。订单可能还没有复制过去（最终一致性）。
* **同步失败？** 如果数据通过事件/消息同步，检查消息队列。“order created”事件在队列里吗？它被消费了吗？消费者失败了吗？
* **过滤？** 历史服务是否按状态、日期或用户过滤订单？也许订单存在但被过滤掉了（错误状态、错误日期范围、错误用户 ID）。

**步骤 4：如果订单在历史服务的存储中存在但没有显示：**

* **分页/排序？** 订单可能在另一个页面上，或者排序后超出了可见范围。
* **缓存？** 历史服务可能缓存了结果。缓存列表不包含新订单。强制刷新缓存。
* **用户会话？** 用户是否在查看正确账号？（边缘情况：不同服务中的用户 ID 不同。）

**步骤 5：使用分布式追踪。** 如果实现了关联 ID，搜索订单的 trace ID，跨所有服务查看完整旅程。

**Q2.** 一个数据流水线处理金融交易。流水线：读取 CSV → 解析 → 验证 → 转换货币 → 按地区聚合 → 生成报表。最终报表显示“Europe”地区收入比预期少 20%。你会如何调试？

**答案：**

**沿流水线反向追溯（第 8 章）：**

  1. **报表 → 聚合：** 检查聚合。手动汇总欧洲交易。聚合计算是否匹配？如果匹配，聚合是正确的——输入数据有问题。

  2. **聚合 → 货币转换：** 检查转换后的欧洲交易。汇率正确吗？错误汇率可能系统性低估欧洲收入。用已知来源验证汇率。

  3. **货币转换 → 验证：** 是否有欧洲交易被验证阶段拒绝？统计 Europe 地区在验证前后的交易数量。如果 20% 被拒绝，说明验证规则对欧洲数据过于严格（不同格式、不同货币、不同小数分隔符）。

  4. **验证 → 解析：** 欧洲交易是否被正确解析？欧洲 CSV 文件可能使用 `;` 作为分隔符，使用 `,` 作为小数分隔符（与美国约定相反）。如果解析器期望美国格式，`1.234,56`（欧洲写法，表示 1,234.56）就会被错误解析。
