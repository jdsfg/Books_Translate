#### 定义：调试

调试是通过假设驱动的调查、系统性地找出意外行为之根因的过程。你观察一个症状，形成关于其原因的假设，基于该假设做出预测，检验预测，并用结果收窄搜索空间。

用白话说：调试就是当侦探。你有证据（症状），你提出理论（假设），你检验那些理论（实验），每一次检验要么确认要么排除一种可能。关键词是*系统性*——你不是在随机猜测，你是在收窄范围。

考虑这个场景：

> 你的 Web 应用登录页对多数用户都正常，但有些用户报告无法登录。他们发誓密码是对的。客服团队已经核实——数据库里的密码与这些用户输入的一致。然而，认证仍然失败。

停一下。什么可能导致这种情况？先别急着下结论——只注意你的大脑在做什么。它立刻想猜。「也许是缓存问题。」「也许有 Unicode 问题。」「也许数据库比较区分大小写。」

这些猜测可能对。也可能错。关键是：它们是*猜测*。调试者不猜——调试者*调查*。而调查意味着遵循一个流程：

  1. **仔细观察**：症状究竟是什么？不是「登录不行」——那太模糊。哪些用户？一直如此还是间歇出现？他们看到什么错误消息？他们用的是什么浏览器？

  2. **形成假设**：基于观察，什么能解释这个模式？如果只有*一部分*用户受影响，这些用户有什么不同？

  3. **做出预测**：如果我的假设正确，还有什么也应该为真？如果是浏览器问题，同一用户换一个浏览器应该能登录。

  4. **检验预测**：真的去查。不要只是假定——要核实。

  5. **收窄搜索**：检验要么支持要么反驳了假设。无论哪种，问题空间都变小了。形成新假设，再来一轮。

我们将在整本书中反复回到这个神秘的登录缺陷。到第8章，你将掌握彻底解决它的工具。眼下，只需留意「猜测」与「调查」的差别。


#### 常见误解

**「好程序员不需要调试，因为他们写出无 bug 的代码。」** 这完全错误，而且信了它会让你的编程水平变得更差。每一位程序员，无论经验多深，都会写出 bug。初级与高级开发者的差别，不在于高级写的 bug 更少（也许略少一点）——而在于高级*发现并修复* bug 的速度快得多，因为他们通过多年练习培养了调试技能。如果你一遇到 bug 就感到羞愧，你是把过程中自然的一部分当成了个人失败。bug 是数据。它们是信息。目标不是避开它们；而是它们不可避免地出现时，能迅速找到它们。
