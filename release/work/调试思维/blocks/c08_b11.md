#### 深入思考

**Q1.** 反向追溯假设你可以识别出从结果到原因的清晰因果链。但如果 bug 是由多个独立原因共同造成同一个症状呢？例如，一个系统很慢，是因为三个独立瓶颈各自增加了 200ms。从“请求耗时 1.2 秒”开始反向追溯——你会如何处理多个贡献因素？

**讨论：** 多原因 bug 会给反向追溯带来挑战，因为没有单一链条可循——而是一棵贡献树。可采用的方法：

**分解症状。** “总共 1.2 秒”可以拆成时间段：0-400ms 用于数据库，400-800ms 用于处理，800-1200ms 用于渲染。现在你可以分别从每个时间段开始反向追溯。

**使用 profiling。** 对性能 bug，profiling 工具会明确显示时间拆分。从 profile data 反向追溯，可以同时识别所有贡献因素，而不是沿着一条链走下去并漏掉其他因素。

**按贡献大小排序。** 如果一个原因贡献 600ms，另外两个各贡献 300ms，就先修复最大的贡献者。从“最大的单个时间块”开始反向追溯，会把精力聚焦在最重要的位置。

**留意交互。** 有时原因不是独立的——修复一个会让另一个变得更糟（例如移除缓存会让数据库成为唯一瓶颈）。修复每个贡献因素后，重新 profile，看看剩余瓶颈是否发生变化。

总原则：反向追溯在单原因 bug 中最清晰，但可以通过把症状分解为多个组成部分，并分别追踪每个组成部分，适应多原因 bug。

**Q2.** Ampersand Bug（与号缺陷）提出了一个更广泛的问题：同一代码库中还有多少类似 bug？如果 password 字段没有编码 `&`，其他表单字段呢？其他特殊字符如 `#`、`%` 或 `+` 呢？你会如何寻找并修复所有相关 bug，而不只是报告中的那一个？

**讨论：** 找到某一类 bug 的单个实例，应该触发对整个类别的搜索：

**立即行动：** 修复 password 字段的编码。这解决报告中的 bug。

**类别搜索：** 审计应用中的所有表单提交。有多少使用了 URL 编码参数却没有正确编码？是否还有其他用户可输入特殊字符的字段（包含 & 的姓名、包含 # 的地址、包含 % 的描述等）？在代码库中搜索没有使用 `encodeURIComponent` 或能处理编码的库的表单提交代码。

**系统性修复：** 与其逐个字段编码，不如使用能自动处理编码的表单提交方式：使用带有 `JSON.stringify` body 和 `Content-Type: application/json` 的 `fetch`，或使用会编码所有字段的表单库。这会防止整个编码 bug 类别，而不只是特定实例。

**测试：** 在表单验证测试套件中添加带特殊字符的测试用例。对每个面向用户的输入字段测试 `&`、`#`、`%`、`+`、`=`、空格和 Unicode 字符。

这种方法——修复实例、搜索类别、实现系统性预防——就是调试与工程的区别。调试找到并修复一个 bug。工程防止整个 bug 类别存在。
