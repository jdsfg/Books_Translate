#### 概念检查

**Q1.** 说出可观测性的三大支柱，并解释每一项告诉你系统的什么信息。

**答案：** (1) **日志**——带时间戳记录的离散事件，告诉你发生了什么以及何时发生。"在 14:30:22，订单 1234 为用户 alice 处理完成。"(2) **指标**——随时间变化的数值测量，告诉你系统表现如何。"请求延迟 p95 是 200ms。错误率是 0.5%。内存使用率是 60%。"(3) **追踪**——单个请求经过系统的路径，告诉你系统中的哪里发生了某件事。"这个请求经过 API 网关、认证服务、用户服务和数据库，并在数据库查询中花费了 150ms。"

**Q2.** 什么时候应该使用调试器而不是 print 语句，反之又是什么时候？

**答案：** 当你需要检查复杂对象状态（许多嵌套字段）、逐步走过不熟悉的代码以理解其流程、缺陷依赖于特定条件（使用条件断点），或者想通过在运行时修改值来实验时，使用**调试器**。当你只需要检查一两个特定值、大致知道缺陷在哪里、正在调试难以附加调试器的远程/生产系统，或者需要跨许多请求观察行为（而不只是一个请求）时，使用 **print 语句**。当缺陷对时序敏感时，print 语句也更好（调试器的暂停可能掩盖竞态）。
**Q3.** 解释海森堡缺陷的概念，以及为什么添加可观测性有时会让缺陷消失。

提示

想想添加日志或断点如何改变系统行为——尤其是时序。

**答案：** 海森堡缺陷是指当你尝试观察它时，行为会改变或消失的缺陷——这个名字来自量子物理中的海森堡不确定性原理。在软件中，这会发生，是因为观察改变了系统：(1) 添加日志语句会引入 I/O 操作，改变执行时序，从而可能阻止竞态显现。(2) 调试器断点会暂停线程，改变并发操作的相对时序。(3) 额外的监控函数调用可能清空 CPU 缓存，或者在不同时间触发垃圾回收。海森堡缺陷几乎总是并发问题（第 11 章）或依赖时序的缺陷——它们的存在会告诉你关于缺陷性质的重要信息。

**Q4.** 什么是 RED 方法，为什么这三个指标足以用于快速健康评估？
**答案：** RED 方法监控三个指标：**R** ate（每秒请求数）、**E** rrors（每秒失败请求数）和 **D** uration（响应时间分布）。它们足够，是因为它们覆盖了关于服务健康的三个基本问题：(1) Rate 告诉你服务是否正在接收和处理流量——下降意味着客户端可能无法到达它，或者请求在完成前失败。(2) Errors 告诉你请求是否成功——即使流量在流动，高错误率也意味着服务正在异常。(3) Duration 告诉你请求是否在可接受时间内完成——一个服务可以没有错误，但慢到无法使用。它们合在一起能检测出绝大多数生产问题。
