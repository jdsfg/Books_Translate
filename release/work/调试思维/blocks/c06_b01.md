你已经调试一个问题一个小时了。应用非常庞大——成千上万个文件，几十个服务，数百万行代码。bug 潜伏在这个巨大的生态系统中的某处，而每次你试图隔离它，复杂性都会把你淹没。移动部件太多，交互太多，可能原因太多。

现在想象你可以挥一挥魔杖，剥离所有无关内容——每个服务、每个模块、每一行不参与这个 bug 的代码。会剩下什么？也许 20 行。也许 5 行。也许只是一个带着错误参数的单一函数调用。那个仍然显示 bug 的、微小的、剥离后的版本——就是**最小可复现示例**，而创建它往往是理解并修复 bug 的最快路径。


### 6.1 什么是最小可复现示例？


#### 定义：最小可复现示例（MRE）

最小可复现示例（也称为 minimum working example、MVCE 或 reprex）是仍然能展示 bug 的最小可能代码、配置或系统设置。它_只_包含触发问题所必需的元素——不多一个。

用通俗的话说：剥离所有不是 bug 的东西。如果你能删除一行、一个文件、一个服务、一个配置选项，而 bug 仍然出现——就删掉它。当你无法再删除任何东西而不让 bug 消失时，你就得到了 MRE。

一个 MRE 有三个属性：

  1. **最小** ：它尽可能小。没有额外 imports，没有额外 functions，没有额外 services。剩下的每个元素都是必要的。
  2. **可复现** ：它稳定地产生 bug。别人可以按照你的设置看到同样的问题。
  3. **完整** ：它包含复现 bug 所需的一切。没有缺失依赖，没有默认上下文，没有“然后你还必须做另一件事”。


### 6.2 为什么 MRE 如此强大

MRE 是一种调试技术，但它也不止于此：它是一种_思维_技术。构建 MRE 的过程常常会_解决 bug_，因为简化迫使你面对每个组件，并追问“这是必要的吗？”

原因如下：

**简化揭示原因。** 当你剥离复杂层次时，bug 能躲藏的地方变少了。在一个 10,000 行应用中，bug 可能在任何地方。在一个 20 行 MRE 中，你可以读完每一行，并理解每一种交互。很多时候，当你完成 MRE 的构建时，原因已经显而易见。

**移除就是测试。** 每次你移除一个组件并检查 bug 是否仍然存在，你都在运行一次二分查找（第 5 章）——把那个组件排除为贡献因素。如果移除数据库连接不影响 bug，数据库就是无辜的。如果移除某个特定 import 让 bug 消失，那个 import 就参与其中。

**MRE 澄清你的思考。** 决定保留什么、移除什么的行为迫使你理解系统。“我需要这个 middleware 吗？它做什么？它可能相关吗？”这些问题就是调试问题——你正在详细层面调查系统行为。

**MRE 可共享。** 如果你自己无法解决 bug，MRE 是寻求帮助最有效的方式。它让别人无需理解你的整个代码库就能复现 bug。这就是为什么 StackOverflow 要求最小示例——这不是吹毛求疵，而是承认 MRE 是沟通 bug 的最高效格式。
