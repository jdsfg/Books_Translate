#### 应用题

**Q1.** 你正在构建一个系统，其中移动应用会向后端服务器发送位置数据。应用使用设备的 GPS，GPS 会报告纬度和经度。设计一个接口契约，以防止火星气候轨道器式的 bug。哪些假设可能出错？你会如何测试这个接口？

提示

思考：坐标格式（decimal degrees vs. degrees-minutes-seconds）、坐标顺序（lat/lng vs. lng/lat）、精度、有效范围，以及 datum（WGS84 vs. others）。

**答案：**

**接口契约：**
    
    
    Endpoint: POST /api/location
    Content-Type: application/json
    
    Body:
    {
      "latitude": <float>,   // 十进制度，WGS84 datum
                              // 有效范围：-90.0 to 90.0
      "longitude": <float>,  // 十进制度，WGS84 datum
                              // 有效范围：-180.0 to 180.0
      "accuracy": <float>,   // Meters, must be > 0
      "timestamp": <string>  // ISO 8601 format, UTC timezone
    }
    

**可能出错的假设：**

  1. **坐标顺序：** 有些系统使用 (latitude, longitude)，另一些使用 (longitude, latitude)。如果应用发送 (37.7749, -122.4194) 表示 San Francisco，而服务器把它解释为 (lat=-122.4194, lng=37.7749)，位置就是无效的/没有意义的。
  2. **单位：** GPS 芯片可能以 decimal degrees 或 degrees-minutes-seconds 报告。契约必须明确指定。
  3. **Datum：** GPS 使用 WGS84，但有些地图系统使用其他 geodetic datums。差异可能达到 tens of meters。
  4. **精度：** 37.77、37.7749、37.774929 这样的纬度——应保留多少小数位？
  5. **时间戳格式：** Unix timestamp（seconds since epoch）vs ISO 8601 string vs milliseconds since epoch。

**接口测试：**

  1. 发送已知坐标（例如 Eiffel Tower：48.8584, 2.2945），并验证服务器把点放在 Paris。
  2. 发送边界情况：(0, 0)——Gulf of Guinea 中的有效点；(90, 0)——North Pole；(-91, 0)——无效。
  3. 以错误顺序发送坐标，并验证服务器拒绝它们（latitude > 90 会被验证捕获）。
  4. 以错误格式发送 timestamp，并验证服务器拒绝它。

  1. **审计解析器：** 哪个库在处理 HTML？它是否仍在维护？是否有已知 CVE（Common Vulnerabilities and Exposures）？它如何处理畸形 HTML？
