#### 深入思考

**Q1.** 性能优化和代码清晰度常常存在张力。一个清晰、可读的实现可能是 O(n²)，而优化后的 O(n log n) 版本更难理解。你如何判断这种权衡是否值得？

**讨论：** 这个决定取决于几个因素：

**数据规模决定它是否重要。** 100 个元素上的 O(n²) 是 10,000 次操作——瞬间完成。1,000,000 个元素上的 O(n²) 是 1,000,000,000,000 次操作——不现实。要问：输入的真实最大规模是多少？如果它总是很小，可读性胜出。

**频率决定影响。** 一个每天调用一次的慢函数，和一个每秒调用 1,000 次的慢函数不同。优化热点路径；让冷路径保持可读。

**先做性能分析再决定。** 不要基于理论就用清晰度换速度。通过性能分析确认可读版本确实是瓶颈。如果是，就优化。如果不是，就保持可读。

**记录优化。** 当你确实以牺牲清晰度为代价做优化时，添加注释说明代码做什么、为什么需要这个优化（“性能分析显示该函数消耗了 80% 的请求时间”），以及清晰版本会是什么样。这能帮助未来维护者理解这种权衡。

**考虑抽象。** 有时你可以两者兼得：把优化版本实现到一个命名良好、输入输出清晰的函数内部。函数接口是可读的，即使实现本身比较复杂。

**Q2.** “最快的代码是不运行的代码。” 这个原则如何应用于性能调试？你能想到哪些例子，说明最佳优化是彻底消除工作，而不是让工作更快？

**讨论：** 消除工作几乎总是比让工作更快收益更大：

**缓存消除重复计算。** 如果你计算同一个结果 1,000 次，在第一次计算后缓存它，就完全消除了 999 次计算。没有任何算法优化能和根本不运行竞争。

**提前返回消除不必要处理。** 如果 80% 的请求可以从缓存回答，先检查缓存并立即返回，就会为这些请求消除所有下游处理。

**惰性求值消除过早计算。** 如果用户只看到前 20 个搜索结果，为什么要计算全部 10,000 个？按需计算结果。

**数据结构消除。** 与其解析一个 10MB JSON 响应来提取一个字段，不如使用只返回所需字段的 API。解析工作被消除了，而不是被优化了。

**功能移除。** 如果一个功能很少使用，但（从性能角度）维护成本高，完全移除它就是终极优化。这需要产品判断，而不只是工程判断。

这个原则延伸到代码之外：在业务流程优化中，最大收益来自消除步骤，而不是让每个步骤更快。
