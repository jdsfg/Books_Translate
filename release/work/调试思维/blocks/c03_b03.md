#### 定义：可得性启发

可得性启发是指根据例子浮现到脑海中的容易程度来判断事件可能性的倾向。最近的、生动的、或亲身经历过的事件会被过度加权；罕见或抽象的原因会被低估。

用直白的话说：你会怀疑最容易想到的东西，而那通常是你最近处理过的东西，或者你以前见过出错的东西。这会把你的调试偏向熟悉的原因，并远离新颖的原因。

可得性启发解释了几种常见的调试模式：

**“我刚改过那个！”** 即使 bug 报告描述的是一个长期存在的问题，你也会怀疑自己最近的改动。相关性（你最近改了 X，而且现在有 bug）不是因果关系。

**“我们以前见过这个。”** 模式匹配可能有用，但也可能误导。症状像你上个月修过的一个 bug，并不意味着原因相同。把模式匹配当作假设生成，而不是假设确认。

**“我从没见它失败过。”** 不够生动 = 不够可得 = 不太被怀疑。很少被讨论的组件里的 bug 会被忽视，因为它们不在你关于“哪些东西会出错”的心理目录中“可得”。


#### 常见误解

**“如果我刚改了某个东西，现在又出现了 bug，那大概就是我的改动造成的。”** 这通常是真的，而这正是可得性启发如此阴险的地方——它经常有效，足以强化自己。但“通常是真的”不是“永远是真的”。这个 bug 可能在你的改动之前就已经存在，只是因为有人碰巧测试了那个区域，现在才被注意到。或者你的改动可能暴露了一个预先存在的潜在 bug。始终验证因果联系；不要只是做假设。


#### 对策

  1. **检查时间线。** bug 实际上是什么时候开始的？使用日志、监控和版本历史（第 9 章）来确定 bug 是与你最近的改动相关，还是早于它们存在。

  2. **问“还有什么可能造成这个？”** 有意头脑风暴与你最近工作无关的原因。强迫自己考虑你没有碰过的组件。

  3. **让别人生成假设。** 今天处理过不同事情的同事会有不同的“可得”记忆，也会自然提出不同的嫌疑对象。这是结对调试有效的原因之一。


### 3.4 过早闭合——停止得太早

你发现了某个错误——配置文件里的一个拼写错误、一个缺失的 null 检查、一个不正确的 import。“找到了！”你喊道，修好它，然后继续前进。

但 bug 仍然存在。或者只部分改善。或者消失了又回来。因为你找到的东西不是根本原因——它是_一个_问题，也许甚至是一个促成因素，但不是_那个_问题。你过早地关闭了调查。
