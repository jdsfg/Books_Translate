### 2.6 实践中的循环：一次演练

我们来走完一次完整的调试会话，看看这个循环如何跨多个迭代发挥作用。

**缺陷报告：** “用户资料页显示了错误用户的数据。用户 Alice 登录后，看到了 Bob 的资料信息。”

**循环 1：**

* **观察：** 以 Alice 身份登录。资料页显示 Bob 的姓名、Bob 的电子邮箱、Bob 的头像。URL 是 `/profile/alice`。导航栏正确显示“Welcome, Alice”。所以认证系统知道这是 Alice，但资料数据是 Bob 的。
* **假设：** 资料页正在用错误的用户 ID 拉取数据——也许它被硬编码了，或者使用了一个陈旧变量。
* **预测：** 如果我检查资料页发出的 API 调用，请求中会包含错误的用户 ID。
* **测试：** 打开 Network 标签页，重新加载资料页。API 调用是 `GET /api/users/alice`。_请求_是正确的。
* **缩小范围：** 请求是对的，所以问题在响应中。这个缺陷在服务器端，而不是客户端。这把整个前端都从调查中排除了。

**循环 2：**

* **观察：** API 请求是 `GET /api/users/alice`，但返回的是 Bob 的数据。
* **假设：** 服务器端 API 处理器的数据库查询有缺陷——也许它没有正确使用 URL 参数。
* **预测：** 如果我直接调用 API（通过 curl），我会看到同样错误的数据。
* **测试：** `curl https://localhost:3000/api/users/alice`——正确返回 Alice 的数据！
* **缩小范围：** 直接调用时 API 工作正常。缺陷只通过浏览器表现出来。这非常有意思——它把问题缩小到浏览器请求的某些特定因素上。

**循环 3：**

* **观察：** curl 正常，浏览器不正常。差别在哪里？Headers、cookies、缓存……
* **假设：** 浏览器响应被缓存了——Alice 看到的是 Bob 之前登录时留下的缓存响应。
* **预测：** 如果我禁用缓存（强制刷新，或在 DevTools 中 Disable Cache），应该会看到 Alice 的正确数据。
* **测试：** 用 Ctrl+Shift+R 强制刷新。现在 Alice 的数据显示正确。
* **缩小范围：** 确认了——这是缓存问题。响应在缓存时没有考虑用户身份。

**循环 4：**

* **观察：** API 响应头显示 `Cache-Control: public, max-age=3600`。`public` 指令意味着缓存不会区分用户。
* **假设：** 服务器发送了不正确的缓存头——对于特定用户的数据，它应该是 `Cache-Control: private`。
* **预测：** 把 header 改成 `private` 应该能防止浏览器从另一个用户的会话中提供缓存数据。
* **测试：** 修改服务器的响应头为 `Cache-Control: private, no-cache`。用两个不同用户测试——每个人都看到自己的数据。
* **缩小范围：** 找到了根本原因，并验证了修复。

四个循环。每一个都显著缩小了搜索空间：

  1. 前端 → 已排除（问题在 API 响应）
  2. API 逻辑 → 已排除（curl 工作正常）
  3. 缓存 → 已确认
  4. 缓存头 → 具体修复

总耗时：也许 15 分钟。对比一下没有这个循环会发生什么：“嗯，数据错了……让我检查数据库查询……让我检查 React 组件……让我检查认证……让我检查路由……”——这种随机戳探可能会花上几个小时。
