#### 常见误解

**"真正的开发者不用 print 语句——他们用正规的调试器。"** 这是精英主义，不是工程建议。Print 语句和其他工具一样，也是一种工具。有时候它们就是最好的工具。当替代方案是在容器化生产服务上设置远程调试器（可能需要 30 分钟）时，添加一个 print 语句、重新部署并检查日志（需要 5 分钟）才是务实选择。使用能最快给你答案的工具。


### 10.3 结构化日志：可以扩展的 Print 语句

Print 语句的演进形态是结构化日志——用可解析格式（通常是 JSON）以及一致字段写日志。

非结构化日志：
    
    
    Processing order 1234 for user alice, total $99.99
    

结构化日志：
    
    
    {"timestamp": "2024-03-15T14:30:22Z", "level": "info", 
     "event": "order_processed", "order_id": 1234, 
     "user_id": "alice", "total": 99.99, "currency": "USD"}
    

结构化版本用人眼阅读更困难，但搜索、过滤和分析起来要容易得多：
    
    
    # Find all orders over $100
    jq 'select(.total > 100)' logs.json
    
    # Find all errors for user alice
    jq 'select(.user_id == "alice" and .level == "error")' logs.json
    
    # Count orders per hour
    jq -r '.timestamp[:13]' logs.json | sort | uniq -c
    


#### 日志最佳实践

**在边界处记录日志。** 最有用的日志点位于系统边界：请求到达时、数据库查询运行时、调用外部 API 时，以及响应发出时。这些边界是数据进入和离开代码的地方——也是反向追溯（第 8 章）的天然检查点。

**包含上下文。** 每条日志都应包含足够上下文，以便重建当时情况：请求 ID、用户 ID、相关实体 ID，以及关键参数值。一条写着"error processing request"的日志几乎没用。一条写着"error processing order 1234 for user alice: payment gateway timeout after 30s"的日志会告诉你一切。

**恰当使用日志级别。**

* `ERROR`: 某件事失败并需要关注。用户请求未被完成。
* `WARN`: 发生了意外情况但已被处理。系统恢复了。
* `INFO`: 值得记录的正常操作。请求已处理、任务已完成。
* `DEBUG`: 详细诊断信息。只在主动调试时启用。
**不要记录敏感数据。** 绝不要记录密码、信用卡号、个人健康信息或 API key。即使在 debug 日志中也不行。这些内容最终会进入日志聚合服务，而那里的访问控制可能比你的应用更宽松。
