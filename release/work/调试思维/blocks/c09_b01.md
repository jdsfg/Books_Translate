"昨天还好好的。"

这三个字是专业软件开发中最常见的调试起点。某个原本运行正常的东西——持续了几天、几周或几个月——突然坏了。你没有改任何东西。或者至少，你并不_认为_自己改过任何东西。

应对这种情况的技术是**版本对比**：系统地找出一个正常状态和一个故障状态之间发生了什么变化。它是把反向追溯（第 8 章）应用到时间维度上，而且它通常是通向根因的最快路径，因为它会大幅缩小搜索空间——你不必调查整个系统，只需要调查过去和现在之间有什么_不同_。


### 9.1 核心原则

#### 定义：版本对比

版本对比是一种调试技术，用来识别系统中一个已知正常状态和一个已知故障状态之间的差异。通过列出从"正常"到"故障"之间发生变化的一切，你可以把调查范围缩小到这些变化本身。

用直白的话说：如果它以前能工作而现在不能，那么一定有东西变了。找到这个变化，就找到缺陷。

这项技术之所以强大，是因为一个简单的逻辑事实：**如果什么都没有变，行为也就不会变。** 因此，导致行为改变的原因必然在发生变化的那些东西之中。你不需要搜索整个系统，只需要搜索这些变化。

当然，挑战在于：发生变化的东西比你意识到的更多。

### 9.2 五类变化

当某个东西意外坏掉时，变化几乎总是落在以下五类之一：


#### 1\. 代码变化

最显而易见的一类。有人改了源代码。用 `git diff` 和 `git log` 看看改了什么。
    
    
    # What changed since the last known-good state?
    git diff HEAD~10..HEAD
    git log --oneline HEAD~10..HEAD
    
    # What files changed?
    git diff --stat HEAD~10..HEAD
    

但要小心——相关变化未必在你的仓库里。它可能在一个共享库里、另一个团队拥有的微服务里，或者在一个子模块里。


#### 2\. 配置变化

代码相同，但某个配置值变了：功能开关被切换，环境变量被更新，配置文件被修改，或者云资源的设置被调整。

配置变化很隐蔽，因为它们往往不经过代码审查或版本控制。有人在管理后台改了一个值，于是系统的行为就不同了。

**需要检查什么：**
* 环境变量（`.env` 文件、云配置）
* 功能开关（LaunchDarkly、split.io，或自研方案）
* 存储在数据库中的配置
* 基础设施设置（负载均衡器规则、DNS、防火墙）
* 管理面板中最近切换过的开关


#### 3\. 数据变化

代码和配置都完全相同，但数据不同了。一个新用户用一个不寻常的名字注册了（包含特殊字符——还记得第 8 章的 Ampersand Bug（与号缺陷）吗？）。一个商品以 0.00 USD 的价格被添加。一次数据库迁移运行后，悄悄改变了模式。

**需要检查什么：**

* 最近的数据库迁移
* 与失败模式匹配的新数据或修改过的数据
* 数据导入或同步
* 最近运行过的数据清理脚本
