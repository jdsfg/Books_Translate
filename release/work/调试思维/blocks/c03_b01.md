你现在已经掌握了调试循环：观察、提出假设、预测、测试、缩小范围。理论上，遵循这个循环应该能让每一次调试都快速而富有成效。实践中，总有东西不断挡路。

那个东西就是你的大脑。

更准确地说，是你的大脑用来快速处理信息的心理捷径。这些捷径——称为**认知偏差**——通常是有帮助的。它们让你在日常生活中无需费力地从零开始分析每一种情境，就能快速做出决定。但在调试中，精确性很重要，而你的直觉又常常是错的，这些捷径就会变成陷阱。

本章讲的就是这些陷阱：它们是什么，如何破坏你的调试，以及你能如何应对它们。理解你自己的认知弱点，是抵御它们的第一道防线。


### 3.1 确认偏差——看见你想看见的东西

想象你正在调试一个很慢的 API 端点。你的第一个念头是：“我敢打赌是数据库查询。”你打开性能分析器，在许多指标中，你注意到数据库查询耗时 150ms。“啊哈！”你想。“我就知道。”

但你没有检查其他指标。JSON 序列化耗时 800ms。数据库没有问题——真正的瓶颈是序列化。你看见了自己正在寻找的东西，然后就停止寻找了。


#### 定义：确认偏差

确认偏差是指倾向于搜索、解释和记住那些证实你既有信念的信息，同时忽略或淡化与之矛盾的信息。

用直白的话说：一旦你有了一个理论，你的大脑就会变成那个理论的律师。它寻找“支持”的证据，驳回“反对”的证据。在调试中，这意味着一旦你怀疑某个原因，你就会无意识地过滤自己的观察结果，让它们支持这个怀疑。

下面是确认偏差在调试中的表现：

**选择性观察：** 你检查数据库日志（因为你怀疑数据库），却跳过应用日志（而应用日志会显示真正的问题）。你没有做到全面，因为你已经“决定”了。

**带偏见的解释：** 数据库查询耗时 150ms。这算慢吗？你其实不知道——但因为你怀疑数据库，所以你把它解释为“慢到足以成为问题”。如果你怀疑的是别的东西，你可能会看着同样的 150ms 然后想“这没问题”。

**过早停止：** 你找到某个_可能_是原因的东西，然后停止调查。“找到了！”但你还没有测试它实际上_是不是_原因。你找到的是嫌疑人，不是定罪判决。


#### 对策

  1. **主动寻求反证。** 对每一个假设，都明确地问：“什么证据能证明我是错的？”然后先去寻找那个证据。如果数据库是瓶颈，那么绕过它应该会让端点变快。会吗？

  2. **测试相反情况。** 不要只测试你的嫌疑对象是否有罪——也要测试它是否无辜。如果你认为数据库很慢，就检查移除数据库调用后端点是否很快。如果它仍然很慢，数据库就不是（主要）问题。

  3. **检查所有东西，而不只是你的嫌疑对象。** 在放大查看任何组件之前，先获得一个宽泛的概览。分析整个请求路径，而不只是你怀疑的部分。查看所有日志，而不只是那些你预期会有趣的日志。
