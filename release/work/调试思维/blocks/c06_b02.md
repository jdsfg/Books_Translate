### 6.3 构建最小可复现示例：减法方法

构建最小可复现示例有两种方法：

**自顶向下（减法）：** 从完整系统开始，一次移除一项内容，直到得到仍然存在缺陷的最小版本。

**自底向上（加法）：** 从零开始，一次添加一项内容，直到能够复现缺陷。

当缺陷位于现有系统中时，减法方法通常更快：

**步骤 1：** 复制一份项目（或创建一个分支）。接下来你会进行破坏性操作。

**步骤 2：** 移除你能想到的、看起来与缺陷无关的最大部分。删除整个模块，禁用一个服务，注释掉一大段代码。测试一下——缺陷还会发生吗？

* 如果会：那一部分无关。让它保持移除状态，然后继续。
* 如果不会：那一部分参与其中。把它放回去，再尝试移除其中更小的一块。

**步骤 3：** 重复这个过程，直到你无法在不让缺陷消失的情况下再移除任何内容。

**步骤 4：** 简化剩下的内容。用硬编码值替换复杂数据。用静态响应替换真实 API 调用。如果可能，把嵌套逻辑简化为平铺的顺序步骤。

来看一个例子：

> **缺陷：** 一个 API 端点在使用某些输入调用时返回 500 错误。

起点：一个完整的 Web 应用，包含 50 条路由、一个数据库、身份验证、日志记录、缓存和限流。

  1. 移除除失败路由之外的所有路由。缺陷还存在吗？是 → 排除了 49 条路由。
  2. 移除身份验证中间件。缺陷还存在吗？是 → 身份验证无关。
  3. 移除日志记录。缺陷还存在吗？是 → 日志记录无关。
  4. 移除缓存。缺陷还存在吗？否！→ 缓存参与其中。
  5. 把缓存放回去。移除限流。缺陷还存在吗？是 → 限流无关。
  6. 现在：一条路由 + 缓存。把路由简化到最小——用硬编码数据替换数据库查询。缺陷还存在吗？是 → 数据库无关。
  7. 简化缓存配置——使用默认值，而不是自定义设置。缺陷还存在吗？否！→ 自定义缓存设置才是原因。
  8. 最小可复现示例：一条路由 + 一个自定义缓存设置。缓存 TTL 被设置为 `0`，这会在缓存失效逻辑中导致除零错误。

七步。从一个 50 条路由的应用开始；最终得到一个 10 行复现示例。原因在完整系统中不可见，但在最小可复现示例中显而易见。


### 6.4 构建最小可复现示例：加法方法

当你怀疑某个特定组件，但不确定它如何与其他部分交互时，加法方法最有效：

**步骤 1：** 创建一个空白项目。真正的空白。

**步骤 2：** 添加触发缺陷所在区域所需的最少代码。只添加那个函数、那个 API 调用、那个组件。

**步骤 3：** 运行它。缺陷出现了吗？

* 如果出现：你已经找到了最小可复现示例。缺陷就在这个孤立组件中。
* 如果没有出现：缺陷还需要其他东西。添加下一个最可能的依赖。

**步骤 4：** 重复，直到缺陷出现。你最后添加的东西（至少部分）负有责任。

加法方法对涉及组件间交互的缺陷尤其有用。每次添加都让你可以问：“添加这个会让缺陷出现吗？”
